Chapter 2

Overview of the Patterns

در Chapter قبل دیدیم که Distributed کردن Data معمولاً ما را به دو مفهوم اساسی می‌رساند: Partitioning و Replication. در این Chapter نویسنده ابتدا روی Replication تمرکز می‌کند و با یک سناریوی ساده، Patternهای اصلی موردنیاز برای ساخت یک Distributed Data System قابل‌اعتماد را قدم‌به‌قدم کنار هم قرار می‌دهد.

مدل ذهنی Chapter

این فصل قرار نیست هر Pattern را با تمام جزئیات آموزش دهد. هدف اصلی این است که ببینیم Patternهایی مانند Write-Ahead Log، Leader and Followers، HeartBeat، Majority Quorum، Generation Clock و High-Water Mark چگونه برای حل مشکلات مختلف یک Cluster به یکدیگر وابسته می‌شوند.

Write-Ahead Log

راه‌حل این است که قبل از اعمال تغییر اصلی، اطلاعات Operation ابتدا در یک Log پایدار نوشته شود. این Pattern با نام Write-Ahead Log یا WAL شناخته می‌شود.

Request
→
Write-Ahead Log
→
Update Data

Log باید اطلاعات کافی برای Recovery داشته باشد. اگر Process بعد از Update کردن Boston Crash کند، هنگام Restart می‌توان با خواندن Log تشخیص داد Operation چه بوده و State را دوباره به وضعیت Consistent رساند.

اصل مهم

اگر چند Node از State یکسان شروع کنند و دقیقاً همان Log Entryها را با همان ترتیب اجرا کنند، در نهایت به State یکسان می‌رسند. همین ویژگی WAL را برای Replication نیز بسیار مهم می‌کند.

ارتباط با Database

Databaseها برای پیاده‌سازی Transaction و Recovery از ساختاری مشابه Write-Ahead Log استفاده می‌کنند. بنابراین این Pattern فقط مخصوص Distributed Systems نیست؛ قبل از Distribution هم برای Durability و Consistency اهمیت دارد.

Competing Updates

حالا سیستم را Distributed می‌کنیم. دو User هم‌زمان به دو Node متفاوت Request می‌فرستند.

User Request
Alice انتقال 30 Widget از Boston به London
Bob انتقال 40 Widget از Boston به Pune

مشکل اینجاست که Boston فقط 50 Widget دارد. اگر هر Node مستقل تصمیم بگیرد، هر دو Request ممکن است براساس مقدار 50 اجرا شوند.

Problem

وقتی چند Node اجازهٔ Update مستقل داشته باشند، Ordering درخواست‌های هم‌زمان مشخص نیست و Replicaها ممکن است به Stateهای متفاوت برسند.

حالا Leader یک نقطهٔ واحد برای Ordering Updateها دارد. مثلاً می‌تواند ابتدا Request Bob را اجرا کند.

چرا Leader مهم است؟

Leader باعث می‌شود Updateهای متعارض یک Ordering مشخص داشته باشند. اما در عوض یک سؤال بسیار مهم ایجاد می‌شود: اگر Leader Fail شود چه اتفاقی می‌افتد؟

فرض کنید Neptune که Leader است Request مربوط به Bob را دریافت کرده و شروع به Replicate کردن آن می‌کند.

Neptune موفق می‌شود Update را برای Jupiter ارسال کند، اما ارتباطش با Saturn قطع می‌شود. کمی بعد ارتباط Neptune با هر دو Follower از بین می‌رود.

Jupiter و Saturn هنوز با یکدیگر ارتباط دارند، اما دیگر به Leader دسترسی ندارند.

HeartBeat

مشکل اول این است که Nodeها چگونه بفهمند Leader دیگر در دسترس نیست؟

Leader نمی‌تواند پیامی بفرستد و بگوید: «ارتباط من قطع شده است»، چون دقیقاً خود ارتباط قطع شده است.

برای حل این مسئله Nodeها از HeartBeat استفاده می‌کنند.

Neptune
Leader
♥ ♥ ♥ →
Saturn

HeartBeat یک Message دوره‌ای است که نشان می‌دهد Node هنوز Alive و قابل دسترس است. البته لازم نیست همیشه Message جداگانه‌ای برای HeartBeat وجود داشته باشد؛ Communicationهای عادی سیستم نیز می‌توانند نقش HeartBeat را ایفا کنند.

اگر Saturn برای مدتی HeartBeat از Neptune دریافت نکند، Neptune را Down در نظر می‌گیرد.

نکتهٔ Distributed Systems

نرسیدن HeartBeat الزاماً ثابت نمی‌کند Process Crash کرده است. ممکن است Network قطع شده باشد یا Process Pause شده باشد. سیستم فقط می‌تواند براساس Timeout تصمیم بگیرد که Node دیگر قابل اعتماد نیست.

Replication با استفاده از Write-Ahead Log

حالا مشکل پیچیده‌تری داریم. فرض کنید Neptune دو Request دریافت کرده است:

  • B1 از Bob
  • A1 از Alice

هر دو Entry روی Jupiter Replicate شده‌اند، ولی Saturn هنوز آن‌ها را دریافت نکرده است. سپس Neptune Crash می‌کند.

Node Log
Jupiter B1, A1
Saturn Empty
Neptune B1, A1 — Crash

Jupiter و Saturn State یکسانی ندارند. اما چون تغییرات به‌صورت Log Entry ذخیره شده‌اند، می‌توان از Log برای همگام‌سازی استفاده کرد.

Jupiter

→

→

اگر Logهای Nodeها قابل مقایسه باشند، Node عقب‌مانده می‌تواند Entryهای Missing را دریافت کند و به State جدید برسد.

Multiple Failures Need a Generation Clock

مقایسهٔ سادهٔ Log Index همیشه کافی نیست. چند Failure پشت سر هم می‌تواند باعث شود دو Node در یک Index یکسان، Entryهای متفاوت داشته باشند.

سناریوی Failure

Neptune در حالی که Leader است Request مربوط به Bob را در Log Index شماره 1 ثبت می‌کند: 

Index: 1
Entry: B1

اما قبل از Replication Crash می‌کند.

سپس Jupiter Leader جدید می‌شود و Request مربوط به Alice را در همان Index ثبت می‌کند: 

Index: 1
Entry: A1

Jupiter نیز قبل از Replication Crash می‌کند.

وقتی هر دو Node دوباره بالا بیایند ممکن است وضعیت چنین باشد:

Node Index Entry
Neptune 1 B1
Jupiter 1 A1

فقط نگاه کردن به Index دیگر کافی نیست. هر دو Entry دارای Index شماره 1 هستند.

Generation Clock

راه‌حل این است که هر Leadership یک Generation داشته باشد. با هر Leader Election مقدار Generation افزایش پیدا می‌کند.

بنابراین در صورت Conflict، Entry مربوط به Generation جدیدتر قابل تشخیص است.

Generation فقط برای Conflict نیست

Generation همچنین مانع فعالیت یک Leader قدیمی می‌شود. اگر Leader قدیمی پس از Network Partition دوباره برگردد، Nodeها می‌توانند Requestهای متعلق به Generation قدیمی‌تر را Reject کنند.

Old Leader Problem

فرض کنید Neptune در Generation 1 Leader بوده، اما فقط به دلیل Network Partition از Cluster جدا شده است.

Jupiter و Saturn تصور می‌کنند Neptune Fail شده و Jupiter را با Generation 2 به عنوان Leader انتخاب می‌کنند.

Neptune

وقتی Neptune دوباره متصل شود، Requestهای Generation 1 دیگر پذیرفته نمی‌شوند.

مدل ذهنی

فقط دانستن اینکه «چه کسی Leader است» کافی نیست. Nodeها باید بدانند «این Leader متعلق به کدام دورهٔ Leadership است».

Log Entries Cannot Be Committed until They Are Accepted by a Majority Quorum

تا اینجا دیدیم Entryهایی که فقط روی Leader نوشته شده‌اند ممکن است پس از Failure از بین بروند یا توسط Leader جدید Overwrite شوند.

بنابراین Leader نباید صرفاً بعد از نوشتن Entry در Log خودش آن را Commit شده در نظر بگیرد.

Majority Quorum

یک Log Entry زمانی Commit می‌شود که توسط Majority از Nodeهای Cluster پذیرفته شده باشد.

Cluster سه Node

تعداد Nodeها: 3

Majority: 2

بنابراین Leader + حداقل یک Follower برای رسیدن به Quorum کافی است.

Bob
B1
→
Neptune
Leader
→
Jupiter
Ack

وقتی Neptune خودش Entry را دارد و Jupiter نیز آن را پذیرفته است: 

Accepted Nodes = 2
Cluster Nodes  = 3

2 / 3 = Majority Quorum

حالا Neptune می‌تواند B1 را Commit کند.

Committed vs Uncommitted

State Meaning
Uncommitted Entry در Log وجود دارد، اما هنوز Majority آن را تأیید نکرده است.
Committed Entry توسط Majority پذیرفته شده و دیگر نباید در اثر Leader Failure از بین برود.
چرا Majority مهم است؟

Leader Election نیز برای معتبر بودن نیازمند مشارکت Majority Cluster است. از آنجا که هر Entry Commit شده نیز روی Majority قرار دارد، هر Majority جدیدی حداقل با بخشی از Majority قبلی Intersection خواهد داشت. بنابراین Commitهای معتبر گم نمی‌شوند.

Leader Crash بعد از Commit

فرض کنید Neptune:

  1. B1 را در Log خودش ذخیره می‌کند.
  2. B1 را روی Saturn Replicate می‌کند.
  3. Saturn پاسخ OK می‌دهد.
  4. Majority Quorum حاصل می‌شود.
  5. Neptune Crash می‌کند.

B1 همچنان روی Saturn وجود دارد. Leader جدید باید قبل از پذیرش Updateهای تازه، Commitهای معتبر قبلی را حفظ کند.

ارتباط با Raft

کتاب اشاره می‌کند که Raft برای Leader Election تلاش می‌کند Nodeای را انتخاب کند که Log به‌روزتری دارد. این کار از انتقال و مقایسهٔ کامل Logهای بزرگ در زمان Election جلوگیری می‌کند.

Followers Commit Based on a High-Water Mark

Leader می‌داند چه زمانی Majority Quorum حاصل شده است، چون Acknowledgmentهای Followerها را دریافت می‌کند. اما سؤال بعدی این است:

Problem

Follower از کجا بفهمد کدام Log Entry واقعاً Commit شده است؟

در Cluster سه Node ممکن است موضوع ساده به نظر برسد، اما در Cluster بزرگ‌تر این‌طور نیست.

مثلاً در یک Cluster پنج Node: 

Leader + 1 Follower = 2 Nodes

Majority of 5 = 3 Nodes

بنابراین صرف دریافت یک Entry از Leader برای Follower ثابت نمی‌کند آن Entry Commit شده است.

High-Water Mark

Leader یک مقدار به نام High-Water Mark نگهداری می‌کند.

این مقدار برابر Index آخرین Log Entry است که Commit شدن آن قطعی شده است.

Log 1
✓
Log 2
✓
Log 3
✓
Log 4

Commit شده‌اند، اما Entry شماره 4 هنوز Uncommitted است.

انتقال High-Water Mark به Followerها

Leader مقدار High-Water Mark را در HeartBeat برای Followerها ارسال می‌کند.

High-Water Mark = 3

می‌داند تمام Log Entryهای خودش تا Index شماره 3 قابل Commit هستند.

نکتهٔ بسیار مهم

Log داشتن به تنهایی کافی نیست. سیستم باید بتواند تشخیص دهد کدام بخش Log واقعاً Commit شده و کدام بخش فقط روی بعضی Nodeها نوشته شده است. High-Water Mark همین مرز را مشخص می‌کند.

است.

چرا این موضوع در Payment مهم است؟

اگر سیستم به Client پاسخ Success بدهد ولی اطلاعات Payment فقط روی Nodeای ذخیره شده باشد که بلافاصله Crash می‌کند، ممکن است پس از Failover آن Payment ناپدید شود. Consensus و Quorum تلاش می‌کنند مانع چنین وضعیتی شوند.

جمع‌بندی Chapter تا بخش موجود در فایل

  • Write-Ahead Log تغییرات را قبل از اعمال نهایی در یک Log پایدار ثبت می‌کند.
  • Leader and Followers Ordering Updateها را با متمرکز کردن تصمیم Write روی Leader ساده‌تر می‌کند.
  • HeartBeat برای تشخیص Nodeهایی استفاده می‌شود که دیگر قابل دسترس به نظر نمی‌رسند.
  • در صورت Failure Leader باید Leader Election انجام شود.
  • Generation Clock دوره‌های مختلف Leadership را از یکدیگر متمایز می‌کند.
  • Generation مانع پذیرفته شدن Requestهای یک Leader قدیمی پس از انتخاب Leader جدید می‌شود.
  • یک Log Entry قبل از رسیدن به Majority Quorum نباید Commit شده در نظر گرفته شود.
  • Majority Quorum کمک می‌کند Commitهای معتبر پس از Leader Failure نیز در Cluster باقی بمانند.
  • High-Water Mark Index آخرین Entry قطعاً Commit شده را مشخص می‌کند.
  • Leader می‌تواند High-Water Mark را همراه HeartBeat به Followerها منتقل کند.
  • Followerها با استفاده از High-Water Mark تشخیص می‌دهند کدام Log Entryها را می‌توانند روی State خود اعمال کنند.
  • Leader قدیمی پس از بازگشت باید Generation جدید را بپذیرد و Entryهای Uncommitted متعارض خود را کنار بگذارد.
مهم‌ترین پیام Chapter

یک Distributed System قابل‌اعتماد معمولاً با یک Pattern ساخته نمی‌شود. Reliability حاصل همکاری چند Pattern است: Log برای Recovery، Leader برای Ordering، HeartBeat برای Failure Detection، Generation برای تشخیص Leadership، Quorum برای Commit و High-Water Mark برای مشخص کردن مرز State معتبر.
