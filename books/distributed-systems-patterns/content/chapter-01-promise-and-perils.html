فرض کنید یک فروشگاه اینترنتی روی یک Server اجرا می‌شود. کاربران کالا جست‌وجو می‌کنند، آن را به سبد خرید اضافه می‌کنند، سفارش می‌سازند و سوابق سفارش را می‌بینند. تا وقتی تعداد درخواست‌ها کم است همه‌چیز ساده به نظر می‌رسد؛ اما هر Server سقف فیزیکی دارد و رشد بار کاری دیر یا زود ما را به آن سقف می‌رساند.

مدل ذهنی Chapter

Distribution قدرت پردازش و ظرفیت داده را افزایش می‌دهد، اما هم‌زمان Failure و Coordination را به بخشی از طراحی نرم‌افزار تبدیل می‌کند.

The Limits of a Single Server

هر محاسبه روی چهار منبع فیزیکی تکیه دارد. ظرفیت نهایی یک Server را منبعی تعیین می‌کند که زودتر از بقیه به سقف برسد؛ به این منبع محدودکننده معمولاً Bottleneck می‌گوییم.

Network

حجم داده‌ای که در یک بازهٔ زمانی می‌تواند وارد یا خارج شود.

Disk

سرعت Read و Write که به الگوی Sequential یا Random و استفاده از Cache وابسته است.

CPU

توان اجرای منطق برنامه، Serialization، Encryption و Query processing.

Memory

فضای لازم برای داده‌های فعال، Cache، Buffer و اجرای Processها.

مثال قابل‌محاسبه

یک اتصال 1 Gbps تقریباً 125 MB/s ظرفیت خام دارد.

اگر اندازهٔ هر Record برابر 1 KB باشد، سقف نظری نزدیک به 125,000 request/s است.

اگر همان Record به 5 KB برسد، سقف نظری به حدود 25,000 request/s کاهش پیدا می‌کند.

این عددها سقف نظری‌اند؛ Protocol overhead، Response، Retry و سایر پردازش‌ها ظرفیت واقعی را کمتر می‌کنند. نکتهٔ اصلی این است که بزرگ‌تر شدن هر Request بدون تغییر Bandwidth، تعداد Request قابل‌انتقال را کاهش می‌دهد.

چرا افزایش Request همیشه Throughput را بیشتر نمی‌کند؟

تا پیش از اشباع منابع، Server می‌تواند با افزایش بار، کار بیشتری انجام دهد. بعد از اشباع، Requestهای تازه وارد Queue می‌شوند. Queue طولانی‌تر یعنی زمان انتظار و Latency بیشتر؛ اگر فشار ادامه پیدا کند، Timeout و Retry نیز بار مضاعفی می‌سازند و Throughput مؤثر ممکن است افت کند.

A Look at Failures

در یک ماشین، احتمال Failure ممکن است کوچک به نظر برسد. اما Cluster تعداد زیادی Disk، Network link، Process و Power unit دارد. زیاد شدن Componentها یعنی Failure از یک اتفاق نادر به یک رویداد عادی عملیاتی تبدیل می‌شود.

اثر مقیاس روی احتمال Failure

اگر احتمال خرابی هر Disk در یک روز 1 / 1000 باشد، برای یک Disk نگرانی روزانه کوچک است. اما در مجموعه‌ای شامل 1000 Disk، انتظار مشاهدهٔ تقریباً یک خرابی در روز منطقی می‌شود.

آمارهای عملیاتی Data Centerها نشان می‌دهند Failure فقط خرابی Disk نیست. دامنهٔ مشکل از یک Process تا Rack، Network و Power گسترش دارد:

جایگزین کردن یک Stateless API Server معمولاً ساده است، چون State اختصاصی روی آن نگهداری نمی‌شود. جایگزین کردن Data Node دشوارتر است: نمونهٔ تازه باید State صحیح داشته باشد و با سایر Nodeها هماهنگ شود تا دادهٔ Stale یا نادرست به کاربر نشان ندهد.

Replication: Masking Failures

Replication یعنی نگهداری Copyهای هماهنگ از داده روی چند ماشین. اگر یک Node در دسترس نباشد، Client می‌تواند از Replica دیگری سرویس بگیرد. هدف فقط داشتن Copy نیست؛ نرم‌افزار باید Failure را تشخیص دهد و نگذارد Inconsistency به رفتار قابل‌مشاهده برای کاربر تبدیل شود.

Process Crash

Process ممکن است به‌دلیل Hardware failure یا Exception متوقف و دوباره اجرا شود. داده‌ای که پیش‌تر با پاسخ موفق تأیید شده باید بعد از Restart همچنان موجود باشد.

Network Delay

TCP/IP سقف قطعی برای زمان تحویل Message نمی‌دهد. نرسیدن Response الزاماً به معنی خراب بودن Node نیست؛ ممکن است فقط Network کند باشد.

Process Pause

یک Process ممکن است برای Garbage Collection یا فشار سیستم Pause شود. اگر پس از اعلام Failure دوباره فعال شود، Messageهای دیررس آن باید با احتیاط پردازش شوند.

Unsynchronized Clocks

Clock ماشین‌ها دقیقاً برابر نیست و Network failure می‌تواند NTP synchronization را مختل کند. بنابراین Ordering داده را نمی‌توان صرفاً به System timestamp سپرد.

ابهام بنیادی

از دید یک Process، «Node خراب شده»، «Network کند است» و «Process مقصد Pause شده» ممکن است همگی فقط به شکل «Response نرسید» دیده شوند. بسیاری از پیچیدگی‌های Distributed Systems از همین ابهام آغاز می‌شوند.

Defining the Term “Distributed Systems”

Distributed System یک Software architecture متشکل از چند Node متصل به Network است که برای رسیدن به هدفی مشترک با یکدیگر Communication و Coordination انجام می‌دهند و در بیرون مانند یک سیستم واحد دیده می‌شوند.

Distribution سه وعدهٔ مهم دارد:

  • تقسیم Workload و اجرای Parallel برای افزایش ظرفیت پردازش؛
  • مدیریت حجم زیاد داده و تعداد بالای کاربر هم‌زمان؛
  • دستیابی به Fault Tolerance و Resilience با توزیع Service و Replication داده.

در مقابل، این مزایا رایگان نیستند. Network نامطمئن، Partial failure، Clock skew و نیاز به Coordination هزینه‌هایی هستند که Design باید آشکارا مدیریت کند.

The Patterns Approach

یک Pattern نامی مشخص برای یک مسئلهٔ تکرارشونده در Context معین و ساختار یک Solution تجربه‌شده است. Pattern صرفاً ایدهٔ جذاب یا نام تازه نیست؛ باید در چند Implementation مستقل مشاهده شده باشد. معیار رایج Rule of Three می‌گوید پیش از Pattern نامیدن یک Solution، بهتر است دست‌کم در سه سیستم دیده شده باشد.

ارزش رویکرد Pattern در این است که فاصلهٔ میان Theory و Code را کم می‌کند. نام مشترک Pattern باعث می‌شود اعضای تیم دربارهٔ Design دقیق‌تر گفتگو کنند و جزئیات آن را در Codebaseهای واقعی تشخیص دهند.

Patternهای این کتاب از مطالعهٔ سیستم‌های Open Source واقعی مانند Apache Kafka، Apache Cassandra، MongoDB، Apache Pulsar، etcd، Apache ZooKeeper، CockroachDB، YugabyteDB، Akka و JGroups استخراج شده‌اند.

Patternها مستقل از هم نیستند

در یک Distributed System واقعی، چند Pattern کنار هم قرار می‌گیرند. برای نمونه، Replicated Log به Leader election، Majority Quorum، Generation Clock و High-Water Mark وابسته می‌شود. فهم رابطهٔ Patternها از حفظ تعریف جداگانهٔ آن‌ها مهم‌تر است.

جمع‌بندی Chapter

  • یک Server به Network، Disk، CPU و Memory محدود است.
  • Stateless compute را می‌توان ساده‌تر Scale و جایگزین کرد؛ Stateful data نیازمند Coordination است.
  • Partitioning ظرفیت را افزایش می‌دهد، اما تعداد نقاط Failure را نیز بیشتر می‌کند.
  • Replication برای Availability ضروری است، ولی تشخیص Failure و حفظ Consistency را پیچیده می‌کند.
  • Process Crash، Network Delay، Process Pause و Unsynchronized Clocks باید جزئی از مدل طراحی باشند.
  • Patterns زبان مشترکی برای Solutionهای تکرارشونده و اثبات‌شده در Codebaseهای واقعی فراهم می‌کنند.
