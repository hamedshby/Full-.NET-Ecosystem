بخش ۱

CI/CD چیست؟

فرض کنید تغییری در پروژهٔ .NET داده‌اید. بعد از git push، به جای اجرای دستی Restore، Build و Test، یک فرایند تعریف‌شده این مراحل را اجرا می‌کند و نتیجه را نشان می‌دهد. CI/CD برای خودکارسازی فرایند اعتبارسنجی و تحویل نرم‌افزار استفاده می‌شود.

مسیر کلی تغییر کدFlow
Developer → git push → GitLab Pipeline
                         ├─ Restore
                         ├─ Build
                         ├─ Test
                         ├─ Publish / Package
                         └─ Deploy

CI یا Continuous Integration

تغییرات مرتب در کد مشترک ادغام می‌شوند و سیستم با بررسی‌هایی مثل Restore، Build و Test، ناسالم‌بودن تغییر را زود تشخیص می‌دهد. Pipeline باید برای رویدادهایی مثل Push یا Merge Request تنظیم شده باشد.

دستورهای پایهٔ CICLI
dotnet restore
dotnet build
dotnet test

CD یا Continuous Delivery / Deployment

تفاوت دو روش تحویل
مفهومرفتار
Continuous Deliveryنسخه مراحل بررسی را گذرانده و آمادهٔ انتشار است. ورود به Production می‌تواند به تأیید دستی نیاز داشته باشد.
Continuous Deploymentنسخه‌ای که تمام کنترل‌ها را با موفقیت گذرانده است به صورت خودکار به Production می‌رود.

بخش ۲

Pipeline، Stage و Job

برای فهم فایل .gitlab-ci.yml ابتدا سه لایه را بشناسیم: کل فرایند، مراحل منطقی و کارهای اجرایی.

ساختار GitLab CI
مفهوممعنی
Pipelineکل فرایند CI/CD از شروع تا پایان.
Stageمرحله‌ای منطقی مثل build، test یا deploy.
Jobیک کار مشخص داخل Stage که دستورهای آن اجرا می‌شوند.
تعریف Stageها و دو JobYAML
stages:
  - build
  - test
  - deploy

build-job:
  stage: build
  script:
    - dotnet build

unit-test:
  stage: test
  script:
    - dotnet test

دو Job در یک Stage، با ظرفیت Runner کافی و نبود وابستگی محدودکننده، می‌توانند موازی اجرا شوند؛ مثلاً Unit Test و Integration Test در Stage مربوط به test.

اجرای موازی تست‌هاFlow
          ┌─ Unit Test ─────────┐
Build ────┤                    ├─ Deploy
          └─ Integration Test ─┘

بخش ۳

Fail Fast

وقتی مرحلهٔ ضروری شکست می‌خورد، ادامهٔ انتشار نتیجهٔ ناسالم منطقی نیست. Fail Fast یعنی خطا را زود تشخیص دهیم و مراحل وابسته را بدون دلیل ادامه ندهیم؛ معمولاً اگر Test شکست بخورد، Deploy نباید انجام شود.

نتیجهٔ یک Pipeline ناموفقResult
Build              OK
Unit Test          OK
Integration Test   FAILED
Deploy             SKIPPED

این رفتار به تنظیمات Pipeline وابسته است. Jobهای معمولی پس از موفقیت مراحل قبلی اجرا می‌شوند؛ تنظیماتی مثل allow_failure یا when می‌توانند این رفتار را تغییر دهند.

بخش ۴

GitLab Runner

GitLab کارها را مدیریت و زمان‌بندی می‌کند، اما Runner Agentی است که Jobها را واقعاً اجرا می‌کند؛ برای مثال دستور dotnet build در محیط اجرای آن انجام می‌شود.

چه کسی دستورها را اجرا می‌کند؟Flow
GitLab → Runner → dotnet restore
                 → dotnet build
                 → dotnet test

Runner می‌تواند روی Server یا VM نصب باشد و بسته به Executor، Job را در Shell، Docker Container یا Kubernetes Pod اجرا کند. اگر ابزار موردنیاز در محیط Job نباشد، دستور شکست می‌خورد؛ مثلاً بدون .NET SDK، اجرای dotnet build ممکن نیست.

بخش ۵

Docker Image برای محیط Job

برای محیطی قابل‌تکرار، می‌توان Image موردنیاز Job را مشخص کرد. در این مثال محیط از قبل .NET SDK دارد.

محیط اجرای BuildYAML
build:
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet restore
    - dotnet build
پیش‌نیاز اجرای مثالکلید image باید توسط Executor پشتیبانی شود؛ مثل Docker یا Kubernetes. Shell Executor با این کلید خودبه‌خود Container نمی‌سازد. این مثال فقط انتخاب محیط Job است؛ ساخت Docker Image برنامه هنوز در ادامهٔ مسیر قرار دارد.

بخش ۶

تفاوت dotnet build و dotnet publish

Compile کردن یا آماده‌کردن خروجی انتشار؟
دستورکاربرد
dotnet buildپروژه را Compile می‌کند و خطاهای Build را مشخص می‌کند.
dotnet publishخروجی مناسب اجرا و Deploy، شامل برنامه و فایل‌های موردنیاز آن را آماده می‌کند.

dotnet publish به صورت پیش‌فرض Restore و Build هم انجام می‌دهد. برای جلوگیری از کار تکراری می‌توان از گزینه‌های مربوط استفاده کرد، اما فقط وقتی فایل‌های موردنیاز از قبل در همان محیط وجود دارند.

دستورهای یک اجرای محلی متوالیCLI
dotnet restore
dotnet build -c Release --no-restore
dotnet test -c Release --no-build
dotnet publish MyApi/MyApi.csproj -c Release -o publish
مرز بین Jobهااین توالی در یک محیط مشترک معنا دارد. Jobهای جدا معمولاً Workspace مستقل دارند؛ --no-build فقط وقتی مناسب است که خروجی Build در Job تست موجود باشد. صرفاً تمام‌شدن Job قبلی آن فایل‌ها را منتقل نمی‌کند.

نام Stage قراردادی است. اجرای Publish در Stageی به نام build ممکن است، ولی جداکردن مراحل build، test و publish خوانایی فرایند را بهتر می‌کند.

بخش ۷

Artifact

Artifact خروجی ذخیره‌شدهٔ یک Job است که کاربر یا Job بعدی می‌تواند آن را دریافت کند. مثلاً پوشهٔ publish/ می‌تواند خروجی قابل Deploy باشد.

نگهداری خروجی PublishYAML
build:
  stage: build
  script:
    - dotnet publish MyApi/MyApi.csproj -c Release -o publish
  artifacts:
    paths:
      - publish/

مسیر Artifact نسبت به پوشهٔ پروژهٔ Job تعریف می‌شود. Build output، فایل‌های Publish و نتیجهٔ Test از نمونه‌های رایج Artifact هستند. فرمان Publish فایل‌ها را می‌سازد و بخش artifacts نگهداری آن‌ها در GitLab را مشخص می‌کند.

بخش ۸

تفاوت Cache و Artifact

Cache برای کاهش کار تکراری است؛ مثلاً استفادهٔ دوباره از Packageهای دانلودشدهٔ NuGet می‌تواند Restore را سریع‌تر کند. Artifact برای نگه‌داشتن خروجی یک Job است.

دو هدف متفاوت
ArtifactCache
خروجی یک Job برای استفادهٔ بعدی.کاهش دانلود یا محاسبات تکراری.
مثال: publish/ یا test-results/.مثال: پوشهٔ Packageهای NuGet.
برای انتقال خروجی لازم به Job بعدی طراحی می‌شود.برای سرعت است و نباید تنها راه رسیدن به فایل ضروری باشد.

در این مرحله مفهوم Cache معرفی شده است. تنظیم عملی آن در GitLab هنوز در فهرست ادامهٔ یادگیری قرار دارد.

بخش ۹

expire_in برای Artifact

با expire_in مدت نگهداری Artifact را مشخص می‌کنیم. در مثال زیر، زمان نگهداری دو روز است.

مدت نگهداری خروجیYAML
artifacts:
  paths:
    - publish/
  expire_in: 2 days

مقدارهایی مثل 3 hours و 1 week هم قابل استفاده‌اند. پس از پایان مدت، Artifact واجد حذف می‌شود؛ تنظیم نگهداری Artifact آخرین Pipeline موفق می‌تواند باعث باقی‌ماندن آن شود.

بخش ۱۰

rules

با rules مشخص می‌کنیم Job با چه شرطی وارد Pipeline شود و چه ویژگی‌هایی بگیرد. نمونهٔ ساده، محدودکردن Job انتشار به Branch اصلی است.

Job فقط روی mainYAML
deploy:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

در Branch دیگر این شرط برقرار نیست و Job اضافه نمی‌شود. قواعد فقط برای Branch نیستند؛ می‌توان شرط‌های Tag یا Merge Request را هم تعریف کرد. بررسی پیشرفتهٔ آن‌ها در ادامه انجام می‌شود.

دستور echo در این مثال فقط نمایش پیام است و برنامه‌ای را Deploy نمی‌کند.

بخش ۱۱

when: manual

وقتی اجرای Job باید با اقدام کاربر شروع شود، از when: manual استفاده می‌کنیم؛ مثلاً برای تأیید انتشار در Production.

انتشار با اقدام دستیYAML
deploy-production:
  stage: deploy
  script:
    - echo "Deploy to production"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  when: manual

rules مشخص می‌کند Job تحت چه شرطی در Pipeline حضور داشته باشد؛ when: manual مشخص می‌کند اجرا به اقدام دستی نیاز دارد.

دستی‌بودن با مسدودکردن Pipeline متفاوت استوقتی when: manual بیرون rules نوشته شود، Job به صورت پیش‌فرض اختیاری است. برای اینکه Pipeline منتظر اجرای موفق آن بماند، allow_failure: false را مشخص کنید. نمونهٔ جمع‌بندی این تنظیم را صریح دارد.

بخش ۱۲

needs

needs وابستگی مستقیم بین Jobها را مشخص می‌کند. یک Job پس از پایان موفق Jobهای موردنیازش می‌تواند شروع شود، حتی اگر Jobهای نامرتبط Stage قبلی هنوز تمام نشده باشند.

وابستگی تست به BuildYAML
build:
  stage: build
  script:
    - dotnet build

test:
  stage: test
  needs:
    - build
  script:
    - dotnet test
ترتیب کلی یا وابستگی مستقیم؟
stagesneeds
ترتیب کلی مراحل را تعریف می‌کند.وابستگی مستقیم Jobها را تعریف می‌کند.
به صورت پیش‌فرض اجرای Stage به Stage می‌سازد.می‌تواند شروع Job را بدون انتظار برای کل Stage قبلی ممکن کند.

Artifact داده و خروجی را نگه می‌دارد؛ needs وابستگی و زمان‌بندی را تعریف می‌کند و می‌تواند دریافت Artifact از Jobهای موردنیاز را هم کنترل کند. بدون ذخیرهٔ Artifact در Job قبلی، needs خروجی Buildی برای دریافت ایجاد نمی‌کند.

بخش ۱۳

allow_failure

گاهی شکست یک بررسی نباید کل Pipeline را متوقف کند. با allow_failure: true اجازه می‌دهیم Pipeline با وجود شکست آن Job ادامه پیدا کند.

نمونهٔ مفهومی بررسی اختیاریYAML
security-scan:
  stage: test
  script:
    - run-security-scan
  allow_failure: true

run-security-scan نام نمونه است؛ در پروژهٔ واقعی باید ابزار اسکن و دستور آن موجود باشند. این تنظیم فقط وقتی مناسب است که سیاست تیم اجازهٔ ادامه پس از شکست آن بررسی را بدهد. برای Test یا بررسی حیاتی، بدون دلیل از آن استفاده نکنید.

بخش ۱۴

before_script و after_script

before_script

دستورهای before_script پیش از script اصلی Job اجرا می‌شوند و برای آماده‌سازی محیط مناسب‌اند.

آماده‌سازی محیطYAML
build:
  stage: build
  before_script:
    - echo "Preparing environment"
    - dotnet --info
  script:
    - dotnet restore
    - dotnet build

after_script

دستورهای after_script بعد از script برای پاک‌سازی یا جمع‌کردن Logها مناسب‌اند. در شکست معمول script نیز اجرا می‌شوند؛ اجرای آن‌ها در تمام انواع شکست یا Timeout تضمین‌شده نیست.

پاک‌سازی در محیط Linux JobYAML
test:
  stage: test
  script:
    - dotnet test
  after_script:
    - echo "Cleaning temporary files"
    - rm -rf temp/
ترتیب مراحل JobFlow
before_script → script → after_script

after_script در Shell جداگانه اجرا می‌شود؛ متغیرهایی که فقط در script با export ساخته‌اید، الزاماً در آن موجود نیستند. پاک‌سازی در این مثال محدود به پوشهٔ موقت همان Job است.

بخش ۱۵

extends و Template مشترک

وقتی چند Job تنظیمات یکسان دارند، آن‌ها را در یک Template قرار می‌دهیم و با extends دوباره استفاده می‌کنیم. نامی که با نقطه آغاز می‌شود یک Hidden Job است و خودش به عنوان Job اجرایی اجرا نمی‌شود.

اشتراک تنظیمات .NETYAML
.common-dotnet:
  image: mcr.microsoft.com/dotnet/sdk:8.0
  before_script:
    - dotnet --info

build:
  extends: .common-dotnet
  stage: build
  script:
    - dotnet build

test:
  extends: .common-dotnet
  stage: test
  script:
    - dotnet test

هر دو Job از Image و before_script مشترک استفاده می‌کنند، ولی script خودشان را دارند. این کار از تکرار تنظیمات جلوگیری می‌کند.

بخش ۱۶

include

اگر .gitlab-ci.yml بزرگ شود، می‌توان تنظیمات را بین چند فایل YAML تقسیم کرد و با include آن‌ها را به تنظیمات Pipeline اضافه کرد.

فایل اصلی .gitlab-ci.ymlYAML
include:
  - local: 'ci/build.yml'
  - local: 'ci/test.yml'
  - local: 'ci/deploy.yml'
ساختار فایل‌هاFiles
.gitlab-ci.yml
ci/
  build.yml
  test.yml
  deploy.yml

فایل‌های local باید در همان Repository و Ref وجود داشته باشند. extends برای اشتراک تنظیمات میان Jobهاست؛ include برای ترکیب فایل‌های تنظیمات است. این دو می‌توانند در یک Pipeline کنار هم استفاده شوند.

بخش ۱۷

CI/CD Variables و Secretها

مقدارهایی مثل Password، Token و Connection String را مستقیم در فایل YAML ننویسید. آن‌ها را در تنظیمات CI/CD Variables پروژه تعریف کنید و در Job از نام Variable استفاده کنید.

استفاده از نام Variable بدون چاپ مقدارYAML
check-configuration:
  stage: test
  script:
    - test -n "$DB_PASSWORD"

این نمونهٔ Shell فقط بررسی می‌کند مقدار خالی نباشد؛ اگر مقدار خالی باشد Job شکست می‌خورد. در اجرای واقعی، برنامه یا ابزار مقصد Variable را می‌خواند. برای نمایش مفهوم، Secret را با echo چاپ نمی‌کنیم.

دو تنظیم مستقل
تنظیممعنی
Masked VariableGitLab تلاش می‌کند مقدار Variable را هنگام ظاهرشدن در Log پنهان کند.
Protected Variableدسترسی به Variable را به Pipelineهای مجاز Refهای Protected محدود می‌کند.

برای Secretهای Production معمولاً هر دو تنظیم لازم‌اند. Masking جایگزین خودداری از چاپ Secret یا بررسی script نیست؛ تغییر شکل مقدار یا دستور مخرب می‌تواند آن را افشا کند.

بخش ۱۸

Environment در CI/CD

Environment مقصد اجرای نسخهٔ برنامه است. نام‌گذاری محیط به GitLab کمک می‌کند Deploymentهای مربوط به آن را ثبت و نمایش دهد.

محیط‌های رایج
Environmentکاربرد
Developmentتوسعه و تست اولیه.
Stagingبررسی نسخه پیش از انتشار نهایی.
Productionمحیط واقعی کاربران.
نام‌گذاری مقصد DeployYAML
deploy-staging:
  stage: deploy
  script:
    - echo "Deploy to staging"
  environment:
    name: staging

deploy-production:
  stage: deploy
  script:
    - echo "Deploy to production"
  environment:
    name: production

کلید environment به‌تنهایی فایل‌ها را روی Server منتقل نمی‌کند. در این مثال script فقط پیام چاپ می‌کند؛ Deploy واقعی باید با دستور مناسب محیط مقصد پیاده‌سازی شود.

بخش ۱۹

Environment-specific Variables

یک نام Variable می‌تواند برای محیط‌های مختلف مقدار متفاوت داشته باشد. مثلاً API_URL در Staging و Production به آدرس یکسان اشاره نمی‌کند.

یک نام و دو مقدار متناسب با محیطExample
API_URL
  staging    → https://staging.example.com
  production → https://api.example.com

در تنظیمات GitLab، Variableها را با Environment Scope مناسب تعریف می‌کنیم. Jobی که environment.name آن staging است، مقدار منطبق با staging را دریافت می‌کند و script می‌تواند همچنان از نام ثابت $API_URL استفاده کند.

این تنظیم جدا از Masked و Protected است: Scope محیط مناسب را انتخاب می‌کند، Masked مربوط به Log است و Protected مربوط به Refهای مجاز است.

بخش ۲۰

Flow مفهومی کامل تا اینجا

حالا اجزای معرفی‌شده را کنار هم بگذاریم. تغییر کد وارد Repository می‌شود، Pipeline آن را بررسی می‌کند، خروجی انتشار تولید می‌شود و در نهایت یک Job انتشار می‌تواند نسخه را به محیط مقصد ببرد.

مسیر مفهومی از Push تا محیط مقصدFlow
Developer → git push → GitLab Repository
                              ↓
                           Pipeline
                              ├─ Restore
                              ├─ Build
                              ├─ Test
                              ├─ Publish → Artifact
                              ├─ Docker / Package step
                              └─ Deploy to Environment
                                  ├─ Development
                                  ├─ Staging
                                  └─ Production

این شکل، جای Docker و Deploy را در مسیر نشان می‌دهد. ساخت عملی Image، ارسال به Registry و انتشار واقعی هنوز در ادامهٔ مطالعه هستند.

بخش ۲۱

نمونهٔ جمع‌بندی Pipeline

این نمونهٔ آموزشی، Stageها، Template مشترک، needs، Artifact و انتشار دستی روی main را کنار هم نشان می‌دهد. برای اجرا باید Repository شامل Solution و پروژهٔ MyApi/MyApi.csproj باشد و Runner از Image پشتیبانی کند.

.gitlab-ci.ymlYAML
stages:
  - build
  - test
  - publish
  - deploy

.common-dotnet:
  image: mcr.microsoft.com/dotnet/sdk:8.0
  before_script:
    - dotnet --info

build:
  extends: .common-dotnet
  stage: build
  script:
    - dotnet restore
    - dotnet build -c Release --no-restore

test:
  extends: .common-dotnet
  stage: test
  needs:
    - build
  script:
    - dotnet test -c Release

publish:
  extends: .common-dotnet
  stage: publish
  needs:
    - test
  script:
    - dotnet publish MyApi/MyApi.csproj -c Release -o publish
  artifacts:
    paths:
      - publish/
    expire_in: 2 days

deploy-production:
  extends: .common-dotnet
  stage: deploy
  needs:
    - publish
  script:
    - echo "Deploy to production"
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  when: manual
  allow_failure: false

این نمونه چه نتیجه‌ای دارد؟

اگر Build یا Test شکست بخورد، مسیر انتشار جلو نمی‌رود. Publish پوشهٔ خروجی را می‌سازد و به عنوان Artifact ذخیره می‌کند. Job آخر فقط روی main ظاهر می‌شود و منتظر اجرای دستی می‌ماند؛ script آن فعلاً فقط پیام چاپ می‌کند.

اصلاح اجرایی نمونهٔ جزوهدر جزوه، Job تست از --no-build استفاده می‌کند، ولی خروجی Build را به Job تست منتقل نمی‌کند. اینجا Test در محیط خودش Build می‌کند تا به فایل‌های Job قبلی وابسته نباشد. بهینه‌سازی با انتقال خروجی و Artifact در ادامه بررسی می‌شود. تنظیم allow_failure: false نیز انتظار برای Job دستی را صریح می‌کند.

ساخت Docker Image، Push به Registry و Deploy واقعی در این YAML وجود ندارند؛ این نمونه جمع‌بندی نقطهٔ فعلی مطالعه است.

پاسخ‌های کوتاه برای مرور و مصاحبه

Runner چه کاری می‌کند؟
Job را در محیط اجرایی مناسب اجرا می‌کند و نتیجه را به GitLab گزارش می‌دهد.
Artifact چه تفاوتی با Cache دارد؟
Artifact خروجی یک Job را نگه می‌دارد؛ Cache برای کاهش کار تکراری مثل دانلود NuGet Packageهاست.
Stage و Job چه تفاوتی دارند؟
Stage یک مرحلهٔ منطقی است؛ Job کار واقعی داخل آن مرحله است. چند Job در یک Stage می‌توانند با ظرفیت Runner کافی موازی اجرا شوند.
rules و when: manual چه تفاوتی دارند؟
rules شرایط حضور و ویژگی‌های Job را تعریف می‌کند؛ when: manual اجرای آن را به اقدام کاربر وابسته می‌کند.
needs چه چیزی را مشخص می‌کند؟
وابستگی مستقیم یک Job به Jobهای دیگر را تعریف می‌کند؛ خودش خروجی Build تولید یا ذخیره نمی‌کند.
build و publish چه تفاوتی دارند؟
Build کد را Compile می‌کند؛ Publish خروجی مناسب اجرا و انتشار را آماده می‌کند.
Masked و Protected چه تفاوتی دارند؟
Masked به پنهان‌سازی مقدار در Log مربوط است؛ Protected به محدودکردن دسترسی بر اساس Refهای مجاز مربوط است.
