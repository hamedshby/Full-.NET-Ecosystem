Conditional Operator ?: چه زمانی از if مناسب‌تر است؟

پاسخ کوتاه مصاحبه‌ای

عملگر شرطی ?: یا Conditional Operator زمانی از if/else مناسب‌تر است که بخواهیم بر اساس یک شرط، یکی از دو مقدار را انتخاب کنیم و منطق کوتاه و خوانا باشد. اگر هر Branch شامل چند دستور، Side Effect، شرط‌های پیچیده یا چند سطح Ternary باشد، if/else معمولاً خواناتر و قابل نگهداری‌تر است.

مدل ذهنی خیلی ساده

به ?: به چشم یک «انتخاب‌کننده مقدار» نگاه کنید:

Pattern
condition ? valueIfTrue : valueIfFalse

یعنی: اگر شرط درست بود این مقدار را بده، در غیر این صورت آن مقدار را بده.

مثلاً:

C#
int age = 20;

string result = age >= 18
    ? "Adult"
    : "Minor";

اگر age >= 18 درست باشد، مقدار "Adult" انتخاب می‌شود؛ در غیر این صورت "Minor".

همین مثال با if/else

C#
string result;

if (age >= 18)
{
    result = "Adult";
}
else
{
    result = "Minor";
}

هر دو کد یک هدف دارند، اما وقتی فقط می‌خواهیم یک مقدار را انتخاب کنیم، نسخه Conditional Operator کوتاه‌تر است:

C#
string result = age >= 18
    ? "Adult"
    : "Minor";

این یکی از بهترین سناریوها برای استفاده از ?: است: یک شرط ساده، دو مقدار ساده و یک Assignment.

ساختار ?: را مرحله‌به‌مرحله بخوانیم

C#
bool isActive = true;

string status = isActive ? "Active" : "Inactive";

این Expression سه قسمت دارد:

  1. isActive → شرط
  2. "Active" → مقدار در صورت true بودن شرط
  3. "Inactive" → مقدار در صورت false بودن شرط

علامت ? بخش true و علامت : بخش false را جدا می‌کند.

چرا به آن Operator می‌گوییم، نه Statement؟

نکته مهم این است که Conditional Operator یک Expression تولید می‌کند؛ یعنی خودش یک مقدار دارد.

به همین دلیل می‌توانیم نتیجه آن را مستقیماً داخل Assignment قرار دهیم:

C#
decimal discount = isVip ? 0.20m : 0.05m;

یا مستقیماً Return کنیم:

C#
public string GetStatus(bool isActive)
{
    return isActive ? "Active" : "Inactive";
}

چه زمانی ?: انتخاب خیلی خوبی است؟

۱. انتخاب یک مقدار ساده

C#
string access = isAdmin
    ? "Full Access"
    : "Limited Access";

۲. مقداردهی یک متغیر

C#
decimal fee = amount > 1_000_000
    ? 10_000
    : 5_000;

۳. Return کردن یک مقدار ساده

C#
public bool CanWithdraw(Account account)
{
    return account.IsActive
        ? account.Balance > 0
        : false;
}

البته در مثال آخر می‌توان منطق را حتی ساده‌تر هم کرد:

C#
return account.IsActive && account.Balance > 0;

هدف استفاده از Ternary کوتاه کردن کد به هر قیمتی نیست؛ هدف این است که Intent کد واضح‌تر شود.

مثال واقعی در Backend

فرض کنید وضعیت Transaction را برای Response تبدیل می‌کنیم:

C#
string statusText = transaction.IsSuccessful
    ? "Successful"
    : "Failed";

این کد خیلی واضح است: بر اساس یک Boolean، یکی از دو مقدار را انتخاب کن.

در چنین سناریویی نوشتن یک بلوک کامل if/else معمولاً اطلاعات بیشتری به خواننده نمی‌دهد.

آیا هر دو طرف ?: اجرا می‌شوند؟

خیر. ابتدا شرط ارزیابی می‌شود و بعد فقط یکی از دو Expression اجرا می‌شود.

C#
string result = isValid
    ? GetSuccessMessage()
    : GetErrorMessage();

اگر isValid برابر true باشد فقط GetSuccessMessage() اجرا می‌شود. اگر false باشد فقط GetErrorMessage() اجرا می‌شود.

چه زمانی if/else بهتر است؟

اگر Branchها فقط «یک مقدار» نیستند و قرار است چند کار انجام دهند، if/else معمولاً انتخاب بهتری است.

C#
if (payment.IsSuccessful)
{
    SaveTransaction();
    PublishPaymentCompletedEvent();
    SendNotification();
}
else
{
    LogFailure();
    UpdateRetryCount();
}

اینجا هدف اجرای مجموعه‌ای از دستورها است، نه انتخاب ساده یک مقدار. پس تلاش برای تبدیل چنین منطقی به Ternary خوانایی را خراب می‌کند.

قاعده ساده: Value Selection یا Control Flow؟

نیاز انتخاب مناسب‌تر
انتخاب یکی از دو مقدار ساده ?:
Assignment ساده بر اساس شرط ?:
Return ساده بر اساس شرط ?:
اجرای چند Statement if/else
Branchهای پیچیده if/else
چند شرط مستقل و مراحل مختلف if/else یا ساختار مناسب‌تر

مشکل Nested Ternary چیست؟

یکی از اشتباهات رایج این است که چون Ternary کوتاه است، چند Ternary را داخل هم قرار دهیم.

C#
string result = score >= 90
    ? "A"
    : score >= 80
        ? "B"
        : score >= 70
            ? "C"
            : "D";

این کد قابل اجراست، اما خواندن آن سخت‌تر شده است. برای یک شرط کوچک مشکلی نیست، ولی با زیاد شدن Branchها بهتر است سراغ ساختار خواناتری برویم.

نسخه خواناتر با if/else

C#
string result;

if (score >= 90)
{
    result = "A";
}
else if (score >= 80)
{
    result = "B";
}
else if (score >= 70)
{
    result = "C";
}
else
{
    result = "D";
}

طولانی‌تر است، اما مسیر تصمیم‌گیری برای بسیاری از خوانندگان واضح‌تر است.

گاهی switch expression حتی بهتر است

در C# مدرن، اگر چند حالت داریم، به جای Nested Ternary می‌توانیم از switch expression استفاده کنیم:

C#
string result = score switch
{
    >= 90 => "A",
    >= 80 => "B",
    >= 70 => "C",
    _     => "D"
};

برای دو انتخاب ساده، Ternary عالی است. برای چند حالت، Switch Expression اغلب Intent را بهتر نشان می‌دهد.

مثال بد: Ternary فقط برای کوتاه کردن کد

C#
var result = user != null
    ? user.IsActive
        ? user.HasPermission
            ? "Allowed"
            : "No Permission"
        : "Inactive"
    : "User Not Found";

ممکن است تعداد خطوط کم باشد، اما خواننده باید چند سطح شرط را در ذهن نگه دارد. این نوع کد در Code Review معمولاً کاندید مناسبی برای ساده‌سازی است.

نسخه خواناتر

C#
if (user is null)
    return "User Not Found";

if (!user.IsActive)
    return "Inactive";

if (!user.HasPermission)
    return "No Permission";

return "Allowed";

اینجا از Guard Clause استفاده کرده‌ایم و هر شرط به صورت مستقل قابل فهم است.

Ternary و Side Effect

بهتر است Branchهای Conditional Operator تا جای ممکن Expressionهای ساده باشند. کدی که عملیات مهم Business را داخل Ternary پنهان کند معمولاً سخت‌تر خوانده می‌شود.

C#
var result = isSuccessful
    ? SaveAndPublish()
    : LogAndRetry();

این کد الزاماً اشتباه نیست، اما اگر هر Method عملیات مهم و چندمرحله‌ای دارد، یک if/else می‌تواند Intent اجرای دو مسیر را واضح‌تر نشان دهد.

آیا ?: از if سریع‌تر است؟

نباید بین ?: و if/else صرفاً بر اساس تصور Performance انتخاب کنیم. Compiler و JIT می‌توانند کد را بهینه کنند و شکل نهایی به Expression و Runtime بستگی دارد.

در کد معمول Application، معیار اصلی باید خوانایی، سادگی و بیان Intent باشد. اگر Performance واقعاً مهم است باید Benchmark و Profiling انجام شود.

آیا ?: فقط برای string و int است؟

خیر. می‌توانیم برای انتخاب Objectها و انواع دیگر نیز از آن استفاده کنیم، به شرط اینکه Type نتیجه قابل تعیین باشد.

C#
PaymentHandler handler = isInternational
    ? internationalHandler
    : domesticHandler;

اینجا بر اساس شرط، یکی از دو Handler انتخاب می‌شود.

مثال با null

C#
string displayName = user != null
    ? user.Name
    : "Guest";

این کد درست است، اما برای چنین سناریویی ممکن است ابزارهای مخصوص null خواناتر باشند:

C#
string displayName = user?.Name ?? "Guest";

پس قبل از استفاده از Ternary بررسی کنید آیا Operator تخصصی‌تر و واضح‌تری برای مسئله وجود دارد یا نه.

جدول مقایسه ?: و if/else

ویژگی ?: if/else
نوع ساختار Expression Statement
تولید مستقیم مقدار بله خیر، معمولاً Assignment/Return داخل Branch
دو انتخاب ساده عالی ممکن است طولانی‌تر باشد
چند Statement در Branch نامناسب مناسب
Nested Condition زیاد سریعاً سخت‌خوان می‌شود معمولاً خواناتر
هدف اصلی انتخاب مقدار کنترل جریان برنامه

اشتباهات رایج

  • اشتباه: Ternary همیشه از if بهتر است چون کوتاه‌تر است.
    درست: کوتاهی کد لزوماً به معنی خوانایی بیشتر نیست.
  • اشتباه: برای هر تعداد شرط می‌توان Nested Ternary نوشت.
    درست: بعد از پیچیده شدن منطق، if/else، Guard Clause یا switch expression معمولاً مناسب‌تر است.
  • اشتباه: ?: فقط شکل کوتاه if است و هیچ تفاوت مفهومی ندارد.
    درست: Conditional Operator یک Expression است و مقدار تولید می‌کند.
  • اشتباه: Ternary را باید برای Performance انتخاب کرد.
    درست: در کد معمول معیار اصلی خوانایی است؛ Performance باید اندازه‌گیری شود.

جزئیات عمیق‌تر برای سطح Senior

Conditional Operator در C# یک Expression است و Compiler باید Type نتیجه آن را از Operandهای دوم و سوم تعیین کند. در نسخه‌های جدید C# قابلیت‌های Type Inference و Target Typing در برخی سناریوها باعث می‌شوند Expressionهای Conditional با Type مقصد بهتر تطبیق داده شوند.

از دید طراحی کد، نکته مهم‌تر این است که Ternary باید Value-oriented باقی بماند. وقتی Branchها تبدیل به Workflow، Side Effect یا Decision Tree می‌شوند، استفاده از ساختارهایی مثل Guard Clause، Pattern Matching یا Switch Expression معمولاً Domain Intent را بهتر منتقل می‌کند.

در پروژه واقعی چه قاعده‌ای داشته باشیم؟

یک Rule of Thumb ساده:

  • یک شرط + دو مقدار ساده → ?:
  • چند Statement یا Side Effect واضح → if/else
  • چند حالت مبتنی بر یک مقدار → switch expression
  • شرط‌های خروج زودهنگام → Guard Clause

هدف این نیست که کمترین تعداد Line را بنویسیم؛ هدف این است که برنامه‌نویس بعدی سریع‌تر Intent کد را بفهمد.

اگر مصاحبه‌کننده فقط در ۲۰ ثانیه جواب بخواهد

می‌توانید بگویید:

«Conditional Operator یا ?: زمانی مناسب‌تر از if/else است که بر اساس یک شرط ساده بخواهیم یکی از دو مقدار را انتخاب کنیم، مثلاً برای Assignment یا Return. چون ?: یک Expression است، نتیجه را مستقیماً تولید می‌کند. اگر Branchها چند دستور، Side Effect یا Nested Conditionهای پیچیده داشته باشند، if/else معمولاً خواناتر است.»

جواب پیشنهادی کامل برای مصاحبه

«Conditional Operator با Syntax شرط ? مقدارTrue : مقدارFalse یک Expression است و یکی از دو مقدار را بر اساس نتیجه شرط تولید می‌کند. من زمانی از آن استفاده می‌کنم که شرط و هر دو Branch ساده باشند، مخصوصاً برای Assignment یا Return کردن یک مقدار. مثلاً status = isActive ? "Active" : "Inactive". اگر منطق هر Branch چند Statement داشته باشد، Side Effect مهم داشته باشیم یا چند Ternary داخل هم قرار بگیرند، if/else، Guard Clause یا switch expression معمولاً خواناتر و قابل نگهداری‌تر هستند. بنابراین انتخاب من بر اساس خوانایی و Intent کد است، نه صرفاً کوتاه‌تر شدن تعداد خطوط.»

چیزی که باید از این سؤال یادت بماند

این جمله را حفظ کنید: ?: برای انتخاب ساده یک مقدار است؛ if/else برای کنترل جریان پیچیده‌تر. اگر Ternary باعث شد برای فهم کد چند ثانیه بیشتر فکر کنید، احتمالاً وقت آن است که آن را ساده‌تر کنید.
