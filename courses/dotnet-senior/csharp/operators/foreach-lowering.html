یک حلقه foreach چگونه ترجمه و اجرا می‌شود؟

پاسخ کوتاه مصاحبه‌ای

foreach در C# یک Syntax سطح‌بالا برای پیمایش عناصر است. Compiler بر اساس Type مجموعه آن را به الگوی مناسب پیمایش تبدیل می‌کند. در حالت عمومی، مجموعه یک Enumerator می‌دهد؛ سپس با MoveNext() به عنصر بعدی می‌رویم و با Current عنصر فعلی را می‌خوانیم. اگر Enumerator نیاز به Dispose داشته باشد، Compiler پاک‌سازی آن را هم تضمین می‌کند. اما نکته مهم این است که ترجمه دقیق foreach همیشه یکسان نیست؛ برای Array و بعضی Typeهای خاص Compiler می‌تواند شکل بهینه‌تری تولید کند.

مدل ذهنی خیلی ساده

وقتی می‌نویسیم:

C#
foreach (var item in items)
{
    Console.WriteLine(item);
}

ذهنی آن را تقریباً این‌طور بخوانید:

  1. یک وسیله برای پیمایش مجموعه بگیر.
  2. بپرس: «عنصر بعدی وجود دارد؟»
  3. اگر بله، عنصر فعلی را بگیر.
  4. بدنه حلقه را اجرا کن.
  5. دوباره برو مرحله ۲.
  6. در پایان منابع Enumerator را در صورت نیاز آزاد کن.

Enumerator چیست؟

Enumerator را می‌توانید مثل یک Cursor یا اشاره‌گر پیمایش در نظر بگیرید که موقعیت فعلی ما را هنگام حرکت روی Collection نگه می‌دارد.

Concept
Collection:
[10] [20] [30] [40]

Enumerator:
  ↓
[10] [20] [30] [40]

MoveNext()
       ↓
[10] [20] [30] [40]

Enumerator خودش Collection نیست؛ ابزاری است که می‌داند در چه مرحله‌ای از پیمایش Collection قرار داریم.

سه عضو اصلی در مدل کلاسیک پیمایش

برای فهم foreach این سه مفهوم بسیار مهم‌اند:

  • GetEnumerator() → Enumerator را می‌گیرد.
  • MoveNext() → تلاش می‌کند Enumerator را به عنصر بعدی ببرد و مشخص می‌کند آیا عنصر دیگری وجود دارد.
  • Current → عنصر فعلی را برمی‌گرداند.

یک foreach ساده

C#
var numbers = new List<int>
{
    10, 20, 30
};

foreach (var number in numbers)
{
    Console.WriteLine(number);
}

در ظاهر فقط چند خط کد داریم، ولی Compiler مکانیزم پیمایش Collection را برای ما مدیریت می‌کند.

شکل مفهومی ترجمه foreach

برای یک Collection معمولی، مدل ذهنی نزدیک به این است:

Conceptual C# 
var enumerator = numbers.GetEnumerator();

try
{
    while (enumerator.MoveNext())
    {
        var number = enumerator.Current;
        Console.WriteLine(number);
    }
}
finally
{
    enumerator.Dispose();
}

این کد برای فهم مفهوم است، نه اینکه Compiler در همه Typeها دقیقاً همین Source Code را تولید کند. Lowering واقعی به Type مجموعه و Enumerator بستگی دارد.

MoveNext دقیقاً چه می‌کند؟

هر بار که MoveNext() صدا زده می‌شود، Enumerator تلاش می‌کند به عنصر بعدی حرکت کند. اگر موفق شود true و اگر دیگر عنصری باقی نمانده باشد false برمی‌گرداند.

Concept
MoveNext() → true   Current = 10
MoveNext() → true   Current = 20
MoveNext() → true   Current = 30
MoveNext() → false  پایان حلقه

Current چه زمانی خوانده می‌شود؟

فقط بعد از اینکه MoveNext() اعلام کرد عنصر معتبری وجود دارد:

C#
while (enumerator.MoveNext())
{
    var current = enumerator.Current;

    // body of foreach
}

پس متغیر حلقه مثل number در هر Iteration از Current عنصر فعلی ساخته می‌شود.

IEnumerable<T> و IEnumerator<T> چه نقشی دارند؟

مدل رایج Generic در .NET تقریباً این رابطه را دارد:

C#
public interface IEnumerable<T>
{
    IEnumerator<T> GetEnumerator();
}

public interface IEnumerator<T> : IDisposable
{
    T Current { get; }
    bool MoveNext();
    void Reset();
}

این نمایش برای درک قرارداد اصلی مفید است. در BCL جزئیات Interfaceها و Inheritance آن‌ها بیشتر از این نسخه ساده‌شده است.

IEnumerable و IEnumerator را با هم اشتباه نکنیم

مفهوم وظیفه
IEnumerable<T> چیزی که قابلیت تولید Enumerator برای پیمایش را دارد
IEnumerator<T> خود شیء/مقداری که وضعیت پیمایش فعلی را نگه می‌دارد

خیلی ساده: IEnumerable می‌گوید «من قابل پیمایشم»؛ IEnumerator عملیات پیمایش را انجام می‌دهد.

چرا try/finally در ترجمه foreach مهم است؟

Enumerator ممکن است Resource یا Stateای داشته باشد که باید بعد از پایان پیمایش آزاد شود. به همین دلیل foreach در صورت نیاز Dispose شدن Enumerator را تضمین می‌کند؛ حتی اگر داخل حلقه Exception رخ دهد یا با break خارج شویم.

C#
foreach (var item in items)
{
    if (item.IsInvalid)
        break;
}

خروج زودهنگام از حلقه نباید Cleanup لازم Enumerator را از بین ببرد.

آیا foreach حتماً به IEnumerable<T> نیاز دارد؟

خیر؛ این یک نکته مهم مصاحبه‌ای است.

C# از یک Pattern برای foreach پشتیبانی می‌کند. اگر Type متد مناسب GetEnumerator() داشته باشد و Enumerator آن اعضای لازم مثل MoveNext() و Current را فراهم کند، در سناریوهای معتبر می‌توان بدون Implement کردن مستقیم IEnumerable<T> نیز از foreach استفاده کرد.

Interfaceها قرارداد استاندارد و بسیار رایج .NET هستند، ولی مفهوم foreach فقط به نام Interface محدود نیست.

یک Enumerator سفارشی چه شکلی دارد؟

برای فهم Pattern، یک نمونه آموزشی بسیار ساده:

C#
public class NumberCollection
{
    public Enumerator GetEnumerator() => new();

    public struct Enumerator
    {
        private int _current;

        public int Current => _current;

        public bool MoveNext()
        {
            if (_current >= 3)
                return false;

            _current++;
            return true;
        }
    }
}

حالا می‌توانیم بنویسیم:

C#
var numbers = new NumberCollection();

foreach (var number in numbers)
{
    Console.WriteLine(number);
}

خروجی:

Output
1
2
3

foreach روی Array چه می‌شود؟

Array یک مورد مهم است. Compiler برای Arrayها می‌تواند پیمایش را به شکل مستقیم و بهینه انجام دهد و لازم نیست مدل ذهنی «Enumerator Interface» را عیناً برای آن فرض کنیم.

C#
int[] numbers = { 10, 20, 30 };

foreach (var number in numbers)
{
    Console.WriteLine(number);
}

از نظر مفهومی برای یک Array یک‌بعدی می‌توان آن را نزدیک به پیمایش Index-based تصور کرد:

Conceptual C# 
for (int i = 0; i < numbers.Length; i++)
{
    int number = numbers[i];
    Console.WriteLine(number);
}

پس جواب «foreach همیشه GetEnumerator را صدا می‌زند» جواب دقیقی برای مصاحبه نیست.

foreach روی List<T> چطور؟

List<T> یک Enumerator اختصاصی دارد. وقتی Type واقعی List برای Compiler مشخص باشد، می‌تواند از همان Enumerator مشخص استفاده کند.

C#
List<int> numbers = new() { 10, 20, 30 };

foreach (int number in numbers)
{
    Console.WriteLine(number);
}

Enumerator مربوط به List یک Value Type است. در مسیر معمولی پیمایش مستقیم List، این موضوع می‌تواند از Allocation مربوط به یک Enumerator کلاس جلوگیری کند؛ اما جزئیات Allocation به Type استاتیک و نحوه استفاده بستگی دارد.

Boxing Enumerator چه زمانی ممکن است مهم شود؟

اگر یک Struct Enumerator از طریق یک Interface استفاده شود، در برخی مسیرها Boxing می‌تواند رخ دهد. به همین دلیل بین پیمایش یک Type concrete و پیمایش همان داده از طریق یک Interface ممکن است جزئیات اجرایی متفاوت باشد.

برای کد Business معمولاً نباید بدون Profiling روی این Micro-Optimization تمرکز کنیم، اما برای سؤال Senior دانستن این تفاوت ارزشمند است.

چرا هنگام foreach معمولاً Collection را تغییر نمی‌دهیم؟

C#
var numbers = new List<int> { 1, 2, 3, 4 };

foreach (var number in numbers)
{
    if (number == 2)
        numbers.Remove(number);
}

برای Collectionهایی مثل List<T>، تغییر ساختاری Collection هنگام پیمایش معمولاً Enumerator را نامعتبر می‌کند و در ادامه پیمایش InvalidOperationException رخ می‌دهد.

چرا Enumerator متوجه تغییر List می‌شود؟

Collectionهایی مثل List یک Version داخلی از وضعیت ساختاری خود نگه می‌دارند. Enumerator هنگام ساخته شدن Version مربوط را ثبت می‌کند. اگر Collection به شکلی تغییر کند که Version عوض شود، Enumerator می‌تواند تشخیص دهد Collection دیگر همان ساختاری نیست که پیمایش با آن شروع شده بود.

Concept
List version       = 5
Enumerator version = 5

Remove(...)

List version       = 6
Enumerator version = 5

MoveNext() → collection was modified

اگر بخواهیم هنگام پیمایش حذف کنیم چه کنیم؟

بسته به مسئله روش‌های مختلفی وجود دارد. مثلاً برای حذف بر اساس شرط از List:

C#
numbers.RemoveAll(x => x % 2 == 0);

یا در سناریوهایی که کنترل Index لازم است، می‌توان با دقت از حلقه for از انتها به ابتدا استفاده کرد:

C#
for (int i = numbers.Count - 1; i >= 0; i--)
{
    if (numbers[i] % 2 == 0)
        numbers.RemoveAt(i);
}

foreach یا for؟

نیاز انتخاب معمول
فقط می‌خواهم همه عناصر را بخوانم foreach
خود Index برای من مهم است for
حرکت با Step خاص یا از انتها به ابتدا for
پیمایش عمومی IEnumerable foreach
تغییر ساختاری Collection حین پیمایش بسته به Collection و مسئله، روش مناسب دیگری

آیا for همیشه از foreach سریع‌تر است؟

خیر. این یک باور قدیمی و بیش از حد کلی است.

Performance به Type مجموعه، نسخه Runtime، شکل کد و Optimizationهای JIT بستگی دارد. برای Array و List، foreach می‌تواند بسیار کارآمد باشد. در کد عادی، اول خوانایی و Intent را در نظر بگیرید؛ اگر مسیر واقعاً Performance-sensitive است، Benchmark بگیرید.

foreach و IEnumerable چه ارتباطی با LINQ دارند؟

بخش بزرگی از LINQ بر پایه مفهوم IEnumerable<T> و پیمایش Lazy ساخته شده است. مثلاً:

C#
var query = numbers.Where(x => x > 10);

foreach (var number in query)
{
    Console.WriteLine(number);
}

در بسیاری از LINQ-to-Objects Queryها، ساخت Query لزوماً همان لحظه همه عناصر را پردازش نمی‌کند. اجرای واقعی هنگام Enumeration، مثلاً با foreach، اتفاق می‌افتد. به این رفتار Deferred Execution می‌گوییم.

yield return چه ارتباطی با foreach دارد؟

yield return راه ساده‌ای برای ساخت یک Sequence قابل پیمایش است. Compiler بخش زیادی از State Machine مربوط به Enumerator را برای ما تولید می‌کند.

C#
static IEnumerable<int> GetNumbers()
{
    yield return 10;
    yield return 20;
    yield return 30;
}

و مصرف‌کننده به سادگی می‌نویسد:

C#
foreach (var number in GetNumbers())
{
    Console.WriteLine(number);
}

هر بار که Enumerator جلو می‌رود، State Machine تولیدشده می‌تواند اجرای Iterator را تا yield return بعدی ادامه دهد.

await foreach چیست؟

برای Sequenceهای Async، C# نسخه‌ای به نام await foreach دارد که با مدل Async Enumeration کار می‌کند:

C#
await foreach (var message in GetMessagesAsync())
{
    Console.WriteLine(message);
}

در اینجا مفهوم مشابه است، اما حرکت به عنصر بعدی می‌تواند Async باشد و قراردادهایی مثل IAsyncEnumerable<T> و Async Enumerator وارد ماجرا می‌شوند.

اشتباهات رایج

  • اشتباه: foreach همیشه دقیقاً به یک while روی IEnumerator<T> تبدیل می‌شود.
    درست: این مدل عمومی خوبی است، اما Lowering دقیق به Type مجموعه بستگی دارد و Arrayها مسیر ویژه دارند.
  • اشتباه: برای foreach حتماً باید IEnumerable<T> را Implement کنیم.
    درست: C# از foreach pattern هم پشتیبانی می‌کند.
  • اشتباه: Current خودش Enumerator را جلو می‌برد.
    درست: حرکت با MoveNext() انجام می‌شود و Current عنصر فعلی را می‌دهد.
  • اشتباه: تغییر List داخل foreach همیشه امن است.
    درست: تغییر ساختاری معمولاً Enumerator را Invalid می‌کند.
  • اشتباه: for همیشه سریع‌تر از foreach است.
    درست: باید Type و Runtime واقعی را در نظر گرفت و در صورت اهمیت Benchmark گرفت.

جزئیات عمیق‌تر برای سطح Senior

foreach در مرحله Compilation اصطلاحاً Lower می‌شود؛ یعنی Syntax سطح‌بالا به عملیات ساده‌تر تبدیل می‌شود. شکل Lowering بر اساس قابلیت‌های Type مشخص می‌شود: Array، Enumerator Pattern، Interface-based Enumeration و در حالت Async، Async Enumerator Pattern.

از دید Performance، Concrete Enumeratorهای Struct می‌توانند مزایایی مثل کاهش Allocation داشته باشند، ولی استفاده از Interface ممکن است مسیر متفاوتی ایجاد کند. JIT نیز می‌تواند بعضی هزینه‌ها را Optimize کند. بنابراین برای Hot Pathها بهتر است IL/Native Code و Benchmark واقعی بررسی شود، نه اینکه صرفاً از روی Syntax نتیجه بگیریم.

مسیر کامل foreach در یک تصویر ذهنی

Flow
foreach (var item in collection)
              |
              v
       Get Enumerator
              |
              v
        MoveNext() ?
          /      \
       true      false
        |          |
        v          v
     Current      End
        |
        v
   Execute Body
        |
        +-------> MoveNext()

After enumeration:
Dispose when required

اگر مصاحبه‌کننده فقط در ۲۰ ثانیه جواب بخواهد

«foreach یک Syntax سطح‌بالا برای Enumeration است. در مدل عمومی Compiler از Collection یک Enumerator می‌گیرد، با MoveNext به عنصر بعدی می‌رود و Current را می‌خواند و در پایان Enumerator را در صورت نیاز Dispose می‌کند. ولی ترجمه دقیق همیشه یکسان نیست؛ مثلاً Arrayها مسیر بهینه و خاص خودشان را دارند و C# علاوه بر IEnumerable از Enumerator Pattern هم پشتیبانی می‌کند.»

جواب پیشنهادی کامل برای مصاحبه

«foreach در C# یک abstraction روی فرآیند Enumeration است. برای یک Collection معمولی، Compiler کد را به الگویی Lower می‌کند که ابتدا Enumerator را از طریق GetEnumerator می‌گیرد، سپس تا زمانی که MoveNext مقدار true می‌دهد، Current را به متغیر iteration اختصاص می‌دهد و بدنه حلقه را اجرا می‌کند. Cleanup Enumerator نیز در صورت نیاز تضمین می‌شود. نکته مهم این است که foreach الزاماً همیشه از IEnumerable<T> به شکل Interface-based استفاده نمی‌کند؛ C# از Enumerator Pattern پشتیبانی می‌کند و برای Typeهایی مثل Array lowering مخصوص و بهینه دارد. همچنین تغییر ساختاری Collectionهایی مثل List هنگام Enumeration معمولاً Enumerator را invalid می‌کند و می‌تواند InvalidOperationException ایجاد کند.»

چیزی که باید از این سؤال یادت بماند

این زنجیره را حفظ کنید: foreach → GetEnumerator → MoveNext → Current → Body → Dispose. اما بلافاصله اضافه کنید: این مدل عمومی است؛ Compiler می‌تواند برای Typeهایی مثل Array مسیر ویژه و بهینه‌تری داشته باشد. همین نکته جواب شما را از یک پاسخ Junior ساده به یک پاسخ مصاحبه‌ای دقیق‌تر تبدیل می‌کند.
