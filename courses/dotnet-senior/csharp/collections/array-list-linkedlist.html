تفاوت Array، List و LinkedList چیست؟

پاسخ کوتاه مصاحبه‌ای

Array اندازه ثابت دارد و عناصرش به صورت پیوسته نگهداری می‌شوند؛ بنابراین دسترسی با Index بسیار سریع است. List<T> در داخل معمولاً از یک Array استفاده می‌کند، اما اندازه‌اش به صورت Dynamic مدیریت می‌شود و برای اکثر سناریوهای روزمره انتخاب پیش‌فرض خوبی است. LinkedList<T> از Nodeهایی تشکیل شده که هر Node به قبلی و بعدی وصل است؛ دسترسی با Index سریع ندارد، اما اگر Node موردنظر را از قبل داشته باشیم، Insert و Remove در همان نقطه می‌تواند بدون جابه‌جایی بقیه عناصر انجام شود.

مدل ذهنی خیلی ساده

برای فهم تفاوت این سه Collection، سه تصویر در ذهن داشته باشید:

  • Array: یک ردیف صندلی با تعداد ثابت.
  • List: یک ردیف صندلی که وقتی پر شد، سیستم یک ردیف بزرگ‌تر می‌سازد و افراد را منتقل می‌کند.
  • LinkedList: یک زنجیر؛ هر حلقه می‌داند حلقه قبلی و بعدی کدام است.

همین مدل ذهنی تقریباً تمام تفاوت‌های Performance آن‌ها را توضیح می‌دهد.

Array چیست؟

Array مجموعه‌ای از عناصر هم‌نوع با طول ثابت است. هنگام ساخت Array باید اندازه آن مشخص باشد.

C#
int[] numbers = new int[3];

numbers[0] = 10;
numbers[1] = 20;
numbers[2] = 30;

این Array دقیقاً سه خانه دارد. بعداً نمی‌توانیم همان Array را تبدیل به چهار خانه کنیم.

دسترسی به عناصر Array چرا سریع است؟

برای دسترسی به یک عنصر کافی است Index را بدانیم:

C#
int value = numbers[2];

Runtime می‌تواند مستقیماً محل عنصر موردنظر را محاسبه کند؛ لازم نیست از عنصر اول تا عنصر سوم حرکت کند. به همین دلیل دسترسی با Index در Array از نظر Big-O برابر O(1) است.

مشکل اصلی Array چیست؟

اندازه آن ثابت است. مثلاً:

C#
int[] numbers = new int[3];

اگر بعداً بخواهیم عنصر چهارم اضافه کنیم، باید Array دیگری با اندازه بزرگ‌تر بسازیم و داده‌ها را منتقل کنیم. به همین دلیل اگر تعداد عناصر دائماً تغییر می‌کند، معمولاً List<T> راحت‌تر است.

List<T> چیست؟

List<T> یک Collection Generic با اندازه Dynamic است:

C#
var numbers = new List<int>();

numbers.Add(10);
numbers.Add(20);
numbers.Add(30);
numbers.Add(40);

ما لازم نیست از ابتدا تعداد نهایی عناصر را بدانیم. List مدیریت فضای داخلی را خودش انجام می‌دهد.

List در داخل چگونه کار می‌کند؟

نکته مهم مصاحبه‌ای این است که List<T> خودش Linked List نیست. در پیاده‌سازی معمول .NET، List در داخل یک Array نگه می‌دارد.

Concept
List<int>
    ↓
Internal Array
[10][20][30][40][ ][ ][ ][ ]

به همین دلیل دسترسی با Index در List نیز سریع است:

C#
int value = numbers[2]; // O(1)

Count و Capacity در List چه فرقی دارند؟

این دو مفهوم را حتماً از هم جدا کنید:

  • Count: تعداد عناصری که واقعاً داخل List داریم.
  • Capacity: تعداد عناصری که Array داخلی فعلی می‌تواند بدون Resize نگه دارد.
C#
var numbers = new List<int>(10);

numbers.Add(100);
numbers.Add(200);

Console.WriteLine(numbers.Count);    // 2
Console.WriteLine(numbers.Capacity); // حداقل 10

یعنی فقط دو عنصر داریم، ولی از ابتدا برای حداقل ده عنصر ظرفیت رزرو کرده‌ایم.

وقتی Capacity پر شود چه اتفاقی می‌افتد؟

اگر Array داخلی دیگر جا نداشته باشد، List به صورت مفهومی این کارها را انجام می‌دهد:

  1. فضای بزرگ‌تری برای نگهداری عناصر فراهم می‌کند.
  2. عناصر قبلی را به فضای جدید منتقل می‌کند.
  3. از آن به بعد از Storage جدید استفاده می‌کند.

پس هر بار Add الزاماً Resize انجام نمی‌دهد. به همین دلیل اضافه کردن به انتهای List به طور معمول Amortized O(1) در نظر گرفته می‌شود.

Amortized O(1) یعنی چه؟

ممکن است بعضی عملیات Add به دلیل Resize گران باشند، اما Resize در هر Add اتفاق نمی‌افتد. وقتی هزینه تعداد زیادی Add را با هم بررسی کنیم، متوسط هزینه هر Add ثابت و بسیار کم می‌شود. به این تحلیل Amortized می‌گوییم.

پس در مصاحبه بهتر است نگوییم «Add در List همیشه O(1) است». دقیق‌تر این است: Add به انتهای List معمولاً Amortized O(1) است.

Insert وسط List چه هزینه‌ای دارد؟

C#
var numbers = new List<int>
{
    10, 20, 30, 40
};

numbers.Insert(1, 15);

برای اینکه 15 در Index شماره 1 قرار بگیرد، عناصر بعدی باید جابه‌جا شوند:

Before / After 
Before:
[10][20][30][40]

Insert 15 at index 1

After:
[10][15][20][30][40]

در بدترین حالت تعداد زیادی عنصر Shift می‌شوند؛ بنابراین Insert یا Remove در وسط List معمولاً O(n) است.

LinkedList<T> چیست؟

LinkedList<T> ساختار متفاوتی دارد. هر عنصر داخل یک Node قرار می‌گیرد و Nodeها به یکدیگر متصل هستند. در .NET، LinkedList<T> یک Doubly Linked List است؛ یعنی هر Node هم Node قبلی و هم Node بعدی را می‌شناسد.

Concept
null
  ← [10] ⇄ [20] ⇄ [30] ⇄ [40] →
                               null

ساخت LinkedList در C#

C#
var numbers = new LinkedList<int>();

numbers.AddLast(10);
numbers.AddLast(20);
numbers.AddLast(30);

numbers.AddFirst(5);

می‌توانیم مستقیم به ابتدا یا انتهای LinkedList عنصر اضافه کنیم.

LinkedList چرا Index ندارد؟

در Array و List می‌توانیم بنویسیم:

C#
numbers[500];

اما LinkedList چنین دسترسی Index-based مستقیمی ندارد. برای رسیدن به یک Node میانی باید از Nodeها عبور کنیم.

Concept
[10] → [20] → [30] → [40] → [50]
 ↑
 start

برای رسیدن به 40:
10 → 20 → 30 → 40

بنابراین پیدا کردن یک عنصر بر اساس موقعیت یا Value معمولاً O(n) است.

پس مزیت LinkedList چیست؟

مزیت مهم زمانی دیده می‌شود که Node موردنظر را از قبل داشته باشیم. در این حالت برای Insert یا Remove لازم نیست عناصر بعدی Shift شوند.

C#
var list = new LinkedList<string>();

var first = list.AddLast("A");
var second = list.AddLast("B");
var third = list.AddLast("C");

list.AddAfter(second, "X");

ساختار تبدیل می‌شود به:

Concept
A ⇄ B ⇄ X ⇄ C

چون Reference مربوط به Node با مقدار B را داریم، لازم نیست برای پیدا کردن محل Insert کل Collection را پیمایش کنیم.

نکته مصاحبه‌ای بسیار مهم درباره O(1)

گاهی گفته می‌شود: Insert و Remove در LinkedList برابر O(1) است. این جمله بدون توضیح کامل نیست.

اگر Node موردنظر را از قبل داشته باشیم، تغییر Linkها می‌تواند O(1) باشد. اما اگر اول مجبور شویم Node را Search کنیم:

C#
var node = list.Find("B"); // O(n)

list.AddAfter(node!, "X"); // O(1) بعد از پیدا شدن Node

در این سناریو کل عملیات هنوز به دلیل Search، O(n) است. این نکته جواب شما را در مصاحبه دقیق‌تر می‌کند.

مقایسه دسترسی با Index

Array O(1) دسترسی مستقیم با Index
List<T> O(1) استفاده از Array داخلی
LinkedList<T> O(n) نیاز به پیمایش Nodeها

اندازه ثابت Dynamic Dynamic

Big-O همه داستان Performance نیست. Cache locality، Allocation، اندازه داده و الگوی دسترسی واقعی نیز مهم هستند.

تفاوت مهم حافظه

LinkedList برای هر عنصر فقط خود Value را نگه نمی‌دارد؛ هر Node اطلاعات ارتباط با Nodeهای دیگر را هم دارد. به علاوه Nodeها Objectهای جداگانه‌ای هستند.

Concept
List:
[Value][Value][Value][Value]

LinkedList:
[Prev | Value | Next]
[Prev | Value | Next]
[Prev | Value | Next]

بنابراین LinkedList معمولاً نسبت به List برای همان تعداد عنصر Memory Overhead بیشتری دارد.

Cache Locality یعنی چه و چرا مهم است؟

Array و List داده‌ها را در Storage متراکم‌تری نگه می‌دارند. وقتی CPU یک بخش از حافظه را می‌خواند، داده‌های نزدیک هم معمولاً وارد Cache می‌شوند. به همین دلیل پیمایش Array و List در بسیاری از Workloadهای واقعی بسیار سریع است.

Nodeهای LinkedList الزاماً در حافظه کنار هم نیستند و برای حرکت بین آن‌ها باید Referenceها دنبال شوند. به همین دلیل اینکه یک عملیات روی کاغذ O(1) است، الزاماً به معنی سریع‌تر بودن کل برنامه نیست.

پس آیا LinkedList برای Insert زیاد همیشه بهتر است؟

خیر. این یکی از مهم‌ترین سوءتفاهم‌هاست.

اگر برای Insert ابتدا مجبور باشید محل موردنظر را با پیمایش پیدا کنید، Search خودش O(n) است. همچنین Allocation هر Node و Cache Locality ضعیف‌تر می‌تواند هزینه ایجاد کند.

بنابراین جمله «Insert زیاد دارم، پس LinkedList انتخاب می‌کنم» کافی نیست. باید الگوی دسترسی واقعی را بررسی کنید.

مثال واقعی: داده‌ای با تعداد ثابت

فرض کنید دقیقاً ۱۲ مقدار برای ماه‌های سال داریم:

C#
decimal[] monthlyRevenue = new decimal[12];

تعداد عناصر از قبل مشخص و ثابت است. در چنین سناریویی Array انتخاب ساده و مناسبی است.

مثال واقعی: لیست تراکنش‌ها

فرض کنید نتیجه Query را پردازش می‌کنیم و تعداد آیتم‌ها می‌تواند تغییر کند:

C#
var transactions = new List<Transaction>();

transactions.Add(transaction1);
transactions.Add(transaction2);

Transaction first = transactions[0];

نیاز به Add داریم و همچنین دسترسی با Index مفید است. برای چنین سناریوهای عمومی، List معمولاً انتخاب طبیعی‌تری است.

مثال واقعی برای LinkedList

فرض کنید ساختاری داریم که دائماً باید Node مشخصی را از زنجیره حذف یا Node جدیدی کنار آن اضافه کنیم و Reference همان Node را از قبل نگه داشته‌ایم:

C#
LinkedList<Job> jobs = new();

LinkedListNode<Job> node =
    jobs.AddLast(job);

jobs.AddAfter(node, urgentJob);

// later...
jobs.Remove(node);

اینجا ویژگی Node-based بودن LinkedList واقعاً می‌تواند مفید باشد.

اگر تعداد عناصر را از قبل بدانیم، List را بهتر کنیم

اگر می‌دانیم تقریباً چند عنصر اضافه می‌شود، می‌توانیم Capacity اولیه بدهیم:

C#
var transactions =
    new List<Transaction>(10_000);

این کار می‌تواند تعداد Resizeها و Copyهای داخلی را کاهش دهد. البته Capacity باید بر اساس اطلاعات واقعی انتخاب شود، نه حدس بی‌دلیل.

اشتباه رایج: List و LinkedList شبیه هم هستند

اسم آن‌ها ممکن است گمراه‌کننده باشد:

Important
List<T> != LinkedList<T>

List<T> یک Dynamic Array است. LinkedList<T> یک زنجیره از Nodeها است. این دو از نظر ساختار داخلی و Performance Characteristics کاملاً متفاوت‌اند.

کدام را به عنوان انتخاب پیش‌فرض استفاده کنیم؟

برای بیشتر Business Applicationها اگر فقط یک Collection ترتیبی و قابل تغییر می‌خواهیم، List<T> انتخاب پیش‌فرض بسیار خوبی است.

Array را زمانی انتخاب می‌کنیم که اندازه ثابت یا API موردنظر Array باشد و ساختار ساده و متراکم بخواهیم. LinkedList را زمانی انتخاب می‌کنیم که واقعاً الگوی Node-based و Insert/Remove محلی آن برای مسئله مفید باشد.

جدول تصمیم‌گیری سریع

نیاز انتخاب معمول
تعداد عناصر ثابت است Array
دسترسی زیاد با Index Array یا List
Collection عمومی با اندازه متغیر List<T>
Add زیاد به انتها List<T> معمولاً عالی است
Insert/Remove کنار Nodeای که از قبل داریم LinkedList<T>
نیاز به کمترین پیچیدگی در Business Code معمولاً List<T>

اشتباهات رایج

  • اشتباه: List همان LinkedList است.
    درست: List معمولاً روی Array داخلی ساخته شده؛ LinkedList Node-based است.
  • اشتباه: Add در List همیشه O(1) است.
    درست: Add انتهایی معمولاً Amortized O(1) است و گاهی Resize رخ می‌دهد.
  • اشتباه: Insert در LinkedList همیشه O(1) است.
    درست: اگر اول مجبور به پیدا کردن Node باشیم، Search می‌تواند O(n) باشد.
  • اشتباه: LinkedList چون Insert آن O(1) است همیشه سریع‌تر است.
    درست: Allocation، Memory Overhead، Cache Locality و Search هم مهم‌اند.
  • اشتباه: Array قدیمی است و دیگر نباید استفاده شود.
    درست: Array همچنان یک ساختار پایه، سریع و بسیار پرکاربرد است.

جزئیات عمیق‌تر برای سطح Senior

در انتخاب Data Structure فقط Big-O را نبینید. List<T> به دلیل Storage پیوسته، Cache Locality خوبی دارد و در بسیاری از Workloadها حتی زمانی که Insert/Remove دارد می‌تواند از LinkedList سریع‌تر باشد.

LinkedList<T> برای هر عنصر یک Node جداگانه دارد و این موضوع Memory Overhead و Pointer Chasing ایجاد می‌کند. مزیت اصلی آن زمانی ارزشمند است که الگوریتم واقعاً Node Referenceها را نگه دارد و مرتباً در همان نقاط Insert/Remove انجام دهد.

در مسیرهای Performance-sensitive، انتخاب نهایی باید با Benchmark روی الگوی داده واقعی انجام شود، نه فقط با جدول Complexity.

اگر مصاحبه‌کننده بپرسد «برای ۹۰٪ پروژه‌ها کدام؟»

می‌توانید بگویید:

«اگر Requirement خاصی نداشته باشم، برای یک Collection ترتیبی با اندازه متغیر معمولاً List<T> را انتخاب می‌کنم، چون API ساده، دسترسی O(1) با Index و Cache Locality خوبی دارد. Array را برای اندازه ثابت یا APIهای Array-based استفاده می‌کنم. LinkedList را فقط وقتی انتخاب می‌کنم که الگوی دسترسی Node-based و Insert/Remove محلی واقعاً مزیت ایجاد کند.»

جواب پیشنهادی کامل برای مصاحبه

«Array اندازه ثابت دارد و عناصرش به شکل متراکم نگهداری می‌شوند، بنابراین دسترسی با Index برابر O(1) است. List<T> در داخل معمولاً از Array استفاده می‌کند ولی Capacity را به صورت Dynamic مدیریت می‌کند؛ دسترسی با Index آن O(1) و Add انتهایی معمولاً Amortized O(1) است، اما Insert و Remove وسط Collection به دلیل Shift شدن عناصر O(n) هستند. LinkedList<T> از Nodeهای Doubly Linked تشکیل شده و Random Access با Index ندارد؛ پیدا کردن یک Node معمولاً O(n) است، اما اگر Reference همان Node را از قبل داشته باشیم، Insert یا Remove در آن نقطه می‌تواند O(1) باشد. در عمل برای اکثر سناریوهای عمومی List انتخاب پیش‌فرض خوبی است و LinkedList را فقط برای الگوهای دسترسی خاص انتخاب می‌کنم.»

چیزی که باید از این سؤال یادت بماند

این سه جمله را حفظ کنید: Array = اندازه ثابت + دسترسی سریع با Index، List = Dynamic Array و انتخاب عمومی برای اکثر سناریوها، و LinkedList = Node-based؛ Insert/Remove سریع وقتی Node را از قبل داریم، ولی Random Access ضعیف‌تر و Memory Overhead بیشتر.
