Concurrent Collectionها و Immutable را چه زمانی انتخاب می‌کنیم؟

پاسخ کوتاه مصاحبه‌ای

Concurrent Collection mutation مشترک بین threadها را هماهنگ می‌کند؛ Immutable Collection به‌جای تغییر object قبلی، snapshot جدید می‌سازد. اولی برای state پرتغییر مشترک و دومی برای انتشار state پایدار و خواندن فراوان مناسب است.

مدل ذهنی ساده

در مدل concurrent چند نفر روی یک تخته مشترک با ابزار هماهنگ می‌نویسند. در مدل immutable هر نسخه تخته پس از انتشار عوض نمی‌شود و نویسنده نسخه تازه می‌سازد. reader نسخه‌ای ثابت می‌بیند، ولی writer باید reference نسخه جدید را به‌درستی منتشر کند.

توضیح کامل

methodهای منفرد Concurrent Collection thread-safe هستند، اما ترکیب check-then-act چندمرحله‌ای لزوماً atomic نیست؛ باید از operation ترکیبی مناسب یا synchronization بیرونی استفاده کرد. در ConcurrentDictionary.GetOrAdd value factory ممکن است در رقابت بیش از یک بار اجرا شود، هرچند تنها یک value ذخیره شود؛ side effect خطرناک است. Immutable Collection با structural sharing هزینه copy کامل را کاهش می‌دهد، اما allocation و publication نسخه جدید همچنان وجود دارد.

C#
var cache = new ConcurrentDictionary<string, Item>();
var item = cache.GetOrAdd(key, Load);

ImmutableArray<string> snapshot = ImmutableArray<string>.Empty;
snapshot = snapshot.Add("ready");

رفتار مثال: cache پرترافیک از ConcurrentDictionary استفاده می‌کند، اما Load در GetOrAdd باید تحمل اجرای چندباره داشته باشد یا Lazy مناسبی ذخیره شود. تنظیمات برنامه با ImmutableDictionary ساخته و reference snapshot جدید atomically منتشر می‌شود؛ reader بدون lock همان نسخه ثابت را تا پایان پردازش می‌خواند.

نکات کلیدی

  • thread-safe بودن collection کل workflow را atomic نمی‌کند.
  • factory مربوط به GetOrAdd ممکن است چند بار اجرا شود.
  • Immutable Collection snapshot پایدار می‌دهد، نه publication خودکار.

اشتباهات رایج

  • قفل‌نکردن invariant چندمرحله‌ای
  • فرض اجرای یک‌باره factory در GetOrAdd
  • اشتراک List فقط‌خواندنی ظاهری.

جزئیات عمیق‌تر

گاهی ownership تک‌thread و message passing از هر دو ساده‌تر است. نوع workload، نسبت read/write، نیاز به snapshot consistency و هزینه allocation معیار انتخاب‌اند. برای invariant چند collection، یک lock یا state immutable واحد می‌تواند از operationهای جدا و ظاهراً thread-safe درست‌تر باشد.

در پروژهٔ واقعی

cache مشترک پرتغییر concurrent می‌خواهد؛ تنظیمات منتشرشده برای خواندن‌های فراوان snapshot immutable مناسبی است.
