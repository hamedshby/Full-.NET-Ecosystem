چرا List به List قابل تبدیل نیست؟

پاسخ کوتاه مصاحبه‌ای

List<Dog> به List<Animal> تبدیل نمی‌شود چون List هم T می‌خواند و هم T می‌نویسد. اگر conversion مجاز بود، caller می‌توانست Cat را در فهرستی اضافه کند که در واقع فقط Dog نگه می‌دارد.

مدل ذهنی ساده

یک List<Dog> را موقتاً List<Animal> فرض کنید. API دوم حق دارد هر Animal، از جمله Cat، اضافه کند. پس فهرست اصلی دیگر List<Dog نیست و type safety شکسته می‌شود. ممنوع‌بودن conversion جلوی همین نوشتن ناسازگار را قبل از اجرا می‌گیرد.

توضیح کامل

List<T> به دلیل methodهایی مانند Add(T) و indexer خواندن/نوشتن، T را هم در موقعیت ورودی و هم خروجی استفاده می‌کند و بنابراین Invariant است. اگر مصرف‌کننده فقط enumeration می‌خواهد، می‌توان IEnumerable<Animal> پذیرفت؛ IEnumerable<out T> Covariant است و امکان mutation ندارد. arrayها در C# Covariant هستند اما این سازگاری تاریخی با check در Runtime و احتمال ArrayTypeMismatchException همراه است، پس الگوی ایمنی برای List محسوب نمی‌شود.

C#
List<Cat> cats = [new Cat()];
IEnumerable<Animal> animals = cats; // امن
// List<Animal> mutable = cats; // غیرمجاز؛ افزودن Dog ممکن بود

رفتار مثال: List<Cat> مستقیماً به List<Animal> assign نمی‌شود. همان list به IEnumerable<Animal> قابل‌دادن است و caller فقط Animal می‌خواند. تبدیل با Cast type collection را عوض نمی‌کند؛ ToList<Animal> یک فهرست جدید می‌سازد و ownership و هزینه متفاوتی دارد.

نکات کلیدی

  • List به‌علت خواندن و نوشتن T، Invariant است.
  • Covariance فقط برای قرارداد producer مانند IEnumerable ایمن است.
  • کپی به List جدید با conversion view یکسان نیست.

اشتباهات رایج

  • حل با cast خطرناک یا کپی بی‌دلیل
  • یکی دانستن covariance array با ایمنی کامل.

جزئیات عمیق‌تر

برای API فقط‌خواندنی بسته به نیاز از IEnumerable<T>، IReadOnlyCollection<T> یا IReadOnlyList<T> استفاده کنید؛ readonly interface به‌تنهایی object زیرین را immutable نمی‌کند. اگر mutation لازم است، type دقیق و ownership تغییرات را صریح نگه دارید.

در پروژهٔ واقعی

برای ورودی فقط‌خواندنی `IEnumerable` بگیرید؛ اگر mutation لازم است ownership را صریح طراحی کنید.
