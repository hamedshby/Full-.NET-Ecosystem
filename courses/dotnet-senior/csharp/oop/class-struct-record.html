تفاوت class، struct و record در انتخاب مدل دامنه چیست؟

پاسخ کوتاه مصاحبه‌ای

برای انتخاب بین class، struct و record فقط به Syntax نگاه نمی‌کنیم؛ باید ببینیم مدل ما هویت دارد یا صرفاً مقدار را نشان می‌دهد، آیا نیاز به Mutation داریم، Semantics کپی چگونه باید باشد و Equality بر چه اساسی معنا پیدا می‌کند. به طور معمول، Entityهای دارای Identity مثل Customer یا Order با class مدل می‌شوند. Valueهای کوچک مثل مختصات یا یک نوع عددی کوچک می‌توانند struct باشند. و record برای مدل‌هایی مناسب است که Equality مبتنی بر داده و مدل‌سازی Value-oriented برایشان مهم است؛ مخصوصاً DTOها و Value Objectهای Immutable.

مدل ذهنی خیلی ساده

سه سؤال از خودتان بپرسید:

  • این Object «چه کسی است» مهم است؟ → معمولاً class.
  • این Object فقط «چه مقداری دارد» مهم است و کوچک است؟ → ممکن است struct مناسب باشد.
  • می‌خواهم دو نمونه با داده یکسان برابر باشند و مدل Value-oriented باشد؟ → record گزینه بسیار خوبی است.

اول Identity و Value را بفهمیم

در Domain Modeling، تفاوت مهمی بین Entity و Value Object وجود دارد.

یک Entity معمولاً با Identity شناخته می‌شود:

C#
public class Customer
{
    public Guid Id { get; set; }
    public string Name { get; set; } = string.Empty;
}

دو Customer ممکن است Name یکسان داشته باشند، ولی اگر Id متفاوت باشد دو Entity جدا هستند.

اما برای یک Value Object مثل Money معمولاً خود Value مهم است:

C#
public record Money(
    decimal Amount,
    string Currency);

دو Money با Amount و Currency یکسان معمولاً از نظر Domain همان Value را نشان می‌دهند.

class چیست؟

class یک Reference Type است. متغیرهای class معمولاً Reference به Object را نگه می‌دارند و Assignment خود Object را Copy نمی‌کند؛ Reference کپی می‌شود.

C#
var first = new Customer
{
    Id = Guid.NewGuid(),
    Name = "Sara"
};

var second = first;

second.Name = "Mina";

Console.WriteLine(first.Name); // Mina

چون first و second به همان Object اشاره می‌کنند، تغییر از یک Reference از Reference دیگر هم دیده می‌شود.

class چه زمانی برای Domain مناسب است؟

class معمولاً برای Objectهایی مناسب است که:

  • Identity مستقل دارند.
  • Lifecycle دارند.
  • State آن‌ها در طول زمان تغییر می‌کند.
  • قرار است چند بخش سیستم به همان Instance منطقی اشاره کنند.
  • Entity یا Aggregate Root هستند.

مثال‌های رایج:

مثال Entity با class

C#
public class Payment
{
    public Guid Id { get; private set; }

    public decimal Amount { get; private set; }

    public PaymentStatus Status { get; private set; }

    public void MarkAsCompleted()
    {
        Status = PaymentStatus.Completed;
    }
}

Payment Identity دارد و State آن در طول Lifecycle تغییر می‌کند. این Characteristics معمولاً با class طبیعی‌تر مدل می‌شوند.

struct چیست؟

struct یک Value Type است. یعنی Assignment به طور معمول Value را Copy می‌کند.

C#
public struct Point
{
    public int X { get; set; }
    public int Y { get; set; }
}

var first = new Point { X = 10, Y = 20 };
var second = first;

second.X = 100;

Console.WriteLine(first.X); // 10

در اینجا second یک Copy مستقل از Value است.

struct برای چه نوع مدل‌هایی مناسب است؟

struct معمولاً وقتی جذاب است که Type:

  • کوچک باشد.
  • یک Value ساده را نمایش دهد.
  • Identity مستقل نداشته باشد.
  • Semantics کپی شدن برایش طبیعی باشد.
  • ترجیحاً Immutable باشد.

مثلاً:

Examples
Point
Coordinate
Range
RgbColor
Small numeric-like value

چرا Mutable Struct خطرناک است؟

چون Struct با Value Semantics کار می‌کند، Copy شدن آن می‌تواند رفتارهایی ایجاد کند که برای Juniorها غافلگیرکننده باشد.

C#
var point1 = new Point { X = 1, Y = 2 };

var point2 = point1;

point2.X = 50;

// point1 تغییر نکرده است

به همین دلیل برای Structها معمولاً طراحی Immutable یا readonly struct انتخاب امن‌تری است.

readonly struct چیست؟

C#
public readonly struct Coordinate
{
    public double Latitude { get; }
    public double Longitude { get; }

    public Coordinate(
        double latitude,
        double longitude)
    {
        Latitude = latitude;
        Longitude = longitude;
    }
}

این Type بعد از ساخته شدن State قابل تغییری ندارد و Value Semantics آن واضح‌تر است.

record چیست؟

record برای مدل‌سازی Data-oriented Typeها طراحی شده و به صورت پیش‌فرض امکاناتی مثل Value-based Equality و Syntax مناسب برای Immutable-style modeling می‌دهد.

C#
public record Address(
    string City,
    string Street,
    string PostalCode);

حالا:

C#
var first = new Address(
    "Tehran",
    "Valiasr",
    "123");

var second = new Address(
    "Tehran",
    "Valiasr",
    "123");

Console.WriteLine(first == second); // True

دو Instance جدا ساخته شده‌اند، ولی چون Data آن‌ها یکسان است، Value Equality برقرار است.

این با class معمولی چه فرقی دارد؟

C#
public class Address
{
    public string City { get; set; } = "";
}

اگر دو Object جدا بسازیم:

C#
var first = new Address { City = "Tehran" };
var second = new Address { City = "Tehran" };

Console.WriteLine(first == second); // False

در class معمولی، Equality پیش‌فرض Reference-based است؛ یعنی این دو Reference به دو Object جدا اشاره می‌کنند. البته می‌توان Equality سفارشی برای class پیاده‌سازی کرد، اما record این رفتار Value-oriented را به شکل built-in فراهم می‌کند.

record class است یا Value Type؟

خود کلمه record به تنهایی لزوماً به معنی Value Type نیست.

C#
public record Person(string Name);

این در حالت معمول یک record class و در نتیجه Reference Type است.

اما C# همچنین دارد:

C#
public record struct Point(int X, int Y);

public readonly record struct Money(
    decimal Amount,
    string Currency);

پس record بیشتر درباره Semantics و امکانات Record است؛ می‌تواند Reference Type یا Value Type باشد.

record class و record struct چه فرقی دارند؟

نوع Category Assignment Equality
record class Reference Type Reference کپی می‌شود Value-based
record struct Value Type Value کپی می‌شود Value-based

with expression در record

یکی از قابلیت‌های بسیار کاربردی record، ساخت Copy با چند تغییر است:

C#
public record CustomerDto(
    string Name,
    string City);

var first =
    new CustomerDto("Sara", "Tehran");

var second = first with
{
    City = "Shiraz"
};

first تغییر نمی‌کند و second نسخه جدیدی با City متفاوت است. این Style برای مدل‌های Immutable بسیار خواناست.

record برای DTO مناسب است؟

در بسیاری از سناریوها بله، مخصوصاً وقتی DTO:

  • فقط Data حمل می‌کند.
  • Behavior پیچیده ندارد.
  • ترجیحاً Immutable است.
  • Value Equality برای Test یا مقایسه مفید است.
C#
public record PaymentResponse(
    Guid TransactionId,
    decimal Amount,
    string Status);

آیا Entity را record کنیم؟

از نظر زبان ممکن است، اما از نظر Domain Design باید دقت کنیم. Entity معمولاً با Identity برابر است، نه با همه Propertyها.

مثلاً دو Customer با Id یکسان ممکن است همان Entity باشند حتی اگر Name آن‌ها در دو Snapshot متفاوت باشد. اما Value Equality خودکار record همه Componentهای Equality را وارد مقایسه می‌کند.

پس برای Entityهای DDD معمولاً class انتخاب طبیعی‌تری است، مگر اینکه Equality و Lifecycle را آگاهانه طراحی کرده باشید.

مثال: Entity با Identity

C#
public class BankAccount
{
    public Guid Id { get; private set; }

    public decimal Balance { get; private set; }

    public void Deposit(decimal amount)
    {
        Balance += amount;
    }
}

اگر Balance تغییر کند، Entity جدیدی ایجاد نشده؛ همان BankAccount با همان Identity است. این دقیقاً Entity Semantics است.

مثال: Value Object با record

C#
public sealed record Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(
        decimal amount,
        string currency)
    {
        if (amount < 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        Amount = amount;
        Currency = currency;
    }
}

Money Identity مستقلی ندارد. 100 USD صرفاً یک Value است. Record کمک می‌کند Equality چنین مدلی طبیعی‌تر باشد، در حالی که Constructor همچنان Invariantهای Domain را enforce می‌کند.

آیا هر Value Object باید record باشد؟

نه. record ابزار بسیار خوبی است، اما قانون اجباری نیست. می‌توان Value Object را با class یا struct هم طراحی کرد و Equality مناسب را خودمان تعریف کنیم.

انتخاب باید بر اساس Semantics و نیاز پروژه باشد، نه صرفاً جدیدتر بودن Feature.

چه زمانی struct برای Value Object بهتر از record class است؟

اگر Value Object:

  • واقعاً کوچک است.
  • بسیار زیاد ساخته و استفاده می‌شود.
  • Semantics کپی طبیعی دارد.
  • عدم وجود null برای آن مطلوب است.
  • Value Type بودن مزیت مشخصی ایجاد می‌کند.

می‌توان readonly record struct را هم بررسی کرد:

C#
public readonly record struct Percentage(
    decimal Value);

ولی چرا Struct بزرگ خطرناک است؟

چون Struct در Assignment و عبور By Value می‌تواند Copy شود. اگر Struct بزرگ باشد، این Copyها می‌توانند هزینه‌دار شوند و Semantics کد هم پیچیده‌تر شود.

پس جمله «Struct روی Stack است و سریع‌تر است» معیار درستی برای Domain Modeling نیست. Value Type بودن درباره Semantics مهم است، نه فقط محل حافظه.

Stack و Heap معیار انتخاب نیستند

یکی از اشتباهات رایج مصاحبه:

Wrong mental model 
class  → Heap
struct → Stack

این تعریف بیش از حد ساده و گمراه‌کننده است. یک Struct می‌تواند داخل یک Object روی Managed Heap قرار بگیرد و Runtime/JIT درباره Storage واقعی تصمیمات مختلفی بگیرند.

برای انتخاب مدل Domain، اول Semantics را ببینید: Identity، Equality، Mutability، Copy semantics و Lifecycle.

Mutability چه نقشی در انتخاب دارد؟

مدل الگوی رایج
Entity Controlled Mutable State
Value Object معمولاً Immutable
DTO Mutable یا Immutable بسته به Serializer/API

مثلاً Order می‌تواند State را از Pending به Paid تغییر دهد. اما Money بهتر است تغییر نکند؛ به جای تغییر Amount، Value جدید بسازیم.

یک مثال مهم: تغییر Value Object

C#
public record Money(
    decimal Amount,
    string Currency);

var price = new Money(100, "USD");

var discounted = price with
{
    Amount = 90
};

Value قبلی تغییر نکرده؛ Value جدید ساخته شده است. این مدل ذهنی برای Value Objectها بسیار طبیعی است.

Equality را چطور تصمیم بگیریم؟

این سؤال بسیار مهم‌تر از «class یا record؟» است.

  • اگر Identity مهم است → Equality باید بر اساس Identity طراحی شود.
  • اگر تمام Valueها معنی Object را تشکیل می‌دهند → Value Equality منطقی است.

Record به صورت پیش‌فرض Value Equality را راحت می‌کند، اما شما باید مطمئن شوید این Equality واقعاً با Domain هماهنگ است.

آیا EF Core با record و struct مسئله دارد؟

برای Entityهای EF Core معمولاً class مسیر رایج و ساده‌تری است، چون Change Tracking، Navigationها، Proxyها و Lifecycle Entity با Reference Typeها طبیعی‌تر هماهنگ هستند.

Value Objectها بسته به طراحی می‌توانند به صورت Owned/Complex Type یا روش مناسب دیگر Map شوند. اما انتخاب نهایی باید با قابلیت‌های نسخه EF Core و Mapping واقعی پروژه هماهنگ شود.

اشتباهات رایج

  • اشتباه: Struct همیشه سریع‌تر است چون روی Stack است.
    درست: Storage به Context بستگی دارد و Value Semantics مهم‌تر است.
  • اشتباه: Record یعنی Value Type.
    درست: record معمولی یک record class است؛ record struct هم داریم.
  • اشتباه: هر Entity را می‌توان record کرد چون Equality راحت‌تر است.
    درست: Entity Equality معمولاً Identity-based است، نه تمام Propertyها.
  • اشتباه: هر Value Object حتماً باید struct باشد.
    درست: record class یا class با Equality مناسب هم می‌تواند Value Object خوبی باشد.
  • اشتباه: کوتاه‌ترین Syntax همیشه بهترین Domain Model است.
    درست: Semantics مدل مهم‌تر از Syntax است.

جزئیات عمیق‌تر برای سطح Senior

در Domain Modeling، انتخاب Type باید از مفهوم Domain شروع شود، نه از Memory Layout. Entity دارای Continuity و Identity است؛ بنابراین Reference Semantics و Controlled Mutation معمولاً منطقی‌اند. Value Object بر اساس Attributes تعریف می‌شود و Immutable بودن آن باعث ساده‌تر شدن Reasoning، Thread Safety و جلوگیری از Shared Mutable State می‌شود.

برای Structها باید هزینه Copy، Boxing در Interface-based usage، اندازه Type و Mutable Struct pitfalls را در نظر گرفت. Record نیز Equality، Deconstruction، Printing و Non-destructive mutation با with را آسان می‌کند، اما این Convenience نباید باعث شود Entity Equality اشتباه طراحی شود.

Rule of Thumb برای پروژه واقعی

  • Entity / Aggregate Root → معمولاً class.
  • Value Object عمومی و Immutable → معمولاً record class.
  • Value بسیار کوچک با Semantics کپی → readonly struct یا readonly record struct.
  • DTO / Message / Response → record اغلب انتخاب تمیزی است.
  • اگر Equality بر اساس Identity است، Value Equality خودکار record را بدون فکر نپذیرید.

اگر مصاحبه‌کننده فقط در ۲۰ ثانیه جواب بخواهد

«من بر اساس Domain Semantics انتخاب می‌کنم. Entityهایی که Identity و Lifecycle دارند معمولاً class هستند. Struct را برای Valueهای کوچک و بدون Identity که Copy semantics طبیعی دارند انتخاب می‌کنم و ترجیح می‌دهم Immutable باشد. Record برای مدل‌های Value-oriented مثل DTO و Value Object مناسب است چون Value-based equality و with expression را به صورت built-in می‌دهد. نکته مهم این است که record معمولی Reference Type است و نباید Entity را فقط به خاطر Syntax ساده‌تر record کنیم.»

جواب پیشنهادی کامل برای مصاحبه

«در انتخاب بین class، struct و record اول به Identity، Equality، Mutability و Copy semantics مدل نگاه می‌کنم. class یک Reference Type است و برای Entityهایی مثل Order یا Transaction که Identity و Lifecycle دارند انتخاب طبیعی‌تری است. struct یک Value Type است و Assignment آن Value را Copy می‌کند، بنابراین برای Valueهای کوچک، بدون Identity و ترجیحاً Immutable مناسب است. record برای Data-oriented modelها Value-based equality، with expression و Syntax مناسبی برای Immutable modeling می‌دهد؛ record معمولی Reference Type است و record struct نیز وجود دارد. برای Value Objectها record اغلب گزینه خوبی است، ولی برای Entity باید مراقب باشیم Equality بر اساس Identity طراحی شود، نه صرفاً همه Propertyها.»

چیزی که باید از این سؤال یادت بماند

این سه خط را حفظ کنید: class = Identity و Reference Semantics، struct = Value کوچک با Copy Semantics، و record = Value-oriented modeling با Value Equality. بعد اضافه کنید: انتخاب واقعی باید از Domain Semantics بیاید، نه از Stack/Heap یا کوتاه‌تر بودن Syntax.
