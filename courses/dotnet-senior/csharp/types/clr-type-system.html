سیستم نوع یکپارچهٔ CLR چگونه C# را پشتیبانی می‌کند؟

پاسخ کوتاه مصاحبه‌ای

وقتی کد C# را Compile می‌کنیم، خروجی مستقیماً Machine Code نیست. Compiler کد را به IL تبدیل می‌کند و اطلاعات Typeها را داخل Metadata قرار می‌دهد. CLR این اطلاعات را می‌خواند، Type Safety را کنترل می‌کند و در زمان اجرا با کمک JIT، IL را به Machine Code تبدیل می‌کند. CTS قرارداد مشترک Typeها در .NET است و CLS مجموعه‌ای محدودتر از قواعد CTS برای سازگاری بهتر بین زبان‌های مختلف .NET است.

مدل ذهنی خیلی ساده

فرض کنید C#، F# و Visual Basic سه زبان مختلف هستند. هرکدام Syntax خودشان را دارند، اما همه باید با یک Runtime مشترک یعنی CLR کار کنند.

برای اینکه CLR بتواند Typeهای همه این زبان‌ها را بفهمد، .NET یک زبان مشترک برای توصیف Typeها دارد که به آن Common Type System یا CTS می‌گوییم.

پس خیلی ساده:

  • C# زبان برنامه‌نویسی ما است.
  • CTS قوانین مشترک Typeها را تعریف می‌کند.
  • Metadata مشخصات Typeها و Memberها را نگه می‌دارد.
  • IL منطق اجرایی Methodها است.
  • CLR همه این‌ها را Load و اجرا می‌کند.
  • JIT در Runtime، IL را به Machine Code تبدیل می‌کند.

اول از همه: وقتی پروژه C# را Build می‌کنیم چه می‌شود؟

مثلاً این کلاس را داریم:

C#
public sealed class Counter
{
    public int Value { get; }

    public Counter(int value)
    {
        Value = value;
    }
}

Compiler این کد را به چند بخش مهم تبدیل می‌کند:

  1. اطلاعات Type و Memberها را در Metadata ثبت می‌کند.
  2. بدنه Methodها و Constructorها را به IL تبدیل می‌کند.
  3. همه این اطلاعات داخل Assembly مثل .dll یا .exe قرار می‌گیرد.

Metadata چیست؟

Metadata را می‌توانیم شناسنامه Assembly در نظر بگیریم. Metadata توضیح می‌دهد داخل Assembly چه چیزهایی وجود دارد.

مثلاً برای کلاس Counter، Metadata می‌تواند اطلاعاتی شبیه این داشته باشد:

  • یک Type به نام Counter وجود دارد.
  • این Type یک class است.
  • این class با sealed تعریف شده است.
  • یک Property به نام Value دارد.
  • Type این Property برابر System.Int32 است.
  • یک Constructor با پارامتر int دارد.

CLR برای شناخت ساختار Typeها لازم نیست Source Code اصلی C# را ببیند؛ Metadata برای این کار کافی است.

IL چیست؟

IL مخفف Intermediate Language است. Compiler C# معمولاً Methodها را مستقیماً به دستورهای CPU تبدیل نمی‌کند، بلکه آن‌ها را به یک زبان میانی تبدیل می‌کند.

مثلاً:

C#
int Add(int a, int b)
{
    return a + b;
}

در Assembly، رفتار این Method به شکل IL ذخیره می‌شود. بعداً CLR و JIT آن را برای CPU واقعی سیستم تبدیل می‌کنند.

پس فرق Metadata و IL چیست؟

بخش وظیفه
Metadata توضیح ساختار Typeها، Methodها، Propertyها، Visibility، Genericها و روابط Typeها
IL توضیح رفتار اجرایی Methodها

به زبان ساده: Metadata می‌گوید «چه چیزی وجود دارد» و IL می‌گوید «چه کاری انجام می‌شود».

CLR چیست؟

CLR مخفف Common Language Runtime است و Runtime اصلی .NET محسوب می‌شود.

CLR مسئول کارهای مهمی است، از جمله:

  • Load کردن Assemblyها
  • شناخت Typeها از روی Metadata
  • اجرای Managed Code
  • مدیریت حافظه و Garbage Collection
  • مدیریت Exceptionها
  • Type Safety
  • اجرای JIT Compilation

پس CLR فقط برای C# نیست؛ زبان‌های مختلف .NET می‌توانند روی آن اجرا شوند.

JIT چیست؟

JIT مخفف Just-In-Time Compiler است. وقتی یک Method برای اجرا نیاز باشد، JIT می‌تواند IL آن Method را به Machine Code مخصوص CPU تبدیل کند.

مسیر ساده اجرا:

Flow
C# Source Code
        ↓
C# Compiler
        ↓
IL + Metadata
        ↓
Assembly (.dll / .exe)
        ↓
CLR
        ↓
JIT
        ↓
Machine Code
        ↓
CPU

CTS چیست؟

CTS مخفف Common Type System است. CTS مشخص می‌کند Typeها در دنیای .NET چگونه تعریف و رفتار کنند.

مثلاً مفاهیمی مثل این‌ها در CTS تعریف می‌شوند:

  • Value Type
  • Reference Type
  • Class
  • Struct
  • Interface
  • Inheritance
  • Method
  • Field
  • Property
  • Generic Type

به همین دلیل CLR می‌تواند Typeهای ساخته‌شده توسط زبان‌های مختلف .NET را بفهمد.

یک مثال مهم: int در C# چیست؟

C#
int number = 10;

در C# از کلمه int استفاده می‌کنیم، ولی در Type System دات‌نت این Type همان:

C#
System.Int32

است.

C#
int first = 10;
System.Int32 second = 20;

این دو از نظر Type یکسان هستند. int فقط Alias زبان C# برای System.Int32 است.

چرا این موضوع مهم است؟

چون زبان‌های مختلف .NET ممکن است نام‌های متفاوتی برای Typeها داشته باشند، ولی در سطح CLR همه به Typeهای مشترک CTS نگاشت می‌شوند.

یعنی C# ممکن است بگوید:

C#
int

ولی Runtime آن را به شکل:

.NET Type
System.Int32

می‌شناسد.

ارتباط System.Object با Type System چیست؟

در .NET همه Typeها در نهایت با System.Object مرتبط هستند.

برای Reference Typeها این ارتباط معمولاً از طریق Inheritance دیده می‌شود. Value Typeها نیز از نظر Type System از System.ValueType مشتق می‌شوند و System.ValueType خودش در نهایت از System.Object می‌آید.

Type hierarchy 
System.Object
    ├── Reference Types
    │     └── Your Classes
    │
    └── System.ValueType
          ├── System.Int32
          ├── System.Boolean
          ├── System.DateTime
          └── Your Structs

CLS چیست؟

CLS مخفف Common Language Specification است. این قسمت معمولاً با CTS اشتباه گرفته می‌شود.

CTS مجموعه بزرگ قوانین Type System دات‌نت است. اما CLS یک زیرمجموعه از قواعد است که اگر Public API ما آن‌ها را رعایت کند، زبان‌های مختلف .NET راحت‌تر می‌توانند از آن API استفاده کنند.

فرق CTS و CLS با یک مثال ذهنی

CTS را مثل تمام قوانین یک کشور در نظر بگیرید. CLS را مثل یک مجموعه کوچک‌تر از قوانینی در نظر بگیرید که همه شهرها روی آن توافق کرده‌اند.

پس:

  • CTS: چه Typeهایی در .NET وجود دارند و چگونه رفتار می‌کنند؟
  • CLS: برای اینکه API بین زبان‌های مختلف .NET قابل استفاده‌تر باشد، بهتر است از چه قواعد مشترکی پیروی کنیم؟

چرا CLS در پروژه واقعی مهم می‌شود؟

اگر فقط داخل یک Application معمولی C# کار می‌کنید، معمولاً هر روز مستقیم با CLS درگیر نیستید. اما اگر یک Library عمومی می‌سازید که ممکن است از F#، Visual Basic یا سایر زبان‌های .NET مصرف شود، طراحی Public API سازگار با CLS مهم‌تر می‌شود.

چطور یک Library زبان دیگر می‌تواند کلاس C# ما را بفهمد؟

فرض کنید یک Library در C# داریم:

C#
public class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }
}

مصرف‌کننده لازم نیست Source Code C# را داشته باشد. اطلاعات Type و Method در Metadata قرار گرفته‌اند و رفتار Method در IL ذخیره شده است. یک زبان .NET دیگر می‌تواند Assembly را بخواند و این قرارداد را بفهمد.

Genericها چه ارتباطی با CTS دارند؟

Genericها هم بخشی از Type System دات‌نت هستند. وقتی می‌نویسیم:

C#
List<int> numbers = new();

اطلاعات Generic Type و Type Argument یعنی System.Int32 در Metadata قابل توصیف است. CLR و JIT نیز می‌توانند بر اساس این اطلاعات Type-safe عمل کنند.

Type Safety یعنی چه؟

Type Safety یعنی Runtime و Compiler اجازه ندهند داده‌ها به شکل نامعتبر استفاده شوند. مثلاً:

C#
int number = 10;

number = "hello"; // Compile Error

در سطح پایین‌تر نیز CLR اطلاعات Typeها را از Metadata می‌شناسد و می‌تواند در اجرای Managed Code از قراردادهای Type System استفاده کند.

یک اشتباه رایج: CLR همان C# است؟

خیر. C# یک Programming Language است. CLR یک Runtime است.

C# تنها یکی از زبان‌هایی است که می‌تواند برای .NET کد تولید کند. بنابراین:

Concept
C# != CLR

یک اشتباه رایج دیگر: CTS و CLS یکی هستند؟

خیر.

مفهوم کار اصلی
CTS تعریف Type System مشترک .NET
CLS تعریف قواعد مشترک‌تر برای سازگاری بهتر API بین زبان‌ها

همه مفاهیم در یک تصویر ذهنی

Flow
          C# Source
              |
              v
        C# Compiler
              |
              v
       ----------------
       |              |
       v              v
      IL          Metadata
                      |
                      |
       ----------------
              |
              v
             CLR
              |
              v
             JIT
              |
              v
        Machine Code

CTS در این تصویر، قرارداد مشترکی است که Typeهای داخل Metadata بر اساس آن توصیف می‌شوند. CLS هم مجموعه‌ای از قواعد برای طراحی APIهای سازگارتر بین زبان‌ها است.

اشتباهات رایج

  • اشتباه: CLR فقط موتور اجرای C# است.
    درست: CLR Runtime مشترک زبان‌های .NET است.
  • اشتباه: CTS و CLS یکی هستند.
    درست: CLS زیرمجموعه‌ای از قواعد مناسب برای Interoperability است.
  • اشتباه: C# مستقیماً همیشه به Machine Code Compile می‌شود.
    درست: در مدل معمول Managed Execution، Compiler IL و Metadata تولید می‌کند و JIT در Runtime کد Native می‌سازد.
  • اشتباه: Metadata و IL یک چیز هستند.
    درست: Metadata ساختار و قرارداد را توضیح می‌دهد؛ IL رفتار Methodها را.

جزئیات عمیق‌تر برای سطح Senior

Type System دات‌نت فقط مجموعه‌ای از نام Typeها نیست. اطلاعاتی مثل Visibility، Inheritance، Interface Implementation، Generic Parameterها، Generic Constraintها، Method Signatureها و بسیاری از قراردادهای Type در Metadata ذخیره می‌شوند.

JIT نیز صرفاً یک تبدیل مکانیکی IL به Machine Code نیست؛ می‌تواند بر اساس Runtime، معماری CPU و اطلاعات موجود Optimization انجام دهد. به همین دلیل نباید درباره شکل نهایی Machine Code یا محل دقیق همه Valueها در حافظه بدون مشاهده و اندازه‌گیری نتیجه‌گیری قطعی کرد.

در پروژه واقعی کجا این دانش به درد می‌خورد؟

  • طراحی Libraryهای عمومی .NET
  • Reflection
  • Source Generatorها و ابزارهای Code Analysis
  • درک Assembly و Dependencyها
  • Debugging مشکلات Runtime و Type Loading
  • درک بهتر Genericها، Boxing، Reflection و JIT

اگر مصاحبه‌کننده بپرسد CTS چه فایده‌ای دارد؟

می‌توانید بگویید:

«CTS یک مدل مشترک برای Typeها در .NET ایجاد می‌کند. به همین دلیل زبان‌های مختلف .NET می‌توانند Typeها، Memberها، Inheritance، Interfaceها و Genericها را به شکلی توصیف کنند که CLR همه آن‌ها را بفهمد. این موضوع پایه Interoperability و Type Safety بین زبان‌های .NET است.»

جواب پیشنهادی کامل برای مصاحبه

«وقتی کد C# را Compile می‌کنیم، Compiler معمولاً IL به همراه Metadata تولید می‌کند. Metadata قرارداد Typeها، Memberها، Visibility و روابط آن‌ها را توضیح می‌دهد و IL رفتار Methodها را نگه می‌دارد. CLR این Assembly را Load می‌کند، Typeها را بر اساس Common Type System یا CTS می‌شناسد و با کمک JIT، Methodهای موردنیاز را به Machine Code تبدیل می‌کند. CTS مدل مشترک Typeها در .NET است و باعث می‌شود زبان‌های مختلف بتوانند روی یک Runtime مشترک کار کنند. CLS هم زیرمجموعه‌ای از قواعد CTS است که برای طراحی Public APIهای سازگارتر بین زبان‌های مختلف .NET استفاده می‌شود.»

چیزی که باید از این سؤال یادت بماند

اگر فقط این زنجیره را به خاطر بسپارید، بخش بزرگی از سؤال را جواب داده‌اید: C# → IL + Metadata → CLR → JIT → Machine Code. بعد اضافه کنید: CTS قرارداد مشترک Typeها است و CLS برای سازگاری بهتر بین زبان‌ها استفاده می‌شود.
