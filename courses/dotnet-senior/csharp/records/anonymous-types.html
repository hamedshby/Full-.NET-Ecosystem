Anonymous Type چه محدودیت‌ها و کاربردهایی دارد؟

پاسخ کوتاه مصاحبه‌ای

Anonymous Type یک Reference Type تولیدشده توسط Compiler با propertyهای فقط‌خواندنی است که معمولاً برای projection محلی، به‌ویژه در LINQ، استفاده می‌شود. نام قابل‌استفاده‌ای برای قرارداد عمومی API ندارد.

مدل ذهنی ساده

وقتی داخل یک method فقط موقتاً به ترکیب Name و Total نیاز دارید، ساخت class نام‌دار ممکن است اضافه باشد. new { order.Name, Total = order.Items.Sum(...) } یک shape محلی می‌سازد. اگر داده باید از مرز method، assembly، serialization contract یا لایه عبور کند، type نام‌دار intent بهتری می‌دهد.

توضیح کامل

Compiler یک class داخلی با propertyهای inferred، constructor، Value Equality، GetHashCode و ToString تولید می‌کند. propertyها پس از construction قابل set نیستند، هرچند objectهایی که داخلشان قرار دارد می‌توانند mutable باشند. دو anonymous object در یک assembly با نام، ترتیب و type propertyهای یکسان می‌توانند از یک type تولیدشده مشترک استفاده کنند. چون نام type در source قابل بیان نیست، return عمومی معمولاً به object یا dynamic منجر می‌شود و type safety را از دست می‌دهد.

C#
var rows = users.Select(u => new
{
    u.Id,
    Display = u.FirstName + " " + u.LastName
});

رفتار مثال: projection فهرست سفارش‌ها فقط Id و Total را برای مرتب‌سازی داخلی نگه می‌دارد، پس Anonymous Type مناسب است. اگر همین داده باید از controller برگردد، OrderSummaryDto بهتر است تا قرارداد، validation و تغییر نسخه روشن باشند. property فقط‌خواندنی است، ولی اگر مقدار آن List باشد خود List هنوز تغییرپذیر است.

نکات کلیدی

  • Anonymous Type برای shape موقت و محلی مناسب است.
  • propertyها فقط‌خواندنی‌اند اما deep immutable نیستند.
  • برای مرز عمومی یا قرارداد پایدار از type نام‌دار استفاده کنید.

اشتباهات رایج

  • برگرداندن anonymous type از API عمومی
  • استفاده از dynamic برای دورزدن مرز.

جزئیات عمیق‌تر

در query providerهایی مانند Entity Framework، expression projection به Anonymous Type می‌تواند به query سمت server ترجمه شود. این یک مزیت کاربردی است، اما نباید type ناشناس را با hackهای reflection از مرز لایه‌ها عبور داد. record یا DTO نام‌دار برای reuse و مستندسازی بهتر است.

در پروژهٔ واقعی

در query داخلی فقط ستون‌های لازم را project کنید؛ پیش از خروج از لایه به DTO نام‌دار تبدیل کنید.
