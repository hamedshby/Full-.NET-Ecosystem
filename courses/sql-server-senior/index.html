درس 1 · آموزش و تمرین · درس گفت‌وگو

Clustered و Non-Clustered Index

در سیستم پرداخت، جدول Transactions می‌تواند میلیون‌ها ردیف داشته باشد. اگر برای پیدا کردن یک تراکنش هر بار همه ردیف‌ها خوانده شوند، کارایی به‌شدت افت می‌کند. ایندکس امکان پیدا کردن سریع کلید یا محدوده‌ای از کلیدها را فراهم می‌کند؛ ساختار رایج ایندکس‌های Rowstore در SQL Server از نوع B+Tree است.

مثال عملیSQL
CREATE TABLE dbo.Transactions (
    Id BIGINT NOT NULL PRIMARY KEY CLUSTERED,
    UserId BIGINT NOT NULL,
    Amount DECIMAL(18,2) NOT NULL,
    Status INT NOT NULL,
    CreatedAt DATETIME2 NOT NULL
);

Clustered Index

در Clustered Index، سطح برگ درخت حاوی خود ردیف‌های داده است؛ ردیف‌ها به ترتیب منطقی کلید سازمان‌دهی می‌شوند، نه اینکه الزاماً از نظر فیزیکی پشت سر هم باشند. هر جدول حداکثر یک Clustered Index دارد. جدول بدون آن Heap است. PRIMARY KEY می‌تواند NONCLUSTERED هم باشد.

مثال عملیSQL
SELECT * FROM dbo.Transactions WHERE Id = 125;
-- Often: Clustered Index Seek

Non-Clustered Index

این ایندکس ساختاری مجزا از داده اصلی دارد. در جدولی که Clustered Index دارد، مکان‌یاب ردیف معمولاً کلید Clustered است؛ در جدول Heap مکان‌یاب از نوع RID است.

مثال عملیSQL
CREATE NONCLUSTERED INDEX IX_Transactions_UserId
ON dbo.Transactions(UserId);

SELECT UserId, Amount, Status
FROM dbo.Transactions
WHERE UserId = 500;

ایندکس فوق می‌تواند UserId را بیابد؛ اما چون Amount و Status داخل آن نیستند، SQL Server ممکن است برای بازیابی این دو ستون عملیات Key Lookup انجام دهد. تعداد بالای Lookup هزینه‌بر است.

ویژگی Clustered Non-Clustered
تعداد در هر جدول حداکثر ۱ چندین مورد
سطح برگ ردیف کامل داده کلید، مکان‌یاب و ستون‌های INCLUDE
کاربرد نمونه جست‌وجو با Id جست‌وجو با UserId
نکته مصاحبهوجود ایندکس تضمین نمی‌کند که Optimizer از آن استفاده کند. برای Query با درصد خروجی زیاد، Scan ممکن است به‌صرفه‌تر از Seek همراه با هزاران Lookup باشد.

سؤال 1 · آمادگی مصاحبه

  1. Aچون ایندکس روی عدد ساخته نمی‌شود
  2. Bچون Amount و Status در ایندکس نیستند
  3. Cچون همیشه Table Scan لازم است
  4. Dچون جدول فقط یک Index دارد

Covering Index، INCLUDE و Key Lookup

در یک گزارش پرتکرار این Query را داریم:

مثال عملیSQL
SELECT UserId, Amount, Status
FROM dbo.Transactions
WHERE UserId = 100;

اگر ایندکس فقط UserId را نگهداری کند، خواندن دو ستون دیگر ممکن است به Key Lookup نیاز داشته باشد. می‌توان برای پوشش دادن Query این ستون‌ها را در سطح برگ ایندکس قرار داد.

مثال عملیSQL
CREATE NONCLUSTERED INDEX IX_Transactions_UserId_Cover
ON dbo.Transactions(UserId)
INCLUDE (Amount, Status);

اگر ایندکس قبلی با همین نام وجود دارد، باید آن را متناسب با شرایط بازسازی یا جایگزین کنی؛ دو تعریف هم‌نام را پشت سر هم اجرا نکن.

کلید ایندکس در برابر INCLUDE

  • ستون Key بخشی از ترتیب و ساختار جست‌وجوی ایندکس است؛ می‌تواند در Seek و عملیات مرتب‌سازی نقش داشته باشد.
  • ستون INCLUDE برای پوشاندن خروجی Query مفید است، اما بخشی از ترتیب کلید نیست و به‌تنهایی نمی‌تواند کلید Seek باشد.
  • اصطلاح Covering Index یک نوع دستور CREATE INDEX نیست؛ به معنای ایندکسی است که برای Query خاص، همه داده‌های لازم را تأمین می‌کند.
مثال عملیSQL
-- Index key = UserId; Amount is included only.
SELECT UserId, Amount, Status
FROM dbo.Transactions
WHERE Amount > 1000000;
-- A scan may be necessary; the INCLUDE column isn't a Seek key.

هزینه ایندکس زیاد

هر ایندکس به فضای ذخیره‌سازی و نگهداری نیاز دارد. درج، حذف و تغییر ستون‌های ایندکس‌شده می‌تواند گران‌تر شود؛ ایندکس‌ها را بر اساس Workload واقعی بساز، نه برای هر ستون.

احتیاط در Productionقبل و بعد از ساخت ایندکس، Logical Reads، زمان اجرا و هزینهٔ INSERT/UPDATE را اندازه بگیر. «پوشش دادن Query» لزوماً به معنی بهترین پلان نیست.

سؤال 2 · آمادگی مصاحبه

آیا INCLUDE(Amount) اجازه می‌دهد شرط WHERE Amount > 1000000 به‌صورت Seek مؤثر روی همان کلید اجرا شود؟

  1. Aبله، چون INCLUDE مانند Key است
  2. Bخیر؛ Amount کلید مرتب‌شده نیست و ممکن است Scan شود
  3. Cهمیشه Clustered Index حذف می‌شود
  4. DINCLUDE فقط برای رشته‌هاست

Composite Index و ترتیب ستون‌ها

برای این Query:

مثال عملیSQL
SELECT Id, UserId, Amount, Status
FROM dbo.Transactions
WHERE UserId = 100 AND Status = 1;

یک ایندکس ترکیبی طراحی می‌کنیم:

مثال عملیSQL
CREATE NONCLUSTERED INDEX IX_Transactions_User_Status
ON dbo.Transactions(UserId, Status)
INCLUDE (Amount);

ایندکس ابتدا بر اساس UserId و سپس درون هر گروه کاربر بر اساس Status مرتب است. در این جدول، Id به‌عنوان کلید Clustered به‌طور ضمنی در ایندکس Non-Clustered موجود است.

قانون Leftmost Prefix

شرط قابلیت متداول
UserId = 100 Seek بر اساس کلید اول
UserId = 100 AND Status = 1 Seek بر اساس هر دو کلید
Status = 1 معمولاً Scan، چون کلید اول فیلتر نشده
Amount > 1000 INCLUDE به‌تنهایی کلید Seek نیست

ترتیب نوشتن شرط‌ها در WHERE با ترتیب ستون‌های کلید یکی نیست: Optimizer قادر به بازآرایی شرط‌هاست. درباره ستون اول باید Selectivity، Queryهای پرتکرار، فیلترهای مساوی و بازه‌ای و مرتب‌سازی را هم در نظر گرفت.

وقتی شرط بازه‌ای داریم

مثال عملیSQL
CREATE INDEX IX_T_User_Date
ON dbo.Transactions(UserId, CreatedAt);

SELECT Id, CreatedAt FROM dbo.Transactions
WHERE UserId = 50
  AND CreatedAt >= '2026-10-01'
  AND CreatedAt < '2026-11-01';

وجود شرط مساوی روی ستون اول و بازه روی ستون بعدی اغلب الگوی مناسبی برای Seek محدوده‌ای است. ستون‌های بعد از یک شرط بازه‌ای لزوماً همگی در محدود کردن Seek کمک یکسان نمی‌کنند.

نکته سنیوربهترین ترتیب کلیدها فقط با قاعدهٔ «ستون پرانتخاب‌تر اول باشد» تعیین نمی‌شود. الگوی predicate، ORDER BY، بازه، آماری بودن ستون‌ها و هزینهٔ نگهداری را با هم بررسی کن.

سؤال 3 · آمادگی مصاحبه

  2. BAmount > 1000000
  3. CUserId = 100 AND Status = 1
  4. DStatus = 1 AND Amount > 1000000

Execution Plan، Index Seek و Index Scan

Execution Plan نشان می‌دهد SQL Server برای اجرای یک Query کدام عملیات را انتخاب کرده است: جست‌وجوی ایندکس، اسکن، Join، Sort و غیره. Estimated Plan فقط برآورد است؛ Actual Plan اطلاعات اجرا، از جمله تعداد واقعی ردیف‌های پردازش‌شده، را نیز می‌دهد.

تفاوت Seek و Scan

  • Index Seek: ورود به موقعیت یا محدوده‌ای از کلیدهای ایندکس و خواندن داده‌های لازم؛ ممکن است محدوده بزرگی را نیز پیمایش کند.
  • Index Scan: پیمایش بخشی بزرگ یا همه برگ‌های ایندکس؛ لزوماً بد نیست.
  • Clustered Index Scan: خواندن داده‌های جدول سازمان‌یافته با ایندکس Clustered.
  • Key Lookup: مراجعه به Clustered Index برای ستون‌هایی که در Non-Clustered Index پوشش داده نشده‌اند.

ابزارهای بررسی

در SSMS با Ctrl + M گزینه Include Actual Execution Plan را فعال کن. سپس Query را با اطلاعات IO و Time اجرا کن:

مثال عملیSQL
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT Id, UserId, Amount
FROM dbo.Transactions
WHERE UserId = 100;
معیار تفسیر
Logical Reads تعداد صفحات خوانده‌شده از Buffer Pool
CPU Time زمان مصرف CPU
Elapsed Time زمان سپری‌شده شامل انتظارها
Estimated Rows پیش‌بینی Optimizer
Actual Rows تعداد ردیف‌های واقعی اپراتور

مثال مقایسه

فرض کن Plan A از Seek + Key Lookup با ۵۰هزار Logical Reads و Plan B از Scan با ۵هزار Reads استفاده می‌کند. نمی‌توان از روی نام اپراتور نتیجه گرفت A بهتر است؛ معیارهای واقعی و تعداد ردیف‌های نهایی را بسنج.

پاسخ مصاحبه«ابتدا Actual Plan و STATISTICS IO/TIME را بررسی می‌کنم، اپراتورهای پرهزینه و اختلاف Estimated/Actual Rows را پیدا می‌کنم و بعد تغییر Query یا ایندکس را آزمایش می‌کنم.»

سؤال 4 · آمادگی مصاحبه

اگر Seek+Lookup دارای ۵۰هزار و Scan دارای ۵هزار Logical Reads باشد، کدام نتیجه‌گیری منطقی‌تر است؟

  1. ASeek قطعاً بهتر است
  2. BScan قطعاً سریع‌تر است
  3. CScan ممکن است بهتر باشد، اما باید زمان و CPU را هم دید
  4. Dهر دو برابرند

Statistics و تخمین تعداد ردیف‌ها

Query Optimizer باید تخمین بزند هر شرط چند ردیف برمی‌گرداند تا بین Seek، Scan، Nested Loops، Hash Join و سایر عملیات انتخاب کند. این برآورد با استفاده از Statistics صورت می‌گیرد؛ هر Statistics ممکن است Histogram و اطلاعات چگالی داشته باشد.

فرض کن ۱۰ میلیون تراکنش داریم: ۹۵٪ موفق، ۴٪ ناموفق و ۱٪ در انتظار. اگر Optimizer تعداد تراکنش‌های در انتظار را اشتباه تخمین بزند، برنامه ممکن است برای حجم داده نادرستی بهینه شود.

مثال عملیSQL
SELECT Id, Amount FROM dbo.Transactions
WHERE Status = 0;

چطور بررسی کنیم؟

مثال عملیSQL
-- Check available statistics:
SELECT name, auto_created, user_created
FROM sys.stats
WHERE object_id = OBJECT_ID('dbo.Transactions');

-- For a known statistic/index name:
DBCC SHOW_STATISTICS
('dbo.Transactions', 'IX_Transactions_UserId');

-- Refresh only when justified:
UPDATE STATISTICS dbo.Transactions;

پیش از اجرای DBCC SHOW_STATISTICS باید مطمئن باشی Statistics با همان نام وجود دارد. SQL Server معمولاً AUTO_CREATE_STATISTICS و AUTO_UPDATE_STATISTICS دارد، ولی نرخ تغییر، نمونه‌گیری و الگوی توزیع داده‌ها همچنان مهم‌اند.

نشانه‌های تخمین غلط

  • اختلاف زیاد Estimated Rows و Actual Rows.
  • انتخاب نوع Join نامناسب یا Memory Grant نامتناسب.
  • تغییر چشمگیر Plan پس از رشد داده‌ها یا تغییر توزیع مقادیر.

این اختلاف همیشه نشانه Statistics قدیمی نیست؛ پیچیدگی شرط‌ها، همبستگی ستون‌ها، Parameter Sniffing و سایر عوامل هم دخیل‌اند.

نکته Productionدستور UPDATE STATISTICS را بی‌هدف یا در اوج بار اجرا نکن. ابتدا آمار موجود، تاریخ آخرین به‌روزرسانی و اثر احتمالی روی Recompile را بررسی کن.

سؤال 5 · آمادگی مصاحبه

وقتی Estimated Rows و Actual Rows اختلاف شدیدی دارند، اولین بررسی مناسب چیست؟

  1. Aهمه Indexها را حذف و بازسازی کنیم
  2. BCPU سرور را زیاد کنیم
  3. CStatistics و کیفیت تخمین‌ها را بررسی کنیم
  4. Dهمه Queryها را Stored Procedure کنیم

SARGable و نوشتن شرط قابل جست‌وجو

SARGable یعنی شرط Query بتواند به‌خوبی از ترتیب کلید ایندکس برای یافتن یک مقدار یا محدوده استفاده کند. قرار دادن تابع روی ستون فیلترشده، تبدیل ضمنی نامناسب یا استفاده از الگوهای خاص LIKE ممکن است Seek مؤثر را دشوار کند.

مثال گزارش روزانه

مثال عملیSQL
CREATE INDEX IX_T_CreatedAt
ON dbo.Transactions(CreatedAt);

-- Usually less favorable:
SELECT * FROM dbo.Transactions
WHERE YEAR(CreatedAt) = 2026;

-- Usually more index-friendly:
SELECT * FROM dbo.Transactions
WHERE CreatedAt >= '20260101'
  AND CreatedAt < '20270101';

برای یک روز نیز از بازه نیمه‌باز استفاده کن؛ این کار بخش زمانی DATETIME2 را درست پوشش می‌دهد:

مثال عملیSQL
WHERE CreatedAt >= '20261016'
  AND CreatedAt < '20261017';

استثناهای مهم

تبدیل CAST(CreatedAt AS date) در برخی حالت‌های SQL Server می‌تواند از Dynamic Seek استفاده کند؛ بنابراین عبارت «هر تابعی حتماً Scan می‌شود» دقیق نیست. اما شرایط بازه‌ای صریح معمولاً قابل‌پیش‌بینی‌ترند.

مثال عملیSQL
-- Leading wildcard often limits an ordinary index Seek:
WHERE StoreName LIKE N'%بازار%';

-- A prefix can be more Seek-friendly:
WHERE StoreName LIKE N'بازار%';

در کنار این‌ها، نوع داده پارامترهای .NET را با ستون دیتابیس سازگار نگه دار تا Implicit Conversion روی ستون به مشکل تبدیل نشود.

سناریوی مصاحبهاگر روی CreatedAt ایندکس داریم ولی گزارش سالانه کند است، پیش از افزودن ایندکس تازه بررسی می‌کنم که predicate به‌صورت بازه‌ای و SARGable نوشته شده باشد.

سؤال 6 · آمادگی مصاحبه

کدام WHERE برای جست‌وجوی تراکنش‌های ۲۰۲۶ معمولاً Index-friendlyتر است؟

  1. AYEAR(CreatedAt)=2026
  2. BCONVERT(VARCHAR,CreatedAt,120) LIKE '2026%'
  3. CCreatedAt >= '20260101' AND CreatedAt < '20270101'
  4. DDATEPART(YEAR,CreatedAt)=2026

درس 7 · آموزش و تمرین · درس گفت‌وگو

Parameter Sniffing و Plan Cache

در یک Stored Procedure ممکن است مقادیر مختلف یک پارامتر، تعداد ردیف‌های کاملاً متفاوتی داشته باشند. SQL Server در زمان کامپایل ممکن است مقدار همان اجرای اول را ببیند (Parameter Sniffing) و برنامه را Cache کند.

مثال عملیSQL
CREATE OR ALTER PROCEDURE dbo.GetTransactions
    @Status INT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT * FROM dbo.Transactions
    WHERE Status = @Status;
END;

EXEC dbo.GetTransactions @Status = 2;
EXEC dbo.GetTransactions @Status = 1;

فرض کن وضعیت ۲ تنها ۱٪ و وضعیت ۱ حدود ۹۹٪ رکوردها را شامل می‌شود. پلانی که برای مقدار کم‌تکرار خوب است ممکن است برای مقدار پرتکرار مناسب نباشد. خود Parameter Sniffing یک قابلیت بهینه‌سازی طبیعی است؛ استفاده مجدد از یک Plan نامتناسب مسئله اصلی است.

راه‌های تحلیل و رفع مشکل

  1. Actual Execution Plan و Query Store را برای مقادیر متفاوت مقایسه کن.
  2. توزیع داده‌ها، ایندکس‌ها و Statistics را بررسی کن.
  3. در صورت نیاز از OPTION (RECOMPILE)، OPTIMIZE FOR یا راهکارهای انتخاب Plan استفاده کن.
  4. قابلیت Parameter Sensitive Plan Optimization در نسخه‌ها و Compatibility Levelهای پشتیبانی‌شده می‌تواند برای بازه‌های مختلف پارامتر برنامه‌های متفاوتی نگه دارد.
مثال عملیSQL
SELECT Id, Status, Amount
FROM dbo.Transactions
WHERE Status = @Status
OPTION (RECOMPILE);

OPTION (RECOMPILE) اجرای همان Statement را دوباره کامپایل می‌کند و هزینه CPU کامپایل دارد؛ برای یک endpoint پرتکرار نباید بدون اندازه‌گیری سراغ آن رفت.

جواب مصاحبه«برای Parameter Sniffing ابتدا وابستگی کارایی به مقدار پارامتر و Planهای ذخیره‌شده را ثابت می‌کنم. سپس با توجه به نسخه SQL Server، اصلاح Index/Stats، Query Store یا Recompile را انتخاب می‌کنم.»

Transaction، COMMIT، ROLLBACK و ACID

در یک انتقال پول، کم کردن مبلغ از حساب A و افزودن همان مبلغ به حساب B باید به‌شکل یک واحد اتمیک اجرا شوند. Transaction تضمین می‌کند تغییرات آن واحد با هم Commit یا Rollback شوند؛ البته قواعد تجاری مانند موجودی کافی و وجود حساب‌ها باید جداگانه اعتبارسنجی شوند.

مثال عملیSQL
SET XACT_ABORT ON;
BEGIN TRY
    BEGIN TRANSACTION;

    UPDATE dbo.Accounts
    SET Balance = Balance - 1000000
    WHERE Id = 1;

    UPDATE dbo.Accounts
    SET Balance = Balance + 1000000
    WHERE Id = 2;

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    THROW;
END CATCH;

این کد فقط ساختار Transaction را نشان می‌دهد، نه پیاده‌سازی کامل انتقال مالی؛ در سیستم واقعی باید شرط کافی بودن موجودی، تعداد ردیف‌های تغییرکرده و جلوگیری از تکرار درخواست لحاظ شود.

چهار اصل ACID

اصل تعریف در انتقال پول
Atomicity همه عملیات یا هیچ‌کدام برداشت و واریز با هم
Consistency حفظ قیود و قواعد داده عدم نقض قواعد موجودی
Isolation کنترل اثر هم‌زمانی جلوگیری از تداخل ناسالم
Durability ماندگاری داده Commitشده ثبت پایدار انتقال

ROLLBACK چه می‌کند؟

اگر در داخل Transaction موجودی ۵ میلیون به ۴ میلیون تغییر کند ولی سپس ROLLBACK اجرا شود، مقدار Commitشده قبلی برقرار می‌ماند.

مرز TransactionTransaction محلی SQL Server به‌تنهایی انتشار پیام RabbitMQ یا فراخوانی HTTP بیرونی را اتمیک نمی‌کند. برای ارتباط میان سرویس‌ها از الگوهایی مانند Transactional Outbox و جبران‌سازی استفاده می‌شود.

Isolation Level و Dirty Read

Isolation Level تعیین می‌کند اجرای هم‌زمان تراکنش‌ها هنگام خواندن و نوشتن داده چگونه روی یکدیگر اثر بگذارند. مشکل نخست Dirty Read است: خواندن تغییراتی که هنوز Commit نشده‌اند و ممکن است Rollback شوند.

مثال دو Connection

اتصال A:

مثال عملیSQL
BEGIN TRANSACTION;
UPDATE dbo.Accounts
SET Balance = 4000000
WHERE Id = 1;
-- Do not commit yet.

اتصال B:

مثال عملیSQL
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT Balance FROM dbo.Accounts WHERE Id = 1;

اتصال B ممکن است مقدار ۴ میلیون را ببیند. اگر A بعداً ROLLBACK کند، مقدار خوانده‌شده B هرگز نهایی نشده است.

سطح‌های اصلی Isolation

سطح نکته کلیدی
READ UNCOMMITTED ممکن است داده Commitنشده خوانده شود
READ COMMITTED جلوگیری از Dirty Read؛ رفتار خواندن بسته به RCSI
REPEATABLE READ جلوگیری از تغییر ردیف‌های خوانده‌شده در طول تراکنش
SERIALIZABLE محافظت از ردیف‌ها و بازه‌های خوانده‌شده
SNAPSHOT مشاهده نسخه سازگار داده‌ها در سطح تراکنش

در READ COMMITTED مبتنی بر قفل، خواندن ردیف در حال تغییر ممکن است منتظر بماند؛ با فعال بودن READ_COMMITTED_SNAPSHOT معمولاً نسخه Commitشده پیشین خوانده می‌شود.

هشدار درباره NOLOCK

WITH (NOLOCK) تقریباً به معنای READ UNCOMMITTED برای خواندن جدول است. استفاده از آن در گزارش مالی می‌تواند داده Commitنشده یا نتایج ناسازگار تولید کند؛ حتی تضمین نمی‌کند هیچ Blocking نداشته باشیم.

نکته سنیور«NOLOCK برای رفع کندی Query» راه‌حل عمومی قابل اعتمادی نیست. نخست علت انتظار، ایندکس، طرح اجرای Query و امکان Row Versioning را بررسی کن.

Non-Repeatable Read و Phantom Read

READ COMMITTED از Dirty Read جلوگیری می‌کند، اما معمولاً تضمین نمی‌کند که اجرای دوباره یک Query در همان تراکنش نتیجه قبلی را برگرداند.

Non-Repeatable Read

تراکنش A موجودی حساب ۱ را ۵ میلیون می‌خواند. تراکنش B همان ردیف را به ۳ میلیون تغییر می‌دهد و Commit می‌کند. تراکنش A در دومین خواندن همان ردیف ۳ میلیون می‌بیند. یک ردیف قبلی مقدار متفاوت داده است.

مثال عملیSQL
-- Connection A:
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
SELECT Balance FROM dbo.Accounts WHERE Id = 1; -- 5m
-- B commits an UPDATE here.
SELECT Balance FROM dbo.Accounts WHERE Id = 1; -- 3m
COMMIT;

Phantom Read

تراکنش A تعداد ردیف‌های Status=2 را ۱۰۰ می‌بیند. تراکنش B یک ردیف جدید با همین وضعیت اضافه می‌کند و Commit می‌کند. اجرای مجدد همان Query در A تعداد ۱۰۱ را نشان می‌دهد. مجموعه ردیف‌های منطبق با شرط تغییر کرده است.

مثال عملیSQL
SELECT COUNT(*)
FROM dbo.Transactions
WHERE Status = 2;
-- Repeated inside one transaction after another commit.

تغییر وضعیت یک ردیف به مقداری که وارد/خارج از محدوده شرط شود هم می‌تواند از نظر مجموعه نتایج نقش مشابهی داشته باشد.

سطح Dirty Read Non-Repeatable Phantom
READ UNCOMMITTED ممکن ممکن ممکن
READ COMMITTED ممنوع ممکن ممکن
REPEATABLE READ ممنوع ممنوع ممکن
SERIALIZABLE ممنوع ممنوع ممنوع
SNAPSHOT ممنوع در Snapshot ثابت در Snapshot ثابت
تفاوت کلیدیNon-Repeatable Read = تغییر مقدار یک ردیف دیده‌شده؛ Phantom Read = تغییر اعضای مجموعهٔ نتایج یک شرط.

درس 11 · آموزش و تمرین · درس گفت‌وگو

Blocking و Lock در SQL Server

وقتی تراکنشی قفلی دارد و تراکنش دیگر برای ادامه به قفل ناسازگار نیاز پیدا می‌کند، Blocking اتفاق می‌افتد. این الزاماً خطا نیست؛ اغلب بخشی از حفاظت در برابر تغییر هم‌زمان ناسازگار است.

اتصال A:

مثال عملیSQL
BEGIN TRANSACTION;
UPDATE dbo.Accounts SET Balance = Balance - 100
WHERE Id = 1;
-- Open transaction: X lock can remain until commit.

اتصال B:

مثال عملیSQL
UPDATE dbo.Accounts SET Balance = Balance - 200
WHERE Id = 1;
-- Usually waits for A under ordinary locking rules.

گونه‌های مهم قفل

  • Shared (S): برای خواندن قفل‌محور؛ با S دیگر سازگار و با X ناسازگار است.
  • Exclusive (X): برای تغییر داده؛ با بیشتر قفل‌های هم‌پوشان ناسازگار است.
  • Update (U): برای کاهش بعضی بن‌بست‌های تبدیل قفل در الگوی خواندن-سپس-نوشتن.
  • Intent Locks: نشانه قصد قفل‌گذاری در سطوح پایین‌تر، مانند صفحه یا ردیف.

چرا Blocking طولانی می‌شود؟

تراکنش طولانی، انتظار روی API خارجی در داخل Transaction، Query بی‌ایندکس، اسکن زیاد، قفل‌گذاری گسترده و تعداد زیاد درخواست‌های هم‌زمان می‌توانند صف انتظار بسازند.

مثال عملیSQL
-- A simple view of currently waiting requests:
SELECT session_id, blocking_session_id,
       wait_type, wait_time, status
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

این DMV برای دیدن درخواست‌های فعال است و در محیط عملی مجوزهای مناسب نیاز دارد.

نکته امنیت عملیاتیبرای رفع Blocking، تراکنش‌های فعال را کورکورانه KILL نکن. مالک تراکنش، مرحله عملیات مالی و پیامد Rollback را شناسایی کن.

Deadlock، خطای 1205 و پیشگیری

در Deadlock دو یا چند تراکنش به‌شکل چرخه‌ای منتظر منابع یکدیگرند؛ برخلاف Blocking ساده، بدون دخالت نمی‌توانند پیش بروند.

نمونه انتقال دوطرفه

اتصال A:

مثال عملیSQL
BEGIN TRANSACTION;
UPDATE dbo.Accounts SET Balance = Balance - 100 WHERE Id = 1;
WAITFOR DELAY '00:00:05';
UPDATE dbo.Accounts SET Balance = Balance + 100 WHERE Id = 2;
COMMIT;

اتصال B:

مثال عملیSQL
BEGIN TRANSACTION;
UPDATE dbo.Accounts SET Balance = Balance - 200 WHERE Id = 2;
WAITFOR DELAY '00:00:05';
UPDATE dbo.Accounts SET Balance = Balance + 200 WHERE Id = 1;
COMMIT;

اگر ترتیب اجرای هم‌زمان مناسب باشد، A قفل حساب ۱ و B قفل حساب ۲ را نگه می‌دارند و هرکدام منتظر حساب دیگری می‌شوند. SQL Server یکی را به‌عنوان Deadlock Victim انتخاب می‌کند، Transaction او را Rollback می‌کند و خطای 1205 برمی‌گرداند.

راهکارهای کاهش احتمال

  1. منابع مشترک را در تمام مسیرهای کد با ترتیب ثابت دسترسی بده؛ مثلاً شناسه حساب کوچک‌تر، بعد بزرگ‌تر.
  2. Transaction را کوتاه نگه دار؛ تماس شبکه‌ای خارجی را درون آن نگه ندار.
  3. با ایندکس مناسب، دامنه ردیف‌های لمس‌شده را کاهش بده.
  4. Deadlock Graph را در Extended Events / system_health بررسی کن تا چرخه واقعی و منابع مشخص شوند.
  5. عملیات قربانی را با Retry محدود، Backoff و کنترل Idempotency دوباره اجرا کن.
تفاوت بنیادینBlocking = یک انتظار یک‌طرفه که ممکن است برطرف شود؛ Deadlock = انتظار چرخه‌ای. افزایش CommandTimeout درمان Deadlock نیست.

Retry تراکنشی در EF Core و Idempotency

وقتی SQL Server خطای 1205 می‌دهد، تراکنش قربانی Rollback شده است. فقط Statement شکست‌خورده را Retry نکن؛ واحد کاری باید به‌صورت کامل و در Transaction جدید دوباره اجرا شود.

استفاده از Execution Strategy

مثال عملیC#
builder.Services.AddDbContextFactory<PaymentDbContext>(options =>
    options.UseSqlServer(connectionString, sql =>
        sql.EnableRetryOnFailure(
            maxRetryCount: 3,
            maxRetryDelay: TimeSpan.FromSeconds(2),
            errorNumbersToAdd: null)));

اگر BeginTransactionAsync را خودمان مدیریت می‌کنیم، باید تمام کار تراکنشی را داخل ExecuteAsync قرار بدهیم:

مثال عملیC#
await using var strategyContext =
    await factory.CreateDbContextAsync();
var strategy = strategyContext.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var db = await factory.CreateDbContextAsync();
    await using var tx = await db.Database.BeginTransactionAsync();

    // ProcessAsync must be idempotent by a unique RequestId
    // and perform all database writes in this transaction.
    await ProcessAsync(db, requestId);

    await tx.CommitAsync();
});

در این کد ProcessAsync یک متد فرضی است. پیاده‌سازی کامل آن باید قفل‌ها/شرط‌های موجودی، RequestId یکتا و خطاهای ناشی از تکرار را مدیریت کند.

چرا Idempotency لازم است؟

اگر اتصال در لحظه Commit قطع شود، برنامه ممکن است نداند Transaction واقعاً ثبت شده یا خیر. این حالت Unknown Commit Outcome است؛ اجرای مجدد کورکورانه می‌تواند انتقال دوباره بسازد. شناسه درخواست را با Unique Index در دیتابیس ذخیره کن و قبل از تلاش دوباره، نتیجه ثبت‌شده را قابل بازیابی کن.

مثال عملیSQL
CREATE UNIQUE INDEX UX_Transfers_RequestId
ON dbo.Transfers(RequestId);
نکته حساس مالیIdempotency فقط چک‌کردن قبل از INSERT نیست؛ باید با محدودیت یکتایی و تغییرات مالی در مرز اتمیک صحیح پیاده‌سازی شود. فراخوانی HTTP و Publish مستقیم را در delegate تکرارشونده قرار نده مگر اثر تکرار آنها کنترل شده باشد.

SNAPSHOT، RCSI و SERIALIZABLE

گاهی می‌خواهیم هم خواندن داده‌ها سازگار باشد و هم خواندن‌ها کمترین تداخل را با نوشتن داشته باشند. SQL Server دو قابلیت مرتبط اما متفاوت برای Row Versioning دارد: READ_COMMITTED_SNAPSHOT یا RCSI و سطح SNAPSHOT.

RCSI: دید ثابت در سطح هر Statement

وقتی RCSI فعال است، خواندن معمولی در READ COMMITTED نسخه Commitشده مناسب همان Statement را می‌بیند. دو SELECT متوالی در یک Transaction می‌توانند نتیجه متفاوت داشته باشند.

مثال عملیSQL
ALTER DATABASE PaymentDb
SET READ_COMMITTED_SNAPSHOT ON;

SNAPSHOT: دید ثابت در سطح Transaction

در SNAPSHOT تمام خواندن‌های عادی Transaction نمای سازگار یکسانی از داده‌ها می‌بینند؛ در SQL Server نقطه Snapshot معمولاً با نخستین دسترسی به داده پس از شروع تراکنش تثبیت می‌شود.

مثال عملیSQL
ALTER DATABASE PaymentDb

GO

BEGIN TRANSACTION;

-- Another transaction commits a change.

اگر اولین خواندن ۵ میلیون بوده، خواندن دوم همان مقدار را مشاهده می‌کند؛ اما تلاش برای تغییر ردیفی که پس از نقطه Snapshot توسط تراکنش دیگری تغییر کرده ممکن است با Update Conflict 3960 مواجه شود.

SERIALIZABLE: محافظت قفل‌محور از محدوده

این سطح از ردیف‌ها و محدوده‌های منطبق با شرایط محافظت می‌کند و جلوی Phantom Read را می‌گیرد؛ در عوض احتمال Blocking و Deadlock بیشتر است.

Lost Update و کنترل برداشت هم‌زمان

این درس، ادامه تکمیلی دوره است: چگونه از برداشت اشتباه در اثر دو درخواست هم‌زمان جلوگیری کنیم؟ فرض کن موجودی حساب ۱ برابر ۱۰۰۰ است و دو درخواست می‌خواهند هر کدام ۸۰۰ برداشت کنند.

روش خطرناک: Read → Check → Write

مثال عملیC#
var account = await db.Accounts.SingleAsync(x => x.Id == 1);
if (account.Balance >= 800)
{
    account.Balance -= 800;
    await db.SaveChangesAsync();
}

اگر دو درخواست مستقل هر دو مقدار ۱۰۰۰ را قبل از ذخیره ببینند، هر دو ممکن است مجاز تصور شوند. بسته به نحوه هم‌زمانی، از دست رفتن تغییر (Lost Update)، خطای Concurrency یا اجرای خلاف قاعده مالی ممکن است رخ دهد.

راه ۱: Conditional UPDATE اتمیک

مثال عملیSQL
UPDATE dbo.Accounts
SET Balance = Balance - @Amount
WHERE Id = @AccountId
  AND Balance >= @Amount;

-- Check @@ROWCOUNT = 1 before considering it successful.

در یک Statement، شرط موجودی و تغییر آن با هم اجرا می‌شوند. اگر یک درخواست ۸۰۰ برداشت کند، درخواست دوم با موجودی ۲۰۰ شرط را پاس نمی‌کند و @@ROWCOUNT صفر می‌شود. ثبت تراکنش مالی و RequestId باید در همان Transaction انجام شود.

راه ۲: Optimistic Concurrency با RowVersion

مثال عملیSQL
ALTER TABLE dbo.Accounts
ADD RowVer ROWVERSION;
مثال عملیC#
modelBuilder.Entity<Account>()
    .Property(x => x.RowVer)
    .IsRowVersion();

در الگوی EF Core اگر ردیف از زمان خواندن تغییر کرده باشد، UPDATE شرط نسخه را پاس نمی‌کند و ممکن است DbUpdateConcurrencyException رخ دهد. سپس داده تازه خوانده می‌شود و قانون تجاری دوباره ارزیابی می‌شود؛ Retry کورکورانه با همان موجودی قبلی اشتباه است.

تغییر چند حساب با قفل مشخص Transaction + ترتیب ثابت + کنترل قانون

Lock Hints و الگوهای قفل‌گذاری

در حالت عادی SQL Server با توجه به Isolation Level و Plan قفل‌ها را مدیریت می‌کند. Lock Hints مانند UPDLOCK، HOLDLOCK و ROWLOCK ابزارهای خاص هستند؛ استفاده نادرست می‌تواند فشار قفل‌ها و Deadlock را بیشتر کند.

چه زمانی UPDLOCK مفید است؟

اگر ناچار باشیم یک ردیف را بخوانیم و سپس بر اساس همان خواندن آن را تغییر دهیم، UPDLOCK می‌تواند تبدیل هم‌زمان قفل Shared به Exclusive را در برخی الگوها کنترل کند.

مثال عملیSQL
BEGIN TRANSACTION;

SELECT Balance
FROM dbo.Accounts WITH (UPDLOCK, HOLDLOCK)
WHERE Id = @AccountId;

-- Validate and perform the UPDATE here.
-- The transaction must remain open until the write is committed.

COMMIT;

HOLDLOCK روی آن مرجع جدول معنایی هم‌ارز Serializable دارد؛ بسته به ایندکس و predicate می‌تواند قفل‌های محدوده‌ای ایجاد کند. این صرفاً یک اسکلت است و برای انتقال پول به بررسی شرایط و کد کامل نیاز دارد.

چند Hint رایج

Hint توضیح
UPDLOCK استفاده از قفل Update هنگام خواندن
HOLDLOCK رفتار Serializable برای مرجع جدول
ROWLOCK درخواست قفل‌گذاری در گرانول ردیف؛ تضمین مطلق نیست
READPAST رد کردن بعضی ردیف‌های قفل‌شده در شرایط پشتیبانی‌شده
NOLOCK امکان خواندن Dirty؛ مناسب صحت مالی نیست

سناریوی صف کاری

در ساخت Worker مبتنی بر جدول SQL، گاهی READPAST برای رد کردن رکوردهای در حال پردازش به‌کار می‌رود، اما باید شرایط Isolation، وضعیت رزرو کار و قابلیت بازیابی پس از Crash بررسی شود.

پیش از Hintنخست Query و ایندکس و الگوی تراکنش را اصلاح کن. Hint می‌تواند Optimizer را محدود کند و با تغییر Workload نتیجه نامطلوب بدهد.

Temp Table، Table Variable و CTE

در Queryهای پیچیده گاهی لازم است نتایج میانی را نگه داریم، چندبار استفاده کنیم یا در همان Statement ساختار خواناتری بسازیم. سه ابزار معمول: #Temp Table، متغیر جدول @Table و CTE.

CTE: نام‌گذاری نتیجه در سطح یک Statement

مثال عملیSQL
WITH RecentPayments AS (
    SELECT Id, UserId, Amount
    FROM dbo.Transactions
    WHERE CreatedAt >= '20261001'
)
SELECT UserId, COUNT(*) AS Total
FROM RecentPayments
GROUP BY UserId;

CTE معمولی به‌طور خودکار Materialize نمی‌شود؛ بیشتر یک بیان منطقی Query است. ارجاع‌های چندباره لزوماً ذخیره نتیجه را تضمین نمی‌کند. برای بازگشت سلسله‌مراتبی، Recursive CTE نیز وجود دارد.

Temp Table: ذخیره موقت فیزیکی

مثال عملیSQL
SELECT Id, UserId, Amount
INTO #RecentPayments
FROM dbo.Transactions
WHERE CreatedAt >= '20261001';

CREATE INDEX IX_Recent_UserId
ON #RecentPayments(UserId);

SELECT UserId, SUM(Amount)
FROM #RecentPayments
GROUP BY UserId;

#Temp Table در tempdb نگهداری می‌شود؛ می‌توان برای آن ایندکس ایجاد کرد و معمولاً Statistics مناسبی نیز دارد. برای نتایج میانی پرحجم یا استفاده چندباره ارزش بررسی دارد، ولی ایجاد آن IO و هزینه tempdb دارد.

Table Variable

مثال عملیSQL
DECLARE @SelectedUsers TABLE (
    UserId BIGINT PRIMARY KEY
);
INSERT INTO @SelectedUsers(UserId) VALUES (100), (200);
SELECT * FROM @SelectedUsers;

Table Variable هم از منابع tempdb بهره می‌گیرد و به‌طور سنتی اطلاعات آماری محدودتری نسبت به Temp Table دارد. ویژگی Deferred Compilation در نسخه‌ها و سطوح سازگاری جدیدتر می‌تواند بعضی تخمین‌ها را بهتر کند؛ پس جمله «Table Variable همیشه کندتر است» درست نیست.

Window Functions: ROW_NUMBER، RANK و LAG

توابع پنجره‌ای محاسبه را روی گروهی از ردیف‌ها انجام می‌دهند، بدون اینکه مثل GROUP BY لزوماً خروجی را به یک ردیف در هر گروه تبدیل کنند. عبارت OVER پنجره را تعیین می‌کند.

آخرین سه تراکنش هر کاربر

مثال عملیSQL
WITH Ranked AS (
    SELECT Id, UserId, Amount, CreatedAt,
           ROW_NUMBER() OVER (
               PARTITION BY UserId
               ORDER BY CreatedAt DESC, Id DESC
           ) AS rn
    FROM dbo.Transactions
)
SELECT * FROM Ranked WHERE rn <= 3;

PARTITION BY داده‌ها را به گروه‌های منطقی تقسیم می‌کند. ORDER BY ترتیب رتبه‌دهی است؛ افزودن Id به‌عنوان Tie-breaker، نتیجه را در صورت تساوی تاریخ پایدارتر می‌کند.

تفاوت ROW_NUMBER، RANK و DENSE_RANK

اگر مبالغ مرتب‌شده برابر [100, 100, 80] باشند:

مقدار ROW_NUMBER RANK DENSE_RANK
100 (اول) 1 1 1
100 (دوم) 2 1 1
80 3 3 2

در داده‌های هم‌ارزش، ROW_NUMBER شماره متفاوت می‌دهد، RANK فاصله می‌اندازد و DENSE_RANK فاصله نمی‌اندازد.

LAG و محاسبه اختلاف با رویداد قبلی

مثال عملیSQL
SELECT UserId, CreatedAt, Amount,
       LAG(Amount) OVER (
           PARTITION BY UserId
           ORDER BY CreatedAt, Id
       ) AS PreviousAmount
FROM dbo.Transactions;

جمع تجمعی

مثال عملیSQL
SELECT UserId, CreatedAt, Amount,
       SUM(Amount) OVER (
           PARTITION BY UserId
           ORDER BY CreatedAt, Id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningTotal
FROM dbo.Transactions;

این مثال جمع تجمعی مبلغ تراکنش‌ها را می‌دهد؛ جایگزین Ledger معتبر و محاسبه مانده مالی نیست.

بهینه‌سازیبرای Window Functionهای پرتکرار، ترتیب کلید ایندکس متناسب با PARTITION BY و ORDER BY را بررسی کن تا هزینه Sort کاهش یابد.

Stored Procedure، View و Function

در مصاحبه ممکن است بپرسند «منطق Query را در Stored Procedure نگه می‌داری یا در EF Core؟» پاسخ به نیاز کسب‌وکار، کنترل اجرای Query، امنیت و نگهداری بستگی دارد؛ هیچ گزینه‌ای همیشه برتر نیست.

Stored Procedure

برای عملیات چندمرحله‌ای، دریافت پارامتر، Transaction و منطق SQL متمرکز مناسب است:

مثال عملیSQL
CREATE OR ALTER PROCEDURE dbo.GetUserTransactions
    @UserId BIGINT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT Id, Amount, Status
    FROM dbo.Transactions
    WHERE UserId = @UserId;
END;

View

یک Query نام‌گذاری‌شده است که مانند جدول مجازی قابل استفاده است؛ View عادی به معنای ذخیره فیزیکی نتیجه نیست.

مثال عملیSQL
CREATE OR ALTER VIEW dbo.SuccessfulTransactions
AS
SELECT Id, UserId, Amount, CreatedAt
FROM dbo.Transactions
WHERE Status = 1;
GO
SELECT * FROM dbo.SuccessfulTransactions;

Function

Scalar UDF مقداری بازمی‌گرداند و Table-Valued Function مجموعه‌ای از ردیف‌ها؛ برخی انواع UDF می‌توانند محدودیت عملکردی داشته باشند. SQL Server در نسخه‌های جدید برای بعضی Scalar UDFها قابلیت Inlining دارد، اما باید Plan واقعی بررسی شود.

مثال عملیSQL
CREATE OR ALTER FUNCTION dbo.TransactionsForUser(@UserId BIGINT)
RETURNS TABLE
AS RETURN
(
    SELECT Id, Amount, Status
    FROM dbo.Transactions
    WHERE UserId = @UserId
);
GO
SELECT * FROM dbo.TransactionsForUser(100);

JOIN، GROUP BY، WHERE و HAVING

در مصاحبه سنیور باید تفاوت Joinهای اصلی، جایگاه شرط‌ها و مدیریت ردیف‌های گمشده را دقیق بدانی. فرض کن دو جدول Users و Transactions داریم.

انواع JOIN

مثال عملیSQL
-- Only matching rows
SELECT u.Id, t.Id AS TransactionId
FROM dbo.Users AS u
INNER JOIN dbo.Transactions AS t ON t.UserId = u.Id;

-- Keep users without any transaction too
SELECT u.Id, t.Id AS TransactionId
FROM dbo.Users AS u
LEFT JOIN dbo.Transactions AS t ON t.UserId = u.Id;

INNER JOIN فقط جفت‌های مطابق را نگه می‌دارد؛ LEFT JOIN تمام کاربران سمت چپ را نگه می‌دارد و برای طرف راست بدون تطبیق، NULL می‌گذارد.

تله مهم: WHERE بعد از LEFT JOIN

مثال عملیSQL
-- This can remove users with no successful transactions:
SELECT u.Id, t.Id
FROM dbo.Users u
LEFT JOIN dbo.Transactions t ON t.UserId = u.Id
WHERE t.Status = 1;

-- Keep all users; only matched successful transactions:
SELECT u.Id, t.Id
FROM dbo.Users u
LEFT JOIN dbo.Transactions t
  ON t.UserId = u.Id AND t.Status = 1;

چون شرط روی ستون جدول راست در WHERE، ردیف‌های NULL را حذف می‌کند، ممکن است LEFT JOIN عملاً رفتاری نزدیک INNER JOIN پیدا کند.

WHERE در برابر HAVING

مثال عملیSQL
SELECT UserId, COUNT(*) AS SuccessCount
FROM dbo.Transactions
WHERE Status = 1
GROUP BY UserId
HAVING COUNT(*) >= 10;

WHERE ردیف‌های ورودی را قبل از گروه‌بندی فیلتر می‌کند؛ HAVING روی گروه‌های تشکیل‌شده شرط می‌گذارد. برای شمارش و جمع، توجه کن که Join ناخواسته چندبرابرشدن ردیف‌ها را ایجاد نکند.

دقت در گزارش مالیقبل از هر SUM یا COUNT پس از JOIN، Cardinailty رابطه و احتمال چندبرابرشدن ردیف‌ها را بررسی کن؛ ظاهر درست SQL تضمین‌کننده جمع درست نیست.

سؤال 20 · آمادگی مصاحبه

چطور در LEFT JOIN تمام کاربران حفظ شوند اما فقط تراکنش‌های موفق به آن‌ها متصل شوند؟

  1. Aشرط t.Status=1 را در WHERE بگذاریم
  2. Bشرط t.Status=1 را داخل ON قرار دهیم

  4. DGROUP BY را حذف کنیم

درس 21 · آموزش و تمرین · ادامه تکمیلی دوره

DELETE، TRUNCATE و DROP

این سه دستور ظاهراً برای پاک‌سازی به‌کار می‌روند اما معنا و پیامد کاملاً متفاوت دارند. در سامانه مالی، استفاده نادرست می‌تواند فاجعه‌بار باشد.

مثال عملیSQL
-- Remove selected rows (WHERE is allowed):
DELETE FROM dbo.Transactions WHERE Status = 99;

-- Remove all rows (when constraints allow):
TRUNCATE TABLE dbo.TempImport;

-- Remove the table definition itself:
DROP TABLE dbo.TempImport;

مقایسه

معیار DELETE TRUNCATE DROP
ردیف انتخابی با WHERE بله خیر خیر
نگهداری ساختار جدول بله بله خیر
اجرای DELETE Trigger بله (در شرایط مربوط) خیر خیر
بازنشانی Identity معمولاً خیر معمولاً بله جدول حذف می‌شود
قابل Rollback در Transaction صریح SQL Server بله بله بله در شرایط معمول

اشتباه رایج: گفتن اینکه TRUNCATE در SQL Server «قابل Rollback نیست» نادرست است. وقتی داخل Transaction قابل Rollback اجرا شود، می‌توان آن را برگرداند؛ ولی اگر Commit شده باشد، بازیابی داستان دیگری است.

محدودیت‌های TRUNCATE

در حضور بعضی قیدهای FOREIGN KEY و سایر وابستگی‌ها، TRUNCATE مجاز نیست. به‌علاوه قفل‌ها و مجوزهای متفاوتی نسبت به DELETE دارد.

نکته Production

به‌جای پاک‌سازی مستقیم داده مالی، اغلب باید طراحی Retention، Archival، پارتیشن‌بندی و الزامات حسابرسی را در نظر گرفت. برای پاک‌سازی حجم زیاد، Batch کردن DELETE ممکن است زمان قفل‌گذاری و فشار Transaction Log را قابل کنترل‌تر کند.

هشدارنمونه‌های این درس فقط برای دیتابیس آزمایشی‌اند؛ دستور TRUNCATE یا DROP را روی جدول واقعی تراکنش مالی اجرا نکن.

  3. Cداخل Transaction مناسب می‌تواند Rollback شود

Columnstore Index و Rowstore Index

ایندکس‌های معمولی Rowstore ردیف‌ها را به‌صورت ردیفی نگهداری می‌کنند و برای تراکنش‌های نقطه‌ای OLTP بسیار متداول‌اند. در مقابل، Columnstore مقادیر هر ستون را به‌صورت فشرده و ستون‌محور سازمان می‌دهد و برای اسکن تحلیلی حجم زیاد مفید است.

مثال کاربردی

برای دریافت یک تراکنش با Id، Rowstore معمولاً مناسب است؛ ولی در گزارشی که از ۲۰۰ میلیون ردیف فقط دو ستون را SUM و GROUP BY می‌کند، Columnstore می‌تواند با فشرده‌سازی و Batch Mode سودمند باشد.

مثال عملیSQL
-- Illustrative analytics-oriented index:
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Transactions_Analytics
ON dbo.Transactions(Status, CreatedAt, Amount);

وجود Columnstore روی جدول OLTP باید دقیق بررسی شود؛ هزینه نگهداری، حافظه، نرخ تغییرات و شکل گزارش اهمیت دارند. برای محیط تحلیلی مستقل گاهی Clustered Columnstore Index روی جدول Fact مناسب است.

مقایسه

ویژگی Rowstore B-Tree Columnstore
بازیابی تک‌ردیف معمولاً بسیار مناسب معمولاً انتخاب اول نیست
Aggregate حجیم به Plan/Index بستگی دارد اغلب مناسب‌تر
سازمان داده ردیف محور ستون محور، فشرده
سناریو OLTP Analytics / Reporting

Batch Mode و Segments

پردازش دسته‌ای تعداد زیادی ردیف، فشرده‌سازی و حذف بخش‌هایی از داده بر اساس Metadata سگمنت‌ها می‌توانند کارایی را بهتر کنند. اما ممکن است برخی Queryها حتی با وجود Columnstore از Plan دیگری استفاده کنند.

بهینه‌سازی Query در EF Core

در مصاحبه سنیور، صرفاً دانستن LINQ کافی نیست؛ باید SQL تولیدشده، Plan و مصرف منابع را بررسی کنی. مشکلات پرتکرار شامل N+1، بارگذاری داده اضافی، Tracking غیرضروری، صفحه‌بندی غیربهینه و Queryهای حجیم هستند.

Projection و AsNoTracking

مثال عملیC#
var result = await db.Transactions
    .AsNoTracking()
    .Where(x => x.UserId == userId)
    .OrderByDescending(x => x.Id)
    .Select(x => new TransactionDto
    {
        Id = x.Id,
        Amount = x.Amount,
        Status = x.Status
    })
    .Take(50)
    .ToListAsync();

این Query فقط ستون‌های موردنیاز را انتخاب می‌کند. چون قرار نیست Entityها تغییر کنند، AsNoTracking معمولاً هزینه Change Tracker را کاهش می‌دهد.

N+1 Query

اگر ابتدا فهرست کاربران را دریافت کنیم و سپس برای هر کاربر جداگانه تراکنش‌ها را Lazy Load کنیم، ممکن است یک Query اولیه به‌علاوه N Query دیگر اجرا شود. راهکارها: Projection، Include هدفمند، Query ترکیبی یا Batch Query. در بارگذاری چند Collection، AsSplitQuery گاهی از انفجار ضرب کارتزین جلوگیری می‌کند، اما Round Tripهای اضافی دارد.

Keyset Pagination

در صفحه‌بندی عمیق، Skip(100000).Take(50) ممکن است کارایی ضعیفی داشته باشد. برای ترتیب پایدار با شناسه:

مثال عملیC#
var page = await db.Transactions
    .AsNoTracking()
    .Where(x => x.UserId == userId && x.Id < lastSeenId)
    .OrderByDescending(x => x.Id)
    .Take(50)
    .Select(x => new { x.Id, x.Amount })
    .ToListAsync();

برای این الگو ایندکس (UserId, Id) را با workload بررسی کن. صفحات باید دارای ترتیب قطعی باشند و ترکیب کلیدها در صفحه‌بندی چندستونی درست نگهداری شود.

دیدن SQL واقعی

مثال عملیC#
var sql = db.Transactions
    .Where(x => x.UserId == userId)
    .ToQueryString();
مصاحبه«به جای حدس درباره LINQ، ابتدا SQL تولیدشده، تعداد Round Trip، Actual Plan، Logical Reads و نیاز به Tracking را اندازه‌گیری می‌کنم.»

عیب‌یابی SQL Server در Production

سؤال واقعی مصاحبه: «API پرداخت دیروز ۵۰ میلی‌ثانیه پاسخ می‌داد، امروز بعضی درخواست‌ها ۵ ثانیه طول می‌کشند. از کجا شروع می‌کنی؟» پاسخ سنیور باید اندازه‌گیری، تفکیک لایه‌ها و اقدام کم‌ریسک باشد.

گام اول: تشخیص محل تأخیر

  1. آیا کندی از شبکه، Connection Pool، SQL Server یا سرویس وابسته است؟
  2. آیا خطای Timeout داریم یا فقط Latency افزایش یافته است؟
  3. آیا تعداد درخواست‌ها، توزیع پارامترها یا Deploy اخیر تغییر کرده است؟
  4. آیا روی سرور Waiting، Blocking، CPU، IO یا فشار حافظه مشاهده می‌شود؟

SQLهای تشخیصی نمونه

مثال عملیSQL
-- Active requests and waits
SELECT session_id, status, command,
       wait_type, wait_time,
       blocking_session_id, total_elapsed_time
FROM sys.dm_exec_requests
WHERE session_id > 50;
مثال عملیSQL
-- Simple index usage snapshot; counters reset on restart.
SELECT OBJECT_NAME(object_id) AS TableName,
       index_id, user_seeks, user_scans, user_updates
FROM sys.dm_db_index_usage_stats
WHERE database_id = DB_ID();

برای تحلیل Queryهای تاریخی از Query Store و برای Deadlock Graph از Extended Events استفاده می‌شود. DMVها و Query Store مجوز مناسب و محدودیت نگهداری داده دارند.

نمونه عیب‌یابی مرحله‌ای

  • اگر LCK_M_X یا انتظار قفل مشابه زیاد است: Blocking Chain و Transactionهای طولانی را بررسی کن.
  • اگر PAGEIOLATCH_* افزایش یافته: الگوی خواندن و وضعیت IO را بررسی کن؛ بدون آزمایش علت را صرفاً دیسک فرض نکن.
  • اگر RESOURCE_SEMAPHORE زیاد است: Memory Grant و تخمین ردیف‌ها را بررسی کن.
  • اگر Plan ناگهان تغییر کرده: Query Store، Statistics و Parameter Sniffing را مقایسه کن.
  • اگر در .NET خطای Connection Pool داریم: Connectionهای بازمانده، Dispose، عمر DbContext و مدت انتظار درخواست‌ها را بررسی کن.

اولویت تصمیم

ابتدا Blast Radius را محدود کن، داده مالی را ایمن نگه دار، شواهد قبل/بعد جمع کن و تغییر را با امکان Rollback انجام بده. NOLOCK سراسری، KILL کورکورانه یا افزایش بدون تحلیل Timeout روش تشخیص نیستند.

پاسخ سطح سنیور«اول مسئله را قابل اندازه‌گیری می‌کنم، سپس با Wait Stats، Query Store و Actual Plan ریشه مشکل را پیدا می‌کنم؛ راه‌حل باید هم سریع و هم برای صحت تراکنش‌های مالی امن باشد.»

مصاحبه نهایی Senior .NET و سناریوهای SQL

در این درس مفهوم جدیدی معرفی نمی‌کنیم؛ آنچه یاد گرفته‌ایم را در قالب سناریوی طراحی و عیب‌یابی به هم متصل می‌کنیم. هدف، پاسخ شفاهی ساخت‌یافته و قابل دفاع در مصاحبه است.

سناریو ۱: یک API تراکنش ناگهان کند شده

سؤال: Query روی UserId ایندکس دارد ولی در بعضی ساعات ۴ ثانیه طول می‌کشد. چه بررسی می‌کنی؟

طرح پاسخ: ابتدا Actual Execution Plan و STATISTICS IO/TIME، تعداد Lookup، کیفیت Statistics، اختلاف Estimated/Actual، Blocking و وابستگی Plan به پارامترها را بررسی می‌کنم. بعد از اندازه‌گیری، ایندکس Covering، بازنویسی SARGable، Query Store یا تغییر محدود Query را آزمایش می‌کنم.

سناریو ۲: دو درخواست هم‌زمان برداشت پول

سؤال: موجودی ۱۰۰۰ است و هر دو درخواست قصد برداشت ۸۰۰ دارند. چه می‌کنی؟

طرح پاسخ: اعتبارسنجی صرف در حافظه کافی نیست. یک Conditional UPDATE اتمیک با شرط Balance >= @Amount و بررسی تعداد ردیف‌ها در Transaction اجرا می‌کنم. برای هر درخواست RequestId یکتا، Unique Index و ثبت نتیجه قابل بازیابی دارم؛ در عملیات چندحسابی ترتیب قفل‌ها، Ledger و Reconciliation را هم لحاظ می‌کنم.

سناریو ۳: RabbitMQ در میانه انتقال قطع می‌شود

سؤال: آیا می‌توانی SQL Transaction را با Publish پیام به RabbitMQ یکی فرض کنی؟

طرح پاسخ: خیر. تغییر مانده و رکورد Outbox را در یک SQL Transaction ثبت می‌کنم. Publisher جداگانه پیام را از Outbox ارسال می‌کند و Consumer با Inbox/Idempotency اثر تکراری را کنترل می‌کند. انتشار ممکن است تکرار شود، ولی نباید اثر مالی دوبار اتفاق بیفتد.

سناریو ۴: Deadlockهای متناوب

سؤال: خطای 1205 داریم. آیا CommandTimeout را زیاد می‌کنی؟

طرح پاسخ: خیر؛ از Deadlock Graph منابع و Queryها را پیدا می‌کنم، ترتیب دسترسی ثابت و Transaction کوتاه طراحی می‌کنم و Retry محدودِ کل Transaction را با Idempotency برقرار می‌کنم.

قالب پاسخ سه‌مرحله‌ای در مصاحبه

  1. تشخیص: چه داده و متریکی جمع می‌کنم؟
  2. تصمیم: چه راه‌حلی می‌دهم و چرا؟
  3. ریسک: چه Trade-off و مسیر Rollback یا کنترل صحت دارد؟

تمرین کوتاه تکمیلی

  • تفاوت Clustered و Non-Clustered را با مثال یک جدول توضیح بده.
  • چرا Index Seek همیشه از Scan بهتر نیست؟
  • چرا NOLOCK در گزارش مانده بانکی خطرناک است؟
  • تفاوت RCSI و SNAPSHOT چیست؟
  • چرا RowVersion جایگزین Idempotency Key نیست؟
جمع‌بندی دورهدانستن تعریف اصطلاحات شرط لازم است؛ معیار سنیور، تحلیل داده واقعی، تشخیص گلوگاه، حفظ صحت مالی و توضیح روشن Trade-offهای تصمیم است.
