Monitoring · 15.3

Trace ID در Microservices

شناخت مسیر یک درخواست، ارتباط Spanها و مشاهدهٔ انتقال خودکار Trace Context در ASP.NET Core

۱. سفارش ثبت شد، اما پاسخ چرا دیر رسید؟

کاربر سفارش ۴۲ را ثبت می‌کند. Order برای بررسی پرداخت به Payment درخواست می‌فرستد و Payment از Database اطلاعات می‌خواند. پاسخ نهایی دو ثانیه طول می‌کشد. Log «سفارش دریافت شد» فقط یک رخداد را نشان می‌دهد؛ برای فهمیدن اینکه زمان در کدام قسمت مصرف شده است، باید بخش‌های اجرای همین درخواست را به هم وصل کنیم.

Trace مجموعهٔ بخش‌های مرتبط اجرای یک عملیات است. هر بخش با نام Span شناخته می‌شود و می‌تواند نام، زمان شروع، مدت اجرا و نتیجه داشته باشد. Trace ID شناسهٔ مشترک Spanهای همان Trace است؛ مثل شمارهٔ پرونده‌ای که روی همهٔ برگه‌های مربوط به یک بررسی قرار دارد.

TraceId = 4bf92f3577b34da6a3ce929d0e0e4736

Order: POST /orders/42          [Server Span A]
  └─ HTTP request to Payment   [Client Span B]
       └─ Payment: GET /payment [Server Span C]
            └─ Database query [Span D, if instrumented]

همهٔ این بخش‌ها Trace ID یکسان دارند، اما هرکدام Span ID جدا دارند. وجود شناسه به‌تنهایی مدت اجرای Database را آشکار نمی‌کند؛ آن بخش باید اندازه‌گیری و اطلاعاتش جمع‌آوری شده باشد. همچنین مدت Spanهای تو‌در‌تو را نباید با هم جمع زد، چون زمان فرزند معمولاً داخل بازهٔ والد قرار دارد.

۲. Trace ID، Span ID و Parent Span ID

Parent Span ID شناسهٔ بخشی است که بخش فعلی از آن آغاز شده است. در مثال بالا، والد C بخش B است. ارتباط والد و فرزند ساختار مسیر را مشخص می‌کند؛ Trace ID فقط نشان می‌دهد بخش‌ها به کدام Trace تعلق دارند.

مقدارپرسش قابل پاسخرفتار در مثال
Trace IDاین بخش متعلق به کدام اجرای سراسری است؟در A، B و C یکسان است
Span IDاین بخش مشخص کدام است؟A، B و C شناسه‌های متفاوت دارند
Parent Span IDاین بخش از کدام بخش آغاز شده است؟در C برابر Span ID بخش B است
Correlation IDطبق قرارداد برنامه، کدام رخدادها مرتبط‌اند؟ممکن است فرایندی شامل چند Trace را به هم وصل کند
OrderIdکدام موجودیت تجاری درگیر است؟سفارش ۴۲ می‌تواند در Trace ثبت، استعلام و لغو دیده شود

در قالب W3C، Trace ID برابر ۱۶ بایت است و با ۳۲ رقم hexadecimal نمایش داده می‌شود؛ Span ID برابر ۸ بایت و ۱۶ رقم است. hexadecimal از رقم‌های 0 تا 9 و حرف‌های a تا f استفاده می‌کند. این شناسه‌ها زمان رخداد یا شمارهٔ مشتری را در خود بیان نمی‌کنند. جزئیات در مفاهیم Distributed Tracing در .NET آمده است.

۳. traceparent چه چیزی را منتقل می‌کند؟

Trace Context اطلاعاتی است که سرویس گیرنده برای ادامه‌دادن Trace لازم دارد. Propagation انتقال این اطلاعات بین بخش‌ها یا سرویس‌هاست. در HTTP، استاندارد W3C این اطلاعات را از طریق Header، یعنی اطلاعات جانبی پیام، منتقل می‌کند. نمونهٔ زیر یک traceparent معتبر در نسخهٔ 00 است:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └────────── trace-id ─────────┘ └── parent-id ─┘ │
          version                                           flags

trace-id شناسهٔ Trace است. parent-id شناسهٔ Span فرستنده است که گیرنده آن را والد خود می‌داند. flags شامل پرچم sampled است؛ مقدار 01 یعنی این پرچم روشن است. این پرچم تضمین نمی‌کند تمام سرویس‌ها داده را ذخیره کرده‌اند.

هنگام ایجاد Span در سرویس بعدی، Trace ID حفظ می‌شود و Span ID تازه ساخته می‌شود. بنابراین کل Header نباید مانند یک رشتهٔ ثابت برای تمام مسیر کپی شود. Trace ID یا Span ID تمام‌صفر معتبر نیست. Header اختیاری tracestate نیز اطلاعات وابسته به سامانهٔ Tracing را حمل می‌کند. قرارداد دقیق در استاندارد W3C Trace Context تعریف شده است.

۴. خواندن Trace ID در .NET

در .NET، Activity نمایندهٔ یک Span است. Activity.Current به Activity فعال در جریان اجرای فعلی اشاره می‌کند. وقتی ASP.NET Core درخواست را پردازش می‌کند، می‌توان شناسه‌های Activity درخواست را خواند:

C# · داخل پردازش درخواست
using System.Diagnostics;

var activity = Activity.Current;
var traceId = activity?.TraceId.ToString();
var spanId = activity?.SpanId.ToString();
var parentSpanId = activity?.ParentSpanId.ToString();

علامت ?. از دسترسی به عضو یک مقدار null جلوگیری می‌کند. خارج از یک عملیات فعال، Activity.Current می‌تواند null باشد؛ مثلاً در یک برنامهٔ Console که هنوز Activity نساخته است. برای پرکردن این جای خالی یک GUID تصادفی با نام TraceId ثبت نکنید، چون آن مقدار به Trace واقعی متصل نیست.

در اجرای معمول async/await، Activity جاری همراه Context اجرای منطقی جریان پیدا می‌کند؛ وابسته به ثابت‌ماندن Thread نیست. بااین‌حال ارسال پیام به Broker یا شروع یک Job مستقل نیازمند انتقال یا ایجاد Context مناسب است. همچنین HttpContext.TraceIdentifier شناسهٔ درخواست میزبان است و جای Activity.TraceId را نمی‌گیرد.

۵. مثال اجرایی: Order و Payment

یک پروژهٔ .NET 10 را در دو Process مستقل اجرا می‌کنیم؛ یکی نقش Order و دیگری نقش Payment را دارد. هر دو از کد یکسان استفاده می‌کنند تا تمرکز روی شناسه‌ها باشد. در این مثال پرداخت واقعی انجام نمی‌شود و به Package اضافی نیاز نداریم.

Terminal · ساخت پروژه
dotnet new web -n TraceIdDemo -f net10.0
cd TraceIdDemo

محتوای Program.cs را جایگزین کنید. IHttpClientFactory ساخت HttpClient و مدیریت Handlerهای ارسال را بر عهده دارد. Client نام‌دار Payment مقصد فراخوانی را مشخص می‌کند. Scope اطلاعات مشترک Logهای یک محدودهٔ اجراست؛ ActivityTrackingOptions شناسه‌های Activity فعال را به Scopeهای Logging اضافه می‌کند.

Program.cs
using System.Diagnostics;

var builder = WebApplication.CreateBuilder(args);
builder.Logging.AddJsonConsole(options => options.IncludeScopes = true);
builder.Logging.Configure(options =>
    options.ActivityTrackingOptions = ActivityTrackingOptions.TraceId
        | ActivityTrackingOptions.SpanId
        | ActivityTrackingOptions.ParentId);

builder.Services.AddHttpClient("Payment", client =>
{
    client.BaseAddress = new Uri("http://localhost:5092");
});

var app = builder.Build();
var serviceName = builder.Configuration["ServiceName"] ?? "Demo";

app.MapGet("/payment", (ILogger<Program> logger) =>
{
    var snapshot = ReadTrace(serviceName);
    logger.LogInformation("Payment request received by {ServiceName}", serviceName);
    return Results.Ok(snapshot);
});

app.MapGet("/orders/{orderId:int}", async (
    int orderId, IHttpClientFactory factory,
    HttpContext context, ILogger<Program> logger) =>
{
    var order = ReadTrace(serviceName);
    logger.LogInformation("Order {OrderId} received by {ServiceName}",
        orderId, serviceName);

    var client = factory.CreateClient("Payment");
    var payment = await client.GetFromJsonAsync<TraceSnapshot>(
        "/payment", context.RequestAborted);

    return Results.Ok(new { orderId, order, payment });
});

app.Run();

static TraceSnapshot ReadTrace(string serviceName)
{
    var current = Activity.Current;
    return new TraceSnapshot(serviceName,
        current?.TraceId.ToString(),
        current?.SpanId.ToString(),
        current?.ParentSpanId.ToString());
}

record TraceSnapshot(string ServiceName, string? TraceId,
    string? SpanId, string? ParentSpanId);

ReadTrace فقط شناسه‌ها را می‌خواند و Activity جدید نمی‌سازد. قبل از فراخوانی Payment، شناسه‌های Activity درخواست Order در متغیر order ذخیره می‌شوند. سپس HttpClient درخواست را می‌فرستد و Payment شناسه‌های Activity سمت خودش را برمی‌گرداند. نمایش شناسه‌ها در Body برای مشاهدهٔ آموزشی است؛ پاسخ یک API واقعی باید متناسب با قرارداد محصول طراحی شود.

در این مسیر و با تنظیمات پیش‌فرض نمونه، ASP.NET Core ورودی و HttpClient خروجی در انتقال Trace Context مشارکت دارند؛ نیازی به افزودن دستی traceparent نیست. جزئیات پشتیبانی در مستندات Networking Tracing آمده است. تنظیمات Scope و ActivityTrackingOptions را نیز در مستندات Logging در ASP.NET Core می‌توانید ببینید.

۶. اجرا و مقایسهٔ نتیجه

ابتدا Build کنید؛ سپس از داخل پوشهٔ پروژه در دو Terminal جدا برنامه را اجرا کنید:

dotnet build
Terminal 1 · Payment
dotnet run --no-build --no-launch-profile -- --urls http://localhost:5092 --ServiceName Payment
Terminal 2 · Order
dotnet run --no-build --no-launch-profile -- --urls http://localhost:5091 --ServiceName Order

در PowerShell سوم درخواست را بفرستید:

PowerShell · Terminal 3
$result = Invoke-RestMethod http://localhost:5091/orders/42
$result | ConvertTo-Json -Depth 5
$result.order.traceId -eq $result.payment.traceId
$result.order.spanId -ne $result.payment.spanId

هر دو مقایسه باید True باشند: Trace ID مشترک است و Span IDها متفاوت‌اند. در Log هر سرویس نیز TraceId و SpanId در Scopes دیده می‌شوند. مقدار ParentSpanId مربوط به Payment معمولاً با SpanId مربوط به Order برابر نیست؛ بین آن‌ها Span فراخوانی HttpClient قرار دارد که والد مستقیم Activity درخواست Payment است.

یک درخواست مستقل دیگر بدون Header بفرستید؛ Trace ID تازه‌ای دریافت می‌کنید. سپس ادامهٔ یک Trace ورودی مشخص را آزمایش کنید:

$headers = @{
    traceparent = "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
$result = Invoke-RestMethod http://localhost:5091/orders/42 -Headers $headers
$result.order.traceId
$result.order.parentSpanId
$result.payment.traceId

Trace ID هر دو سرویس برابر 4bf92f3577b34da6a3ce929d0e0e4736 و ParentSpanId سرویس Order برابر 00f067aa0ba902b7 می‌شود. این Header ثابت فقط برای آزمایش است؛ آن را در تمام درخواست‌های واقعی تکرار نکنید. فرستادن Header نامعتبر نیز نباید برنامه را وابسته به شناسهٔ ارسالی شما کند؛ رفتار پذیرش Context را با تنظیمات واقعی Gateway و سرویس خود بررسی کنید.

۷. داشتن Trace ID با ذخیره‌شدن Trace فرق دارد

نمونهٔ ما شناسه‌ها را در پاسخ و Log نشان می‌دهد، اما هیچ صفحهٔ نمایش مسیر یا محل ذخیرهٔ Spanها راه‌اندازی نمی‌کند. Instrumentation کدی است که اطلاعات اجرای عملیات را تولید می‌کند. Exporter آن اطلاعات را به محل جمع‌آوری می‌فرستد. Sampling سیاست انتخاب بخشی از اجراها برای ثبت است تا هزینه و حجم داده کنترل شود.

بنابراین ممکن است Trace ID را در Log داشته باشید، اما Trace متناظر در ابزار مشاهده پیدا نشود: آن اجرا انتخاب نشده، Exporter تنظیم نیست، ارسال شکست خورده یا داده از دورهٔ نگهداری خارج شده است. برای تشخیص کندی به Spanهای جمع‌آوری‌شده و زمان آن‌ها نیاز دارید؛ رشتهٔ Trace ID به‌تنهایی اطلاعات Performance ندارد.

برای افزودن یک بخش داخلی، مثلاً محاسبهٔ تخفیف، API مناسب ActivitySource است؛ این شیء Activityهای مربوط به یک بخش از برنامه را تولید می‌کند. نمونهٔ زیر فقط الگوی Instrumentation است و باید در کلاس سرویس قرار گیرد:

private static readonly ActivitySource Source = new("Shop.Pricing");

public decimal CalculateDiscount(decimal total)
{
    using var activity = Source.StartActivity("CalculateDiscount");
    return total * 0.05m;
}

در صورت ایجاد Activity، با Activity جاری رابطهٔ والد و فرزند برقرار می‌شود و using پایان Span را مشخص می‌کند. StartActivity ممکن است به علت نبود Listener علاقه‌مند یا تصمیم Sampling مقدار null بدهد؛ منطق برنامه باید همچنان کار کند. Listener مصرف‌کننده‌ای است که به ActivitySource گوش می‌دهد؛ در راه‌اندازی OpenTelemetry، Source مربوط به Shop.Pricing باید ثبت شود. جزئیات در راهنمای افزودن Instrumentation و راهنمای جمع‌آوری Trace آمده است.

۸. مرزهای پیام و خطاهای رایج

  • ساخت Trace ID تازه در هر سرویس: وقتی سرویس باید ادامهٔ همان درخواست باشد، این کار مسیر را تکه‌تکه می‌کند. بررسی کنید Gateway و Client اطلاعات Context را حفظ کرده باشند.
  • انتقال فقط Trace ID در پیام: گیرنده برای ارتباط والد و فرزند به Context نیاز دارد. از Instrumentation و Propagator کتابخانهٔ Messaging استفاده کنید؛ Propagator مسئول نوشتن و خواندن Context در Metadata پیام است.
  • فرض یک Trace برای تمام عمر سفارش: درخواست لغو روز بعد می‌تواند Trace مستقلی داشته باشد. OrderId یا Correlation ID رابطهٔ تجاری را نگه می‌دارد. برای ارتباط چند Context، مثلاً پردازش دسته‌ای پیام‌ها، ActivityLink امکان اشاره به عملیات مرتبط را می‌دهد.
  • اعتماد به Trace ID ورودی: این مقدار می‌تواند از Client بیاید؛ برای Authentication، Authorization یا جلوگیری از پرداخت تکراری کاربرد ندارد. سیاست مرز اعتماد و Sampling باید مستقل باشد.
  • استفاده به‌عنوان Metric Label: تنوع بسیار زیاد شناسه‌ها، یا Cardinality بالا، تعداد سری‌های Metric را زیاد می‌کند. برای جست‌وجوی یک اجرای خاص از Log و Trace استفاده کنید.
  • کپی دستی traceparent در HttpClient: در مسیر دارای Instrumentation، این کار ممکن است والد نادرست ایجاد کند. انتقال را به سازوکار استاندارد واگذار کنید و نتیجه را در گیرنده بررسی کنید.

۹. تمرین عیب‌یابی

Payment را متوقف کنید و دوباره /orders/42 را صدا بزنید. Order به خطای اتصال می‌رسد؛ Log دریافت درخواست هنوز Trace ID دارد، اما Payment درخواست را دریافت نکرده که Log متناظر بسازد. این تفاوت کمک می‌کند نبود Log را با «پرداخت انجام شد» اشتباه نگیرید.

سپس Payment را اجرا کنید و دو درخواست مستقل به Order بفرستید. معیار موفقیت: داخل هر درخواست، Trace ID دو سرویس یکسان باشد؛ بین دو درخواست مستقل، Trace ID تغییر کند؛ و Span ID سرویس‌ها یکسان نباشد. برای بررسی سرعت، در درس Distributed Tracing همین ساختار را با جمع‌آوری Spanها و زمان اجرا ادامه می‌دهیم.

پرسش مرور: آیا یکسان بودن Trace ID دو Log یعنی یکی مستقیماً دیگری را فراخوانی کرده است؟ خیر؛ آن‌ها ممکن است دو فرزند مستقل در یک Trace باشند. برای فهمیدن رابطهٔ مستقیم، Parent Span ID و ساختار Spanها را بررسی کنید.
