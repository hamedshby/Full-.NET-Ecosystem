OpenTelemetry در Microservices

تولید و ارسال Trace، Metric و Log با APIهای .NET، شناخت SDK و Collector و یک نمونهٔ قابل‌اجرا

۱. سه سؤال دربارهٔ یک سفارش

کاربر می‌گوید ثبت سفارش کند شده است. تیم پشتیبانی می‌خواهد بداند برای سفارش او چه اتفاقی افتاده، تیم عملیات می‌خواهد تعداد درخواست‌های ناموفق را ببیند و توسعه‌دهنده می‌خواهد محل انتظار در مسیر اجرا را پیدا کند. برای این سه سؤال، یک نوع داده کافی نیست.

Telemetry داده‌ای است که دربارهٔ رفتار برنامه تولید می‌کنیم. OpenTelemetry، با نام کوتاه OTel، مجموعه‌ای از استانداردها، APIها، SDKها و ابزارها برای تولید، جمع‌آوری و ارسال این داده‌هاست. مثلاً برنامهٔ Order می‌تواند اطلاعات اجرای خود را با OTel تولید کند و بعداً مقصد ذخیره‌سازی را با تغییر تنظیمات Export عوض کند.

Signalمعنینمونهٔ سؤال
Traceبخش‌های مرتبط اجرای یک عملیات؛ هر بخش Span نام دارداین درخواست در کدام مرحله منتظر ماند؟
Metricاندازه‌گیری عددی، معمولاً تجمیع‌شده در بازهٔ زمانیچند عملیات کامل شد و زمان آن‌ها چگونه توزیع شده است؟
Logسابقهٔ یک رخداد با پیام و ویژگی‌های مرتبطبرای سفارش ۴۲ چه نتیجه‌ای ثبت شد؟

Signal یعنی دستهٔ اطلاعات مشاهده‌پذیری؛ تمرکز این درس روی سه مورد جدول است. OpenTelemetry خودش صفحهٔ Dashboard و پایگاه ذخیره‌سازی بلندمدت نیست. برای جست‌وجو، نمودار و Alert، یعنی اعلام وضعیت نیازمند توجه، به ابزار مقصد و تنظیمات آن نیاز داریم. معرفی این نقش در راهنمای Observability با OTel در .NET آمده است.

۲. از API تا Backend

Instrumentation کدی است که رفتار برنامه را اندازه می‌گیرد؛ مثلاً شروع و پایان درخواست HTTP. API قرارداد نوشتن این اندازه‌گیری‌هاست. SDK پیاده‌سازی جمع‌آوری و پردازش آن‌هاست و تعیین می‌کند چه داده‌ای به کجا برود.

Exporter داده را به یک مقصد می‌فرستد. OTLP پروتکل انتقال OpenTelemetry است و می‌تواند روی gRPC یا HTTP استفاده شود. Collector یک برنامهٔ جداست که داده را دریافت، پردازش و به مقصدهای بعدی ارسال می‌کند. Backend سامانهٔ ذخیره و جست‌وجو است.

Application
  ActivitySource / Meter / ILogger
                 ↓
        OpenTelemetry SDK
                 ↓ Exporter / OTLP
        [OpenTelemetry Collector]
          ↓          ↓          ↓
       Traces     Metrics      Logs
       backend    backend      backend

Collector برای همهٔ سناریوها اجباری نیست؛ ارسال مستقیم هم ممکن است. اضافه‌کردن آن در یک سیستم چندسرویسی می‌تواند فیلتر و ارسال به چند مقصد را متمرکز کند. بااین‌حال، انتخاب Backend همچنان مهم است: مثلاً ارسال هر سه Signal به یک مقصد مخصوص Trace باعث نمی‌شود آن مقصد Metric و Log را هم ذخیره کند.

۳. APIهای اصلی در .NET

APIکاربردنحوهٔ اتصال به SDK
ActivitySource و Activityتولید Span و مشخص‌کردن محدودهٔ اجراثبت نام Source با AddSource
Meterتعریف ابزارهای اندازه‌گیری مانند Counter و Histogramثبت نام Meter با AddMeter
ILoggerثبت رخدادها با Message Template و ویژگی‌هاافزودن OpenTelemetry Logging Provider

Counter مجموع مقدارهای افزوده‌شده را اندازه می‌گیرد؛ مثلاً به‌ازای هر عملیات کامل‌شده یک واحد اضافه می‌کنیم. Histogram توزیع مقدارها را نگه می‌دارد؛ مثلاً تعداد و مجموع زمان عملیات و تعداد مشاهده‌ها در بازه‌های زمانی مشخص. Histogram به معنی نگهداری تک‌تک درخواست‌ها نیست.

Providerهای مربوط به Trace، Metric و Log چرخهٔ جمع‌آوری هر Signal را مدیریت می‌کنند. آن‌ها را در شروع برنامه پیکربندی کنید و در هر درخواست Provider تازه نسازید. نام Source و Meter باید دقیقاً با نام ثبت‌شده مطابق باشد؛ تولید داده بدون ثبت منبع ممکن است خروجی قابل مشاهده‌ای نداشته باشد.

۴. Resource، Attribute و ارتباط داده‌ها

Resource مشخصات تولیدکنندهٔ داده است؛ مثل service.name برابر OrderService و service.version برابر 1.0.0. Attribute یک ویژگی نام‌دار روی داده است؛ مثلاً outcome برابر completed. مشخصات مشترک سرویس را روی Resource و جزئیات همان عملیات را روی دادهٔ مربوط ثبت کنید.

Semantic Conventions قراردادهای مشترک نام‌گذاری و معنای ویژگی‌ها و اندازه‌گیری‌ها هستند؛ مثلاً ابزارها با نام یکسان ویژگی‌های HTTP، اطلاعات سرویس‌های مختلف را بهتر کنار هم قرار می‌دهند. برای ویژگی استاندارد، نام دلخواه مشابه نسازید؛ قرارداد متناسب با نسخهٔ Instrumentation را دنبال کنید.

وقتی Log داخل Activity فعال ثبت شود، OpenTelemetry .NET می‌تواند TraceId و SpanId همان Activity را همراه آن ثبت کند. بنابراین از رخداد سفارش می‌توان به Trace مرتبط رسید، به شرط اینکه Backend و تنظیمات نمایش این ارتباط را پشتیبانی کنند. Metric تجمیع‌شده معمولاً متعلق به یک درخواست خاص نیست؛ Trace ID را به Label آن اضافه نکنید. جزئیات Log در راهنمای Logging در ASP.NET Core آمده است.

۵. نمونهٔ اجرایی: هر سه Signal در Console

این نمونه با .NET 10 یک عملیات آموزشی ثبت سفارش را اجرا می‌کند و داده‌های سه Signal را در Console نشان می‌دهد. Database و سرویس بیرونی ندارد. ابتدا پروژه و Packageها را آماده کنید:

Terminal
dotnet new web -n OpenTelemetryDemo -f net10.0
cd OpenTelemetryDemo
dotnet add package OpenTelemetry.Extensions.Hosting
dotnet add package OpenTelemetry.Instrumentation.AspNetCore
dotnet add package OpenTelemetry.Exporter.Console

فرمان‌ها نسخهٔ پایدار در دسترس را نصب می‌کنند؛ نسخه‌های ثبت‌شده در فایل پروژه را برای اجرای قابل‌بازتولید نگه دارید. محتوای Program.cs را جایگزین کنید:

Program.cs
using System.Diagnostics;
using System.Diagnostics.Metrics;
using OpenTelemetry.Logs;
using OpenTelemetry.Metrics;
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

var builder = WebApplication.CreateBuilder(args);
const string serviceName = "OrderService";
const string sourceName = "Shop.Orders";

using var source = new ActivitySource(sourceName);
using var meter = new Meter(sourceName);
var completed = meter.CreateCounter<long>("shop.orders.completed",
    unit: "{order}");
var duration = meter.CreateHistogram<double>("shop.orders.duration",
    unit: "s");

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource =>
        resource.AddService(serviceName, serviceVersion: "1.0.0"))
    .WithTracing(tracing => tracing
        .SetSampler(new AlwaysOnSampler())
        .AddAspNetCoreInstrumentation()
        .AddSource(sourceName)
        .AddConsoleExporter())
    .WithMetrics(metrics => metrics
        .AddMeter(sourceName)
        .AddConsoleExporter((exporterOptions, readerOptions) =>
        {
            readerOptions.PeriodicExportingMetricReaderOptions
                .ExportIntervalMilliseconds = 1000;
        }));

// Only the OpenTelemetry provider is needed for this console demo.
builder.Logging.ClearProviders();
builder.Logging.AddOpenTelemetry(options =>
{
    options.SetResourceBuilder(ResourceBuilder.CreateDefault()
        .AddService(serviceName, serviceVersion: "1.0.0"));
    options.IncludeFormattedMessage = true;
    options.IncludeScopes = true;
    options.AddConsoleExporter();
});

var app = builder.Build();

app.MapPost("/orders/{orderId:int}", async (
    int orderId, ILogger<Program> logger, CancellationToken cancellationToken) =>
{
    if (orderId <= 0)
        return Results.BadRequest(new { error = "OrderId must be positive" });

    using var activity = source.StartActivity("Order.Process");
    using var scope = logger.BeginScope(new Dictionary<string, object>
    {
        ["OrderId"] = orderId
    });

    var start = Stopwatch.GetTimestamp();
    await Task.Delay(120, cancellationToken);

    var elapsed = Stopwatch.GetElapsedTime(start).TotalSeconds;
    activity?.SetTag("order.outcome", "completed");
    completed.Add(1);
    duration.Record(elapsed);
    logger.LogInformation("Order {OrderId} completed", orderId);

    return Results.Ok(new
    {
        orderId,
        traceId = Activity.Current?.TraceId.ToString(),
        status = "Completed"
    });
});

app.Run();

ActivitySource و Meter در طول عمر برنامه مشترک‌اند. هر درخواست معتبر یک Span با نام ثابت Order.Process ایجاد می‌کند. using پایان محدودهٔ Span و Log Scope را مشخص می‌کند. Scope اطلاعات مشترک رخدادهای داخل محدوده است؛ در اینجا OrderId را نگه می‌دارد. StartActivity ممکن است null باشد، بنابراین کد باید بدون آن هم کار کند.

پس از پایان انتظار شبیه‌سازی‌شده، Counter یک واحد افزایش می‌یابد و Histogram زمان مرحلهٔ پردازش را برحسب ثانیه ثبت می‌کند؛ این زمان کل پاسخ HTTP، از جمله ارسال پاسخ، نیست. درخواست نامعتبر یا لغوشده پیش از تکمیل در این دو Instrument ثبت نمی‌شود. Instrument همان ابزار اندازه‌گیری مثل Counter است؛ پس نام completed آگاهانه انتخاب شده است.

ClearProviders فقط برای جلوگیری از خروجی تکراری این آزمایش است؛ در پروژهٔ دارای Providerهای موردنیاز، آن‌ها را بدون بررسی حذف نکنید. IncludeFormattedMessage متن قالب‌بندی‌شدهٔ پیام و IncludeScopes داده‌های Scope را فعال می‌کند. AlwaysOnSampler و بازهٔ یک‌ثانیه‌ای Export نیز برای مشاهدهٔ سریع آزمایش‌اند. الگوی Metric در راهنمای رسمی Metrics توضیح داده شده است.

۶. اجرا و نتیجهٔ مورد انتظار

Terminal 1
dotnet run --no-launch-profile --urls http://localhost:15201

در PowerShell دیگری سه درخواست معتبر بفرستید و یکی دو ثانیه برای Export دوره‌ای Metric صبر کنید:

PowerShell · Terminal 2
1..3 | ForEach-Object {
    Invoke-RestMethod -Method Post "http://localhost:15201/orders/$_"
}
  • Trace: برای هر درخواست، Span ورودی HTTP و Span داخلی Order.Process را می‌بینید. Trace ID آن دو مشترک و Span IDها متفاوت است.
  • Log: پیام Order … completed دارای OrderId، TraceId و SpanId است؛ چون داخل Span داخلی ثبت شده، SpanId آن به Order.Process اشاره می‌کند.
  • Metric: پس از سه درخواست و در اجرای تازه، Counter مقدار ۳ دارد؛ Histogram نیز سه مشاهده با زمان حدود ۰٫۱۲ ثانیه یا بیشتر دارد. زمان دقیق ثابت نیست.

خروجی Metric در تنظیمات پیش‌فرض این نمونه Cumulative است؛ یعنی مقدارها از شروع جمع‌آوری انباشته می‌شوند. تکرار مقدار ۳ در Export بعدی به معنی سه سفارش جدید نیست. با Restart برنامه، مقدارهای درون حافظه دوباره شروع می‌شوند. در Delta، هر خروجی تغییرات بازهٔ مربوط را گزارش می‌کند؛ نوع خروجی و تفسیر Backend باید هماهنگ باشند.

Metric رخدادها را تجمیع می‌کند، پس سه Log، سه Trace و یک مقدار Counter همگی می‌توانند همان سه عملیات را توصیف کنند. واحد، نام و بازهٔ اندازه‌گیری را هنگام خواندن نمودار بررسی کنید. برای مثال میانگین به‌تنهایی کندترین درخواست‌ها را نشان نمی‌دهد.

۷. انتقال هر سه Signal با OTLP

برای ارسال به Collector، Package زیر را اضافه کنید. سپس در هر سه محل AddConsoleExporter، Exporter مناسب OTLP را جایگزین کنید؛ افزودن آن فقط در WithTracing، Metric و Log را ارسال نمی‌کند.

dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol

ابتدای فایل، using OpenTelemetry.Exporter; را اضافه کنید. در WithTracing، فراخوانی AddConsoleExporter را با این فراخوانی جایگزین کنید؛ در WithMetrics نیز کل AddConsoleExporter همراه Lambda مربوط به بازهٔ زمانی را با همین فراخوانی جایگزین کنید:

.AddOtlpExporter(options =>
{
    options.Endpoint = new Uri("http://localhost:4317");
    options.Protocol = OtlpExportProtocol.Grpc;
})

داخل builder.Logging.AddOpenTelemetry، خط options.AddConsoleExporter را با این قطعه جایگزین کنید:

options.AddOtlpExporter(exporter =>
{
    exporter.Endpoint = new Uri("http://localhost:4317");
    exporter.Protocol = OtlpExportProtocol.Grpc;
});

بعد از تغییر، Build و اجرا را تکرار کنید. Collector باید Signalهای ارسالی را بپذیرد. Metric به بازهٔ پیش‌فرض OTLP برمی‌گردد و ممکن است بلافاصله دیده نشود. در این نمونه، Endpoint و Protocol صریح انتخاب شده‌اند؛ در محیط واقعی می‌توان از تنظیمات پشتیبانی‌شده مانند OTEL_EXPORTER_OTLP_ENDPOINT و OTEL_EXPORTER_OTLP_PROTOCOL استفاده کرد. پورت رایج gRPC برابر 4317 و HTTP برابر 4318 است؛ عوض‌کردن پورت بدون تغییر Protocol کافی نیست. جزئیات در راهنمای Exporterهای .NET آمده است.

۸. Collector: تعریف جزء با فعال‌کردن آن فرق دارد

Receiver دادهٔ ورودی Collector را دریافت می‌کند. Processor آن را پردازش می‌کند؛ مثلاً batch ارسال‌ها را گروه‌بندی می‌کند. Pipeline مسیر پردازش یک Signal از Receiver تا Exporter است. مثال زیر برای Collector نصب‌شده روی همان میزبان است و فقط داده را برای عیب‌یابی چاپ می‌کند:

otelcol.yaml · آزمایش محلی
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 127.0.0.1:4317

processors:
  batch: {}

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]

برای اجرا باید نسخه‌ای از Collector شامل این مؤلفه‌ها نصب شده باشد. فایل را ذخیره و از پوشهٔ آن با executable در دسترس اجرا کنید؛ در ویندوز ممکن است نام فرمان otelcol.exe باشد:

otelcol validate --config=otelcol.yaml
otelcol --config=otelcol.yaml

صرف تعریف otlp یا debug آن‌ها را برای همهٔ Signalها فعال نمی‌کند؛ ارجاع در service.pipelines لازم است. این تنظیمات پایگاه داده و UI نمی‌سازند. برای Production باید مقصد ذخیره‌سازی، محدودیت منابع، سیاست صف و Retry، امنیت ارتباط و دسترسی را متناسب با محیط مشخص کنید. اگر Collector داخل Container باشد، Bind و آدرس مقصد را مطابق شبکه تنظیم کنید؛ localhost در هر Container به خودش اشاره می‌کند. ساختار فایل در مستندات پیکربندی Collector آمده است.

۹. انتخاب دادهٔ مفید و کنترل هزینه

Cardinality تعداد ترکیب‌های متمایز ویژگی‌هاست. اگر برای Metric هر OrderId یا TraceId را ثبت کنید، به‌ازای عملیات فراوان سری‌های جدا می‌سازید. ویژگی محدود مثل outcome با چند مقدار مشخص، کنترل‌پذیرتر است. شناسهٔ سفارش را در Log یا Span و با رعایت سیاست داده ثبت کنید.

Sampling انتخاب بخشی از Traceها برای ثبت است. این انتخاب، شمارش Metric را خودکار به همان نسبت کاهش نمی‌دهد و Logها را هم خودکار حذف نمی‌کند. برای هر Signal سیاست مناسب خودش را تنظیم کنید. اگر Trace نمونه‌برداری نشده باشد، ممکن است Log دارای Trace ID باشد ولی Trace کامل در Backend پیدا نشود.

اطلاعات شخصی، Token و Body کامل را بدون نیاز وارد Telemetry نکنید. حذف داده در Collector جلوی انتقال اولیهٔ آن از برنامه تا Collector را نمی‌گیرد؛ بهتر است دادهٔ غیرضروری از ابتدا تولید نشود. از طرف دیگر، ثبت نکردن همه‌چیز نباید به حذف علت و نتیجهٔ عملیات مهم منجر شود؛ نام مرحله، نتیجه و اطلاعات لازم برای تشخیص مشکل را هدفمند انتخاب کنید.

Export ممکن است با صف و Batch انجام شود. خاموش‌کردن ناگهانی Process می‌تواند دادهٔ ارسال‌نشده را از بین ببرد؛ پایان عادی Host به پایان عمر Providerها کمک می‌کند، اما تضمین تحویل در همهٔ شرایط نیست. Counter در حافظه نیز دفتر حساب سفارش‌ها نیست؛ برای آمار تجاری قطعی به دادهٔ پایدار و قرارداد پردازش کسب‌وکار رجوع کنید.

۱۰. عیب‌یابی و تمرین

مشکلبررسی اول

تمرین اول: پس از سه درخواست معتبر، یک درخواست با OrderId برابر صفر بفرستید. باید پاسخ 400 بگیرید، Counter همچنان ۳ بماند و Log تکمیل برای این درخواست ثبت نشود. Span ورودی HTTP ممکن است وجود داشته باشد، چون Instrumentation پیش از ورود به منطق Endpoint فعال است.

تمرین دوم: زمان Delay را دو برابر کنید و برنامه را Restart کنید. سه درخواست تازه بفرستید. انتظار داریم تعداد تکمیل دوباره ۳ باشد، ولی زمان مشاهده‌های Histogram و مدت Span داخلی بیشتر شود. این مقایسه تفاوت «چند بار اجرا شد» و «چقدر طول کشید» را نشان می‌دهد.

پرسش مرور: اگر فقط WithTracing را تنظیم کنیم، آیا تمام Logها و Metricها هم در Backend ظاهر می‌شوند؟ خیر؛ هر Signal مسیر ثبت، جمع‌آوری و Export خودش را دارد. برای مشاهدهٔ هر سه، تنظیمات و مقصد هر سه را بررسی کنید.
