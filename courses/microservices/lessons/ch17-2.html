JWT Authentication in ASP.NET Core

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۷
⏱️ زمان مطالعه: ۳۰ دقیقه
👤 تیم فنی

در این درس چه چیزی یاد می‌گیریم؟

در درس قبل با ساختار JWT، Claimها، Signature و Access Token آشنا شدیم. حالا می‌خواهیم ببینیم ASP.NET Core چگونه یک JWT را دریافت و اعتبارسنجی می‌کند.

هدف اصلی این درس این است که API بتواند Access Token را از Header بخواند، آن را Validate کند و در صورت معتبر بودن، اطلاعات User را در قالب ClaimsPrincipal در اختیار Application قرار دهد.

ابتدا تصویر کلی را ببینیم

در یک معماری معمول Production، API خودش Token صادر نمی‌کند. Token توسط یک Identity Provider یا Authorization Server صادر می‌شود.

💡
در این معماری، وظیفهٔ API معمولاً صدور Token نیست؛ بلکه Validate کردن Token است.
⚠️
در Production عمومی، Access Token را با Flow استاندارد OAuth 2.0 یا OpenID Connect و یک Identity Provider معتبر دریافت کنید. صدور دستی Token با Username و Password در این درس فقط برای درک مکانیزم JWT بررسی می‌شود.

نصب Package

برای JWT Authentication در ASP.NET Core از Package زیر استفاده می‌کنیم:

.NET CLI 
dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer

روش پیشنهادی Production

اعتبارسنجی Token صادرشده توسط Identity Provider

در این حالت User ابتدا توسط Identity Provider احراز هویت می‌شود و Access Token دریافت می‌کند.

سپس Client آن Token را برای API ارسال می‌کند و API فقط مسئول Validation است.

در ASP.NET Core می‌توان Authentication را به شکل زیر تنظیم کرد:

Program.cs 
using Microsoft.AspNetCore.Authentication.JwtBearer;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority =
            builder.Configuration["Authentication:Authority"];

        options.Audience =
            builder.Configuration["Authentication:Audience"];

        options.MapInboundClaims = false;
    });

builder.Services.AddAuthorization();

var app = builder.Build();

app.UseHttpsRedirection();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();

Authority چیست؟

Authority آدرس Identity Provider مورد اعتماد را مشخص می‌کند.

Middleware از Metadata آن برای دریافت اطلاعات موردنیاز Validation، از جمله Signing Keyها استفاده می‌کند.

Configuration 
"Authentication": {
  "Authority": "https://identity.example.com",
  "Audience": "orders-api"
}

Audience چیست؟

Audience مشخص می‌کند Access Token برای کدام API صادر شده است.

برای مثال:

Concept 
Token Audience = orders-api

Orders API   ✅ Accept

Payment API  ❌ Reject

ترتیب Middlewareها مهم است

ASP.NET Core Pipeline 
app.UseAuthentication();

app.UseAuthorization();

ابتدا UseAuthentication Token را بررسی می‌کند و User را می‌سازد.

سپس UseAuthorization بررسی می‌کند که این User اجازهٔ اجرای Endpoint را دارد یا خیر.

💡
Authentication یعنی: «این User چه کسی است؟»

Authorization یعنی: «این User اجازهٔ انجام چه کاری را دارد؟»

نمونه آموزشی: وقتی Application خودش Token صادر می‌کند

🎓
بخش بعدی برای یادگیری اجزای JWT است.

در یک سیستم Production بزرگ معمولاً بهتر است Authentication و صدور Token توسط Identity Provider یا Authorization Server انجام شود.

برای درک بهتر مکانیزم JWT، فرض می‌کنیم Application خودش Token صادر می‌کند.

در این نمونه برای امضای Token از HMAC و یک Secret Key مشترک استفاده می‌کنیم.

تعریف تنظیمات JWT

JwtOptions.cs 
public sealed class JwtOptions
{
    public const string SectionName = "Jwt";

    public required string Issuer { get; init; }

    public required string Audience { get; init; }

    public required string SigningKey { get; init; }

    public int AccessTokenMinutes { get; init; } = 10;
}

Secret Key نباید داخل Source Code یا Repository قرار گیرد.

🛡️
Signing Key را در Secret Manager، Environment Variable، Vault یا سرویس مدیریت Secret نگهداری کنید.

پیکربندی Token Validation

Program.cs - JWT Validation 
using System.Text;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;

var jwtSection =
    builder.Configuration.GetRequiredSection(JwtOptions.SectionName);

builder.Services.Configure<JwtOptions>(jwtSection);

var jwt = jwtSection.Get<JwtOptions>()
    ?? throw new InvalidOperationException(
        "Jwt configuration is missing.");

var signingKey = new SymmetricSecurityKey(
    Encoding.UTF8.GetBytes(jwt.SigningKey));

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.MapInboundClaims = false;

        options.TokenValidationParameters =
            new TokenValidationParameters
            {
                ValidateIssuer = true,
                ValidIssuer = jwt.Issuer,

                ValidateAudience = true,
                ValidAudience = jwt.Audience,

                ValidateIssuerSigningKey = true,
                IssuerSigningKey = signingKey,

                ValidateLifetime = true,

                RequireExpirationTime = true,

                RequireSignedTokens = true,

                ClockSkew = TimeSpan.FromSeconds(30),

                NameClaimType = "name",

                RoleClaimType = "role"
            };
    });

builder.Services.AddAuthorization();

تولید Access Token

حالا یک Service ایجاد می‌کنیم که JWT بسازد.

AccessTokenService.cs 
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.Extensions.Options;
using Microsoft.IdentityModel.Tokens;

public sealed record AccessTokenResult(
    string Token,
    DateTime ExpiresAtUtc);

public sealed class AccessTokenService(
    IOptions<JwtOptions> options)
{
    private readonly JwtOptions _options = options.Value;

    public AccessTokenResult Create(
        string userId,
        string displayName,
        string[] roles)
    {
        var now = DateTime.UtcNow;

        var expires =
            now.AddMinutes(_options.AccessTokenMinutes);

        var claims = new List<Claim>
        {
            new(
                JwtRegisteredClaimNames.Sub,
                userId),

            new(
                JwtRegisteredClaimNames.Jti,
                Guid.NewGuid().ToString("N")),

            new(
                JwtRegisteredClaimNames.Iat,
                EpochTime.GetIntDate(now).ToString(),
                ClaimValueTypes.Integer64),

            new(
                "name",
                displayName)
        };

        claims.AddRange(
            roles.Select(
                role => new Claim("role", role)));

        var key = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(
                _options.SigningKey));

        var credentials =
            new SigningCredentials(
                key,
                SecurityAlgorithms.HmacSha256);

        var jwt =
            new JwtSecurityToken(
                issuer: _options.Issuer,
                audience: _options.Audience,
                claims: claims,
                notBefore: now,
                expires: expires,
                signingCredentials: credentials);

        var token =
            new JwtSecurityTokenHandler()
                .WriteToken(jwt);

        return new AccessTokenResult(
            token,
            expires);
    }
}

ثبت Service در Dependency Injection

چون قرار است AccessTokenService را داخل Controller تزریق کنیم، باید آن را در DI Container ثبت کنیم.

Program.cs 
builder.Services.AddSingleton<AccessTokenService>();

Claim کاربرد

💡

تمدید Session با استفاده از Refresh Token در درس بعد بررسی می‌شود.

ساخت Login Endpoint

بعد از Validate شدن Username و Password، می‌توان Access Token تولید کرد.

AuthController.cs 
[ApiController]
[Route("api/auth")]
public sealed class AuthController(
    IUserAuthenticator authenticator,
    AccessTokenService tokens)
    : ControllerBase
{
    [HttpPost("login")]
    [AllowAnonymous]
    public async Task<IActionResult> Login(
        LoginRequest request,
        CancellationToken cancellationToken)
    {
        var user =
            await authenticator.ValidateAsync(
                request.Email,
                request.Password,
                cancellationToken);

        if (user is null)
            return Unauthorized();

        var token =
            tokens.Create(
                user.Id,
                user.DisplayName,
                user.Roles);

        return Ok(token);
    }
}

در این مثال فرض می‌کنیم IUserAuthenticator مسئول بررسی Credentialهای User است.

🛡️
Password را مستقیم با مقدار ذخیره‌شده مقایسه نکنید.

Password باید با الگوریتم مناسب Hash شود و Login Endpoint نیز باید مکانیزم‌هایی مانند Rate Limiting و Lockout داشته باشد.
⚠️
Token، Signing Key و Password را داخل Log قرار ندهید.

محافظت از Endpoint با [Authorize]

برای اینکه Endpoint فقط توسط User احراز هویت‌شده قابل دسترسی باشد، از [Authorize] استفاده می‌کنیم.

OrdersController.cs 
using System.Security.Claims;
using Microsoft.AspNetCore.Authorization;

[Authorize]
[ApiController]
[Route("api/orders")]
public sealed class OrdersController
    : ControllerBase
{
    [HttpGet("mine")]
    public IActionResult Mine()
    {
        ClaimsPrincipal principal = User;

        var userId =
            principal.FindFirstValue("sub");

        return Ok(
            new
            {
                UserId = userId
            });
    }
}

وقتی JWT معتبر باشد، ASP.NET Core یک ClaimsPrincipal می‌سازد و آن را از طریق Property زیر در اختیار Controller قرار می‌دهد:

ASP.NET Core 
HttpContext.User

در Controller نیز معمولاً از طریق:

Controller 
User

به آن دسترسی داریم.

Authorization بر اساس Role

اگر داخل JWT Claim مربوط به Role داشته باشیم، می‌توانیم دسترسی Endpoint را بر اساس Role محدود کنیم.

OrdersController.cs 
[Authorize(Roles = "Admin")]
[HttpDelete("{id:guid}")]
public IActionResult Delete(Guid id)
{
    return NoContent();
}

فقط Userی که دارای Role زیر باشد:

JWT Claim 
"role": "Admin"

اجازهٔ اجرای Endpoint را خواهد داشت.

تفاوت 401 و 403

این دو Status Code در Authentication و Authorization بسیار مهم هستند.

Status معنا مثال
401 Unauthorized Authentication معتبر وجود ندارد. Token وجود ندارد، نامعتبر است یا Expire شده است.
403 Forbidden User احراز هویت شده ولی Permission کافی ندارد. User وارد شده ولی Admin نیست.
Mental Model 
No Valid Token
      │
      ▼
401 Unauthorized


Valid Token
but
No Permission
      │
      ▼
403 Forbidden
💡
401 یعنی: «نمی‌دانم چه کسی هستی یا Authentication معتبر نیست.»

403 یعنی: «می‌دانم چه کسی هستی، اما اجازهٔ انجام این عملیات را نداری.»

یک قدم جلوتر: Authorization Policy

استفاده مستقیم از Role برای سیستم‌های ساده مناسب است.

اما در سیستم‌های بزرگ‌تر معمولاً بهتر است Authorization را بر اساس Business Permission یا Policy طراحی کنیم.

مثلاً به‌جای:

Role Based 
[Authorize(Roles = "Admin")]

می‌توانیم Permission مشخصی تعریف کنیم:

Authorization Policy 
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy(
        "orders.write",
        policy =>
            policy.RequireClaim(
                "permission",
                "orders.write"));
});

و Endpoint را به آن Policy متصل کنیم:

Minimal API 
app.MapPost(
        "/api/orders",
        CreateOrder)
    .RequireAuthorization(
        "orders.write");

حالا Token باید Claim زیر را داشته باشد:

JWT Claim 
"permission": "orders.write"
💡
Policy معمولاً بهتر از پخش کردن Roleهای مختلف در سراسر Application است، زیرا Business Capability را مستقیماً بیان می‌کند.
⚠️
داشتن Claim یا Permission به‌تنهایی همیشه کافی نیست.

برای مثال User ممکن است Permission خواندن Order را داشته باشد، اما API همچنان باید بررسی کند که آیا این Order متعلق به همین User است یا خیر.

چک‌لیست اجرای صحیح JWT Authentication

  • Requestها فقط روی HTTPS دریافت شوند.
  • Signature، Issuer، Audience و Lifetime همگی Validate شوند.
  • Signing Key داخل Source Code یا Repository قرار نگیرد.
  • Access Token کوتاه‌عمر باشد.
  • Claimهای Token کمینه باشند.
  • UseAuthentication قبل از UseAuthorization اجرا شود.
  • Authentication با Authorization اشتباه گرفته نشود.
  • Authorization سطح Resource نیز بررسی شود.
  • Password، Signing Key و Access Token داخل Log ثبت نشوند.

جمع‌بندی

✅
در ASP.NET Core، JWT Authentication معمولاً توسط JwtBearer Middleware انجام می‌شود.

Middleware Token را از Header می‌خواند و Signature، Issuer، Audience و Lifetime را بررسی می‌کند.

سپس Authorization با استفاده از [Authorize]، Role یا Policy تصمیم می‌گیرد Request اجازهٔ ادامه دارد یا خیر.
