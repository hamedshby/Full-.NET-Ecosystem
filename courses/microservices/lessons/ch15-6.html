Prometheus در Microservices

جمع‌آوری Pull-based معیارها، مدل داده Time Series، انواع Metric و یک نمونهٔ قابل‌اجرا با .NET

۱. سه سؤال دربارهٔ ظرفیت سیستم

تیم عملیات می‌خواهد بداند سرویس Order در حال حاضر چند درخواست در ثانیه پردازش می‌کند. توسعه‌دهنده می‌خواهد بداند مصرف حافظه در یک ساعت گذشته چه روندی داشته است. تیم مدیریت حادثه می‌خواهد پیش از پر شدن صف، هشدار خودکار دریافت کند. هر سه سؤال به یک نوع داده نیاز دارند: مقدارهای عددی که در طول زمان نمونه‌برداری شده‌اند.

Prometheus سامانه‌ای متن‌باز برای مانیتورینگ و هشداردهی است که داده را به روش Pull جمع‌آوری می‌کند؛ یعنی خودش با فاصلهٔ زمانی مشخص به سراغ برنامه می‌رود، نه اینکه برنامه داده را فشار (Push) کند. داده در یک پایگاه سری‌زمانی (TSDB) ذخیره می‌شود و با زبان PromQL پرس‌وجو می‌شود.

برخلاف OpenTelemetry که استانداردی برای هر سه Signal یعنی Trace، Metric و Log است، Prometheus تنها روی Metric تمرکز دارد. این دو ابزار رقیب نیستند؛ در بسیاری از سیستم‌ها، برنامه Metric را با کتابخانهٔ سازگار با OpenTelemetry تولید می‌کند و Prometheus یا یک Backend دیگر آن را ذخیره می‌کند.

۲. مدل داده: Metric، Label، Series و Sample

Metric یک سنجهٔ نام‌دار است؛ مثلاً shop_orders_completed_total. Label جفت کلید-مقداری است که یک Metric را به زیرمجموعه‌های مشخص تقسیم می‌کند؛ مثلاً method="POST" یا status_code="200". ترکیب نام Metric با مجموعهٔ Labelهای آن یک Time Series منحصربه‌فرد می‌سازد. Sample یک مقدار عددی به‌همراه برچسب زمانی است که در یک Series ثبت می‌شود.

مفهوم معنی مثال
Metric نام سنجه‌ای که اندازه‌گیری می‌شود shop_orders_completed_total
Label بعدی که Series را تفکیک می‌کند method="POST", path="/orders"
Time Series یک Metric به‌همراه یک ترکیب مشخص از Labelها شمارندهٔ سفارش‌های تکمیل‌شده برای path="/orders"
Sample یک مقدار در یک لحظهٔ مشخص مقدار ۴۲ در ساعت ۱۰:۰۰:۱۵

افزودن یک Label جدید به یک Metric، Time Series تازه‌ای برای هر مقدار متمایز آن Label می‌سازد؛ به همین دلیل انتخاب Labelها مستقیماً روی حجم داده و هزینهٔ ذخیره‌سازی اثر می‌گذارد.

۳. چهار نوع Metric در Prometheus

نوع معنی نمونهٔ کاربرد
Counter مقداری که فقط افزایش می‌یابد یا در Restart صفر می‌شود تعداد کل سفارش‌های تکمیل‌شده
Gauge مقداری که می‌تواند بالا و پایین برود تعداد آیتم‌های فعلی در صف
Histogram توزیع مقدارها در Bucketهای از پیش تعریف‌شده، به‌همراه شمارش و مجموع توزیع زمان پردازش سفارش
Summary شمارش، مجموع و صدک‌های محاسبه‌شده در سمت برنامه میانهٔ زمان پاسخ در همان فرآیند

Counter هرگز کاهش پیدا نمی‌کند؛ اگر مقداری نیاز به کاهش دارد، Gauge مناسب‌تر است. Histogram Bucketهای خود را در سمت برنامه تعریف می‌کند و می‌توان بعداً در PromQL صدک را از روی آن‌ها تخمین زد؛ Summary صدک را از قبل در برنامه محاسبه می‌کند و نمی‌توان صدک‌های آن را در Backend با هم جمع کرد. برای Metricهایی که قرار است بین چند نمونه از سرویس تجمیع شوند، Histogram معمولاً انتخاب امن‌تری است.

۴. از Exporter تا Alertmanager: معماری Pull

Client Library کتابخانه‌ای در زبان برنامه است که Metricها را در حافظه نگه می‌دارد و آن‌ها را روی یک مسیر HTTP، معمولاً /metrics، در قالب متنی Prometheus قابل‌خواندن می‌کند. Exporter برنامه‌ای کمکی است که Metric یک سامانهٔ بیرونی، مثل یک پایگاه‌داده یا سیستم‌عامل، را به همین قالب تبدیل می‌کند. Prometheus Server با فاصلهٔ زمانی مشخص این مسیرها را Scrape، یعنی درخواست و جمع‌آوری، می‌کند و در TSDB ذخیره می‌کند. Alertmanager بر اساس قواعدی که در Prometheus تعریف می‌شود، هشدار تولید و مسیریابی می‌کند.

Application
  Client Library  →  GET /metrics
        ↑                 ↓
        |          Prometheus Server  →  TSDB
        |                 ↓
        |            Rule Evaluation
        |                 ↓
        |            Alertmanager  →  Notification
        |
   PromQL / Grafana  ←———— Query API

برخلاف مدل Push در OpenTelemetry Exporterهای رایج، اینجا برنامه هیچ داده‌ای را فعالانه ارسال نمی‌کند؛ فقط آماده نگه می‌دارد تا Prometheus بیاید و بخواند. این یعنی برنامه باید در دسترس شبکهٔ Prometheus باشد؛ برای Jobهای کوتاه‌عمر که قبل از Scrape بعدی از بین می‌روند، از Pushgateway به‌عنوان واسطه استفاده می‌شود، نه از خود Prometheus.

۵. نمونهٔ اجرایی: راه‌اندازی با .NET

این نمونه با .NET 10 و کتابخانهٔ prometheus-net یک عملیات آموزشی ثبت سفارش را اجرا می‌کند و سه نوع Metric را منتشر می‌کند. ابتدا پروژه و Packageها را آماده کنید:

Terminal
dotnet new web -n PrometheusDemo -f net10.0
cd PrometheusDemo
dotnet add package prometheus-net.AspNetCore

محتوای Program.cs را جایگزین کنید:

Program.cs
using Prometheus;

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.UseHttpMetrics();   // generic HTTP request metrics
app.UseMetricServer();  // publish on the default /metrics path

var ordersCompleted = Metrics.CreateCounter(
    "shop_orders_completed_total", "Total completed orders");

var ordersDuration = Metrics.CreateHistogram(
    "shop_orders_duration_seconds", "Order processing duration");

var queueSize = Metrics.CreateGauge(
    "shop_orders_queue_size", "Current in-flight orders");

app.MapPost("/orders/{orderId:int}", async (int orderId) =>
{
    if (orderId <= 0)
        return Results.BadRequest(new { error = "OrderId must be positive" });

    queueSize.Inc();
    using (ordersDuration.NewTimer())
    {
        await Task.Delay(120);
    }
    queueSize.Dec();
    ordersCompleted.Inc();

    return Results.Ok(new { orderId, status = "Completed" });
});

app.Run();

UseHttpMetrics پیش از Map کردن Endpointها اضافه می‌شود تا زمان و کد وضعیت هر درخواست را به‌طور خودکار اندازه بگیرد. UseMetricServer یک Middleware مجزا است که فقط به مسیر /metrics پاسخ می‌دهد و به منطق سایر Endpointها کاری ندارد. ordersDuration.NewTimer() یک IDisposable برمی‌گرداند که در پایان using، مدت اجرا را در Histogram ثبت می‌کند؛ اگر داخل این محدوده استثنایی رخ دهد، زمان تا همان لحظه ثبت می‌شود.

۶. اجرا و نتیجهٔ مورد انتظار

Terminal 1
dotnet run --no-launch-profile --urls http://localhost:15201

در ترمینال دیگری سه درخواست معتبر و یک درخواست نامعتبر بفرستید:

PowerShell · Terminal 2
1..3 | ForEach-Object {
    Invoke-RestMethod -Method Post "http://localhost:15201/orders/$_"
}
Invoke-RestMethod -Method Post "http://localhost:15201/orders/0"

سپس مسیر /metrics را در مرورگر یا با curl باز کنید:

/metrics
# HELP shop_orders_completed_total Total completed orders
# TYPE shop_orders_completed_total counter
shop_orders_completed_total 3

# HELP shop_orders_duration_seconds Order processing duration
# TYPE shop_orders_duration_seconds histogram
shop_orders_duration_seconds_bucket{le="0.1"} 0
shop_orders_duration_seconds_bucket{le="0.25"} 3
shop_orders_duration_seconds_bucket{le="+Inf"} 3
shop_orders_duration_seconds_sum 0.372
shop_orders_duration_seconds_count 3

# HELP shop_orders_queue_size Current in-flight orders
# TYPE shop_orders_queue_size gauge
shop_orders_queue_size 0

درخواست OrderId برابر صفر پیش از رسیدن به queueSize.Inc() با پاسخ 400 برمی‌گردد؛ بنابراین در Counter و Histogram سفارش شمرده نمی‌شود، اما به‌عنوان یک درخواست HTTP در Metricهای UseHttpMetrics با کد وضعیت 400 ثبت می‌شود. Bucketهای پیش‌فرض Histogram ممکن است با زمان واقعی درخواست‌های شما هم‌خوانی نداشته باشند؛ در استفادهٔ واقعی، Bucketها را متناسب با محدودهٔ زمانی سرویس تنظیم کنید.

۷. مرحلهٔ بعد: افزودن prometheus.yml و PromQL مقدماتی

برای اینکه Prometheus خودش این مسیر را Scrape کند، یک فایل تنظیمات نیاز است:

prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'order-service'
    static_configs:
      - targets: ['localhost:15201']
prometheus --config.file=prometheus.yml

پس از اجرا، در رابط وب Prometheus روی پورت پیش‌فرض 9090 می‌توان PromQL نوشت. چند نمونه:

عبارت PromQL معنی
rate(shop_orders_completed_total[1m]) نرخ تکمیل سفارش در ثانیه، میانگین‌گیری‌شده روی بازهٔ یک‌دقیقه‌ای
shop_orders_queue_size مقدار لحظه‌ای فعلی صف، بدون نیاز به rate
histogram_quantile(0.95, sum(rate(shop_orders_duration_seconds_bucket[5m])) by (le)) برآورد صدک ۹۵ زمان پردازش در پنج دقیقهٔ اخیر

rate فقط روی Counter معنا دارد، چون فرض می‌کند مقدار پایه‌ای پیوسته افزایش می‌یابد؛ اجرای rate روی Gauge نتیجهٔ گمراه‌کننده می‌دهد. histogram_quantile روی خود مقدار Histogram اجرا نمی‌شود، بلکه روی سری _bucket آن اجرا می‌شود که به‌طور خودکار توسط کتابخانهٔ Client تولید شده است.

۸. Cardinality و کنترل هزینه

Cardinality تعداد ترکیب‌های متمایز Labelهاست. افزودن Labelی مانند order_id یا user_id به یک Metric پرتکرار، به‌ازای هر مقدار متمایز یک Time Series تازه می‌سازد؛ در حجم بالای سفارش، این کار می‌تواند میلیون‌ها Series تولید کند و حافظه و کارایی Prometheus را به‌شدت تحت‌فشار بگذارد.

  • شناسه‌های یکتا و پرتکرار مثل order_id یا request_id را Label نکنید؛ این‌ها متعلق به Log یا Trace هستند.
  • Labelهایی با تعداد مقدار محدود و از‌پیش‌شناخته مثل method یا status_code گزینهٔ مناسب‌تری هستند.
  • پیش از افزودن یک Label جدید، تخمین بزنید که چند مقدار متمایز ممکن است داشته باشد.
  • Bucketهای Histogram را کم و هدفمند نگه دارید؛ هر Bucket یک Time Series جداگانه است.

برخلاف Sampling در Tracing که حجم داده را با از‌دست‌دادن بخشی از رخدادها کاهش می‌دهد، در Prometheus معمولاً کنترل حجم از طریق طراحی درست Label و Bucket انجام می‌شود، نه حذف تصادفی Sampleها.

۹. عیب‌یابی و تمرین

مشکل بررسی اول
مسیر /metrics پاسخ نمی‌دهد ثبت UseMetricServer پیش از app.Run و باز بودن پورت
Prometheus هدف را Down نشان می‌دهد درستی targets در prometheus.yml و دسترسی شبکه به آن آدرس
Counter در Grafana صفر یا خطی مسطح است استفاده از rate() به‌جای نمایش مستقیم Counter خام
Histogram صدک درستی نمی‌دهد تعریف Bucketهای متناسب با بازهٔ واقعی زمان پاسخ
حجم حافظهٔ Prometheus به‌سرعت رشد می‌کند بررسی Cardinality؛ جست‌وجوی Labelهای با مقادیر بسیار متنوع

تمرین اول: پس از سه درخواست معتبر، مقدار shop_orders_queue_size را بلافاصله پس از افزایش هر درخواست، پیش از پایان Task.Delay، از مسیر /metrics بخوانید. باید مقداری بزرگ‌تر از صفر ببینید، چون درخواست هنوز در حال پردازش است.

تمرین دوم: یک Label به نام order_id به Counter شمارش سفارش اضافه کنید و ۵۰ سفارش با شناسه‌های متفاوت بفرستید. تعداد Time Seriesهای تولیدشده در /metrics را بشمارید و نتیجه را با حالت بدون این Label مقایسه کنید.

پرسش مرور: اگر UseHttpMetrics را اضافه کنیم اما UseMetricServer را حذف کنیم، آیا Metricهای HTTP در جایی قابل‌مشاهده خواهند بود؟ خیر؛ UseHttpMetrics فقط مقدارها را در حافظهٔ Client Library ثبت می‌کند؛ بدون یک مسیر منتشرشده برای Scrape، هیچ سامانهٔ بیرونی نمی‌تواند آن‌ها را بخواند.
