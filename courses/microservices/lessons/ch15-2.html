Correlation ID در Microservices

دنبال کردن یک عملیات از Order تا Payment با یک شناسهٔ مشترک و Logهای قابل جست‌وجو

۱. کدام Logها متعلق به درخواست من هستند؟

دو کاربر هم‌زمان سفارش ثبت می‌کنند. سرویس Order برای هر دو درخواست از سرویس Payment کمک می‌گیرد. حالا یکی از پرداخت‌ها ناموفق شده است. اگر فقط زمان و متن «پرداخت ناموفق بود» را داشته باشیم، نزدیک بودن زمان رخدادها مشخص نمی‌کند کدام درخواست به این خطا رسیده است.

Correlation ID شناسه‌ای است که رخدادهای مرتبط با یک عملیات را به هم وصل می‌کند. در مثال زیر مقدار کوتاه checkout-a فقط برای خوانایی است؛ در برنامه از یک مقدار تصادفی بلندتر استفاده می‌کنیم:

Order    CorrelationId=checkout-a  OrderId=42  Order accepted
Order    CorrelationId=checkout-b  OrderId=43  Order accepted
Payment  CorrelationId=checkout-b  Payment approved
Payment  CorrelationId=checkout-a  Payment declined

با جست‌وجوی فیلد CorrelationId برابر checkout-a، رخدادهای سفارش اول را کنار هم می‌بینیم. این شناسه دلیل شکست را به‌تنهایی نمی‌گوید؛ جزئیات Log توضیح می‌دهند چه اتفاقی افتاده است. همچنین ترتیب نمایش Logها الزاماً ترتیب واقعی رخدادها نیست، چون ساعت و زمان رسیدن Logهای سرویس‌ها می‌تواند متفاوت باشد.

۲. شناسه کجا ساخته و چگونه منتقل می‌شود؟

Header بخشی از پیام HTTP برای حمل اطلاعات جانبی درخواست یا پاسخ است. در این درس قرارداد خودمان را با نام X-Correlation-ID تعریف می‌کنیم؛ این نام یک قرارداد رایج است و استاندارد اجباری و یکسان همهٔ سیستم‌ها نیست.

  1. نقطهٔ ورود، مثلاً API Gateway یا اولین سرویس، یک شناسه می‌سازد؛ یا شناسهٔ معتبر فرستندهٔ قابل اعتماد را می‌پذیرد.
  2. سرویس شناسه را در اطلاعات مشترک Logهای همان درخواست قرار می‌دهد.
  3. هنگام فراخوانی سرویس بعدی، همان مقدار را در Header درخواست خروجی می‌فرستد.
  4. سرویس گیرنده همین مراحل را تکرار می‌کند و شناسه در پاسخ اولیه هم برگردانده می‌شود تا پشتیبانی بتواند آن را از کاربر دریافت کند.
Client → Order → Payment
         X-Correlation-ID: 79c7795a68274e54ae61d1e3be1262d7
         Same value is forwarded to Payment.

اگر هر سرویس بدون بررسی ورودی یک شناسهٔ تازه بسازد، ارتباط Logها قطع می‌شود. از طرف دیگر، نگه‌داشتن یک مقدار ثابت برای همهٔ درخواست‌های یک کاربر باعث مخلوط‌شدن عملیات مستقل می‌شود. دامنهٔ شناسه را مشخص کنید؛ در این درس هر عملیات ورودی مستقل یک Correlation ID دارد.

۳. تفاوت با Request ID، Trace ID و OrderId

Trace مسیر اجرای یک عملیات و Span یک بخش از آن مسیر با زمان شروع و پایان است. در .NET، Activity نمایندهٔ یک بخش از اجرای قابل ردیابی است. جدول زیر کمک می‌کند شناسه‌ها را جای یکدیگر استفاده نکنیم:

شناسهکاربردمثال
Correlation IDگروه‌بندی رخدادهای مرتبط طبق قرارداد برنامهیک فرایند ثبت سفارش بین چند سرویس
Request IDتشخیص یک درخواست در محدودهٔ تعریف‌شدهٔ میزبانHttpContext.TraceIdentifier برای درخواست HTTP جاری؛ انتقال بین سرویس‌ها را تضمین نمی‌کند
Trace IDشناسهٔ مشترک Spanهای یک TraceActivity.Current?.TraceId
Span IDتشخیص یک بخش مشخص از Traceبخش اجرای فراخوانی Payment
OrderIdشناسهٔ موجودیت تجاری سفارشسفارش ۴۲ که ممکن است امروز ایجاد و فردا لغو شود

در W3C Trace Context، Header به نام traceparent اطلاعات Trace و بخش والد را حمل می‌کند. در مسیرهای پشتیبانی‌شده و با تنظیمات مناسب، ASP.NET Core و HttpClient در انتقال این Context مشارکت دارند. اما Header سفارشی X-Correlation-ID خودکار از این راه منتقل نمی‌شود. آن را جای traceparent ننویسید و GUID دلخواه را به‌عنوان مقدار کامل traceparent ارسال نکنید.

اگر هدف فقط یافتن Logهای یک Trace است، Trace ID می‌تواند نیاز شما را برطرف کند. Correlation ID جدا زمانی مفید است که قرارداد پشتیبانی یا یک فرایند تجاری چندمرحله‌ای را دنبال می‌کنید؛ چنین فرایندی ممکن است چند Trace داشته باشد. برای جزئیات بیشتر، مفاهیم Distributed Tracing در .NET و Tracing در کتابخانه‌های شبکهٔ .NET را ببینید.

۴. نمونهٔ قابل‌اجرای ASP.NET Core

ابتدا ساخت و ثبت شناسه را در یک سرویس یاد می‌گیریم. این نمونه با .NET 10 اجرا می‌شود و Endpoint آن فقط دریافت سفارش را شبیه‌سازی می‌کند؛ Database و پرداخت واقعی ندارد.

Terminal
dotnet new web -n CorrelationDemo -f net10.0
cd CorrelationDemo

Middleware بخشی از مسیر پردازش درخواست است که می‌تواند قبل و بعد از مرحلهٔ بعدی اجرا شود. Scope اطلاعات مشترکی به Logهای یک محدودهٔ اجرای منطقی اضافه می‌کند. کد زیر را در Program.cs قرار دهید:

Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Logging.AddJsonConsole(options => options.IncludeScopes = true);
var app = builder.Build();

const string headerName = "X-Correlation-ID";
const string itemKey = "CorrelationId";

app.Use(async (context, next) =>
{
    var incoming = context.Request.Headers[headerName];
    // Demo contract: accept exactly one GUID in the 32-digit N format.
    var correlationId = incoming.Count == 1
        && Guid.TryParseExact(incoming[0], "N", out var parsed)
        && parsed != Guid.Empty
            ? parsed.ToString("N")
            : Guid.NewGuid().ToString("N");

    context.Items[itemKey] = correlationId;
    context.Response.OnStarting(() =>
    {
        context.Response.Headers[headerName] = correlationId;
        return Task.CompletedTask;
    });

    using var scope = app.Logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = correlationId,
        ["ServiceName"] = "OrderService"
    });

    await next(context);
});

app.MapPost("/orders/{orderId:int}", (
    int orderId, HttpContext context, ILogger<Program> logger) =>
{
    logger.LogInformation("Order {OrderId} received", orderId);
    return Results.Ok(new
    {
        orderId,
        correlationId = (string)context.Items[itemKey]!
    });
});

app.Run();

اگر Header وجود نداشته باشد، خالی، چندمقداری، GUID صفر یا خارج از قالب توافق‌شده باشد، نمونه یک شناسهٔ تازه می‌سازد. ورودی نامعتبر در Log بازنویسی نمی‌شود. HttpContext.Items مقدار را فقط برای همان درخواست نگه می‌دارد؛ متغیر static برای این کار مناسب نیست، چون درخواست‌های هم‌زمان مقدار یکدیگر را تغییر می‌دهند.

OnStarting، Header را پیش از ارسال پاسخ تنظیم می‌کند. Scope تا پایان اجرای await next فعال است و با using آزاد می‌شود. IncludeScopes باعث می‌شود JSON Console اطلاعات Scope را نمایش دهد؛ همهٔ Providerها الزاماً Scope را یکسان ذخیره نمی‌کنند. Scope نیز فقط Logهای داخل محدودهٔ خود را پوشش می‌دهد، نه تمام Logهای میزبان پیش از ورود یا پس از خروج از Middleware. توضیح رسمی در مستندات Logging و Log Scope آمده است.

این نمونه برای آموزش، شناسهٔ معتبر ورودی را می‌پذیرد. اعتبار قالب به معنی اعتماد به فرستنده نیست. در ورودی عمومی می‌توانید همیشه شناسهٔ داخلی تازه بسازید و تنها در ارتباط داخلی قابل اعتماد مقدار ورودی را حفظ کنید. این سیاست باید در Gateway و سرویس‌ها هماهنگ باشد.

۵. اجرا و مشاهدهٔ نتیجه

Terminal 1
dotnet run --no-launch-profile --urls http://localhost:5086

در PowerShell دیگری درخواست بفرستید. Invoke-WebRequest امکان دیدن Header پاسخ و محتوای آن را می‌دهد:

PowerShell · Terminal 2
$id = [Guid]::NewGuid().ToString("N")
$response = Invoke-WebRequest -Method Post `
    -Uri http://localhost:5086/orders/42 `
    -Headers @{ "X-Correlation-ID" = $id }
$response.Headers["X-Correlation-ID"]
$response.Content

شناسه در Header و فیلد correlationId پاسخ باید همان $id باشد. در خروجی Console، Log دریافت سفارش دارای Scope شامل CorrelationId است. در ابزار مرکزی Log، همین فیلد را همراه نام محیط و بازهٔ زمانی جست‌وجو کنید؛ شکل دقیق دستور جست‌وجو به ابزار وابسته است.

بار دوم بدون Header درخواست بفرستید؛ یک شناسهٔ جدید دریافت می‌کنید. بار سوم مقدار invalid بفرستید؛ باز هم سرور مقدار معتبر جدید تولید می‌کند. با دو شناسهٔ متفاوت هم درخواست بفرستید و بررسی کنید Logهای آن‌ها مخلوط نشده باشد.

۶. انتقال به سرویس بعدی با HttpClient

Propagation یعنی منتقل‌کردن اطلاعات لازم از فرستنده به گیرنده. ثبت شناسه در Scope یا Items آن را به شبکه نمی‌فرستد. برای فراخوانی HTTP، مقدار را روی پیام خروجی قرار دهید. این قطعه الگوی ادغام در سرویس واقعی است و برای اجرا به PaymentService نیاز دارد.

پیش از builder.Build، یک Client نام‌دار ثبت کنید. IHttpClientFactory ساخت Client و مدیریت Handlerهای زیربنایی را انجام می‌دهد:

builder.Services.AddHttpClient("Payment", client =>
{
    client.BaseAddress = new Uri("http://localhost:5087");
});

در Endpoint از نوع async، با دریافت HttpContext به نام context و IHttpClientFactory به نام factory، فراخوانی را به شکل زیر انجام دهید:

var correlationId = (string)context.Items["CorrelationId"]!;
var client = factory.CreateClient("Payment");
using var request = new HttpRequestMessage(HttpMethod.Get, "/health");
request.Headers.Add("X-Correlation-ID", correlationId);
using var response = await client.SendAsync(request, context.RequestAborted);
response.EnsureSuccessStatusCode();

در این مثال، /health یک مسیر آزمایشی در PaymentService است. گیرنده باید Header را بخواند و Scope مخصوص خودش را بسازد؛ برای مثال همان Middleware با ServiceName برابر PaymentService. سپس Logهای دو سرویس با CorrelationId مشترک قابل جست‌وجو هستند.

شناسهٔ متغیر هر درخواست را روی HttpRequestMessage بگذارید. تغییر DefaultRequestHeaders یک Client مشترک هنگام اجرای هم‌زمان درخواست‌ها می‌تواند شناسه‌ها را جابه‌جا کند. در پروژهٔ بزرگ می‌توانید انتقال را در DelegatingHandler، یعنی مرحلهٔ سفارشی مسیر ارسال HttpClient، متمرکز کنید؛ ولی Context درخواست را در فیلد مشترک یا طولانی‌عمر نگه ندارید و شناسه را فقط به مقصدهای مورد اعتماد بفرستید.

۷. پیام، Retry و کار پس‌زمینه

وقتی Order یک پیام برای پردازش بعدی منتشر می‌کند، ممکن است درخواست HTTP پیش از مصرف پیام تمام شود. بنابراین Consumer، یعنی دریافت‌کنندهٔ پیام، نمی‌تواند به HttpContext فرستنده تکیه کند. شناسه را در Metadata پیام، یعنی اطلاعات همراه آن، قرار دهید:

{
  "messageId": "msg-102",
  "correlationId": "79c7795a68274e54ae61d1e3be1262d7",
  "causationId": "msg-101",
  "type": "OrderCreated",
  "data": { "orderId": 42 }
}

این JSON قرارداد آموزشی است؛ محل واقعی فیلدها می‌تواند Header یا Properties مربوط به Broker باشد. MessageId یک پیام مشخص را معرفی می‌کند و CausationId شناسهٔ پیام یا عملیاتی است که باعث تولید پیام فعلی شده است. در این مثال msg-101 باعث تولید msg-102 شده، اما هر دو در یک فرایند با Correlation ID مشترک قرار دارند.

Consumer برای هر پیام یک Scope مستقل باز می‌کند، عملیات را با await انجام می‌دهد و Scope را پس از پردازش می‌بندد. در ارسال پیام بعدی همان Correlation ID حفظ می‌شود. برای یک Job مستقل بدون پیام ورودی، شناسه در شروع اجرای همان Job ساخته می‌شود.

Retry تکرار تلاش برای انجام همان عملیات است. معمولاً Correlation ID را در Retry حفظ می‌کنیم و شمارهٔ تلاش را در فیلدی مثل Attempt ثبت می‌کنیم. Idempotency Key کلیدی برای جلوگیری از اثر تجاری تکراری است؛ Correlation ID چنین تضمینی نمی‌دهد. مثلاً دو تلاش با شناسهٔ یکسان همچنان می‌توانند بدون سازوکار Idempotency دو بار پرداخت انجام دهند.

۸. اشتباه‌های رایج و تمرین

  • اعتماد امنیتی به شناسه: Correlation ID مدرک هویت و مجوز دسترسی نیست. دانستن آن نباید اجازهٔ مشاهدهٔ سفارش یا Log را بدهد.
  • قرار دادن دادهٔ شخصی در شناسه: ایمیل، شماره تلفن و Token را وارد شناسه نکنید؛ شناسه باید یک مقدار opaque، یعنی فاقد معنای تجاری قابل خواندن، باشد.
  • استفاده در Metric Label: هر شناسه مقدار متفاوتی دارد. این تنوع زیاد که Cardinality نام دارد، تعداد سری‌های Metric را زیاد می‌کند؛ برای بررسی یک عملیات از Log یا Trace استفاده کنید.
  • فرض انتقال خودکار: هر مرز HTTP، پیام و Job را بررسی کنید؛ اولین مرزی که شناسه را حذف کند، جست‌وجوی سراسری را ناقص می‌کند.

تمرین: دو نسخه از نمونه را روی پورت‌های 5086 و 5087 اجرا کنید. در نسخهٔ دوم ServiceName را PaymentService بگذارید و یک Endpoint از نوع GET با مسیر /health بسازید که یک Log بنویسد. در نسخهٔ اول یک Endpoint از نوع async اضافه کنید که قطعهٔ فراخوانی بخش قبل را اجرا کند. درخواست را با شناسهٔ مشخص بفرستید. معیار موفقیت این است که پاسخ Order و Logهای هر دو سرویس یک CorrelationId داشته باشند؛ درخواست مستقل بعدی بدون Header باید شناسهٔ تازه داشته باشد.

پرسش مرور: اگر Order شناسه را ثبت کند ولی Payment شناسهٔ دیگری داشته باشد، ابتدا چه چیزی را بررسی می‌کنید؟ Header پیام خروجی، سیاست پذیرش شناسه در گیرنده و قالب معتبر مورد توافق را بررسی کنید؛ اضافه‌کردن Logهای بیشتر بدون اصلاح انتقال، ارتباط رخدادها را بازسازی نمی‌کند.
