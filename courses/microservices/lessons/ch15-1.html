Logging در Microservices

از پیدا کردن یک سفارش ناموفق تا ثبت رخدادهای قابل جست‌وجو در ASP.NET Core

۱. چرا سفارش ۴۲ تکمیل نشد؟

کاربر روی «ثبت سفارش» کلیک کرده، اما نتیجه را دریافت نکرده است. سرویس Order درخواست را پذیرفته، سرویس Payment پرداخت را بررسی کرده و سرویس Inventory باید موجودی را رزرو می‌کرده است. وقتی فقط پیام «خطایی رخ داد» را داریم، معلوم نیست کدام مرحله متوقف شده است.

Logging یعنی ثبت رخدادهای اجرای برنامه به شکلی که بعداً بتوانیم آن‌ها را بررسی کنیم. هر Log یک سابقه از یک اتفاق است؛ مثلاً «درخواست پرداخت سفارش ۴۲ در زمان مشخص ناموفق شد». نمونهٔ زیر آموزشی است و قالب خروجی یک ابزار خاص نیست:

10:00:00Z  Information  Order      OrderId=42  Order accepted
10:00:01Z  Information  Payment    OrderId=42  Payment approved
10:00:03Z  Warning      Inventory  OrderId=42  Reservation timed out

اکنون یک سرنخ داریم: پرداخت تأیید شده، اما پاسخ رزرو موجودی به‌موقع نرسیده است. هنوز نمی‌توان گفت رزرو انجام نشده؛ شاید عملیات انجام شده و پاسخ آن گم شده باشد. Log شاهد یک رفتار مشاهده‌شده است، نه اثبات وضعیت نهایی همهٔ سرویس‌ها. برای تصمیم تجاری باید وضعیت سفارش و نتیجهٔ عملیات را هم بررسی کنیم.

۲. تفاوت Log، Metric و Trace

Metric یک اندازه‌گیری عددی است؛ مثلاً تعداد سفارش‌های ناموفق در هر دقیقه. Trace مسیر اجرای یک عملیات بین چند بخش یا سرویس را نشان می‌دهد. Monitoring پایش وضعیت سیستم است و می‌تواند از هر سه نوع اطلاعات استفاده کند.

نوع اطلاعاتپرسش نمونهکاربرد
Logبرای سفارش ۴۲ چه اتفاقی افتاد؟بررسی جزئیات یک رخداد
Metricچند درصد سفارش‌ها ناموفق‌اند؟تشخیص تغییر وضعیت و تعریف Alert
Traceدرخواست در کدام سرویس کند شد؟مشاهدهٔ مسیر و مدت اجرای بخش‌ها

مثلاً افزایش نرخ خطا شما را متوجه مشکل می‌کند؛ Trace سرویس کند را مشخص می‌کند و Log همان عملیات، خطا و شناسهٔ سفارش را در اختیار شما قرار می‌دهد. ثبت هزاران Log به‌تنهایی جای اندازه‌گیری نرخ خطا را نمی‌گیرد.

۳. چه اطلاعاتی ثبت کنیم؟

یک پیام قابل‌استفاده باید توضیح دهد چه اتفاقی، در کدام سرویس، برای کدام عملیات و با چه نتیجه‌ای رخ داده است. زمان را با UTC ثبت کنید تا تبدیل منطقهٔ زمانی باعث ابهام نشود؛ UTC جای همگام‌سازی ساعت سرورها را نمی‌گیرد.

  • Timestamp: زمان رخداد؛ برای محدود کردن بازهٔ جست‌وجو.
  • ServiceName و Environment: مثلاً OrderService و Production؛ برای جدا کردن سرویس و محیط.
  • Level و EventId: اهمیت رخداد و شناسهٔ ثابت نوع آن؛ مثلاً ۱۰۰۱ برای پذیرش سفارش.
  • OrderId یا MessageId: شناسهٔ عملیاتی که بررسی می‌کنیم. شناسه‌های تجاری هم باید مطابق سیاست دسترسی سازمان محافظت شوند.
  • Outcome و DurationMs: نتیجه و زمان سپری‌شده، وقتی برای رخداد معنی دارند.
  • Exception: اطلاعات خطای غیرمنتظره، در صورت وقوع و با توجه به احتمال وجود دادهٔ حساس در آن.

نام فیلدها را بین سرویس‌ها هماهنگ نگه دارید. اگر یکی از سرویس‌ها OrderId و دیگری order_number بنویسد، جست‌وجوی یک سفارش به دانستن قرارداد هر سرویس وابسته می‌شود.

۴. Structured Logging: پیام به‌علاوهٔ داده

Structured Logging یعنی مقدارهای مهم را جدا از متن پیام نگه داریم. این کار اجازه می‌دهد ابزار جست‌وجو روی فیلد OrderId فیلتر کند، نه اینکه فقط دنبال یک قطعه متن بگردد.

C# · مقایسه
// The value becomes part of a single string.
logger.LogInformation($"Order {orderId} accepted");

// A stable template and a named property.
logger.LogInformation("Order {OrderId} accepted", orderId);

در خط دوم، Message Template همان متن ثابت دارای جای‌نگهدار {OrderId} است. مقدار واقعی به‌صورت آرگومان جداگانه ارسال می‌شود. ذخیره و نمایش فیلدها به Provider وابسته است؛ صرف استفاده از Template به معنی وجود یک پایگاه جست‌وجوی مرکزی نیست.

Provider بخشی است که رخدادهای Logger را به یک خروجی می‌فرستد؛ مثلاً Console. ILogger<T> رابط ثبت رخداد است و نوع T به تعیین Category کمک می‌کند. Category نام گروه تولیدکنندهٔ Log است و برای فیلترکردن مفید است. مستندات Logging در .NET قرارداد این APIها را توضیح می‌دهند.

۵. انتخاب Log Level با مثال

Log Level اهمیت رخداد را مشخص می‌کند. تصمیم را بر اساس نتیجهٔ عملیات بگیرید؛ وجود Exception همیشه به معنی اختلال گسترده نیست.

Levelمثال در فروشگاه
Traceجزئیات بسیار ریز مراحل داخلی؛ معمولاً فقط در بررسی محدود یک مشکل.
Debugتعداد اقلام خوانده‌شده از Cache برای عیب‌یابی.
Informationپذیرش سفارش یا تکمیل موفق یک عملیات مهم.
WarningTimeout موقت که برای آن تلاش مجدد برنامه‌ریزی شده است.
Errorشکست نهایی عملیات پرداخت پس از تمام تلاش‌های مجاز.
Criticalاختلالی که ادامهٔ کار بخش حیاتی سرویس را ناممکن کرده است.
Noneمقدار تنظیماتی برای غیرفعال‌کردن ثبت؛ Level یک رخداد نیست.

مثلاً رد شدن پرداخت به علت موجودی ناکافی می‌تواند یک نتیجهٔ تجاری عادی باشد؛ ثبت آن با Error، گزارش سلامت فنی را گمراه می‌کند. برای Retry نیز هر تلاش را شکست نهایی معرفی نکنید: شمارهٔ تلاش و نتیجهٔ نهایی را از هم جدا ثبت کنید.

۶. نمونهٔ قابل‌اجرای ASP.NET Core

این نمونه با .NET 10 ساخته می‌شود و یک Endpoint آموزشی دارد که پذیرش سفارش را شبیه‌سازی می‌کند. Database و پرداخت واقعی ندارد. ابتدا پروژه را بسازید:

Terminal
dotnet new web -n LoggingDemo -f net10.0
cd LoggingDemo

محتوای Program.cs را با کد زیر جایگزین کنید. Dependency Injection یعنی دریافت وابستگی آماده از Container برنامه؛ در اینجا ASP.NET Core مقدار ILogger را به Endpoint می‌دهد. Scope مجموعه‌ای از اطلاعات مشترک برای Logهای یک محدودهٔ اجرای منطقی است. using پایان عمر آن را مشخص می‌کند.

Program.cs
using System.Diagnostics;
using Microsoft.Extensions.Logging;

var builder = WebApplication.CreateBuilder(args);

builder.Logging.ClearProviders();
builder.Logging.AddJsonConsole(options =>
{
    options.IncludeScopes = true;
    options.UseUtcTimestamp = true;
    options.TimestampFormat = "yyyy-MM-dd'T'HH:mm:ss.fff'Z'";
});

var app = builder.Build();

app.MapPost("/orders/{orderId:int}", (
    int orderId,
    ILogger<Program> logger) =>
{
    using var scope = logger.BeginScope(new Dictionary<string, object?>
    {
        ["ServiceName"] = "OrderService",
        ["Environment"] = app.Environment.EnvironmentName,
        ["OrderId"] = orderId,
        ["TraceId"] = Activity.Current?.TraceId.ToString()
    });

    if (orderId <= 0)
    {
        logger.LogWarning(new EventId(1000, "OrderRejected"),
            "Order rejected: {Reason}", "InvalidOrderId");
        return Results.BadRequest(new { error = "OrderId must be positive." });
    }

    logger.LogInformation(new EventId(1001, "OrderAccepted"),
        "Order {OrderId} accepted", orderId);

    return Results.Ok(new { orderId, status = "Accepted" });
});

app.Run();

ClearProviders خروجی‌های پیش‌فرض را حذف می‌کند و AddJsonConsole خروجی JSON را اضافه می‌کند؛ در پروژه‌ای که Provider دیگری دارد، حذف آن‌ها باید آگاهانه باشد. IncludeScopes اطلاعات Scope را هم وارد خروجی می‌کند. JSON کردن دوبارهٔ پیام لازم نیست؛ قالب‌بندی را Formatter انجام می‌دهد. جزئیات این تنظیمات در مستندات Console Formatter آمده است.

برنامه را اجرا کنید و در Terminal دوم درخواست بفرستید:

Terminal 1
dotnet run --no-launch-profile --urls http://localhost:5085
PowerShell · Terminal 2
Invoke-RestMethod -Method Post http://localhost:5085/orders/42

پاسخ شامل orderId برابر ۴۲ و status برابر Accepted است. یک Log با EventId برابر ۱۰۰۱ هم ثبت می‌شود. نمونهٔ زیر فقط فیلدهای منتخب خروجی را نشان می‌دهد؛ Timestamp و TraceId در هر اجرا تغییر می‌کنند و Scopes ممکن است اطلاعات بیشتری داشته باشد:

{
  "LogLevel": "Information",
  "EventId": 1001,
  "Category": "Program",
  "Message": "Order 42 accepted",
  "State": {
    "OrderId": 42,
    "{OriginalFormat}": "Order {OrderId} accepted"
  }
}

برای مسیر نامعتبر، درخواست به /orders/0 بفرستید: HTTP 400 و رخداد Warning با EventId برابر ۱۰۰۰ دریافت می‌شود. PowerShell برای پاسخ 400 خطا نمایش می‌دهد؛ این رفتار Client است و Log مربوط به رد درخواست را در Terminal برنامه می‌بینید.

۷. کم‌کردن شلوغی با تنظیم Category

اگر تمام جزئیات Framework را در کنار رخدادهای سفارش ثبت کنیم، پیدا کردن اتفاق اصلی سخت می‌شود. تنظیم زیر را در appsettings.json قرار دهید:

appsettings.json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}

رخدادهای Information برنامه ثبت می‌شوند، اما از Categoryهای Microsoft.AspNetCore فقط Warning و بالاتر باقی می‌مانند. اگر Information سفارش دیده نمی‌شود، علاوه بر این فایل، تنظیمات محیط مانند appsettings.Development.json، Environment Variableها و فیلتر مخصوص Provider را بررسی کنید. بالا بردن Level حداقل به Warning، Information را حذف می‌کند.

۸. Exception را کجا و چگونه ثبت کنیم؟

Exception خطایی است که جریان عادی اجرای کد را قطع می‌کند. برای عیب‌یابی، فقط Message آن کافی نیست؛ مسیر فراخوانی یا Stack Trace هم کمک می‌کند محل خطا را پیدا کنیم. Logger یک overload برای دریافت خود Exception دارد.

C# · الگوی ثبت در محل رسیدگی نهایی
logger.LogError(exception,
    "Payment failed for order {OrderId} after {AttemptCount} attempts",
    orderId, attemptCount);

این قطعه الگو است و متغیرهای آن از عملیات پرداخت می‌آیند. اگر Repository خطا را ثبت کند، Service دوباره ثبت کند و Middleware بار سوم ثبت کند، یک شکست به سه خطا تبدیل می‌شود. محل ثبت نهایی را مشخص کنید؛ مثلاً لایه‌ای که شکست عملیات را پاسخ می‌دهد. قبل از اضافه کردن Log دستی، رفتار ثبت خود Framework یا کتابخانهٔ پیام‌رسان را بررسی کنید.

اگر خطا را دوباره پرتاب می‌کنید، از throw; استفاده کنید تا Stack Trace اولیه حفظ شود. Cancellation ناشی از قطع درخواست کاربر را هم بدون بررسی به‌عنوان Error سرویس گزارش نکنید. Timeout وابستگی و لغو درخواست کاربر یک معنا ندارند.

۹. اتصال Logها بین سرویس‌ها

Correlation Id شناسه‌ای برای مرتبط کردن رخدادهای یک جریان کاری است. Trace Id شناسهٔ یک Trace است و Span Id یک بخش از اجرای آن را مشخص می‌کند. OrderId نیز شناسهٔ تجاری سفارش است؛ یک سفارش می‌تواند طی چند درخواست و چند Trace پردازش شود.

در نمونهٔ ما، Activity.Current اجرای فعال را نشان می‌دهد و TraceId از آن خوانده می‌شود. در عملیات فاقد Activity، این مقدار ممکن است null باشد. BeginScope اطلاعات را در محدودهٔ محلی در اختیار Provider می‌گذارد؛ آن را خودکار به سرویس بعدی ارسال نمی‌کند.

برای ادامهٔ Trace، Context باید با HTTP یا Headerهای پیام منتقل و در مقصد استخراج شود. ابزارهایی مانند OpenTelemetry با Instrumentation مناسب در این مسیر کمک می‌کنند. در Consumer پیام، MessageId و شمارهٔ تلاش هم مفیدند: یک پیام ممکن است چند بار تحویل شود و هر تحویل یک اجرای متفاوت داشته باشد. جزئیات Correlation Id و Distributed Tracing موضوع درس‌های بعدی فصل است.

۱۰. از Console تا جست‌وجوی مرکزی

وقتی سه نسخه از OrderService داریم، دیدن Console یکی از آن‌ها کافی نیست. Centralized Logging یعنی جمع‌آوری Logهای چند اجرا در یک محل قابل جست‌وجو. یک الگوی رایج این است که برنامه JSON را روی Console بنویسد، یک Agent یا Collector آن را جمع کند و به Backend ذخیره‌سازی بفرستد.

در این مسیر، Collector مسئول دریافت و انتقال است و Backend مسئول نگهداری و جست‌وجو. ابزارهایی مثل Seq یا مجموعه‌های مبتنی بر Elasticsearch گزینه‌های این لایه‌اند؛ انتخاب به نیاز جست‌وجو، حجم و زیرساخت بستگی دارد. برنامهٔ این درس فقط خروجی Console دارد و اتصال به Backend را پیاده‌سازی نمی‌کند.

برای بررسی سفارش، ابتدا Environment و ServiceName را محدود کنید، سپس OrderId و بازهٔ زمان را انتخاب کنید و در صورت وجود، TraceId را دنبال کنید. فقط به ترتیب رسیدن Logها اعتماد نکنید؛ انتقال شبکه و تفاوت ساعت میزبان‌ها می‌تواند ترتیب ظاهری را تغییر دهد.

برای صف انتقال ظرفیت مشخص، رفتار زمان پر شدن و هشدار افت داده تعریف کنید. قطعی Backend نباید بی‌تصمیم رها شود: Blocking می‌تواند درخواست‌ها را کند کند و Drop باعث از دست رفتن شواهد می‌شود. انتخاب Buffer محدود، Retry محدود یا ذخیرهٔ موقت باید با حساسیت داده و منابع سیستم هماهنگ باشد.

۱۱. امنیت، هزینه و Performance

ثبت کامل Request Body ممکن است رمز عبور، Access Token یا اطلاعات پرداخت را وارد Log کند. فیلدهای مجاز را از قبل انتخاب کنید و Authorization Header، Cookie، Secret و اطلاعات کارت را ثبت نکنید. خود Exception یا URL نیز ممکن است دادهٔ حساس داشته باشد؛ محدودکردن دسترسی و حذف یا پوشاندن این داده‌ها باید قبل از ارسال به Backend انجام شود.

Retention مدت نگهداری داده است. برای Logهای عیب‌یابی، مدت نگهداری و حجم مجاز تعیین کنید و دسترسی خواندن را محدود کنید. Audit Log سابقهٔ اعمال حساس مانند تغییر دسترسی است؛ نیازهای تمامیت، دسترسی و نگهداری آن ممکن است با Log تشخیصی متفاوت باشد. خروجی Console جای سازوکار قابل‌اتکای Audit یا ثبت تراکنش تجاری نیست.

در مسیر پرتکرار، تولید یک پیام بزرگ و محاسبهٔ دادهٔ آن هزینه دارد، حتی اگر خروجی بعداً فیلتر شود. برای محاسبهٔ گران Debug ابتدا IsEnabled را بررسی کنید. Source-generated Logging کد ثبت را هنگام Compile تولید می‌کند؛ LoggerMessage برای کم‌کردن هزینهٔ پردازش Template و Boxing در مسیرهای پرتکرار مناسب است. کاربرد و محدودیت‌ها را در مستندات High-performance Logging ببینید.

برای مثال، به‌جای ثبت تک‌تک هزار قلم سفارش در Information، تعداد اقلام و نتیجهٔ نهایی را ثبت کنید. Sampling یعنی ثبت بخشی از رخدادها برای کاهش حجم؛ برای دادهٔ الزامی Audit یا رخداد شکست نهایی، حذف نمونه‌ای را بدون سیاست مشخص اعمال نکنید.

۱۲. تمرین و معیار بررسی

  1. درخواست سفارش ۴۲ را اجرا کنید؛ وجود EventId برابر ۱۰۰۱ و State.OrderId برابر ۴۲ را در خروجی پیدا کنید.
  2. درخواست سفارش صفر را اجرا کنید؛ باید 400 بگیرید و فقط رخداد رد سفارش برای آن درخواست ثبت شود، نه OrderAccepted.
  3. Default را موقتاً Warning کنید و برنامه را دوباره اجرا کنید؛ Log پذیرش حذف می‌شود ولی Log رد سفارش باقی می‌ماند. سپس تنظیم را برگردانید.
  4. در دو درخواست متفاوت، Scope را بررسی کنید؛ OrderId هر درخواست باید متعلق به همان درخواست باشد.
  5. یک بازبینی محتوایی انجام دهید: آیا هیچ Token، رمز یا Body کامل درخواست در خروجی وجود دارد؟

برای بررسی خطای واقعی، از «چه چیزی را می‌خواهیم بفهمیم؟» شروع کنید. Log خوب برای همان پرسش شواهد می‌سازد: چه عملیاتی، در کدام اجرا، با چه نتیجه‌ای. تعداد بیشتر پیام‌ها الزاماً پاسخ دقیق‌تری نمی‌دهد.
