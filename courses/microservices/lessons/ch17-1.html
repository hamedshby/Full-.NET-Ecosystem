JWT Fundamentals

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۷
⏱️ زمان مطالعه: ۱۵ دقیقه
👤 تیم فنی

JWT را با یک مثال شروع کنیم

فرض کنید کاربر وارد سیستم می‌شود و می‌خواهد لیست سفارش‌های خودش را ببیند.

بعد از Login، سیستم یک Access Token به کاربر می‌دهد. Client این Token را در Requestهای بعدی برای API ارسال می‌کند.

HTTP 
GET /api/orders/42 HTTP/1.1
Host: api.example.com

Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

API قبل از اجرای Endpoint بررسی می‌کند که Token معتبر است یا خیر.

Flow 
User Login
    │
    ▼
Identity Server
    │
    │ Access Token
    ▼
Client
    │
    │ Authorization: Bearer TOKEN
    ▼
API
    │
    ├── Validate Signature
    ├── Validate Issuer
    ├── Validate Audience
    ├── Validate Expiration
    │
    ▼
Execute Endpoint

JWT چیست؟

JWT مخفف JSON Web Token است.

JWT یک فرمت استاندارد و فشرده برای انتقال اطلاعات یا همان Claim بین سیستم‌ها است.

💡
JWT خودش سیستم Login یا Authorization نیست. JWT فقط یک Token Format است که می‌تواند اطلاعاتی دربارهٔ User یا Client را حمل کند.

برای مثال Token ممکن است اطلاعات زیر را داشته باشد:

JSON 
{
  "sub": "123",
  "role": "Admin",
  "aud": "orders-api",
  "exp": 1790000000
}

ساختار JWT

یک JWT معمولاً از سه قسمت تشکیل شده است:

JWT 
Header.Payload.Signature

هر قسمت با یک نقطه . از قسمت بعدی جدا می‌شود.

JWT Example 
eyJhbGciOiJSUzI1NiJ9
.
eyJzdWIiOiIxMjMiLCJhdWQiOiJvcmRlcnMtYXBpIn0
.
X4iK7m...
بخش وظیفه
Header مشخص می‌کند Token با چه Algorithmی امضا شده است.
Payload Claimهای مربوط به User، Client و Token را نگه می‌دارد.
Signature برای تشخیص دست‌کاری Token استفاده می‌شود.

1. Header

Header معمولاً Algorithm امضا و نوع Token را مشخص می‌کند.

JSON 
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2026-09"
}

در این مثال:

  • alg الگوریتم امضا را مشخص می‌کند.
  • typ نوع Token را مشخص می‌کند.
  • kid مشخص می‌کند کدام Key برای امضا استفاده شده است.

2. Payload

Payload اطلاعات یا همان Claimها را نگه می‌دارد.

JSON 
{
  "sub": "123",
  "name": "Hamed",
  "role": "Admin",
  "aud": "orders-api",
  "exp": 1790000000
}
⚠️
Payload یک JWT معمولی رمزنگاری نشده است. هر کسی که Token را داشته باشد می‌تواند Payload آن را Decode کند.

بنابراین اطلاعات حساس مثل موارد زیر را داخل JWT قرار ندهید:

  • Password
  • Secret Key
  • شماره کامل کارت بانکی
  • اطلاعات محرمانهٔ شخصی

3. Signature

Signature برای این استفاده می‌شود که API متوجه شود Token تغییر نکرده است و توسط Issuer مورد اعتماد صادر شده است.

Concept 
Header
   +
Payload
   +
Signing Key
   │
   ▼
Signature

اگر مهاجم Payload را تغییر دهد، برای مثال:

Before 
"role": "User"

را تبدیل کند به:

After 
"role": "Admin"

Signature دیگر معتبر نخواهد بود و API باید Token را Reject کند.

Base64Url رمزنگاری نیست

Header و Payload معمولاً با Base64Url Encode می‌شوند.

Base64Url فقط Binary Data را به Text تبدیل می‌کند. این کار هیچ محرمانگی ایجاد نمی‌کند.

⚠️
Encoded ≠ Encrypted
هر کسی که JWT را داشته باشد می‌تواند Header و Payload آن را Decode کند.

Claim چیست؟

Claim یک اطلاعات کوچک دربارهٔ User، Client یا Token است.

برای مثال:

Claims 
UserId = 123

Role = Admin

Audience = orders-api

Expiration = 2026-09-18

JWT تعدادی Claim استاندارد دارد که در بیشتر سیستم‌ها استفاده می‌شوند.

Claim نام معنا
iss Issuer چه سیستمی Token را صادر کرده است؟
aud Audience Token برای کدام API صادر شده است؟
sub Subject Token متعلق به چه User یا Clientی است؟
exp Expiration Token چه زمانی منقضی می‌شود؟
nbf Not Before Token از چه زمانی قابل استفاده است؟
iat Issued At Token چه زمانی صادر شده است؟
jti JWT ID شناسهٔ یکتای Token
scope Scope Client اجازهٔ انجام چه عملیات‌هایی را دارد؟

API هنگام دریافت JWT چه چیزهایی را بررسی می‌کند؟

API نباید صرفاً به این دلیل که Request دارای JWT است آن را معتبر بداند.

چند بررسی مهم باید انجام شود:

Validation 
JWT Received
     │
     ▼
Signature Valid?
     │
     ▼
Issuer Valid?
     │
     ▼
Audience Valid?
     │
     ▼
Token Expired?
     │
     ▼
Create ClaimsPrincipal
     │
     ▼
Authorization
     │
     ▼
Execute Endpoint
Validation سؤال
Signature آیا Token دست‌کاری شده است؟
Issuer آیا Token توسط Identity Provider مورد اعتماد صادر شده است؟
Audience آیا این Token برای همین API صادر شده است؟
Expiration آیا Token هنوز معتبر است؟
Not Before آیا زمان استفاده از Token شروع شده است؟
✅
Token زمانی قابل اعتماد است که Signature، Issuer، Audience و زمان اعتبار آن به‌درستی بررسی شده باشند.

Authentication با Authorization چه فرقی دارد؟

این دو مفهوم در JWT بسیار مهم هستند.

مفهوم سؤال اصلی مثال
Authentication این شخص چه کسی است؟ UserId = 123
Authorization این شخص اجازهٔ انجام چه کاری را دارد؟ CanDeleteOrder

JWT معمولاً Claimهایی در اختیار Application قرار می‌دهد که بعداً Authorization بر اساس آن‌ها انجام می‌شود.

Access Token، Refresh Token و ID Token

این سه Token کاربردهای متفاوتی دارند و نباید با یکدیگر اشتباه گرفته شوند.

Token استفاده‌کننده کاربرد
Access Token API اجازهٔ دسترسی به Resource
Refresh Token Authorization Server دریافت Access Token جدید
ID Token Client اطلاعات Authentication در OpenID Connect

Access Token

Access Token همان Tokenی است که Client برای دسترسی به API ارسال می‌کند.

HTTP 
Authorization: Bearer ACCESS_TOKEN

بهتر است Access Token عمر کوتاهی داشته باشد.

Refresh Token

وقتی Access Token منقضی شد، Client می‌تواند Refresh Token را به Authorization Server ارسال کند و Access Token جدید بگیرد.

Flow 
Access Token Expired
        │
        ▼
Send Refresh Token
        │
        ▼
Authorization Server
        │
        ▼
New Access Token

Refresh Token معمولاً عمر بیشتری دارد و باید با امنیت بیشتری نگهداری شود.

💡
Refresh Token لازم نیست JWT باشد. در بسیاری از سیستم‌ها یک مقدار تصادفی و Opaque انتخاب مناسبی است.

ID Token

ID Token در OpenID Connect برای انتقال اطلاعات مربوط به Authentication به Client استفاده می‌شود.

⚠️
ID Token را نباید به‌جای Access Token برای فراخوانی API استفاده کرد.

Signed JWT و Encrypted JWT

JWT می‌تواند Signed یا Encrypted باشد.

نوع Payload هدف
JWS قابل خواندن جلوگیری از دست‌کاری Token
JWE رمزنگاری‌شده محرمانگی Payload

بیشتر Access Tokenهای JWT که در APIها مشاهده می‌کنیم از نوع Signed JWT هستند.

⚠️
حتی اگر JWT امضا یا رمزنگاری شده باشد، انتقال آن باید روی HTTPS انجام شود.

چرا JWT در Microservices محبوب است؟

یکی از مزایای مهم JWT این است که API می‌تواند Token را بدون مراجعهٔ مستقیم به Session Database اعتبارسنجی کند.

Microservices 
                 Identity Server
                       │
                       │ JWT
                       ▼
                    Client
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
     Orders API   Payment API   Profile API

       Validate      Validate      Validate
         JWT           JWT           JWT

هر سرویس می‌تواند با استفاده از Key معتبر، Token را بررسی کند.

💡
Stateless بودن JWT به این معنا نیست که کل Authentication System بدون State است. اطلاعاتی مانند User، Refresh Token، Revocation، Permission و Audit همچنان ممکن است در Database نگهداری شوند.

مشکل Claimهای قدیمی

فرض کنید هنگام Login این Claim داخل Token قرار گرفته باشد:

JWT Claim 
"role": "Admin"

حالا Administrator سیستم دسترسی کاربر را تغییر می‌دهد:

Database 
Admin → User

اما Token قبلی ممکن است هنوز این Claim را داشته باشد:

Old Token 
"role": "Admin"

در نتیجه تا زمان Expire شدن Token، اطلاعات آن می‌تواند قدیمی باشد.

به همین دلیل معمولاً Access Tokenها کوتاه‌عمر طراحی می‌شوند.

چه زمانی JWT انتخاب مناسبی نیست؟

JWT همیشه بهترین انتخاب نیست.

  • اگر یک Web Application ساده با Backend هم‌دامنه دارید، Cookie و Server-side Session ممکن است ساده‌تر باشند.
  • اگر Logout فوری و سراسری نیاز دارید، Access Token طولانی‌عمر مدیریت Revocation را سخت می‌کند.
  • اگر اطلاعات داخل Token دائماً تغییر می‌کنند، Claimها سریعاً قدیمی می‌شوند.
  • اگر فقط به یک شناسهٔ تصادفی نیاز دارید، Opaque Token ممکن است ساده‌تر باشد.
