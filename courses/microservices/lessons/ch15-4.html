Distributed Tracing در Microservices

از مشاهدهٔ یک درخواست کند تا جمع‌آوری Spanها، پیدا کردن محل تأخیر و بررسی خطا بین سرویس‌ها

۱. کاربر دو ثانیه منتظر ماند؛ زمان کجا مصرف شد؟

ثبت سفارش از Order شروع می‌شود، برای پرداخت به Payment می‌رود و سپس پاسخ به کاربر برمی‌گردد. Order می‌گوید درخواست موفق بوده و Payment هم خطایی ثبت نکرده است، اما کاربر منتظر مانده است. برای بررسی این وضعیت، فقط دانستن نتیجه کافی نیست؛ باید مسیر و زمان بخش‌های اجرای همین درخواست را ببینیم.

Distributed Tracing روشی برای دنبال‌کردن اجرای یک عملیات در چند بخش یا سرویس است. Trace مجموعهٔ بخش‌های مرتبط این اجراست. هر بخش، یا Span، نام، زمان شروع، مدت اجرا و اطلاعاتی دربارهٔ نتیجه دارد. Trace ID شناسهٔ مشترک بخش‌های یک Trace است؛ Span ID هر بخش را مشخص می‌کند و Parent Span ID ارتباط آن با بخش والد را نشان می‌دهد.

One trace — illustrative durations

Order /checkout                  [====================]  2000 ms
  HTTP call to Payment            [==================]   1800 ms
    Payment /authorize             [================]    1600 ms
      Provider call                 [==============]     1400 ms

در این مثال فرضی، انتظار برای Provider، یعنی ارائه‌دهندهٔ بیرونی پرداخت، بخش بزرگی از زمان را گرفته است. این مشاهده جهت بررسی را مشخص می‌کند؛ هنوز علت نهایی، مثلاً اشباع اتصال یا کندی خود Provider، معلوم نیست. مجموع این چهار زمان ۶۸۰۰ میلی‌ثانیه، زمان انتظار کاربر نیست؛ Spanهای فرزند داخل بازهٔ والد اجرا شده‌اند.

۲. کنار Log و Metric چه چیزی اضافه می‌کند؟

Log سابقهٔ یک رخداد و Metric اندازه‌گیری عددی وضعیت سیستم است. مثلاً Metric نشان می‌دهد درخواست‌ها کندتر شده‌اند؛ Trace یک نمونهٔ مشخص از مسیر کند را نشان می‌دهد و Log جزئیات رخداد همان مسیر را روشن می‌کند.

ابزار بررسیپرسشمحدودیت
Metricچند درصد درخواست‌ها کند یا ناموفق‌اند؟معمولاً مسیر یک درخواست مشخص را نشان نمی‌دهد
Traceاین درخواست از کجا گذشت و کجا منتظر ماند؟بخش اندازه‌گیری‌نشده یا جمع‌آوری‌نشده را نمی‌بیند
Logدر مرحلهٔ ناموفق چه اتفاقی ثبت شد؟به‌تنهایی نمودار زمان و ارتباط فراخوانی‌ها را نمی‌سازد

یک مسیر عملی این است: با افزایش زمان پاسخ متوجه مشکل شوید، Traceهای کند همان بازه و نسخهٔ سرویس را پیدا کنید، سپس Logهای دارای Trace ID همان اجرا را بخوانید. یک Trace کند به‌تنهایی ثابت نمی‌کند همهٔ درخواست‌ها همین مشکل را دارند؛ آن را با چند نمونه و Metricهای همان بازه مقایسه کنید.

۳. اطلاعات چگونه به صفحهٔ نمایش می‌رسد؟

Instrumentation کدی است که Spanها و داده‌های اجرای برنامه را تولید می‌کند. Propagation انتقال Trace Context، یعنی اطلاعات لازم برای ادامهٔ Trace، بین سرویس‌هاست. در HTTP، این انتقال معمولاً با Header استاندارد traceparent انجام می‌شود؛ فقط نوشتن Trace ID در متن Log کافی نیست.

OpenTelemetry مجموعهٔ APIها، SDKها و ابزارهای تولید و انتقال Telemetry است؛ Telemetry داده‌ای است که دربارهٔ رفتار برنامه جمع می‌کنیم. Exporter داده را از برنامه به مقصد می‌فرستد. Collector یک مؤلفهٔ جدا برای دریافت، پردازش و ارسال Telemetry است. Backend محل ذخیره و جست‌وجوی داده است؛ مثلاً Jaeger امکان جست‌وجو و نمایش Traceها را فراهم می‌کند.

Request path:  Client → Order → Payment
                           traceparent →

Telemetry:     Order   ─┐
                        ├→ Exporter → [Collector] → Trace backend / UI
               Payment ─┘

مسیر Telemetry با مسیر پاسخ تجاری متفاوت است. در این نمودار Collector اختیاری است؛ برای آزمایش می‌توان مستقیم به Backend فرستاد. در محیط واقعی Collector می‌تواند Batch، یعنی گروه‌بندی ارسال‌ها، و پردازش متمرکز انجام دهد. ارسال معمولاً از صف‌های محدود استفاده می‌کند؛ خرابی مقصد می‌تواند باعث ازدست‌رفتن داده شود، پس Tracing دفتر قطعی تراکنش‌های تجاری نیست. نمای کلی در مستندات Observability با OpenTelemetry آمده است.

۴. یک آزمایش قابل‌اجرا با .NET 10

یک برنامه را در دو Process مستقل با نام‌های Order و Payment اجرا می‌کنیم. Order یک درخواست HTTP می‌فرستد و Payment یک عملیات ۶۰۰ میلی‌ثانیه‌ای را شبیه‌سازی می‌کند. ابتدا Spanها را در Console می‌بینیم؛ در بخش بعد، ارسال به Jaeger را اضافه می‌کنیم. این نمونه Database یا پرداخت واقعی ندارد.

Terminal · ساخت پروژه
dotnet new web -n DistributedTracingDemo -f net10.0
cd DistributedTracingDemo
dotnet add package OpenTelemetry.Extensions.Hosting
dotnet add package OpenTelemetry.Instrumentation.AspNetCore
dotnet add package OpenTelemetry.Instrumentation.Http
dotnet add package OpenTelemetry.Exporter.Console

این فرمان‌ها نسخهٔ پایدار قابل‌دسترسی Packageها را به پروژه اضافه می‌کنند. نسخه‌های ثبت‌شده در فایل پروژه را برای بازتولید نگه دارید. Activity نمایندهٔ Span در .NET است و ActivitySource منبع تولید Activityهای سفارشی است. Program.cs را با کد زیر جایگزین کنید:

Program.cs
using System.Diagnostics;
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

var builder = WebApplication.CreateBuilder(args);
var serviceName = builder.Configuration["ServiceName"] ?? "Order";
using var source = new ActivitySource("Shop.Checkout");

builder.Services.AddHttpClient("Payment", client =>
    client.BaseAddress = new Uri("http://localhost:15102"));

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService(serviceName))
    .WithTracing(tracing => tracing
        .SetSampler(new AlwaysOnSampler())
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("Shop.Checkout")
        .AddConsoleExporter());

var app = builder.Build();

app.MapGet("/payment", async (bool? fail, CancellationToken cancellationToken) =>
{
    using var activity = source.StartActivity("Payment.Authorize");
    activity?.SetTag("payment.provider", "simulator");
    await Task.Delay(600, cancellationToken);

    if (fail == true)
    {
        activity?.SetStatus(ActivityStatusCode.Error, "Simulated provider failure");
        return Results.StatusCode(503);
    }

    return Results.Ok(new { approved = true });
});

app.MapGet("/checkout", async (
    bool? fail, IHttpClientFactory factory, HttpContext context) =>
{
    var traceId = Activity.Current?.TraceId.ToString();
    var client = factory.CreateClient("Payment");
    var path = fail == true ? "/payment?fail=true" : "/payment";
    using var response = await client.GetAsync(path, context.RequestAborted);

    if (!response.IsSuccessStatusCode)
    {
        return Results.Json(new { traceId, error = "Payment unavailable" },
            statusCode: 502);
    }

    return Results.Ok(new { traceId, status = "Completed" });
});

app.Run();

AddService نام سرویس را در Resource ثبت می‌کند؛ Resource اطلاعات تولیدکنندهٔ داده است، نه مشخصات یک درخواست. AddAspNetCoreInstrumentation درخواست ورودی و AddHttpClientInstrumentation فراخوانی خروجی را پوشش می‌دهند. AddSource باعث جمع‌آوری Activityهای منبع Shop.Checkout می‌شود؛ اگر نام با ActivitySource متفاوت باشد، Span سفارشی دیده نمی‌شود.

StartActivity بخش Payment.Authorize را زیر Activity درخواست Payment ایجاد می‌کند. using پایان آن را ثبت می‌کند. Tag یک ویژگی نام‌دار روی Span است؛ در اینجا می‌گوید Provider شبیه‌ساز است. عملگر ?. لازم است، چون در نبود Listener مناسب یا با سیاست Sampling، StartActivity می‌تواند null باشد. توضیح APIها در راهنمای Instrumentation در .NET آمده است.

AlwaysOnSampler برای این آزمایش انتخاب شده تا اجراها برای ثبت انتخاب شوند؛ تنظیم پیشنهادی عمومی برای Production نیست. AddConsoleExporter خود Spanها را چاپ می‌کند و با Console Logger معمولی تفاوت دارد. این برنامه Logs را به Backend ارسال نمی‌کند. الگوی پیکربندی بر اساس راهنمای رسمی OpenTelemetry برای ASP.NET Core است.

۵. اجرا، مشاهدهٔ Span و ایجاد خطا

یک بار Build کنید و سپس در دو Terminal از پوشهٔ پروژه اجرا کنید:

dotnet build
Terminal 1 · Payment
dotnet run --no-build --no-launch-profile -- --urls http://localhost:15102 --ServiceName Payment
Terminal 2 · Order
dotnet run --no-build --no-launch-profile -- --urls http://localhost:15101 --ServiceName Order

در PowerShell سوم درخواست را بفرستید:

Invoke-RestMethod http://localhost:15101/checkout
curl.exe -i "http://localhost:15101/checkout?fail=true"

درخواست اول پاسخ Completed و یک traceId می‌دهد. در Console دو Process، Spanهای مرتبط را با همان TraceId پیدا کنید. مسیر اصلی شامل Span ورودی Order، Span خروجی HttpClient، Span ورودی Payment و Span داخلی Payment.Authorize است؛ بسته به نسخه و Instrumentation ممکن است Spanهای دیگری هم دیده شوند.

در خروجی، DisplayName نام عملیات، Duration مدت اجرا، SpanId شناسهٔ بخش و ParentSpanId والد آن است. Payment.Authorize حدود ۶۰۰ میلی‌ثانیه یا بیشتر طول می‌کشد؛ زمان دقیق به زمان‌بندی و بار سیستم وابسته است. اولین درخواست ممکن است به دلیل راه‌اندازی اولیه و ساخت اتصال کندتر باشد؛ چند بار اجرا کنید.

درخواست دوم از Payment پاسخ 503 می‌گیرد و Order پاسخ 502 برمی‌گرداند. Span سفارشی با SetStatus به Error علامت‌گذاری می‌شود؛ Instrumentation مربوط به HTTP نیز وضعیت 5xx را روی Spanهای HTTP منعکس می‌کند. SetStatus پاسخ HTTP را تغییر نمی‌دهد و Exception پرتاب نمی‌کند؛ به همین دلیل در کد، نتیجهٔ HTTP جداگانه مشخص شده است. نتیجهٔ تجاری عادی مثل «موجودی ناکافی» را الزاماً خطای زیرساختی در نظر نگیرید.

۶. نمایش مسیر در Jaeger

برای دیدن نمودار، Docker باید نصب و Engine آن فعال باشد. در یک Terminal جدا Jaeger را فقط روی رابط محلی اجرا کنید. این حالت آزمایشی از ذخیره‌سازی حافظه‌ای استفاده می‌کند و داده با پایان اجرا باقی نمی‌ماند:

Terminal · Jaeger
docker run --rm --name tracing-lesson-jaeger -p 127.0.0.1:16686:16686 -p 127.0.0.1:4317:4317 cr.jaegertracing.io/jaegertracing/jaeger:2.21.0

طبق راهنمای Jaeger، پورت 16686 برای UI و پورت 4317 برای دریافت OTLP روی gRPC است. OTLP پروتکل انتقال دادهٔ OpenTelemetry است. برنامه‌های این مثال روی میزبان اجرا می‌شوند؛ اگر آن‌ها را Container کنید، localhost داخل Container به همان Container اشاره می‌کند و آدرس مقصد باید متناسب با شبکه تغییر کند.

دو برنامه را با Ctrl+C متوقف کنید، Package زیر را اضافه کنید و سپس تغییر کد را انجام دهید:

dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol

این using را ابتدای Program.cs اضافه کنید:

using OpenTelemetry.Exporter;

انتهای زنجیرهٔ WithTracing، عبارت .AddConsoleExporter()); را با قطعهٔ زیر جایگزین کنید تا Spanها به هر دو مقصد بروند:

.AddConsoleExporter()
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri("http://localhost:4317");
            options.Protocol = OtlpExportProtocol.Grpc;
        }));

دوباره dotnet build و فرمان‌های اجرای دو سرویس را بزنید، سپس درخواست تازه بفرستید. صفحهٔ Jaeger محلی را باز کنید، سرویس Order را انتخاب و Traceهای بازهٔ اخیر را جست‌وجو کنید. Trace مربوط به درخواست را با traceId پاسخ تطبیق دهید و شاخهٔ Payment.Authorize را باز کنید. ارسال OTLP ممکن است با تأخیر کوتاه Batch انجام شود. اگر Console خروجی دارد ولی UI ندارد، ابتدا Endpoint، Protocol و دسترسی مقصد را بررسی کنید. گزینه‌های Export در مستندات Exporterهای OpenTelemetry .NET آمده است.

۷. نمودار را چگونه تحلیل کنیم؟

Waterfall نمایی است که Spanها را به‌صورت نوارهای زمانی نشان می‌دهد. نوار بلندتر فقط مدت سپری‌شدهٔ بیشتری دارد؛ الزاماً CPU بیشتری مصرف نکرده است. در نمونه، Task.Delay تقریباً تمام زمان Span سفارشی را به انتظار اختصاص می‌دهد.

  1. درخواست درست را انتخاب کنید: Trace ID، زمان، نام سرویس و نسخهٔ منتشرشده را تطبیق دهید.
  2. از ریشه به فرزند بروید: اگر بیشتر زمان Order داخل فراخوانی Payment است، بررسی را در Payment ادامه دهید.
  3. شاخه‌های هم‌زمان را تشخیص دهید: دو فراخوانی موازی ۷۰۰ و ۹۰۰ میلی‌ثانیه‌ای معمولاً حدود ۹۰۰ میلی‌ثانیه به انتظار بخش منتظر همهٔ نتایج اضافه می‌کنند، نه ۱۶۰۰؛ سربار هم وجود دارد.
  4. Critical Path را پیدا کنید: این مسیر از وابستگی‌ها زمان تکمیل کل عملیات را تعیین می‌کند. کوتاه‌کردن یک شاخهٔ سریع و موازی ممکن است پاسخ نهایی را سریع‌تر نکند.
  5. فضای خالی را با شواهد بررسی کنید: فاصلهٔ زمانی می‌تواند از انتظار، صف، شبکه، بخش فاقد Instrumentation یا تفاوت ساعت سرورها باشد؛ به‌تنهایی علت را ثابت نمی‌کند.

برای Spanهای هم‌پوشان، کم‌کردن سادهٔ مجموع زمان فرزندان از والد هم می‌تواند اشتباه باشد. پیش از نتیجه‌گیری دربارهٔ شبکه یا CPU، Metricهای اتصال، صف و منابع و Logهای همان عملیات را بررسی کنید. همگام‌سازی ساعت سرویس‌ها نیز به تفسیر Timeline کمک می‌کند.

۸. پیام، Retry و Trace ناقص

در پیام‌رسانی، Producer فرستنده و Consumer دریافت‌کنندهٔ پیام است. Context باید در Metadata پیام منتقل و هنگام پردازش بازیابی شود. یک پیام ممکن است پس از پایان درخواست HTTP مصرف شود؛ به HttpContext فرستنده تکیه نکنید. کتابخانهٔ Messaging و Propagator آن، یعنی سازوکار نوشتن و خواندن Context، باید هماهنگ پیکربندی شوند.

در پردازش دسته‌ای چند پیام، یک Span نمی‌تواند چند والد مستقیم داشته باشد. Span Link ارتباط با Contextهای دیگر را نشان می‌دهد؛ در .NET با ActivityLink بیان می‌شود. در فرایندهای طولانی ممکن است چند Trace با Link یا Correlation ID مرتبط شوند. جزئیات لینک‌ها در راهنمای Span Link در OpenTelemetry .NET توضیح داده شده است.

Retry تلاش دوباره برای یک عملیات است. چند Span خروجی مشابه می‌تواند نشان‌دهندهٔ چند تلاش باشد؛ شمارهٔ تلاش و نتیجهٔ نهایی را ثبت کنید. Timeout اثبات نمی‌کند سرویس مقصد هیچ کاری انجام نداده است. برای جلوگیری از اثر تکراری، مانند دو بار پرداخت، به Idempotency نیاز دارید؛ Tracing فقط به بررسی رفتار کمک می‌کند.

نشانهاول چه چیزی را بررسی کنیم؟
Order و Payment در دو Trace جدا دیده می‌شوندانتقال traceparent، تنظیمات Gateway و ساخت اشتباه Context جدید
Span داخلی وجود نداردتطابق ActivitySource با AddSource و تصمیم Sampling
یک سرویس اصلاً دیده نمی‌شودنام Resource، Instrumentation، Exporter، بازهٔ جست‌وجو و دسترسی شبکه
Trace ID در Log هست ولی Trace پیدا نمی‌شودSampling، شکست ارسال و زمان نگهداری داده

۹. Sampling و هزینهٔ نگهداری

Sampling انتخاب بخشی از اجراها برای ثبت و نگهداری است. در Head Sampling تصمیم نزدیک شروع عملیات گرفته می‌شود؛ هزینه زود محدود می‌شود، اما نتیجهٔ نهایی هنوز معلوم نیست. در Tail Sampling تصمیم پس از دریافت بخشی از Spanها و انتظار برای اطلاعات بیشتر گرفته می‌شود؛ می‌توان اجراهای کند یا خطادار را هدف گرفت، ولی حافظه، زمان انتظار و مسیریابی هماهنگ لازم است.

اگر Head Sampling داده‌ای را از ابتدا حذف کرده باشد، Tail Sampling نمی‌تواند آن را بازسازی کند. سیاست Parent-based نیز کمک می‌کند سرویس‌های بعدی تصمیم والد را دنبال کنند. Sampling به معنی نمونهٔ کاملاً بی‌طرف از همهٔ رخدادها نیست؛ نرخ خطای کل سرویس را صرفاً از Traceهایی که عمداً برای خطا انتخاب شده‌اند محاسبه نکنید. توضیح سیاست‌ها در مستندات Sampling آمده است.

نام Span را ثابت و کم‌تنوع نگه دارید، مثلاً Payment.Authorize، نه Payment.Authorize.Order42. Token، شمارهٔ کارت و Body کامل درخواست را در Tagها نگذارید. نام سرویس، نسخه و محیط را هماهنگ تعریف کنید و مدت نگهداری، دسترسی به Backend و هزینهٔ ارسال را مشخص کنید. خرابی سیستم Tracing نباید به وابستگی اجباری موفقیت پرداخت تبدیل شود.

۱۰. تمرین: تأخیر را با شواهد پیدا کنید

در Payment مقدار Task.Delay را از 600 به 1200 تغییر دهید، Build و سرویس را دوباره اجرا کنید. چند درخواست تازه بفرستید و آن‌ها را با قبل مقایسه کنید. انتظار داریم زمان Payment.Authorize و والدهای منتظر آن بیشتر شود؛ تعداد Spanهای مسیر اصلی نباید صرفاً به علت افزایش Delay تغییر کند.

بعد درخواست fail=true را اجرا کنید. بررسی کنید Span داخلی Payment خطادار است و پاسخ Order برابر 502 است. اگر فقط رنگ قرمز را دیدید، بررسی تمام نشده است؛ باید مشخص کنید کدام مرحله خطا را ایجاد کرده، کدام مرحله فقط آن را دریافت کرده و چه اطلاعاتی هنوز جمع‌آوری نشده است.

پرسش مرور: اگر Order حدود دو ثانیه طول بکشد ولی هیچ Span فرزندی دیده نشود، آیا نتیجه می‌گیریم تمام زمان در کد Order مصرف شده است؟ خیر؛ ممکن است فراخوانی خروجی یا عملیات داخلی Instrumentation نداشته باشد. ابتدا پوشش جمع‌آوری را بررسی کنید، سپس دربارهٔ محل مصرف زمان نتیجه بگیرید.
