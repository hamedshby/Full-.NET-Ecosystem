Refresh Token, Rotation and Revocation

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۷
⏱️ زمان مطالعه: ۲۸ دقیقه
👤 تیم فنی

Access Token باید کوتاه‌عمر باشد. اگر پس از پایان آن کاربر مجبور به Login مجدد شود، تجربهٔ کاربری ضعیف خواهد شد. Refresh Token اجازه می‌دهد Client از Authorization Server یک Access Token جدید بگیرد.

Token Lifecycle
Login
  └─ Access Token A (10 min) + Refresh Token R1 (30 days)
       └─ Refresh R1
            ├─ revoke R1
            └─ issue Access Token B + Refresh Token R2

در این مدل هر Refresh Token فقط یک بار مصرف می‌شود. این رفتار Rotation نام دارد و سرقت Token قدیمی را قابل‌تشخیص می‌کند.

⚠️
Refresh Token یک Bearer credential قدرتمند است. آن را JWT طولانی‌عمر و بدون State نسازید. یک مقدار opaque با entropy بالا تولید کنید، hash آن را در Database نگه دارید و lifecycle را سمت Server کنترل کنید.

مدل دادهٔ Refresh Token

RefreshToken.cs
public sealed class RefreshToken
{
    public Guid Id { get; init; }
    public required string UserId { get; init; }
    public required string TokenHash { get; init; }
    public required string FamilyId { get; init; }
    public DateTime CreatedAtUtc { get; init; }
    public DateTime ExpiresAtUtc { get; init; }
    public DateTime? UsedAtUtc { get; set; }
    public DateTime? RevokedAtUtc { get; set; }
    public Guid? ReplacedByTokenId { get; set; }
    public required string DeviceId { get; init; }

    public bool IsActive(DateTime now) =>
        UsedAtUtc is null &&
        RevokedAtUtc is null &&
        ExpiresAtUtc > now;
}

FamilyId زنجیرهٔ R1، R2 و R3 را به هم متصل می‌کند. DeviceId امکان Logout یک Device بدون خروج همهٔ Deviceها را می‌دهد. Database باید روی TokenHash یک Unique Index داشته باشد.

تولید مقدار تصادفی و Hash

RefreshTokenFactory.cs
using System.Security.Cryptography;
using System.Text;

public static class RefreshTokenFactory
{
    public static string CreatePlainText()
    {
        var bytes = RandomNumberGenerator.GetBytes(64);
        return Convert.ToBase64String(bytes);
    }

    public static string Hash(string token)
    {
        var bytes = Encoding.UTF8.GetBytes(token);
        return Convert.ToHexString(SHA256.HashData(bytes));
    }
}

مقدار plain text فقط هنگام صدور به Client برمی‌گردد و بعد دور ریخته می‌شود. Database فقط Hash را نگه می‌دارد؛ بنابراین نشت Database مستقیماً credential قابل‌استفاده تولید نمی‌کند. entropy بالای مقدار تصادفی، brute-force کردن Hash را غیرعملی می‌کند.

الگوریتم Rotation اتمیک

  1. Refresh Token ورودی را Hash کنید.
  2. رکورد را داخل Transaction و با concurrency control بخوانید.
  3. Expiration، Revocation و User/Client binding را بررسی کنید.
  4. Token قبلی را مصرف‌شده علامت بزنید.
  5. Refresh Token جایگزین با همان Family و یک Access Token جدید بسازید.
  6. هر دو تغییر را در یک Commit ذخیره کنید و plain text Token جدید را فقط یک بار برگردانید.
Refresh flow - simplified
public async Task<TokenPair> RotateAsync(
    string presentedToken,
    string deviceId,
    CancellationToken cancellationToken)
{
    var now = _timeProvider.GetUtcNow().UtcDateTime;
    var hash = RefreshTokenFactory.Hash(presentedToken);

    await using var transaction = await _db.Database
        .BeginTransactionAsync(cancellationToken);

    var current = await _db.RefreshTokens
        .SingleOrDefaultAsync(x => x.TokenHash == hash, cancellationToken)
        ?? throw new SecurityTokenException("Invalid refresh token.");

    if (current.UsedAtUtc is not null)
    {
        await RevokeFamilyAsync(current.FamilyId, now, cancellationToken);
        await transaction.CommitAsync(cancellationToken);
        throw new SecurityTokenException("Refresh token reuse detected.");
    }

    if (!current.IsActive(now) || current.DeviceId != deviceId)
        throw new SecurityTokenException("Invalid refresh token.");

    var user = await _users.GetRequiredAsync(
        current.UserId, cancellationToken);

    current.UsedAtUtc = now;
    var replacement = CreateReplacement(current, now, out var plainText);
    current.ReplacedByTokenId = replacement.Id;
    _db.RefreshTokens.Add(replacement);

    await _db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);

    return new TokenPair(
        _accessTokens.Create(user.Id, user.DisplayName, user.Roles),
        plainText);
}
💡
این کد flow را نشان می‌دهد، نه strategy عمومی locking. با توجه به Database از optimistic concurrency، row lock یا isolation مناسب استفاده کنید. دو Request هم‌زمان نباید هر دو یک Token را با موفقیت rotate کنند.

Reuse Detection چگونه کار می‌کند؟

فرض کنید Client معتبر R1 را مصرف کرده و R2 گرفته است. اگر بعداً R1 دوباره ارائه شود، یا Request تکراری رخ داده یا R1 قبلاً سرقت شده است. Server نمی‌تواند تشخیص دهد کدام طرف مهاجم است؛ پس کل Token Family را Revocation می‌کند و Login مجدد می‌خواهد.

Reuse Detection
R1 --used--> R2 --used--> R3
 |
 +-- presented again => revoke R1, R2, R3 and require Login

رویداد Reuse Detection باید بدون ثبت خود Token، با UserId، FamilyId، DeviceId، زمان و Correlation Id در Security Audit ثبت شود.

Logout و Revocation

  • Logout یک Device: تمام Refresh Tokenهای فعال همان Device یا Family را revoke کنید.
  • Logout همه‌جا: تمام Familyهای User را revoke کنید و در صورت نیاز Security Stamp را تغییر دهید.
  • Password change یا incident: تمام Sessionها را invalidate کنید.
  • Access Token فعال: تا پایان عمر کوتاهش معتبر می‌ماند، مگر denylist یا introspection اضافه شود.

denylist برای هر Request دوباره State و lookup ایجاد می‌کند. معمولاً Access Token کوتاه‌عمر به‌همراه Revocation فوری Refresh Token تعادل بهتری است. برای عملیات بسیار حساس می‌توان علاوه بر آن Security Stamp یا Session Version را سمت Server بررسی کرد.

انتقال امن Refresh Token

Mobile یا native client باید از secure storage سیستم‌عامل استفاده کند. در Browser، معماری BFF یا Cookie با HttpOnly، Secure و SameSite مناسب معمولاً exposure به JavaScript را کاهش می‌دهد. اگر Cookie credential را خودکار ارسال می‌کند، محافظت CSRF نیز لازم است.

Secure refresh cookie
Response.Cookies.Append("refresh_token", plainTextRefreshToken,
    new CookieOptions
    {
        HttpOnly = true,
        Secure = true,
        SameSite = SameSiteMode.Strict,
        Path = "/api/auth/refresh",
        Expires = DateTimeOffset.UtcNow.AddDays(30)
    });

انتخاب SameSite به معماری واقعی و cross-site flow بستگی دارد. Cookie scope را تا Endpoint refresh محدود کنید و برای سناریوهای cross-site از anti-forgery strategy صریح استفاده کنید.

خطاهای رایج

  • ذخیرهٔ plain text Refresh Token در Database.
  • قابل‌استفاده نگه داشتن Token قبلی بعد از Rotation.
  • Rotation خارج از Transaction و صدور چند replacement در رقابت.
  • Refresh Token بدون Expiration، Device binding یا امکان Revocation.
  • فرستادن پاسخ متفاوت برای Token ناشناخته و Token مربوط به User مشخص.
  • Log کردن Token کامل در application log، proxy یا telemetry.
