Security Best Practices and Production Readiness

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۷
⏱️ زمان مطالعه: ۲۵ دقیقه
👤 تیم فنی

یک نمونه ممکن است روی سیستم توسعه کار کند ولی هنوز برای Production امن نباشد. Production Readiness یعنی Keyها قابل‌چرخش باشند، Token سطح حملهٔ کوچکی داشته باشد، Browser Storage آگاهانه انتخاب شود و failureها با آزمون و observability کنترل شوند.

Signing Key را داخل Repository قرار ندهید

در Development از Secret Manager استفاده کنید. این ابزار Secret را از project tree و Git بیرون نگه می‌دارد، اما storage رمزنگاری‌شدهٔ قابل‌اعتماد نیست. در Production از یک secret store کنترل‌شده مانند Azure Key Vault و ترجیحاً Managed Identity استفاده کنید.

Development secret
dotnet user-secrets init
dotnet user-secrets set "Jwt:SigningKey" "<high-entropy-development-key>"
⚠️
Secret Manager برای Development است. Secret را در appsettings.json، Docker image، source code، screenshot یا CI log قرار ندهید. دسترسی به Key Vault نیز باید با least privilege و audit همراه باشد.

HMAC یا RSA/ECDSA؟

روشمدل Keyمزیتریسک و کاربرد
HMACیک Secret مشترک برای sign و validateساده و سریعهر API دارای Secret می‌تواند Token هم بسازد؛ مناسب trust boundary کوچک
RSA / ECDSAPrivate Key برای sign و Public Key برای validateAPIها بدون قدرت صدور Token validation می‌کنندمدیریت certificate و rotation پیچیده‌تر؛ مناسب چند سرویس

در معماری Microservices معمولاً asymmetric signing boundary بهتری می‌سازد: Identity Service از Private Key محافظت می‌کند و APIها فقط Public Key را دریافت می‌کنند. Algorithm پذیرفته‌شده را محدود کنید و هرگز بر اساس مقدار alg ارسالی مهاجم validation را شل نکنید.

Expiration و ClockSkew

Access Token را کوتاه‌عمر نگه دارید؛ عدد دقیق تابع ریسک و تجربهٔ کاربری است و معمولاً چند دقیقه است، نه چند روز. ClockSkew تحمل اختلاف ساعت Serverهاست و نباید ناخواسته عمر Token را طولانی کند. همهٔ nodeها باید time synchronization معتبر داشته باشند.

Strict lifetime validation
options.TokenValidationParameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidateAudience = true,
    ValidateIssuerSigningKey = true,
    ValidateLifetime = true,
    RequireExpirationTime = true,
    ClockSkew = TimeSpan.FromSeconds(30),
    ValidAlgorithms = [SecurityAlgorithms.RsaSha256]
};

اگر زیرساخت ساعت دقیق دارد، مقدار کم یا حتی TimeSpan.Zero قابل‌بررسی است. تصمیم را با مشاهدهٔ clock drift واقعی بگیرید و failure نزدیک مرز Expiration را Integration Test کنید.

Key Rotation با kid

Header می‌تواند kid یا Key ID داشته باشد. هنگام Rotation، Issuer با Key جدید Token صادر می‌کند ولی Public Key قبلی را تا پایان عمر آخرین Token قدیمی برای validation نگه می‌دارد.

Safe Rotation Timeline
T0: publish public keys K1 and K2
T1: start signing new tokens with K2 (kid=K2)
T2: validate both K1 and K2 during overlap
T3: after every K1 token expires, remove K1

حذف فوری K1 تمام Requestهای دارای Token معتبر قدیمی را می‌شکند. overlap باید حداقل برابر بیشینهٔ عمر Token به‌اضافهٔ ClockSkew و زمان انتشار configuration باشد.

Token در Browser: XSS و CSRF

محلویژگیتهدید اصلی
localStorageJavaScript می‌تواند Token را بخواندXSS می‌تواند Token را سرقت کند
HttpOnly CookieJavaScript Token را نمی‌خواند و Browser خودکار ارسال می‌کندCSRF باید کنترل شود
BFFToken اصلی روی Backend قابل‌اعتماد می‌ماندنیازمند Cookie security و CSRF protection

هیچ storageی به‌تنهایی همهٔ تهدیدها را حذف نمی‌کند. برای Web App حساس، الگوی Backend for Frontend یا secure HttpOnly cookie معمولاً Token را از JavaScript دور نگه می‌دارد. هم‌زمان CSP، output encoding، dependency hygiene و anti-forgery controls لازم‌اند.

Logging و Observability بدون افشای Token

  • Header کامل Authorization، Access Token و Refresh Token را redact کنید.
  • برای تحلیل failure از reason category مانند expired، invalid audience یا invalid signature استفاده کنید.
  • UserId، ClientId، CorrelationId و زمان را فقط مطابق privacy policy ثبت کنید.
  • افزایش ناگهانی 401، Refresh Reuse یا login failure را alert کنید.
  • Token را در URL و Query String قرار ندهید؛ URLها در log و browser history پخش می‌شوند.

WebApplicationFactory - assertion sketch
[Fact]
public async Task Protected_endpoint_rejects_expired_token()
{
    using var client = _factory.CreateClient();
    client.DefaultRequestHeaders.Authorization =
        new AuthenticationHeaderValue("Bearer", CreateExpiredToken());

    var response = await client.GetAsync("/api/orders/mine");

    Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
}

برای تست خود Authorization policy می‌توان AuthenticationHandler آزمایشی تزریق کرد؛ اما برای تست pipeline واقعی JWT باید Tokenهای معتبر و نامعتبر با Key مخصوص Test ساخته و validation واقعی اجرا شود.

چک‌لیست Production Readiness

  • HTTPS اجباری و HTTP redirect یا rejection در edge تنظیم شده است.
  • Issuer، Audience، Signature، Lifetime و Algorithm validation فعال است.
  • Keyها در Secret Manager فقط برای Development و در Key Vault برای Production نگهداری می‌شوند.
  • Key Rotation تمرین و rollback آن مستند شده است.
  • Access Token کوتاه‌عمر و Refresh Token دارای Rotation، Hash و Reuse Detection است.
  • هیچ دادهٔ حساس یا ناپایدار غیرضروری در Payload نیست.
  • Browser strategy در برابر XSS و CSRF بررسی شده است.
  • 401 و 403 درست تفکیک می‌شوند و logها Token را افشا نمی‌کنند.
  • Integration Test مسیرهای منفی و race condition را پوشش می‌دهد.
  • Incident response برای revoke کردن sessionها و key compromise وجود دارد.
✅
Best Practice اصلی این است که JWT را یک جزء از security architecture ببینید، نه کل آن. Identity Provider، validation دقیق، lifecycle Refresh Token، مدیریت Key، Browser security و آزمون‌ها باید با هم طراحی شوند.
