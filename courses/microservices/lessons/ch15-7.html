Grafana در Microservices

از Data Source تا Dashboard قابل‌اشتراک؛ Panel، Variable، Alerting و Provisioning به‌عنوان کد

۱. سه سؤال دربارهٔ یک صفحهٔ نمایش

مدیر عملیات هر صبح می‌خواهد در یک نگاه ببیند وضعیت کلی سرویس‌ها سالم است یا نه. توسعه‌دهنده می‌خواهد روند زمان پاسخ یک Endpoint خاص را در دو هفتهٔ گذشته مقایسه کند. تیم پشتیبانی می‌خواهد به‌محض عبور نرخ خطا از یک آستانه، پیامکی دریافت کند. Prometheus این داده را ذخیره می‌کند، اما نمایش، مقایسه و هشدار روی آن، کار یک لایهٔ دیگر است.

Grafana ابزاری متن‌باز برای نمایش، کاوش و هشداردهی روی داده‌های سری‌زمانی است. Grafana خودش داده تولید یا ذخیره نمی‌کند؛ به یک یا چند Data Source مثل Prometheus وصل می‌شود، پرس‌وجو را به آن می‌فرستد و نتیجه را در قالب نمودار، جدول یا عدد نمایش می‌دهد.

در زنجیرهٔ مانیتورینگ، Prometheus مسئول جمع‌آوری و ذخیرهٔ Metric است و Grafana مسئول نمایش و هشدار مبتنی بر همان داده؛ جای‌گزین Prometheus نیست و می‌تواند هم‌زمان به چند Backend دیگر مثل Loki برای Log یا Tempo برای Trace هم متصل شود.

۲. مفاهیم پایه: Data Source، Dashboard، Panel و Query

مفهوم معنی
Data Source اتصال پیکربندی‌شده به یک منبع داده، مثل یک سرور Prometheus با آدرس و احراز هویت مشخص
Dashboard مجموعه‌ای از Panelها که در کنار هم یک دید کامل از یک سرویس یا موضوع می‌سازند
Panel یک واحد نمایش، مثل یک نمودار خطی یا یک عدد تکی، که از یک یا چند Query تغذیه می‌شود
Query عبارتی به زبان همان Data Source، مثلاً PromQL، که Panel برای گرفتن داده اجرا می‌کند

هر Panel به‌طور مستقل Data Source و Query خودش را دارد؛ بنابراین یک Dashboard می‌تواند هم‌زمان از چند Data Source مختلف تغذیه شود. تغییر بازهٔ زمانی بالای Dashboard روی همهٔ Panelها اثر می‌گذارد، اما تنظیمات نمایش هر Panel جداگانه است.

۳. انواع رایج Panel

نوع Panel کاربرد مناسب
Time series روند یک یا چند مقدار در طول زمان، مثل نرخ درخواست یا مصرف حافظه
Stat یک عدد لحظه‌ای بزرگ، مثل تعداد کاربر فعال یا وضعیت آخرین Deploy
Gauge یک مقدار نسبت به آستانه‌های مشخص، مثل درصد اشغال دیسک
Table مقایسهٔ چند سری کنار هم به‌صورت سطر و ستون، مثل زمان پاسخ به‌ازای هر Endpoint
Heatmap توزیع مقدارها در طول زمان، مناسب برای نمایش Bucketهای Histogram

انتخاب نوع Panel به شکل داده بستگی دارد، نه فقط سلیقه: یک Histogram معمولاً در Heatmap یا با محاسبهٔ صدک در Time series بهتر دیده می‌شود، در حالی‌که یک Counter تجمیع‌نشده در Stat گمراه‌کننده است و باید پیش از نمایش با rate() تبدیل شود.

۴. Provisioning: تعریف Data Source و Dashboard به‌عنوان کد

ساخت Data Source و Dashboard از طریق رابط وب سریع است، اما با هر بازسازی Container از بین می‌رود. Provisioning یعنی تعریف همین تنظیمات در فایل‌های YAML و JSON که Grafana هنگام بالا آمدن آن‌ها را می‌خواند؛ به این ترتیب تنظیمات در Git نگه‌داری و در محیط‌های مختلف تکرارپذیر می‌شود.

provisioning/datasources/prometheus.yml
apiVersion: 1

datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true

مقدار url به آدرس سرویس Prometheus در همان شبکه اشاره می‌کند، نه به localhost؛ در Docker Compose این آدرس معمولاً نام سرویس در همان فایل Compose است. access: proxy یعنی درخواست از سمت سرور Grafana به Data Source ارسال می‌شود، نه مستقیماً از مرورگر کاربر.

۵. نمونهٔ اجرایی: Prometheus، Grafana و سرویس .NET با Docker Compose

این نمونه سرویس Order از درس Prometheus را با Prometheus و Grafana در یک شبکه اجرا می‌کند. ساختار پوشه:

.
├── docker-compose.yml
├── prometheus.yml
└── grafana/
    └── provisioning/
        └── datasources/
            └── prometheus.yml
docker-compose.yml 
services:
  order-service:
    build: ./order-service
    ports:
      - "15201:8080"

  prometheus:
    image: prom/prometheus:v2.55.1
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
    ports:
      - "9090:9090"

  grafana:
    image: grafana/grafana:11.2.0
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning
    ports:
      - "3000:3000"
    depends_on:
      - prometheus

در prometheus.yml مربوط به این Compose، آدرس Target باید نام سرویس order-service باشد، نه localhost:

prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'order-service'
    static_configs:
      - targets: ['order-service:8080']
docker compose up -d

پس از بالا آمدن، آدرس http://localhost:3000 را باز کنید. کاربر و رمز پیش‌فرض admin/admin است و در اولین ورود تغییر رمز درخواست می‌شود. Data Source با نام Prometheus باید از قبل، بدون نیاز به تنظیم دستی، در فهرست Data Sourceها دیده شود.

۶. ساخت اولین Dashboard

در بخش Dashboards گزینهٔ New و سپس New Dashboard را انتخاب کنید، یک Panel اضافه کنید و در بخش Query این عبارت را بنویسید:

rate(shop_orders_completed_total[1m])

نوع Panel را روی Time series نگه دارید و روی Apply بزنید. برای دیدن تغییر در نمودار، چند درخواست به سرویس order-service بفرستید و چند ثانیه صبر کنید تا Prometheus مقدار جدید را Scrape کند.

1..5 | ForEach-Object {
    Invoke-RestMethod -Method Post "http://localhost:15201/orders/$_"
}

یک Panel دوم با نوع Stat و عبارت زیر برای مشاهدهٔ اندازهٔ لحظه‌ای صف اضافه کنید:

shop_orders_queue_size

Dashboard را با نامی مثل Order Service Overview ذخیره کنید. ذخیره‌شدن از طریق رابط وب، تنظیمات را در پایگاه‌دادهٔ داخلی Grafana نگه می‌دارد؛ برای نگه‌داری آن به‌صورت فایل قابل‌بازبینی در Git، باید Dashboard را Export و به پوشهٔ Provisioning اضافه کرد.

۷. Variable: یک Dashboard برای چند نمونه از سرویس

Variable مقداری است که در بالای Dashboard قابل‌انتخاب است و می‌تواند داخل Queryها جایگزین شود؛ به این ترتیب یک Dashboard می‌تواند بدون تغییر، برای چند سرویس یا چند نمونه از یک سرویس استفاده شود. برای ساخت آن، در تنظیمات Dashboard بخش Variables را باز کنید و یک Variable با نام job از نوع Query تعریف کنید که مقدارش را از خود Prometheus می‌گیرد:

label_values(job)

سپس در Query هر Panel، مقدار ثابت job را با متغیر جایگزین کنید:

rate(shop_orders_completed_total{job="$job"}[1m])

اکنون یک منوی کشویی در بالای Dashboard ظاهر می‌شود که کاربر می‌تواند سرویس موردنظر را انتخاب کند، بدون نیاز به ساخت یک Dashboard جداگانه برای هر سرویس.

۸. Alerting در Grafana

Grafana می‌تواند مستقل از Alertmanager خود Prometheus، قواعد هشدار تعریف کند. این قواعد روی هر Panel یا به‌صورت متمرکز در بخش Alerting قابل تعریف‌اند و بر پایهٔ همان Query کار می‌کنند؛ اگر نتیجهٔ Query از آستانهٔ مشخصی عبور کند، هشدار فعال می‌شود.

بخش قاعده معنی
Query همان عبارت PromQL که مقدار مورد بررسی را برمی‌گرداند
Condition شرطی مثل IS ABOVE 10 که روی نتیجهٔ Query اعمال می‌شود
Evaluation interval فاصلهٔ زمانی بررسی مجدد شرط
For مدتی که شرط باید پیوسته برقرار بماند تا هشدار از Pending به Firing برسد
Contact point مقصد اعلان، مثل ایمیل، Slack یا Webhook

فیلد For برای جلوگیری از هشدارهای زودگذر مهم است؛ بدون آن، یک جهش لحظه‌ای در ترافیک می‌تواند هشدار کاذب ایجاد کند. تعریف Contact point و مسیر اعلان جدا از تعریف خود قاعده انجام می‌شود؛ به این ترتیب می‌توان چند قاعده را به یک مقصد مشترک وصل کرد بدون تکرار تنظیمات.

۹. سازمان‌دهی و کنترل دسترسی

  • Dashboardهای مرتبط را در یک Folder قرار دهید؛ دسترسی و اشتراک‌گذاری در سطح Folder ساده‌تر از تک‌تک Dashboardهاست.
  • به‌جای کپی‌کردن یک Dashboard برای هر سرویس، از Variable برای پارامتری‌کردن آن استفاده کنید.
  • Dashboardهای پرکاربرد را Export و در Provisioning نگه دارید تا با تغییر Container از بین نروند.
  • Panelهای زیاد با Refresh کوتاه روی یک صفحه، فشار پرس‌وجوی زیادی به Data Source وارد می‌کند؛ بازهٔ Refresh را متناسب با نیاز واقعی تنظیم کنید.

Grafana خودش دادهٔ Metric را تغییر یا حذف نمی‌کند؛ حذف یک Panel یا Dashboard فقط نمایش را از بین می‌برد، نه Time Seriesهای ذخیره‌شده در Prometheus.

۱۰. عیب‌یابی و تمرین

مشکل بررسی اول
Data Source وضعیت خطا نشان می‌دهد درستی url در تنظیمات Data Source و دسترسی شبکهٔ Container به Prometheus
Panel داده‌ای نشان نمی‌دهد درستی نام Metric و Label در Query، و بازهٔ زمانی انتخاب‌شدهٔ Dashboard
Variable مقداری نشان نمی‌دهد درستی عبارت label_values و اینکه Metric مربوط حداقل یک بار Scrape شده باشد
هشدار فعال نمی‌شود بررسی Condition، مقدار For و اینکه Evaluation در حال اجراست
Dashboard پس از بازسازی Container ناپدید شده ذخیره‌نشدن آن در Provisioning و تکیه بر پایگاه‌دادهٔ داخلی موقت

تمرین اول: یک Panel از نوع Table بسازید که هم‌زمان نرخ تکمیل سفارش و اندازهٔ صف را در دو ستون کنار هم نشان دهد و نتیجه را با دیدن همان دو مقدار در دو Panel جدا مقایسه کنید.

تمرین دوم: یک قاعدهٔ هشدار برای زمانی تعریف کنید که shop_orders_queue_size برای مدت یک دقیقه بیشتر از ۵۰ بماند و با ارسال درخواست‌های پیاپی، رفتار Pending و Firing را مشاهده کنید.

پرسش مرور: اگر Prometheus برای چند دقیقه از دسترس خارج شود، آیا Panelهای Grafana دادهٔ آن بازه را از جایی دیگر می‌گیرند؟ خیر؛ Grafana فقط نمایش‌دهندهٔ همان چیزی است که Data Source برمی‌گرداند و خودش داده‌ای ذخیره نمی‌کند، پس آن بازه در نمودار خالی یا ناپیوسته دیده می‌شود.
