آشنایی با Garbage Collector و چرخهٔ عمر اشیا

۱. وظیفهٔ Garbage Collector چیست؟

در محیط اجرای دات‌نت (CLR)، حافظهٔ بیشتر اشیای مرجع در Managed Heap اختصاص داده می‌شود. Garbage Collector یا GC زمانی که اشیا دیگر قابل‌دسترسی نباشند، حافظهٔ آن‌ها را در یکی از دوره‌های جمع‌آوری بازیابی می‌کند.

یک شیء موقت از PaymentC#
public sealed class Payment
{
    public decimal Amount { get; set; }
}

static void ProcessPayment()
{
    var payment = new Payment { Amount = 500 };
    Console.WriteLine(payment.Amount);
}

۲. غیرقابل‌دسترسی یعنی چه؟

جمع‌آوری به پایان متد وابسته نیست؛ GC از ریشه‌هایی مانند متغیرهای زندهٔ استک، فیلدهای استاتیک و GC Handle مسیر دسترسی به اشیا را بررسی می‌کند. شیئی که هیچ مسیر دسترسی از ریشه‌ها به آن نباشد، واجد شرایط جمع‌آوری است. زمان دقیق این جمع‌آوری قطعی نیست.

Object allocated→Reachable from GC Roots→Unreachable→Reclaimed in later GC
نکتهٔ مهم مصاحبهمتغیر محلی لزوماً تا انتهای متد زنده نمی‌ماند؛ JIT می‌تواند عمر مؤثر یک ارجاع را کوتاه‌تر تشخیص دهد. بنابراین صرف وجود نام متغیر در متن متد، تضمین زنده‌بودن شیء تا آخر متد نیست.

سؤال مرور

اگر متد ProcessPayment تمام شود، آیا حافظهٔ payment فوراً آزاد می‌شود؟

نمایش پاسخ تشریحی
خیر. وقتی شیء دیگر قابل‌دسترسی نباشد، نامزد جمع‌آوری می‌شود؛ اما زمان جمع‌آوری را Runtime تعیین می‌کند.

نسل‌های حافظه: Gen 0، Gen 1 و Gen 2

۱. چرا GC نسلی است؟

بیشتر اشیای برنامه عمر کوتاهی دارند؛ برای همین GC، اشیای کوچک را در نسل‌های مختلف مدیریت می‌کند تا برای آزادسازی اشیای کوتاه‌عمر مجبور نباشد همیشه تمام حافظه را بررسی کند.

Gen 0اشیای جدید و کوتاه‌عمر
بقای شیء در جمع‌آوری
Gen 1مرحلهٔ میانی
بقای مجدد در جمع‌آوری
Gen 2اشیای بادوام
نسلویژگیزمان جمع‌آوری
Gen 0اشیای تازه و معمولاً کوتاه‌عمرمعمولاً پرتکرارتر
Gen 1اشیای باقی‌مانده از نسل صفرکمتر از نسل صفر
Gen 2اشیای بادوام؛ همچنین جمع‌آوری LOHعموماً پرهزینه‌تر
مثال ارجاع زندهC#
var cache = new List<Payment>();
cache.Add(new Payment { Amount = 100 });

// While cache is reachable and holds its item,
// the Payment object is also reachable.

وقتی شیء در جمع‌آوری نسل صفر زنده بماند، معمولاً به نسل یک ارتقا پیدا می‌کند؛ با باقی‌ماندن در جمع‌آوری نسل یک، به نسل دو می‌رود. بقای شیء در نسل دو به معنی ارتقای بیشتر نیست. این ارتقا لزوماً به معنی جابه‌جایی فیزیکی نیست.

تفاوت مهمجمع‌آوری نسل دو، نسل‌های کوچک‌تر را هم پوشش می‌دهد؛ اما جمع‌آوری فقط نسل صفر، به معنی بررسی کامل نسل‌های یک و دو نیست.

سؤال مرور

شیئی که بعد از جمع‌آوری Gen 0 هنوز قابل‌دسترسی است، معمولاً چه سرنوشتی دارد؟

نمایش پاسخ تشریحی
حافظهٔ آن بازیابی نمی‌شود و شیء به Gen 1 ارتقا پیدا می‌کند.

تفاوت منابع Managed و Unmanaged

۱. حافظهٔ تحت مدیریت چیست؟

حافظهٔ یک شیء مانند Payment توسط GC مدیریت می‌شود. با این حال یک شیء تحت مدیریت می‌تواند مالک منبعی خارج از Managed Heap باشد.

۲. منبع Unmanaged چیست؟

منابعی مثل File Handle، Socket Handle و حافظهٔ Native به آزادسازی مخصوص خودشان نیاز دارند. نمونهٔ شناخته‌شده، شیء FileStream است که یک شیء مدیریت‌شده بوده، اما دسترسی به فایل را با منابع سیستم‌عامل انجام می‌دهد.

نمونهٔ مدیریت نادرست فایلC#
var stream = new FileStream(
    "payment.txt", FileMode.Open, FileAccess.Read);

// Read file ...
// No Dispose here!
مفهوممدیریت‌شده با GC؟نیاز به آزادسازی مشخص؟
شیء سادهٔ Paymentبلهمعمولاً خیر
خود شیء FileStreamحافظهٔ شیء: بلهبله؛ منابع فایل را آزاد کنید
هندل سیستم‌عاملخیر، به شکل مستقیمبله؛ معمولاً توسط Wrapper
اصلاح یک برداشت رایجGC مستقیماً متد Dispose را اجرا نمی‌کند. ممکن است آزادسازی منابع زیرساختی بعدها از راه Finalizer یا SafeHandle انجام شود؛ اما زمان آن قابل‌اتکا نیست.

سؤال مرور

چرا نباید برای آزادسازی File Handle منتظر GC ماند؟

نمایش پاسخ تشریحی
زیرا زمان جمع‌آوری نامشخص است؛ در این فاصله هندل‌ها اشغال می‌مانند و بسته به حالت اشتراک فایل، سایر عملیات ممکن است با مشکل مواجه شوند.

رابط IDisposable و متد Dispose

۱. قرارداد IDisposable

تعریف رابطC#
public interface IDisposable
{
    void Dispose();
}

پیاده‌سازی این رابط به مصرف‌کنندهٔ کلاس اعلام می‌کند که پس از پایان استفاده باید منابع تحت مالکیت شیء را آزاد کند. روش آزادسازی و اینکه کلاس مالک کدام منبع است، بخشی از طراحی آن کلاس محسوب می‌شود.

مثال سادهٔ کلاس مالک FileStreamC#
public sealed class PaymentFileReader : IDisposable
{
    private readonly FileStream _stream;

    public PaymentFileReader(string path)
    {
        _stream = File.OpenRead(path);
    }

    public void Dispose() => _stream.Dispose();
}
فراخوانی آزادسازی توسط مصرف‌کنندهC#
var reader = new PaymentFileReader("payment.txt");
try
{
    // Use reader...
}
finally
{
    reader.Dispose();
}
نکتهٔ مصاحبهحتی اگر کلاس IDisposable را پیاده کند، صرف غیرقابل‌دسترسی‌شدن آن باعث فراخوانی خودکار Dispose() نمی‌شود. آزادسازی باید توسط مصرف‌کننده، using یا مالک طول‌عمر شیء انجام شود.

سؤال مرور

آیا GC.Collect() تضمین می‌کند متد Dispose شیء غیرقابل‌دسترسی فراخوانی شود؟

نمایش پاسخ تشریحی
خیر؛ GC با Dispose قرارداد فراخوانی مستقیم ندارد.

دستور using و تضمین آزادسازی منابع

۱. مشکل Dispose دستی

کد آسیب‌پذیر در برابر ExceptionC#
var stream = File.OpenRead("payment.txt");
ProcessFile(stream); // May throw
stream.Dispose();     // May never execute

وقتی عملیات پردازش خطا بدهد، مسیر عادی اجرا قطع می‌شود و احتمال دارد به فراخوانی دستی Dispose() نرسیم.

۲. راه‌حل using

استفادهٔ صحیح از usingC#
using (var stream = File.OpenRead("payment.txt"))
{
    ProcessFile(stream);
} // stream.Dispose()

کامپایلر ساختاری معادل try/finally ایجاد می‌کند. خروج از بلوک، حتی بر اثر استثنا، باعث فراخوانی Dispose می‌شود. در این مثال آزادسازی پس از ساخت موفق منبع تضمین می‌شود.

نمای مفهومی کد تولیدشدهC#
var stream = File.OpenRead("payment.txt");
try
{
    ProcessFile(stream);
}
finally
{
    stream.Dispose();
}
سناریوی خروج در اثر خطاC#
public sealed class TestResource : IDisposable
{
    public void Dispose() => Console.WriteLine("Disposed");
}

try
{
    using (var resource = new TestResource())
    {
        Console.WriteLine("Start");
        throw new Exception("Error");
    }
}
catch (Exception)
{
    Console.WriteLine("Exception");
}
// Start
// Disposed
// Exception
حد تضمیندستور using خطای رخ‌داده را نمی‌بلعد. ضمن اینکه در صورت متوقف‌شدن اجباری فرایند یا شکست ساخت خود منبع، آزادسازی از مسیر معمول using لزوماً رخ نمی‌دهد.

سؤال مرور

در مثال بالا، چرا Disposed قبل از Exception چاپ می‌شود؟

نمایش پاسخ تشریحی
چون پیش از انتقال کنترل به catch، خروج از using و اجرای بلوک finally داخلی آن انجام می‌شود.

تفاوت using (...) و using var

۱. زمان پایان عمر منبع

روش بلوکیC#
using (var resource = new TestResource())
{
    Console.WriteLine("A");
}
Console.WriteLine("B");
// A, Disposed, B
روش تعریفی از C# 8C#
static void Test()
{
    using var resource = new TestResource();
    Console.WriteLine("A");
    Console.WriteLine("B");
}
// A, B, Disposed

در روش بلوکی، منبع در پایان بلوک مشخص‌شده آزاد می‌شود. در روش using var، منبع هنگام خروج از محدودهٔ تعریف متغیر آزاد می‌شود؛ در مثال دوم پایان متد.

۲. ترتیب آزادسازی چند منبع

آزادسازی به‌ترتیب معکوسC#
using var first = new TestResource();
using var second = new TestResource();
Console.WriteLine("Work");
// Work
// Disposed (second)
// Disposed (first)
به‌خاطر بسپارمنابع معمولاً به‌ترتیب معکوس ساخته‌شدن آزاد می‌شوند. اگر منبعی باید زودتر بسته شود، از بلوک using داخلی استفاده کن.

سؤال مرور

اگر بعد از بسته‌شدن بلوک using (resource2) هنوز متد ادامه داشته باشد، کدام منبع زودتر آزاد می‌شود: resource2 یا منبعی که با using var resource1 در ابتدای متد ساخته شده؟

نمایش پاسخ تشریحی
ابتدا resource2 در پایان بلوک خودش آزاد می‌شود؛ سپس resource1 در پایان محدودهٔ تعریفش.

درس ۷ · در حال یادگیری

آزادسازی غیرهم‌زمان با IAsyncDisposable و await using

۱. چرا آزادسازی غیرهم‌زمان؟

برخی منابع برای پایان کار باید عملیات I/O غیرهم‌زمان انجام دهند؛ مانند ثبت نهایی یا تخلیهٔ بافر. رابط IAsyncDisposable یک متد DisposeAsync() برمی‌گرداند که می‌توان تکمیل آن را await کرد.

قرارداد آزادسازی غیرهم‌زمانC#
public interface IAsyncDisposable
{
    ValueTask DisposeAsync();
}
کلاس نمونهٔ مالک جریان فایلC#
public sealed class AsyncPaymentWriter : IAsyncDisposable
{
    private readonly FileStream _stream = new(
        "payments.log", FileMode.Append, FileAccess.Write,
        FileShare.Read, 4096, useAsync: true);

    public async Task WriteAsync(byte[] data)
    {
        await _stream.WriteAsync(data);
    }

    public ValueTask DisposeAsync() => _stream.DisposeAsync();
}
مصرف منبع با await usingC#
public static async Task SaveAsync(byte[] data)
{
    await using var writer = new AsyncPaymentWriter();
    await writer.WriteAsync(data);
} // DisposeAsync is awaited here
نوعفراخوانیکاربرد
IDisposableusing → Dispose()آزادسازی هم‌زمان
IAsyncDisposableawait using → DisposeAsync()آزادسازی غیرهم‌زمان
دام مصاحبهاگر کلاس فقط IAsyncDisposable را پیاده‌سازی کند، using var x = ... برای آن کامپایل نمی‌شود. باید در محدودهٔ async از await using استفاده کرد. پیاده‌سازی هم‌زمان هر دو رابط هم مجاز است.

سؤال مرور

آیا using var writer = new AsyncPaymentWriter(); کامپایل می‌شود؟

نمایش پاسخ تشریحی
خیر. این کلاس فقط IAsyncDisposable دارد و باید بنویسیم await using var writer = new AsyncPaymentWriter(); در یک متد async.

شناخت Finalizer و تفاوت آن با Dispose

۱. Finalizer دقیقاً چیست؟

متدی که در زبان #C با نحو ~TypeName() تعریف می‌شود، مکانیزم نهایی‌سازی را فراهم می‌کند. برای انواع واجد شرایط نهایی‌سازی، زمان اجرای آن قطعی نیست و ممکن است پیش از خاتمهٔ فرایند اصلاً اجرا نشود.

شکل کلی FinalizerC#
public class NativeResource
{
    // Conceptual example only; real native handles
    // should normally be wrapped in SafeHandle.
    ~NativeResource()
    {
        // Release directly owned unmanaged resource.
        // Do not call arbitrary managed dependencies here.
    }
}
ویژگیDisposeFinalizer
زمان اجرابا فراخوانی مصرف‌کننده یا مالکنامعین؛ از مسیر نهایی‌سازی
نحوهٔ اجراهم‌زمان با مسیر برنامه یا DisposeAsyncتوسط Runtime در فرایند نهایی‌سازی
هدفآزادسازی به‌موقع منابعپشتیبان منابع Native مستقیم در شرایط خاص
اجراشدن خودکار Dispose؟خیرخیر

۲. نقش SafeHandle و SuppressFinalize

در کد واقعی بهتر است هندل‌های سیستم‌عامل را با SafeHandle مدیریت کنیم؛ این کار در بیشتر موارد نیاز به نوشتن Finalizer اختصاصی را از بین می‌برد. بعد از آزادسازی قطعی، GC.SuppressFinalize(this) می‌تواند اجرای Finalizer آن شیء را در صورت وجود، حذف کند.

الگوی رایج متد DisposeC#
public void Dispose()
{
    Dispose(disposing: true);
    GC.SuppressFinalize(this);
}
هشداراز Finalizer برای دسترسی به اشیای مدیریت‌شدهٔ دیگر، ثبت لاگ معمولی یا صدا زدن سرویس شبکه‌ای استفاده نکن. ترتیب نهایی‌سازی اشیا قابل‌اتکا نیست و وجود Finalizer هزینهٔ جمع‌آوری دارد.

سؤال مرور

اگر کلاس فقط یک FileStream را نگهداری کند، آیا نوشتن Finalizer اختصاصی لازم است؟

نمایش پاسخ تشریحی
خیر. کلاس باید منبعی را که مالک آن است در Dispose آزاد کند؛ FileStream و SafeHandle زیرساخت لازم برای هندل را دارند.

الگوی استاندارد Dispose Pattern

۱. یک کلاس sealed با مالکیت مشخص

اگر کلاسی فقط منابع IDisposable تحت مالکیت خودش را نگهداری می‌کند و ارث‌بری ندارد، معمولاً یک پیاده‌سازی ساده، کافی و خواناست.

مثال ساده برای .NET جدیدC#
public sealed class PaymentFileReader : IDisposable
{
    private readonly FileStream _stream;
    private bool _disposed;

    public PaymentFileReader(string path)
        => _stream = File.OpenRead(path);

    public int ReadByte()
    {
        ObjectDisposedException.ThrowIf(_disposed, this);
        return _stream.ReadByte();
    }

    public void Dispose()
    {
        if (_disposed) return;
        _stream.Dispose();
        _disposed = true;
    }
}

در این نمونه، Dispose دوباره قابل‌فراخوانی است؛ پس از آزادسازی استفادهٔ مجدد از شیء با ObjectDisposedException رد می‌شود. این نمونه فرض می‌کند Dispose هم‌زمان از چند ترد اجرا نمی‌شود.

۲. وقتی کلاس قابل ارث‌بری است

الگوی قابل‌گسترش IDisposableC#
public class DisposableBase : IDisposable
{
    private Stream? _ownedStream;
    private bool _disposed;

    public DisposableBase(Stream ownedStream)
        => _ownedStream = ownedStream;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            _ownedStream?.Dispose();
            _ownedStream = null;
        }

        // Directly owned unmanaged resources, if any,
        // would be released here on both paths.
        _disposed = true;
    }
}

پارامتر disposing مشخص می‌کند فراخوانی از مسیر Dispose() است یا از مسیر نهایی‌سازی. در شاخهٔ disposing: false نباید به اشیای مدیریت‌شدهٔ دیگر تکیه کنیم. این کلاس به Finalizer نیازی ندارد، چون خودش منبع Native خام را مالک نیست.

۳. اصل مالکیت

اگر یک Stream را از بیرون دریافت می‌کنی، قبل از اینکه در Dispose آن را ببندی باید روشن باشد مالک آن هستی یا نه. گاهی API با گزینه‌ای مانند leaveOpen تعیین می‌کند که Stream ورودی پس از پایان کار باز بماند.

توجه به نسخهٔ زبان و چارچوبنمونهٔ اول از ObjectDisposedException.ThrowIf استفاده می‌کند که در نسخه‌های جدید دات‌نت در دسترس است. در پروژه‌های قدیمی‌تر می‌توان به‌جای آن if (_disposed) throw new ObjectDisposedException(nameof(PaymentFileReader)); نوشت.

سؤال مرور

آیا هر کلاسی که IDisposable دارد باید Finalizer هم داشته باشد؟

نمایش پاسخ تشریحی
خیر. Finalizer معمولاً فقط برای مالکیت مستقیم منابع Unmanaged بدون Wrapper امن مطرح می‌شود؛ در بیشتر برنامه‌ها SafeHandle یا Dispose منابع مدیریت‌شده کافی است.

درس ۱۰ · مبحث تکمیلی

نشت حافظه و روش تشخیص آن در .NET

۱. آیا در زبان دارای GC هم Memory Leak داریم؟

بله. وقتی دیگر به داده‌ای نیاز نداریم اما هنوز از یک ریشهٔ حافظه مسیر دسترسی به آن وجود دارد، GC نمی‌تواند آن را جمع‌آوری کند. به این وضعیت معمولاً نشت منطقی یا Managed Memory Leak می‌گوییم.

نمونهٔ فهرست استاتیک بدون محدودیتC#
public static class PaymentCache
{
    public static readonly List<byte[]> Items = new();
}

// Simulate a leak: references grow without bound.
void OnEachRequest()
{
    PaymentCache.Items.Add(new byte[100_000]);
}

در این مثال مشکل این نیست که GC ضعیف کار می‌کند؛ مشکل این است که فهرست استاتیک همچنان به تمام آرایه‌ها ارجاع دارد.

۲. سایر علت‌های رایج

  • رویدادهایی که Subscriber طول‌عمر کوتاه را نزد Publisher طول‌عمر بلند نگه می‌دارند.
  • کش بدون محدودیت، دیکشنری با کلیدهای قدیمی و بافرهای بزرگ انباشته‌شده.
  • تایمرها، تسک‌ها و اشتراک‌هایی که در پایان عمرشان متوقف یا آزاد نشده‌اند.
  • منابع Native که Dispose نشده‌اند؛ ممکن است خارج از Managed Heap مصرف حافظه یا هندل ایجاد کنند.
رفع نگهداری ناخواسته با لغو اشتراکC#
// Illustrative event subscription pattern:
source.Changed += OnChanged;

// When the subscription is no longer required:
source.Changed -= OnChanged;

۳. تشخیص با ابزارهای دات‌نت

دستورهای خط فرمانCLI
dotnet tool install --global dotnet-counters
dotnet-counters monitor -p 1234 --counters System.Runtime

# For deeper investigation (can trigger a full GC):
dotnet tool install --global dotnet-gcdump
dotnet-gcdump collect -p 1234 -o payment.gcdump

برای تشخیص، روند Allocation Rate، رشد اشیای زنده و شمار جمع‌آوری‌های نسل دو را بررسی کن. سپس با Heap Dump به دنبال GC Root نگهدارندهٔ اشیا بگرد. صرف زیادبودن حافظهٔ فرایند یا افزایش Working Set به‌تنهایی ثابت نمی‌کند نشت داریم.

احتیاط در Productionجمع‌آوری dotnet-gcdump ممکن است یک Full GC ایجاد کند. پیش از اجرا روی سرویس پرترافیک، اثر آن بر تأخیر و وضعیت عملیاتی را بسنج.

سؤال مرور

اگر بعد از ده هزار درخواست، یک static List ده هزار آبجکت قدیمی را نگه داشته باشد، چرا GC آن‌ها را آزاد نمی‌کند؟

نمایش پاسخ تشریحی
چون از فیلد استاتیک به آن‌ها مسیر ارجاع وجود دارد؛ باید سیاست انقضا، سقف اندازه یا حذف صریح داده‌ها طراحی شود.

درس ۱۱ · مبحث تکمیلی

کارایی GC، دستور GC.Collect و حافظهٔ LOH

۱. چرا GC.Collect معمولاً توصیه نمی‌شود؟

دات‌نت بر اساس فشار حافظه و الگوی تخصیص، زمان مناسب جمع‌آوری را تخمین می‌زند. فراخوانی دستی GC.Collect() ممکن است جمع‌آوری پرهزینه را زودتر از موعد آغاز کند، باعث توقف تردهای مدیریت‌شده شود و کارایی را کاهش دهد.

دو عملیات با مسئولیت متفاوتC#
// Usually avoid in application request paths:
GC.Collect();

// This is not a replacement for:
stream.Dispose();

۲. مفهوم Large Object Heap

اشیایی که اندازهٔ تخصیص آن‌ها به آستانهٔ LOH برسد، معمولاً در Large Object Heap قرار می‌گیرند. آستانهٔ پیش‌فرض حدود 85,000 bytes برای اندازهٔ خود شیء است، نه شمار عناصر آرایه. این آستانه قابل پیکربندی است.

نمونهٔ تخصیص بزرگC#
byte[] buffer = new byte[100_000];
// This allocation normally belongs to LOH.

// LOH is collected with Gen 2 collections.

به‌طور معمول LOH مانند ناحیهٔ اشیای کوچک به‌دفعات فشرده نمی‌شود؛ فشرده‌سازی آن را می‌توان برای شرایط ویژه درخواست کرد. تخصیص پرتکرار بافرهای بزرگ باعث فشار حافظه و جمع‌آوری‌های پرهزینه‌تر می‌شود.

۳. استفادهٔ محتاطانه از ArrayPool

الگوی بازگرداندن بافر اجاره‌ایC#
using System.Buffers;

byte[] buffer = ArrayPool<byte>.Shared.Rent(100_000);
try
{
    // Use only the needed portion of buffer.
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
}

استفاده از ArrayPool می‌تواند تخصیص‌های بزرگ مکرر را کم کند، ولی آرایهٔ اجاره‌ای ممکن است از اندازهٔ خواسته‌شده بزرگ‌تر باشد و نباید بعد از بازگرداندن آن را استفاده کرد.

جمع‌بندی اجراییابتدا مصرف حافظه را اندازه بگیر، سپس الگوی تخصیص را اصلاح کن. افزایش غیرعادی Gen 2 GC، بافرهای بزرگ موقت، یا نگهداری بی‌مورد اشیا، سرنخ‌هایی برای بررسی‌اند؛ پاسخ پیش‌فرض، صدا زدن GC.Collect() نیست.

سؤال مرور

آیا آرایهٔ new byte[100_000] معمولاً در Gen 0 ساخته می‌شود؟

نمایش پاسخ تشریحی
خیر. با آستانهٔ پیش‌فرض، معمولاً در LOH قرار می‌گیرد که همراه با جمع‌آوری نسل دو بررسی می‌شود.

سناریوهای واقعی و پرسش‌های مصاحبهٔ Senior

۱. سناریوی اتصال دیتابیس در سرویس پرداخت

آزادسازی منابع دیتابیس در عملیات asyncC#
using Microsoft.Data.SqlClient;

public static async Task<int> ReadCountAsync(
    string connectionString, CancellationToken token)
{
    await using var connection = new SqlConnection(connectionString);
    await connection.OpenAsync(token);

    await using var command = new SqlCommand(
        "SELECT COUNT(*) FROM dbo.Payments", connection);

    return Convert.ToInt32(await command.ExecuteScalarAsync(token));
}

در این مثال اتصال و فرمان تحت مالکیت همین متد هستند و بعد از کار آزاد می‌شوند. با فعال‌بودن Connection Pooling، بستن یا Dispose کردن اتصال معمولاً اتصال فیزیکی را برای استفادهٔ مجدد به استخر برمی‌گرداند، نه اینکه حتماً شبکه را قطع کند.

۲. سناریوی تزریق وابستگی

در سرویس‌های ASP.NET Core، طول عمر اشیایی که توسط DI Container ساخته می‌شوند معمولاً توسط همان ظرف مدیریت می‌شود. برای نمونه DbContext تزریق‌شدهٔ Scoped را در میانهٔ درخواست بی‌دلیل دستی Dispose نکن؛ پایان Scope وظیفهٔ ظرف است.

نمونهٔ مالکیت توسط DIC#
public sealed class PaymentService
{
    private readonly AppDbContext _db;

    public PaymentService(AppDbContext db) => _db = db;

    public Task<int> CountAsync(CancellationToken token)
        => _db.Payments.CountAsync(token);

    // Do not dispose injected _db here.
}

۳. سناریوی پردازش فایل

آزادسازی جریان‌ها هنگام موفقیت یا ExceptionC#
public async Task CopyAsync(
    string sourcePath, string destinationPath,
    CancellationToken token)
{
    await using var source = File.OpenRead(sourcePath);
    await using var destination = File.Create(destinationPath);
    await source.CopyToAsync(destination, token);
}
نکتهٔ مهمدر این مثال پایان کار، منابع را آزاد می‌کند اما تضمین نمی‌کند در صورت لغو یا خطای نیمه‌راه، فایل مقصد حتماً محتوای کامل داشته باشد. برای عملیات حساس باید نوشتن موقت، اعتبارسنجی و جابه‌جایی اتمیک در شرایط مناسب طراحی شود.
