درس 01

مفهوم Deferred Execution

تعریف ساده

در دات‌نت، Deferred Execution به این معنی است که ساختن یک زنجیرهٔ عملیات الزاماً آن را اجرا نمی‌کند. برای نمونه، Where روی یک IEnumerable<T> مجموعه‌ای قابل پیمایش می‌سازد و شرط معمولاً زمانی بررسی می‌شود که آن مجموعه را پیمایش کنیم.

نمونه کد / خروجیCSHARP
var numbers = new List<int> { 1, 2, 3, 4, 5 };
var result = numbers.Where(x => x > 3); // ساخت Query، نه پیمایش

foreach (var number in result)
    Console.WriteLine(number);
// 4
// 5

مرحلهٔ اول تعریف پرس‌وجو و مرحلهٔ دوم مصرف نتیجه است. در مثال بالا foreach باعث شروع اجرای شرط می‌شود.

Immediate Execution چه تفاوتی دارد؟

نمونه کد / خروجیCSHARP
var deferred = numbers.Where(x => x > 3);
var immediate = numbers.Where(x => x > 3).ToList();

متد ToList() زنجیره را همان لحظه پیمایش و نتیجه را در یک لیست ذخیره می‌کند. متدهایی مانند Count()، First() و Any() هم عملیات را اجرا می‌کنند، اما الزاماً کل نتیجه را در لیست ذخیره نمی‌کنند.

خلاصه: Deferred بودن، دربارهٔ زمان اجرای عملیات است؛ نه لزوماً سریع‌تر بودن آن.

پرسش مرور: در numbers.Where(x => x > 3)، آیا همان لحظه تمام اعداد بررسی می‌شوند؟ پاسخ: خیر، نه در زنجیرهٔ معمول LINQ to Objects.

درس 02

تفاوت IEnumerable و IQueryable

فیلتر در حافظه یا دیتابیس؟

وقتی منبع context.Users از نوع IQueryable<User> است، EF Core می‌تواند عبارت Where را به SQL ترجمه کند.

نمونه کد / خروجیCSHARP
// Query در دیتابیس فیلتر می‌شود.
var users = await context.Users
    .Where(x => x.IsActive)
    .ToListAsync();

دستور تولیدشده معمولاً مشابه زیر است:

نمونه کد / خروجیSQL
SELECT ... FROM Users WHERE IsActive = 1;

اما اگر پیش از Where به AsEnumerable() برویم، عملگرهای بعدی LINQ to Objects خواهند بود:

نمونه کد / خروجیCSHARP
var users = context.Users
    .AsEnumerable()             // هنوز اجرا نمی‌کند
    .Where(x => x.IsActive)     // فیلتر سمت برنامه
    .ToList();                 // آغاز خواندن و پیمایش

در مثال یک میلیون کاربر با تنها ۱۰۰ کاربر فعال، مسیر دوم ممکن است یک میلیون رکورد را از دیتابیس منتقل و شرط را در برنامه ارزیابی کند؛ مسیر اول فقط رکوردهای منطبق را برمی‌گرداند.

هشدار: AsEnumerable() خودش داده را بارگذاری نمی‌کند؛ فقط تعیین می‌کند عملگرهای بعدی کجا اجرا شوند. IQueryable نیز تضمین نمی‌کند هر عبارت دلخواهی قابل ترجمه به SQL باشد.

پرسش مرور: اگر Where بعد از AsEnumerable() باشد، فیلتر کجا انجام می‌شود؟ پاسخ: در برنامه.

درس 03

اجرای مجدد Query در EF Core

یک متغیر، دو پرس‌وجو

IQueryable<T> نتیجهٔ ذخیره‌شده نیست؛ توصیف پرس‌وجویی است که می‌توان آن را چند بار اجرا کرد.

نمونه کد / خروجیCSHARP
var users = context.Users.Where(x => x.IsActive);

var count = users.Count(); // Query شمارهٔ ۱
var list = users.ToList(); // Query شمارهٔ ۲

اجرای اول معمولاً SELECT COUNT(*) و اجرای دوم یک SELECT برای دریافت سطرها می‌فرستد. شمارش اول نتیجهٔ Query را کش نمی‌کند.

نمونه کد / خروجیSQL
SELECT COUNT(*) FROM Users WHERE IsActive = 1;
-- سپس:
SELECT ... FROM Users WHERE IsActive = 1;

اگر بین دو اجرا دادهٔ دیتابیس تغییر کند، حتی ممکن است عدد count با تعداد list متفاوت شود. بنابراین نباید تصور کنیم چند بار مصرف یک IQueryable حتماً یک Snapshot یکسان می‌دهد.

پرسش مرور: آیا دوبار پیمایش یک IQueryable می‌تواند دوبار به دیتابیس مراجعه کند؟ پاسخ: بله.

درس 04

تفاوت Count و ToList

برای شمارش، رکوردها را بارگذاری نکنیم

نمونه کد / خروجیCSHARP
// روش بهینه‌تر برای شمارش
var count = await context.Users
    .Where(x => x.IsActive)
    .CountAsync();

در این روش دیتابیس عدد شمارش را حساب می‌کند و معمولاً فقط یک عدد به برنامه برمی‌گرداند.

نمونه کد / خروجیCSHARP
// روش پرهزینه‌تر
var count = (await context.Users
    .Where(x => x.IsActive)
    .ToListAsync()).Count;

در روش دوم تمام موجودیت‌های منطبق منتقل و در حافظه ساخته می‌شوند تا بعد اندازهٔ لیست محاسبه شود. پس CountAsync() و ToListAsync() هر دو باعث اجرای Query هستند، ولی نوع نتیجه و مقدار دادهٔ انتقالی فرق دارد.

نکته: دیتابیس برای شمارش ممکن است تعداد زیادی سطر یا ورودی ایندکس را بررسی کند؛ اما آن سطرها لزوماً به برنامه فرستاده نمی‌شوند.

پرسش مرور: اگر فقط تعداد کاربران را لازم داشته باشیم، کدام روش بهتر است؟ پاسخ: معمولاً CountAsync() روی IQueryable.

درس 05

تفاوت Any و Count

برای بررسی وجود رکورد

اگر فقط می‌خواهیم بدانیم آیا حداقل یک کاربر با ایمیل مشخص وجود دارد، AnyAsync() معمولاً انتخاب مناسب‌تری است.

نمونه کد / خروجیCSHARP
bool exists = await context.Users
    .AnyAsync(x => x.Email == email);

به‌جای آن می‌توان نوشت:

نمونه کد / خروجیCSHARP
bool exists = await context.Users
    .CountAsync(x => x.Email == email) > 0;

هر دو درست هستند، اما Any معمولاً با دستورهایی از جنس EXISTS یا معادل آن اجرا می‌شود و می‌تواند پس از یافتن نخستین تطبیق کار را تمام کند؛ Count باید تعداد همهٔ موارد منطبق را به‌دست آورد.

نمونه کد / خروجیSQL
SELECT CASE WHEN EXISTS (
    SELECT 1 FROM Users WHERE Email = @email
) THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END;

وجود ایندکس روی Email می‌تواند هر دو روش را سریع‌تر کند؛ تفاوت قطعی سرعت به نقشهٔ اجرای Query وابسته است.

پرسش مرور: آیا CountAsync() تمام موجودیت‌ها را به حافظهٔ برنامه می‌آورد؟ پاسخ: خیر؛ شمارش در دیتابیس محاسبه می‌شود.

درس 06

تغییر منبع قبل از پیمایش

Deferred Query یک تصویر ثابت نیست

نمونه کد / خروجیCSHARP
var numbers = new List<int> { 1, 2, 3, 4, 5 };
var result = numbers.Where(x => x > 3);

Console.WriteLine(result.Count()); // 2
numbers.Add(6);
Console.WriteLine(result.Count()); // 3

بار اول اعداد 4 و 5 منطبق‌اند. بار دوم، چون نتیجه ذخیره نشده، عدد 6 هم بررسی می‌شود.

ساخت یک نتیجهٔ مستقل

نمونه کد / خروجیCSHARP
var snapshot = numbers.Where(x => x > 3).ToList();
numbers.Add(7);
Console.WriteLine(snapshot.Count); // همچنان 3

ToList() یک لیست جدید از عضویت‌های آن لحظه می‌سازد. برای انواع ارجاعی، این کار کپی عمیقِ خود اشیا نیست؛ اگر ویژگی یک شیء مشترک تغییر کند، هر دو لیست همان شیء را می‌بینند.

پرسش مرور: آیا Count() اول در مثال، نتیجه را برای دفعات بعد ذخیره می‌کند؟ پاسخ: خیر.

درس 07

توقف زودهنگام با First

Short-Circuit Execution

بعضی عملگرها برای رسیدن به نتیجه به همهٔ عناصر احتیاج ندارند؛ First() به‌محض یافتن اولین مقدار مناسب متوقف می‌شود.

نمونه کد / خروجیCSHARP
var numbers = new[] { 1, 2, 3, 4, 5 };
var result = numbers.Where(x =>
{
    Console.WriteLine($"Checking: {x}");
    return x > 3;
});

var first = result.First();

خروجی:

نمونه کد / خروجیTEXT
Checking: 1
Checking: 2
Checking: 3
Checking: 4

عدد 5 بررسی نمی‌شود؛ چون عدد 4 اولین مورد منطبق بود. در مثال بالا، با اینکه Console.WriteLine قبل از return قرار دارد، فقط برای عناصری اجرا می‌شود که Query تا آن نقطه پیش رفته است.

پرسش مرور: اگر اولین عنصر منطبق همان عنصر اول باشد، شرط چند بار اجرا می‌شود؟ پاسخ: یک بار.

درس 08

تفاوت First مستقیم و بعد از ToList

جای ToList رفتار پیمایش را عوض می‌کند

نمونه کد / خروجیCSHARP
var numbers = new[] { 1, 2, 3, 4, 5 };

var result = numbers.Where(x =>
{
    Console.WriteLine($"Checking: {x}");
    return x > 3;
}).ToList();

var first = result.First();

با وجود اینکه فقط یک عدد می‌خواهیم، ToList() زنجیرهٔ قبلی را کامل مصرف می‌کند. پس Checking پنج بار چاپ می‌شود؛ result برابر [4, 5] و first برابر 4 است.

عبارت تعداد ارزیابی شرط در این مثال
numbers.Where(...).First() ۴ بار
numbers.Where(...).ToList().First() ۵ بار

برای دریافت یک رکورد از دیتابیس نیز معمولاً بهتر است FirstOrDefaultAsync() را مستقیماً روی IQueryable اجرا کنیم، نه اینکه تمام نتایج را نخست به لیست تبدیل کنیم.

پرسش مرور: کدام روش پیش از انتخاب اولین عنصر همهٔ داده‌ها را مادی‌سازی می‌کند؟ پاسخ: حالت دارای ToList().

درس 09

Streaming و Non-Streaming در LINQ

Deferred همیشه یعنی «یکی‌یکی خروجی دادن» نیست

متد Where از نوع پردازش تدریجی است: برای تولید نتیجهٔ اول، معمولاً تنها تا همان نقطه از ورودی جلو می‌رود. اما OrderBy برای ترتیب‌دهی باید تمام عناصر ورودی را دریافت و مقایسه کند؛ بااین‌حال هنوز تا زمان پیمایش، اجرا را به تأخیر می‌اندازد.

نمونه کد / خروجیCSHARP
var numbers = new[] { 5, 1, 4, 2, 3 };
var result = numbers
    .Where(x =>
    {
        Console.WriteLine($"Checking: {x}");
        return x > 2;
    })
    .OrderBy(x => x)
    .Take(1)
    .ToList();

خروجی Checking برای تمام ۵ عدد چاپ می‌شود. Where ابتدا اعداد [5, 4, 3] را به مرحلهٔ مرتب‌سازی می‌دهد؛ سپس OrderBy آن‌ها را مرتب می‌کند و Take(1) عدد 3 را تحویل می‌گیرد.

جمع‌بندی: Where معمولاً Streaming است. OrderBy یک عملگر Deferred اما با نیاز به بافرکردن ورودی است.

پرسش مرور: آیا حضور Take(1) بعد از OrderBy لزوماً خواندن همهٔ ورودی را منتفی می‌کند؟ پاسخ: خیر.

درس 10

ترتیب Where و OrderBy

تغییر ترتیب عملگرها، تغییر کارکرد

نمونه کد / خروجیCSHARP
var numbers = new[] { 5, 1, 4, 2, 3 };
var result = numbers
    .OrderBy(x => x)
    .Where(x =>
    {
        Console.WriteLine($"Checking: {x}");
        return x > 2;
    })
    .Take(1)
    .ToList();

این بار OrderBy ابتدا تمام داده‌ها را برای مرتب‌سازی مصرف می‌کند و دنبالهٔ مرتب [1, 2, 3, 4, 5] را می‌سازد. Where فقط اعداد 1، 2 و 3 را بررسی می‌کند. بنابراین Checking سه بار و نتیجه [3] است.

زنجیره تعداد اجرای شرط در این مثال نتیجه
Where → OrderBy → Take(1) ۵ [3]
OrderBy → Where → Take(1) ۳ [3]

این جدول صرفاً رفتار همین نمونهٔ LINQ to Objects را نشان می‌دهد. هنگام کار با EF Core، بهینه‌ساز دیتابیس می‌تواند نقشهٔ اجرایی متفاوتی انتخاب کند.

پرسش مرور: آیا OrderBy در هر دو حالت تمام پنج عدد را مصرف می‌کند؟ پاسخ: بله.

درس 11

ساخت Iterator با yield return

تولید مقدارها در زمان درخواست

در دات‌نت می‌توان با yield return متدی نوشت که به‌جای بازگرداندن همهٔ نتایج، هر بار یک مقدار تولید کند.

نمونه کد / خروجیCSHARP
IEnumerable<int> GetNumbers()
{
    Console.WriteLine("A");
    yield return 10;

    Console.WriteLine("B");
    yield return 20;
}

var numbers = GetNumbers();
Console.WriteLine("C");

foreach (var number in numbers)
    Console.WriteLine(number);

خروجی:

نمونه کد / خروجیTEXT
C
A
10
B
20

فراخوانی GetNumbers() یک دنبالهٔ قابل پیمایش به‌وجود می‌آورد. نخستین درخواست عنصر، بدنه را تا اولین yield return اجرا می‌کند. درخواست عنصر بعدی، اجرا را از همان نقطه ادامه می‌دهد.

پرسش مرور: آیا yield return مثل return معمولی اجرای متد را برای همیشه تمام می‌کند؟ پاسخ: خیر.

درس 12

اجرای دوبارهٔ Iterator

هر پیمایش مستقل است

نمونه کد / خروجیCSHARP
IEnumerable<int> GetNumbers()
{
    Console.WriteLine("Start");
    yield return 10;
    yield return 20;
}

var numbers = GetNumbers();

foreach (var number in numbers)
    Console.WriteLine(number);

foreach (var number in numbers)
    Console.WriteLine(number);

در این مثال Start دو بار چاپ می‌شود. دلیل: دو بار پیمایش جدید روی Iterator آغاز کرده‌ایم؛ شیء نتیجه، حافظهٔ پنهانی برای کش‌کردن 10 و 20 ندارد.

توقف زودهنگام

نمونه کد / خروجیCSHARP
var first = GetNumbers().Take(1).ToList();

این قطعه فقط اولین عنصر را درخواست می‌کند. اگر پس از yield return 10 دستور دیگری وجود داشته باشد، در این پیمایش الزاماً اجرا نمی‌شود.

پرسش مرور: آیا نگهداری نتیجه در متغیر IEnumerable<int> باعث جلوگیری از اجرای دوباره می‌شود؟ پاسخ: خیر.

درس 13

کاربرد yield return در پردازش فایل پرداخت

خواندن تراکنش‌های موفق به‌صورت تدریجی

فرض کنیم فایلی با یک میلیون تراکنش داریم و فقط ده تراکنش موفق نخست را نیاز داریم.

نمونه کد / خروجیCSHARP
IEnumerable<string> GetSuccessfulPayments(string path)
{
    foreach (var line in File.ReadLines(path))
    {
        if (line.Contains(",Success,"))
            yield return line;
    }
}

var payments = GetSuccessfulPayments("payments.csv")
    .Take(10)
    .ToList();

ReadLines خطوط را تدریجی در دسترس می‌گذارد و Iterator فقط موارد موفق را تحویل می‌دهد. Take(10) پس از دهمین تراکنش موفق، درخواست عنصر بعدی را متوقف می‌کند.

اگر دهمین تراکنش موفق در خط ۵۰۰ باشد، نیازی نیست برنامه همهٔ یک میلیون خط را از نظر منطقی بررسی کند.

نکتهٔ فنی: خواندن تدریجی به معنی یک خواندن فیزیکیِ دیسک برای هر خط نیست؛ سیستم فایل می‌تواند بافر داشته باشد.

پرسش مرور: در این سناریو، اگر دهمین موفق در خط ۵۰۰ باشد، چند خط لازم است بررسی شود؟ پاسخ: تا همان خط ۵۰۰.

درس 14

تفاوت File.ReadLines و File.ReadAllLines

دو شیوهٔ خواندن فایل

نمونه کد / خروجیCSHARP
// تمام خطوط ابتدا وارد حافظه می‌شوند.
var a = File.ReadAllLines("payments.csv")
    .Where(x => x.Contains("Success"))
    .Take(10)
    .ToList();
نمونه کد / خروجیCSHARP
// خواندن تدریجی، با امکان توقف زودهنگام.
var b = File.ReadLines("payments.csv")
    .Where(x => x.Contains("Success"))
    .Take(10)
    .ToList();
ویژگی ReadAllLines() ReadLines()
زمان دریافت خطوط پیش از بازگشت متد هنگام پیمایش
مصرف حافظه برای فایل بزرگ زیاد معمولاً بسیار کمتر
توقف پس از ده مورد فایل قبلاً خوانده شده می‌تواند خواندن باقی را متوقف کند

برای فایل چند گیگابایتی، روش دوم در بسیاری از سناریوهای گزارش‌گیری به‌صرفه‌تر است؛ با این شرط که عملیات بعدی مانند OrderBy ناخواسته تمام داده‌ها را بافر نکند.

پرسش مرور: آیا ReadAllLines با وجود Take(10) فقط ده خط اول فایل را می‌خواند؟ پاسخ: خیر.

درس 15

خطر Multiple Enumeration

دوبار مصرف، دوبار تولید

نمونه کد / خروجیCSHARP
IEnumerable<string> GetPayments()
{
    Console.WriteLine("Reading payments...");
    yield return "Payment1";
    yield return "Payment2";
    yield return "Payment3";
}

var payments = GetPayments();

if (payments.Any())
{
    foreach (var payment in payments)
        Console.WriteLine(payment);
}

متن Reading payments... دو بار چاپ می‌شود: نخست Any() پیمایش را شروع می‌کند و بعد foreach یک پیمایش تازه آغاز می‌کند.

در سناریوی ساده فقط چند عدد تولید می‌شود؛ ولی اگر این دنباله یک Query دیتابیس، درخواست شبکه یا پردازش سنگین باشد، هزینهٔ اجرای تکراری جدی خواهد شد.

نکته: Any() صرفاً مصرف یک دنباله است و نتایج دیگر آن را برای foreach ذخیره نمی‌کند.

پرسش مرور: آیا فقط چون نام متغیر payments یکسان است، نتیجه خودبه‌خود کش می‌شود؟ پاسخ: خیر.

درس 16

جلوگیری از Multiple Enumeration

یک بار اجرا، چند بار استفاده

نمونه کد / خروجیCSHARP
var payments = GetPayments().ToList();

Console.WriteLine(payments.Count);

foreach (var payment in payments)
    Console.WriteLine(payment);

foreach (var payment in payments)
    Console.WriteLine(payment);

متد GetPayments() فقط یک بار پیمایش می‌شود. دو foreach بعدی روی لیست ساخته‌شده در حافظه حرکت می‌کنند.

اما آیا همیشه ToList خوب است؟

خیر. اگر مجموعه میلیون‌ها رکورد دارد و فقط یک بار مصرف می‌شود، ToList() ممکن است مصرف حافظه را بی‌دلیل افزایش دهد. راهکار به هدف بستگی دارد:

  • اگر چند بار داده‌های محدود لازم‌اند، مادی‌سازی یک‌باره منطقی است.
  • اگر داده‌ها بسیار بزرگ و فقط یک بار مصرف می‌شوند، پیمایش تدریجی را حفظ کنیم.
  • اگر تنها هدف بررسی وجود است، ممکن است اصلاً نیازی به دوبار پیمایش نباشد.

پرسش مرور: در کد بالا چند بار متن Reading payments... چاپ می‌شود؟ پاسخ: یک بار.

درس 17

Deferred Execution و DbContext آزادشده

ساختن Query داخل using کافی نیست

نمونه کد / خروجیCSHARP
IQueryable<User> users;
using (var context = new AppDbContext())
{
    users = context.Users.Where(x => x.IsActive);
}

var result = users.ToList(); // ObjectDisposedException

متد Where فقط Query را توصیف کرده است؛ در زمان اجرای ToList()، DbContext از قبل Dispose شده و دیگر قابل استفاده نیست.

روش صحیح

نمونه کد / خروجیCSHARP
List<User> users;
using (var context = new AppDbContext())

درس 18

تغییر مقدار متغیر در Query

Closure و زمان ارزیابی

نمونه کد / خروجیCSHARP
var numbers = new List<int> { 10, 20, 30, 40, 50 };
int minValue = 20;

var result = numbers.Where(x => x > minValue);
minValue = 40;

foreach (var number in result)
    Console.WriteLine(number);

خروجی فقط 50 است. عبارت لامبدا متغیر minValue را Capture کرده است، نه اینکه الزاماً مقدار ۲۰ را همان لحظه تثبیت کند. هنگام پیمایش، مقدار فعلی یعنی ۴۰ استفاده می‌شود.

اگر می‌خواهیم شرط با مقدار زمان ساخت Query ثابت بماند، یک متغیر محلی مستقل برای همان مقدار بسازیم و دیگر آن را تغییر ندهیم:

نمونه کد / خروجیCSHARP
int minValue = 20;
int capturedThreshold = minValue;
var result = numbers.Where(x => x > capturedThreshold);
minValue = 40; // نتیجه دیگر به minValue وابسته نیست

توجه: در گفت‌وگوی آموزشی، سؤال این درس را رد کردیم و مستقیماً به درس بعد رفتیم؛ پاسخ تشریحی اینجا برای کامل‌بودن جزوه اضافه شده است.

پرسش مرور: در مثال نخست چه عددی چاپ می‌شود؟ پاسخ: ۵۰.

درس 19

آشنایی با IAsyncEnumerable و await foreach

Async Streaming

با IAsyncEnumerable<T> می‌توان عناصر را در چند مرحله و به‌شکل غیرهم‌زمان تولید کرد؛ مصرف‌کننده با await foreach هر عنصر آماده‌شده را دریافت می‌کند.

نمونه کد / خروجیCSHARP
async IAsyncEnumerable<int> GetNumbersAsync()
{
    Console.WriteLine("Start");
    await Task.Delay(1000);
    yield return 10;

    await Task.Delay(1000);
    yield return 20;

    await Task.Delay(1000);
    yield return 30;
}

var numbers = GetNumbersAsync();
Console.WriteLine("Before");

await foreach (var number in numbers)
    Console.WriteLine(number);

ابتدا Before چاپ می‌شود، سپس بدنه با شروع await foreach وارد اجرا می‌شود و اعداد تقریباً با فاصلهٔ یک ثانیه می‌رسند.

Task<List<T>> معمولاً پس از آماده‌شدن کل لیست نتیجه می‌دهد، اما IAsyncEnumerable<T> اجازه می‌دهد مصرف‌کننده پیش از تکمیل تولید همهٔ عناصر کار خود را آغاز کند.

پرسش مرور: آیا صدا زدن GetNumbersAsync() بدون پیمایش، Start را چاپ می‌کند؟ پاسخ: خیر.

درس 20

لغو پیمایش با CancellationToken

لغو در مرزهای await

نمونه کد / خروجیCSHARP
using System.Runtime.CompilerServices;

async IAsyncEnumerable<int> GetNumbersAsync(
    [EnumeratorCancellation] CancellationToken token)
{
    yield return 10;
    await Task.Delay(1000, token);
    yield return 20;
}

using var cts = new CancellationTokenSource();

try
{
    await foreach (var number in GetNumbersAsync(cts.Token))
    {
        Console.WriteLine(number);
        cts.Cancel();
    }
}
catch (OperationCanceledException)
{
    Console.WriteLine("Canceled");
}

خروجی:

نمونه کد / خروجیTEXT
10
Canceled

فراخوانی Cancel() یک درخواست لغو ثبت می‌کند، نه اینکه هر دستور دلخواه را فوراً متوقف کند. در این مثال Task.Delay توکن را بررسی می‌کند و با OperationCanceledException متوقف می‌شود.

لغو از سمت مصرف‌کننده

در طراحی Iteratorها می‌توان توکن مصرف‌کننده را با WithCancellation(token) منتقل کرد؛ استفاده از [EnumeratorCancellation] روی پارامتر مناسب کمک می‌کند توکن به Enumerator برسد.

پرسش مرور: آیا Cancel() بدون همکاری کد درحال‌اجرا همیشه عملیات را متوقف می‌کند؟ پاسخ: خیر.

درس 21

AsAsyncEnumerable در EF Core

پردازش تدریجی رکوردهای دیتابیس

نمونه کد / خروجیCSHARP
// Materialization: دریافت نتیجه در یک List
var users = await context.Users
    .Where(x => x.IsActive)
    .ToListAsync();
نمونه کد / خروجیCSHARP
// Streaming: پردازش هنگام دریافت
var users = context.Users
    .Where(x => x.IsActive)
    .AsAsyncEnumerable();

await foreach (var user in users)
    Console.WriteLine(user.Name);

در حالت دوم، ابتدا لازم نیست همهٔ نتایج در یک List<User> ساخته شوند. برای صادرات گزارش‌های بزرگ، این روش می‌تواند مصرف حافظه را کاهش دهد.

اما چند شرط مهم وجود دارد: اجرای Query و خواندن نتایج، معمولاً اتصال و DbContext را تا پایان پیمایش درگیر نگه می‌دارد؛ بعضی Providerها یا امکانات EF Core ممکن است داخلی بافر کنند؛ و یک DbContext برای چند عملیات هم‌زمان مستقل طراحی نشده است.

نکته: AsAsyncEnumerable() به خودی خود نتایج را اجرا یا بارگذاری نمی‌کند؛ پیمایش await foreach اجرای واقعی را آغاز می‌کند.

پرسش مرور: برای صادرکردن یک میلیون رکورد به فایل، کدام روش معمولاً حافظهٔ کمتری می‌خواهد؟ پاسخ: پردازش تدریجی با AsAsyncEnumerable().

درس 22

مرز فیلتر سمت دیتابیس و سمت برنامه

جای فیلتر بسیار مهم است

نمونه کد / خروجیCSHARP
// فیلتر SQL؛ معمولاً فقط رکوردهای فعال برمی‌گردند.
var stream = context.Users
    .Where(x => x.IsActive)
    .AsAsyncEnumerable();

await foreach (var user in stream)
    Console.WriteLine(user.Name);

اما پس از AsAsyncEnumerable() وارد دنیای IAsyncEnumerable<T> می‌شویم. اگر در مصرف‌کننده فیلتر کنیم، فیلتر در برنامه اجرا می‌شود:

نمونه کد / خروجیCSHARP
var stream = context.Users.AsAsyncEnumerable();

await foreach (var user in stream)
{
    if (!user.IsActive) continue; // فیلتر سمت برنامه
    Console.WriteLine(user.Name);
}

در این نمونه، احتمالاً تمام یک میلیون رکورد به برنامه انتقال داده می‌شوند؛ حتی اگر فقط صد رکورد فعال باشند. اگر از عملگرهای Async LINQ نظیر Where بعد از AsAsyncEnumerable() استفاده کنیم نیز همین مرز اجرا را داریم؛ دسترسی به این Extensionها به نسخهٔ دات‌نت و بسته‌های استفاده‌شده بستگی دارد.

پرسش مرور: فیلتر کاربران فعال را برای کارایی بهتر در کدام سمت AsAsyncEnumerable می‌گذاریم؟ پاسخ: قبل از آن، روی IQueryable.

درس 23

AsNoTracking و اجرای به‌تعویق‌افتاده

غیرفعال‌کردن Tracking به‌معنی اجرای Query نیست

نمونه کد / خروجیCSHARP
var query = context.Users
    .AsNoTracking()
    .Where(x => x.IsActive); // هنوز اجرا نشده است

var users = await query.ToListAsync(); // اجرای Query

AsNoTracking() می‌گوید EF Core موجودیت‌های نتیجه را برای شناسایی تغییرات در ChangeTracker ثبت نکند. این تصمیم دربارهٔ ردیابی موجودیت‌ها است، نه دربارهٔ زمان اجرای Query.

نمونه کد / خروجیCSHARP
var query = context.Users.AsNoTracking();
var count = await query.CountAsync();  // SQL شماره ۱
var list  = await query.ToListAsync(); // SQL شماره ۲

در این مثال دو دستور SQL جدا ارسال می‌شود؛ AsNoTracking کش نتایج نیست. ضمن اینکه برای Projection صرفاً اسکالر، گاهی اصلاً موجودیت قابل ردیابی ایجاد نمی‌شود.

پرسش مرور: آیا AsNoTracking() مانع Multiple Enumeration می‌شود؟ پاسخ: خیر.

درس 24

تفاوت AsTracking و AsNoTracking

خواندن برای ویرایش یا فقط نمایش؟

نمونه کد / خروجیCSHARP
var user = await context.Users
    .FirstAsync(x => x.Id == 10);

user.Name = "Ali";
await context.SaveChangesAsync();

اگر Query در حالت Tracking باشد، EF Core تغییر روی موجودیت ردیابی‌شده را هنگام SaveChangesAsync() تشخیص می‌دهد.

نمونه کد / خروجیCSHARP
var user = await context.Users
    .AsNoTracking()
    .FirstAsync(x => x.Id == 10);

user.Name = "Ali";
await context.SaveChangesAsync(); // این تغییر خودکار ذخیره نمی‌شود

در گزارش‌گیری از تراکنش‌های زیاد که قصد ویرایش نداریم، AsNoTracking() معمولاً مصرف حافظه و سربار پردازشی کمتری دارد. برای به‌روزرسانی همان موجودیت‌ها در یک Unit of Work، Tracking معمولاً ساده‌تر است.

نکته: این دو حالت مستقیماً تعریف Deferred Execution را عوض نمی‌کنند؛ هر دو Query همچنان در زمان عملیات پایانی اجرا می‌شوند.

پرسش مرور: برای گزارش فقط‌خواندنیِ ۱۰۰ هزار تراکنش کدام انتخاب معمولاً بهتر است؟ پاسخ: AsNoTracking().

درس 26

Pagination با Skip و Take

ترتیب اجرا روی دیتابیس

فرض کنیم صفحهٔ دوم گزارش تراکنش‌ها را با اندازهٔ ۲۰ رکورد می‌خواهیم.

نمونه کد / خروجیCSHARP
// غیربهینه: ابتدا همه را بارگذاری می‌کند.
var all = await context.Transactions
    .AsNoTracking()
    .OrderBy(x => x.Id)
    .ToListAsync();

var page = all.Skip(20).Take(20).ToList();
نمونه کد / خروجیCSHARP
// بهتر: صفحه‌بندی روی IQueryable
var page = await context.Transactions
    .AsNoTracking()
    .OrderBy(x => x.Id)
    .Skip(20)
    .Take(20)
    .ToListAsync();

در SQL Server پرس‌وجو معمولاً از OFFSET و FETCH استفاده می‌کند:

نمونه کد / خروجیSQL
SELECT ... FROM Transactions
ORDER BY Id
OFFSET 20 ROWS FETCH NEXT 20 ROWS ONLY;

تنها ۲۰ رکورد برای این صفحه به برنامه منتقل می‌شوند، ولی به این معنی نیست که دیتابیس فقط ۲۰ رکورد را بررسی کرده است. برای صفحه‌های عمیق، ردکردن تعداد زیادی سطر ممکن است هزینه‌بر شود. مرتب‌سازی ثابت و ترجیحاً یکتا برای صفحه‌بندی قابل‌اعتماد ضروری است.

پرسش مرور: آیا Take(20) به معنی بررسی حداکثر ۲۰ رکورد در دیتابیس است؟ پاسخ: خیر.

درس 27 بخش تکمیلی · هنوز تمرین نشده

تفاوت Offset و Keyset Pagination

چرا Skip زیاد می‌تواند گران شود؟

در صفحه‌بندی Offset برای رفتن به صفحهٔ هزارم، دیتابیس ممکن است مجبور شود تعداد زیادی رکورد را به ترتیب پیمایش و کنار بگذارد. برای دنباله‌ای از صفحات که کاربر یکی‌یکی جلو می‌رود، Keyset Pagination اغلب بهتر است.

نمونه کد / خروجیCSHARP
// صفحه بعدی بر اساس آخرین Id مشاهده‌شده
long lastSeenId = 120050;

var nextPage = await context.Transactions
    .AsNoTracking()
    .Where(x => x.Id < lastSeenId)
    .OrderByDescending(x => x.Id)
    .Take(20)
    .Select(x => new { x.Id, x.Amount })
    .ToListAsync();

با وجود ایندکس مناسب روی Id، دیتابیس معمولاً می‌تواند به محدودهٔ لازم دسترسی پیدا کند، بدون آنکه Skip بزرگ انجام دهد.

محدودیت‌ها

  • این روش برای «صفحهٔ بعد/قبل» عالی است، ولی رفتن مستقیم به صفحهٔ ۲۰۰ بدون Cursor مناسب ساده نیست.
  • فیلد مرتب‌سازی باید ترتیب پایدار و ترجیحاً یکتا داشته باشد.
  • اگر مرتب‌سازی بر اساس CreatedAt است، برای رفع تساوی بهتر است Id هم در ترتیب و شرط Cursor وارد شود.
  • ایندکس و Query Plan همچنان تعیین‌کنندهٔ عملکردند.

مثال مصاحبه: در جدول بزرگ پرداخت، برای حرکت پیوسته بین صفحه‌ها، Keyset معمولاً در برابر Offsetهای عمیق مناسب‌تر است.

پرسش مرور: برای «رفتن مستقیم به صفحهٔ ۷۵ بدون Cursor» کدام مدل ساده‌تر است؟ پاسخ: Offset؛ هرچند ممکن است کندتر شود.

IQueryable و IEnumerable در Repository

آیا Repository باید IQueryable برگرداند؟

فرض کن API باید فقط تراکنش‌های موفق یک مشتری را با Pagination بگیرد. اگر Repository داده‌ها را زود ToList() کند، Service دیگر نمی‌تواند فیلتر را به SQL منتقل کند.

نمونه کد / خروجیCSHARP
// روش ضعیف برای این سناریو
public async Task<List<Transaction>> GetAllAsync()
    => await _context.Transactions.ToListAsync();

// Service بعداً در حافظه فیلتر می‌کند.
var result = (await repo.GetAllAsync())
    .Where(x => x.Status == PaymentStatus.Success)
    .Take(20);

دو راه طراحی

راه اول: بازگرداندن IQueryable؛ امکان ترکیب پرس‌وجو را فراهم می‌کند، ولی جزئیات Persistence و عمر DbContext را به لایهٔ فراخواننده نشت می‌دهد و تست یا کنترل Query را دشوارتر می‌کند.

راه دوم: مشخص‌کردن Query در قرارداد Repository؛ مرز معماری را روشن نگه می‌دارد و فیلتر را داخل Repository پیش از اجرای SQL انجام می‌دهد:

نمونه کد / خروجیCSHARP
public Task<List<TransactionSummaryDto>> GetSuccessfulPageAsync(
    long clientId, int skip, int take, CancellationToken ct)
{
    return _context.Transactions
        .AsNoTracking()
        .Where(x => x.ClientId == clientId &&
                    x.Status == PaymentStatus.Success)
        .OrderByDescending(x => x.Id)
        .Skip(skip).Take(take)
        .Select(x => new TransactionSummaryDto(x.Id, x.Amount))
        .ToListAsync(ct);
}

قاعدهٔ معماری: هیچ انتخاب واحدی برای همهٔ سیستم‌ها وجود ندارد. باید Composition Query، مرزبندی لایه‌ها، عمر Context و بهینه‌بودن SQL را آگاهانه متعادل کنیم.

پرسش مرور: چرا برگشت List<Transaction> از متد GetAllAsync برای گزارش بزرگ می‌تواند خطرناک باشد؟ پاسخ: فیلتر و صفحه‌بندی بعدی ممکن است در حافظه اجرا شود.

اشتباهات رایج Deferred Execution در پروژه واقعی

چک‌لیست عیب‌یابی

اشتباه پیامد راه‌حل
پیمایش چندبارهٔ IQueryable چند Query جدا به دیتابیس یک‌بار مادی‌سازی یا بازطراحی نیاز
AsEnumerable زودهنگام فیلتر و Skip/Take سمت برنامه نگه‌داشتن عملگرهای قابل ترجمه روی IQueryable
ToList قبل از Select انتقال ستون‌های غیرضروری Projection قبل از Materialization
بازگرداندن Query از Context آزادشده ObjectDisposedException اجرا در طول عمر Context
OrderBy روی جریان عظیم داده بافر و پردازش تمام ورودی محدودکردن داده پیش از مرتب‌سازی، در صورت امکان
استفاده از yield با منبع ناپایدار خطا در زمان پیمایش، نه ساخت Iterator مدیریت عمر منبع و استثنا در محل مصرف
تغییر مجموعه حین foreach احتمال InvalidOperationException برای List<T> جداکردن مرحلهٔ تغییر از پیمایش یا Snapshot

مثال: زمان واقعی خطا

نمونه کد / خروجیCSHARP
IEnumerable<int> GetValues()
{
    Console.WriteLine("Run");
    throw new InvalidOperationException("Failed");
#pragma warning disable CS0162
    yield return 1;
#pragma warning restore CS0162
}

var values = GetValues(); // استثنا هنوز رخ نداده است
foreach (var item in values) // استثنا هنگام پیمایش
    Console.WriteLine(item);

نمونه نشان می‌دهد زمان فراخوانی Iterator با زمان اجرای بدنهٔ آن یکی نیست. هنگام مشاهدهٔ خطا، خط Where یا متد سازندهٔ Iterator الزاماً محل شروع اجرای واقعی نیست.

توصیه در پروژهٔ پرداخت

برای Queryهای پرترافیک، با ToQueryString()، ثبت SQL و بررسی Query Plan، محل اجرای فیلتر، Pagination، دفعات فراخوانی و حجم نتایج را مشخص کنیم. تصمیم بر اساس اندازه‌گیری باشد، نه صرفاً نام متد.

پرسش مرور: آیا تعویض IQueryable با IEnumerable همیشه باعث انتقال فوری داده می‌شود؟ پاسخ: خیر؛ مرز اجرای عملگرها عوض می‌شود.

مرور نهایی و سؤالات مصاحبه Senior .NET

جمع‌بندی ۱۰ نکتهٔ کلیدی

  1. Deferred Execution یعنی اجرای عملیات تا زمان مصرف نتیجه به تعویق می‌افتد.

  2. Where و Select روی IEnumerable معمولاً هنگام پیمایش اجرا می‌شوند.

  3. ToList نتیجه را مادی‌سازی می‌کند؛ Count یا Any Query را اجرا می‌کنند اما لزوماً نتیجهٔ مجموعه را کش نمی‌کنند.

  4. IQueryable اجازهٔ ترجمهٔ پرس‌وجو به SQL را می‌دهد؛ AsEnumerable عملیات بعدی را سمت برنامه می‌آورد.

  5. پیمایش مجدد یک Query می‌تواند درخواست جدید دیتابیس بسازد.

  6. First، Take و Any اغلب زود متوقف می‌شوند، اما OrderBy برای مرتب‌کردن کل ورودی را نیاز دارد.

  7. yield return مقادیر را به‌تدریج تولید می‌کند و اجرای متد را بین دو دریافت نگه می‌دارد.

  8. IAsyncEnumerable برای دریافت تدریجی غیرهم‌زمان مناسب است؛ لغو نیازمند همکاری کد و بررسی توکن است.

  9. AsNoTracking مربوط به Tracking است و Deferred بودن را تغییر نمی‌دهد.

  10. Projection و Pagination باید تا جای ممکن پیش از Materialization و در سمت دیتابیس قرار بگیرند.

پنج سؤال مصاحبه‌ای

۱. چرا کد زیر ممکن است دو Query ارسال کند؟

نمونه کد / خروجیCSHARP
var query = db.Users.Where(x => x.IsActive);
var exists = await query.AnyAsync();
var count = await query.CountAsync();

۲. چرا ToList() همیشه بهینه‌سازی نیست؟

<details><summary>نمایش پاسخ</summary><p>چون همهٔ عناصر را در حافظه نگه می‌دارد و شاید مانع پردازش تدریجی یا انتقال فیلتر به SQL شود؛ تنها وقتی Materialization لازم است از آن استفاده کنیم.</p></details>

۳. Where().Take(1) و OrderBy().Take(1) چه تفاوتی دارند؟

<details><summary>نمایش پاسخ</summary><p>در LINQ to Objects، Where می‌تواند بعد از نخستین تطبیق متوقف شود؛ OrderBy برای یافتن کوچک‌ترین عنصر، باید تمام ورودی را بررسی کند.</p></details>

۴. آیا AsAsyncEnumerable() همهٔ نتایج را یکباره می‌خواند؟

<details><summary>نمایش پاسخ</summary><p>خیر، پیمایش تدریجی را ممکن می‌کند؛ بااین‌حال Provider و EF Core ممکن است در برخی سناریوها بافر داخلی داشته باشند.</p></details>

۵. برای گزارش ده میلیون تراکنش، چه کارهایی می‌کنی؟

<details><summary>نمایش پاسخ</summary><p>Projection فقط ستون‌های لازم، فیلتر قبل از Materialization، AsNoTracking، Pagination مناسب، ایندکس و Query Plan؛ برای صادرات طولانی، Streaming و مدیریت عمر اتصال را هم در نظر می‌گیرم.</p></details>

پاسخ کوتاه آمادهٔ مصاحبه

«در LINQ، اجرای به‌تعویق‌افتاده به این معناست که ساخت یک Query الزاماً آن را اجرا نمی‌کند. با شروع Enumeration یا فراخوانی عملگرهای پایانی مثل ToListAsync و CountAsync، Query اجرا می‌شود. در EF Core باید دقت کنم فیلتر و Projection روی IQueryable باقی بمانند؛ وگرنه ممکن است دادهٔ غیرضروری به حافظه منتقل شود یا چند بار به دیتابیس درخواست بزنیم.»
