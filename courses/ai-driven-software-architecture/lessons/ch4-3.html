فصل چهارم — انتخاب معماری و Trade-offs

تعریف Quality Attributeهای قابل اندازه‌گیری

یک Quality Attribute زمانی برای تصمیم‌گیری معماری مفید است که بتوان آن را اندازه‌گیری و آزمایش کرد. عباراتی مثل «سیستم سریع باشد» یا «خیلی پایدار باشد» برای طراحی معماری کافی نیستند.

چرا باید قابل اندازه‌گیری باشد؟

اگر Quality Attribute دقیق نباشد، تیم نمی‌تواند تشخیص دهد معماری انتخاب‌شده واقعاً نیاز پروژه را برآورده کرده است یا نه.

مبهم: سیستم باید سریع باشد.

قابل اندازه‌گیری: 95٪ درخواست‌های پرداخت باید در کمتر از 200ms پاسخ داده شوند.

اصل مهم: چیزی که قابل اندازه‌گیری نباشد، به‌سختی قابل ارزیابی و مقایسه است.

ساختار یک Quality Attribute خوب

برای دقیق‌کردن یک Quality Attribute می‌توان این سؤال‌ها را پاسخ داد:

  • چه چیزی؟ کدام رفتار یا بخش سیستم را اندازه می‌گیریم؟
  • در چه شرایطی؟ بار عادی، Peak Load یا هنگام Failure؟
  • با چه معیاری؟ Latency، Throughput، Error Rate یا Availability؟
  • هدف چقدر است؟ عدد یا محدودهٔ قابل قبول چیست؟

نمونه‌های مبهم و قابل اندازه‌گیری

Attribute تعریف مبهم تعریف قابل اندازه‌گیری
Performance سیستم سریع باشد. 95٪ درخواست‌ها کمتر از 200ms پاسخ داده شوند.
Availability سیستم همیشه در دسترس باشد. Availability ماهانه حداقل 99.99٪ باشد.
Scalability سیستم Load بالا را تحمل کند. سیستم بتواند 10,000 Request در ثانیه را بدون عبور Latency از 300ms پردازش کند.
Reliability تراکنش‌ها مطمئن باشند. هیچ Retry مجازی نباید باعث ثبت بیش از یک Payment موفق شود.
Recovery سیستم سریع Recover شود. پس از Failure سرویس، بازیابی کامل حداکثر در 2 دقیقه انجام شود.

مثال واقعی: Payment Service

فرض کنید یک سرویس پرداخت داریم. به‌جای نوشتن «سیستم باید Performance بالایی داشته باشد»، می‌توان چند معیار مشخص تعریف کرد:

  • Latency: 95٪ درخواست‌های پرداخت کمتر از 200ms پاسخ داده شوند.
  • Throughput: سرویس حداقل 5,000 تراکنش در ثانیه را پردازش کند.
  • Availability: دسترس‌پذیری ماهانه حداقل 99.99٪ باشد.
  • Error Rate: خطاهای داخلی سرویس کمتر از 0.1٪ درخواست‌ها باشند.
  • Recovery: در صورت Crash شدن Instance، ترافیک حداکثر طی 30 ثانیه به Instance سالم منتقل شود.

حالا تیم می‌تواند Architecture را طراحی، Load Test اجرا و نتیجه را با این اهداف مقایسه کند.

فقط Average کافی نیست

در سیستم‌های پرترافیک، Average Latency ممکن است تصویر اشتباهی بدهد. معمولاً بهتر است از Percentileهایی مثل P95 و P99 استفاده شود.

Average: میانگین پاسخ 100ms است.

P95: 95٪ درخواست‌ها حداکثر در 180ms پاسخ می‌گیرند.

P99: 99٪ درخواست‌ها حداکثر در 350ms پاسخ می‌گیرند.

این معیارها نشان می‌دهند کاربران در بدترین بخش‌های واقعی ترافیک چه تجربه‌ای دارند.

معیار باید قابل Verification باشد

برای هر Quality Attribute باید مشخص باشد چگونه صحت آن بررسی می‌شود.

Attribute روش بررسی
Performance Load Test و APM Metrics
Availability Uptime Monitoring و SLI
Scalability Stress Test و افزایش تدریجی Load
Resilience Failure Test یا Chaos Test
Security Security Test و Vulnerability Assessment

استفاده از AI برای دقیق‌کردن Quality Attributeها

AI می‌تواند Requirementهای مبهم را شناسایی کند و آن‌ها را به Candidate Metricهای قابل‌اندازه‌گیری تبدیل کند.

نمونه Prompt

«این Requirementها را بررسی کن. Quality Attributeهای مبهم را پیدا کن و برای هرکدام Scenario، Metric و Target قابل‌اندازه‌گیری پیشنهاد بده. عددهایی که اطلاعات واقعی برایشان نداریم به‌عنوان Assumption مشخص کن.»

AI نباید عددهای مهم Business را بدون دادهٔ واقعی تعیین کند. اعداد پیشنهادی باید با Product Owner، تیم فنی، SLA و داده‌های Production اعتبارسنجی شوند.

اشتباهات رایج

  • استفاده از عباراتی مثل Fast، Highly Available یا Scalable بدون عدد.
  • تعریف عدد بدون مشخص‌کردن شرایط Load و Scenario.
  • استفادهٔ صرف از Average به‌جای P95 و P99 در سیستم‌های پرترافیک.
  • تعیین Targetهای غیرواقعی بدون توجه به Cost و محدودیت‌های زیرساخت.
  • تعریف معیار بدون مشخص‌کردن روش Test و Verification.

جمع‌بندی

  • Quality Attribute باید تا حد امکان دقیق و قابل‌اندازه‌گیری باشد.
  • یک تعریف خوب شامل Scenario، Condition، Metric و Target است.
  • به‌جای «سیستم سریع باشد» باید هدفی مثل P95 < 200ms تعریف شود.
  • معیار باید با Test یا Monitoring قابل Verification باشد.
  • AI می‌تواند معیار پیشنهاد دهد، اما اعداد نهایی باید با Context واقعی پروژه اعتبارسنجی شوند.
