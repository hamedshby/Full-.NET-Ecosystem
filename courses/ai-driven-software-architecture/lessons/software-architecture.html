Software Architecture چیست؟

معماری نرم‌افزار یعنی تصمیم‌گیری دربارهٔ ساختار کلی یک سیستم: سیستم از چه بخش‌هایی تشکیل شود، این بخش‌ها چگونه با هم ارتباط داشته باشند و برای رسیدن به نیازهای مهم پروژه چه محدودیت‌هایی را رعایت کنند.

یک مثال ساده: ساخت فروشگاه اینترنتی

فرض کنید قرار است یک فروشگاه اینترنتی بسازیم. کاربران باید محصول ببینند، سفارش ثبت کنند و هزینه را بپردازند. پیش از نوشتن اولین خط Code، چند سؤال مهم وجود دارد:

  • اطلاعات محصول، مشتری و سفارش کجا نگهداری شوند؟
  • پرداخت چگونه به یک سرویس بانکی متصل شود؟
  • اگر سرویس پرداخت موقتاً از دسترس خارج شد، سفارش چه وضعیتی پیدا کند؟
  • اگر تعداد کاربران ده برابر شد، کدام بخش باید قابل گسترش باشد؟
  • چه کسی اجازه دارد قیمت یا موجودی محصول را تغییر دهد؟

پاسخ این سؤال‌ها فقط جزئیات Code نیست. این پاسخ‌ها شکل کلی سیستم و رفتار آن در شرایط مهم را تعیین می‌کنند؛ بنابراین تصمیم‌های معماری هستند.

تعریف Software Architecture

Software Architecture نمای سطح‌بالای سیستم و مجموعه‌ای از تصمیم‌های مهم دربارهٔ ساختار، اجزا، ارتباط‌ها، داده‌ها و محدودیت‌های آن است.

عبارت «سطح‌بالا» یعنی در معماری معمولاً به‌جای جزئیات یک method یا نام یک متغیر، دربارهٔ مرزهای بزرگ‌تر صحبت می‌کنیم؛ برای مثال:

  • سیستم یک Modular Monolith باشد یا از چند سرویس مستقل تشکیل شود.
  • ارتباط اجزا مستقیم و هم‌زمان باشد یا از Message Broker استفاده شود.
  • هر Module مالک دادهٔ خودش باشد یا چند بخش یک Database مشترک داشته باشند.
  • Authentication در خود برنامه انجام شود یا به یک Identity Provider سپرده شود.
مدل ذهنی: معماری نقشهٔ شهر است؛ خیابان‌های اصلی، منطقه‌ها و مسیرهای ارتباطی را مشخص می‌کند. Code مانند ساختمان‌هایی است که داخل این نقشه ساخته می‌شوند.

تفاوت Architecture، Software Design و Implementation

سطحسؤال اصلینمونه
Architectureبخش‌های اصلی سیستم چه هستند و چگونه همکاری می‌کنند؟سفارش، پرداخت و موجودی Moduleهای جدا با مرز مشخص باشند.
Software Designداخل هر بخش، مسئولیت‌ها چگونه بین typeها و objectها تقسیم شوند؟OrderService ثبت سفارش را هماهنگ کند و PricingPolicy قیمت را محاسبه کند.
Implementationاین طراحی دقیقاً با چه Code و APIهایی ساخته شود؟پیاده‌سازی method، query، validation و مدیریت exception.

مرز این سه سطح همیشه کاملاً سخت و دقیق نیست. یک تصمیم ممکن است در پروژه‌ای معماری و در پروژه‌ای دیگر فقط طراحی باشد. معیار مهم، میزان اثر تصمیم و هزینهٔ تغییر آن است.

چه چیزی یک تصمیم را معماری می‌کند؟

هر تصمیم فنی، تصمیم معماری نیست. انتخاب نام یک متغیر مهم است، اما معمولاً معماری محسوب نمی‌شود. تصمیمی معماری است که یک یا چند ویژگی زیر را داشته باشد:

  • اثر گسترده دارد: چند Module، چند تیم یا بخش بزرگی از سیستم را تحت تأثیر قرار می‌دهد.
  • تغییر آن پرهزینه است: عوض‌کردنش پس از رشد پروژه به مهاجرت داده، بازنویسی یا هماهنگی زیاد نیاز دارد.
  • یک Quality Attribute را تعیین می‌کند: روی Performance، Security، Availability یا Maintainability اثر جدی دارد.
  • برای تیم محدودیت ایجاد می‌کند: مشخص می‌کند اجزا چگونه مجازند به هم وابسته شوند یا داده را به اشتراک بگذارند.

معماری همیشه با Trade-off همراه است

در معماری معمولاً گزینه‌ای وجود ندارد که از هر نظر بهترین باشد. هر انتخاب چیزی به دست می‌دهد و هزینه‌ای ایجاد می‌کند.

نمونه: Microservices

تقسیم سیستم به سرویس‌های مستقل می‌تواند استقرار مستقل و گسترش جداگانهٔ بخش‌ها را ممکن کند. در مقابل، ارتباط شبکه، Observability، مدیریت خطا و سازگاری داده‌ها دشوارتر می‌شود.

پس سؤال درست این نیست که «آیا Microservices خوب است؟» سؤال درست این است که «آیا مزایای آن برای مسئله و محدودیت‌های این پروژه، هزینه‌هایش را توجیه می‌کند؟»

ارتباط معماری با Quality Attributeها

Functional Requirement می‌گوید سیستم چه کاری انجام دهد؛ برای مثال «کاربر بتواند سفارش ثبت کند». Quality Attribute مشخص می‌کند سیستم آن کار را با چه کیفیتی انجام دهد:

  • Performance: ثبت سفارش چقدر سریع انجام شود؟
  • Availability: سرویس چه مدت باید در دسترس باشد؟
  • Security: چه کسی به اطلاعات سفارش دسترسی داشته باشد؟
  • Scalability: سیستم باید چه تعداد سفارش هم‌زمان را مدیریت کند؟
  • Maintainability: افزودن یک روش پرداخت جدید چقدر آسان باشد؟

معماری خوب از نیازهای واقعی پروژه شروع می‌شود. اگر تعداد کاربران کم و تیم کوچک است، یک ساختار ساده و منظم احتمالاً بهتر از یک معماری توزیع‌شدهٔ پیچیده است.

اشتباهات رایج

  • شروع با Technology: انتخاب Kubernetes یا Kafka پیش از شناخت مسئله، معماری را ابزارمحور می‌کند.
  • پیچیده‌سازی زودهنگام: استفاده از Microservices برای پروژه‌ای کوچک می‌تواند هزینه‌ای بیشتر از ارزش آن ایجاد کند.
  • نادیده‌گرفتن محدودیت‌ها: معماری باید با بودجه، زمان، مهارت تیم و زیرساخت موجود سازگار باشد.
  • ثبت‌نکردن دلیل تصمیم: اگر فقط نتیجه نوشته شود، اعضای آیندهٔ تیم نمی‌دانند تصمیم برای حل چه مسئله‌ای گرفته شده است.
  • تصور ثابت‌بودن معماری: معماری باید همراه با تغییر نیازها تکامل پیدا کند، اما این تغییر باید آگاهانه و کنترل‌شده باشد.

جمع‌بندی

  • Software Architecture ساختار سطح‌بالا و تصمیم‌های مهم سیستم را مشخص می‌کند.
  • معماری روی Componentها، ارتباط‌ها، داده‌ها، محدودیت‌ها و Quality Attributeها تمرکز دارد.
  • Software Design به طراحی داخلی اجزا نزدیک‌تر است و Implementation آن طراحی را به Code تبدیل می‌کند.
  • هر تصمیم معماری یک Trade-off دارد و باید متناسب با Context پروژه انتخاب شود.
  • معماری خوب لزوماً پیچیده نیست؛ معماری خوب برای مسئلهٔ واقعی مناسب و برای تیم قابل‌فهم است.
