Modular Monolith

Modular Monolith یک برنامهٔ واحد برای Build و Deployment است، اما داخل آن سیستم به ماژول‌های مستقل با مرزهای مشخص تقسیم می‌شود. مهم‌ترین اصل آن این است که ماژول‌ها آزادانه وارد جزئیات داخلی یکدیگر نشوند.

Modular Monolith چیست؟

در Monolith معمولی، بخش‌های مختلف سیستم ممکن است به‌مرور به هم وابسته شوند. Modular Monolith تلاش می‌کند همان سادگی Deployment یک Monolith را نگه دارد، ولی ساختار داخلی سیستم را به Moduleهای مستقل تقسیم کند.

Order Module
↔
Payment Module
↔
Notification Module
مدل ذهنی: یک ساختمان واحد با چند واحد مستقل؛ همه زیر یک سقف هستند، اما هر واحد مرز، مسئولیت و ورودی مشخص خودش را دارد.

هر Module چه چیزی دارد؟

  • Business Logic خودش
  • Entity و Domain Model خودش
  • Application Serviceهای خودش
  • Contract یا API عمومی برای ارتباط با سایر Moduleها
  • Data Access و Schema مربوط به خودش

سایر Moduleها نباید مستقیماً به Entity، Repository یا Table داخلی آن دسترسی داشته باشند.

ارتباط بین Moduleها چگونه انجام می‌شود؟

ارتباط Moduleها معمولاً به دو شکل اصلی انجام می‌شود: Synchronous و Asynchronous.

روش زمان استفاده مثال
Synchronous Call وقتی نتیجه فوراً لازم است. Order از Payment می‌پرسد آیا پرداخت موفق شده است یا نه.
Domain / Integration Event وقتی Module فقط می‌خواهد وقوع یک اتفاق را اعلام کند. PaymentCompleted منتشر می‌شود و Notification واکنش نشان می‌دهد.

روش اول: ارتباط مستقیم از طریق Contract

یک Module نباید مستقیماً Classهای داخلی Module دیگر را صدا بزند. بهتر است هر Module یک Contract عمومی محدود داشته باشد.

مثال در .NET

public interface IPaymentModule
{
    Task<PaymentResult> GetPaymentStatusAsync(
        Guid transactionId,
        CancellationToken cancellationToken);
}

Order Module فقط IPaymentModule را می‌شناسد. این Interface مرز ارتباطی Payment Module است و جزئیات داخلی آن را مخفی می‌کند.

Order Module
→
IPaymentModule
→
Payment Module

روش دوم: ارتباط Event-Based

گاهی Module مبدا نباید بداند چه Moduleهایی به نتیجهٔ عملیات آن نیاز دارند. در این شرایط Event ارتباط را Loose Coupledتر می‌کند.

مثال Payment

public sealed record PaymentCompleted(
    Guid TransactionId,
    decimal Amount);

Payment Module بعد از پرداخت موفق Event را منتشر می‌کند:

Payment Module
→
PaymentCompleted
→
Order Module
+
Notification Module

Payment لازم نیست بداند Notification یا Reporting وجود دارند. هر Module به Event موردنیاز خودش Subscribe می‌کند.

آیا داخل Modular Monolith به RabbitMQ نیاز داریم؟

لزوماً نه. چون همهٔ Moduleها داخل یک Process هستند، Eventها می‌توانند ابتدا به شکل In-Process منتشر شوند؛ مثلاً با Mediator یا Event Dispatcher داخلی. 

await eventDispatcher.PublishAsync(
    new PaymentCompleted(transaction.Id, transaction.Amount));

اگر بعدها یک Module به Microservice مستقل تبدیل شود، همان Event می‌تواند از طریق RabbitMQ، Kafka یا Broker دیگری منتشر شود.

نکته: Modular Monolith به معنی شبیه‌سازی اجباری Microservices نیست. تا وقتی نیاز واقعی نداریم، ارتباط In-Process ساده‌تر و کم‌هزینه‌تر است.

مهم‌ترین قانون: Moduleها Database همدیگر را دور نزنند

یکی از خطرناک‌ترین نوع وابستگی این است که یک Module مستقیماً Tableهای Module دیگر را Query یا Update کند.

اشتباه: Order Module مستقیماً جدول Payment.Transactions را Query کند.

درست: Order از Contract عمومی Payment Module استفاده کند.

حتی اگر همهٔ Moduleها در یک SQL Server و حتی یک Database باشند، مالکیت داده باید مشخص باشد.

روش توضیح
Schema per Module مثلاً payment.Transactions و orders.Orders.
DbContext per Module هر Module DbContext و Migrationهای خودش را دارد.
Database per Module جداسازی بیشتر؛ در صورت نیاز و پیچیدگی بالاتر.

Transaction بین Moduleها چه می‌شود؟

چون Moduleها در یک Monolith هستند، از نظر فنی ممکن است بتوان یک Transaction مشترک بین چند Module ایجاد کرد؛ اما استفادهٔ زیاد از آن Coupling را بالا می‌برد.

اگر Order برای ثبت سفارش مجبور باشد هم‌زمان چند Table داخلی Payment را Update کند، مرز Module عملاً شکسته شده است.

بهتر است هر Module Business Transaction خودش را مدیریت کند و برای تغییرات جانبی از Event استفاده شود.

مثال کامل ارتباط Moduleها در Payment System

فرض کنید سه Module داریم:

  • Payment: مسئول انجام تراکنش
  • Settlement: مسئول تسویه
  • Notification: مسئول ارسال پیام
Payment
→
PaymentCompleted
→
Settlement
+
Notification

Payment فقط Event را منتشر می‌کند. Settlement بر اساس آن رکورد تسویه ایجاد می‌کند و Notification پیام موفقیت می‌فرستد. هیچ‌کدام نباید مستقیماً Repository داخلی Payment را استفاده کنند.

قواعد خوب برای ارتباط بین Moduleها

  • هر Module یک Public API یا Contract محدود داشته باشد.
  • Moduleها به Internal Classهای یکدیگر Reference مستقیم نداشته باشند.
  • دسترسی مستقیم به Table یا DbContext Module دیگر ممنوع باشد.
  • برای Query فوری از Synchronous Contract استفاده شود.
  • برای اعلام رخداد از Event استفاده شود.
  • Dependencyها ترجیحاً یک‌طرفه و کنترل‌شده باشند.
  • از Shared Model بزرگ بین Moduleها جلوگیری شود.

ساختار پیشنهادی در .NET

Modules/
 ├── Payments/
 │    ├── Payments.Domain
 │    ├── Payments.Application
 │    ├── Payments.Infrastructure
 │    └── Payments.Contracts
 │
 ├── Orders/
 │    ├── Orders.Domain
 │    ├── Orders.Application
 │    ├── Orders.Infrastructure
 │    └── Orders.Contracts
 │
 └── Notifications/
      ├── Notifications.Application
      └── Notifications.Contracts

پروژهٔ Contracts فقط چیزهایی را نگه می‌دارد که سایر Moduleها اجازه دارند ببینند؛ نه Entity، Repository یا جزئیات داخلی.

تفاوت ارتباط Moduleها با Microservices

موضوع Modular Monolith Microservices
Process مشترک جدا
Call مستقیم In-Process Network Call
Event می‌تواند In-Process باشد معمولاً Message Broker
Deployment یک Deployment مستقل برای هر Service
پیچیدگی Operational کمتر بیشتر

استفاده از AI برای بررسی مرز Moduleها

AI می‌تواند Dependencyهای بین Moduleها را بررسی کند و وابستگی‌هایی را که مرزها را می‌شکنند پیدا کند.

نمونه Prompt

«این ساختار Modular Monolith را بررسی کن. Dependency بین Moduleها، دسترسی مستقیم به Data Model سایر Moduleها و Cyclic Dependencyها را شناسایی کن و برای هر مورد راه‌حل مبتنی بر Contract یا Event پیشنهاد بده.»

اشتباهات رایج

  • تقسیم پروژه به Folderهای مختلف بدون مرز واقعی.
  • Reference مستقیم Domain یک Module از Module دیگر.
  • استفاده از یک DbContext بزرگ برای کل سیستم.
  • Query مستقیم Tableهای Module دیگر.
  • ایجاد Shared Library بزرگ شامل تمام Entityها.
  • استفاده از Event برای هر Call ساده و ایجاد پیچیدگی غیرضروری.
  • ایجاد Dependency دوطرفه بین Moduleها.

جمع‌بندی

  • Modular Monolith یک Deployment دارد ولی از Moduleهای مستقل تشکیل شده است.
  • مهم‌ترین اصل، حفظ مرز و مالکیت هر Module است.
  • ارتباط فوری می‌تواند از طریق Contract و Call مستقیم In-Process انجام شود.
  • برای اعلام رخداد و کاهش Coupling می‌توان از Event استفاده کرد.
  • Moduleها نباید مستقیماً Database، Entity یا Repository یکدیگر را استفاده کنند.
  • مرزهای خوب باعث می‌شوند در آینده جداکردن یک Module و تبدیل آن به Microservice بسیار ساده‌تر شود.
