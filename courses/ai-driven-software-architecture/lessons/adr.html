فصل اول — مقدمه

ADR چیست؟

Architecture Decision Record یا ADR یک سند کوتاه است که توضیح می‌دهد تیم چه تصمیم معماری گرفته، چرا آن را گرفته و چه پیامدهایی را پذیرفته است.

یک مثال ساده: چرا این راه را انتخاب کردیم؟

فرض کنید به یک پروژهٔ فروشگاه اینترنتی ملحق شده‌اید. Code نشان می‌دهد سیستم به‌صورت Modular Monolith ساخته شده است، اما هیچ‌کس نمی‌داند چرا تیم به‌جای Microservices این ساختار را انتخاب کرده است.

شاید تصمیم به‌دلیل تیم کوچک و زمان تحویل کوتاه کاملاً منطقی بوده باشد. اگر دلیل ثبت نشده باشد، تیم جدید ممکن است تصمیم درستی را اشتباه تصور کند یا همان بحث قدیمی را از ابتدا تکرار کند.

مدل ذهنی: Code نتیجهٔ تصمیم را نشان می‌دهد؛ ADR داستان و دلیل پشت آن تصمیم را نگه می‌دارد.

نام ADR چه معنایی دارد؟

واژهمعنا در این اصطلاح
Architectureتصمیم روی ساختار یا ویژگی‌های مهم سیستم اثر می‌گذارد.
Decisionتیم از میان چند گزینه، یک راه را انتخاب کرده است.
Recordتصمیم و دلیل آن برای استفادهٔ آینده ثبت می‌شود.

خودِ انتخاب، Architectural Decision است. سندی که این انتخاب را ثبت می‌کند، ADR نام دارد. بنابراین ADR جای تصمیم‌گیری را نمی‌گیرد؛ نتیجهٔ یک فرایند تصمیم‌گیری را قابل فهم و قابل ردیابی می‌کند.

هر ADR چه بخش‌هایی دارد؟

بخشبه چه سؤالی پاسخ می‌دهد؟
Titleموضوع تصمیم چیست؟
Statusتصمیم پیشنهادی، پذیرفته‌شده یا جایگزین‌شده است؟
Contextچه مسئله، Requirement یا Constraint باعث این تصمیم شد؟
Decisionدر نهایت چه گزینه‌ای انتخاب شد؟
Consequencesچه مزایا، هزینه‌ها و محدودیت‌هایی را پذیرفتیم؟

می‌توان بخش‌هایی مانند Options، Rationale، تاریخ و افراد درگیر را نیز افزود. مهم این است که سند کوتاه بماند و دلیل تصمیم را روشن کند، نه اینکه به یک گزارش طولانی تبدیل شود.

نمونهٔ کامل و ساده

ADR-001: استفاده از Modular Monolith برای نسخهٔ اول

Status: Accepted

Context: تیم پنج Developer دارد، نسخهٔ اول باید در سه ماه تحویل شود و Boundaryهای Domain هنوز در حال تغییرند. نگهداری چند Deployment مستقل برای تیم پرهزینه است.

Decision: سیستم به‌صورت Modular Monolith ساخته می‌شود. Moduleهای سفارش، پرداخت و موجودی Boundary و قرارداد مشخص خواهند داشت، اما با یک واحد Deploy می‌شوند.

Consequences مثبت: توسعه و Deployment ساده‌تر است و تیم سریع‌تر بازخورد می‌گیرد.

Consequences منفی: Moduleها Deployment مستقل ندارند و تیم باید وابستگی میان آن‌ها را کنترل کند.

این ADR نمی‌گوید Modular Monolith همیشه بهتر است. فقط توضیح می‌دهد چرا برای این Context انتخاب مناسبی بوده است.

Statusهای رایج

  • Proposed: تصمیم پیشنهاد شده، اما هنوز Review و تأیید نشده است.
  • Accepted: تصمیم تأیید شده و تیم باید بر اساس آن عمل کند.
  • Deprecated: تصمیم دیگر برای استفادهٔ جدید توصیه نمی‌شود.
  • Superseded: یک ADR جدید جای این تصمیم را گرفته است.

معمولاً ADR قدیمی را پاک یا بازنویسی نمی‌کنیم. اگر شرایط تغییر کند، ADR جدیدی می‌نویسیم و با Superseded رابطهٔ میان تصمیم قدیمی و جدید را نشان می‌دهیم. به این ترتیب تاریخچهٔ معماری از بین نمی‌رود.

چه زمانی باید ADR بنویسیم؟

برای تصمیمی ADR بنویسید که اثر گسترده دارد، تغییر آن پرهزینه است یا احتمال دارد بعداً دربارهٔ دلیل آن سؤال شود. برای مثال:

  • انتخاب Architecture Pattern اصلی سیستم
  • تعیین Boundary و مالکیت دادهٔ Moduleها
  • انتخاب روش ارتباط هم‌زمان یا غیرهم‌زمان
  • انتخاب Database یا راهبرد ذخیره‌سازی مهم
  • تصمیم‌های مهم Security، Reliability و Deployment

برای نام یک variable یا تغییر کوچک UI معمولاً ADR لازم نیست. معیار، اهمیت و ماندگاری تصمیم است؛ نه صرفاً فنی‌بودن آن.

فرایند نوشتن ADR

  1. مسئله را روشن کنید: Requirement، Constraint و Context را بنویسید.
  2. گزینه‌ها را بررسی کنید: مزایا، هزینه‌ها و Risk هر گزینه را مقایسه کنید.
  3. پیش‌نویس بسازید: تصمیم پیشنهادی و Consequenceهای مثبت و منفی را ثبت کنید.
  4. با تیم Review کنید: افراد متأثر باید بتوانند ابهام‌ها و Riskهای جاافتاده را مطرح کنند.
  5. Status را مشخص کنید: پس از تأیید، وضعیت را به Accepted تغییر دهید.
  6. در آینده جایگزین کنید، نه حذف: تصمیم جدید را با ADR تازه ثبت و به قبلی پیوند دهید.

نقش AI در نوشتن ADR

AI می‌تواند از روی Context و گزینه‌های ارائه‌شده، پیش‌نویس ADR تولید کند، متن مبهم را پیدا کند، Consequenceهای احتمالی را پیشنهاد دهد و تصمیم را با ADRهای قبلی مقایسه کند.

نمونهٔ Prompt

«با استفاده از Context، Options و Decision زیر یک ADR کوتاه بساز. بخش‌های Title، Status، Context، Decision و Consequences را بنویس. Assumptionهای بدون مدرک را جداگانه مشخص کن و اطلاعاتی از خودت نساز.»

Human-in-the-Loop: AI تصمیم‌گیر نهایی نیست. تیم باید صحت Context، واقعی‌بودن Options و قابل‌پذیرش‌بودن Consequenceها را Review کند.

اشتباهات رایج

  • نوشتن فقط نتیجه: «از PostgreSQL استفاده می‌کنیم» بدون Context و Consequences برای آینده کافی نیست.
  • پنهان‌کردن هزینه‌ها: تصمیم معماری همیشه Trade-off دارد؛ پیامد منفی را نیز بنویسید.
  • ثبت تصمیم‌های بسیار کوچک: تعداد زیاد ADR کم‌ارزش، پیدا کردن تصمیم‌های مهم را دشوار می‌کند.
  • تغییر متن تصمیم قدیمی: این کار تاریخچه را از بین می‌برد؛ ADR جدیدی بسازید.
  • سپردن تصمیم به AI: خروجی AI پیش‌نویس است و ممکن است بر Assumption نادرست تکیه کند.

جمع‌بندی

  • ADR سند کوتاه یک تصمیم معماری و دلیل آن است.
  • بخش‌های پایهٔ آن Title، Status، Context، Decision و Consequences هستند.
  • ADR خوب هم مزایا و هم هزینه‌های تصمیم را نشان می‌دهد.
  • تصمیم قدیمی حذف نمی‌شود؛ ADR جدید می‌تواند آن را Supersede کند.
  • AI در تولید پیش‌نویس و یافتن ابهام کمک می‌کند، اما تأیید نهایی با انسان است.
