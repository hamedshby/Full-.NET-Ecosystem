نقش Software Architect

Software Architect کمک می‌کند تیم دربارهٔ ساختار کلی سیستم تصمیم‌های درست و هماهنگ بگیرد. او فقط Diagram نمی‌کشد؛ مسئله را می‌فهمد، گزینه‌ها را مقایسه می‌کند، دلیل تصمیم‌ها را ثبت می‌کند و همراه تیم مطمئن می‌شود معماری در Code رعایت شده است.

یک مثال ساده

فرض کنید تیم شما یک فروشگاه اینترنتی می‌سازد. یک Developer روی سفارش، یک نفر روی پرداخت و فرد دیگری روی موجودی کار می‌کند. اگر هرکس بدون هماهنگی ساختار دلخواه خودش را بسازد، ممکن است داده‌ها چند بار ذخیره شوند، خطاهای پرداخت سفارش را خراب کنند یا تغییر یک بخش چند بخش دیگر را بشکند.

معمار به تیم کمک می‌کند سؤال‌های مشترک را پاسخ دهد: مرز هر بخش کجاست؟ مالک داده کیست؟ اجزا چگونه ارتباط دارند؟ هنگام خرابی چه اتفاقی می‌افتد؟ چه تصمیمی اکنون ساده و برای رشد آینده مناسب است؟

مدل ذهنی: معمار مانند کسی است که نقشه و قواعد اصلی ساخت یک مجتمع را هماهنگ می‌کند؛ اما اعضای تیم همچنان ساختمان را می‌سازند و در جزئیات فنی مشارکت دارند.

مسئولیت‌های اصلی معمار نرم‌افزار

۱. فهم مسئله و نیازهای پروژه

پیش از پیشنهاد Technology، معمار باید بداند سیستم چه مشکلی را حل می‌کند، کاربران چه کسانی هستند و چه محدودیت‌هایی وجود دارد. برای مثال، بودجه، زمان تحویل، مهارت تیم و قوانین نگهداری داده روی معماری اثر می‌گذارند.

۲. شناسایی تصمیم‌های مهم

همهٔ تصمیم‌ها معماری نیستند. معمار روی تصمیم‌هایی تمرکز می‌کند که اثر گسترده دارند یا تغییرشان بعداً پرهزینه است؛ مانند مرز Moduleها، مالکیت داده، روش ارتباط اجزا و راهبرد Authentication.

۳. مقایسهٔ گزینه‌ها

معمار نباید اولین ایده را فوراً انتخاب کند. او گزینه‌ها، مزایا، هزینه‌ها و Riskهای آن‌ها را مقایسه می‌کند. مثلاً بررسی می‌کند یک Modular Monolith برای تیم مناسب‌تر است یا پیچیدگی Microservices واقعاً توجیه دارد.

۴. ثبت دلیل تصمیم‌ها

تیم باید بداند چه تصمیمی، برای حل چه مسئله‌ای و با پذیرش چه پیامدی گرفته شده است. این اطلاعات معمولاً در Architecture Decision Record یا ADR ثبت می‌شوند.

۵. همراهی با پیاده‌سازی

کار معمار با تحویل Diagram تمام نمی‌شود. او Code و Dependencyها را بررسی می‌کند، به پرسش‌های تیم پاسخ می‌دهد و اگر واقعیت پروژه با فرض‌های اولیه فرق داشت، معماری را اصلاح می‌کند.

Architectural Thinking یعنی چه؟

Architectural Thinking یعنی هنگام تصمیم‌گیری فقط به «آیا کار می‌کند؟» فکر نکنیم. باید اثر تصمیم بر آینده و کل سیستم را نیز بسنجیم:

  • این راهکار با نیاز واقعی پروژه هماهنگ است؟
  • اگر تعداد کاربران بیشتر شود چه اتفاقی می‌افتد؟
  • اگر Dependency خارجی قطع شود سیستم چگونه رفتار می‌کند؟
  • آیا تیم فعلی می‌تواند این راهکار را نگهداری کند؟
  • چه پیچیدگی و هزینه‌ای به دست می‌آوریم؟

این نوع تفکر مخصوص عنوان شغلی Architect نیست. یک Junior Developer هم می‌تواند با پرسیدن این سؤال‌ها به‌تدریج نگاه معماری پیدا کند.

تفاوت نقش‌ها در تیم

نقشتمرکز اصلینمونه فعالیت
Developerساخت و نگهداری Featureهاپیاده‌سازی API، Test و رفع Bug
Tech Leadهدایت فنی روزانهٔ تیمتقسیم کار فنی، Code Review و رفع مانع‌ها
Software Architectهماهنگی تصمیم‌های سطح سیستمتعریف Boundaryها، بررسی Trade-off و ثبت تصمیم
Product Teamارزش تجاری و نیاز کاربرتعیین اولویت، Scope و Acceptance Criteria

این مرزها در شرکت‌ها متفاوت‌اند. در تیم کوچک ممکن است Tech Lead بخشی از نقش معمار را انجام دهد. نکتهٔ مهم همکاری است، نه عنوان شغلی.

معمار چگونه با تیم ارتباط برقرار می‌کند؟

  • با Developerها: محدودیت‌ها و دلیل تصمیم‌ها را توضیح می‌دهد و از تجربهٔ پیاده‌سازی آن‌ها بازخورد می‌گیرد.
  • با Tech Lead: معماری را به کارهای قابل اجرا تبدیل و انحراف‌های فنی را بررسی می‌کند.
  • با Product Team: اثر تصمیم‌های تجاری بر Cost، زمان، Security و Scalability را روشن می‌کند.
  • با Stakeholderها: Riskها و Trade-offها را با زبان قابل‌فهم بیان می‌کند، نه فقط با اصطلاحات فنی.

معمار خوب فقط خوب فکر نمی‌کند؛ باید بتواند فکر خود را شفاف منتقل کند و به نظر متخصصان دیگر گوش دهد.

یک روز کاری نمونه

  1. بررسی Requirement جدید برای افزودن پرداخت قسطی.
  2. پرسیدن سؤال دربارهٔ قوانین تجاری، Security و رفتار هنگام خطا.
  3. گفت‌وگو با تیم پرداخت و سفارش دربارهٔ Boundaryها.
  4. مقایسهٔ دو راهکار و نوشتن Trade-offهای هرکدام.
  5. ثبت تصمیم در ADR و توضیح آن برای تیم.
  6. بازبینی پیاده‌سازی اولیه برای اطمینان از رعایت Contractها.

همان‌طور که می‌بینید، بخش زیادی از کار معمار تحلیل، سؤال‌پرسیدن، ارتباط و تصمیم‌سازی است؛ نه فقط نوشتن Code.

معمار چه کاری نباید انجام دهد؟

  • بدون شناخت مسئله، Technology محبوب خودش را تحمیل نکند.
  • تمام تصمیم‌ها را به‌تنهایی نگیرد و دانش را نزد خودش نگه ندارد.
  • Diagramی نسازد که با Code واقعی ارتباطی ندارد.
  • پیچیدگی را نشانهٔ حرفه‌ای‌بودن نداند.
  • پس از تصمیم‌گیری، تیم را هنگام Implementation تنها نگذارد.

جمع‌بندی

  • Software Architect تصمیم‌های مهم سطح سیستم را هماهنگ می‌کند.
  • او مسئله، Constraintها، Quality Attributeها و Trade-offها را بررسی می‌کند.
  • معمار با Developer، Tech Lead و Product Team همکاری می‌کند؛ جای آن‌ها را نمی‌گیرد.
  • مسئولیت او فقط طراحی اولیه نیست و تا Implementation و Review ادامه دارد.
  • Junior Developer نیز می‌تواند با پرسیدن سؤال‌های سطح سیستم، Architectural Thinking را تمرین کند.
