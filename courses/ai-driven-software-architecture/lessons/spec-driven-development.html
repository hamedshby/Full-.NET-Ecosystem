Spec-Driven Development

Spec-Driven Development یا SDD روشی است که در آن پیش از تولید Code، انتظارها و محدودیت‌های سیستم را در Specificationهای ساختاریافته ثبت می‌کنیم. سپس Developer یا AI بر اساس همان Specification طراحی و پیاده‌سازی را پیش می‌برد.

یک مثال ساده

فرض کنید از AI می‌خواهید Feature ثبت‌نام را بسازد و فقط می‌نویسید: «یک API برای ثبت‌نام کاربر ایجاد کن.» AI می‌تواند Code تولید کند، اما پاسخ چند سؤال را نمی‌داند:

  • ایمیل باید Unique باشد؟
  • Password چه قواعدی دارد؟
  • پس از ثبت‌نام، ایمیل تأیید ارسال شود؟
  • اطلاعات در کدام Module و Database ذخیره شوند؟
  • خطاهای API چه ساختاری داشته باشند؟

اگر این Context را ندهیم، AI ناچار به حدس‌زدن می‌شود. در SDD ابتدا این تصمیم‌ها در یک Spec ثبت می‌شوند و بعد Code از روی آن ساخته می‌شود.

مدل ذهنی: Prompt مانند یک درخواست شفاهی است؛ Spec مانند نقشه و قرارداد مکتوبی است که تیم می‌تواند آن را بررسی و دوباره استفاده کند.

مشکل پروژه‌های بزرگ AI-Generated

در Feature کوچک، چند Prompt پیاپی معمولاً کافی است. اما در پروژه‌ای بزرگ مانند فروشگاه، سامانهٔ آگهی خودرو یا سیستم بانکی، تعداد Business Ruleها و Dependencyها زیاد می‌شود. در این حالت مشکلات زیر پدیدار می‌شوند:

  • AI بین Sessionها بخشی از Context پروژه را از دست می‌دهد.
  • Requirement مبهم را اشتباه تفسیر می‌کند.
  • Feature جدید را با Pattern متفاوتی می‌سازد.
  • Code در لحظه کار می‌کند، اما به‌تدریج Technical Debt ایجاد می‌شود.
  • تصمیم تازه ممکن است با Architecture یا تصمیم قبلی تناقض داشته باشد.

ریشهٔ مشترک این مشکلات کمبود Context پایدار است. AI تمام مدل ذهنی تیم را نمی‌داند؛ فقط Contextی را می‌بیند که در اختیارش قرار گرفته است.

Vibe Coding چیست؟

در Vibe Coding کار را با Prompt شروع می‌کنیم، خروجی AI را می‌بینیم و با Promptهای بعدی آن را اصلاح می‌کنیم:

«یک Endpoint برای ثبت‌نام بساز.»

«Validation ایمیل را اضافه کن.»

«حالا Testها را بنویس.»

این روش بد نیست. برای Prototype، ابزار کوچک، آزمایش و یادگیری بسیار سریع و مفید است. مشکل زمانی شروع می‌شود که سیستم بزرگ است و تصمیم‌های فراوان باید در طول زمان هماهنگ بمانند.

تعریف Spec-Driven Development

در SDD، AI به‌جای تکیه بر Promptهای پراکنده، از مجموعه‌ای از اسناد ساختاریافته استفاده می‌کند. این اسناد توضیح می‌دهند چه چیزی، چرا و تحت چه محدودیت‌هایی باید ساخته شود.

یک مجموعه Spec می‌تواند شامل موارد زیر باشد:

  • نمای کلی Application و هدف Business
  • Technology Stack و Dependencyهای مجاز
  • قواعد Architecture و جهت Dependencyها
  • Coding Standardها و قراردادهای Error Handling
  • Featureها، User Storyها و Business Ruleها
  • Acceptance Criteria و Edge Caseها
  • Taskهای Implementation و ترتیب Dependency آن‌ها

این فایل‌ها معمولاً در Markdown و کنار Code نگهداری می‌شوند تا Version Control، Review و استفادهٔ دوباره برای انسان و AI آسان باشد.

فرایند SDD چگونه کار می‌کند؟

  1. تعریف Context پایه: نوع Application، Stack، Ruleهای Business و Constraintهای Architecture ثبت می‌شوند.
  2. تعریف Feature: مسئله، Actor، رفتار مورد انتظار، خارج از Scope و Acceptance Criteria نوشته می‌شوند.
  3. رفع ابهام: سؤال‌های بدون پاسخ و Assumptionهای پنهان پیش از Code مشخص می‌شوند.
  4. تولید Plan: Feature به Taskهای کوچک و مرتب‌شده بر اساس Dependency تبدیل می‌شود.
  5. Review انسانی: تیم Spec و Plan را بررسی و تأیید می‌کند.
  6. Implementation: AI یا Developer Taskها را با Context تأییدشده اجرا می‌کند.
  7. Verification: Code با Acceptance Criteria، Testها و Constraintهای Architecture مقایسه می‌شود.

یک Spec ساده برای ثبت‌نام

هدف: کاربر جدید بتواند با ایمیل حساب ایجاد کند.

Business Rule: هر ایمیل فقط به یک حساب فعال تعلق دارد.

Input: ایمیل، Password و نام نمایشی.

رفتار: داده Validation، Password Hash و حساب در حالت Pending ذخیره شود.

Integration: پس از ثبت موفق، پیام تأیید ایمیل منتشر شود.

Error: ایمیل تکراری با Status Code و Error Code مشخص پاسخ داده شود.

Acceptance Criteria: ثبت‌نام معتبر موفق است؛ ایمیل تکراری رد می‌شود؛ Password خام ذخیره نمی‌شود.

Constraint: دسترسی مستقیم API به Infrastructure مجاز نیست و باید از Application Layer عبور کند.

این Spec هنوز کوتاه است، اما نسبت به یک Prompt یک‌خطی، حدس‌های AI را بسیار کمتر می‌کند و مبنای روشنی برای Review و Test می‌دهد.

Spec خوب چه ویژگی‌هایی دارد؟

  • مسئله را توضیح می‌دهد: فقط راهکار فنی را تحمیل نمی‌کند.
  • Scope روشن دارد: مشخص است چه چیزی داخل و خارج Feature است.
  • قابل بررسی است: Acceptance Criteria و نتیجهٔ قابل مشاهده دارد.
  • ابهام را پنهان نمی‌کند: سؤال‌ها و Assumptionها صریح ثبت می‌شوند.
  • با Architecture هماهنگ است: Constraintها و Dependency Ruleها را رعایت می‌کند.
  • مختصر اما کافی است: جزئیاتی دارد که تصمیم و پیاده‌سازی را هدایت کند، نه متن طولانی بدون کاربرد.

مزایا و هزینه‌ها

مزایا

  • کاهش سوءبرداشت میان Product، Developer و AI
  • Context پایدار در Sessionها و تغییر اعضای تیم
  • امکان Review تصمیم‌ها پیش از تولید Code پرهزینه
  • ارتباط روشن میان Requirement، Task، Code و Test
  • کاهش Architecture Drift و Implementationهای ناسازگار

هزینه‌ها

  • نوشتن و Review کردن Spec زمان می‌خواهد.
  • Spec قدیمی می‌تواند AI و تیم را به مسیر اشتباه ببرد.
  • برای Task بسیار کوچک ممکن است فرایند بیش‌ازحد سنگین باشد.
  • Specification کامل نیز جای دانش Domain و قضاوت انسانی را نمی‌گیرد.

ابزارها و Frameworkهای رایج

مقالهٔ منبع چند نمونه را معرفی می‌کند: OpenSpec، GitHub Spec Kit، BMAD Method، Kiro و Tessl. نام و جزئیات ابزارها ممکن است تغییر کنند، اما ایدهٔ مشترک آن‌ها ثابت است:

  1. Context و قواعد پروژه را ثبت کن.
  2. Feature را به Specification قابل Review تبدیل کن.
  3. Specification را به Plan و Task تبدیل کن.
  4. Code را از روی Context تأییدشده تولید و بررسی کن.

یادگیری اصل فرایند از وابستگی به یک ابزار خاص مهم‌تر است.

اشتباهات رایج

  • Spec را تضمین صحت دانستن: AI می‌تواند Specification خوب را هم اشتباه پیاده کند؛ Verification همچنان لازم است.
  • نوشتن راهکار بدون مسئله: Spec باید هدف و Context را روشن کند، نه فقط Class و Technology را فهرست کند.
  • به‌روزرسانی‌نکردن اسناد: Spec ناسازگار با Code منبع Context نادرست می‌شود.
  • حذف Human Review: Specification تولیدشده توسط AI ممکن است Requirement جعلی یا Assumption خطرناک داشته باشد.
  • فرایند سنگین برای هر تغییر: میزان Specification باید متناسب با ریسک و پیچیدگی Task باشد.

جمع‌بندی

  • SDD به AI Context پایدار و ساختاریافته می‌دهد.
  • Specification پیش از Code بررسی می‌شود تا سوءبرداشت زودتر کشف شود.
  • Vibe Coding برای Prototype و Task کوچک همچنان ارزشمند است.
  • SDD برای Domain پیچیده، تیم بزرگ و پروژهٔ بلندمدت مفیدتر می‌شود.
  • Spec باید زنده، قابل Review و هماهنگ با Code باقی بماند.
  • AI دستیار اجرای Specification است؛ مسئولیت تصمیم و تأیید نهایی با انسان است.
