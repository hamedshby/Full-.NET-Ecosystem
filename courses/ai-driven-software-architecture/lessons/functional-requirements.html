Functional Requirements

Functional Requirement مشخص می‌کند سیستم باید چه رفتار یا قابلیتی ارائه دهد. به زبان ساده، کارهایی که کاربر یا یک سیستم دیگر می‌تواند با نرم‌افزار انجام دهد، معمولاً در این گروه قرار می‌گیرند.

یک مثال ساده: سفارش غذا

در برنامهٔ سفارش غذا، مشتری انتظار دارد چند کار مشخص انجام دهد:

  • فهرست غذاها را ببیند.
  • غذا را به سبد خرید اضافه یا از آن حذف کند.
  • نشانی تحویل را انتخاب کند.
  • سفارش را ثبت و پرداخت کند.
  • وضعیت سفارش را ببیند.

هر مورد یک رفتار قابل مشاهده از سیستم را توصیف می‌کند. این‌ها نمونه‌های سادهٔ Functional Requirement هستند.

مدل ذهنی: اگر Requirement پاسخ سؤال «سیستم چه کاری باید انجام دهد؟» باشد، احتمالاً Functional است. اگر پاسخ دهد «آن کار را با چه کیفیتی انجام دهد؟»، احتمالاً Non-Functional است.

تعریف دقیق‌تر

Functional Requirement رفتار، قابلیت، محاسبه، واکنش یا تبادل داده‌ای را تعریف می‌کند که سیستم باید انجام دهد. معمولاً یک Trigger، یک رفتار و یک نتیجه وجود دارد.

Trigger: مشتری دکمهٔ ثبت سفارش را انتخاب می‌کند.

رفتار: سیستم موجودی، نشانی و اطلاعات پرداخت را بررسی می‌کند.

نتیجه: سفارش ایجاد می‌شود و شمارهٔ پیگیری به مشتری نمایش داده می‌شود.

Functional Requirement فقط مربوط به صفحه و دکمه نیست. پردازش خودکار، ارتباط با سیستم خارجی و واکنش به Event نیز رفتار سیستم محسوب می‌شوند؛ مانند ارسال پیام پس از پرداخت موفق.

تفاوت Functional و Non-Functional

نوعپرسشمثال
Functionalسیستم چه کاری انجام دهد؟مشتری بتواند وضعیت سفارش خود را مشاهده کند.
Non-Functionalآن کار با چه کیفیت یا محدودیتی انجام شود؟وضعیت سفارش در کمتر از یک ثانیه نمایش داده شود.

این دو مکمل یکدیگرند. قابلیت مشاهدهٔ سفارش بدون Performance، Security و Availability مناسب ممکن است برای کاربر قابل استفاده نباشد.

چه چیزهایی Functional Requirement هستند؟

  • ورودی و خروجی: سیستم چه داده‌ای می‌گیرد و چه نتیجه‌ای برمی‌گرداند.
  • محاسبه: مبلغ نهایی، مالیات یا تخفیف چگونه محاسبه شود.
  • Workflow: سفارش از چه وضعیت‌هایی عبور کند.
  • Validation: چه داده‌ای معتبر یا نامعتبر است.
  • Authorization Rule: کدام نقش اجازهٔ انجام چه عملی را دارد.
  • Integration: سیستم چه اطلاعاتی برای درگاه پرداخت بفرستد و چگونه پاسخ را پردازش کند.
  • Notification: چه زمانی پیام، ایمیل یا اعلان ارسال شود.
  • Error Behavior: در خطاهای قابل پیش‌بینی چه واکنشی نشان داده شود.

Use Case چیست؟

Use Case تعامل گام‌به‌گام یک Actor با سیستم برای رسیدن به یک هدف را توضیح می‌دهد. Actor می‌تواند انسان یا یک سیستم دیگر باشد.

Use Case: ثبت سفارش

Actor: مشتری

پیش‌شرط: سبد خرید خالی نیست و نشانی معتبر ثبت شده است.

  1. مشتری سبد خرید را تأیید می‌کند.
  2. سیستم موجودی و قیمت را دوباره بررسی می‌کند.
  3. مشتری روش پرداخت را انتخاب می‌کند.
  4. سیستم پرداخت را انجام می‌دهد.
  5. سیستم سفارش را ایجاد و شمارهٔ پیگیری را نمایش می‌دهد.

جریان جایگزین: اگر موجودی کافی نباشد، سفارش ایجاد نمی‌شود و اقلام ناموجود نمایش داده می‌شوند.

Use Case برای رفتارهای چندمرحله‌ای مفید است، چون مسیر موفق و مسیرهای خطا یا جایگزین را کنار هم نشان می‌دهد.

User Story چیست؟

User Story یک نیاز را کوتاه و از دید کاربر بیان می‌کند. قالب رایج آن چنین است:

به‌عنوان مشتری، می‌خواهم سفارش خود را پیگیری کنم تا بدانم چه زمانی تحویل داده می‌شود.

User Story نقطهٔ شروع گفتگو است، نه تمام Specification. جملهٔ بالا هنوز دربارهٔ وضعیت‌ها، Permission، خطا و معیار پذیرش اطلاعات کافی ندارد.

Acceptance Criteria چیست؟

Acceptance Criteria شرایط قابل بررسی برای پذیرفتن یک Requirement را مشخص می‌کند. این معیارها به Product، Development و Test کمک می‌کنند برداشت مشترکی از رفتار مورد انتظار داشته باشند.

برای پیگیری سفارش

  • مشتری فقط سفارش‌های متعلق به حساب خودش را می‌بیند.
  • وضعیت نمایش‌داده‌شده یکی از ثبت‌شده، درحال آماده‌سازی، ارسال‌شده، تحویل‌شده یا لغوشده است.
  • اگر شمارهٔ سفارش وجود نداشته باشد، پیام قابل‌فهم نمایش داده می‌شود.
  • تغییر وضعیت پس از Refresh نیز باقی می‌ماند.

هر معیار باید قابل Test باشد. عبارت‌هایی مانند «صفحه خوب کار کند» معیار مناسبی نیستند، چون نتیجهٔ مشخصی برای بررسی ندارند.

Business Rule چیست؟

Business Rule قانونی از Domain است که رفتار سیستم باید از آن پیروی کند. این Ruleها حتی اگر Technology عوض شود، معمولاً همچنان معتبر می‌مانند.

  • سفارش پس از شروع آماده‌سازی قابل لغو نیست.
  • تخفیف مشتری جدید فقط یک بار قابل استفاده است.
  • مبلغ سفارش برای ارسال رایگان باید حداقل ۵۰۰ هزار تومان باشد.

Business Rule ممکن است روی چند Functional Requirement اثر بگذارد. مثلاً قانون لغو هم روی API لغو، هم UI، هم بازپرداخت و هم Testها اثر دارد.

چگونه Functional Requirement خوبی بنویسیم؟

  1. Actor را مشخص کنید: چه کسی یا چه سیستمی رفتار را شروع می‌کند؟
  2. Trigger را بنویسید: چه رویدادی باعث اجرای رفتار می‌شود؟
  3. رفتار مورد انتظار را روشن کنید: سیستم دقیقاً چه کاری انجام می‌دهد؟
  4. نتیجه را مشخص کنید: چه داده یا وضعیت قابل مشاهده‌ای ایجاد می‌شود؟
  5. شرایط خطا را اضافه کنید: اگر داده نامعتبر یا Dependency قطع بود چه می‌شود؟
  6. معیار پذیرش بنویسید: چگونه تشخیص می‌دهیم رفتار درست ساخته شده است؟

ضعیف: «سیستم پرداخت داشته باشد.»

روشن‌تر: «مشتری بتواند سفارش ثبت‌شده را از طریق درگاه بانکی پرداخت کند. پس از پاسخ موفق بانک، سیستم وضعیت پرداخت را موفق و سفارش را تأیید کند. پاسخ تکراری بانک نباید پرداخت دوم ایجاد کند.»

Edge Caseها را فراموش نکنید

Edge Case حالتی است که در مسیر عادی کمتر دیده می‌شود، اما سیستم باید رفتار مشخصی برای آن داشته باشد.

  • موجودی بین مشاهدهٔ سبد و ثبت سفارش تمام شود.
  • کاربر دکمهٔ پرداخت را دو بار انتخاب کند.
  • بانک پرداخت را موفق اعلام کند، اما پاسخ به برنامه نرسد.
  • قیمت یک محصول هنگام بازبودن سبد تغییر کند.
  • سفارش هم‌زمان توسط مشتری و پشتیبانی لغو شود.

بررسی Edge Caseها فقط کار Tester نیست. این حالت‌ها می‌توانند روی Transaction، Idempotency، State Model و Architecture اثر بگذارند.

نقش AI در تحلیل Functional Requirements

AI می‌تواند پیش‌نویس و تحلیل را سریع‌تر کند:

  • تبدیل توضیح خام به فهرست رفتارهای سیستم
  • پیشنهاد Actor و Use Case
  • تولید Acceptance Criteria اولیه
  • پیشنهاد مسیرهای جایگزین و Edge Case
  • پیدا کردن واژه‌های مبهم یا تناقض‌ها
Human Review ضروری است: AI ممکن است Business Rule نادرست بسازد یا یک فرض را به‌جای Requirement واقعی بنویسد. Stakeholder و Domain Expert باید صحت خروجی را تأیید کنند.

اشتباهات رایج

  • نوشتن UI به‌جای نیاز: «یک دکمهٔ سبز بسازید» راهکار UI است؛ نیاز اصلی شاید «امکان تأیید سفارش» باشد.
  • ندیدن مسیر خطا: فقط Happy Path نوشته می‌شود و رفتار شکست نامشخص می‌ماند.
  • ترکیب چند رفتار بزرگ: Requirement بسیار بزرگ فهم، تخمین و Test را دشوار می‌کند.
  • استفاده از عبارت مبهم: واژه‌هایی مثل «مناسب»، «راحت» و «در صورت نیاز» بدون تعریف دقیق‌اند.
  • نادیده‌گرفتن Business Rule: رفتار ساخته می‌شود، اما با قوانین واقعی Domain سازگار نیست.

جمع‌بندی

  • Functional Requirement می‌گوید سیستم چه رفتار یا قابلیتی ارائه دهد.
  • Use Case جریان کامل، User Story نیاز کوتاه کاربر و Acceptance Criteria شرایط پذیرش را بیان می‌کند.
  • Business Rule قوانین Domain را تعریف می‌کند و ممکن است روی چند Feature اثر بگذارد.
  • Requirement مناسب باید مسیر موفق، خطاها و Edge Caseهای مهم را روشن کند.
  • AI دستیار خوبی برای تولید سؤال و پیش‌نویس است، اما تصمیم نهایی به بررسی انسان نیاز دارد.
