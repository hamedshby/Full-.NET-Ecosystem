Fundamentals

Stateless vs Stateful

یکی از مهم‌ترین تصمیم‌های System Design این است که State کجا نگهداری شود. در سیستم Stateless هر Request تا حد ممکن مستقل از Requestهای قبلی پردازش می‌شود، اما در سیستم Stateful یک Node یا Service بخشی از State مربوط به Session، Connection یا Business Process را نگه می‌دارد. این تفاوت مستقیماً روی Scalability، Availability، Failover و Complexity اثر می‌گذارد.

از یک مثال ساده شروع کنیم

فرض کنید کاربر وارد یک سایت شده است و اطلاعات Login او فقط در Memory همان Server نگهداری می‌شود. 

Request 1
User Login
↓
Server A

Session stored in Server A memory

حالا Request بعدی کاربر به Server B می‌رسد: 

Request 2
↓
Server B

Session not found

این نمونه‌ای از وابستگی به State محلی است. اگر State فقط روی یک Node باشد، Load Balancing و Failover پیچیده‌تر می‌شوند.

مدل ذهنی: Stateless یعنی هر کارمند بتواند با اطلاعات موجود در Request یا Storage مشترک کار مشتری را انجام دهد. Stateful یعنی مشتری باید دوباره به همان کارمندی مراجعه کند که پرونده‌اش را روی میز خود نگه داشته است.

State چیست؟

State اطلاعاتی است که وضعیت فعلی یک User، Session، Connection، Process یا Business Entity را مشخص می‌کند.

نمونه‌های State:

  • Session کاربر
  • Shopping Cart
  • Authentication State
  • Current Workflow Step
  • Connection State
  • Payment Status
  • Game State
  • Consumer Offset
نکته: Stateless به این معنی نیست که «سیستم هیچ Stateی ندارد». هر سیستم واقعی State دارد؛ سؤال اصلی این است که State کجا نگهداری می‌شود.

Stateless چیست؟

یک Service Stateless است اگر برای پردازش Request بعدی، وابسته به اطلاعات موقتی ذخیره‌شده در Memory همان Instance نباشد.

مثال

Client
↓
Request + JWT
↓
Any API Instance
↓
Database / Redis

هر Instance می‌تواند Request را پردازش کند، چون اطلاعات مورد نیاز داخل Request یا در Storage مشترک قرار دارد.

نمونه‌های Stateless مناسب:

  • REST API
  • ASP.NET Core Web API
  • Authentication با JWT
  • Workerهایی که Job مستقل پردازش می‌کنند
  • Microserviceهایی که State دائمی را در Database نگه می‌دارند

Stateful چیست؟

یک Service Stateful است اگر State مهمی را در خود Instance نگه دارد و Request یا Connection بعدی برای ادامهٔ کار به همان State وابسته باشد. 

User
↓
Server A

Server A memory:
SessionId = 123
Cart = ...
WorkflowStep = 4

اگر Server A از بین برود و State جای دیگری ذخیره نشده باشد، اطلاعات مربوط به Session یا Process نیز از دست می‌رود.

نمونه‌های Stateful:

  • In-Memory Session
  • WebSocket Connection
  • Game Server با State فعال بازیکنان
  • Database
  • Message Broker
  • Stateful Stream Processing

مقایسه Stateless و Stateful

ویژگی Stateless Stateful
وابستگی به Instance کم بیشتر
Scale Out ساده‌تر پیچیده‌تر
Failover ساده‌تر نیازمند انتقال یا Replication State
Load Balancing ساده ممکن است Session Affinity لازم شود
Local Memory برای Business State حیاتی استفاده نمی‌شود ممکن است State مهم نگهداری شود
پیچیدگی Storage مشترک ممکن است بیشتر شود State نزدیک به Process است
نمونه REST API Database / WebSocket Session

چرا Stateless برای Horizontal Scaling مناسب‌تر است؟

اگر Service Stateless باشد، Load Balancer می‌تواند هر Request را به هر Instance سالم ارسال کند.

Client
→
Load Balancer
→
API 1
API 2
API 3

چون Instanceها Business State مهمی در Memory خود نگه نمی‌دارند، اضافه یا حذف‌کردن Instance ساده‌تر است.

اگر API 2 Down شود، Request بعدی می‌تواند به API 1 یا API 3 برود.

اصل مهم: Stateless Design یکی از پایه‌های اصلی Elastic Scaling در Cloud و Kubernetes است.

State را کجا نگه داریم؟

در معماری Stateless، State حذف نمی‌شود؛ معمولاً به Storage بیرونی منتقل می‌شود.

API 1
API 2
API 3
→
Redis / Database

بسته به نوع State می‌توان از این موارد استفاده کرد:

  • Database: State دائمی و Business Data
  • Redis: Session، Cache، Temporary State
  • Object Storage: فایل و Blob
  • Message Broker: Event یا Work Queue
  • Distributed Cache: دادهٔ موقت مشترک

Session در سیستم Stateless

اگر Session در Memory یک Server ذخیره شود، Application عملاً Stateful می‌شود.

In-Memory Session

Server A
Session 101
Session 102

Server B
Session 201
Session 202

یک راه بهتر، نگهداری Session در Storage مشترک است: 

Server A ─┐
Server B ─┼──> Redis Session Store
Server C ─┘

در این حالت هر Instance می‌تواند Session را بازیابی کند.

JWT و Stateless Authentication

در بسیاری از APIها Authentication با Token انجام می‌شود. Token اطلاعات لازم برای شناسایی User را همراه Request حمل می‌کند. 

Client

Authorization:
Bearer eyJhbGciOi...

↓

Any API Instance

↓

Validate token

Server لازم نیست Session Authentication را برای هر User در Memory نگه دارد.

نکته: JWT همه‌چیز را Stateless نمی‌کند. مثلاً Revocation، Permissionهای پویا یا Business State ممکن است همچنان به Database یا Cache نیاز داشته باشند.

مثال در ASP.NET Core

برای Scale Out مناسب، بهتر است Business State مهم را داخل Singleton یا Static Memory نگهداری نکنیم.

نمونهٔ مشکل‌دار

public static Dictionary<string, Cart> Carts = new();

این Dictionary فقط روی همان Process وجود دارد. اگر Request بعدی به Instance دیگری برسد، Cart دیده نمی‌شود.

راه بهتر برای State مشترک

builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = redisConnectionString;
});

یا اگر State دائمی است، آن را در Database نگهداری می‌کنیم.

Sticky Session چیست؟

Sticky Session یا Session Affinity یعنی Load Balancer تلاش کند Requestهای یک User را همیشه به همان Instance ارسال کند.

User A
→
Server 1
User B
→
Server 2

این روش می‌تواند Application Stateful را موقتاً قابل استفاده کند، اما مشکلاتی دارد:

  • Failure همان Instance
  • Load Distribution نامتعادل
  • Scale Down دشوارتر
  • Migration سخت‌تر
  • وابستگی User به یک Node

برای APIهای معمول Backend، اگر امکان‌پذیر باشد Stateless Design معمولاً انتخاب تمیزتری است.

Failure در Stateful Service

یکی از چالش‌های اصلی Stateful Service این است که با Failure Node چه اتفاقی برای State می‌افتد. 

Node A

State:
X = 100

↓

Node crashes

↓

Where is X?

برای جلوگیری از از دست رفتن State ممکن است نیاز داشته باشیم:

  • Replication
  • Persistent Storage
  • Snapshot
  • Write-Ahead Log
  • Failover
  • Leader Election

به همین دلیل Scale و Recovery در Stateful System معمولاً پیچیده‌تر است.

آیا Stateful بد است؟

خیر. Stateful Design ذاتاً بد نیست. بعضی Componentها باید State داشته باشند.

مثلاً:

  • Database باید State داده‌ها را نگه دارد.
  • RabbitMQ باید Messageهای تحویل‌نشده را نگه دارد.
  • Kafka باید Log و Offsetها را نگه دارد.
  • WebSocket Server Connectionهای فعال دارد.
  • Game Server ممکن است State لحظه‌ای بازی را نگه دارد.
اصل مهم: سؤال درست این نیست که «Stateful خوب است یا Stateless؟» سؤال درست این است که «State در کدام Component باید قرار بگیرد و چگونه محافظت شود؟»

WebSocket چرا Stateful‌تر است؟

در HTTP معمولی Request مستقل است. اما WebSocket یک Connection طولانی‌مدت بین Client و یک Server ایجاد می‌کند. 

Client
   |
   | persistent connection
   |
Server A

اگر Server A Down شود، Connection قطع می‌شود و Client باید Reconnect کند.

در سیستم‌های بزرگ ممکن است برای مدیریت Connection Mapping، Presence یا Pub/Sub از Redis یا Broker استفاده شود.

Database یک سیستم Stateful است

Database ذاتاً Stateful است چون دادهٔ دائمی را نگهداری می‌کند.

به همین دلیل Horizontal Scaling Database سخت‌تر از Web API است.

موضوعاتی که باید حل شوند:

  • Replication
  • Consistency
  • Failover
  • Partitioning
  • Leader / Replica
  • Backup / Recovery

مثال

Stateless API Instances
        ↓
   Stateful Database

این یکی از رایج‌ترین معماری‌هاست: Application Layer Stateless و Data Layer Stateful.

مثال کامل در Payment System

Clients
→
Load Balancer
→
Payment API × N
→
SQL Server
+
Redis
+
RabbitMQ

در یک Payment System بهتر است Payment API تا حد امکان Stateless باشد.

  • Payment State در SQL Server ذخیره شود.
  • Cache یا Temporary State در Redis قرار گیرد.
  • Request اطلاعات Authentication را همراه خود داشته باشد.
  • هیچ Transaction State مهمی فقط در Memory یک Pod نگهداری نشود.
  • Outbox Message در Storage پایدار نگهداری شود.

سناریوی Failure

Request
↓
Payment API Pod A
↓
Save payment in SQL
↓
Pod A crashes

Next request
↓
Payment API Pod B
↓
Reads payment state from SQL

چون State در SQL Server است، از بین رفتن Pod A باعث از بین رفتن Business State نمی‌شود.

Stateless و Stateful در Kubernetes

Kubernetes برای Stateless Workload معمولاً از Deployment استفاده می‌کند. 

Deployment
↓
Pod 1
Pod 2
Pod 3

Pods can be replaced freely

برای Workloadهای Stateful، معمولاً نیاز به Persistent Storage، Stable Identity یا StatefulSet داریم. 

StatefulSet

db-0
db-1
db-2

Stable identity
Persistent volumes
نکته: StatefulSet یک Application را به‌صورت جادویی Reliable نمی‌کند؛ Replication و Consistency باید توسط خود سیستم یا Database طراحی شوند.

Trade-offها

  • Stateless vs Network: انتقال State به Redis/Database باعث Remote Call بیشتر می‌شود.
  • Stateless vs Simplicity of Scale: Storage مشترک Complexity دارد، اما Scale Out Application را ساده می‌کند.
  • Stateful vs Performance: Local State می‌تواند سریع باشد، ولی Failure و Migration پیچیده‌تر می‌شوند.
  • Sticky Session vs Flexibility: Stateful Session را ساده می‌کند ولی Load Balancing و Failover را محدود می‌کند.
  • Replication vs Consistency: Replicate کردن State Availability را افزایش می‌دهد ولی هماهنگی State را پیچیده می‌کند.

اشتباهات رایج

  • فکر کردن Stateless یعنی سیستم هیچ Stateی ندارد
  • ذخیره Business State مهم در Static یا Singleton Memory
  • وابسته‌کردن Session به یک Pod بدون نیاز واقعی
  • استفاده از Sticky Session برای پوشاندن طراحی ضعیف
  • استفاده از Redis برای هر نوع State بدون توجه به Durability
  • از دست دادن State هنگام Restart Container
  • فرض اینکه JWT همهٔ State سیستم را حذف می‌کند
  • نادیده گرفتن Replication و Recovery در Stateful Componentها

چطور تصمیم بگیریم State کجا باشد؟

برای هر State این سؤال‌ها را بپرسید:

  1. آیا State باید بعد از Restart باقی بماند؟
  2. آیا چند Instance باید آن را ببینند؟
  3. آیا از دست رفتن آن قابل قبول است؟
  4. Consistency چقدر مهم است؟
  5. Latency دسترسی چقدر حساس است؟
  6. حجم State چقدر است؟
  7. آیا State فقط موقتی است؟
نوع State Storage احتمالی
Payment Transaction Database
User Session Redis / Distributed Cache
Authentication Token Client + Token Validation
Temporary Cache Redis
File Object Storage
Persistent Message Message Broker

در مصاحبه System Design چطور درباره Stateless/Stateful صحبت کنیم؟

اگر از شما پرسیدند «چطور این API را Scale می‌کنی؟»، یکی از اولین سؤال‌ها باید این باشد که آیا Application State محلی دارد یا نه.

  1. مشخص کنید چه Stateهایی وجود دارند.
  2. Business State و Temporary State را جدا کنید.
  3. Application Layer را تا حد امکان Stateless نگه دارید.
  4. Persistent State را در Database قرار دهید.
  5. Shared Temporary State را در Redis یا Distributed Cache قرار دهید.
  6. Load Balancer را بدون وابستگی به Instance خاص طراحی کنید.
  7. Sticky Session را فقط در صورت نیاز واقعی استفاده کنید.
  8. برای Stateful Componentها Replication و Failover را توضیح دهید.

نمونهٔ پاسخ کوتاه

«برای Scale Out کردن API سعی می‌کنم Application Layer Stateless باشد. Business State را در Database و Shared Temporary State را در Redis نگه می‌دارم. در نتیجه هر Request می‌تواند به هر Instance سالم برسد و Load Balancer نیازی به Sticky Session ندارد. Stateful Componentهایی مثل Database را جداگانه با Replication، Failover و Persistent Storage طراحی می‌کنم.»

تمرین کوتاه

یک ASP.NET Core API سه Instance دارد. Shopping Cart کاربران در Memory هر Instance ذخیره می‌شود. بعد از اضافه‌شدن Load Balancer، کاربران گاهی Cart خالی می‌بینند. بهترین راه‌حل معماری چیست؟

  1. افزایش CPU هر Instance
  2. انتقال Cart State به Shared Store مانند Redis یا Database
  3. افزایش Timeout
  4. کاهش تعداد Instanceها به یک عدد
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. Cart به State محلی هر Instance وابسته شده است. انتقال آن به یک Shared Store باعث می‌شود هر Instance بتواند Request بعدی User را پردازش کند و Scale Out بدون وابستگی به یک Node خاص انجام شود.

جمع‌بندی

  • State اطلاعاتی است که وضعیت فعلی User، Session، Process یا Business Entity را مشخص می‌کند.
  • Stateless یعنی Instance برای Request بعدی به State محلی خودش وابسته نباشد.
  • Stateful یعنی بخشی از State داخل Node یا Service نگهداری و برای ادامهٔ کار لازم باشد.
  • Stateless Design Scale Out و Failover را ساده‌تر می‌کند.
  • Stateless به معنی نبود State نیست؛ State معمولاً به Database یا Redis منتقل می‌شود.
  • Sticky Session می‌تواند Stateful Session را مدیریت کند ولی محدودیت‌هایی دارد.
  • Database و Message Broker نمونه‌های طبیعی Stateful Component هستند.
  • Application Layer اغلب Stateless و Data Layer Stateful طراحی می‌شود.
  • در ASP.NET Core نباید Business State مهم فقط در Static یا Process Memory ذخیره شود.
  • در Payment System بهتر است State تراکنش در Storage پایدار باشد، نه داخل یک Pod.
