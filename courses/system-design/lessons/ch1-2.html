فصل 1 از ۱۰

Fundamentals

Availability

Availability یعنی سیستم در زمانی که کاربر به آن نیاز دارد، قابل‌دسترسی باشد و بتواند سرویس مورد انتظار را ارائه دهد. در این درس یاد می‌گیریم Availability را چگونه اندازه بگیریم، چه عواملی آن را کاهش می‌دهند و چگونه با Redundancy، Failover، Health Check و حذف Single Point of Failure یک سیستم Highly Available طراحی کنیم.

از یک سیستم پرداخت شروع کنیم

فرض کنید یک درگاه پرداخت در بیشتر ساعات روز کاملاً سالم است، اما هر بار که سرور اصلی Database از دسترس خارج می‌شود، کل Payment API نیز متوقف می‌شود. ممکن است این خرابی فقط ۳۰ دقیقه طول بکشد، ولی در همان مدت هیچ کاربری نمی‌تواند پرداخت انجام دهد.

اینجا مسئله Performance نیست. ممکن است در زمان سلامت، هر Request در کمتر از ۱۰۰ میلی‌ثانیه پاسخ بگیرد؛ اما وقتی یکی از اجزای حیاتی خراب می‌شود، کل سرویس دیگر قابل استفاده نیست. این مسئله به Availability مربوط است.

مدل ذهنی: یک فروشگاه را تصور کنید که کارکنان سریع و حرفه‌ای دارد، اما در ورودی فقط یک در وجود دارد. اگر همان یک در خراب شود، سرعت کارکنان دیگر اهمیتی ندارد. آن در یک Single Point of Failure است.

Availability دقیقاً چیست؟

Availability نشان می‌دهد یک سرویس چه درصدی از زمان مورد انتظار، آمادهٔ ارائهٔ خدمت بوده است. تعریف سادهٔ آن:

فرمول ساده

Availability = Uptime / Total Time × 100

اگر یک سرویس در یک بازهٔ ۱۰۰ ساعته، ۹۹ ساعت قابل استفاده و ۱ ساعت Down باشد، Availability آن تقریباً ۹۹٪ است.

اما در معماری واقعی فقط روشن‌بودن Process کافی نیست. اگر API پاسخ 200 بدهد ولی نتواند عملیات اصلی را انجام دهد، از نگاه کاربر سرویس واقعاً Available نیست. بنابراین Availability باید بر اساس قابلیت ارائهٔ سرویس مورد انتظار تعریف شود.

تعریف قابل‌اندازه‌گیری

«Payment API باید در هر ماه حداقل ۹۹٫۹۹٪ از زمان قادر باشد درخواست پرداخت معتبر را دریافت و پردازش اولیه کند.»

عددهای 99.9% و 99.99% چه معنایی دارند؟

در Availability معمولاً از تعداد Nines صحبت می‌شود. تفاوت ظاهراً کوچک بین ۹۹٫۹٪ و ۹۹٫۹۹٪، در میزان Downtime مجاز تفاوت بزرگی ایجاد می‌کند.

Availability Downtime تقریبی در سال Downtime تقریبی در ماه
99% حدود 3 روز و 15 ساعت حدود 7 ساعت و 18 دقیقه
99.9% حدود 8 ساعت و 46 دقیقه حدود 44 دقیقه
99.99% حدود 52 دقیقه و 36 ثانیه حدود 4 دقیقه و 23 ثانیه
99.999% حدود 5 دقیقه و 16 ثانیه حدود 26 ثانیه
نکته مهم: هر Nine اضافه معمولاً هزینه و پیچیدگی معماری را به‌طور قابل‌توجهی افزایش می‌دهد. برای هر سیستم نباید بدون دلیل هدف 99.999% تعیین کرد.

SLA، SLO و SLI

  • SLI — Service Level Indicator: مقداری که واقعاً اندازه‌گیری می‌کنیم؛ برای مثال درصد Requestهای موفق.
  • SLO — Service Level Objective: هدف داخلی یا فنی؛ مثلاً Availability سرویس حداقل ۹۹٫۹۹٪ باشد.
  • SLA — Service Level Agreement: تعهد رسمی یا قراردادی به مشتری که ممکن است در صورت نقض، پیامد مالی یا حقوقی داشته باشد.

مثال

SLI فعلی = 99.97%
SLO داخلی = 99.99%
SLA با مشتری = 99.9%

معمولاً SLO داخلی باید سخت‌گیرانه‌تر از SLA باشد تا قبل از نقض تعهد مشتری، فضای عملیاتی برای تیم وجود داشته باشد.

چه چیزهایی Availability را کاهش می‌دهند؟

خرابی همیشه به معنی خاموش‌شدن یک سرور نیست. Failure Modeهای مختلفی می‌توانند سرویس را برای کاربر غیرقابل استفاده کنند:

  • Crash شدن Application: Process یا Container متوقف می‌شود.
  • Database Failure: Database اصلی از دسترس خارج می‌شود.
  • Network Failure: ارتباط میان Serviceها یا Data Centerها قطع می‌شود.
  • Dependency Failure: سرویس خارجی مانند بانک، PSP یا Identity Provider Down می‌شود.
  • Resource Exhaustion: Connection Pool، Thread Pool، Memory یا Disk پر می‌شود.
  • Bad Deployment: نسخهٔ جدید باعث خطا در همهٔ Instanceها می‌شود.
  • Overload: حجم درخواست بیشتر از ظرفیت سیستم می‌شود و سرویس عملاً غیرقابل استفاده می‌گردد.
  • Configuration Error: یک Secret، Certificate، DNS یا Connection String اشتباه سرویس را از کار می‌اندازد.

هدف طراحی High Availability این نیست که «هیچ چیزی خراب نشود»؛ چنین هدفی واقع‌بینانه نیست. هدف این است که خرابی یک جزء باعث از دسترس خارج‌شدن کل سیستم نشود.

Single Point of Failure

Single Point of Failure یا SPOF جزئی است که اگر خراب شود، سرویس اصلی متوقف می‌شود.

در این معماری اگر API Server یا Database از دسترس خارج شود، کل سیستم Down می‌شود. برای افزایش Availability معمولاً اجزای حیاتی را Redundant می‌کنیم.

سؤال طراحی: هر بار در دیاگرام فقط یک Instance از یک Component حیاتی می‌بینید، بپرسید: «اگر این Component همین الآن Down شود، چه اتفاقی می‌افتد؟»

Redundancy؛ اولین ابزار High Availability

Redundancy یعنی بیش از یک نمونه از یک جزء مهم داشته باشیم تا خرابی یک نمونه باعث توقف کامل سرویس نشود.

  • چند Application Instance پشت Load Balancer
  • Database Primary همراه Replica یا Secondary
  • چند Message Broker Node در Cluster
  • چند Availability Zone
  • چند DNS Server یا Load Balancer در لایهٔ زیرساخت

اما صرفاً داشتن دو Server کافی نیست. سیستم باید بتواند تشخیص دهد کدام Node سالم است و Traffic را به Node سالم منتقل کند. اینجاست که Health Check و Failover اهمیت پیدا می‌کنند.

Failover چیست؟

Failover یعنی وقتی Component اصلی خراب می‌شود، سرویس به Instance یا Component جایگزین منتقل شود.

مدل نحوه کار مزیت Trade-off
Active-Passive یک Node فعال است و Node دوم آمادهٔ جایگزینی سادگی بیشتر بخشی از ظرفیت در حالت عادی بدون استفاده است و Failover زمان می‌برد
Active-Active چند Node هم‌زمان Traffic می‌گیرند استفاده بهتر از ظرفیت و Failover سریع‌تر هماهنگی State و Consistency پیچیده‌تر می‌شود

در Application Layer معمولاً Active-Active ساده‌تر است، به‌خصوص اگر Instanceها Stateless باشند. در Data Layer انتخاب Active-Passive یا Active-Active بسیار وابسته به نوع Database و نیازهای Consistency است.

Health Check؛ از کجا بفهمیم Instance سالم است؟

Load Balancer یا Orchestrator باید بداند یک Instance هنوز قادر به سرویس‌دهی هست یا نه. برای همین معمولاً Endpointهای Health Check تعریف می‌شوند.

  • Liveness: آیا Process زنده است؟ اگر نه، Container یا Process Restart شود.
  • Readiness: آیا این Instance همین الآن آمادهٔ دریافت Traffic است؟ اگر نه، موقتاً از Load Balancer خارج شود.

نمونه در ASP.NET Core

builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString);

app.MapHealthChecks("/health/live");
app.MapHealthChecks("/health/ready");

در Kubernetes معمولاً Liveness Probe و Readiness Probe از همین Endpointها استفاده می‌کنند. اگر Readiness شکست بخورد، Pod لزوماً Restart نمی‌شود؛ فقط تا زمان سلامت از دریافت Traffic کنار گذاشته می‌شود.

نکته: Health Check نباید آن‌قدر سنگین باشد که خودش به Dependencyها فشار ایجاد کند. همچنین Liveness را نباید به هر Dependency خارجی وابسته کرد؛ وگرنه خرابی یک سرویس خارجی می‌تواند باعث Restart بی‌پایان همهٔ Instanceها شود.

Availability فقط با Server دوم ساخته نمی‌شود

در سیستم‌های Distributed، Availability به نحوهٔ مدیریت Failure در ارتباط میان Serviceها نیز وابسته است.

  • Timeout: Request نباید برای همیشه منتظر Dependency بماند.
  • Retry: خطاهای موقتی را می‌توان با Retry کنترل‌شده دوباره امتحان کرد.
  • Circuit Breaker: هنگام خرابی شدید Dependency از ارسال درخواست‌های بیشتر جلوگیری می‌کند.
  • Bulkhead: خرابی یا فشار یک Dependency نباید تمام Thread/Connectionهای سیستم را مصرف کند.
  • Rate Limiting: از فروپاشی سیستم هنگام Overload جلوگیری می‌کند.
  • Queue: می‌تواند بخشی از Workload را موقتاً Buffer کند تا Consumer بعداً آن را پردازش کند.

این الگوها معمولاً زیر عنوان Resilience بررسی می‌شوند و مستقیماً روی Availability سیستم اثر می‌گذارند.

Graceful Degradation؛ همه یا هیچ نباشد

گاهی یک Dependency غیرحیاتی خراب می‌شود. لازم نیست کل سیستم را Down کنیم. بهتر است قابلیت‌های فرعی را موقتاً محدود کنیم ولی مسیر اصلی Business را حفظ کنیم.

مثال فروشگاه

اگر Recommendation Service Down شود، صفحهٔ محصول همچنان نمایش داده شود ولی بخش «پیشنهادهای مشابه» حذف شود.

مثال Payment

اگر Notification Service Down باشد، تراکنش موفق نباید Failed اعلام شود. Payment ثبت می‌شود و Notification Event برای پردازش بعدی در Queue باقی می‌ماند.

این تصمیم نیازمند تشخیص Dependencyهای Critical و Non-Critical است.

Availability در Database

Application ممکن است چند Instance داشته باشد، اما اگر همه به یک Database بدون Failover وصل شوند، Database همچنان SPOF است.

راهکارهای رایج بسته به Database می‌توانند شامل این موارد باشند:

  • Primary + Secondary/Replica
  • Automatic Failover
  • Replication
  • Multi-AZ Deployment
  • Backup و Restore برای Disaster Recovery

برای SQL Server نمونه‌هایی مانند Always On Availability Groups می‌توانند برای افزایش Availability استفاده شوند. اما باید Failover، Connection String، Retry Policy و رفتار Application هنگام تغییر Primary نیز طراحی شوند.

نکته: Replica داشتن با Backup داشتن یکی نیست. Replica برای ادامهٔ سرویس‌دهی هنگام خرابی مفید است؛ Backup برای بازیابی از حذف، Corruption یا Disaster استفاده می‌شود.

مثال واقعی: High Availability در Payment System

Client
→
Load Balancer / API Gateway
→
Payment Service × N
→
SQL Server HA
+
RabbitMQ Cluster

برای افزایش Availability می‌توانیم:

  1. چند Instance از Payment Service داشته باشیم و آن‌ها را Stateless نگه داریم.
  2. Load Balancer فقط Traffic را به Instanceهای Ready ارسال کند.
  3. Database دارای Replica و Failover باشد.
  4. Eventهای غیرهمزمان مانند Notification و Reporting را از طریق Message Broker جدا کنیم.
  5. برای ارتباط با بانک یا PSP از Timeout، Retry محدود و Circuit Breaker استفاده کنیم.
  6. درخواست‌ها را Idempotent طراحی کنیم تا Retry باعث تراکنش تکراری نشود.
  7. Metric، Log و Alert داشته باشیم تا Failure سریع تشخیص داده شود.

یک Failure Scenario مهم

Payment Service درخواست را به بانک می‌فرستد، بانک تراکنش را انجام می‌دهد، اما قبل از رسیدن Response ارتباط قطع می‌شود. اگر Application کورکورانه Retry کند ممکن است عملیات دوباره انجام شود.

بنابراین Availability در Payment فقط به «دوباره امتحان کردن» محدود نیست؛ Retry باید همراه Idempotency، Transaction Status Query و طراحی صحیح State Machine باشد.

RTO و RPO در Disaster Recovery

High Availability خرابی‌های معمول را مدیریت می‌کند، اما برای Disasterهای بزرگ مانند از دست رفتن کامل Region یا Data Center، باید Recovery نیز طراحی شود.

  • RTO — Recovery Time Objective: حداکثر زمانی که برای بازگرداندن سرویس قابل قبول است.
  • RPO — Recovery Point Objective: حداکثر میزان داده‌ای که از نظر زمانی قابل از دست رفتن است.

مثال

RTO = 15 دقیقه یعنی بعد از Disaster باید حداکثر طی ۱۵ دقیقه سرویس برگردد.
RPO = 1 دقیقه یعنی نباید بیش از یک دقیقه داده از دست برود.

هرچه RTO و RPO کوچک‌تر باشند، معمولاً هزینهٔ Infrastructure، Replication و Automation بیشتر می‌شود.

Availability با Reliability یکی نیست

مفهوم سؤال اصلی مثال
Availability آیا سرویس الآن قابل استفاده است؟ API در 99.99% زمان قابل دسترس است
Reliability آیا سرویس در طول زمان درست و بدون Failure کار می‌کند؟ پرداخت موفق بدون Duplicate و Corruption ثبت می‌شود

یک سیستم ممکن است Availability بالایی داشته باشد ولی Reliability ضعیفی داشته باشد؛ مثلاً همیشه پاسخ بدهد اما گاهی نتیجهٔ اشتباه تولید کند.

Trade-offهای High Availability

  • هزینه: Server، Replica، Zone و Region اضافی هزینه دارند.
  • پیچیدگی: Failover، Replication، Routing و Recovery نیازمند طراحی و تست هستند.
  • Consistency: Replicaها ممکن است دقیقاً در یک لحظه یک State یکسان نداشته باشند.
  • Operational Complexity: سیستم Distributed Failure Modeهای بیشتری دارد.
  • Performance: برخی روش‌های Replication همزمان می‌توانند Latency عملیات Write را افزایش دهند.

هدف این نیست که هر Component را به پیچیده‌ترین شکل ممکن Redundant کنیم. ابتدا باید مشخص کنیم کدام مسیر Business واقعاً Critical است و Downtime آن چه هزینه‌ای دارد.

اشتباهات رایج

  • فقط چند Instance ساختن: اگر Database یا Message Broker هنوز SPOF باشد، سیستم Highly Available نیست.
  • نداشتن Health Check درست: Load Balancer ممکن است Traffic را به Instance خراب بفرستد.
  • Retry بدون محدودیت: می‌تواند خرابی کوچک را به Retry Storm و خرابی بزرگ تبدیل کند.
  • Retry بدون Idempotency: در Payment و Order ممکن است عملیات تکراری ایجاد کند.
  • اعتماد به Failover بدون تست: Failover فقط وقتی قابل اعتماد است که عملاً و دوره‌ای آزمایش شده باشد.
  • یکی گرفتن Backup و High Availability: Backup جای Replica و Failover را نمی‌گیرد.
  • انتخاب Availability غیرواقعی: 99.999% بدون نیاز Business، هزینه و Complexity زیادی ایجاد می‌کند.

در مصاحبه System Design چطور درباره Availability صحبت کنیم؟

اگر از شما خواستند یک سیستم Highly Available طراحی کنید، می‌توانید با این ترتیب جلو بروید:

  1. Availability هدف را مشخص کنید: مثلاً 99.99%.
  2. Critical Path سیستم را مشخص کنید.
  3. SPOFها را پیدا کنید.
  4. برای Componentهای حیاتی Redundancy در نظر بگیرید.
  5. Health Check و Failover را توضیح دهید.
  6. Failure سرویس‌های Downstream را با Timeout، Retry و Circuit Breaker مدیریت کنید.
  7. برای عملیات حساس، Retry را با Idempotency ترکیب کنید.
  8. Observability، Alerting و Recovery Plan را فراموش نکنید.
  9. در پایان Trade-off هزینه، Consistency و Complexity را بیان کنید.

نمونهٔ پاسخ کوتاه

«برای حذف Single Point of Failure چند Stateless Instance پشت Load Balancer قرار می‌دهم. Health Check باعث می‌شود Instance ناسالم Traffic نگیرد. Database نیز باید Replica و Failover داشته باشد. برای Dependencyهای خارجی Timeout، Retry محدود و Circuit Breaker می‌گذارم و در عملیات Payment، Retry را فقط همراه Idempotency انجام می‌دهم. همچنین Availability هدف و Recovery Metricهایی مثل RTO/RPO را از ابتدا مشخص می‌کنم.»

تمرین کوتاه

یک Payment API سه Instance پشت Load Balancer دارد، اما هر سه Instance به یک SQL Server منفرد متصل هستند. اگر SQL Server خاموش شود، هیچ پرداختی انجام نمی‌شود. مهم‌ترین مشکل معماری چیست؟

  1. تعداد Application Instanceها کم است
  2. Database یک Single Point of Failure است
  3. باید Redis اضافه شود
  4. باید تمام Requestها Asynchronous شوند
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. Application Layer Redundant است، اما Database همچنان SPOF است. برای افزایش Availability باید برای Data Layer نیز Replication/Failover مناسب طراحی شود.

جمع‌بندی

  • Availability یعنی سرویس در زمان مورد نیاز واقعاً قابل استفاده باشد.
  • Availability باید به‌صورت عددی با SLI و SLO تعریف شود؛ مثلاً 99.99%.
  • هر Component حیاتی منفرد می‌تواند Single Point of Failure باشد.
  • Redundancy، Health Check و Failover پایه‌های اصلی High Availability هستند.
  • Timeout، Retry، Circuit Breaker، Bulkhead و Graceful Degradation از انتشار Failure جلوگیری می‌کنند.
  • Database، Message Broker و Dependencyهای خارجی نیز باید در طراحی Availability در نظر گرفته شوند.
  • Retry در سیستم‌های Payment باید همراه Idempotency و تشخیص State واقعی تراکنش باشد.
  • High Availability هزینه و Complexity دارد؛ سطح هدف باید بر اساس نیاز Business انتخاب شود.
  • برای Disaster Recovery نیز RTO و RPO باید مشخص باشند.
