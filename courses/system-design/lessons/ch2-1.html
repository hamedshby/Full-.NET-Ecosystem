Networking & Request Flow

DNS

DNS — Domain Name System سیستمی است که نام‌هایی مانند api.example.com را به آدرس IP تبدیل می‌کند. در System Design، DNS فقط «تبدیل نام به IP» نیست؛ TTL، Cache، Failover، Geo Routing، Load Distribution و Availability آن مستقیماً روی مسیر Request و رفتار سیستم اثر می‌گذارند.

از یک Request ساده شروع کنیم

کاربر این آدرس را فراخوانی می‌کند:

https://api.payment.com/v1/payments

Client برای ایجاد Connection به IP نیاز دارد:

api.payment.com
↓
DNS Resolution
↓
185.10.20.30
↓
TCP / TLS
↓
HTTP Request
مدل ذهنی: DNS شبیه دفترچه تلفن اینترنت است؛ نام را به آدرس قابل‌استفاده در شبکه تبدیل می‌کند.

DNS دقیقاً چیست؟

DNS یک سیستم توزیع‌شده و سلسله‌مراتبی برای نگاشت Domain Name به اطلاعاتی مانند IP Address است.

api.example.com
↓
203.0.113.20
  • نام برای انسان خواناتر از IP است.
  • IP می‌تواند تغییر کند ولی Domain ثابت بماند.
  • می‌توان Traffic را بین چند IP یا Region توزیع کرد.
  • DNS می‌تواند در Failover و Routing نقش داشته باشد.

DNS یک سیستم Hierarchical است

اجزای اصلی DNS

  • Stub Resolver: بخش Client/OS که Query را آغاز می‌کند.
  • Recursive Resolver: پاسخ نهایی را برای Client پیدا می‌کند.
  • Root Name Server: نقطه شروع سلسله‌مراتب DNS.
  • TLD Name Server: مسیر Domainهای یک TLD مثل .com را مشخص می‌کند.
  • Authoritative Name Server: منبع معتبر رکوردهای Domain است.

وقتی Domain را وارد می‌کنیم چه اتفاقی می‌افتد؟

  1. Browser یا OS ابتدا Cache محلی را بررسی می‌کند.
  2. اگر پاسخ نبود Query به Recursive Resolver می‌رود.
  3. Resolver در صورت نیاز از Root Server سؤال می‌کند.
  4. Root مسیر TLD مناسب را می‌دهد.
  5. TLD آدرس Authoritative DNS را برمی‌گرداند.
  6. Resolver رکورد Domain را از Authoritative Server می‌گیرد.
  7. IP به Client برمی‌گردد.
  8. Client اتصال TCP/TLS و سپس HTTP Request را ایجاد می‌کند.

→

نکته: به دلیل Cache این مسیر کامل برای هر Request تکرار نمی‌شود.

DNS Cache

DNS معمولاً در چند لایه Cache می‌شود:

  • Browser Cache
  • Operating System Cache
  • Router / Local Network
  • Recursive Resolver Cache

Cache باعث کاهش Latency، Queryهای تکراری و Load روی DNS Infrastructure می‌شود.

TTL — Time To Live

TTL تعیین می‌کند یک DNS Record چه مدت Cache شود.

api.example.com
A
203.0.113.20
TTL = 300 seconds
TTL مزیت Trade-off
کوتاه تغییر و Failover سریع‌تر دیده می‌شود DNS Query بیشتر
بلند Cache بهتر IP قدیمی دیرتر کنار گذاشته می‌شود

رکوردهای مهم DNS

Record کاربرد مثال

AAAA Domain → IPv6 api.example.com → IPv6
CNAME Alias یک نام به نام دیگر www → web.example.net

TXT Verification / SPF / DKIM Domain verification

DNS می‌تواند Traffic را میان چند Endpoint یا Region توزیع کند.

  • Round Robin DNS
  • Weighted Routing
  • Geo DNS
  • Latency-based Routing
  • Failover Routing
نکته: DNS Load Balancing جای Load Balancer Application را کامل نمی‌گیرد؛ Cache و TTL کنترل لحظه‌ای را محدود می‌کنند.

Geo Routing می‌تواند Network Latency را کم و Traffic را بین Regionها پخش کند، اما Replication و Consistency داده پیچیده‌تر می‌شوند.

DNS و Failover

Normal
api.example.com
↓
Region A

Failure
Region A unavailable
↓
DNS changed
↓

DNS Failover کاملاً Instant نیست، چون Client یا Resolver ممکن است IP قبلی را تا پایان TTL نگه دارد.

اصل مهم: برای Recovery بسیار سریع فقط به تغییر DNS متکی نباشید.

اگر DNS Down شود چه می‌شود؟

اگر Domain Resolve نشود، حتی با سالم بودن API و Database کاربر به سرویس دسترسی ندارد. بنابراین DNS خودش بخشی از Availability کل سیستم است.

  • چند Authoritative Name Server
  • چند Location
  • Cache در Resolverها
  • Anycast در Providerهای بزرگ

Trade-offهای DNS

  • TTL کوتاه vs Query Load: تغییر سریع‌تر، Query بیشتر.
  • TTL بلند vs Failover: Cache بهتر، تغییر کندتر.
  • Geo Routing vs Consistency: Latency کمتر، Data Replication پیچیده‌تر.
  • DNS Load Balancing vs Control: Global و ساده، ولی Routing لحظه‌ای نیست.
  • CNAME Flexibility vs Extra Lookup: مدیریت ساده‌تر، Resolution ممکن است یک مرحله بیشتر داشته باشد.

اشتباهات رایج

  • فرض اینکه DNS فقط تبدیل Name به IP است
  • TTL بسیار بلند هنگام Migration
  • اتکا به DNS Failover برای Recovery کاملاً Instant
  • وابستگی Microservice به IP ثابت
  • نادیده گرفتن Cache هنگام Debug
  • اشتباه گرفتن CNAME با HTTP Redirect
  • نادیده گرفتن Availability DNS Provider

در مصاحبه System Design چطور درباره DNS صحبت کنیم؟

  1. Client Domain را به IP Resolve می‌کند.
  2. Recursive Resolver و Authoritative DNS را توضیح دهید.
  3. نقش Cache و TTL را بیان کنید.
  4. DNS می‌تواند چند Endpoint یا Region برگرداند.
  5. Failover تحت تأثیر TTL و Cache است.
  6. در Microserviceها DNS بخشی از Service Discovery است.
  7. در Kubernetes از Service Name استفاده می‌کنیم، نه IP Pod.
  8. DNS را بخشی از Availability کل سیستم در نظر بگیرید.

نمونه پاسخ کوتاه

«Client ابتدا api.example.com را با DNS به IP Load Balancer Resolve می‌کند. Resolver پاسخ را طبق TTL Cache می‌کند. برای سیستم Global می‌توان از Geo یا Latency-based Routing استفاده کرد، اما DNS Failover Instant نیست چون Client ممکن است IP قدیمی را Cache کرده باشد. داخل Kubernetes نیز Serviceها را با DNS Name پیدا می‌کنیم تا به IP موقت Podها وابسته نباشیم.»

تمرین کوتاه

IP جدید یک API Deploy شده است، اما بخشی از کاربران هنوز برای چند ساعت به IP قدیمی وصل می‌شوند. محتمل‌ترین دلیل چیست؟

  1. Thread Pool پر شده است
  2. DNS Record قدیمی هنوز در Cache و TTL معتبر است
  3. Database Index خراب است
  4. RabbitMQ Retry می‌کند
مشاهده پاسخ پیشنهادی

گزینه ۲. Resolver یا Client ممکن است Record قبلی را تا پایان TTL نگه داشته باشد. برای Migrationهای حساس معمولاً TTL از قبل کاهش داده می‌شود.

جمع‌بندی

  • DNS Domain Name را به اطلاعاتی مانند IP تبدیل می‌کند.
  • DNS یک سیستم توزیع‌شده و Hierarchical است.
  • Recursive Resolver، Root، TLD و Authoritative DNS اجزای اصلی Resolution هستند.
  • Cache و TTL Latency و Load DNS را کاهش می‌دهند.
  • A، AAAA، CNAME، MX، TXT و NS از رکوردهای مهم DNS هستند.
  • DNS می‌تواند در Load Balancing، Geo Routing و Failover نقش داشته باشد.
  • DNS Failover به دلیل Cache و TTL کاملاً Instant نیست.
  • DNS بخشی حیاتی از Availability کل سیستم است.
  • در Kubernetes از DNS برای Service Discovery استفاده می‌شود.
  • در Request Flow معمولاً DNS قبل از TCP، TLS و HTTP قرار دارد.
