فصل 1 از ۱۰

Fundamentals

Throughput

Throughput یعنی سیستم در یک بازهٔ زمانی مشخص چه مقدار کار را با موفقیت انجام می‌دهد. در Backend معمولاً آن را با معیارهایی مانند RPS، TPS یا تعداد Message پردازش‌شده در ثانیه می‌سنجیم. در این درس یاد می‌گیریم Throughput چگونه اندازه‌گیری می‌شود، چه چیزی آن را محدود می‌کند و چگونه ظرفیت واقعی سیستم را افزایش دهیم.

از یک Payment System شروع کنیم

فرض کنید Payment Service در حال حاضر می‌تواند ۱۰۰۰ تراکنش در ثانیه را پردازش کند. در ساعات عادی فقط ۳۰۰ TPS دریافت می‌کند، اما هنگام کمپین ترافیک به ۱۵۰۰ TPS می‌رسد.

وقتی نرخ ورودی از ظرفیت واقعی سیستم بیشتر می‌شود، Requestها شروع به صف‌شدن می‌کنند، Latency افزایش پیدا می‌کند و در نهایت Error Rate نیز بالا می‌رود.

مدل ذهنی: Throughput را مانند ظرفیت یک عوارضی در نظر بگیرید. اگر عوارضی بتواند در هر دقیقه ۱۰۰ خودرو را عبور دهد ولی ۱۵۰ خودرو وارد شوند، صف تشکیل می‌شود؛ حتی اگر عبور هر خودرو به‌تنهایی سریع باشد.

Throughput دقیقاً چیست؟

Throughput مقدار کاری است که سیستم در واحد زمان تکمیل می‌کند. واحد آن بسته به نوع سیستم متفاوت است.

  • RPS — Requests Per Second: تعداد Request تکمیل‌شده در هر ثانیه.
  • TPS — Transactions Per Second: تعداد تراکنش تکمیل‌شده در هر ثانیه.
  • Messages/sec: تعداد Message پردازش‌شده در ثانیه.
  • Rows/sec: تعداد رکورد پردازش یا نوشته‌شده در ثانیه.
  • MB/sec: حجم داده منتقل‌شده در ثانیه.

مثال

اگر سیستم در ۱۰ ثانیه ۲۰,۰۰۰ Request موفق را کامل کند:

Throughput
=
20,000 / 10
=
2,000 RPS

دقت کنید که Throughput تعداد Requestهای واردشده نیست؛ بلکه تعداد عملیات تکمیل‌شده در واحد زمان است.

تفاوت Throughput و Latency

مفهوم سؤال اصلی مثال
Latency هر Operation چقدر زمان می‌برد؟ هر Payment در p95 زیر 300 ms تکمیل می‌شود
Throughput در هر ثانیه چند Operation کامل می‌شود؟ سرویس 2500 Payment در ثانیه پردازش می‌کند

یک سیستم می‌تواند Latency پایین ولی Throughput پایین داشته باشد. برای مثال یک Worker هر Job را در ۱۰ میلی‌ثانیه انجام می‌دهد، اما چون فقط یک Job را در لحظه پردازش می‌کند، ظرفیت کل محدود است.

برعکس، ممکن است Throughput بالا باشد ولی بعضی Requestها Latency زیادی تجربه کنند؛ مثلاً با Batch Processing تعداد زیادی آیتم پردازش می‌شود اما هر آیتم باید منتظر تشکیل Batch بماند.

Capacity با Throughput چه فرقی دارد؟

Throughput مقدار کاری است که سیستم همین الآن انجام می‌دهد. Capacity حداکثر Throughput قابل‌پشتیبانی در شرایط تعریف‌شده است.

مثال

اگر Payment Service الآن ۸۰۰ TPS پردازش کند، ولی در Load Test تا ۲۲۰۰ TPS بتواند SLO را حفظ کند: 

Current Throughput = 800 TPS
Capacity ≈ 2200 TPS

ظرفیت واقعی باید همراه SLO تعریف شود. اگر سیستم در ۳۰۰۰ TPS هنوز Response بدهد ولی p99 به ۲۰ ثانیه برسد و Error Rate بالا رود، نمی‌توان گفت ظرفیت مفید سیستم ۳۰۰۰ TPS است.

Saturation؛ وقتی سیستم به سقف نزدیک می‌شود

Saturation یعنی یک Resource یا Component به نقطه‌ای نزدیک می‌شود که دیگر نمی‌تواند Workload بیشتری را بدون افت کیفیت تحمل کند.

  • CPU بالا
  • Thread Pool Queue رو‌به‌رشد
  • Connection Pool Exhaustion
  • Database Lock/Blocking
  • Queue Depth رو‌به‌رشد
  • Disk I/O بالا
  • Consumer Lag
  • Latency صعودی
  • Error Rate افزایشی
نکته: معمولاً قبل از رسیدن به شکست کامل، Latency و Queueing رشد می‌کنند. بنابراین فقط CPU=100% را به‌عنوان علامت Saturation در نظر نگیرید.

Bottleneck Throughput کل را محدود می‌کند

ظرفیت یک Pipeline معمولاً توسط کندترین یا محدودترین Stage تعیین می‌شود.

API: 5000 TPS
→
Payment Service: 4000 TPS
→
Database: 1800 TPS
→
Bank Adapter: 2500 TPS

در این مثال Throughput کل سیستم تقریباً توسط Database محدود می‌شود. اضافه‌کردن Application Instance بدون رفع محدودیت Database ظرفیت واقعی را چندان افزایش نمی‌دهد.

اصل مهم

ابتدا Bottleneck را پیدا کنید، سپس همان نقطه را Scale یا Optimize کنید.

هزینهٔ هر Request مهم است

Throughput فقط به تعداد Serverها وابسته نیست. هرچه CPU، Database Call، Network Call یا Lock بیشتری برای هر Request نیاز باشد، تعداد Request قابل پردازش در واحد زمان کمتر می‌شود.

مثال

Version A
Each request = 1 DB query
Capacity ≈ 3000 RPS

Version B
Each request = 8 DB queries
Capacity ≈ 700 RPS

کاهش Work Per Request اغلب یکی از کم‌هزینه‌ترین راه‌های افزایش Throughput است.

Little's Law؛ ارتباط Concurrency، Throughput و Latency

در یک سیستم پایدار می‌توان به‌صورت ساده از رابطهٔ زیر استفاده کرد:

Concurrency ≈ Throughput × Latency

مثال:

Throughput = 1000 requests/sec
Average latency = 0.2 sec

Concurrency ≈ 1000 × 0.2
Concurrency ≈ 200 requests

یعنی به‌طور متوسط حدود ۲۰۰ Request هم‌زمان داخل سیستم در حال پردازش هستند.

کاربرد: این رابطه برای تخمین Connection، Worker، Thread، Queue Capacity و Load Test مفید است، البته زمانی که سیستم در وضعیت نسبتاً پایدار باشد.

Parallelism و Concurrency برای افزایش Throughput

اگر Workload قابل تقسیم باشد، می‌توان چند Operation را هم‌زمان پردازش کرد.

مثال Worker

1 Worker
50 messages/sec

10 Workers
≈ 500 messages/sec

اما افزایش Parallelism فقط تا زمانی مفید است که Dependency مشترک اشباع نشده باشد. اگر ۱۰ Worker همه به یک Database محدود وصل باشند، اضافه‌کردن Worker بیشتر ممکن است فقط Lock، Connection Wait و Latency را افزایش دهد.

Batch Processing

Batch Processing چند آیتم را در یک Operation پردازش می‌کند تا هزینهٔ ثابت هر Request کاهش پیدا کند.

روش مزیت Trade-off
Single Item Latency هر آیتم کمتر Overhead بیشتر
Batch Throughput بالاتر Latency بعضی آیتم‌ها و پیچیدگی Error Handling بیشتر

مثال

به‌جای Insert هزار رکورد با هزار Round Trip، می‌توان از Bulk Insert یا Batch Insert استفاده کرد.

Queue چگونه Throughput را مدیریت می‌کند؟

Queue می‌تواند Producer و Consumer را از نظر سرعت از هم جدا کند. 

Producer
5000 msg/sec
↓
Queue
↓
Consumers
4000 msg/sec

Queue Burst کوتاه‌مدت را جذب می‌کند، اما اگر نرخ ورودی برای مدت طولانی از نرخ مصرف بیشتر باشد، Queue دائماً رشد خواهد کرد.

  • افزایش Consumerها
  • کاهش هزینهٔ پردازش هر Message
  • Partition کردن Workload
  • کاهش ورودی با Rate Limiting یا Backpressure
اصل مهم: Queue ظرفیت تولید نمی‌کند؛ فقط تفاوت موقت بین نرخ ورودی و نرخ پردازش را Buffer می‌کند.

Backpressure

Backpressure یعنی وقتی Consumer یا Downstream ظرفیت کافی ندارد، سیستم اجازه ندهد Producer بدون محدودیت Work بیشتری وارد کند.

  • Rate Limiting
  • Bounded Queue
  • Reject یا Delay کردن Request
  • Consumer Prefetch Limit
  • Adaptive Concurrency Limit

مثال

اگر Payment Processor فقط ۲۰۰۰ TPS ظرفیت دارد، قبول کردن ۲۰,۰۰۰ TPS بدون محدودیت می‌تواند کل سیستم را ناپایدار کند. بهتر است ورودی کنترل شود تا سیستم از محدودهٔ امن خارج نشود.

Database و Throughput

Database در بسیاری از Backendها اصلی‌ترین Bottleneck Throughput است.

  • Index مناسب
  • Query Optimization
  • Connection Pool Size
  • Lock Contention
  • Transaction Duration
  • Read/Write Ratio
  • Batching
  • Read Replica
  • Partitioning / Sharding

مثال

اگر یک Update روی Rowهای مشترک Lock سنگین ایجاد کند، اضافه‌کردن CPU به Application Serverها Throughput را افزایش نمی‌دهد؛ چون Transactionها همچنان پشت Lock منتظر می‌مانند.

Cache چگونه Throughput را افزایش می‌دهد؟

Cache علاوه بر کاهش Latency می‌تواند Throughput سیستم را نیز افزایش دهد، چون Load از روی Database یا Dependency اصلی برداشته می‌شود. 

Without Cache

10,000 reads/sec
↓
Database


With Cache

9,000 reads/sec → Redis
1,000 reads/sec → Database

در نتیجه Database ظرفیت بیشتری برای Writeها یا Queryهای ضروری خواهد داشت. البته Cache Miss، Invalidation و Hot Key می‌توانند Bottleneck جدید ایجاد کنند.

Scale Up و Scale Out برای Throughput

  • Scale Up: CPU، Memory یا Disk سریع‌تر به یک Node اضافه می‌کنیم.
  • Scale Out: Instance یا Worker بیشتری اضافه می‌کنیم و Workload را تقسیم می‌کنیم.

Stateless Applicationها معمولاً راحت‌تر Scale Out می‌شوند. اما Throughput خطی افزایش پیدا نمی‌کند؛ چون Shared Resourceها، Coordination و Database می‌توانند مانع شوند.

مثال واقعی

1 instance  = 800 RPS
2 instances = 1500 RPS
4 instances = 2400 RPS
8 instances = 2700 RPS

از ۴ Instance به بعد رشد تقریباً متوقف شده است. احتمالاً Bottleneck از Application به Component دیگری منتقل شده است.

Load Test برای پیدا کردن ظرفیت واقعی

Throughput را نباید فقط از روی تعداد Core یا Spec سرور حدس زد. باید سیستم را تحت بار واقعی یا شبیه‌سازی‌شده آزمایش کرد.

  • Input RPS/TPS
  • Completed RPS/TPS
  • p50 / p95 / p99 Latency
  • Error Rate
  • CPU / Memory
  • Database Duration
  • Connection Pool
  • Queue Depth
  • Consumer Lag

Capacity مفید نقطه‌ای است که سیستم هنوز SLO را حفظ می‌کند، نه آخرین نقطه‌ای که Process هنوز Crash نکرده است.

مثال کامل Throughput در Payment System

Normal load: 1000 TPS
Peak load:   3000 TPS
Burst:       5000 TPS for 2 minutes

p95 latency: < 500 ms
Error rate:  < 0.1%
Client
→
Load Balancer
→
Payment Service × N
→
SQL Server
+
RabbitMQ
  1. Payment Service را Stateless طراحی می‌کنیم تا Scale Out شود.
  2. Query و Indexهای SQL را Optimize می‌کنیم.
  3. Transactionها را کوتاه نگه می‌داریم تا Lock Contention کاهش یابد.
  4. Readهای پرتکرار و مناسب را Cache می‌کنیم.
  5. Notification و Reporting را از مسیر Sync خارج و به RabbitMQ منتقل می‌کنیم.
  6. Consumerها را بر اساس Queue Depth و Lag Scale می‌کنیم.
  7. برای Burst از Queue و ظرفیت اضافی استفاده می‌کنیم.
  8. برای جلوگیری از Overload از Rate Limiting و Backpressure استفاده می‌کنیم.
  9. Load Test تا بالاتر از Peak مورد انتظار انجام می‌دهیم.

Trade-offهای افزایش Throughput

  • Throughput vs Latency: Batch یا Queue می‌تواند Throughput را بالا ببرد ولی Latency هر آیتم را افزایش دهد.
  • Parallelism vs Contention: Worker بیشتر ممکن است Lock و فشار روی Database را افزایش دهد.
  • Cache vs Consistency: Throughput Read افزایش می‌یابد اما Stale Data ممکن است ایجاد شود.
  • Async vs Immediate Consistency: مسیر Sync سبک‌تر می‌شود ولی برخی Stateها با تأخیر به‌روز می‌شوند.
  • Scale Out vs Cost: Instance بیشتر هزینهٔ Infrastructure و عملیات را افزایش می‌دهد.

اشتباهات رایج

  • یکی دانستن Throughput با تعداد Request ورودی
  • اندازه‌گیری TPS بدون درنظرگرفتن Error Rate و Latency
  • افزایش Worker بدون بررسی Bottleneck مشترک
  • استفاده از Queue به‌عنوان راه‌حل دائمی کمبود Capacity
  • نداشتن Backpressure در زمان Overload
  • فرض افزایش خطی Capacity با تعداد Instance
  • نادیده گرفتن Connection Pool و Lock Contention
  • Load Test فقط روی Application و بدون Dependencyهای واقعی
  • بهینه‌سازی قبل از پیدا کردن Bottleneck

در مصاحبه System Design چطور درباره Throughput صحبت کنیم؟

اگر از شما پرسیدند «این سیستم چطور ۱۰,۰۰۰ Request در ثانیه را تحمل می‌کند؟»، مستقیم نگویید «Kubernetes اضافه می‌کنم».

  1. Throughput هدف، Peak و Burst را مشخص کنید.
  2. SLO مربوط به Latency و Error Rate را مشخص کنید.
  3. Critical Path را رسم کنید.
  4. ظرفیت هر Component را بررسی کنید.
  5. Bottleneck را پیدا کنید.
  6. Work Per Request را کاهش دهید.
  7. Application را در صورت Stateless بودن Scale Out کنید.
  8. Database، Cache و Queue را جداگانه بررسی کنید.
  9. برای Async Work، Consumer Parallelism و Partitioning را طراحی کنید.
  10. Backpressure و Rate Limiting را برای Overload مشخص کنید.
  11. با Load Test طراحی را اعتبارسنجی کنید.

نمونهٔ پاسخ کوتاه

«ابتدا Peak TPS و SLO را مشخص می‌کنم. سپس ظرفیت هر Component را با Load Test می‌سنجم و Bottleneck را پیدا می‌کنم. Applicationهای Stateless را پشت Load Balancer Scale Out می‌کنم، Query و Transactionهای Database را بهینه می‌کنم، Readهای مناسب را Cache می‌کنم و عملیات غیرضروری را به Queue منتقل می‌کنم. برای Consumerها Parallelism کنترل‌شده و برای Overload Backpressure و Rate Limiting در نظر می‌گیرم. هدف این است که Throughput افزایش پیدا کند بدون اینکه p95/p99 Latency و Error Rate از SLO خارج شوند.»

تمرین کوتاه

یک API با ۲ Instance تا ۱۵۰۰ RPS عملکرد خوبی دارد. با اضافه‌کردن ۴ Instance دیگر، Throughput فقط به ۱۷۰۰ RPS می‌رسد. هم‌زمان Database CPU برابر ۹۵٪ و Connection Pool تقریباً پر است. بهترین نتیجه‌گیری چیست؟

  1. باید Instanceهای Application را باز هم بیشتر کنیم
  2. Database احتمالاً Bottleneck فعلی است
  3. باید همهٔ APIها را Async کنیم
  4. مشکل فقط Network است
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. افزایش Application Instance دیگر رشد معناداری ایجاد نکرده و Database به Saturation نزدیک شده است. بنابراین باید Queryها، Indexها، Connection Pool، Locking، Transactionها و در صورت نیاز Scale Strategy دیتابیس بررسی شوند.

جمع‌بندی

  • Throughput مقدار کار تکمیل‌شده در واحد زمان است.
  • RPS، TPS و Messages/sec واحدهای رایج Throughput هستند.
  • Throughput با Latency و Capacity یکسان نیست.
  • Capacity باید همراه SLO، Latency و Error Rate تعریف شود.
  • Bottleneck محدودکنندهٔ Throughput کل سیستم است.
  • Little's Law ارتباط Concurrency، Throughput و Latency را نشان می‌دهد.
  • Parallelism، Batch، Cache و Scale Out می‌توانند Throughput را افزایش دهند، اما Trade-off دارند.
  • Queue فقط Burst را Buffer می‌کند و جای Capacity واقعی را نمی‌گیرد.
  • Backpressure از ناپایداری سیستم هنگام Overload جلوگیری می‌کند.
  • Load Test بهترین راه برای سنجش ظرفیت واقعی سیستم است.
  • در Payment System، Database، Lock، Connection Pool و Dependency خارجی معمولاً نقاط مهم ظرفیت هستند.
