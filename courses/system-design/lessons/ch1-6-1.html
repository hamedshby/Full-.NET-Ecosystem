Fundamentals

Vertical vs Horizontal Scaling

وقتی Workload رشد می‌کند، سیستم به Capacity بیشتری نیاز دارد. دو راه اصلی برای افزایش Capacity وجود دارد: Vertical Scaling یا Scale Up یعنی قوی‌تر کردن یک Node، و Horizontal Scaling یا Scale Out یعنی اضافه‌کردن Nodeهای بیشتر. انتخاب بین این دو به Bottleneck، نوع Workload، Availability، State و هزینه وابسته است.

از یک Payment API شروع کنیم

فرض کنید Payment Service روی یک Server با 4 Core CPU و 8 GB RAM اجرا می‌شود و در Peak به ۹۰٪ CPU می‌رسد.

برای افزایش Capacity دو گزینهٔ اصلی داریم:

  • Server را قوی‌تر کنیم؛ مثلاً 16 Core و 32 GB RAM.
  • چند Instance از Payment Service ایجاد کنیم و Traffic را بین آن‌ها پخش کنیم.
مدل ذهنی: Scale Up یعنی به یک صندوق فروشگاهی سریع‌تر و قوی‌تر بدهیم. Scale Out یعنی چند صندوق دیگر باز کنیم و مشتری‌ها را بین آن‌ها تقسیم کنیم.

Vertical Scaling یا Scale Up

در Vertical Scaling قدرت یک Machine یا Node را افزایش می‌دهیم.

مثال

Before
4 CPU
8 GB RAM

↓ Scale Up

16 CPU
32 GB RAM
Faster Disk

نمونه‌های رایج شامل افزایش CPU، Memory، IOPS، استفاده از Disk سریع‌تر یا انتقال Database به Server قوی‌تر است.

مزایای Vertical Scaling

  • سادگی: معمولاً معماری Application تغییر نمی‌کند.
  • پیاده‌سازی سریع: نیازی به Load Balancer یا Distributed Coordination جدید نیست.
  • State Management ساده‌تر: State می‌تواند روی همان Node باقی بماند.
  • مناسب برای Database: بسیاری از Databaseها در مراحل اولیه با Scale Up بسیار خوب رشد می‌کنند.
  • Operational Complexity کمتر: Nodeهای کمتری برای Deploy و Monitor داریم.

مثال

اگر SQL Server کمبود Memory برای Buffer Pool دارد، افزایش RAM ممکن است بسیار ساده‌تر و مؤثرتر از Sharding فوری باشد.

محدودیت‌های Vertical Scaling

  • سقف سخت‌افزاری: هر Machine حداکثر CPU و Memory مشخصی دارد.
  • هزینهٔ غیرخطی: Serverهای بسیار بزرگ معمولاً بسیار گران می‌شوند.
  • Single Point of Failure: اگر فقط یک Node داشته باشیم، خرابی آن می‌تواند کل سرویس را متوقف کند.
  • Downtime احتمالی: بعضی Upgradeها نیاز به Restart یا Migration دارند.
  • رشد محدود: نمی‌توان یک Machine را بی‌نهایت قوی کرد.
اصل مهم: Scale Up راه‌حل بدی نیست؛ مشکل زمانی است که آن را تنها Strategy برای رشد بلندمدت در نظر بگیریم.

Horizontal Scaling یا Scale Out

در Horizontal Scaling به‌جای قوی‌ترکردن یک Node، تعداد Nodeها یا Instanceها را افزایش می‌دهیم.

Client
→
Load Balancer
→
App 1
App 2
App 3

مثال

1 instance = 800 RPS

↓ 4 instances

Total ≈ 2800 RPS

مزایای Horizontal Scaling

  • Capacity بیشتر: Workload میان Nodeها تقسیم می‌شود.
  • Availability بهتر: خرابی یک Instance الزاماً کل سرویس را متوقف نمی‌کند.
  • Elasticity: Instanceها می‌توانند بر اساس Load کم یا زیاد شوند.
  • رشد بلندمدت بهتر: محدودیت یک Machine کمتر تعیین‌کننده است.
  • مناسب برای Stateless Service: Web API و Worker معمولاً راحت‌تر Scale Out می‌شوند.

چرا Horizontal Scaling پیچیده‌تر است؟

وقتی چند Instance داریم، وارد مسائل Distributed Systems می‌شویم.

  • State کجا نگهداری شود؟
  • Request بعدی کاربر ممکن است به Instance دیگری برسد.
  • Cacheهای Local ممکن است با هم متفاوت باشند.
  • Distributed Lock ممکن است لازم شود.
  • Configuration باید بین Instanceها هماهنگ باشد.
  • Logging و Tracing باید Centralized باشد.
  • Health Check و Deployment پیچیده‌تر می‌شوند.
اصل مهم: Scale Out فقط اضافه‌کردن Server نیست؛ Application باید برای اجرای Distributed طراحی شده باشد.

مقایسه Vertical و Horizontal Scaling

ویژگی Vertical Scaling Horizontal Scaling
روش قوی‌ترکردن Node اضافه‌کردن Node
پیچیدگی کمتر بیشتر
سقف رشد محدود به Hardware معمولاً بالاتر
Availability اگر یک Node باشد پایین‌تر معمولاً بهتر
State Management ساده‌تر پیچیده‌تر
Elasticity محدود مناسب‌تر
کاربرد رایج Database و رشد اولیه Web/API، Worker و Microservice

Stateless Design؛ کلید Scale Out ساده

اگر هر Instance بتواند هر Request را بدون وابستگی به State محلی پردازش کند، Scale Out بسیار ساده‌تر می‌شود.

طراحی مشکل‌دار

Request 1 → Instance A → Session in Memory
Request 2 → Instance B → Session not found

طراحی بهتر

Instance A ─┐
Instance B ─┼──> Redis / Database
Instance C ─┘

State مشترک در Store خارجی نگهداری می‌شود و هر Instance می‌تواند Request را پردازش کند.

مثال در ASP.NET Core

Web APIهای ASP.NET Core اگر State محلی نداشته باشند، معمولاً به‌خوبی Horizontal Scale می‌شوند.

  • Session مشترک خارج از Process
  • Distributed Cache
  • Distributed Lock در صورت نیاز واقعی
  • Persistent Data در Database
  • Background Job State در Storage مشترک

نمونهٔ Redis Cache

builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = redisConnectionString;
});

Load Balancer در Horizontal Scaling

Load Balancer Requestهای ورودی را میان Instanceها توزیع می‌کند و معمولاً Health Check و Failover نیز انجام می‌دهد.

Users
→
Load Balancer
→
API 1
API 2
API 3

اگر API 2 Health Check را Fail کند، Load Balancer باید Traffic را به Instanceهای سالم بفرستد.

Scale Out معمولاً خطی نیست

1 instance  = 1000 RPS
2 instances = 1900 RPS
4 instances = 3200 RPS
8 instances = 3500 RPS

از یک نقطه به بعد ممکن است Database، Connection Pool، External API، Lock، Network یا Storage Bottleneck شود.

نکته: با Scale Out کردن یک Layer، Bottleneck معمولاً به Layer بعدی منتقل می‌شود.

Scaling در Database

Scale Out کردن Application معمولاً ساده‌تر از Database است چون Database State و Consistency دارد.

یک مسیر رشد رایج:

  1. Query Optimization
  2. Index مناسب
  3. Scale Up
  4. Cache
  5. Read Replica
  6. Partitioning
  7. Sharding در صورت نیاز واقعی

مثال

Writes → Primary DB
Reads  → Read Replica 1 / Read Replica 2

Read Replica نوعی Scale Out برای Read Workload است، اما Replication Lag و Consistency باید در نظر گرفته شوند.

Partitioning و Sharding

اگر یک Database دیگر نتواند Data یا Throughput مورد نیاز را تحمل کند، ممکن است داده را بین چند Node تقسیم کنیم.

MerchantId 1-10000     → Shard A
MerchantId 10001-20000 → Shard B
MerchantId 20001-30000 → Shard C

اما Sharding پیچیدگی‌هایی مثل Shard Key، Hot Shard، Cross-Shard Query، Distributed Transaction و Rebalancing دارد.

اصل مهم: Sharding معمولاً راه‌حل اول نیست. قبل از آن Query، Index، Cache، Replica و Scale Up را بررسی کنید.

Auto Scaling

در Horizontal Scaling می‌توان تعداد Instanceها را بر اساس Metric افزایش یا کاهش داد.

مثال Kubernetes

Normal traffic → 3 Pods
Traffic rises   → HPA → 8 Pods
Traffic drops   → Scale down → 3 Pods

Metricهای رایج: CPU، Memory، RPS، Queue Length، Consumer Lag یا Custom Business Metric.

Auto Scaling آنی نیست؛ Provision و Warm-up زمان می‌برند، پس برای Burst سریع باید Headroom نیز داشته باشیم.

Sticky Session راه‌حل است؟

Sticky Session کاربر را تا حد امکان به همان Instance می‌فرستد؛ اما می‌تواند Load را نامتعادل کند و Failure یا Scale Down را سخت‌تر کند.

برای Backend API معمولاً Stateless Design انتخاب مناسب‌تری است، مگر اینکه دلیل مشخصی برای Session Affinity وجود داشته باشد.

مثال کامل در Payment System

فرض کنید Payment Service از ۵۰۰ TPS به ۵۰۰۰ TPS رشد کرده است.

Clients
→
Load Balancer / API Gateway
→
Payment Service × N
→
SQL Server HA
+
Redis
+
RabbitMQ
  1. Payment Service را Stateless نگه می‌داریم.
  2. چند Instance پشت Load Balancer اجرا می‌کنیم.
  3. Kubernetes HPA بر اساس CPU یا RPS تعداد Podها را تغییر می‌دهد.
  4. Redis برای Cache یا State مشترک مناسب استفاده می‌شود.
  5. Notification و Reporting با RabbitMQ از مسیر Sync جدا می‌شوند.
  6. SQL Server ابتدا با Query Optimization، Index و Scale Up تقویت می‌شود.
  7. در صورت Read-heavy بودن، Read Replica بررسی می‌شود.
  8. در حجم بسیار بالا و نیاز واقعی، Partitioning یا Sharding بررسی می‌شود.

در معماری واقعی معمولاً ترکیبی از Vertical و Horizontal Scaling استفاده می‌کنیم.

چه زمانی Scale Up و چه زمانی Scale Out؟

سناریو انتخاب اولیهٔ محتمل
Database کوچک با کمبود RAM Scale Up
Stateless Web API با Traffic زیاد Scale Out
Workerهای مستقل Scale Out
سیستم ساده با Load متوسط Scale Up ممکن است کافی باشد
نیاز به High Availability Scale Out / Redundancy
Database بسیار بزرگ ترکیبی؛ Scale Up، Replica و در صورت نیاز Partition/Sharding
نکته: در System Design کمتر پیش می‌آید پاسخ درست فقط یکی از این دو باشد؛ معماری واقعی معمولاً ترکیبی است.

Trade-offها

  • Scale Up: ساده‌تر است ولی سقف Hardware دارد.
  • Scale Out: Capacity و Availability بهتری می‌دهد ولی Complexity بیشتری دارد.
  • Statelessness: Scale Out را ساده می‌کند ولی نیازمند External State Store است.
  • Read Replica: Read Throughput را بالا می‌برد ولی Replication Lag ایجاد می‌کند.
  • Sharding: Capacity زیادی می‌دهد ولی Query و Transaction را پیچیده می‌کند.
  • Auto Scaling: هزینه را کنترل می‌کند ولی واکنش آن Instant نیست.

اشتباهات رایج

  • فرض اینکه Horizontal Scaling همیشه بهتر است
  • Scale Out کردن Application در حالی که Database Bottleneck است
  • نگه‌داری Session مهم در Memory یک Instance
  • فرض رشد خطی Capacity با تعداد Instance
  • Sharding زودهنگام Database
  • Auto Scaling فقط بر اساس CPU بدون بررسی Workload واقعی
  • نداشتن Health Check برای Instanceهای جدید
  • استفاده از Sticky Session به‌عنوان جایگزین طراحی Stateless
  • Scale کردن بدون Load Test و Measurement

در مصاحبه System Design چطور درباره Scaling صحبت کنیم؟

اگر از شما پرسیدند «وقتی Traffic ده برابر شد چه کار می‌کنی؟»، فقط نگویید «Server بیشتری اضافه می‌کنم».

  1. Workload و Bottleneck را مشخص کنید.
  2. بررسی کنید مشکل CPU، Memory، Database، Network یا Dependency است.
  3. اگر افزایش Resource ساده و کافی است، Scale Up را در نظر بگیرید.
  4. برای Stateless Serviceها Scale Out طراحی کنید.
  5. Load Balancer و Health Check را توضیح دهید.
  6. State محلی را حذف یا به Store مشترک منتقل کنید.
  7. Database Scaling را جداگانه بررسی کنید.
  8. Auto Scaling و Metric مناسب را مشخص کنید.
  9. بگویید Scale Out خطی نیست و Bottleneck بعدی را باید پیدا کرد.
  10. در پایان Cost، Complexity و Availability را به‌عنوان Trade-off بیان کنید.

نمونهٔ پاسخ کوتاه

«ابتدا Bottleneck را با Metric و Load Test پیدا می‌کنم. اگر محدودیت سادهٔ CPU یا Memory باشد، Scale Up می‌تواند سریع‌ترین راه باشد. برای Web APIهای Stateless چند Instance پشت Load Balancer قرار می‌دهم و در صورت نیاز با HPA Scale Out می‌کنم. State مشترک را در Database یا Redis نگه می‌دارم. Database را جداگانه بررسی می‌کنم چون Scale Out آن پیچیده‌تر است؛ ابتدا Query Optimization، Index، Scale Up و Replica، و فقط در صورت نیاز واقعی Partitioning یا Sharding را در نظر می‌گیرم.»

تمرین کوتاه

یک ASP.NET Core API با ۸ Instance اجرا می‌شود. با افزایش Instanceها از ۴ به ۸، Throughput تقریباً تغییری نکرده است. CPU Applicationها زیر ۴۰٪ است، اما Database CPU برابر ۹۵٪ است. بهترین اقدام بعدی چیست؟

  1. تعداد API Instanceها را به ۱۶ افزایش دهیم
  2. Database Bottleneck را بررسی و Optimize/Scale کنیم
  3. Sticky Session فعال کنیم
  4. Memory APIها را دو برابر کنیم
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. Application Layer ظرفیت اضافه دارد اما Database به Saturation رسیده است. Scale Out بیشتر در API مشکل اصلی را حل نمی‌کند. باید Query، Index، Lock، Connection Pool و Strategy دیتابیس بررسی شود.

جمع‌بندی

  • Vertical Scaling یعنی قوی‌ترکردن یک Node.
  • Horizontal Scaling یعنی اضافه‌کردن Nodeهای بیشتر.
  • Scale Up ساده‌تر است ولی سقف Hardware دارد.
  • Scale Out ظرفیت و Availability بهتری ایجاد می‌کند ولی Complexity بیشتری دارد.
  • Stateless Design مهم‌ترین عامل ساده‌شدن Scale Out در Web APIهاست.
  • Load Balancer Traffic را بین Instanceها تقسیم و Instance ناسالم را حذف می‌کند.
  • Scale Out معمولاً خطی نیست چون Shared Bottleneckها وجود دارند.
  • Database Scaling سخت‌تر از Application Scaling است و معمولاً مرحله‌به‌مرحله انجام می‌شود.
  • Auto Scaling باید بر اساس Metric مناسب طراحی شود.
  • در معماری واقعی معمولاً ترکیبی از Scale Up و Scale Out استفاده می‌شود.
