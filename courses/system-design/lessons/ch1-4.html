Fundamentals

Latency

Latency مدت‌زمانی است که طول می‌کشد یک Request از لحظهٔ شروع تا دریافت Response کامل شود. در System Design فقط Average Latency مهم نیست؛ باید Percentileهایی مانند p95 و p99، مسیر کامل Request، Queueing Delay، Network و Database را نیز بررسی کنیم.

از یک Payment API شروع کنیم

فرض کنید Payment API در تست‌های اولیه میانگین زمان پاسخ ۱۲۰ میلی‌ثانیه دارد. در نگاه اول این عدد عالی به نظر می‌رسد.

اما وقتی Metricها را دقیق‌تر بررسی می‌کنیم:

  • p50 = 80 ms
  • p95 = 350 ms
  • p99 = 2.8 s

یعنی بخش کوچکی از کاربران تجربه‌ای بسیار کند دارند. اگر فقط Average را ببینیم، این مشکل پنهان می‌ماند.

مدل ذهنی: Latency فقط «سرعت متوسط» نیست. مهم است بدانیم کندترین بخش قابل‌توجه کاربران چه تجربه‌ای دارند.

Latency دقیقاً چیست؟

Latency زمان لازم برای تکمیل یک عملیات است. این زمان می‌تواند از دید Client، Service یا یک Component خاص اندازه‌گیری شود.

مثال

Client در زمان 10:00:00.000 Request را ارسال می‌کند و Response در 10:00:00.180 دریافت می‌شود. Latency از دید Client برابر ۱۸۰ میلی‌ثانیه است.

Latency انتها‌به‌انتها معمولاً مجموع چند بخش است:

Total Latency
=
Network
+ Load Balancer
+ Application
+ Database
+ Downstream Services
+ Queueing
+ Serialization
+ Network Back

بنابراین وقتی یک API کند است، الزاماً مشکل در Application Code نیست.

تفاوت Latency و Throughput

مفهوم سؤال اصلی مثال
Latency یک عملیات چقدر زمان می‌برد؟ هر Request در 120 ms پاسخ می‌گیرد
Throughput در واحد زمان چند عملیات کامل می‌شود؟ سیستم 3000 Request در ثانیه پردازش می‌کند

این دو مرتبط‌اند اما یکسان نیستند. ممکن است سیستمی Throughput بالایی داشته باشد ولی بعضی Requestها Latency زیادی تجربه کنند.

همچنین ممکن است برای افزایش Throughput از Batch Processing استفاده کنیم، اما در نتیجه Latency هر آیتم افزایش پیدا کند.

چرا Average کافی نیست؟

Average می‌تواند Outlierها و کاربران کند را پنهان کند. برای همین در سیستم‌های واقعی از Percentile استفاده می‌کنیم.

  • p50: ۵۰٪ Requestها سریع‌تر از این مقدار هستند.
  • p95: ۹۵٪ Requestها سریع‌تر از این مقدار هستند.
  • p99: ۹۹٪ Requestها سریع‌تر از این مقدار هستند.

مثال

اگر p99 = 2 ثانیه باشد، یعنی از هر ۱۰۰ Request تقریباً یک Request ممکن است بیش از ۲ ثانیه طول بکشد.

اصل مهم: در سیستم‌های High Traffic، حتی ۱٪ Request کند می‌تواند تعداد زیادی کاربر واقعی را تحت تأثیر قرار دهد.

Tail Latency

Tail Latency به بخش کند توزیع Latency گفته می‌شود؛ معمولاً p95، p99 یا p99.9.

در معماری Distributed، Tail Latency اهمیت بیشتری پیدا می‌کند چون یک Request ممکن است هم‌زمان به چند Service وابسته باشد.

مثال

API Gateway
   |
   +--> User Service
   |
   +--> Product Service
   |
   +--> Pricing Service
   |
   +--> Recommendation Service

اگر Response نهایی منتظر همهٔ این Serviceها باشد، کندترین Dependency می‌تواند Latency کل Request را تعیین کند.

هرچه تعداد Remote Callها بیشتر شود، احتمال برخورد با یک Request کند نیز بیشتر می‌شود.

Latency Budget

یکی از روش‌های خوب طراحی این است که برای کل Request یک Latency Target تعیین کنیم و آن را بین Componentها تقسیم کنیم.

مثال Payment API

هدف: p95 کمتر از 300 ms

API Gateway      20 ms
Network          20 ms
Payment Service  40 ms
Database         60 ms
Fraud Service    80 ms
Bank Adapter     50 ms
Safety Margin    30 ms
----------------------
Total           300 ms

این تقسیم کمک می‌کند وقتی Latency افزایش یافت، بدانیم کدام Component از Budget خود عبور کرده است.

منابع رایج Latency

  • Network Latency: فاصله جغرافیایی، Hopها، DNS، TLS و Packet Loss.
  • Database Latency: Query کند، Lock، Index نامناسب، Disk I/O و Connection Pool.
  • Application Latency: CPU-heavy operation، Serialization، GC و Lock داخلی.
  • Queueing Delay: Request قبل از پردازش در Queue منتظر می‌ماند.
  • Downstream Latency: سرویس خارجی، بانک، PSP یا API داخلی کند است.
  • Cold Start: Instance یا Function هنوز Warm نشده است.
  • Connection Establishment: ساخت TCP/TLS connection جدید هزینه دارد.

Queueing Delay؛ دشمن پنهان Latency

وقتی Workload به ظرفیت سیستم نزدیک می‌شود، Requestها قبل از پردازش منتظر می‌مانند.

در این حالت حتی اگر زمان واقعی پردازش تغییر نکرده باشد، Latency کل افزایش پیدا می‌کند. 

Request arrives
↓
Wait in queue      400 ms
↓
Actual processing   80 ms
↓
Total latency      480 ms

به همین دلیل وقتی CPU، Thread Pool، Connection Pool یا Consumerها اشباع می‌شوند، Latency معمولاً ناگهان رشد می‌کند.

نکته: نزدیک شدن Utilization به 100% معمولاً به معنی استفادهٔ بهینه نیست؛ ممکن است Queueing Delay و Tail Latency به‌شدت افزایش پیدا کنند.

Database چگونه Latency ایجاد می‌کند؟

در Backend Systemها Database یکی از رایج‌ترین منابع Latency است.

  • Table Scan به دلیل نبود Index
  • Index نامناسب
  • Query Plan ضعیف
  • Lock و Blocking
  • Deadlock Retry
  • Connection Pool Exhaustion
  • N+1 Query
  • دریافت Columns یا Rows غیرضروری

مثال

API total latency = 900 ms

Application code = 40 ms
Database query   = 810 ms
Other            = 50 ms

در این سناریو Scale Out کردن Application مشکل اصلی را حل نمی‌کند. Bottleneck در Query یا Database است.

Remote Call رایگان نیست

هر بار که یک Service به Service دیگری Call می‌زند، هزینه‌هایی به مسیر اضافه می‌شود:

  • Network Round Trip
  • Serialization / Deserialization
  • TLS
  • Load Balancer
  • Queueing در Service مقصد
  • احتمال Retry و Timeout

مثال Microservice

Order API
↓
Customer Service    40 ms
↓
Inventory Service   60 ms
↓
Pricing Service     50 ms
↓
Payment Service    120 ms

اگر این Callها کاملاً Sequential باشند، Latency آن‌ها روی هم جمع می‌شود.

بنابراین شکستن یک Monolith به تعداد زیادی Microservice بدون توجه به Chattiness می‌تواند Latency را افزایش دهد.

Sequential vs Parallel Call

اگر چند Dependency مستقل باشند، می‌توان بعضی Callها را موازی اجرا کرد.

مدل Latency تقریبی نکته
Sequential 50 + 80 + 40 = 170 ms ساده ولی Latency جمع می‌شود
Parallel تقریباً 80 ms به شرط استقلال عملیات‌ها

Parallelism همیشه بهتر نیست؛ ممکن است Load بیشتری روی Dependencyها ایجاد کند.

Caching برای کاهش Latency

Cache یکی از مؤثرترین ابزارها برای کاهش Latency Read است.

Without Cache

API
↓
Database
↓
80 ms


With Cache

API
↓
Redis
↓
5 ms

اما Cache Trade-off دارد:

  • Stale Data
  • Cache Invalidation
  • Cache Miss
  • Cache Stampede

بنابراین نباید فقط برای سریع‌تر شدن، هر داده‌ای را Cache کرد.

Asynchronous Processing

همهٔ کارها لازم نیست در مسیر Sync Request انجام شوند.

مثال Payment

Client
↓
Payment API
↓
Save Transaction
↓
Return Response

Async:
RabbitMQ
↓
Notification
↓
Reporting
↓
Analytics

ارسال Notification و Reporting معمولاً لازم نیست Response اصلی Payment را معطل کند. انتقال این کارها به Background Processing می‌تواند Latency مسیر اصلی را کاهش دهد.

نکته: Async کردن کار، Latency خود آن کار را حذف نمی‌کند؛ فقط آن را از Critical Path کاربر خارج می‌کند.

Timeout بخشی از طراحی Latency است

اگر برای Dependencyها Timeout نداشته باشیم، یک سرویس کند می‌تواند Requestهای زیادی را برای مدت طولانی نگه دارد.

مثال

اگر SLA داخلی Payment API برابر 2 ثانیه باشد، منطقی نیست یک Downstream Service تا 30 ثانیه Timeout داشته باشد.

Timeout باید با Latency Budget کل سیستم سازگار باشد.

Retry چگونه Latency را افزایش می‌دهد؟

Retry می‌تواند Reliability را بهتر کند، اما Latency Request را افزایش می‌دهد. 

First attempt   300 ms
Wait            200 ms
Second attempt  300 ms

Total ≈ 800 ms

اگر چند لایه هم‌زمان Retry داشته باشند، Latency و Load می‌توانند به‌شدت افزایش پیدا کنند.

اصل مهم: Retry Policy باید همراه Timeout، Backoff و Latency Budget طراحی شود.

مثال کامل Latency در Payment System

Client
→
API Gateway
→
Payment Service
→
Database
→
Bank / PSP

فرض کنیم p95 هدف 500 ms باشد:

Component Latency Budget
API Gateway + Network 40 ms
Payment Service 50 ms
Database 80 ms
Bank / PSP 250 ms
Margin 80 ms

Notification، Reporting و Analytics را از Critical Path خارج می‌کنیم و Async انجام می‌دهیم.

سپس برای هر Dependency Metric جداگانه جمع می‌کنیم تا مشخص شود p95 و p99 کجا افزایش پیدا کرده‌اند.

چطور بفهمیم Latency کجا ایجاد شده است؟

فقط Metric کل API کافی نیست. باید بتوانیم زمان هر مرحله را ببینیم.

  • API Latency
  • Database Query Duration
  • External API Duration
  • Queue Wait Time
  • Connection Pool Wait
  • Thread Pool Queue
  • Cache Hit/Miss Latency

Distributed Tracing در معماری Microservice کمک می‌کند مشخص شود Request در کدام Service یا Dependency زمان بیشتری مصرف کرده است.

Trace ساده

POST /payment              820 ms

├── Validation              10 ms
├── SQL Insert              35 ms
├── Fraud Service           70 ms
└── Bank API               680 ms

در این Trace مشخص است که مشکل اصلی Bank API است، نه SQL یا Application.

راهکارهای رایج کاهش Latency

  • بهینه‌سازی Query و Index
  • استفاده از Cache برای Readهای پرتکرار
  • کاهش Remote Call غیرضروری
  • موازی‌سازی Callهای مستقل
  • استفاده از Connection Pooling
  • Reuse کردن HTTP Connection با HttpClientFactory
  • انتقال کارهای غیرضروری به Background Processing
  • کاهش Payload و Serialization Cost
  • قرار دادن Service نزدیک‌تر به User یا Dependency
  • استفاده از CDN برای محتوای مناسب
  • Timeout صحیح برای Dependencyها
  • Scale Out در صورت ایجاد Queueing ناشی از ظرفیت ناکافی

مهم‌ترین اصل این است که قبل از Optimization، Latency را اندازه‌گیری و Bottleneck واقعی را پیدا کنیم.

Trade-offهای کاهش Latency

  • Cache vs Consistency: پاسخ سریع‌تر ممکن است با دادهٔ قدیمی همراه باشد.
  • Parallelism vs Load: Call موازی Latency را کم می‌کند ولی Load بیشتری به Dependencyها می‌دهد.
  • Async vs Consistency: Response سریع‌تر می‌شود اما بعضی عملیات‌ها بعداً تکمیل می‌شوند.
  • Replication vs Freshness: Read Replica می‌تواند Latency Read را بهتر کند ولی Replication Lag وجود دارد.
  • Retry vs Latency: Reliability بهتر می‌شود ولی زمان پاسخ افزایش پیدا می‌کند.

اشتباهات رایج

  • فقط نگاه کردن به Average Latency
  • نادیده گرفتن p95 و p99
  • فرض اینکه مشکل همیشه در Application Code است
  • Remote Call زیاد بین Microserviceها
  • Timeout بسیار بزرگ
  • Retry در چند لایه بدون هماهنگی
  • بهینه‌سازی بدون Measurement و Trace
  • Cache کردن دادهٔ حساس فقط برای سرعت بیشتر
  • نادیده گرفتن Queueing Delay هنگام Load بالا

در مصاحبه System Design چطور درباره Latency صحبت کنیم؟

اگر از شما پرسیدند «چطور Latency این سیستم را کاهش می‌دهی؟»، می‌توانید با این ترتیب جلو بروید:

  1. Latency Target را مشخص کنید؛ مثلاً p95 کمتر از 300 ms.
  2. Critical Path Request را رسم کنید.
  3. Latency Budget را بین Componentها تقسیم کنید.
  4. Metricهای p50، p95 و p99 را بررسی کنید.
  5. Bottleneck را با Trace و Profiling پیدا کنید.
  6. Database Query و Indexها را بررسی کنید.
  7. Remote Call و Sequential Dependencyها را کم کنید.
  8. برای Read مناسب Cache استفاده کنید.
  9. کارهای غیرضروری را Async کنید.
  10. Timeout و Retry Policy را با Budget هماهنگ کنید.
  11. در پایان Trade-offها را توضیح دهید.

نمونهٔ پاسخ کوتاه

«ابتدا p95 و p99 را اندازه می‌گیرم و مسیر کامل Request را با Distributed Tracing بررسی می‌کنم. بعد Latency Budget برای Database، Downstream Service و Application تعیین می‌کنم. Remote Callهای غیرضروری را حذف یا در صورت استقلال موازی می‌کنم، Readهای مناسب را Cache می‌کنم و کارهای غیرضروری مثل Notification و Reporting را از Critical Path خارج می‌کنم. همچنین Timeout و Retry را طوری تنظیم می‌کنم که از Budget کل Request عبور نکنند.»

تمرین کوتاه

یک API میانگین Latency برابر 140 ms دارد، اما p99 آن 4 ثانیه است. بهترین قدم اول چیست؟

  1. افزایش تعداد Instanceها بدون بررسی بیشتر
  2. بررسی Trace و Metricهای Requestهای کند برای پیدا کردن Tail Latency
  3. اضافه کردن Redis به همهٔ Endpointها
  4. تبدیل کل معماری به Microservice
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. Average مناسب است اما p99 بسیار بالاست، بنابراین باید ابتدا Requestهای کند و Component مسئول Tail Latency را با Trace، Query Duration، Queueing و Dependency Metrics پیدا کنیم.

جمع‌بندی

  • Latency مدت‌زمان تکمیل یک Operation است.
  • Latency انتها‌به‌انتها مجموع Network، Application، Database، Queue و Dependencyهاست.
  • Average به‌تنهایی کافی نیست؛ p95 و p99 برای دیدن Tail Latency ضروری‌اند.
  • Throughput تعداد عملیات در واحد زمان است و با Latency یکسان نیست.
  • Latency Budget کمک می‌کند سهم هر Component از زمان کل مشخص شود.
  • Database، Remote Call، Queueing و Retry از منابع رایج Latency هستند.
  • Cache، Parallelism و Async Processing می‌توانند Latency را کاهش دهند اما Trade-off دارند.
  • Distributed Tracing بهترین ابزار برای پیدا کردن محل مصرف زمان در مسیر Request است.
  • در Payment System باید مسیر Critical از Notification و Reporting جدا شود.
  • اول Measurement، بعد Optimization.
