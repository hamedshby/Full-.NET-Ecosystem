Networking & Request Flow

REST

REST یک سبک معماری برای طراحی APIهای مبتنی بر HTTP است که در آن مفاهیم سیستم به شکل Resource مدل می‌شوند و Client با استفاده از Methodهای استاندارد HTTP مانند GET، POST، PUT و DELETE با آن‌ها کار می‌کند.

مسئله چیست؟

فرض کنید یک سیستم Payment داریم و Client باید بتواند یک Payment ایجاد کند، وضعیت آن را بگیرد یا آن را Cancel کند.

می‌توانیم برای هر عملیات یک Endpoint جدا طراحی کنیم: 

POST /createPayment
POST /getPayment
POST /cancelPayment
POST /updatePayment

این API می‌تواند کار کند، اما از مدل و قابلیت‌های استاندارد HTTP استفاده نمی‌کند.

در REST معمولاً ابتدا Resource را مشخص می‌کنیم: 

/payments

سپس نوع عملیات را از طریق HTTP Method مشخص می‌کنیم: 

POST   /payments
GET    /payments/123
PUT    /payments/123
DELETE /payments/123
مدل ذهنی: در REST ابتدا دربارهٔ «چه چیزی» یعنی Resource فکر می‌کنیم، سپس HTTP Method مشخص می‌کند چه عملیاتی روی آن انجام شود.

مفهوم Resource

مهم‌ترین مفهوم در REST، Resource است.

Resource می‌تواند هر مفهوم مهمی در Domain باشد:

  • Customer
  • Payment
  • Transaction
  • Order
  • Merchant
  • Settlement

هر Resource معمولاً توسط یک URI مشخص می‌شود. 

GET /payments/123

در این مثال:

  • payments نوع Resource است.
  • 123 شناسهٔ Resource است.

طراحی صحیح URI

در REST معمولاً URI باید Resource را نمایش دهد، نه Action را.

طراحی ضعیف طراحی RESTful
/getPayment/123 GET /payments/123
/createPayment POST /payments
/deletePayment/123 DELETE /payments/123
/getCustomerPayments/20 GET /customers/20/payments
قاعدهٔ ساده: URI معمولاً باید اسم باشد؛ HTTP Method عملیات را مشخص می‌کند.

HTTP Methodها در REST

Method کاربرد مثال
GET دریافت Resource GET /payments/123
POST ایجاد Resource یا اجرای Command POST /payments
PUT جایگزینی کامل Resource PUT /customers/10
PATCH تغییر بخشی از Resource PATCH /customers/10
DELETE حذف Resource DELETE /customers/10

REST و Statelessness

یکی از Constraintهای اصلی REST این است که Requestها باید Stateless باشند.

یعنی Server نباید برای پردازش Request فعلی وابسته به State مربوط به Request قبلی Client باشد.

هر Request باید اطلاعات لازم برای پردازش خود را همراه داشته باشد. 

GET /payments/123
Authorization: Bearer eyJ...

Server با همین Request می‌تواند هویت Client و Resource موردنظر را تشخیص دهد.

این ویژگی Scale Out کردن Application Serverها را ساده‌تر می‌کند:

Client
→
Load Balancer
→
API Instance 1
API Instance 2
API Instance 3
چون Request به Session داخل یک Instance وابسته نیست، Load Balancer می‌تواند Request بعدی را به Instance دیگری ارسال کند.

Representation

Client معمولاً خود Resource داخل Database را دریافت نمی‌کند؛ بلکه یک Representation از آن دریافت می‌کند.

رایج‌ترین Representation در APIهای امروزی JSON است. 

{
  "id": 123,
  "amount": 500000,
  "status": "Pending",
  "merchantId": 20
}

بنابراین REST به JSON محدود نیست. Representation می‌تواند JSON، XML یا Format دیگری باشد.

استفاده از HTTP Status Code

API باید نتیجهٔ Request را با Status Code مناسب مشخص کند.

Status معنی نمونه
200 OK عملیات موفق دریافت Payment
201 Created Resource ایجاد شده است ایجاد Payment
204 No Content عملیات موفق بدون Response Body Delete
400 Bad Request Request نامعتبر است Validation Error
401 Unauthorized Authentication انجام نشده است Token وجود ندارد
403 Forbidden Client اجازهٔ عملیات ندارد عدم دسترسی Merchant
404 Not Found Resource پیدا نشده است Payment وجود ندارد
409 Conflict Conflict در State سیستم Concurrent Update
500 Internal Server Error خطای داخلی Server Unhandled Exception

مفهوم Idempotency

عملیاتی Idempotent است که اجرای چندبارهٔ یک Request با همان ورودی، اثر نهایی متفاوتی نسبت به اجرای یک‌باره ایجاد نکند.

بعضی HTTP Methodها ذاتاً باید Idempotent باشند:

  • GET
  • PUT
  • DELETE

اما POST معمولاً Idempotent نیست.

این مسئله در Payment بسیار مهم است. 

POST /payments

{
  "amount": 500000,
  "merchantId": 20
}

اگر Client به دلیل Timeout دوباره همین Request را ارسال کند، نباید دو Payment ایجاد شود.

یک روش رایج استفاده از Idempotency Key است: 

POST /payments

Idempotency-Key: 8dc42d1f-43e0-4a74

{
  "amount": 500000,
  "merchantId": 20
}
در سیستم‌های Payment: Idempotency فقط یک موضوع طراحی API نیست؛ بخشی از Reliability سیستم است و از ایجاد تراکنش مالی تکراری جلوگیری می‌کند.

مثال واقعی: Payment API

Client درخواست ایجاد Payment ارسال می‌کند: 

POST /api/v1/payments

Authorization: Bearer ...
Idempotency-Key: 7f425d...

{
  "amount": 500000,
  "merchantId": 1001,
  "callbackUrl": "https://merchant.com/payment/callback"
}

Server پس از ایجاد Resource پاسخ می‌دهد: 

HTTP/1.1 201 Created

Location: /api/v1/payments/87542

{
  "id": 87542,
  "amount": 500000,
  "status": "Pending"
}

سپس Client می‌تواند وضعیت Payment را دریافت کند: 

GET /api/v1/payments/87542

Response: 

{
  "id": 87542,
  "amount": 500000,
  "status": "Completed"
}

تفاوت REST و HTTP

REST و HTTP یک چیز نیستند.

  • HTTP یک Protocol برای انتقال Request و Response است.
  • REST یک Architectural Style برای طراحی سیستم‌های Network-based است.

REST معمولاً روی HTTP پیاده‌سازی می‌شود و از قابلیت‌هایی مانند URI، Method، Header، Status Code و Cache استفاده می‌کند.

هر API که از HTTP و JSON استفاده می‌کند الزاماً RESTful نیست.

Constraintهای اصلی REST

  • Client-Server: Client و Server مسئولیت‌های جدا دارند.
  • Stateless: هر Request باید مستقل باشد.
  • Cacheable: Responseها در صورت مناسب بودن باید قابلیت Cache شدن داشته باشند.
  • Uniform Interface: ارتباط Client و Server باید از یک Interface استاندارد و قابل‌پیش‌بینی استفاده کند.
  • Layered System: Client لازم نیست بداند مستقیماً با Server اصلی، Proxy، API Gateway یا Load Balancer صحبت می‌کند.
  • Code on Demand: Server می‌تواند در صورت نیاز Code برای Client ارسال کند. این Constraint اختیاری است.

اشتباهات رایج

  • استفاده از فعل در تمام URLها مانند /getUser و /createOrder.
  • استفاده از POST برای تمام عملیات.
  • برگرداندن همیشه 200 OK حتی زمانی که Request خطا دارد.
  • نگه‌داشتن Session وابسته به یک Application Instance.
  • نادیده گرفتن Idempotency در عملیات مالی.
  • قرار دادن جزئیات Database در قرارداد API.
  • طراحی Endpointها براساس Tableهای Database به‌جای Domain Resourceها.

REST در System Design

در System Design فقط دانستن GET و POST کافی نیست. هنگام طراحی REST API باید دربارهٔ موضوعات زیر نیز تصمیم بگیریم:

  • Authentication و Authorization
  • API Versioning
  • Pagination
  • Filtering و Sorting
  • Timeout
  • Retry
  • Idempotency
  • Rate Limiting
  • Caching
  • Concurrency Control
  • Error Contract
  • Observability

بنابراین REST فقط Naming Endpointها نیست؛ بخشی از Contract بین Client و Server و یکی از تصمیم‌های مهم در طراحی Interface سیستم است.

تمرین کوتاه

برای دریافت تمام تراکنش‌های Merchant شماره 100 کدام طراحی مناسب‌تر است؟

  1. POST /getMerchantTransactions
  2. GET /merchants/100/transactions
  3. POST /transactions/getByMerchant
  4. GET /getTransactions/100
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲: GET /merchants/100/transactions. Resource موردنظر Transactionهای متعلق به Merchant مشخص است و GET نیز برای دریافت داده استفاده شده است.

جمع‌بندی

  • REST یک Architectural Style برای طراحی APIهای Network-based است.
  • مهم‌ترین مفهوم REST، Resource است.
  • URI معمولاً Resource را مشخص می‌کند و HTTP Method نوع عملیات را.
  • REST از GET، POST، PUT، PATCH و DELETE برای عملیات مختلف استفاده می‌کند.
  • RESTful API باید تا حد ممکن Stateless باشد.
  • HTTP Status Code بخشی از قرارداد API است.
  • Idempotency مخصوصاً در Payment APIها اهمیت زیادی دارد.
  • REST با HTTP یکسان نیست؛ HTTP Protocol است و REST Architectural Style.
  • طراحی REST API خوب فقط Endpoint Naming نیست؛ Versioning، Security، Retry، Timeout، Rate Limiting و Error Handling نیز بخشی از طراحی هستند.
