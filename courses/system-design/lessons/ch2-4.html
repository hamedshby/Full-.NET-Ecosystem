Networking & Request Flow

gRPC

gRPC یک فریم‌ورک ارتباطی سریع و strongly typed برای ارتباط بین سرویس‌ها است که معمولاً از HTTP/2 و Protocol Buffers استفاده می‌کند و برای ارتباط داخلی Microserviceها بسیار مناسب است.

مسئله چیست؟

فرض کنید در یک سیستم Payment چند Microservice داریم:

  • Payment Service
  • Account Service
  • Merchant Service
  • Fraud Service

Payment Service برای انجام تراکنش باید اطلاعات Merchant را از Merchant Service بگیرد.

می‌توانیم این ارتباط را با REST پیاده‌سازی کنیم: 

GET /api/merchants/1001

اما در ارتباط داخلی بین سرویس‌ها گاهی نیاز داریم:

  • Latency پایین‌تر باشد.
  • Payload کوچک‌تر باشد.
  • Contract بین Client و Server دقیق باشد.
  • Client Code به صورت خودکار تولید شود.
  • Streaming داشته باشیم.

یکی از گزینه‌های مناسب در چنین شرایطی gRPC است.

gRPC چیست؟

gRPC یک Remote Procedure Call Framework است.

یعنی Client می‌تواند یک Method روی Server را تقریباً مانند یک Method محلی صدا بزند. 

var merchant =
    await merchantClient.GetMerchantAsync(request);

اما پشت صحنه این Call از طریق Network انجام می‌شود.

Payment Service
→
gRPC Client
→
HTTP/2
→
Merchant Service

Protocol Buffers

gRPC معمولاً برای تعریف Contract از Protocol Buffers یا همان Protobuf استفاده می‌کند.

Contract داخل فایل .proto تعریف می‌شود. 

syntax = "proto3";

service MerchantGrpc {
  rpc GetMerchant(GetMerchantRequest)
      returns (MerchantResponse);
}

message GetMerchantRequest {
  int64 merchant_id = 1;
}

message MerchantResponse {
  int64 merchant_id = 1;
  string name = 2;
  bool is_active = 3;
}

از روی این فایل، ابزارهای gRPC می‌توانند Client و Server Code موردنیاز را تولید کنند.

مزیت مهم: Client و Server یک Contract مشخص دارند و بسیاری از خطاهای Serialization یا تغییر قرارداد در زمان Compile مشخص می‌شوند.

Binary Serialization

REST APIها معمولاً داده را به شکل JSON ارسال می‌کنند. 

{
  "merchantId": 1001,
  "name": "Merchant A",
  "isActive": true
}

gRPC معمولاً از Protobuf استفاده می‌کند که یک Format باینری است.

در نتیجه Payload معمولاً از JSON کوچک‌تر است و Serialization و Deserialization نیز سریع‌تر انجام می‌شود.

این مزیت در سیستم‌هایی با تعداد زیاد Request یا ارتباط زیاد بین Microserviceها می‌تواند مهم باشد.

چرا HTTP/2؟

gRPC معمولاً از HTTP/2 استفاده می‌کند.

HTTP/2 قابلیت‌هایی مانند موارد زیر دارد:

  • Multiplexing
  • Persistent Connections
  • Binary Framing
  • Header Compression
  • Streaming

Multiplexing اجازه می‌دهد چند Request و Response به صورت همزمان روی یک Connection ارسال شوند. 

Connection
   ├── Request 1
   ├── Request 2
   ├── Request 3
   └── Request 4

این ویژگی برای ارتباط Service-to-Service با تعداد Call زیاد بسیار مفید است.

انواع Call در gRPC

gRPC چهار مدل اصلی Communication دارد.

1. Unary RPC

Client یک Request می‌فرستد و Server یک Response برمی‌گرداند. 

Request → Response

مثال: 

GetMerchant(merchantId)
    → MerchantResponse

این مدل شبیه Request/Response معمولی REST است.

2. Server Streaming

Client یک Request می‌فرستد و Server چند Response ارسال می‌کند. 

Request → Response
          Response
          Response
          Response

مثال: 

GetTransactions()
    → Transaction 1
    → Transaction 2
    → Transaction 3
    → ...

3. Client Streaming

Client چند Message ارسال می‌کند و Server در پایان یک Response می‌دهد. 

Request
Request
Request
   ↓
Response

4. Bidirectional Streaming

Client و Server می‌توانند همزمان چند Message برای یکدیگر ارسال کنند. 

Client ←→ Server

این مدل برای Real-Time Communication یا Streamهای طولانی مناسب است.

چه زمانی از gRPC استفاده کنیم؟

gRPC معمولاً برای این سناریوها مناسب است:

  • ارتباط داخلی Microserviceها
  • سیستم‌های Low Latency
  • تعداد زیاد Service-to-Service Call
  • سیستم‌هایی با Contract دقیق
  • Streaming
  • سیستم‌های Polyglot

برای مثال در معماری Payment: 

Payment Service
      │
      ├── gRPC → Merchant Service
      │
      ├── gRPC → Account Service
      │
      └── gRPC → Fraud Service

آیا برای Public API مناسب است؟

gRPC می‌تواند برای Public API استفاده شود، اما معمولاً REST انتخاب ساده‌تر و رایج‌تری است.

یکی از معماری‌های رایج:

Mobile / Web
→
REST API / API Gateway
→
Payment Service
→
gRPC
→
Internal Services
یک الگوی رایج این است که ارتباط Client خارجی با REST انجام شود و ارتباط داخلی بین Microserviceها با gRPC.

مثال ساده در .NET

Proto Contract: 

syntax = "proto3";

option csharp_namespace = "Payment.Grpc";

service PaymentGrpc {
  rpc GetPayment(GetPaymentRequest)
      returns (GetPaymentResponse);
}

message GetPaymentRequest {
  int64 payment_id = 1;
}

message GetPaymentResponse {
  int64 payment_id = 1;
  int64 amount = 2;
  string status = 3;
}

پیاده‌سازی Server: 

public class PaymentGrpcService
    : PaymentGrpc.PaymentGrpcBase
{
    public override Task<GetPaymentResponse> GetPayment(
        GetPaymentRequest request,
        ServerCallContext context)
    {
        return Task.FromResult(
            new GetPaymentResponse
            {
                PaymentId = request.PaymentId,
                Amount = 500000,
                Status = "Completed"
            });
    }
}

Client: 

var response =
    await grpcClient.GetPaymentAsync(
        new GetPaymentRequest
        {
            PaymentId = 87542
        });

Console.WriteLine(response.Status);

Deadline و Timeout

یکی از نکات مهم در Distributed System این است که هیچ Call شبکه‌ای نباید بدون Timeout باشد.

در gRPC می‌توان Deadline مشخص کرد: 

var response =
    await client.GetMerchantAsync(
        request,
        deadline: DateTime.UtcNow.AddSeconds(2));

اگر سرویس مقصد در زمان مشخص پاسخ ندهد، Call متوقف می‌شود.

بدون Timeout، یک سرویس کند می‌تواند Threadها و Connectionهای سرویس‌های دیگر را نیز درگیر کند و باعث Cascading Failure شود.

مدیریت خطا در gRPC

gRPC به جای HTTP Status Codeهای معمول REST، مجموعه‌ای از Status Codeهای استاندارد دارد.

Status معنی
OK عملیات موفق
INVALID_ARGUMENT Request نامعتبر
NOT_FOUND Resource پیدا نشده
ALREADY_EXISTS Resource از قبل وجود دارد
PERMISSION_DENIED عدم دسترسی
UNAVAILABLE سرویس در دسترس نیست
DEADLINE_EXCEEDED Timeout
INTERNAL خطای داخلی سرویس

مثال واقعی در سیستم Payment

فرض کنید Payment Service درخواست پرداخت دریافت کرده است: 

POST /api/payments

Payment Service برای ادامه عملیات باید Merchant را بررسی کند.

Client
→
Payment API
→
Payment Service
→ gRPC →
Merchant Service

Payment Service می‌تواند چنین Callی انجام دهد: 

var merchant =
    await merchantGrpcClient.GetMerchantAsync(
        new GetMerchantRequest
        {
            MerchantId = request.MerchantId
        });

Merchant Service نتیجه را برمی‌گرداند: 

{
    MerchantId = 1001,
    IsActive = true
}

Payment Service سپس عملیات Payment را ادامه می‌دهد.

gRPC همچنان یک ارتباط Synchronous است

نکته مهم این است که استفاده از gRPC مشکل Coupling زمانی بین سرویس‌ها را حذف نمی‌کند.

اگر Payment Service برای پاسخ دادن حتماً منتظر Merchant Service باشد: 

Payment Service
      ↓
wait
      ↓
Merchant Service

در صورت Down بودن Merchant Service، Payment Service نیز ممکن است نتواند Request را کامل کند.

بنابراین کنار gRPC باید به موارد زیر نیز فکر کنیم:

  • Timeout
  • Retry
  • Circuit Breaker
  • Fallback
  • Bulkhead
  • Observability

gRPC vs Message Broker

gRPC و RabbitMQ یا Kafka جایگزین مستقیم یکدیگر نیستند.

ویژگی gRPC Message Broker
نوع ارتباط معمولاً Synchronous Asynchronous
نیاز به پاسخ فوری بله معمولاً خیر
Temporal Coupling بیشتر کمتر
Streaming بله مدل متفاوت
Event Processing انتخاب اصلی نیست بسیار مناسب

مثال: 

بررسی موجودی حساب
→ gRPC

ارسال PaymentCompleted Event
→ RabbitMQ / Kafka

اشتباهات رایج

  • استفاده از gRPC برای تمام ارتباطات بدون بررسی نیاز واقعی.
  • نداشتن Deadline یا Timeout.
  • Retry بدون درنظر گرفتن Idempotency.
  • ایجاد زنجیره طولانی از Callهای Synchronous.
  • ایجاد Contractهای بسیار بزرگ در فایل Proto.
  • وابسته کردن Domain Model مستقیماً به Proto Model.
  • استفاده از gRPC به جای Event-driven Communication در جایی که پاسخ فوری لازم نیست.

gRPC در System Design

هنگام انتخاب gRPC فقط Performance را بررسی نکنید.

باید این سؤال‌ها را نیز بررسی کنید:

  • آیا ارتباط Synchronous لازم است؟
  • Latency چقدر مهم است؟
  • آیا Client مرورگر است؟
  • آیا Streaming نیاز داریم؟
  • Timeout چقدر باشد؟
  • Retry Policy چیست؟
  • آیا عملیات Idempotent است؟
  • اگر سرویس مقصد Down شود چه اتفاقی می‌افتد؟
  • Versioning فایل Proto چگونه مدیریت می‌شود؟
  • Observability و Distributed Tracing چگونه انجام می‌شود؟
انتخاب بین REST، gRPC و Messaging باید براساس نیاز سیستم باشد، نه صرفاً سریع‌تر بودن یک تکنولوژی.

تمرین کوتاه

در یک سیستم Payment، Payment Service برای ادامه تراکنش باید موجودی حساب را بلافاصله از Account Service دریافت کند. کدام گزینه مناسب‌تر است؟

  1. RabbitMQ Event
  2. gRPC Unary Call
  3. Background Job
  4. Database Polling
مشاهده پاسخ پیشنهادی

گزینه ۲ یعنی gRPC Unary Call. چون Payment Service برای ادامه عملیات به یک Response فوری از Account Service نیاز دارد.

جمع‌بندی

  • gRPC یک Framework برای Remote Procedure Call است.
  • معمولاً از HTTP/2 و Protocol Buffers استفاده می‌کند.
  • Protobuf یک Contract strongly typed بین Client و Server ایجاد می‌کند.
  • Payload باینری معمولاً کوچک‌تر و سریع‌تر از JSON است.
  • gRPC از Unary و انواع مختلف Streaming پشتیبانی می‌کند.
  • gRPC برای ارتباط داخلی Microserviceها انتخاب بسیار مناسبی است.
  • REST معمولاً برای Public API و Browser Clientها ساده‌تر است.
  • gRPC همچنان می‌تواند Temporal Coupling ایجاد کند.
  • Timeout، Retry، Circuit Breaker و Idempotency در طراحی gRPC مهم هستند.
  • gRPC و Message Broker کاربرد متفاوتی دارند؛ یکی معمولاً برای Request/Response فوری و دیگری برای ارتباط Asynchronous مناسب است.
