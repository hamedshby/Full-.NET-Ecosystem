فصل 1 از ۱۰

Fundamentals

Vertical vs Horizontal Scaling

وقتی Throughput یا Capacity یک سیستم کافی نیست، دو مسیر اصلی برای افزایش ظرفیت وجود دارد: قوی‌تر کردن یک Node (Scale Up) یا اضافه‌کردن Nodeهای بیشتر (Scale Out). در این درس یاد می‌گیریم این دو استراتژی چه تفاوتی دارند، هرکدام چه محدودیت‌هایی دارند و چگونه بین آن‌ها تصمیم بگیریم.

از یک Order Service شروع کنیم

فرض کنید Order Service روی یک Server با ۴ Core و ۸ گیگابایت Memory اجرا می‌شود و در حال حاضر ۴۰۰ RPS را پاسخ می‌دهد. با افزایش کاربران، تیم باید تصمیم بگیرد: همین Server را به ۱۶ Core و ۳۲ گیگابایت ارتقا دهد، یا به‌جای یک Server قوی‌تر، ۴ Server معمولی پشت یک Load Balancer قرار دهد.

این دقیقاً همان انتخاب بین Vertical Scaling و Horizontal Scaling است؛ انتخابی که نه‌تنها روی Capacity، بلکه روی Cost، Reliability و پیچیدگی معماری هم اثر می‌گذارد.

تعریف دقیق دو استراتژی

  • Vertical Scaling (Scale Up): افزایش منابع یک Node واحد — CPU قوی‌تر، Memory بیشتر، Disk سریع‌تر یا NIC پرسرعت‌تر — بدون تغییر در تعداد Nodeها.
  • Horizontal Scaling (Scale Out): اضافه‌کردن Node یا Instance بیشتر و تقسیم Workload بین آن‌ها، معمولاً از طریق یک Load Balancer یا مکانیزم Partitioning.
مدل ذهنی: Vertical Scaling مثل جایگزین‌کردن یک ماشین‌ظرفشویی کوچک با یک مدل بزرگ‌تر و سریع‌تر است. Horizontal Scaling مثل اضافه‌کردن چند ماشین‌ظرفشویی کنار هم و تقسیم ظرف‌ها بین آن‌هاست.

مقایسهٔ کلی

معیار Vertical Scaling Horizontal Scaling
پیچیدگی پیاده‌سازی کم — معمولاً نیازی به تغییر Application نیست بیشتر — نیاز به Load Balancer، هماهنگی State و گاهی Partitioning
سقف رشد محدود به بزرگ‌ترین سخت‌افزار موجود در تئوری با اضافه‌کردن Node ادامه‌دار است
Single Point of Failure بله — از کار افتادن همان یک Node، کل سرویس را متوقف می‌کند کمتر — از کار افتادن یک Node، ظرفیت را کم می‌کند نه صفر
Downtime هنگام ارتقا معمولاً نیاز به Restart یا Migration دارد می‌توان Node جدید را بدون Downtime اضافه کرد
هزینه رشد هزینه در سخت‌افزار سطح بالا معمولاً نمایی است رشد هزینه نزدیک‌تر به خطی، اما هزینهٔ عملیاتی بیشتر
سازگاری با State برای Stateful Systemها (مثل اغلب Databaseها) طبیعی‌تر است برای Stateless Applicationها ساده، برای Stateful نیازمند طراحی اضافه

چرا Stateless بودن برای Horizontal Scaling مهم است؟

وقتی هیچ Session یا Local State‌ای روی یک Instance خاص ذخیره نشود، هر Request می‌تواند توسط هر Instance پردازش شود و Load Balancer آزادانه Traffic را تقسیم می‌کند.

مثال

اگر Session کاربر در Memory یک Instance خاص نگه‌داری شود، Requestهای بعدی همان کاربر باید حتماً به همان Instance برسند (Sticky Session)، که Load Balancing را نامتوازن می‌کند و Scale Out را پیچیده‌تر می‌سازد. راه‌حل رایج، انتقال Session به یک Store مشترک مثل Redis است.

Load Balancer باید سلامت هر Instance را با Health Check تشخیص دهد و در صورت خرابی، Traffic را از آن Instance دور کند. الگوریتم‌های رایج توزیع Load عبارتند از Round Robin، Least Connections و Weighted Routing بر اساس ظرفیت هر Instance.

محدودیت Vertical Scaling در Database

بسیاری از Databaseهای رابطه‌ای به‌طور طبیعی Vertical Scale می‌شوند، چون Consistency و Transaction در یک Node واحد ساده‌تر مدیریت می‌شود. اما این مسیر سقف دارد.

مثال

SQL Server: 8 Core  → 4000 TPS
SQL Server: 32 Core → 9000 TPS
SQL Server: 64 Core → 10500 TPS (رشد کاهنده)

وقتی حتی بزرگ‌ترین Instance موجود دیگر جواب‌گو نیست، تیم باید به سراغ Read Replica، Partitioning یا Sharding برود؛ یعنی نوعی Horizontal Scaling مخصوص Dataها، که پیچیدگی‌های خودش را دارد از جمله انتخاب Shard Key، Cross-Shard Query و Rebalancing داده هنگام اضافه‌کردن Shard جدید.

تأثیر روی Reliability

در Vertical Scaling، تمام Traffic روی یک Node متمرکز است؛ هر مشکل سخت‌افزاری یا Restart باعث Downtime کامل می‌شود.

در Horizontal Scaling، از کار افتادن یک Instance فقط بخشی از Capacity را کم می‌کند و اگر Redundancy کافی طراحی شده باشد، کاربر اصلاً متوجه قطعی نمی‌شود. به همین دلیل Horizontal Scaling معمولاً پایه‌ای برای High Availability نیز هست.

هزینه و نقطهٔ بازگشت

هزینهٔ سخت‌افزار در سطوح بالا معمولاً نمایی رشد می‌کند؛ یک Server با ۶۴ Core لزوماً دو برابر یک Server با ۳۲ Core هزینه ندارد، بلکه معمولاً بیشتر است. در مقابل، افزودن Instanceهای معمولی هزینه‌ای نزدیک به خطی دارد، اما هزینهٔ عملیاتی (Load Balancer، Monitoring، Deployment، Networking) را اضافه می‌کند.

در عمل بسیاری از تیم‌ها ابتدا با Vertical Scaling شروع می‌کنند چون ساده‌تر و سریع‌تر است، و وقتی به سقف عملی یا اقتصادی رسیدند به‌سمت Horizontal Scaling حرکت می‌کنند.

Trade-offهای اصلی

  • سادگی vs مقیاس‌پذیری بلندمدت: Vertical Scaling سریع و بی‌دردسر است ولی سقف دارد.
  • هزینهٔ سخت‌افزار vs هزینهٔ عملیاتی: Horizontal Scaling هزینهٔ واحد را پایین نگه می‌دارد ولی پیچیدگی عملیاتی می‌آورد.
  • Consistency vs Availability: توزیع داده بین چند Node اغلب طراحی Consistency را دشوارتر می‌کند.
  • Single Point of Failure vs Coordination Overhead: چند Node ریسک قطعی کامل را کم می‌کند اما نیاز به Coordination (مثل Leader Election یا Consensus) ایجاد می‌کند.

اشتباهات رایج

  • فرض این‌که Horizontal Scaling همیشه بهترین گزینه است، حتی برای Bottleneckهایی که در Database یا یک Dependency مشترک هستند
  • Scale Out کردن یک Application که هنوز Stateful طراحی شده
  • نادیده گرفتن Sticky Session و اثر آن روی توزیع Load
  • ادامهٔ Vertical Scaling تا رسیدن به سقف اقتصادی، بدون برنامه‌ریزی برای مسیر بعدی
  • Scale Out کردن Applicationها بدون رفع Bottleneck واقعی در Database
  • نداشتن Health Check مناسب برای Instanceهای جدید

در مصاحبه System Design چطور دربارهٔ این موضوع صحبت کنیم؟

اگر پرسیدند «چطور این سرویس را Scale می‌کنید؟»، مستقیم نگویید «چند Instance اضافه می‌کنم».

  1. ابتدا مشخص کنید Bottleneck فعلی کجاست (Application یا Database یا Dependency دیگر).
  2. بررسی کنید Application Stateless است یا Stateful.
  3. اگر Bottleneck در Application است و Stateless است، Horizontal Scaling پیشنهاد دهید.
  4. اگر Bottleneck در Database است، ابتدا Vertical Scaling یا Read Replica را بررسی کنید و در صورت نیاز به Sharding فکر کنید.
  5. Trade-off هزینه، پیچیدگی و Reliability را توضیح دهید.
  6. نتیجه را با Load Test اعتبارسنجی کنید.

نمونهٔ پاسخ کوتاه

«اول باید ببینم Bottleneck کجاست. اگر Application Layer است و Stateless طراحی شده، پشت یک Load Balancer آن را Horizontal Scale می‌کنم. اگر مشکل از Database است، ابتدا Vertical Scaling و Read Replica را بررسی می‌کنم و اگر کافی نبود، به سراغ Partitioning یا Sharding می‌روم. در نهایت تصمیم را با Load Test و بر اساس SLO، نه فقط حدس، اعتبارسنجی می‌کنم.»

تمرین کوتاه

یک Notification Service به‌صورت Stateless روی یک Instance اجرا می‌شود و در ساعات پیک به سقف CPU می‌رسد، در حالی که Database آن هنوز زیر ۳۰٪ Load است. بهترین گام بعدی چیست؟

  1. ارتقای Database به یک نسخهٔ قوی‌تر
  2. اضافه‌کردن چند Instance دیگر از Notification Service پشت Load Balancer
  3. افزایش Connection Pool دیتابیس
  4. تبدیل کل سیستم به Batch Processing
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. چون Bottleneck در Application Layer است، Service Stateless است و Database هنوز ظرفیت آزاد دارد، Horizontal Scaling سرویس ساده‌ترین و مؤثرترین راه‌حل است.

جمع‌بندی

  • Vertical Scaling یعنی قوی‌ترکردن یک Node؛ Horizontal Scaling یعنی اضافه‌کردن Node بیشتر.
  • Vertical Scaling ساده‌تر است اما سقف سخت‌افزاری و اقتصادی دارد و Single Point of Failure می‌ماند.
  • Horizontal Scaling در تئوری نامحدود است اما نیاز به Load Balancer، Health Check و اغلب Stateless بودن دارد.
  • Stateful Applicationها برای Horizontal Scaling باید State را به یک Store مشترک منتقل کنند.
  • Database معمولاً ابتدا Vertical Scale می‌شود و در سقف، به Read Replica یا Sharding می‌رود.
  • Horizontal Scaling معمولاً Reliability بهتری می‌دهد چون قطعی یک Node، کل سیستم را از کار نمی‌اندازد.
  • تصمیم درست همیشه با پیدا کردن Bottleneck واقعی شروع می‌شود، نه با انتخاب پیش‌فرض یکی از دو استراتژی.
