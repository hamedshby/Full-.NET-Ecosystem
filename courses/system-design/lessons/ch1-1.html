Fundamentals

Scalability

Scalability یعنی سیستم بتواند با افزایش Workload، سطح سرویس قابل‌قبولی را حفظ کند و ظرفیت آن با هزینه و پیچیدگی منطقی افزایش پیدا کند. در این درس از تعریف و اندازه‌گیری ظرفیت شروع می‌کنیم، Bottleneck را پیدا می‌کنیم و سپس Scale Up، Scale Out و یک مثال واقعی Payment در .NET را بررسی می‌کنیم.

از یک فروشگاه آنلاین شروع کنیم

یک فروشگاه در روزهای عادی در هر ثانیه ۱۰۰ درخواست دریافت می‌کند و صفحهٔ محصول را در کمتر از ۲۰۰ میلی‌ثانیه نمایش می‌دهد. با شروع یک کمپین، ترافیک به ۱۰۰۰ درخواست در ثانیه می‌رسد؛ زمان پاسخ از ۲۰۰ میلی‌ثانیه به ۵ ثانیه افزایش پیدا می‌کند و بخشی از درخواست‌ها با خطا مواجه می‌شوند.

سیستم هنوز روشن است، اما نتوانسته کیفیت سرویس خود را زیر بار جدید حفظ کند. مسئله فقط «کندشدن» نیست؛ ظرفیت فعلی با شکل تازهٔ Workload متناسب نیست.

مدل ذهنی: یک جاده را تصور کنید. اگر تعداد خودروها ده برابر شود، افزودن یک خط شاید موقتاً کمک کند؛ اما اگر گلوگاه اصلی عوارضی باشد، پهن‌ترکردن جاده مشکل را حل نمی‌کند. در سیستم نیز ابتدا باید Bottleneck را پیدا کنیم.

Scalability دقیقاً چیست؟

Workload مقدار و نوع کاری است که سیستم باید انجام دهد؛ مانند تعداد درخواست‌ها، تعداد کاربران هم‌زمان، حجم داده، تعداد پیام‌ها یا نرخ تراکنش‌ها. افزایش Workload می‌تواند تدریجی، ناگهانی یا فصلی باشد.

یک سیستم Scalable است اگر بتوانیم برای پاسخ‌گویی به Workload بیشتر، منابع یا معماری آن را توسعه دهیم و کیفیت مورد انتظار را حفظ کنیم. «قابل توسعه بودن» بخش مهم تعریف است: سیستمی که اکنون سریع است اما برای دو برابرشدن بار باید از نو نوشته شود، Scalability مناسبی ندارد.

Scalability یک ویژگی صفر و یک نیست. باید بگوییم سیستم تا چه Workload، با چه سطح سرویس و با چه هزینه‌ای مقیاس‌پذیر است.

تعریف قابل‌اندازه‌گیری

«سرویس جست‌وجو باید تا ۵۰۰۰ درخواست در ثانیه را پشتیبانی کند؛ p95 Latency کمتر از ۳۰۰ میلی‌ثانیه باشد؛ نرخ خطا از ۰٫۱٪ بیشتر نشود و افزودن هر Instance ظرفیت را به‌صورت قابل‌پیش‌بینی افزایش دهد.»

پیش از Scaling چه چیزهایی را اندازه می‌گیریم؟

عبارت «کاربر زیاد» برای طراحی کافی نیست. ابتدا باید ورودی سیستم و کیفیت خروجی را با Metricهای مشخص توصیف کنیم:

  • Request Rate: تعداد درخواست در واحد زمان؛ معمولاً با Requests Per Second یا RPS بیان می‌شود.
  • Concurrent Users: تعداد کاربرانی که هم‌زمان با سیستم تعامل دارند. این عدد با کل کاربران ثبت‌نام‌شده یکسان نیست.
  • Throughput: مقدار کار تکمیل‌شده در واحد زمان؛ برای مثال تعداد Order پردازش‌شده در ثانیه.
  • Latency: مدت‌زمان پاسخ به یک درخواست. به‌جای تکیه بر Average، معمولاً Percentileهایی مانند p95 و p99 نیز بررسی می‌شوند.
  • Error Rate: نسبت درخواست‌های ناموفق به کل درخواست‌ها.
  • Resource Utilization: مصرف CPU، Memory، Network، Disk I/O، Connection Pool و Thread Pool.
  • Data Volume: حجم فعلی داده، نرخ رشد آن و الگوی Read و Write.

Service Level Objective یا SLO هدف قابل‌اندازه‌گیری سرویس است. برای مثال «۹۵٪ درخواست‌ها زیر ۳۰۰ میلی‌ثانیه پاسخ بگیرند». ظرفیت زمانی تمام شده است که با افزایش Workload دیگر نتوانیم SLO را حفظ کنیم، نه صرفاً زمانی که CPU به ۱۰۰٪ برسد.

یک تخمین سادهٔ ظرفیت

فرض کنید فروشگاه ۲ میلیون کاربر فعال روزانه دارد. هر کاربر به‌طور متوسط ۲۰ درخواست ایجاد می‌کند و ۱۰٪ کل درخواست‌های روز در شلوغ‌ترین ساعت وارد می‌شوند.

  1. تعداد درخواست روزانه: ۲,۰۰۰,۰۰۰ × ۲۰ = ۴۰,۰۰۰,۰۰۰
  2. درخواست در شلوغ‌ترین ساعت: ۴۰,۰۰۰,۰۰۰ × ۱۰٪ = ۴,۰۰۰,۰۰۰
  3. میانگین RPS در آن ساعت: ۴,۰۰۰,۰۰۰ ÷ ۳۶۰۰ ≈ ۱۱۱۲

ترافیک درون همان ساعت نیز یکنواخت نیست. اگر برای Burst ضریب ۲٫۵ در نظر بگیریم، طراحی اولیه باید حدود ۲۷۸۰ RPS را تحمل کند. سپس با Load Test بررسی می‌کنیم این فرض چقدر به رفتار واقعی نزدیک است.

نکته: تخمین، جای اندازه‌گیری را نمی‌گیرد. هدف آن مشخص‌کردن مرتبهٔ بزرگی مسئله، آشکارکردن فرض‌ها و انتخاب نقطهٔ شروع برای آزمایش است.

سیستم از چه جهت‌هایی رشد می‌کند؟

افزایش Workload همیشه به معنای افزایش RPS نیست. نوع رشد تعیین می‌کند کدام بخش معماری باید تغییر کند.

نوع رشد نمونه فشار محتمل
Traffic Growth RPS از ۵۰۰ به ۵۰۰۰ می‌رسد CPU، Connection و Downstream Service
Data Growth جدول Order از ۱۰ میلیون به یک میلیارد Row می‌رسد Index، Storage، Query و Backup
Concurrency Growth تعداد Connectionهای هم‌زمان ده برابر می‌شود Memory، Thread Pool و Connection Pool
Geographic Growth کاربران از چند قاره به سرویس متصل می‌شوند Network Latency، Data Placement و Consistency

دو جهت اصلی Scaling

برای افزایش ظرفیت، معمولاً دو مسیر اصلی داریم: Scale Up و Scale Out. این دو رقیب مطلق نیستند و در بسیاری از سیستم‌های واقعی هم‌زمان استفاده می‌شوند.

Vertical Scaling — بزرگ‌تر کردن همان ماشین

در Vertical Scaling یا Scale Up، منابع همان Server را بیشتر می‌کنیم؛ برای مثال CPU، RAM یا Disk سریع‌تر اضافه می‌کنیم.

مثال

اگر SQL Server به‌دلیل کمبود Memory تحت فشار باشد، افزایش RAM می‌تواند بدون تغییر معماری ظرفیت را بالا ببرد. این راه‌حل برای شروع ساده و مؤثر است، اما یک سقف سخت‌افزاری دارد.

  • مزیت: ساده، سریع و معمولاً بدون تغییر Code.
  • محدودیت: سقف سخت‌افزاری و هزینهٔ زیاد ماشین‌های بزرگ.
  • ریسک: اگر فقط یک Instance داشته باشیم، همچنان Single Point of Failure داریم.

Horizontal Scaling — اضافه کردن Instance

در Horizontal Scaling یا Scale Out، به‌جای قوی‌تر کردن یک ماشین، چند Instance از سرویس اجرا می‌کنیم و Load را بین آن‌ها تقسیم می‌کنیم.

برای مثال ممکن است Application Serverها Scale Out شوند، اما Database در مرحلهٔ اول Scale Up شود. تصمیم درست به Bottleneck، هزینه، Availability و پیچیدگی عملیاتی بستگی دارد.

چرا Stateless بودن برای Scale Out مهم است؟

فرض کنید کاربر Login می‌کند و Session او فقط داخل Memory یک API Instance ذخیره شده است. Request بعدی ممکن است توسط Load Balancer به Instance دیگری برسد که آن Session را ندارد.

به همین دلیل سرویس‌هایی که قرار است Horizontal Scale شوند بهتر است تا جای ممکن Stateless باشند؛ یعنی Instance خاصی مالک State حیاتی کاربر یا Request نباشد.

در ASP.NET Core

به‌جای نگه‌داشتن State مهم داخل Memory هر Pod، دادهٔ مشترک می‌تواند در Database، Redis یا Storage مشترک نگه‌داری شود. این کار باعث می‌شود هر Request بتواند توسط هر Instance سالم پردازش شود.

قاعدهٔ کاربردی: اگر بتوانید هر Instance را بدون نگرانی حذف و با Instance دیگری جایگزین کنید، Horizontal Scaling و Auto Scaling بسیار ساده‌تر می‌شود.

Bottleneck ظرفیت سیستم را تعیین می‌کند

Bottleneck بخشی است که زودتر از اجزای دیگر به محدودیت می‌رسد و Throughput کل سیستم را محدود می‌کند. اگر Application را از ۲ Instance به ۱۰ Instance افزایش دهیم اما همهٔ آن‌ها منتظر یک Database اشباع‌شده باشند، ظرفیت نهایی تقریباً تغییری نمی‌کند.

نشانهٔ Bottleneck فقط مصرف CPU نیست. Lockهای Database، Query کند، محدودیت Connection Pool، Disk I/O، صف رو‌به‌رشد، API خارجی یا حتی یک Lock در Code می‌توانند ظرفیت را محدود کنند. به همین دلیل Scaling باید بر پایهٔ Metric و Profiling انجام شود.

اصل مهم

هر بار که یک Bottleneck را برطرف می‌کنیم، Bottleneck بعدی آشکار می‌شود. Scalability یک پروژهٔ یک‌باره نیست؛ چرخه‌ای از اندازه‌گیری، آزمایش، اصلاح و اندازه‌گیری دوباره است.

ابزارهای رایج برای افزایش ظرفیت

هیچ ابزار واحدی همهٔ مسئله‌های Scalability را حل نمی‌کند. هر تکنیک فشار نوع مشخصی از Workload را کاهش می‌دهد:

  • Stateless Application Instances: نگه‌نداشتن Session محلی باعث می‌شود Load Balancer بتواند درخواست را به هر Instance سالم بفرستد.
  • Caching: دادهٔ پرتکرار را نزدیک‌تر به مصرف‌کننده نگه می‌دارد و Readهای تکراری از Database یا سرویس خارجی را کم می‌کند.
  • Asynchronous Processing: کارهای غیرضروری برای پاسخ فوری، مانند ارسال Email، در Queue قرار می‌گیرند تا Request اصلی زودتر تمام شود و Burst جذب شود.
  • Database Indexing و Query Optimization: مقدار داده‌ای را که Database برای پاسخ باید بررسی کند کاهش می‌دهد.
  • Read Replica: Readها را میان Replicaها پخش می‌کند، به شرط آن‌که تأخیر Replication با نیاز Consistency سازگار باشد.
  • Partitioning و Sharding: داده و Workload را میان چند Partition تقسیم می‌کند؛ اما Queryهای بین Partition، Rebalancing و Hot Partition را پیچیده‌تر می‌سازد.
  • CDN: محتوای Cacheable را از Location نزدیک‌تر به کاربر ارائه می‌دهد و بار Origin را کاهش می‌دهد.
  • Backpressure و Rate Limiting: اجازه نمی‌دهد بار ورودی کنترل‌نشده همهٔ منابع را مصرف و کل سیستم را ناپایدار کند.

هر تکنیک Trade-off دارد. برای نمونه Cache، Latency و بار Database را کاهش می‌دهد، اما مسئلهٔ Stale Data و Cache Invalidation را به سیستم اضافه می‌کند.

یک مسیر رشد مرحله‌به‌مرحله

برای یک محصول تازه معمولاً لازم نیست از روز اول پیچیده‌ترین معماری Distributed را بسازیم. یک مسیر معقول می‌تواند چنین باشد:

  1. Workload و SLO را تعریف کنید: RPS، الگوی Peak، حجم داده، Latency و Error Rate هدف را بنویسید.
  2. یک معماری ساده و قابل‌اندازه‌گیری بسازید: Application و Database را Instrument کنید تا Metric، Log و Trace قابل استفاده داشته باشید.
  3. Baseline بگیرید: با Load Test مشخص کنید سیستم فعلی تا چه باری SLO را حفظ می‌کند.
  4. اولین Bottleneck را پیدا کنید: حدس نزنید؛ Metric و Profiling را با رفتار کاربر تطبیق دهید.
  5. کم‌هزینه‌ترین اصلاح مؤثر را انجام دهید: ممکن است یک Index، حذف Query اضافی یا تنظیم Connection Pool کافی باشد.
  6. در صورت نیاز Scale Out کنید: Instanceهای Stateless و Load Balancer اضافه کنید و وابستگی‌های مشترک را دوباره بسنجید.
  7. دوباره آزمایش کنید: ظرفیت، Latency، Error Rate و هزینه را با Baseline مقایسه کنید.
ترتیب سالم تصمیم‌گیری: ابتدا اندازه‌گیری، سپس بهینه‌سازی و در نهایت افزودن منابع. اضافه‌کردن ماشین بدون شناخت Bottleneck ممکن است فقط هزینه را بیشتر کند.

مثال واقعی: Scale کردن یک Payment System

فرض کنید Payment API امروز حدود 200 TPS پردازش می‌کند و باید در آینده به 5000 TPS برسد. پاسخ خوب این نیست که فوراً Redis، Kafka یا Sharding اضافه کنیم؛ ابتدا باید مسیر اصلی تراکنش و Bottleneckها را مشخص کنیم.

یک مسیر رشد منطقی می‌تواند شامل این تصمیم‌ها باشد:

  • Payment API را Stateless طراحی کنیم تا بتوان چند Pod از آن اجرا کرد.
  • اطلاعات کم‌تغییر مثل Merchant Configuration را در Redis Cache کنیم، نه دادهٔ حساس به Consistency مثل موجودی را بدون تحلیل دقیق.
  • Notification، Reporting و کارهای غیرضروری برای پاسخ فوری را از مسیر اصلی Transaction خارج و به RabbitMQ منتقل کنیم.
  • Queryهای SQL را با Index، Execution Plan و کاهش Round-tripها بهینه کنیم.
  • برای Readهای سنگین، در صورت سازگاری با نیاز Consistency از Read Replica استفاده کنیم.
  • با Kubernetes HPA تعداد Podها را براساس Metric مناسب افزایش دهیم؛ CPU همیشه بهترین Metric نیست و ممکن است RPS یا Queue Length مناسب‌تر باشد.

مسیر Synchronous

Client → Payment API → Payment Processing → Database → Response

مسیر Asynchronous

Payment Completed → RabbitMQ → Notification / Reporting

هدف این است که مسیر حیاتی Payment کوتاه، قابل پیش‌بینی و قابل اندازه‌گیری بماند؛ کارهای جانبی نباید Latency تراکنش اصلی را بالا ببرند.

Trade-offهایی که نباید پنهان بمانند

  • هزینه: دو برابرکردن منابع الزاماً دو برابر ظرفیت ایجاد نمی‌کند، اما تقریباً همیشه هزینهٔ بیشتری دارد.
  • پیچیدگی: Queue، Cache، Replica و Shard ظرفیت می‌آورند، ولی Deployment، Debugging و Operations را دشوارتر می‌کنند.
  • Consistency: توزیع داده ممکن است باعث شود همهٔ Nodeها در یک لحظه یک نسخهٔ یکسان نبینند.
  • Availability: افزودن Node می‌تواند تحمل خرابی را بیشتر کند، اما تعداد Failure Modeها و وابستگی‌های شبکه را نیز افزایش می‌دهد.
  • بهره‌وری: ظرفیت زیاد برای Peak کوتاه‌مدت ممکن است در بیشتر روز بلااستفاده بماند؛ Auto Scaling کمک می‌کند اما آنی نیست و به Threshold درست نیاز دارد.

هدف System Design بیشترین مقیاس ممکن نیست؛ هدف، مقیاس کافی برای نیاز واقعی با هزینه و پیچیدگی پذیرفتنی است.

اشتباهات رایج

  • شروع از Solution: انتخاب Kafka، Redis یا Sharding پیش از تعریف Workload و Bottleneck.
  • استفاده از Average: میانگین Latency می‌تواند تجربهٔ کند کاربران در p95 و p99 را پنهان کند.
  • نادیده‌گرفتن Peak و Burst: تقسیم درخواست روزانه بر ۸۶۴۰۰ معمولاً ترافیک لحظه‌ای را کمتر از واقعیت نشان می‌دهد.
  • Scaling فقط در Application Layer: افزایش Instance بدون بررسی Database، Cache، Queue و سرویس‌های Downstream.
  • فرض خطی‌بودن ظرفیت: چهار برابرشدن Instanceها لزوماً Throughput را چهار برابر نمی‌کند؛ منابع مشترک و هزینهٔ هماهنگی مانع می‌شوند.
  • ساخت برای مقیاس خیالی: پیچیدگی Distributed قبل از وجود نیاز واقعی، سرعت توسعه و Reliability را کاهش می‌دهد.

در مصاحبهٔ System Design چطور درباره Scalability صحبت کنیم؟

اگر مصاحبه‌کننده بپرسد «چطور این سیستم را Scale می‌کنی؟»، پاسخ حرفه‌ای با نام تکنولوژی شروع نمی‌شود. ابتدا مسئله و محدودیت را مشخص می‌کنیم.

  1. Workload، Peak Load و SLO را مشخص کن.
  2. Bottleneck فعلی را با Metric و Load Test پیدا کن.
  3. مشخص کن سیستم Read-heavy است، Write-heavy است یا مشکل اصلی Concurrency است.
  4. کم‌هزینه‌ترین اصلاح مؤثر را بررسی کن؛ شاید یک Index یا Query Optimization کافی باشد.
  5. در صورت نیاز درباره Scale Up، Scale Out، Cache، Queue یا Database Scaling تصمیم بگیر.
  6. Trade-off انتخابت را توضیح بده؛ هزینه، Consistency، Complexity و Failure Modeها.
نکتهٔ مصاحبه: جملهٔ «اول Bottleneck را پیدا می‌کنم» معمولاً از جملهٔ «Redis و Kafka اضافه می‌کنم» پخته‌تر است؛ چون Scalability یک مسئلهٔ ظرفیت و Trade-off است، نه فهرست تکنولوژی‌ها.

تمرین کوتاه

یک API گزارش‌گیری در ۵۰ RPS عملکرد مناسبی دارد، اما در ۱۰۰ RPS کند می‌شود. CPU سرور Application فقط ۳۵٪ است، Connection Pool پر می‌شود و Query گزارش به‌طور متوسط ۲ ثانیه طول می‌کشد. کدام اقدام باید زودتر بررسی شود؟

  1. دو برابرکردن تعداد Application Instanceها
  2. بررسی Query Plan، Indexها و مدت نگه‌داری Connection
  3. افزودن Kafka به معماری
  4. Sharding فوری Database
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. شواهد نشان می‌دهند Database یا نحوهٔ استفاده از Connection گلوگاه است. افزودن Application Instance احتمالاً تعداد Connectionهای منتظر را بیشتر می‌کند. ابتدا Query Plan، Index مناسب، تعداد Queryها، Timeout و طول عمر Connection بررسی می‌شوند؛ سپس سیستم دوباره Load Test می‌شود.

جمع‌بندی

  • Scalability یعنی حفظ سطح سرویس هنگام رشد Workload، با امکان افزایش ظرفیت به شکلی اقتصادی و قابل‌مدیریت.
  • Scalability بدون عدد معنای دقیقی ندارد؛ RPS، Throughput، Latency، Error Rate، حجم داده و SLO باید مشخص باشند.
  • نوع رشد مهم است: Traffic، Data، Concurrency، Geography و Feature فشارهای متفاوتی ایجاد می‌کنند.
  • ظرفیت کل را Bottleneck محدود می‌کند؛ Scaling یک جزء غیرمحدودکننده مشکل را حل نمی‌کند.
  • Scale Up و Scale Out ابزارند، نه هدف. Cache، Queue، Index، Replica و Partition نیز هرکدام مسئله و Trade-off مشخصی دارند.
  • چرخهٔ درست شامل تخمین، اندازه‌گیری Baseline، Load Test، یافتن Bottleneck، اصلاح و آزمایش دوباره است.
