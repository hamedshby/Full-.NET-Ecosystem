Fundamentals

Reliability

Reliability یعنی سیستم در طول زمان، عملیات را درست و قابل پیش‌بینی انجام دهد؛ حتی وقتی بخشی از سیستم با Failure، Retry، Timeout، Duplicate Message یا خرابی موقت روبه‌رو می‌شود. در این درس یاد می‌گیریم Reliability چه تفاوتی با Availability دارد و چگونه یک سیستم قابل اعتماد طراحی کنیم.

از یک مثال Payment شروع کنیم

فرض کنید Payment API همیشه در دسترس است و در 99.99% زمان پاسخ می‌دهد. اما گاهی وقتی ارتباط با بانک قطع می‌شود، سیستم یک تراکنش را دوبار ثبت می‌کند.

از نظر Availability سرویس تقریباً همیشه قابل دسترس است، اما از نظر Reliability قابل اعتماد نیست؛ چون نتیجهٔ عملیات همیشه درست نیست.

مدل ذهنی: Availability می‌پرسد «آیا سیستم در دسترس است؟» Reliability می‌پرسد «آیا سیستم در طول زمان درست کار می‌کند؟»

Reliability دقیقاً چیست؟

Reliability توانایی یک سیستم برای انجام صحیح وظیفهٔ مورد انتظار، در یک بازهٔ زمانی مشخص و تحت شرایط مشخص است.

یک سیستم Reliable فقط نباید Crash نکند؛ بلکه باید:

  • دادهٔ صحیح تولید کند.
  • عملیات را گم نکند.
  • عملیات را ناخواسته دوبار انجام ندهد.
  • در برابر Failureهای موقت رفتار قابل پیش‌بینی داشته باشد.
  • بعد از Recovery، State معتبر سیستم را حفظ کند.

تعریف قابل‌اندازه‌گیری

«در سیستم پرداخت، هیچ تراکنش موفقی نباید گم شود و Retry یک درخواست نباید باعث ایجاد پرداخت تکراری شود.»

تفاوت Reliability و Availability

مفهوم سؤال اصلی مثال
Availability آیا سیستم الآن قابل استفاده است؟ API در 99.99% زمان در دسترس است
Reliability آیا سیستم در طول زمان عملیات را درست انجام می‌دهد؟ یک Payment فقط یک بار و با State صحیح ثبت می‌شود

یک سیستم می‌تواند Available باشد ولی Reliable نباشد. برای مثال API همیشه پاسخ بدهد، اما پاسخ یا دادهٔ اشتباه تولید کند.

چه چیزهایی Reliability را تهدید می‌کنند؟

  • Network Failure: Request ارسال شده ولی Response برنگشته است.
  • Partial Failure: بخشی از عملیات موفق و بخش دیگر ناموفق شده است.
  • Duplicate Request: Client یا Retry یک عملیات را چندبار ارسال می‌کند.
  • Duplicate Message: یک پیام در Broker دوباره Deliver می‌شود.
  • Lost Message: پیام قبل از ثبت پایدار از بین می‌رود.
  • Race Condition: چند عملیات هم‌زمان State ناسازگار ایجاد می‌کنند.
  • Data Corruption: دادهٔ ذخیره‌شده معتبر نیست.
  • Timeout: نتیجهٔ عملیات برای Caller نامشخص می‌شود.
  • Software Bug: سیستم پاسخ می‌دهد اما Business Rule را اشتباه اجرا می‌کند.

Partial Failure در سیستم‌های Distributed

در یک برنامه Monolith ممکن است یک Failure باعث Rollback کل Transaction شود. اما در سیستم Distributed ممکن است بخشی از عملیات موفق و بخش دیگر ناموفق شود.

مثال

Payment Service مبلغ را ثبت می‌کند، سپس Event را برای Reporting ارسال می‌کند. اگر ثبت Payment موفق ولی ارسال Event ناموفق شود، سیستم وارد یک State ناقص می‌شود.

این یکی از مهم‌ترین دلایل استفاده از Patternهایی مانند:

  • Transactional Outbox
  • Saga
  • Idempotency
  • Retry

Idempotency؛ پایهٔ Reliability در عملیات حساس

یک عملیات Idempotent است اگر اجرای چندبارهٔ یک Request، نتیجهٔ Business را بیش از یک بار اعمال نکند.

مثال Payment

Client یک Request با TransactionId = 123 ارسال می‌کند. اگر به دلیل Timeout همان Request دوباره ارسال شود، سیستم نباید Payment جدید ایجاد کند. 

TransactionId = 123

First Request
→ Payment created

Retry
→ TransactionId already exists
→ Return previous result
→ Do not create another payment

معمولاً این کار با یک شناسهٔ یکتا و Unique Constraint یا Inbox Table انجام می‌شود.

Retry؛ مفید اما خطرناک

Retry برای Failureهای موقتی مفید است؛ اما اگر اشتباه استفاده شود، Reliability را کاهش می‌دهد.

Retry مناسب معمولاً باید:

  • فقط برای خطاهای Transient انجام شود.
  • تعداد محدودی Attempt داشته باشد.
  • از Backoff استفاده کند.
  • ترجیحاً Jitter داشته باشد.
  • برای عملیات غیر Idempotent با احتیاط استفاده شود.

مثال خطرناک

بانک Payment را انجام داده ولی Response در شبکه گم شده است. اگر سیستم بدون Idempotency دوباره Payment را ارسال کند، ممکن است مشتری دوبار Charge شود.

اصل مهم: Retry در Payment بدون Idempotency می‌تواند از خود Failure خطرناک‌تر باشد.

Message Delivery و Reliability

در Message Brokerها معمولاً با چند مدل Delivery روبه‌رو هستیم:

مدل رفتار Trade-off
At-most-once پیام حداکثر یک بار پردازش می‌شود ممکن است پیام گم شود
At-least-once پیام حداقل یک بار پردازش می‌شود ممکن است Duplicate ایجاد شود
Exactly-once از دید Business اثر عملیات یک بار اعمال می‌شود پیاده‌سازی پیچیده و وابسته به Context است

در بسیاری از سیستم‌ها، روش عملی این است:

At-least-once Delivery + Idempotent Consumer

Inbox Pattern

برای جلوگیری از پردازش دوبارهٔ پیام، Consumer می‌تواند شناسهٔ پیام‌های پردازش‌شده را در Inbox ذخیره کند. 

Message arrives

↓
Check MessageId in Inbox

If exists:
    Skip business operation
    Ack message

Else:
    Begin transaction
    Process business operation
    Save MessageId in Inbox
    Commit
    Ack message

Business Operation و ثبت MessageId بهتر است در یک Transaction واحد انجام شوند، تا سیستم بین این دو مرحله وارد State ناسازگار نشود.

Transactional Outbox

یکی از مشکلات رایج این است: 

Save Payment in SQL
↓
Publish PaymentCreated to RabbitMQ

اگر Database Commit شود ولی Publish شکست بخورد، Payment ذخیره شده اما Event از دست رفته است.

در Outbox Pattern، Business Data و Event در همان Database Transaction ذخیره می‌شوند. 

BEGIN TRANSACTION

Insert Payment
Insert OutboxMessage

COMMIT

Background Worker
↓
Read Outbox
↓
Publish to RabbitMQ
↓
Mark as Published

این Pattern احتمال Dual Write Failure را به‌شدت کاهش می‌دهد.

Concurrency و Reliability

دو Request هم‌زمان می‌توانند State سیستم را خراب کنند.

مثال

دو درخواست هم‌زمان موجودی یک Wallet را می‌خوانند. هر دو Balance = 100 را می‌بینند و هر کدام 80 واحد برداشت می‌کنند. اگر Concurrency کنترل نشود، نتیجهٔ نهایی اشتباه خواهد بود.

راهکارها بسته به سناریو می‌توانند شامل این موارد باشند:

  • Optimistic Concurrency با RowVersion
  • Pessimistic Locking
  • Distributed Lock
  • Unique Constraint
  • Atomic Database Operation
نکته: Lock بیشتر همیشه Reliability بیشتری ایجاد نمی‌کند. Lock نامناسب می‌تواند Deadlock، Latency و کاهش Availability ایجاد کند.

Data Integrity

یک سیستم Reliable باید State معتبر خود را حفظ کند. فقط Application Code نباید مسئول اعتبار داده باشد؛ Database نیز باید از Invariantهای مهم محافظت کند.

  • Primary Key
  • Foreign Key
  • Unique Constraint
  • Check Constraint
  • Database Transaction
  • Optimistic Concurrency

مثال

اگر MerchantReferenceCode باید برای هر Merchant یکتا باشد، بهتر است علاوه بر Validation در Application، Database نیز Unique Constraint داشته باشد.

MTBF و MTTR

دو Metric رایج برای بررسی Reliability و عملیات سیستم:

  • MTBF — Mean Time Between Failures: میانگین زمان بین دو Failure.
  • MTTR — Mean Time To Recovery: میانگین مدت‌زمان لازم برای Recover شدن از Failure.

مثال

اگر یک سرویس به‌طور متوسط هر ۳۰ روز یک بار Failure جدی داشته باشد، MTBF آن حدود ۳۰ روز است. اگر تیم به‌طور متوسط در ۱۰ دقیقه سرویس را Recover کند، MTTR حدود ۱۰ دقیقه است.

Reliability فقط با کمترکردن Failure بهتر نمی‌شود؛ کاهش زمان تشخیص و Recovery نیز اهمیت زیادی دارد.

Fault Tolerance

Fault Tolerance یعنی سیستم بتواند با وجود خرابی بخشی از اجزا، همچنان رفتار صحیح یا حداقل قابل قبول داشته باشد.

ابزارهای رایج:

  • Replication
  • Retry
  • Timeout
  • Circuit Breaker
  • Failover
  • Queue
  • Idempotency
  • Graceful Degradation

Reliability و Fault Tolerance نزدیک‌اند، اما Fault Tolerance بیشتر روی ادامهٔ عملکرد هنگام Failure تمرکز دارد.

بدون Observability، Reliability قابل مدیریت نیست

اگر Failure رخ دهد ولی نتوانیم آن را سریع تشخیص دهیم، MTTR افزایش پیدا می‌کند.

برای همین باید حداقل این موارد را داشته باشیم:

  • Structured Logging
  • Metrics
  • Distributed Tracing
  • Correlation ID
  • Alerting
  • Dashboard

مثال Payment

با Correlation ID باید بتوانیم مسیر یک Payment را بین API Gateway، Payment Service، RabbitMQ، Notification و Reporting دنبال کنیم.

یک طراحی قابل اعتماد می‌تواند این ویژگی‌ها را داشته باشد:

  1. Client برای هر عملیات یک TransactionId یکتا ارسال کند.
  2. TransactionId در Database دارای Unique Constraint باشد.
  3. Payment و Outbox Event در یک Database Transaction ذخیره شوند.
  4. Background Worker پیام Outbox را به RabbitMQ ارسال کند.
  5. Consumer از Inbox Pattern استفاده کند.
  6. Ack فقط بعد از Commit موفق انجام شود.
  7. Retry محدود و با Backoff باشد.
  8. برای ارتباط با بانک Idempotency یا Status Query وجود داشته باشد.
  9. Concurrency با RowVersion یا مکانیزم مناسب کنترل شود.
  10. تمام مسیر با Logging، Metrics و Trace قابل ردیابی باشد.

Trade-offهای Reliability

  • Performance: Transaction، Replication و Validation بیشتر ممکن است Latency را افزایش دهند.
  • Complexity: Outbox، Inbox، Saga و Retry Logic پیاده‌سازی را پیچیده‌تر می‌کنند.
  • Storage: نگهداری Inbox، Outbox و Audit Log فضای بیشتری مصرف می‌کند.
  • Operational Cost: Monitoring، Alerting و Redundancy هزینه دارند.
  • Consistency vs Availability: در سیستم Distributed ممکن است نتوان همیشه بالاترین سطح هر دو را هم‌زمان داشت.

هدف، بیشترین پیچیدگی ممکن نیست؛ باید Reliability متناسب با Criticality بیزینس طراحی شود.

اشتباهات رایج

  • Retry بدون Idempotency
  • Ack کردن Message قبل از Commit
  • Publish مستقیم Event بعد از Database Commit بدون Outbox
  • اعتماد صرف به Application Validation بدون Database Constraint
  • نداشتن Timeout برای Dependencyها
  • استفاده از Distributed Lock برای هر مسئله
  • نداشتن Observability برای Failureهای Distributed
  • فرض اینکه Message فقط یک بار Deliver می‌شود

در مصاحبه System Design چطور درباره Reliability صحبت کنیم؟

اگر از شما پرسیدند «چطور این سیستم را Reliable می‌کنی؟»، می‌توانید به این ترتیب فکر کنید:

  1. Critical Operationها را مشخص کنید.
  2. Failure Scenarioها را پیدا کنید.
  3. بررسی کنید Request یا Message ممکن است Duplicate شود یا نه.
  4. برای عملیات حساس Idempotency طراحی کنید.
  5. برای Dual Write از Outbox استفاده کنید.
  6. Consumerها را Idempotent کنید.
  7. Retry، Timeout و Circuit Breaker را مشخص کنید.
  8. Concurrency و Data Integrity را در Database کنترل کنید.
  9. Observability و Recovery Strategy را توضیح دهید.
  10. در پایان Trade-offها را بیان کنید.

نمونهٔ پاسخ کوتاه

«برای Reliability ابتدا Failure Scenarioها و Critical Operationها را مشخص می‌کنم. Requestهای حساس را Idempotent طراحی می‌کنم، برای Dual Write از Transactional Outbox، برای Consumerها از Inbox و Unique MessageId استفاده می‌کنم. Retry محدود و همراه Backoff است و Ack فقط بعد از Commit انجام می‌شود. همچنین Data Integrity را با Transaction و Constraintهای Database محافظت می‌کنم و کل مسیر را با Logging، Metrics و Distributed Tracing قابل مشاهده نگه می‌دارم.»

تمرین کوتاه

Consumer یک پیام RabbitMQ را دریافت می‌کند. Business Operation را در Database ذخیره می‌کند، اما قبل از ارسال Ack، Process Crash می‌کند. بعد از Restart همان پیام دوباره Deliver می‌شود. بهترین راه جلوگیری از اجرای دوبارهٔ Business Operation چیست؟

  1. افزایش Timeout
  2. Idempotent Consumer همراه Inbox و Unique MessageId
  3. افزایش تعداد Consumerها
  4. حذف Database Transaction
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. در At-least-once Delivery احتمال دریافت دوبارهٔ پیام وجود دارد. Consumer باید MessageId را در Inbox ذخیره کند و Business Operation و ثبت MessageId را در یک Transaction انجام دهد.

جمع‌بندی

  • Reliability یعنی سیستم در طول زمان عملیات را درست و قابل پیش‌بینی انجام دهد.
  • Availability و Reliability یکسان نیستند؛ سیستم می‌تواند Available ولی غیرReliable باشد.
  • Partial Failure یکی از مهم‌ترین چالش‌های سیستم‌های Distributed است.
  • Idempotency برای Request، Retry و Message Processing حیاتی است.
  • At-least-once Delivery معمولاً باید با Idempotent Consumer ترکیب شود.
  • Inbox از Duplicate Processing و Outbox از Dual Write Failure جلوگیری می‌کند.
  • Transaction، Constraint و Concurrency Control برای Data Integrity ضروری‌اند.
  • MTBF و MTTR دو Metric مهم برای بررسی رفتار Failure و Recovery هستند.
  • Observability باعث کاهش زمان تشخیص و Recovery می‌شود.
  • در سیستم Payment، Reliability مستقیماً با جلوگیری از Duplicate، Lost Transaction و State ناسازگار مرتبط است.
