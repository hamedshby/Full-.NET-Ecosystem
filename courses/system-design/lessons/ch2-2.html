Networking & Request Flow

HTTP / HTTPS

HTTP پروتکل اصلی ارتباط Request/Response در وب است و HTTPS همان HTTP روی یک ارتباط رمزنگاری‌شده با TLS است. برای System Design لازم نیست وارد همهٔ جزئیات RFCها شویم؛ مهم این است که بدانیم Request چگونه ساخته می‌شود، Connection چگونه برقرار می‌شود، TLS چه کاری انجام می‌دهد، Versionهای مختلف HTTP چه Trade-offهایی دارند و این مفاهیم چگونه روی Latency، Security، Scalability و Reliability اثر می‌گذارند.

از یک Request واقعی شروع کنیم

Client می‌خواهد یک Payment ایجاد کند: 

POST https://api.payment.com/v1/payments

در نگاه Application فقط یک HTTP Request دیده می‌شود، اما پشت صحنه چند مرحله اتفاق می‌افتد: 

DNS Lookup
↓
TCP Connection
↓
TLS Handshake
↓
HTTP Request
↓
Application Processing
↓
HTTP Response
مدل ذهنی: HTTP زبان گفتگو بین Client و Server است؛ HTTPS همان گفتگو در یک کانال امن و رمزنگاری‌شده است.

HTTP چیست؟

HTTP — Hypertext Transfer Protocol یک پروتکل Application Layer برای انتقال Request و Response است.

مدل پایهٔ آن ساده است:

Client
→
HTTP Request
→
Server
→
HTTP Response

HTTP ذاتاً Request/Response محور است؛ Client درخواست می‌فرستد و Server پاسخ می‌دهد.

ساختار HTTP Request

یک HTTP Request معمولاً شامل این بخش‌هاست:

  • Method
  • Path / URL
  • Headers
  • Body

مثال

POST /v1/payments HTTP/1.1
Host: api.payment.com
Authorization: Bearer eyJ...
Content-Type: application/json
Idempotency-Key: 7f0c...

{
  "amount": 250000,
  "currency": "IRR",
  "merchantId": 1024
}

Method هدف عملیات را مشخص می‌کند، Headerها Metadata را منتقل می‌کنند و Body دادهٔ اصلی Request را حمل می‌کند.

HTTP Methodهای مهم

Method کاربرد رایج مثال
GET دریافت Resource GET /payments/123
POST ایجاد Resource یا اجرای Operation POST /payments
PUT جایگزینی کامل Resource PUT /customers/10
PATCH به‌روزرسانی بخشی از Resource PATCH /customers/10
DELETE حذف Resource DELETE /tokens/55
HEAD دریافت Headerها بدون Body HEAD /files/1

Safe و Idempotent در HTTP

این دو مفهوم مهم‌اند و نباید با هم اشتباه شوند.

  • Safe: Method نباید هدفش تغییر State سرور باشد؛ GET معمولاً Safe است.
  • Idempotent: اجرای چندبارهٔ همان Request باید اثر نهایی یکسانی داشته باشد؛ PUT و DELETE از نظر Semantics پروتکل Idempotent محسوب می‌شوند.
نکته مهم در Payment: POST ذاتاً Idempotent نیست. برای Payment معمولاً با Idempotency Key یا TransactionId یکتا، Idempotency را در سطح Business پیاده‌سازی می‌کنیم.

ساختار HTTP Response

HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/payments/987

{
  "id": 987,
  "status": "Pending"
}

HTTP Headerها چه کاری انجام می‌دهند؟

Headerها Metadata مربوط به Request و Response را منتقل می‌کنند.

نمونه‌های مهم:

  • Authorization: Authentication Token
  • Content-Type: نوع Body
  • Accept: فرمت مورد انتظار Response
  • Cache-Control: سیاست Cache
  • Host: Domain مقصد
  • User-Agent: اطلاعات Client
  • Correlation-Id: ردیابی Request
  • Idempotency-Key: جلوگیری از Duplicate Operation

HTTP ذاتاً Stateless است

از دید Protocol، هر Request مستقل است و Server نباید فرض کند Request قبلی را به خاطر دارد.

اگر Session نیاز باشد، باید مکانیزمی بالاتر از HTTP استفاده کنیم:

  • Cookie
  • Session ID
  • JWT
  • Distributed Session Store
نکته: Stateless بودن HTTP همان Stateless بودن کل Application نیست؛ Application ممکن است Session یا Business State داشته باشد.

HTTPS چیست؟

HTTPS در اصل HTTP روی یک ارتباط امن TLS است. 

HTTP
↓
TLS
↓
TCP
↓
IP

TLS سه هدف اصلی دارد:

  • Confidentiality: داده رمزنگاری می‌شود.
  • Integrity: تغییر غیرمجاز داده قابل تشخیص است.
  • Authentication: Client می‌تواند هویت Server را با Certificate بررسی کند.

Certificate چه کاری انجام می‌دهد؟

Server برای HTTPS یک Digital Certificate ارائه می‌دهد. Certificate مشخص می‌کند Public Key متعلق به چه Domain یا Organizationی است.

Client معمولاً این موارد را بررسی می‌کند:

  • Certificate Expired نشده باشد.
  • Domain با Certificate مطابقت داشته باشد.
  • Certificate Chain به یک CA قابل اعتماد برسد.
  • Certificate معتبر و قابل Verify باشد.
نکته عملی: Expire شدن Certificate می‌تواند باعث شود سرویس کاملاً سالم باشد، اما Client اتصال HTTPS را رد کند.

TLS Handshake به زبان ساده

قبل از انتقال HTTP Data روی HTTPS، Client و Server باید یک Secure Session بسازند. 

Client
↓ ClientHello
Server

Server
↓ Certificate + TLS parameters
Client

Client verifies certificate
↓
Key agreement
↓

بعد از Handshake، HTTP Request داخل ارتباط رمزنگاری‌شده ارسال می‌شود.

Handshake روی Latency اولین Connection اثر دارد؛ به همین دلیل Connection Reuse مهم است.

Connection Reuse و Keep-Alive

ساخت Connection جدید هزینه دارد:

  • TCP Handshake
  • TLS Handshake
  • Network Round Trip

بهتر است برای Requestهای متعدد تا حد امکان Connection موجود Reuse شود. 

Bad

Request 1 → New TCP/TLS
Request 2 → New TCP/TLS
Request 3 → New TCP/TLS


Better

One TCP/TLS connection
↓
Request 1
Request 2
Request 3

در .NET به همین دلیل استفاده صحیح از HttpClient و IHttpClientFactory اهمیت دارد.

مثال در .NET

builder.Services.AddHttpClient<BankClient>(client =>
{
    client.BaseAddress = new Uri("https://bank.example.com");
    client.Timeout = TimeSpan.FromSeconds(2);
});

ایجاد HttpClient جدید برای هر Request می‌تواند باعث مشکلات Connection Management و Socket Exhaustion شود. HttpClientFactory برای مدیریت بهتر Connection Pool و Handler Lifetime استفاده می‌شود.

HTTP/1.1، HTTP/2 و HTTP/3

Version ویژگی مهم نکته
HTTP/1.1 Persistent Connections برای Parallel Requestها معمولاً چند Connection استفاده می‌شود
HTTP/2 Multiplexing روی یک TCP Connection چند Stream هم‌زمان روی یک Connection
HTTP/3 استفاده از QUIC روی UDP کاهش بعضی مشکلات TCP-level Head-of-Line Blocking

HTTP/2 Multiplexing

در HTTP/2 چند Request و Response می‌توانند هم‌زمان روی یک Connection حرکت کنند. 

One TCP Connection

Stream 1 → Request A
Stream 3 → Request B
Stream 5 → Request C

این کار نیاز به چند Connection را کاهش می‌دهد و برای سرویس‌های پرRequest مفید است.

HTTP/3 و QUIC

HTTP/3 از QUIC استفاده می‌کند که روی UDP ساخته شده ولی Reliability و Security مورد نیاز را در خود Protocol مدیریت می‌کند.

یکی از مزیت‌های مهم این است که مشکل Loss روی یک Stream، کمتر روی Streamهای دیگر اثر می‌گذارد.

برای System Design: لازم نیست QUIC را در سطح Packet بلد باشید؛ کافی است بدانید HTTP/3 می‌تواند در شبکه‌های با Latency یا Packet Loss بالا تجربهٔ بهتری ایجاد کند.

Timeout در HTTP Call

هر HTTP Call به Downstream Service باید Timeout مناسب داشته باشد. 

Payment API SLO = 2 seconds

Bank API timeout = 30 seconds

❌ Invalid design

اگر Dependency تا ۳۰ ثانیه Connection را نگه دارد، API نمی‌تواند SLO دوثانیه‌ای خود را حفظ کند.

Timeout باید با Latency Budget کل Request هماهنگ باشد.

Retry در HTTP

Retry برای خطاهای موقت مفید است، اما نباید برای همهٔ HTTP Errorها استفاده شود.

وضعیت Retry؟
400 Bad Request معمولاً خیر
401 Unauthorized معمولاً نیازمند اصلاح Authentication
429 Too Many Requests ممکن است با Backoff و Retry-After
503 Service Unavailable ممکن است با Retry محدود
Timeout / transient network error در صورت Idempotency و Policy مناسب
اصل مهم: Retry در عملیات Payment بدون Idempotency ممکن است Duplicate Transaction ایجاد کند.

  • Forward Proxy: نمایندهٔ Client است.

در System Design معمولاً Reverse Proxy مهم‌تر است.

Reverse Proxy

Reverse Proxy Request را دریافت و به Backend مناسب هدایت می‌کند.

وظایف رایج:

  • Load Balancing

  • Compression
  • Rate Limiting
  • Header Management

Client IP پشت Proxy چه می‌شود؟

وقتی Request از Load Balancer یا Reverse Proxy عبور می‌کند، Backend ممکن است IP Proxy را ببیند، نه IP واقعی Client.

Headerهایی مانند این‌ها برای انتقال اطلاعات اصلی استفاده می‌شوند:

Forwarded
نکته امنیتی: این Headerها را فقط از Proxyهای مورد اعتماد قبول کنید؛ Client خارجی می‌تواند آن‌ها را جعل کند.

HTTP مکانیزم‌های استانداردی برای Cache دارد:

  • If-None-Match
  • Last-Modified
  • If-Modified-Since

Compression

برای Payloadهای متنی، Compression می‌تواند حجم Network را کاهش دهد. 

Accept-Encoding: gzip, br

Content-Encoding: br

Trade-off این است که Compression و Decompression CPU مصرف می‌کنند. برای Payloadهای بسیار کوچک ممکن است ارزش نداشته باشد.

Payload Size روی Latency اثر دارد

Response بزرگ‌تر یعنی:

  • Serialization بیشتر
  • Network Transfer بیشتر
  • Memory بیشتر
  • Deserialization بیشتر

بنابراین API Design باید فقط دادهٔ مورد نیاز را منتقل کند. 

Bad:
GET /transactions
→ 50 MB response

Better:
GET /transactions?page=1&pageSize=50

HTTP با REST یکی نیست

HTTP یک Protocol است. REST یک Architectural Style است که معمولاً از HTTP استفاده می‌کند.

نکته: هر HTTP API الزاماً RESTful نیست. همچنین gRPC نیز می‌تواند روی HTTP/2 اجرا شود، ولی REST محسوب نمی‌شود.

مثال کامل Request Flow در Payment System

POST https://api.payment.com/v1/payments
Client
→
DNS
→
TCP/TLS
→
Load Balancer
→
API Gateway
→
Payment Service
→
Bank API

در یک طراحی مناسب:

  1. Client با HTTPS متصل می‌شود.
  2. TLS Certificate اعتبار Domain را تأیید می‌کند.
  3. Load Balancer یا Gateway ممکن است TLS را Terminate کند.
  4. Gateway Authentication و Rate Limiting را انجام می‌دهد.
  5. Payment Service Request را Validate می‌کند.
  6. برای POST حساس از Idempotency Key استفاده می‌شود.
  7. Call به Bank API دارای Timeout و Retry محدود است.
  8. Response با Status Code مناسب برمی‌گردد.

Failure Scenarioهای مهم HTTP/HTTPS

  • DNS Failure: Domain Resolve نمی‌شود.
  • TCP Connection Failure: اتصال شبکه برقرار نمی‌شود.
  • TLS Error: Certificate نامعتبر یا Expired است.
  • Timeout: Downstream دیر پاسخ می‌دهد.
  • 502 Bad Gateway: Proxy پاسخ معتبر از Backend نگرفته است.
  • 503 Service Unavailable: Backend فعلاً سرویس نمی‌دهد.
  • 504 Gateway Timeout: Gateway منتظر Backend مانده و Timeout شده است.
  • 429 Too Many Requests: Rate Limit اعمال شده است.

برای Debug یک HTTP Call چه چیزهایی را بررسی کنیم؟

  1. آیا DNS Resolve می‌شود؟
  2. آیا TCP Connection برقرار می‌شود؟
  3. آیا TLS Certificate معتبر است؟
  4. Method و URL درست هستند؟
  5. Headerهای لازم وجود دارند؟
  6. Status Code چیست؟
  7. Response Time چقدر است؟
  8. Proxy/Gateway چه Logی دارد؟
  9. آیا Retry یا Redirect رخ داده است؟

ابزارهای رایج

curl -v https://api.example.com/health

curl -I https://api.example.com

openssl s_client -connect api.example.com:443

Trade-offهای مهم

  • HTTPS vs CPU: Encryption هزینه دارد، ولی برای سرویس Production عملاً ضروری است.
  • Compression vs CPU: Network کمتر، CPU بیشتر.
  • Keep-Alive vs Resources: Connection Reuse سریع‌تر است ولی Connection باز Resource مصرف می‌کند.
  • Retry vs Latency: Reliability بهتر، Latency و Load بیشتر.
  • Large Payload vs Simplicity: Response بزرگ ساده‌تر است ولی Network و Memory بیشتری مصرف می‌کند.
  • HTTP/2 Multiplexing vs Shared TCP: Connection کمتر، ولی Packet Loss روی TCP هنوز می‌تواند Streamها را تحت تأثیر قرار دهد.

اشتباهات رایج

  • ساخت HttpClient جدید برای هر Request در .NET
  • Timeout بسیار بزرگ یا بدون Timeout
  • Retry کردن همهٔ 4xx و 5xxها
  • Retry کردن POST حساس بدون Idempotency
  • نادیده گرفتن Expiration Certificate
  • اعتماد مستقیم به X-Forwarded-For از Client ناشناس
  • برگرداندن Payload بسیار بزرگ بدون Pagination
  • استفاده از 200 برای هر نوع نتیجه و خطا
  • اشتباه گرفتن REST با خود HTTP

در مصاحبه System Design چطور درباره HTTP/HTTPS صحبت کنیم؟

در مصاحبه معمولاً نیاز نیست RFCها را حفظ باشید. این موارد مهم‌ترند:

  1. Request Flow را از DNS تا HTTP Response توضیح دهید.
  2. HTTP Method و Status Code مناسب را انتخاب کنید.
  3. برای Production از HTTPS استفاده کنید.
  4. نقش TLS و Certificate را بدانید.
  5. Connection Reuse و Keep-Alive را در نظر بگیرید.
  6. Timeout و Retry Policy را درست طراحی کنید.
  7. برای POSTهای حساس Idempotency را توضیح دهید.
  8. نقش Reverse Proxy و API Gateway را مشخص کنید.
  9. در سیستم‌های پرترافیک HTTP/2/3 و Payload Size را در نظر بگیرید.

نمونه پاسخ کوتاه

«Client ابتدا Domain را Resolve می‌کند، سپس TCP/TLS Connection می‌سازد و HTTP Request را به Load Balancer یا API Gateway می‌فرستد. HTTPS برای Confidentiality، Integrity و Authentication استفاده می‌شود. برای کاهش Latency از Connection Reuse استفاده می‌کنم، Timeout هر Downstream را با Latency Budget هماهنگ می‌کنم و Retry را فقط برای خطاهای Transient و در عملیات Idempotent انجام می‌دهم. برای Payment POST نیز Idempotency Key در نظر می‌گیرم تا Retry باعث Duplicate نشود.»

تمرین کوتاه

Payment Service یک POST به Bank API می‌فرستد. بانک عملیات را انجام می‌دهد اما Response در شبکه گم می‌شود و Client Timeout می‌گیرد. کدام گزینه بهترین طراحی است؟

  1. بدون محدودیت POST را Retry کنیم
  2. Retry همراه Idempotency Key یا TransactionId و بررسی Status انجام شود
  3. Timeout را حذف کنیم
  4. همیشه 500 برگردانیم
مشاهدهٔ پاسخ پیشنهادی

گزینهٔ ۲. نتیجهٔ واقعی عملیات برای Caller نامشخص است. Retry کورکورانه می‌تواند Duplicate Payment ایجاد کند. باید عملیات Idempotent طراحی شود یا Status تراکنش قابل بررسی باشد.

جمع‌بندی

  • HTTP پروتکل Request/Response در Application Layer است.
  • HTTPS همان HTTP روی TLS است.
  • Request شامل Method، URL، Headers و Body است.
  • Status Code نتیجهٔ استاندارد عملیات را مشخص می‌کند.
  • HTTP ذاتاً Stateless است، ولی Application می‌تواند Stateful باشد.
  • TLS برای Confidentiality، Integrity و Authentication استفاده می‌شود.
  • Connection Reuse و Keep-Alive Latency و هزینهٔ Handshake را کاهش می‌دهند.
  • HTTP/2 از Multiplexing و HTTP/3 از QUIC استفاده می‌کند.
  • Timeout و Retry باید با Latency Budget و Idempotency هماهنگ باشند.
  • Reverse Proxy و API Gateway بخش مهم Request Flow در معماری‌های Backend هستند.
  • در Payment API، POST حساس باید Idempotent طراحی شود.
