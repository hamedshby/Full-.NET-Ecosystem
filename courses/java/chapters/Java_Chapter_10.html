درس 01 · فصل دهم

JDBC، JPA و Hibernate

مفهوم و نکات کلیدی

JDBC ابزار سطح پایین Java برای اتصال به دیتابیس، اجرای SQL و پردازش ResultSet است. JPA یا Jakarta Persistence یک قرارداد استاندارد برای Persistence است و به‌تنهایی ORM اجرایی نیست. Hibernate یکی از پیاده‌سازی‌های JPA و یک ORM است که تغییرات Entityها را مدیریت کرده و معمولاً SQL را با JDBC اجرا می‌کند.

معادل در دات‌نت و تفاوت‌های مهم

JDBC از نظر کارکرد به ADO.NET نزدیک است: Connection، Command/PreparedStatement و Reader/ResultSet. Hibernate از لحاظ نقش ORM به EF Core نزدیک است. JPA برخلاف EF Core یک Specification است، نه محصول ORM یکپارچه. EntityManager از نظر وظیفه شبیه DbContext است.

مثال عملی و مقایسه کد

Java — JDBC / SQLJAVA
try (Connection c = DriverManager.getConnection(url, user, password);
     PreparedStatement ps = c.prepareStatement("SELECT amount FROM payments WHERE id = ?")) {
    ps.setLong(1, 100L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) System.out.println(rs.getLong("amount"));
    }
}
Java — JPAJAVA
Payment payment = entityManager.find(Payment.class, 100L);
entityManager.persist(new Payment(50000L));
C# — EF CoreCSHARP
var payment = await dbContext.Payments.FindAsync(100L);
dbContext.Payments.Add(new Payment { Amount = 50000L });
await dbContext.SaveChangesAsync();
سؤال مرور درس 01 — نمایش پاسخ

سؤال: کدام گزینه درست است؟

پاسخ: JDBC لایه ارتباط با دیتابیس است؛ JPA استاندارد Persistence و Hibernate یکی از پیاده‌سازی‌های JPA است. (گزینه C)

درس 02 · فصل دهم

تعریف Entity با @Entity، @Table و @Id

مفهوم و نکات کلیدی

@Entity کلاس را به‌عنوان Entity معرفی می‌کند؛ @Table نام جدول را تنظیم می‌کند؛ @Id مشخص‌کننده کلید اصلی است. @GeneratedValue راهبرد تولید شناسه را تعیین می‌کند و @Column نگاشت و ویژگی ستون را مشخص می‌کند. Entity باید سازنده بدون پارامتر public یا protected داشته باشد.

معادل در دات‌نت و تفاوت‌های مهم

در EF Core کلاس مدل را با convention، Data Annotation یا Fluent API به جدول نگاشت می‌کنیم. @Table شبیه ToTable، @Id شبیه HasKey، @Column شبیه Property/HasColumnName و @GeneratedValue شبیه ValueGeneratedOnAdd است؛ البته راهبرد تولید کلید باید با دیتابیس هماهنگ باشد.

مثال عملی و مقایسه کد

Java — نگاشت PaymentJAVA
@Entity
@Table(name = "payments")
public class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(name = "amount", nullable = false)
    private Long amount;
    protected Payment() {}
    public Payment(Long amount) { this.amount = amount; }
}
C# — Fluent MappingCSHARP
modelBuilder.Entity<Payment>(e => {
    e.ToTable("payments");
    e.HasKey(x => x.Id);
    e.Property(x => x.Amount).IsRequired();
});
سؤال مرور درس 02 — نمایش پاسخ

سؤال: @Entity و @Id به چه معنا هستند؟

پاسخ: @Entity کلاس را Entity می‌کند و @Id مشخص‌کننده کلید اصلی است؛ @Id به‌تنهایی به معنای تولید خودکار شناسه نیست. (گزینه D)

درس 03 · فصل دهم

EntityManager و Persistence Context

مفهوم و نکات کلیدی

EntityManager رابط اصلی JPA برای بازیابی و مدیریت Entityها است. Persistence Context مجموعه Entityهای Managed را نگهداری می‌کند. Hibernate از Dirty Checking برای تشخیص تغییرات استفاده می‌کند؛ Flush تغییرات را به دیتابیس ارسال می‌کند اما Commit نیست. حالت‌های مهم Entity عبارت‌اند از Transient، Managed، Detached و Removed.

معادل در دات‌نت و تفاوت‌های مهم

EntityManager و Persistence Context از نظر نقش به DbContext و ChangeTracker نزدیک‌اند. در EF Core معمولاً SaveChangesAsync برای ارسال تغییرات لازم است؛ در JPA تغییر Entity Managed در یک Transaction فعال، هنگام Flush/Commit می‌تواند بدون update() دستی به دیتابیس منتقل شود. Detach مشابه Entry(entity).State = Detached است.

مثال عملی و مقایسه کد

Java — Managed و Dirty CheckingJAVA
@Transactional
public void adjust(Long id) {
    Payment p = entityManager.find(Payment.class, id);
    p.setAmount(50000L);  // Managed: dirty checking
}
Java — DetachedJAVA
Payment p = entityManager.find(Payment.class, 100L);
entityManager.detach(p);
p.setAmount(50000L); // این تغییر خودکار Persist نمی‌شود
C# — Change TrackingCSHARP
var payment = await dbContext.Payments.FindAsync(100L);
payment.Amount = 50000L;
await dbContext.SaveChangesAsync();
سؤال مرور درس 03 — نمایش پاسخ

سؤال: تغییر روی Entity از نوع Managed در Transaction موفق چگونه ذخیره می‌شود؟

پاسخ: Hibernate با Dirty Checking تغییر را تشخیص می‌دهد و در Flush آن را اعمال می‌کند؛ Commit تراکنش تغییرات را نهایی می‌کند. (گزینه B)

درس 04 · فصل دهم

Spring Data JPA و JpaRepository

مفهوم و نکات کلیدی

Spring Data JPA بر پایه JPA پیاده‌سازی Repository را تولید می‌کند. JpaRepository متدهایی چون save، findById، findAll، deleteById و count را فراهم می‌کند. همچنین Query Method مثل findByAmount بر اساس نام متد و ویژگی Entity ساخته می‌شود. findById از Optional برای بیان نبودن نتیجه استفاده می‌کند.

معادل در دات‌نت و تفاوت‌های مهم

از نظر تجربه برنامه‌نویسی شبیه Generic Repository آماده در کنار EF Core است، اما EF Core به‌خودی‌خود JpaRepository و Query Derivation بر اساس نام متد ندارد؛ در دات‌نت معمولاً DbSet، LINQ یا Repository سفارشی می‌نویسیم. save در JpaRepository معادل یک‌به‌یک SaveChangesAsync نیست.

مثال عملی و مقایسه کد

Java — RepositoryJAVA
public interface PaymentRepository
        extends JpaRepository<Payment, Long> {
    List<Payment> findByAmount(Long amount);
}
Java — ServiceJAVA
@Service
public class PaymentService {
    private final PaymentRepository repo;
    public PaymentService(PaymentRepository repo) { this.repo = repo; }
    public Payment create(Long amount) {
        return repo.save(new Payment(amount));
    }
}
C# — DbSet و LINQCSHARP
var matches = await dbContext.Payments
    .Where(x => x.Amount == amount)
    .ToListAsync();
سؤال مرور درس 04 — نمایش پاسخ

سؤال: مزیت JpaRepository و findByAmount چیست؟

پاسخ: متدهای متداول CRUD از قبل فراهم‌اند و Spring Data JPA می‌تواند Query ساده را از نام findByAmount بسازد. (گزینه C)

درس 05 · فصل دهم

پرس‌وجو با JPQL و Native SQL

مفهوم و نکات کلیدی

JPQL روی نام Entity و خصوصیات Java کار می‌کند؛ SELECT p FROM Payment p WHERE p.amount > :minAmount. Native SQL مستقیماً نام جدول و ستون واقعی را به‌کار می‌برد. @Query در Spring Data JPA به‌صورت پیش‌فرض JPQL است و برای SQL خام باید nativeQuery=true تعیین شود. پارامترگذاری برای جلوگیری از تزریق SQL ضروری است.

معادل در دات‌نت و تفاوت‌های مهم

JPQL از نظر سطح انتزاع به LINQ روی Entityهای EF Core نزدیک است، اما LINQ یک API تایپ‌شده C# است و JPQL یک زبان رشته‌ای. Native SQL به اجرای FromSql/ExecuteSql در EF Core شباهت دارد. برتری کارایی هیچ‌کدام را نمی‌توان بدون بررسی SQL خروجی و Execution Plan تضمین کرد.

مثال عملی و مقایسه کد

Java — JPQL در RepositoryJAVA
@Query("SELECT p FROM Payment p WHERE p.amount > :minAmount")
List<Payment> findLargePayments(@Param("minAmount") Long minAmount);
Java — Native SQLJAVA
@Query(value = "SELECT * FROM payments WHERE amount > :minAmount",
       nativeQuery = true)
List<Payment> findLargePaymentsNative(@Param("minAmount") Long minAmount);
C# — LINQCSHARP
var payments = await dbContext.Payments
    .Where(p => p.Amount > minAmount)
    .ToListAsync();
سؤال مرور درس 05 — نمایش پاسخ

سؤال: چرا SELECT p FROM Payment p WHERE p.amount > 1000 یک JPQL است؟

پاسخ: زیرا Payment نام Entity و amount ویژگی Java آن است، نه الزاماً نام جدول و ستون دیتابیس. (گزینه D)

درس 06 · فصل دهم

ارتباط Entityها با @OneToMany و @ManyToOne

مفهوم و نکات کلیدی

یک Customer می‌تواند چند Payment داشته باشد و هر Payment به یک Customer تعلق داشته باشد. سمت Payment با @ManyToOne و @JoinColumn(name="customer_id") معمولاً مالک ارتباط است. سمت Customer با @OneToMany(mappedBy="customer") سمت معکوس رابطه است. LAZY بارگذاری ارتباط را به تعویق می‌اندازد.

معادل در دات‌نت و تفاوت‌های مهم

این نگاشت معادل مفهومی HasOne(p=>p.Customer).WithMany(c=>c.Payments).HasForeignKey(p=>p.CustomerId) در Fluent API EF Core است. mappedBy نام فیلد ارتباط در سمت مالک را مشخص می‌کند. بارگذاری ارتباط‌ها در JPA با FetchType کنترل می‌شود، اما در EF Core از Include، explicit loading یا lazy-loading وابسته به پیکربندی استفاده می‌کنیم.

مثال عملی و مقایسه کد

Java — CustomerJAVA
@Entity
public class Customer {
    @Id private Long id;
    @OneToMany(mappedBy = "customer")
    private List<Payment> payments = new ArrayList<>();
    protected Customer() {}
}
Java — PaymentJAVA
@Entity
public class Payment {
    @Id private Long id;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
    protected Payment() {}
}
C# — EF Core Fluent APICSHARP
modelBuilder.Entity<Payment>()
    .HasOne(p => p.Customer)
    .WithMany(c => c.Payments)
    .HasForeignKey(p => p.CustomerId);
سؤال مرور درس 06 — نمایش پاسخ

سؤال: در Payment.customer کدام annotation مناسب است؟

پاسخ: @ManyToOne زیرا تعداد زیادی Payment می‌توانند به یک Customer مربوط باشند. (گزینه B)

درس 07 · فصل دهم

Lazy Loading، Eager Loading و مشکل N+1

مفهوم و نکات کلیدی

در Lazy Loading، موجودیت مرتبط در صورت نیاز بارگذاری می‌شود؛ Eager Loading بارگذاری ارتباط را الزام می‌کند، اما لزوماً به معنای یک SQL JOIN نیست. اگر یک Query برای ۱۰۰ Payment و سپس ۱۰۰ Query برای Customerهای متفاوت اجرا شود، N+1 داریم. JOIN FETCH یا @EntityGraph می‌توانند روش بارگذاری را بهبود دهند.

معادل در دات‌نت و تفاوت‌های مهم

در EF Core، مسئله N+1 نیز هنگام Lazy Loading یا اجرای Query داخل حلقه اتفاق می‌افتد. JOIN FETCH از نظر هدف شبیه Include(p=>p.Customer) است. EntityGraph هم روشی اعلامی برای تعیین ارتباط‌های مورد نیاز است. تعداد Query و Execution Plan را باید با لاگ SQL و ابزار مانیتورینگ بررسی کنیم.

مثال عملی و مقایسه کد

Java — وضعیت بالقوه N+1JAVA
List<Payment> payments = repository.findAll();
for (Payment p : payments) {
    System.out.println(p.getCustomer().getName());
}
Java — JOIN FETCHJAVA
@Query("SELECT p FROM Payment p JOIN FETCH p.customer")
List<Payment> findAllWithCustomer();
C# — IncludeCSHARP
var payments = await dbContext.Payments
    .Include(p => p.Customer)
    .ToListAsync();
سؤال مرور درس 07 — نمایش پاسخ

سؤال: برای جلوگیری از N+1 در بارگذاری Customerها چه می‌کنیم؟

پاسخ: به‌جای Lazy Load جداگانه هر Customer، از JOIN FETCH یا روش مناسب Fetch Planning استفاده می‌کنیم؛ صرفاً EAGER کردن همه روابط راه‌حل عمومی نیست. (گزینه C)

درس 08 · فصل دهم

مدیریت Transaction با @Transactional

مفهوم و نکات کلیدی

در Spring، @Transactional روی متد Service مرز تراکنش را مشخص می‌کند. در پیکربندی پراکسی استاندارد، فراخوانی باید از پراکسی Spring عبور کند؛ فراخوانی مستقیم یک متد از متد دیگر همان کلاس (Self-invocation) ممکن است آن را فعال نکند. Rollback پیش‌فرض برای RuntimeException و Error است، نه اغلب Checked Exceptionها. rollbackFor=Exception.class دامنه Rollback را افزایش می‌دهد.

معادل در دات‌نت و تفاوت‌های مهم

در EF Core می‌توان BeginTransactionAsync، CommitAsync و RollbackAsync فراخوانی کرد. یک SaveChanges معمولاً برای تغییرات همان فراخوانی تراکنش خود را دارد، ولی برای چند عملیات مرز تراکنش صریح لازم می‌شود. @Transactional از نظر نقش به مرزبندی Transaction/Unit of Work نزدیک است؛ معادل یک Annotation پیش‌فرض در EF Core نیست.

مثال عملی و مقایسه کد

Java — TransferServiceJAVA
@Service
public class TransferService {
    private final AccountRepository repo;
    public TransferService(AccountRepository repo) { this.repo = repo; }
    @Transactional
    public void transfer(Long fromId, Long toId, long amount) {
        Account a = repo.findById(fromId).orElseThrow();
        Account b = repo.findById(toId).orElseThrow();
        if (amount <= 0 || a.getBalance() < amount)
            throw new IllegalArgumentException("Invalid transfer");
        a.setBalance(a.getBalance() - amount);
        b.setBalance(b.getBalance() + amount);
    }
}
C# — تراکنش صریحCSHARP
await using var tx = await dbContext.Database.BeginTransactionAsync();
try {
    accountA.Balance -= amount;
    accountB.Balance += amount;
    await dbContext.SaveChangesAsync();
    await tx.CommitAsync();
} catch {
    await tx.RollbackAsync();
    throw;
}
Java — Checked ExceptionJAVA
@Transactional(rollbackFor = Exception.class)
public void process() throws Exception { /* ... */ }
سؤال مرور درس 08 — نمایش پاسخ

سؤال: اگر RuntimeException از @Transactional بیرون بیاید، رفتار پیش‌فرض چیست؟

پاسخ: تراکنش Rollback می‌شود. Managed بودن Entity باعث Commit قطعی نمی‌شود. گزینه D؛ در تمرین جبرانی نیز گزینه B صحیح بود. (گزینه D)

درس 09 · فصل دهم

Optimistic Locking با @Version

مفهوم و نکات کلیدی

@Version یک فیلد نسخه روی Entity معرفی می‌کند. Hibernate هنگام UPDATE نسخه مورد انتظار را در شرط WHERE بررسی می‌کند؛ اگر درخواست هم‌زمان نسخه را تغییر داده باشد، تعارض تشخیص داده می‌شود و خطایی از جنس OptimisticLockException ممکن است رخ دهد. پس از Conflict باید تراکنش قبلی را خاتمه دهیم و در تراکنش جدید داده و قوانین کسب‌وکار را دوباره بررسی کنیم.

معادل در دات‌نت و تفاوت‌های مهم

@Version از نظر هدف به Concurrency Token و SQL Server rowversion در EF Core شباهت دارد، اما لزوماً همان نوع ستون SQL Server نیست؛ نسخه عددی در Hibernate رایج است. در EF Core معمولاً DbUpdateConcurrencyException رخ می‌دهد. Optimistic Locking جایگزین Idempotency یا Transaction درست مالی نیست.

مثال عملی و مقایسه کد

Java — نسخه عددیJAVA
@Entity
public class Account {
    @Id private Long id;
    private Long balance;
    @Version private Long version;
}
SQL — UPDATE مبتنی بر VersionSQL
UPDATE account
SET balance = 7000, version = 6
WHERE id = 100 AND version = 5;
C# — RowVersionCSHARP
public class Account {
    public long Id { get; set; }
    public long Balance { get; set; }
    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}
سؤال مرور درس 09 — نمایش پاسخ

سؤال: اگر درخواست A نسخه ۵ را به ۶ برساند، درخواست B با نسخه ۵ چه می‌کند؟

پاسخ: Hibernate تعارض نسخه را تشخیص می‌دهد و عملیات B با خطای Optimistic Locking مواجه می‌شود. (گزینه C)

درس 10 · فصل دهم

Performance، Pagination و Batch Processing

مفهوم و نکات کلیدی

برای دیتاست بزرگ از Pagination استفاده می‌کنیم. Page<T> محتوا و اطلاعات صفحه و معمولاً شمارش کل را در اختیار می‌گذارد، درحالی‌که Slice<T> برای پیمایش بدون نیاز به تعداد کل مناسب است. JDBC Batching می‌تواند تعداد رفت‌وبرگشت‌ها را کاهش دهد. هنگام Import حجیم، flush() و clear() دوره‌ای در یک Transaction مناسب از بزرگ‌شدن Persistence Context جلوگیری می‌کنند. تولید شناسه IDENTITY ممکن است جلوی Batch Insert را بگیرد.

معادل در دات‌نت و تفاوت‌های مهم

PageRequest.of(page,size) شبیه Skip/Take در EF Core است؛ اما EF Core عموماً برای شمارش کل یک CountAsync مجزا نیاز دارد. Hibernate JDBC Batching از نظر هدف شبیه Bulk/Batch تکنیک‌ها در اکوسیستم .NET است، اما با EF Core AddRange یا ExecuteUpdate یکسان نیست. flush شبیه ارسال SQL و clear شبیه ChangeTracker.Clear است، ولی flush به معنای Commit نیست.

مثال عملی و مقایسه کد

Java — PaginationJAVA
Page<Payment> page = repository.findAll(
    PageRequest.of(0, 20, Sort.by("id").ascending()));
List<Payment> result = page.getContent();
YAML — تنظیم HibernateYAML
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
Java — پردازش حجیمJAVA
@Transactional
public void importAll(List<Payment> payments) {
    for (int i = 0; i < payments.size(); i++) {
        entityManager.persist(payments.get(i));
        if ((i + 1) % 50 == 0) {
            entityManager.flush();
            entityManager.clear();
        }
    }
}
C# — PaginationCSHARP
var payments = await dbContext.Payments
    .OrderBy(x => x.Id)
    .Skip(0).Take(20).ToListAsync();
سؤال مرور درس 10 — نمایش پاسخ
