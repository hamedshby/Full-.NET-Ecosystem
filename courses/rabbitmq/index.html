بخش ۱

مفاهیم پایهٔ RabbitMQ

۱. RabbitMQ چیست؟

فرض کنید پرداخت موفق شده است و باید برای کاربر اعلان ارسال شود. سرویس پرداخت می‌تواند یک پیام منتشر کند و سرویس اعلان بعداً آن را دریافت و پردازش کند. RabbitMQ یک Message Broker است؛ واسطه‌ای که پیام را از یک برنامه می‌گیرد و برای مصرف توسط برنامهٔ دیگر مدیریت می‌کند. در این مسیر، سرویس‌ها مجبور نیستند همیشه مستقیماً و هم‌زمان با یکدیگر ارتباط برقرار کنند.

Payment Service→RabbitMQ→Notification Service

۲. Message چیست؟

Message همان داده‌ای است که بین سرویس‌ها جابه‌جا می‌شود؛ مثلاً شناسهٔ پرداخت، شناسهٔ کاربر، مبلغ و وضعیت تراکنش. این نمونه فقط شکل اطلاعات را نشان می‌دهد؛ ارسال و دریافت مدل‌های JSON در ادامهٔ یادگیری بررسی خواهد شد.

نمونهٔ اطلاعات پرداختJSON
{
  "paymentId": 123,
  "userId": 45,
  "amount": 250000,
  "status": "Paid"
}

۳. Producer

سرویسی که Message را می‌سازد و آن را منتشر می‌کند. در این مثال، Payment Service نقش Producer را دارد.

۴. Consumer

سرویسی که Message را دریافت می‌کند و بر اساس آن کاری انجام می‌دهد. در این مثال، Notification Service نقش Consumer را دارد.

۵. Queue چیست؟

Queue محل نگهداری پیام‌ها تا زمان دریافت توسط Consumer است. وقتی سرویس اعلان در دسترس نیست، صف می‌تواند پیام را نگه دارد تا بعداً مصرف شود؛ طول عمر صف و پیام به تنظیمات آن‌ها وابسته است.

Producer → [ Queue: Message1 | Message2 | Message3 ] → Consumer

۶. Exchange چیست؟

Exchange مسئول مسیریابی پیام به صف‌های مناسب است. Producer پیام را به Exchange می‌فرستد و قوانین مسیریابی تعیین می‌کنند کدام Queue پیام را دریافت کند.

Producer→Exchange→Queue→Consumer

۷. Binding چیست؟

Binding رابطهٔ مسیریابی میان Exchange و Queue است. در Direct Exchange این رابطه یک کلید دارد که برای تطبیق با کلید پیام استفاده می‌شود.

۸. Routing Key چیست؟

Routing Key یک مقدار متنی است که Producer همراه پیام می‌فرستد؛ مثلاً payment.success. Exchange بسته به نوع خود از این کلید برای انتخاب مقصد استفاده می‌کند.

۹. Direct Exchange چیست؟

در Direct Exchange، پیام به هر صفی می‌رسد که Binding Key آن دقیقاً برابر Routing Key پیام باشد. اگر دو مقدار متفاوت باشند، آن Binding منطبق نیست.

Routing Key = payment.success
Binding Key = payment.success
Result: Match → Queue receives message

۱۰. اشارهٔ کوتاه به Fanout Exchange

Fanout Exchange پیام را بدون توجه به Routing Key به تمام صف‌های متصل به خود می‌فرستد. در جزوهٔ اول فقط معرفی شده است؛ آموزش آن در ادامهٔ جزوهٔ سوم آمده است.

بخش ۲

آماده‌سازی پروژه‌های .NET

۱۱. یک Solution و دو برنامه

دو Console Application مستقل می‌سازیم؛ یکی برای ارسال پیام و دیگری برای دریافت آن. برای اجرای نمونه‌ها باید .NET SDK نصب باشد و یک RabbitMQ Broker روی localhost:5672 در دسترس باشد. کد جزوه از APIهای RabbitMQ.Client 7.x استفاده می‌کند.

ساخت پروژه‌ها و نصب ClientCLI
dotnet new sln -n RabbitMqDirectDemo
dotnet new console -n Payment.Producer
dotnet new console -n Notification.Consumer
dotnet sln add Payment.Producer
dotnet sln add Notification.Consumer

dotnet add Payment.Producer package RabbitMQ.Client --version 7.*
dotnet add Notification.Consumer package RabbitMQ.Client --version 7.*

هر دو پروژه به Package نیاز دارند، چون هر دو با Broker ارتباط برقرار می‌کنند. در جزوه دستور dotnet add package RabbitMQ.Client آمده است؛ اینجا نام پروژه هم مشخص شده تا دستور از پوشهٔ Solution قابل استفاده باشد.

۱۲. ConnectionFactory و Connection

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();

ConnectionFactory تنظیمات اتصال مثل آدرس Broker، نام کاربری، رمز عبور، Port و VirtualHost را نگه می‌دارد. ساختن این شیء اتصال را باز نمی‌کند؛ CreateConnectionAsync اتصال واقعی را ایجاد می‌کند.

برای هر پیام یک Connection جدید نمی‌سازیم. ایجاد اتصال TCP هزینه دارد و معمولاً اتصال را برای استفادهٔ طولانی‌تر باز نگه می‌داریم.

۱۳. Channel چیست؟

using var channel = await connection.CreateChannelAsync();

Channel یک ارتباط منطقی روی Connection است. بیشتر عملیات، مثل تعریف Exchange و Queue، ارسال پیام و ثبت Consumer از طریق آن انجام می‌شوند. این ساختار اجازه می‌دهد برای هر عملیات یک اتصال TCP تازه باز نکنیم.

بخش ۳

ساخت توپولوژی Direct Exchange

توپولوژی در این مثال یعنی یک Exchange، یک Queue و رابطهٔ Binding بین آن‌ها.

۱۴. Declare کردن Exchange

await channel.ExchangeDeclareAsync(
    exchange: "payment.direct",
    type: ExchangeType.Direct
);

این دستور مطمئن می‌شود Exchange با نام payment.direct و نوع Direct وجود دارد. اگر قبلاً با مشخصات سازگار تعریف شده باشد، همان استفاده می‌شود.

مشخصات باید سازگار باشندنمی‌توان یک نام را یک بار با نوع Direct و بار دیگر با نوع Fanout تعریف کرد. تعریف مجدد منابع با مشخصات ناسازگار خطا ایجاد می‌کند.

۱۵. Declare کردن Queue

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

اگر صفی با این نام و مشخصات وجود نداشته باشد، ساخته می‌شود؛ اگر وجود داشته باشد، مشخصات باید با تعریف قبلی سازگار باشند.

۱۶. durable
با durable: true خود صف برای باقی‌ماندن بعد از Restart شدن Broker تعریف می‌شود. این گزینه به‌تنهایی پیام‌های صف را ماندگار نمی‌کند.
۱۷. exclusive
با exclusive: true صف به اتصال ایجادکننده وابسته است؛ استفاده از آن به همان Connection محدود می‌شود و با بسته‌شدن اتصال حذف می‌شود. برای صف اصلی پرداخت از false استفاده می‌کنیم.
۱۸. autoDelete
صفی با autoDelete: true که قبلاً Consumer داشته است، پس از جداشدن آخرین Consumer حذف می‌شود. در این مثال مقدار false است تا با قطع‌شدن Consumer صف حذف نشود.
۱۹. arguments
برای تنظیمات اضافی صف استفاده می‌شود. وقتی تنظیم اضافه نداریم، مقدار null می‌دهیم. برای مثال x-message-ttl مدت مجاز ماندن پیام در صف را بر حسب میلی‌ثانیه مشخص می‌کند.
var arguments = new Dictionary<string, object?>
{
    ["x-message-ttl"] = 60000
};

این مثال مقدار ۶۰ ثانیه را نشان می‌دهد و در صف اصلی جزوه استفاده نشده است. x-message-ttl مربوط به انقضای پیام است؛ برای انقضای خود صف تنظیم جداگانه‌ای مثل x-expires وجود دارد.

۲۰. ساخت Binding

await channel.QueueBindAsync(
    queue: "payment.notification.queue",
    exchange: "payment.direct",
    routingKey: "payment.success"
);

از این لحظه، پیام‌هایی که با Routing Key برابر payment.success به این Direct Exchange برسند، به صف payment.notification.queue مسیریابی می‌شوند.

بخش ۴

ارسال Message از Producer

۲۱. تبدیل Message به بایت

var message = "Payment 123 succeeded";
var body = Encoding.UTF8.GetBytes(message);

بدنهٔ پیام در RabbitMQ بایت است. پس داده‌ای مثل متن یا JSON باید پیش از ارسال به بایت تبدیل شود. در این مثال از UTF-8 استفاده می‌کنیم و Consumer هم با همان Encoding متن را بازسازی می‌کند.

۲۲. Publish کردن Message

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.success",
    body: body
);

exchange مقصد اولیهٔ پیام است، routingKey کلید لازم برای یافتن Binding منطبق است و body محتوای واقعی پیام را نگه می‌دارد.

۲۳. Durable Queue و Persistent Message

ماندگاری صف و ماندگاری پیام دو تنظیم جدا هستند. برای علامت‌گذاری پیام به‌عنوان Persistent از BasicProperties استفاده می‌کنیم.

var properties = new BasicProperties
{
    Persistent = true
};

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.success",
    basicProperties: properties,
    body: body
);
دو تنظیم با دو مسئولیت متفاوت
تنظیممعنی
durable: trueخود صف پس از Restart شدن Broker باقی می‌ماند.
Persistent = trueپیام با حالت Persistent منتشر می‌شود؛ ماندگاری آن نیازمند صف Durable هم هست.
مرز این مرحله از آموزشPersistent بودن پیام تضمین کامل تحویل یا پردازش نیست. برای اطمینان سمت Publisher، مبحث Publisher Confirms در ادامه بررسی می‌شود. همچنین Exchange در نمونهٔ جزوه با تنظیم پیش‌فرض غیر Durable تعریف شده است؛ ماندگاری صف به معنی ماندگاری Exchange و مسیر آن نیست.

بخش ۵

ساخت Consumer

۲۴. اتصال مستقل Consumer

برنامهٔ دریافت‌کننده اتصال و Channel خودش را می‌سازد. هر دو برنامه به یک Broker متصل می‌شوند، ولی اتصال مشترکی در حافظه ندارند.

var factory = new ConnectionFactory { HostName = "localhost" };
using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

۲۵. Declare کردن Queue در Consumer

دریافت‌کننده هم صف را با همان مشخصات تعریف می‌کند تا اگر زودتر اجرا شد، صف موجود باشد. این کار فقط صف را آماده می‌کند؛ Exchange و Binding در نمونهٔ فعلی توسط Producer ساخته می‌شوند.

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

۲۶. ساخت AsyncEventingBasicConsumer

var consumer = new AsyncEventingBasicConsumer(channel);

این شیء دریافت asynchronous پیام را پشتیبانی می‌کند و رویدادی به نام ReceivedAsync دارد. ساختن شیء به‌تنهایی دریافت پیام از صف را آغاز نمی‌کند.

۲۷. رویداد ReceivedAsync

consumer.ReceivedAsync += async (model, ea) =>
{
    Console.WriteLine("Message received");
    await Task.CompletedTask;
};

این Handler زمانی اجرا می‌شود که پیام به Consumer تحویل داده شود. در این قطعه هنوز فقط دریافت را در Console اعلام می‌کنیم.

۲۸. خواندن بدنهٔ Message

var body = ea.Body.ToArray();
var message = Encoding.UTF8.GetString(body);

در زمان اجرای ReceivedAsync پیام قبلاً به Handler تحویل شده است. ToArray بدنه را کپی می‌کند و GetString بایت‌ها را به متن تبدیل می‌کند. در Client نسخهٔ ۷، دادهٔ بدنه باید پیش از پایان Handler خوانده یا کپی شود.

۲۹. ثبت Consumer روی Queue

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: true,
    consumer: consumer
);

BasicConsumeAsync دریافت‌کننده را روی صف ثبت می‌کند. مقدار autoAck: true اولین حالت معرفی‌شده در جزوه است؛ در بخش بعد آن را به تأیید دستی تغییر می‌دهیم.

بخش ۶

Ack، Nack و رفتار خطا

۳۰. مفهوم autoAck

با autoAck: true، Broker پیام ارسالی به Consumer را تأییدشده در نظر می‌گیرد و منتظر تمام‌شدن پردازش برنامه نمی‌ماند. اگر برنامه پس از تحویل و پیش از پایان پردازش متوقف شود، احتمال از دست رفتن پیام وجود دارد.

با autoAck: false، تأیید را خود برنامه پس از موفقیت پردازش ارسال می‌کند.

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: false,
    consumer: consumer
);

۳۱. BasicAckAsync

await channel.BasicAckAsync(
    deliveryTag: ea.DeliveryTag,
    multiple: false
);

Ack موفقیت پردازش پیام را اعلام می‌کند. DeliveryTag شناسهٔ تحویل روی همان Channel است و multiple: false یعنی فقط همین تحویل تأیید شود. تأیید باید روی Channel دریافت‌کنندهٔ پیام ارسال شود.

۳۲. BasicNackAsync

await channel.BasicNackAsync(
    deliveryTag: ea.DeliveryTag,
    multiple: false,
    requeue: true
);

Nack ناموفق‌بودن پردازش را اعلام می‌کند. با requeue: true پیام برای امکان دریافت دوباره به صف برمی‌گردد.

۳۳. تفاوت requeue: true و requeue: false

پس از ردکردن پیام چه اتفاقی می‌افتد؟
تنظیمرفتار
requeue: trueپیام به صف اصلی برمی‌گردد و می‌تواند دوباره تحویل داده شود.
requeue: falseپیام به صف اصلی برنمی‌گردد؛ در صورت تنظیم Dead Letter به مسیر آن می‌رود و در غیر این صورت کنار گذاشته می‌شود.
حلقهٔ Redeliveryاگر دادهٔ پیام خراب باشد و هر بار شکست بخورد، requeue: true بدون محدودیت می‌تواند دریافت دوبارهٔ بی‌پایان ایجاد کند. این نمونهٔ جزوهٔ اول آموزشی است؛ مسیر Dead Letter و مقدمات Retry با TTL در جزوهٔ دوم آمده‌اند و Retry محدود هنوز کامل نشده است.

بخش ۷

رفتار Direct Exchange در چند مسیر

۳۴. چند Queue با Routing Keyهای متفاوت

payment.success → payment.notification.queue
payment.failed  → payment.failed.queue

اگر پیام با payment.failed منتشر شود، صفی آن را دریافت می‌کند که Binding Key منطبق داشته باشد. صف مربوط به payment.success از این Binding پیام نمی‌گیرد.

۳۵. یک Routing Key برای چند Queue

Queue A → payment.success
Queue B → payment.success
Queue C → payment.failed

Publish: payment.success
Result: Queue A + Queue B

هر دو صف A و B نسخه‌ای از پیام را دریافت می‌کنند، چون هر دو Binding منطبق دارند. Direct Exchange الزاماً پیام را فقط به یک صف نمی‌فرستد.

۳۶. پیام Unroutable

اگر هیچ Binding با کلید پیام تطابق نداشته باشد، پیام وارد هیچ صفی نمی‌شود. مثلاً وقتی فقط کلیدهای payment.success و payment.failed تعریف شده‌اند، پیام با کلید payment.refund مقصدی ندارد. در حالت پیش‌فرض و بدون سازوکار دیگری، این پیام کنار گذاشته می‌شود.

۳۷. گزینهٔ mandatory

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.refund",
    mandatory: true,
    basicProperties: properties,
    body: body
);

با mandatory: true اگر پیام به هیچ صفی مسیریابی نشود، RabbitMQ آن را از مسیر basic.return به Publisher برمی‌گرداند. این گزینه به معنی پردازش موفق پیام توسط Consumer نیست.

ادامه در جزوهٔ دومجزوهٔ اول در معرفی mandatory متوقف می‌شود. پیاده‌سازی Handler رویداد BasicReturnAsync در بخش دریافت پیام برگشتی آمده است.

کد کامل Producer در جزوهٔ اول

using RabbitMQ.Client;
using System.Text;

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

await channel.ExchangeDeclareAsync(
    exchange: "payment.direct",
    type: ExchangeType.Direct

    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

await channel.QueueBindAsync(
    queue: "payment.notification.queue",
    exchange: "payment.direct",
    routingKey: "payment.success"
);

var message = "Payment 123 succeeded";
var body = Encoding.UTF8.GetBytes(message);

var properties = new BasicProperties
{
    Persistent = true
};

    exchange: "payment.direct",
    routingKey: "payment.success",
    mandatory: true,
    basicProperties: properties,
    body: body
);

Console.WriteLine($"Sent: {message}");

پیام با کلید payment.success به صف اعلان می‌رود. Console.ReadLine برنامه را باز نگه می‌دارد؛ خروجی Sent به‌تنهایی اثبات دریافت یا پردازش پیام نیست.

وضعیت نمونهٔ جزوهٔ اولmandatory فعال است، ولی Handler پیام برگشتی و Publisher Confirms در این نمونه وجود ندارند. روش افزودن آن‌ها در بخش ۱۱ و بخش ۱۲ توضیح داده شده است.

کد کامل Consumer در جزوهٔ اول

این کد را در Notification.Consumer/Program.cs قرار دهید. نمونهٔ فعلی متن پیام را نمایش می‌دهد و بعد از اجرای بخش پردازش، تأیید دستی می‌فرستد.

Notification.Consumer/Program.csC#
using RabbitMQ.Client;
using RabbitMQ.Client.Events;
using System.Text;

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

var consumer = new AsyncEventingBasicConsumer(channel);

consumer.ReceivedAsync += async (model, ea) =>
{
    try
    {
        var body = ea.Body.ToArray();
        var message = Encoding.UTF8.GetString(body);

        Console.WriteLine($"Received: {message}");

        // Business operation

        await channel.BasicAckAsync(
            deliveryTag: ea.DeliveryTag,
            multiple: false
        );
    }
    catch
    {
        await channel.BasicNackAsync(
            deliveryTag: ea.DeliveryTag,
            multiple: false,
            requeue: true
        );
    }
};

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: false,
    consumer: consumer
);

Console.WriteLine("Waiting for messages...");
Console.ReadLine();

در نمونهٔ جزوه، محل عملیات کسب‌وکار با Comment مشخص شده است؛ فعلاً ارسال واقعی اعلان پیاده‌سازی نشده است. اگر پردازش در این بخش خطا بدهد، Nack با requeue: true ارسال می‌شود.

دریافت پیام برگشتی در Producer

فرض کنید فقط Binding با کلید payment.success داریم، اما Producer پیام را با payment.refund و mandatory: true منتشر می‌کند. چون هیچ Queue منطبقی وجود ندارد، Broker پیام را برمی‌گرداند. برای مشاهدهٔ این اتفاق، رویداد BasicReturnAsync را قبل از انتشار ثبت می‌کنیم.

روی Channel مربوط به Producer، پیش از BasicPublishAsyncC# · Client 7.x
channel.BasicReturnAsync += (sender, ea) =>
{
    var message = Encoding.UTF8.GetString(ea.Body.ToArray());
    Console.WriteLine($"Returned: {message}");
    Console.WriteLine($"Routing key: {ea.RoutingKey}");
    Console.WriteLine($"Reason: {ea.ReplyText}");
    return Task.CompletedTask;
};

خروجی شامل متن پیام، کلید payment.refund و دلیل برگشت، مانند NO_ROUTE است. کپی‌کردن Body با ToArray() داده را در همان Handler در اختیار ما می‌گذارد. این Handler فقط گزارش می‌دهد؛ ذخیره‌سازی یا ارسال مجدد باید جداگانه طراحی شود.

خاموش‌بودن Consumer باعث Return نیستاگر Queue منطبق موجود باشد و Consumer خاموش باشد، پیام می‌تواند در Queue منتظر بماند. mandatory وجود مسیر به Queue را بررسی می‌کند، نه موفقیت پردازش Consumer.

تأیید انتشار با Publisher Confirms

Producer می‌خواهد بداند Broker انتشار را پذیرفته است. Publisher Confirms همین تأیید را فراهم می‌کند؛ این تأیید مستقل از Consumer Ack است. حتی وقتی Consumer خاموش است، Broker می‌تواند انتشار را تأیید کند.

در Producer، خط ساخت Channel در نمونهٔ اول را با کد زیر جایگزین کنید. سپس Handler بخش قبل را روی همین Channel و پیش از انتشار ثبت کنید؛ connection همان اتصال بازشدهٔ قبلی است.

فعال‌کردن تأیید و پیگیری آنC#
var options = new CreateChannelOptions(
    publisherConfirmationsEnabled: true,
    publisherConfirmationTrackingEnabled: true);
using var channel = await connection.CreateChannelAsync(options);
انتشار روی Channel دارای Confirm TrackingC#
try
{
    await channel.BasicPublishAsync(
        exchange: "payment.direct",
        routingKey: "payment.refund",
        mandatory: true,
        basicProperties: new BasicProperties(),
        body: Encoding.UTF8.GetBytes("Payment refunded"));
    Console.WriteLine("Publish confirmed");
}
catch (Exception ex)
{
    Console.WriteLine($"Publish failed: {ex.Message}");
}

با فعال‌بودن هر دو گزینه، await BasicPublishAsync منتظر تأیید می‌ماند و در صورت Nack یا Return خطا می‌دهد. در مثال بدون Binding منطبق، خط Publish confirmed اجرا نمی‌شود. اگر Binding منطبق اضافه شود، تأیید انتشار همچنان به معنی ارسال موفق اعلان نیست.

catch (Exception) در این قطعه برای نمایش خطا در آموزش است؛ برنامهٔ واقعی باید خطای مسیریابی، قطع اتصال و خطاهای دیگر را تشخیص دهد. Confirm به‌تنهایی وجود مقصد را ثابت نمی‌کند؛ mandatory و مدیریت Return نیز لازم‌اند. مرجع رسمی Publisher Confirms در .NET.

تأیید گم‌شده و پیام تکراری

Broker پیام پرداخت را وارد Queue کرده است، اما قبل از رسیدن Confirm، شبکه قطع می‌شود. Producer تأییدی نمی‌بیند و ممکن است همان پیام را دوباره بفرستد. بنابراین «تأیید نرسید» الزاماً به معنی «پیام نرسید» نیست و ارسال مجدد می‌تواند پیام تکراری بسازد.

MessageId شناسه‌ای است که Producer برای یک پیام منطقی تعیین می‌کند. آن را یک بار بسازید و در تمام تلاش‌های انتشار همان پیام حفظ کنید؛ ساختن شناسهٔ جدید در هر Retry تشخیص تکرار را مختل می‌کند.

شناسه در Producer و خواندن آن در Handler مربوط به ConsumerC#
// Producer: create once for this logical message.
var messageId = Guid.NewGuid().ToString();
var properties = new BasicProperties { MessageId = messageId };
// Pass properties as basicProperties; reuse MessageId for retries.

// Consumer: inside ReceivedAsync.
var receivedMessageId = ea.BasicProperties.MessageId;

تنظیم MessageId باعث حذف خودکار پیام تکراری توسط Broker نمی‌شود. این شناسه را با DeliveryTag اشتباه نگیرید: DeliveryTag شناسهٔ تحویل روی Channel و ورودی Ack/Nack است و در تحویل مجدد ممکن است تغییر کند. اگر Producer، MessageId تعیین نکرده باشد، مقدار آن ممکن است null باشد؛ Consumer باید برای این حالت تصمیم مشخص داشته باشد.

جلوگیری از اثر تکراری با Inbox

اگر پیام پرداخت دو بار برسد، نباید موجودی دو بار تغییر کند. Idempotency در این مثال یعنی پردازش مجدد همان پیام، اثر کسب‌وکار تازه‌ای ایجاد نکند. Inbox جدول ثبت شناسهٔ پیام‌های پردازش‌شده در دیتابیس Consumer است.

  1. برای پیام جدید، یک Transaction در دیتابیس شروع می‌کنیم.
  2. MessageId را در Inbox ثبت می‌کنیم و تغییر دادهٔ کسب‌وکار را در همان Transaction انجام می‌دهیم.
  3. پس از Commit موفق، پیام را با BasicAckAsync تأیید می‌کنیم.
  4. اگر پردازش قبلی همان MessageId به‌طور معتبر تأیید شده باشد، عملیات را تکرار نمی‌کنیم و پیام تکراری را Ack می‌کنیم.

اگر برنامه بعد از Commit و پیش از Ack قطع شود، Broker می‌تواند پیام را دوباره تحویل دهد. Inbox کمک می‌کند این تحویل اثر تکراری نسازد. اما Ack پیش از Commit خطرناک است: اگر Transaction شکست بخورد، عملیات ثبت نشده و Broker نیز پیام تأییدشده را برای جبران آن دوباره تحویل نمی‌دهد.

چرا بررسی وجود شناسه کافی نیست؟

دو Consumer یک سرویس با جدول مشترک ممکن است هم‌زمان نبودن شناسه را ببینند. Unique Index محدودیتی در دیتابیس است که ثبت دوبارهٔ یک مقدار را منع می‌کند. قطعهٔ زیر پس از ساخت جدول Inbox و ستون MessageId اجرا می‌شود:

قید یکتایی روی جدول موجودSQL Server
CREATE UNIQUE INDEX UX_Inbox_MessageId
ON dbo.Inbox (MessageId);

Transaction بازنده باید کامل Rollback شود تا تغییر کسب‌وکار آن نیز ثبت نشود. خطای قطع دیتابیس را تکراری‌بودن پیام فرض نکنید؛ فقط پس از تشخیص معتبر تکرار و تأیید پردازش قبلی، Ack بدون اجرای دوباره درست است.

مرز Transactionاین الگو عملیات داخل همان Transaction دیتابیس را پوشش می‌دهد. ارسال پیامک یا فراخوانی سرویس خارجی خودکار با آن اتمیک نمی‌شود. جزوه در این مرحله الگوریتم را توضیح می‌دهد و پیاده‌سازی کامل دیتابیس ارائه نمی‌کند.

تفاوت خطای موقت و دائمی

اگر دیتابیس چند ثانیه در دسترس نباشد، تلاش بعدی ممکن است موفق شود؛ این یک خطای موقت است. اما اگر فیلد ضروری پیام وجود نداشته باشد، تکرار همان داده مشکل را حل نمی‌کند؛ این خطا در مثال ما دائمی است.

انتخاب مسیر پیام ناموفق
وضعیترفتار مناسب
خطای موقت مانند قطعی کوتاه دیتابیسRetry با فاصله و تعداد محدود، پس از طراحی انتقال امن.
خطای دائمی مانند نبود فیلد ضروریانتقال به مسیر بررسی پیام ناموفق، به‌جای تکرار همان داده.

ساخت مسیر Dead Letter

می‌خواهیم پیام اعلان ناموفق از Queue اصلی خارج شود و برای بررسی در Queue جداگانه بماند. Dead Letter Exchange یا DLX یک Exchange معمولی است که Queue اصلی برای مسیریابی پیام‌های Dead-letter از آن استفاده می‌کند. Dead Letter Queue یا DLQ مقصد نگهداری این پیام‌هاست.

تعریف مقصد بررسی پیام ناموفقC#
await channel.ExchangeDeclareAsync(
    exchange: "payment.dlx", type: ExchangeType.Direct,
    durable: true, autoDelete: false, arguments: null);
await channel.QueueDeclareAsync(
    queue: "payment.notification.dlq", durable: true,
    exclusive: false, autoDelete: false, arguments: null);
await channel.QueueBindAsync(
    queue: "payment.notification.dlq",
    exchange: "payment.dlx", routingKey: "notification.failed");

روی Queue اصلی، نام DLX و Routing Key خروج پیام را تنظیم می‌کنیم. Exchange قبلی payment.direct باید با همان تنظیمات بخش اول موجود باشد؛ این قطعه آن را دوباره با تنظیمات متفاوت تعریف نمی‌کند.

Queue اصلی جدید با تنظیمات Dead LetterC#
var arguments = new Dictionary<string, object?>
{
    ["x-dead-letter-exchange"] = "payment.dlx",
    ["x-dead-letter-routing-key"] = "notification.failed"
};
await channel.QueueDeclareAsync(
    queue: "payment.notification.v2.queue", durable: true,
    exclusive: false, autoDelete: false, arguments: arguments);
await channel.QueueBindAsync(
    queue: "payment.notification.v2.queue",
    exchange: "payment.direct", routingKey: "payment.success");

Consumer را با autoAck: false روی payment.notification.v2.queue ثبت کنید؛ نمونهٔ کامل Consumer در بخش ۹ هنوز به Queue نسخهٔ اول متصل است. سپس برای ردکردن پیامی که باید به مسیر بررسی برود، داخل Handler از کد زیر استفاده کنید:

await channel.BasicNackAsync(
    deliveryTag: ea.DeliveryTag,
    multiple: false,
    requeue: false);
مسیر مورد انتظار پیام ردشدهFlow
payment.notification.v2.queue
    → payment.dlx (notification.failed)
    → payment.notification.dlq

با requeue: true پیام به Queue اصلی برمی‌گردد و این مسیر ردکردن فعال نمی‌شود. DLQ نیز پیام را خودکار اصلاح یا دوباره منتشر نمی‌کند؛ ابتدا دلیل شکست، داده و کد بررسی می‌شوند، سپس ارسال مجدد کنترل‌شده انجام می‌شود.

تعریف مجدد و ایمنی انتقالنام Queue جدید برای جلوگیری از PRECONDITION_FAILED ناشی از تغییر آرگومان‌های Queue قبلی است. ساخت v2 پیام‌های Queue قدیمی را منتقل نمی‌کند و Binding قبلی نیز باقی می‌ماند. برای برخی تنظیمات DLX می‌توان از Policy استفاده کرد. انتقال Dead Letter به پیکربندی صحیح و دسترس‌پذیری مقصد وابسته است و تضمین مطلق تحویل نیست؛ جزئیات رسمی DLX.

Retry با تأخیر و TTL

اگر دیتابیس قطع باشد، تلاش فوری و پیاپی همان خطا را تکرار می‌کند. Queue انتظار به پیام فرصت می‌دهد مدتی بماند و سپس به Queue اصلی برگردد. Time-To-Live یا TTL مدت اعتبار پیام است؛ آرگومان x-message-ttl آن را برای پیام‌های یک Queue بر حسب میلی‌ثانیه تنظیم می‌کند.

در این مثال مقدار 5000 یعنی ۵ ثانیه. Queue انتظار Consumer ندارد؛ وگرنه پیام ممکن است پیش از انقضا مصرف شود. پس از انقضا، DLX آن را به Exchange اصلی برمی‌گرداند. بدون مسیر Dead Letter، پیام منقضی‌شده حذف می‌شود؛ زمان خروج نیز دقت تضمین‌شدهٔ یک Timer را ندارد.

Binding اختصاصی بازگشت اعلان و Queue انتظارC#
await channel.QueueBindAsync(
    queue: "payment.notification.v2.queue",
    exchange: "payment.direct", routingKey: "notification.retry");
var retryArguments = new Dictionary<string, object?>
{
    ["x-message-ttl"] = 5000,
    ["x-dead-letter-exchange"] = "payment.direct",
    ["x-dead-letter-routing-key"] = "notification.retry"
};
await channel.QueueDeclareAsync(
    queue: "payment.notification.retry.5s.v2.queue",
    durable: true, exclusive: false, autoDelete: false,
    arguments: retryArguments);
بخش ساخته‌شدهٔ مسیر RetryFlow
payment.notification.retry.5s.v2.queue (no consumer)
    → TTL expires
    → payment.direct (notification.retry)
    → payment.notification.v2.queue

چرا کلید بازگشت اختصاصی است؟

اگر بازگشت با payment.success انجام شود، Queueهای دیگری مانند گزارش‌گیری که با این کلید Binding دارند نیز پیام را دوباره می‌گیرند. با notification.retry فقط Queue اعلان را به مسیر Retry وصل می‌کنیم.

Binding جدید، Binding قبلی با payment.success را حذف نمی‌کند. Queue اعلان اکنون هر دو کلید را می‌پذیرد: یکی برای رویداد اولیه و دیگری برای بازگشت Retry. نام Queue انتظار نیز جدید است تا با تنظیمات مثال قبلی تعارض نداشته باشد؛ تعریف مجدد همان نام، راه تغییر آرگومان‌های ناسازگار نیست.

فاصله‌های ۵، ۱۵ و ۳۰ ثانیه در جزوه مثال‌اند؛ فقط Queue پنج‌ثانیه‌ای اینجا تعریف شده است. این تنظیم به‌تنهایی پیام ناموفق Consumer را وارد Queue انتظار نمی‌کند. مرجع TTL و انقضای پیام.

بخش ۱۸ · جزوهٔ دوم، بخش ۸

مرز پیاده‌سازی در پایان جزوهٔ دوم

تا اینجا مسیر خروج پیام منقضی‌شده از Queue انتظار و بازگشت آن به Queue اصلی را تنظیم کرده‌ایم. مسیر Nack(requeue: false) در بخش ۱۶ به DLQ می‌رود؛ هیچ اتصال خودکاری از آن به Queue انتظار ساخته نشده است.

Retry هنوز کامل نیستانتقال امن پیام خطادار از Consumer به Queue انتظار، حفظ MessageId هنگام انتقال، شمارندهٔ تلاش‌ها و سقف Retry هنوز پیاده‌سازی نشده‌اند. نباید پیام اصلی را پیش از اطمینان از انتقال لازم، موفق فرض کرد. کدهای جزوهٔ دوم قطعات آموزشی‌اند و یک سامانهٔ کامل Retry نیستند.

نمونه‌های کامل Producer و Consumer در بخش‌های ۸ و ۹ مربوط به جزوهٔ اول‌اند. قطعات این ادامه باید با توجه به توضیح هر بخش روی Channel مناسب و Queue جدید اعمال شوند؛ کنار هم گذاشتن تمام قطعات، بدون طراحی مسیرهای باقی‌مانده، کافی نیست.

بخش ۲۱ · جزوهٔ سوم، مرحلهٔ ۱

Fanout Exchange چیست؟

فرض کنید پس از پرداخت، اعلان، گزارش‌گیری و حسابداری هر کدام باید رویداد را مستقل دریافت کنند. Fanout Exchange پیام را به همهٔ Queueهای متصل به خودش مسیریابی می‌کند. برخلاف Direct Exchange، مقدار Routing Key در انتخاب مقصدهای Fanout نقشی ندارد.

یک انتشار، یک نسخه برای هر Queue متصلFlow
Payment Producer → payment.fanout
                      ├─→ Notification Queue
                      ├─→ Reporting Queue
                      └─→ Accounting Queue

در Direct، Queue باید Binding با کلید منطبق داشته باشد؛ در Fanout، اتصال Queue به Exchange کافی است. تکثیر در این مدل بین Queueها رخ می‌دهد؛ نحوهٔ تحویل به Consumerهای هر Queue را در بخش ۲۴ بررسی می‌کنیم.

بخش ۲۲ · جزوهٔ سوم، مراحل ۲ و ۳

ساخت Exchange و اتصال چند Queue

روی Channel بازشده، Exchange تازه‌ای با نام payment.fanout می‌سازیم. پارامتر type با مقدار ExchangeType.Fanout نوع آن را تعیین می‌کند؛ نام Exchange به‌تنهایی نوع را مشخص نمی‌کند.

تعریف Exchange جدیدC# · Client 7.x
await channel.ExchangeDeclareAsync(
    exchange: "payment.fanout",
    type: ExchangeType.Fanout,
    durable: true,
    autoDelete: false,
    arguments: null);

Exchange موجود payment.direct را با نوع جدید دوباره تعریف نمی‌کنیم؛ تغییر نوع همان نام خطا می‌دهد. جزوه فرض می‌کند Queueهای اعلان و گزارش‌گیری قبلاً ساخته شده‌اند. اگر Queue گزارش‌گیری هنوز وجود ندارد، ابتدا با مشخصات سازگار آن را تعریف کنید؛ مثلاً برای Queue تازه:

آماده‌سازی Queue گزارش‌گیری در صورت نبودن آنC#
await channel.QueueDeclareAsync(
    queue: "payment.reporting.queue", durable: true,
    exclusive: false, autoDelete: false, arguments: null);

Queue اعلان payment.notification.queue همان Queue جزوهٔ اول است. پس از موجودبودن هر دو Queue، آن‌ها را به Exchange متصل می‌کنیم:

Binding دو QueueC#
await channel.QueueBindAsync(
    queue: "payment.notification.queue",
    exchange: "payment.fanout",
    routingKey: "");
await channel.QueueBindAsync(
    queue: "payment.reporting.queue",
    exchange: "payment.fanout",
    routingKey: "");

کلید را خالی گذاشته‌ایم چون Fanout آن را برای انتخاب Queue به کار نمی‌برد. هر دو Queue نسخهٔ مستقل می‌گیرند؛ Ack در Queue اعلان نسخهٔ گزارش‌گیری را حذف نمی‌کند و هر سرویس جداگانه پردازش و تأیید می‌کند.

انتشار پیام در Fanout

پس از ساخت Exchange و Bindingها، Producer پیام پرداخت را روی payment.fanout منتشر می‌کند. Encoding.UTF8 و BasicProperties مانند نمونهٔ قبلی به namespaceهای System.Text و RabbitMQ.Client نیاز دارند.

انتشار از ProducerC#
var body = Encoding.UTF8.GetBytes("Payment succeeded");
await channel.BasicPublishAsync(
    exchange: "payment.fanout",
    routingKey: "",
    mandatory: true,
    basicProperties: new BasicProperties(),
    body: body);

نتیجهٔ مورد انتظار، دریافت متن Payment succeeded در هر دو Queue متصل است. برای مشاهده در Console، Consumer اعلان را روی Queue اعلان و Consumer گزارش را روی Queue گزارش ثبت کنید؛ الگوی دریافت و Ack همان نمونهٔ Consumer جزوهٔ اول است.

اگر Routing Key را payment.failed بگذارید، مقصدها تغییر نمی‌کنند؛ حتی پیام با این کلید هم به تمام Queueهای متصل می‌رسد. اگر در این مثال هیچ Queue متصلی و هیچ مسیر جایگزینی نباشد، mandatory: true باعث Return به Producer می‌شود؛ برای مشاهدهٔ آن، Handler مربوط به BasicReturnAsync را پیش از انتشار ثبت کنید.

این قطعه، نمونهٔ انتشار جزوه است؛ new BasicProperties() خودکار MessageId یا Persistent را تنظیم نمی‌کند و BasicPublishAsync روی Channel معمولی نیز خودکار منتظر Confirm نمی‌ماند. آن قابلیت‌ها را طبق بخش تأیید انتشار و بخش شناسهٔ پیام جداگانه فعال می‌کنیم.

بخش ۲۴ · جزوهٔ سوم، مراحل ۵ و ۶

چند Queue در برابر چند Consumer

دو Consumer اعلان روی یک Queue داریم و یک Consumer گزارش روی Queue دیگر. یک انتشار، در تحویل معمول به یکی از دو Consumer اعلان و به Consumer گزارش می‌رسد؛ هر دو Consumer اعلان نسخهٔ مستقل همان پیام را نمی‌گیرند.

payment.fanout
  ├─→ payment.notification.queue → Notification A OR B
  └─→ payment.reporting.queue    → Reporting Consumer

Fanout بین Queueها تکثیر می‌کند؛ Consumerهای یک Queue کار همان Queue را تقسیم می‌کنند. Redelivery هنگام شکست همچنان ممکن است، بنابراین این رفتار وعدهٔ پردازش دقیقاً یک‌باره نیست.

حسابداری باید Queue مستقل داشته باشد

برای دریافت مستقل همهٔ رویدادها توسط حسابداری، یک Queue جدا می‌سازیم و به Exchange متصل می‌کنیم. اتصال Consumer حسابداری به Queue اعلان، آن را رقیب Consumerهای اعلان می‌کند و نسخهٔ مستقل فراهم نمی‌کند.

اگر Consumer گزارش‌گیری خاموش شود اما Queue آن برقرار و متصل باشد، پیام‌ها می‌توانند آنجا منتظر بمانند و سرویس اعلان کار خود را ادامه دهد. فرض این مثال، نبود انقضا یا حذف پیام و باقی‌ماندن Queue است؛ خاموش‌بودن Consumer با نبود Binding فرق دارد.

بخش ۲۵ · جزوهٔ سوم، مرحلهٔ ۷

Queue دیرمتصل، پیام قبلی را نمی‌گیرد

در زمان انتشار پرداخت شمارهٔ ۱۲۳، Queue حسابداری هنوز Binding ندارد. بعد از انتشار آن را متصل می‌کنیم. پیام قبلی برای حسابداری بازپخش نمی‌شود؛ فقط انتشارهای بعد از اتصال به آن مسیریابی می‌شوند.

T1: publish Payment 123 → Notification + Reporting
T2: bind Accounting Queue to payment.fanout
T3: publish Payment 124 → Notification + Reporting + Accounting

Exchange سابقهٔ پیام‌ها را برای Queueهای آینده نگه نمی‌دارد. اما اگر Queue حسابداری از ابتدا متصل بود و فقط Consumer آن خاموش بود، پیام می‌توانست در همان Queue منتظر بماند. پس زمان ساخت Binding و زمان روشن‌شدن Consumer دو موضوع جدا هستند.

انتخاب بین Fanout و Direct

تمرین نهایی و مرور بعدی

حسابداری را پیش از انتشار به Exchange متصل کنید. اکنون با دو Consumer اعلان، یک Consumer گزارش و یک Consumer حسابداری، چند Queue و چند Consumer در تحویل معمول پیام را می‌گیرند؟ پاسخ: سه Queue نسخه می‌گیرند و سه Consumer دریافت می‌کنند؛ فقط یکی از دو Consumer اعلان انتخاب می‌شود.

مرور بعدی را روی تفاوت mandatory و requeue، مسئول تشخیص تکرار، تفاوت تنظیم مقصد DLX با ساخت Exchange، و نقش Queue بدون Consumer در تأخیر متمرکز کنید. مفهوم اصلی Fanout در جزوه کامل شده است؛ Topic Exchange فقط معرفی شده و هنوز آموزش داده نشده است.
