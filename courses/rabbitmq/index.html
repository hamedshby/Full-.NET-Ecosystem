مفاهیم پایهٔ RabbitMQ

۱. RabbitMQ چیست؟

فرض کنید پرداخت موفق شده است و باید برای کاربر اعلان ارسال شود. سرویس پرداخت می‌تواند یک پیام منتشر کند و سرویس اعلان بعداً آن را دریافت و پردازش کند. RabbitMQ یک Message Broker است؛ واسطه‌ای که پیام را از یک برنامه می‌گیرد و برای مصرف توسط برنامهٔ دیگر مدیریت می‌کند. در این مسیر، سرویس‌ها مجبور نیستند همیشه مستقیماً و هم‌زمان با یکدیگر ارتباط برقرار کنند.

Payment Service→RabbitMQ→Notification Service

۲. Message چیست؟

Message همان داده‌ای است که بین سرویس‌ها جابه‌جا می‌شود؛ مثلاً شناسهٔ پرداخت، شناسهٔ کاربر، مبلغ و وضعیت تراکنش. این نمونه فقط شکل اطلاعات را نشان می‌دهد؛ ارسال و دریافت مدل‌های JSON در ادامهٔ یادگیری بررسی خواهد شد.

نمونهٔ اطلاعات پرداختJSON
{
  "paymentId": 123,
  "userId": 45,
  "amount": 250000,
  "status": "Paid"
}

۳. Producer

سرویسی که Message را می‌سازد و آن را منتشر می‌کند. در این مثال، Payment Service نقش Producer را دارد.

۴. Consumer

سرویسی که Message را دریافت می‌کند و بر اساس آن کاری انجام می‌دهد. در این مثال، Notification Service نقش Consumer را دارد.

۵. Queue چیست؟

Queue محل نگهداری پیام‌ها تا زمان دریافت توسط Consumer است. وقتی سرویس اعلان در دسترس نیست، صف می‌تواند پیام را نگه دارد تا بعداً مصرف شود؛ طول عمر صف و پیام به تنظیمات آن‌ها وابسته است.

Producer → [ Queue: Message1 | Message2 | Message3 ] → Consumer

۶. Exchange چیست؟

Exchange مسئول مسیریابی پیام به صف‌های مناسب است. Producer پیام را به Exchange می‌فرستد و قوانین مسیریابی تعیین می‌کنند کدام Queue پیام را دریافت کند.

Producer→Exchange→Queue→Consumer

۷. Binding چیست؟

Binding رابطهٔ مسیریابی میان Exchange و Queue است. در Direct Exchange این رابطه یک کلید دارد که برای تطبیق با کلید پیام استفاده می‌شود.

۸. Routing Key چیست؟

Routing Key یک مقدار متنی است که Producer همراه پیام می‌فرستد؛ مثلاً payment.success. Exchange بسته به نوع خود از این کلید برای انتخاب مقصد استفاده می‌کند.

۹. Direct Exchange چیست؟

در Direct Exchange، پیام به هر صفی می‌رسد که Binding Key آن دقیقاً برابر Routing Key پیام باشد. اگر دو مقدار متفاوت باشند، آن Binding منطبق نیست.

Routing Key = payment.success
Binding Key = payment.success
Result: Match → Queue receives message

۱۰. اشارهٔ کوتاه به Fanout Exchange

Fanout Exchange پیام را بدون توجه به Routing Key به تمام صف‌های متصل به خود می‌فرستد. این مفهوم در جزوه فقط معرفی شده است؛ تمرکز فعلی روی Direct Exchange است.

آماده‌سازی پروژه‌های .NET

۱۱. یک Solution و دو برنامه

دو Console Application مستقل می‌سازیم؛ یکی برای ارسال پیام و دیگری برای دریافت آن. برای اجرای نمونه‌ها باید .NET SDK نصب باشد و یک RabbitMQ Broker روی localhost:5672 در دسترس باشد. کد جزوه از APIهای RabbitMQ.Client 7.x استفاده می‌کند.

ساخت پروژه‌ها و نصب ClientCLI
dotnet new sln -n RabbitMqDirectDemo
dotnet new console -n Payment.Producer
dotnet new console -n Notification.Consumer
dotnet sln add Payment.Producer
dotnet sln add Notification.Consumer

dotnet add Payment.Producer package RabbitMQ.Client --version 7.*
dotnet add Notification.Consumer package RabbitMQ.Client --version 7.*

هر دو پروژه به Package نیاز دارند، چون هر دو با Broker ارتباط برقرار می‌کنند. در جزوه دستور dotnet add package RabbitMQ.Client آمده است؛ اینجا نام پروژه هم مشخص شده تا دستور از پوشهٔ Solution قابل استفاده باشد.

۱۲. ConnectionFactory و Connection

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();

ConnectionFactory تنظیمات اتصال مثل آدرس Broker، نام کاربری، رمز عبور، Port و VirtualHost را نگه می‌دارد. ساختن این شیء اتصال را باز نمی‌کند؛ CreateConnectionAsync اتصال واقعی را ایجاد می‌کند.

برای هر پیام یک Connection جدید نمی‌سازیم. ایجاد اتصال TCP هزینه دارد و معمولاً اتصال را برای استفادهٔ طولانی‌تر باز نگه می‌داریم.

۱۳. Channel چیست؟

using var channel = await connection.CreateChannelAsync();

Channel یک ارتباط منطقی روی Connection است. بیشتر عملیات، مثل تعریف Exchange و Queue، ارسال پیام و ثبت Consumer از طریق آن انجام می‌شوند. این ساختار اجازه می‌دهد برای هر عملیات یک اتصال TCP تازه باز نکنیم.

ساخت توپولوژی Direct Exchange

توپولوژی در این مثال یعنی یک Exchange، یک Queue و رابطهٔ Binding بین آن‌ها.

۱۴. Declare کردن Exchange

await channel.ExchangeDeclareAsync(
    exchange: "payment.direct",
    type: ExchangeType.Direct
);

این دستور مطمئن می‌شود Exchange با نام payment.direct و نوع Direct وجود دارد. اگر قبلاً با مشخصات سازگار تعریف شده باشد، همان استفاده می‌شود.

مشخصات باید سازگار باشندنمی‌توان یک نام را یک بار با نوع Direct و بار دیگر با نوع Fanout تعریف کرد. تعریف مجدد منابع با مشخصات ناسازگار خطا ایجاد می‌کند.

۱۵. Declare کردن Queue

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

اگر صفی با این نام و مشخصات وجود نداشته باشد، ساخته می‌شود؛ اگر وجود داشته باشد، مشخصات باید با تعریف قبلی سازگار باشند.

۱۶. durable
با durable: true خود صف برای باقی‌ماندن بعد از Restart شدن Broker تعریف می‌شود. این گزینه به‌تنهایی پیام‌های صف را ماندگار نمی‌کند.
۱۷. exclusive
با exclusive: true صف به اتصال ایجادکننده وابسته است؛ استفاده از آن به همان Connection محدود می‌شود و با بسته‌شدن اتصال حذف می‌شود. برای صف اصلی پرداخت از false استفاده می‌کنیم.
۱۸. autoDelete
صفی با autoDelete: true که قبلاً Consumer داشته است، پس از جداشدن آخرین Consumer حذف می‌شود. در این مثال مقدار false است تا با قطع‌شدن Consumer صف حذف نشود.
۱۹. arguments
برای تنظیمات اضافی صف استفاده می‌شود. وقتی تنظیم اضافه نداریم، مقدار null می‌دهیم. برای مثال x-message-ttl مدت مجاز ماندن پیام در صف را بر حسب میلی‌ثانیه مشخص می‌کند.
var arguments = new Dictionary<string, object?>
{
    ["x-message-ttl"] = 60000
};

این مثال مقدار ۶۰ ثانیه را نشان می‌دهد و در صف اصلی جزوه استفاده نشده است. x-message-ttl مربوط به انقضای پیام است؛ برای انقضای خود صف تنظیم جداگانه‌ای مثل x-expires وجود دارد.

۲۰. ساخت Binding

await channel.QueueBindAsync(
    queue: "payment.notification.queue",
    exchange: "payment.direct",
    routingKey: "payment.success"
);

از این لحظه، پیام‌هایی که با Routing Key برابر payment.success به این Direct Exchange برسند، به صف payment.notification.queue مسیریابی می‌شوند.

ارسال Message از Producer

۲۱. تبدیل Message به بایت

var message = "Payment 123 succeeded";
var body = Encoding.UTF8.GetBytes(message);

بدنهٔ پیام در RabbitMQ بایت است. پس داده‌ای مثل متن یا JSON باید پیش از ارسال به بایت تبدیل شود. در این مثال از UTF-8 استفاده می‌کنیم و Consumer هم با همان Encoding متن را بازسازی می‌کند.

۲۲. Publish کردن Message

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.success",
    body: body
);

exchange مقصد اولیهٔ پیام است، routingKey کلید لازم برای یافتن Binding منطبق است و body محتوای واقعی پیام را نگه می‌دارد.

۲۳. Durable Queue و Persistent Message

ماندگاری صف و ماندگاری پیام دو تنظیم جدا هستند. برای علامت‌گذاری پیام به‌عنوان Persistent از BasicProperties استفاده می‌کنیم.

var properties = new BasicProperties
{
    Persistent = true
};

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.success",
    basicProperties: properties,
    body: body
);
دو تنظیم با دو مسئولیت متفاوت
تنظیممعنی
durable: trueخود صف پس از Restart شدن Broker باقی می‌ماند.
Persistent = trueپیام با حالت Persistent منتشر می‌شود؛ ماندگاری آن نیازمند صف Durable هم هست.
مرز این مرحله از آموزشPersistent بودن پیام تضمین کامل تحویل یا پردازش نیست. برای اطمینان سمت Publisher، مبحث Publisher Confirms در ادامه بررسی می‌شود. همچنین Exchange در نمونهٔ جزوه با تنظیم پیش‌فرض غیر Durable تعریف شده است؛ ماندگاری صف به معنی ماندگاری Exchange و مسیر آن نیست.

ساخت Consumer

۲۴. اتصال مستقل Consumer

برنامهٔ دریافت‌کننده اتصال و Channel خودش را می‌سازد. هر دو برنامه به یک Broker متصل می‌شوند، ولی اتصال مشترکی در حافظه ندارند.

var factory = new ConnectionFactory { HostName = "localhost" };
using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

۲۵. Declare کردن Queue در Consumer

دریافت‌کننده هم صف را با همان مشخصات تعریف می‌کند تا اگر زودتر اجرا شد، صف موجود باشد. این کار فقط صف را آماده می‌کند؛ Exchange و Binding در نمونهٔ فعلی توسط Producer ساخته می‌شوند.

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

۲۶. ساخت AsyncEventingBasicConsumer

var consumer = new AsyncEventingBasicConsumer(channel);

این شیء دریافت asynchronous پیام را پشتیبانی می‌کند و رویدادی به نام ReceivedAsync دارد. ساختن شیء به‌تنهایی دریافت پیام از صف را آغاز نمی‌کند.

۲۷. رویداد ReceivedAsync

consumer.ReceivedAsync += async (model, ea) =>
{
    Console.WriteLine("Message received");
    await Task.CompletedTask;
};

این Handler زمانی اجرا می‌شود که پیام به Consumer تحویل داده شود. در این قطعه هنوز فقط دریافت را در Console اعلام می‌کنیم.

۲۸. خواندن بدنهٔ Message

var body = ea.Body.ToArray();
var message = Encoding.UTF8.GetString(body);

در زمان اجرای ReceivedAsync پیام قبلاً به Handler تحویل شده است. ToArray بدنه را کپی می‌کند و GetString بایت‌ها را به متن تبدیل می‌کند. در Client نسخهٔ ۷، دادهٔ بدنه باید پیش از پایان Handler خوانده یا کپی شود.

۲۹. ثبت Consumer روی Queue

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: true,
    consumer: consumer
);

BasicConsumeAsync دریافت‌کننده را روی صف ثبت می‌کند. مقدار autoAck: true اولین حالت معرفی‌شده در جزوه است؛ در بخش بعد آن را به تأیید دستی تغییر می‌دهیم.

Ack، Nack و رفتار خطا

۳۰. مفهوم autoAck

با autoAck: true، Broker پیام ارسالی به Consumer را تأییدشده در نظر می‌گیرد و منتظر تمام‌شدن پردازش برنامه نمی‌ماند. اگر برنامه پس از تحویل و پیش از پایان پردازش متوقف شود، احتمال از دست رفتن پیام وجود دارد.

با autoAck: false، تأیید را خود برنامه پس از موفقیت پردازش ارسال می‌کند.

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: false,
    consumer: consumer
);

۳۱. BasicAckAsync

await channel.BasicAckAsync(
    deliveryTag: ea.DeliveryTag,
    multiple: false
);

Ack موفقیت پردازش پیام را اعلام می‌کند. DeliveryTag شناسهٔ تحویل روی همان Channel است و multiple: false یعنی فقط همین تحویل تأیید شود. تأیید باید روی Channel دریافت‌کنندهٔ پیام ارسال شود.

۳۲. BasicNackAsync

await channel.BasicNackAsync(
    deliveryTag: ea.DeliveryTag,
    multiple: false,
    requeue: true
);

Nack ناموفق‌بودن پردازش را اعلام می‌کند. با requeue: true پیام برای امکان دریافت دوباره به صف برمی‌گردد.

۳۳. تفاوت requeue: true و requeue: false

پس از ردکردن پیام چه اتفاقی می‌افتد؟
تنظیمرفتار
requeue: trueپیام به صف اصلی برمی‌گردد و می‌تواند دوباره تحویل داده شود.
requeue: falseپیام به صف اصلی برنمی‌گردد؛ در صورت تنظیم Dead Letter به مسیر آن می‌رود و در غیر این صورت کنار گذاشته می‌شود.
حلقهٔ Redeliveryاگر دادهٔ پیام خراب باشد و هر بار شکست بخورد، requeue: true بدون محدودیت می‌تواند دریافت دوبارهٔ بی‌پایان ایجاد کند. کد فعلی آموزشی است؛ Retry محدود و Dead Letter Queue هنوز به آن اضافه نشده‌اند.

رفتار Direct Exchange در چند مسیر

۳۴. چند Queue با Routing Keyهای متفاوت

payment.success → payment.notification.queue
payment.failed  → payment.failed.queue

اگر پیام با payment.failed منتشر شود، صفی آن را دریافت می‌کند که Binding Key منطبق داشته باشد. صف مربوط به payment.success از این Binding پیام نمی‌گیرد.

۳۵. یک Routing Key برای چند Queue

Queue A → payment.success
Queue B → payment.success
Queue C → payment.failed

Publish: payment.success
Result: Queue A + Queue B

هر دو صف A و B نسخه‌ای از پیام را دریافت می‌کنند، چون هر دو Binding منطبق دارند. Direct Exchange الزاماً پیام را فقط به یک صف نمی‌فرستد.

۳۶. پیام Unroutable

اگر هیچ Binding با کلید پیام تطابق نداشته باشد، پیام وارد هیچ صفی نمی‌شود. مثلاً وقتی فقط کلیدهای payment.success و payment.failed تعریف شده‌اند، پیام با کلید payment.refund مقصدی ندارد. در حالت پیش‌فرض و بدون سازوکار دیگری، این پیام کنار گذاشته می‌شود.

۳۷. گزینهٔ mandatory

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.refund",
    mandatory: true,
    basicProperties: properties,
    body: body
);

با mandatory: true اگر پیام به هیچ صفی مسیریابی نشود، RabbitMQ آن را از مسیر basic.return به Publisher برمی‌گرداند. این گزینه به معنی پردازش موفق پیام توسط Consumer نیست.

تا اینجا خوانده شدهرفتار mandatory معرفی شده است، اما Handler رویداد BasicReturnAsync هنوز در آموزش پیاده‌سازی نشده است. مدیریت پیام برگشتی نقطهٔ شروع ادامهٔ مطالعه خواهد بود.

کد کامل Producer تا نقطهٔ فعلی

این کد را در Payment.Producer/Program.cs قرار دهید. این برنامه توپولوژی را آماده می‌کند و پیام موفقیت پرداخت را منتشر می‌کند.

Payment.Producer/Program.csC#
using RabbitMQ.Client;
using System.Text;

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

await channel.ExchangeDeclareAsync(
    exchange: "payment.direct",
    type: ExchangeType.Direct
);

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

await channel.QueueBindAsync(
    queue: "payment.notification.queue",
    exchange: "payment.direct",
    routingKey: "payment.success"
);

var message = "Payment 123 succeeded";
var body = Encoding.UTF8.GetBytes(message);

var properties = new BasicProperties
{
    Persistent = true
};

await channel.BasicPublishAsync(
    exchange: "payment.direct",
    routingKey: "payment.success",
    mandatory: true,
    basicProperties: properties,
    body: body
);

Console.WriteLine($"Sent: {message}");
Console.ReadLine();

پیام با کلید payment.success به صف اعلان می‌رود. Console.ReadLine برنامه را باز نگه می‌دارد؛ خروجی Sent به‌تنهایی اثبات دریافت یا پردازش پیام نیست.

وضعیت نمونهmandatory فعال است، ولی Handler پیام برگشتی و Publisher Confirms هنوز در نمونهٔ جزوه وجود ندارند.

کد کامل Consumer تا نقطهٔ فعلی

این کد را در Notification.Consumer/Program.cs قرار دهید. نمونهٔ فعلی متن پیام را نمایش می‌دهد و بعد از اجرای بخش پردازش، تأیید دستی می‌فرستد.

Notification.Consumer/Program.csC#
using RabbitMQ.Client;
using RabbitMQ.Client.Events;
using System.Text;

var factory = new ConnectionFactory
{
    HostName = "localhost"
};

using var connection = await factory.CreateConnectionAsync();
using var channel = await connection.CreateChannelAsync();

await channel.QueueDeclareAsync(
    queue: "payment.notification.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: null
);

var consumer = new AsyncEventingBasicConsumer(channel);

consumer.ReceivedAsync += async (model, ea) =>
{
    try
    {
        var body = ea.Body.ToArray();
        var message = Encoding.UTF8.GetString(body);

        Console.WriteLine($"Received: {message}");

        // Business operation

        await channel.BasicAckAsync(
            deliveryTag: ea.DeliveryTag,
            multiple: false
        );
    }
    catch
    {
        await channel.BasicNackAsync(
            deliveryTag: ea.DeliveryTag,
            multiple: false,
            requeue: true
        );
    }
};

await channel.BasicConsumeAsync(
    queue: "payment.notification.queue",
    autoAck: false,
    consumer: consumer
);

Console.WriteLine("Waiting for messages...");
Console.ReadLine();

در نمونهٔ جزوه، محل عملیات کسب‌وکار با Comment مشخص شده است؛ فعلاً ارسال واقعی اعلان پیاده‌سازی نشده است. اگر پردازش در این بخش خطا بدهد، Nack با requeue: true ارسال می‌شود.

اجرای نمونه در دو Terminal

با Broker فعال، ابتدا Consumer را اجرا کنید و باز نگه دارید. سپس Producer را در Terminal دیگری اجرا کنید.

Terminal 1CLI
dotnet run --project Notification.Consumer
Terminal 2CLI
dotnet run --project Payment.Producer
خروجی مورد انتظارConsole
// Producer
Sent: Payment 123 succeeded

// Consumer
Waiting for messages...
Received: Payment 123 succeeded

در اجرای تمیز، Consumer بعد از ساخته‌شدن Binding توسط Producer پیام را دریافت می‌کند. اگر از قبل پیام‌هایی در صف باشند، ممکن است خروجی بیشتری ببینید.
