درس 1 · آموزش و تمرین

Authentication در برابر Authorization

Authentication یعنی شناسایی هویت کاربر؛ Authorization یعنی بررسی مجوز عملیات. هویت معتبر به‌تنهایی به معنی دسترسی به همه منابع نیست.

مثال عملی / کد آموزشیC# / HTTP
GET /api/admin/users
Authorization: Bearer <access-token>

سؤال مرور درس 1

کاربر با Access Token معتبر و نقش Customer به API مخصوص Admin درخواست دهد؛ پاسخ چیست؟

نمایش پاسخ تشریحی
403 Forbidden؛ چون کاربر احراز هویت شده اما مجوز ندارد. در نبود هویت معتبر معمولاً 401 Unauthorized است.

فرآیند Login و بررسی رمز عبور

سرور کاربر را پیدا می‌کند، رمز ورودی را با Password Hash ذخیره‌شده و الگوریتم و پارامترهای متناظر بررسی می‌کند، سپس در صورت موفقیت Access Token صادر می‌کند. Password Hash رمزگشایی نمی‌شود.

مثال عملی / کد آموزشیC# / HTTP
POST /api/auth/login
Content-Type: application/json

{"username":"hamed","password":"<password>"}

// Example response
{"accessToken":"<signed-access-token>","expiresIn":3600}

سؤال مرور درس 2

سرور برای بررسی رمز ورودی باید Hash دیتابیس را Decode کند؟

نمایش پاسخ تشریحی
خیر. باید از Password Verification متناسب با الگوریتم ذخیره‌شده (مثلاً PBKDF2 یا Argon2id) استفاده کند.

تفاوت Session، Cookie و Token

در Session مبتنی بر سرور، وضعیت نشست سمت سرور نگهداری می‌شود. Cookie سازوکار مرورگر برای نگهداری و ارسال داده است؛ ممکن است شناسه Session یا Authentication Ticket در آن باشد. JWT امضاشده می‌تواند بدون Session سمت سرور اعتبارسنجی شود.

مثال عملی / کد آموزشیC# / HTTP
Cookie: sessionId=<opaque-id>

Authorization: Bearer <signed-access-token>

سؤال مرور درس 3

آیا اعتبارسنجی JWT همیشه به خواندن Session از دیتابیس نیاز دارد؟

نمایش پاسخ تشریحی
خیر. برای JWT خودبسنده بررسی امضا، زمان انقضا، Issuer و Audience می‌تواند محلی باشد؛ لغو فوری ممکن است به وضعیت سمت سرور نیاز داشته باشد.

درس 4 · آموزش و تمرین

ساختار JWT: Header، Payload و Signature

JWT امضاشده معمولاً از سه بخش Base64Url(Header).Base64Url(Payload).Signature تشکیل می‌شود. Header الگوریتم، Payload ادعاها و Signature صحت و اصالت را پوشش می‌دهد. Payload محرمانه نیست.

مثال عملی / کد آموزشیC# / HTTP
// Header
{"alg":"HS256","typ":"JWT"}

// Payload
{"sub":"1001","role":"Customer","exp":1795000000}

// Format
<header>.<payload>.<signature>

سؤال مرور درس 4

اگر مهاجم Role را از Customer به Admin تغییر دهد ولی Secret Key نداشته باشد چه می‌شود؟

نمایش پاسخ تشریحی
امضای JWT دیگر معتبر نیست و سرور باید آن را رد کند.

تفاوت Encoding، Signing و Encryption

Encoding فقط قالب انتقال را تغییر می‌دهد، Signing اصالت و یکپارچگی را اثبات می‌کند و Encryption محرمانگی ایجاد می‌کند. JWT امضاشده معمولاً JWS است و رمزنگاری نیست؛ JWE برای رمزنگاری وجود دارد.

مثال عملی / کد آموزشیC# / HTTP
Signature = HMACSHA256(
  Base64Url(Header) + "." + Base64Url(Payload),
  SecretKey
)

سؤال مرور درس 5

آیا مهاجم می‌تواند Payload یک JWT امضاشده با HS256 را بخواند؟

نمایش پاسخ تشریحی
بله؛ Payload قابل Decode است، اما بدون Secret Key نمی‌تواند برای محتوای تغییریافته امضای معتبر بسازد.

اعتبارسنجی Issuer، Audience و Expiration

امضای معتبر کافی نیست. exp زمان انقضا، iss صادرکننده قابل اعتماد و aud مخاطب مورد انتظار را مشخص می‌کند. ClockSkew اختلاف ساعت را مدیریت می‌کند.

مثال عملی / کد آموزشیC# / HTTP
options.TokenValidationParameters = new()
{
    ValidateIssuer = true,
    ValidIssuer = "https://auth.payment.com",
    ValidateAudience = true,
    ValidAudience = "payment-api",
    ValidateLifetime = true,
    RequireExpirationTime = true,
    ValidateIssuerSigningKey = true,
    RequireSignedTokens = true,
    ClockSkew = TimeSpan.Zero
};
// Signing key and allowed algorithms configured separately.

سؤال مرور درس 7

Access Token با aud=reporting-api به payment-api ارسال شود و بررسی Audience فعال باشد؛ نتیجه چیست؟

نمایش پاسخ تشریحی
درخواست رد می‌شود، حتی اگر امضا و انقضا معتبر باشند.

درس 8 · آموزش و تمرین

تولید JWT با C#

پس از بررسی موفق Login، Claims و SigningCredentials را می‌سازیم و Access Token را با زمان انقضای محدود تولید می‌کنیم. در HS256 کلید باید تصادفی، قوی (حداقل ۳۲ بایت) و خارج از سورس‌کد نگهداری شود.

مثال عملی / کد آموزشیC# / HTTP
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;

public string GenerateToken(int userId, string role, IConfiguration config)
{
    var secret = config["Jwt:Secret"]
        ?? throw new InvalidOperationException("Missing secret");
    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret));
    var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub, userId.ToString()),
        new Claim(ClaimTypes.Role, role),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
    };
    var jwt = new JwtSecurityToken(
        issuer: config["Jwt:Issuer"],
        audience: config["Jwt:Audience"],
        claims: claims,
        expires: DateTime.UtcNow.AddMinutes(30),
        signingCredentials: credentials);
    return new JwtSecurityTokenHandler().WriteToken(jwt);
}

سؤال مرور درس 8

اگر SigningCredentials حذف شود ولی API امضای JWT را اجباری بداند چه می‌شود؟

نمایش پاسخ تشریحی
JWT بدون امضا رد می‌شود.

درس 9 · آموزش و تمرین

تنظیم AddAuthentication و AddJwtBearer

AddAuthentication سرویس احراز هویت و Scheme پیش‌فرض را ثبت می‌کند؛ AddJwtBearer Handler دریافت و اعتبارسنجی Bearer Access Token را تنظیم می‌کند؛ AddAuthorization سرویس‌های بررسی مجوز را ثبت می‌کند.

مثال عملی / کد آموزشیC# / HTTP
using System.Text;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;

var builder = WebApplication.CreateBuilder(args);
var jwt = builder.Configuration.GetSection("Jwt");
var secret = jwt["Secret"] ?? throw new InvalidOperationException("Missing secret");

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = jwt["Issuer"],
            ValidateAudience = true,
            ValidAudience = jwt["Audience"],
            ValidateLifetime = true,
            RequireExpirationTime = true,
            ValidateIssuerSigningKey = true,
            RequireSignedTokens = true,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret)),
            ValidAlgorithms = new[] { SecurityAlgorithms.HmacSha256 },
            ClockSkew = TimeSpan.Zero
        };
    });
builder.Services.AddAuthorization();
var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapGet("/api/payments", () => Results.Ok("Payment list"))
   .RequireAuthorization();
app.Run();

سؤال مرور درس 9

وظیفه اصلی AddJwtBearer چیست؟

نمایش پاسخ تشریحی
تنظیم دریافت و اعتبارسنجی JWT Bearer است؛ نه صدور Access Token.

Authorize، Roles و Claims

Authorize به‌طور پیش‌فرض کاربر احرازشده می‌خواهد. Roles محدودیت مبتنی بر نقش است و Claims مقادیر ادعاها مانند permission یا department هستند. مجوز دسترسی به حساب متعلق به شخص دیگر باید جداگانه بررسی شود.

مثال عملی / کد آموزشیC# / HTTP
[Authorize]
[HttpGet("payments")]
public IActionResult GetPayments() => Ok();

[Authorize(Roles = "Admin")]
[HttpGet("admin/reports")]
public IActionResult GetReports() => Ok();

var role = User.FindFirst(ClaimTypes.Role)?.Value;

درس 12 · آموزش و تمرین

Policy-Based Authorization

Policy مجموعه‌ای از شرط‌های صریح را تعریف می‌کند؛ مثلاً هم Role=Manager و هم permission=payment.refund. برای کنترل منابع، سقف مبلغ و مالکیت می‌توان AuthorizationHandler و Requirement نوشت.

مثال عملی / کد آموزشیC# / HTTP
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanRefundPayment", policy =>
    {
        policy.RequireRole("Manager");
        policy.RequireClaim("permission", "payment.refund");
    });
});

[Authorize(Policy = "CanRefundPayment")]
[HttpPost("payments/{id}/refund")]
public IActionResult Refund(long id) => Ok();

سؤال مرور درس 12

Manager با permission=payment.read می‌تواند Refund انجام دهد؟

نمایش پاسخ تشریحی
خیر. تمام Requirementهای این Policy باید برقرار باشند؛ معمولاً 403 دریافت می‌کند.

درس 13 · آموزش و تمرین

Access Token در برابر Refresh Token

Access Token برای درخواست‌های تکراری API است و معمولاً کوتاه‌عمر است. Refresh Token صرفاً برای درخواست تمدید Access Token به AuthService فرستاده می‌شود و اغلب یک مقدار تصادفی و طولانی‌عمرتر است. این دو را نباید با هم اشتباه گرفت.

تفاوت حیاتیAccess Token را می‌توان در درخواست‌های متعدد استفاده کرد؛ در Refresh Token Rotation تنها Refresh Token پس از تمدید به Used تغییر می‌کند.
مثال عملی / کد آموزشیC# / HTTP
GET /api/payments
Authorization: Bearer <access-token>

POST /api/auth/refresh
Content-Type: application/json

{"refreshToken":"<refresh-token>"}

سؤال مرور درس 13

پس از انقضای Access Token، کلاینت چگونه بدون Login مجدد Access Token جدید می‌گیرد؟

نمایش پاسخ تشریحی
Refresh Token معتبر را به AuthService می‌فرستد و سرور پس از کنترل‌های لازم Access Token جدید صادر می‌کند.

درس 14 · آموزش و تمرین

Logout، Revocation و Refresh Token Rotation

لغو Refresh Token مانع تمدید آینده می‌شود اما الزاماً Access Token فعلی را بی‌درنگ باطل نمی‌کند. برای لغو Access Token می‌توان از Revocation List و jti استفاده کرد. در Refresh Token Rotation، فقط Refresh Token یک‌بارمصرف است؛ Access Token تا زمان اعتبار می‌تواند بارها به API ارسال شود.

نوعنمونهوضعیت پس از تمدید
Access TokenAccess Aممکن است منقضی شده باشد؛ استفاده از Access B مجاز است
Refresh TokenRefresh AUsed
Refresh TokenRefresh BActive
مثال عملی / کد آموزشیC# / HTTP
// Refresh Token Rotation (pseudo-code)
BEGIN TRANSACTION;
SELECT * FROM RefreshTokens WHERE TokenHash = @hash FOR UPDATE;
IF Status != 'Active' OR ExpiresAt <= now: REJECT;
UPDATE RefreshTokens SET Status = 'Used' WHERE Id = @id;
INSERT INTO RefreshTokens(TokenHash, Status) VALUES (@newHash, 'Active');
COMMIT;
// Issue new Access Token and new Refresh Token.
// Syntax is conceptual; SQL Server uses different locking syntax.

سؤال مرور درس 14

اگر Refresh Token A قبلاً Used باشد و دوباره برای تمدید ارسال شود چه می‌شود؟

نمایش پاسخ تشریحی
درخواست رد می‌شود و ممکن است نشانه سرقت Refresh Token باشد. این وضعیت فقط به Refresh Token Rotation مربوط است، نه استفاده معمول Access Token.

حملات و امنیت JWT

برای جلوگیری از سوءاستفاده: HTTPS، نگهداری امن Access Token و Refresh Token، زمان انقضای کوتاه Access Token، اعتبارسنجی امضا و الگوریتم مجاز، محافظت در برابر XSS/CSRF و سازوکار لغو دسترسی ضروری‌اند. تغییر Role در دیتابیس Claims صادرشده را به‌روزرسانی نمی‌کند.

مثال عملی / کد آموزشیC# / HTTP
// Example: restrict allowed algorithm
ValidAlgorithms = new[] { SecurityAlgorithms.HmacSha256 };

// For urgent revocation, check a server-side denylist keyed by jti.
// Sensitive operations may also require current permissions.

نمایش پاسخ تشریحی
سرویس صرفاً مبتنی بر Claims قدیمی، دسترسی Admin را تا پایان اعتبار Access Token ممکن است بپذیرد.

درس 16 · آموزش و تمرین

JWT در Microservices و API Gateway

Gateway می‌تواند Access Token را اعتبارسنجی و درخواست را Route کند، اما سرویس مقصد نیز باید مرز اعتماد، مجوز عملیات و مالکیت منبع را کنترل کند. در RS256 سرویس صادرکننده با Private Key امضا می‌کند و سرویس‌های دیگر با Public Key اعتبارسنجی می‌کنند.

مثال عملی / کد آموزشیC# / HTTP
Client -> API Gateway -> PaymentService
                        -> WalletService
                        -> ReportService

AuthService signs Access Token with RSA private key.
PaymentService validates signature with RSA public key.
PaymentService checks payment.refund and ownership rules.

سؤال مرور درس 16

برای اعتبارسنجی Access Token امضاشده با RS256 در PaymentService کدام کلید لازم است؟

نمایش پاسخ تشریحی
Public Key؛ Private Key فقط برای امضای Access Token نگهداری می‌شود.

سناریوی عملی سیستم پرداخت و پرسش‌های Senior

طراحی نهایی: AuthService پس از Login، Access Token کوتاه‌عمر و Refresh Token امن صادر می‌کند؛ کلاینت Access Token را به Gateway می‌فرستد؛ Gateway بررسی اولیه و مسیریابی انجام می‌دهد؛ PaymentService اعتبار هویت و مجوز Refund، مالکیت/حد مبلغ و قواعد تجاری را کنترل می‌کند. برای Logout، Refresh Token لغو و در صورت نیاز Access Token هم از طریق Revocation بررسی می‌شود.

// Example: protected refund endpoint
[Authorize(Policy = "CanRefundPayment")]

public async Task<IActionResult> Refund(long paymentId)
{
    // Load payment from database

    // Record/refund using an atomic financial workflow
    return Accepted();
