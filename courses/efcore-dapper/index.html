درس 1 · آموزش و تمرین

مشکل N+1 و Lazy Loading

در سیستم پرداخت، دریافت مشتریان و سپس تراکنش‌های هر مشتری می‌تواند تعداد بسیار زیادی دستور SQL ایجاد کند.

سناریوی مشتریان و تراکنش‌ها

فرض کن ۵۰۰ مشتری داریم. ابتدا فهرست مشتریان دریافت می‌شود و سپس به مجموعه تراکنش‌های هر مشتری دسترسی داریم. اگر Lazy Loading فعال باشد و هیچ مجموعه‌ای قبلاً بارگذاری نشده باشد، برای هر مشتری یک Query جدا اجرا می‌شود.

نمونه مشکل N+1C#
var customers = await db.Customers.ToListAsync();
foreach (var customer in customers)
{
    Console.WriteLine(customer.Transactions.Count);
}
دستورات معادل تقریبیSQL
SELECT * FROM Customers;
SELECT * FROM Transactions WHERE CustomerId = 1;
SELECT * FROM Transactions WHERE CustomerId = 2;
-- ... for every customer

در این شرایط، یک درخواست اولیه و ۵۰۰ درخواست بعدی داریم: ۵۰۱ Query. این مسئله با افزایش رفت‌وبرگشت شبکه و فشار دیتابیس موجب افت کارایی می‌شود.

نکته مهماین سناریو مشروط به فعال بودن Lazy Loading است. در تنظیمات عادی EF Core، بارگذاری تنبل خودکار فعال نیست و باید صریحاً پیکربندی شود.

سؤال مرور درس 1

اگر ۵۰۰ مشتری داشته باشیم و هر مجموعه تراکنش هنگام اولین دسترسی Lazy Load شود، چند Query خواهیم داشت؟

نمایش پاسخ تشریحی
۵۰۱ Query: یک دستور دریافت مشتریان و ۵۰۰ دستور دریافت تراکنش‌ها.

درس 2 · آموزش و تمرین

حل N+1 با Include و AsSplitQuery و Projection

سه راهکار مهم برای کنترل دریافت روابط و تعداد Queryها را با مثال مقایسه می‌کنیم.

Include: دریافت موجودیت مرتبط

بارگذاری رابطهC#
var customers = await db.Customers
    .Include(c => c.Transactions)
    .ToListAsync();

در حالت پیش‌فرض Single Query، داده‌ها معمولاً در یک Query با JOIN دریافت می‌شوند. با این حال، داده مشتری ممکن است برای هر ردیف تراکنش در نتیجه تکرار شود.

AsSplitQuery: چند Query کنترل‌شده

تقسیم به چند QueryC#
var customers = await db.Customers
    .Include(c => c.Transactions)
    .AsSplitQuery()
    .ToListAsync();

برای یک مجموعه مرتبط، معمولاً دو Query اجرا می‌شود؛ نه یک Query برای هر مشتری. این روش به‌خصوص زمانی مفید است که چند مجموعه مرتبط باعث بزرگ شدن ضربی نتایج JOIN شوند.

Projection: فقط ستون‌های موردنیاز

بهینه برای گزارش تعداد تراکنش‌هاC#
var result = await db.Customers
    .Select(c => new
    {
        c.Id,
        c.Name,
        TransactionCount = c.Transactions.Count()
    })
    .ToListAsync();

به‌جای بارگذاری همه تراکنش‌ها، شمارش در دیتابیس انجام می‌شود و تنها داده‌های موردنیاز منتقل می‌شوند.

روشزمان استفادهملاحظه
Includeدریافت کامل موجودیت‌های مرتبطتکرار داده و حجم JOIN
AsSplitQueryدریافت چند Collectionرفت‌وبرگشت بیشتر و توجه به سازگاری خواندن
Projectionگزارش و خروجی سبک APIفقط خروجی انتخاب‌شده در دسترس است
نکته مهمبرای فهرست‌های بزرگ، Pagination نیز مهم است. Projection به‌تنهایی جای صفحه‌بندی و ایندکس مناسب را نمی‌گیرد.

سؤال مرور درس 2

برای نمایش فقط نام مشتری و تعداد تراکنش‌های ۱۰ هزار مشتری کدام روش مناسب‌تر است؟

نمایش پاسخ تشریحی
Projection با Select و Count؛ زیرا نیازی به دریافت تمام تراکنش‌ها نیست.

Change Tracker و AsNoTracking

EF Core موجودیت‌های ردیابی‌شده را برای تشخیص و ذخیره تغییرات نگهداری می‌کند.

Change Tracker چگونه عمل می‌کند؟

ردیابی پیش‌فرضC#
var customer = await db.Customers.FirstAsync(c => c.Id == 1);
customer.Name = "Hamed";
await db.SaveChangesAsync();

موجودیت دریافت‌شده به‌طور پیش‌فرض ردیابی می‌شود؛ در هنگام ذخیره، تغییر نام تشخیص داده شده و UPDATE مربوطه اجرا می‌شود.

خواندن بدون ردیابی

AsNoTrackingC#
var payment = await db.Payments
    .AsNoTracking()
    .FirstAsync(x => x.Id == 100);
payment.Status = "Completed";
await db.SaveChangesAsync();

در این مثال و با فرض نبود تغییرات ردیابی‌شده دیگر، UPDATE اجرا نمی‌شود؛ زیرا شیء payment زیر نظر Change Tracker نیست.

نکته مهمAsNoTracking اغلب برای سناریوهای فقط‌خواندنی مصرف حافظه و سربار ردیابی را کاهش می‌دهد. با این حال در سناریوهایی که Identity Resolution مهم است، باید نوع Query بررسی شود.

سؤال مرور درس 3

بعد از تغییر یک موجودیت AsNoTracking و اجرای SaveChangesAsync بدون Attach چه اتفاقی می‌افتد؟

نمایش پاسخ تشریحی
تغییر آن شیء به‌صورت خودکار در دیتابیس ذخیره نمی‌شود.

درس 4 · آموزش و تمرین

به‌روزرسانی موجودیت Detached با Attach

وقتی موجودیت را بدون ردیابی خوانده‌ایم، می‌توانیم فقط ویژگی موردنظر را برای UPDATE مشخص کنیم.

Attach و تنظیم فیلد تغییرکردهC#
db.Payments.Attach(payment);
db.Entry(payment)
    .Property(p => p.Status)
    .IsModified = true;
await db.SaveChangesAsync();

با Attach موجودیت وارد ردیابی می‌شود و با IsModified تنها ستون مشخص‌شده برای UPDATE علامت‌گذاری می‌شود.

مقایسه با Update

Update کل موجودیتC#
db.Payments.Update(payment);
await db.SaveChangesAsync();

برای موجودیت ساده و جداشده، روش Update معمولاً همه خصوصیات قابل‌به‌روزرسانی را Modified می‌کند. این می‌تواند به بازنویسی ناخواسته ستون‌های دیگر منجر شود.

احتیاط در محیط عملیاتیپیش از Attach، به وضعیت Entity مشابه در همان DbContext توجه کن؛ ردیابی هم‌زمان دو نمونه با کلید یکسان می‌تواند خطا ایجاد کند. در سیستم مالی، Idempotency و کنترل دسترسی نیز ضروری‌اند.

سؤال مرور درس 4

برای تغییر فقط ستون Status در یک موجودیت Detached، کدام روش دقیق‌تر است؟

نمایش پاسخ تشریحی
Attach سپس تعیین IsModified برای Status.

وضعیت‌های EntityState

هر موجودیت ردیابی‌شده وضعیت مشخصی دارد که تعیین می‌کند هنگام ذخیره چه عملی انجام شود.

وضعیترفتار هنگام SaveChanges
AddedINSERT
ModifiedUPDATE
DeletedDELETE
Unchangedبدون عملیات تغییر
Detachedخارج از ردیابی
بعد از Insert موفقC#
var payment = new Payment { Amount = 100000, Status = "Pending" };
db.Payments.Add(payment);
Console.WriteLine(db.Entry(payment).State); // Added
await db.SaveChangesAsync();
Console.WriteLine(db.Entry(payment).State); // Unchanged
شناسایی تغییرC#
var payment = await db.Payments.FirstAsync(x => x.Id == 100);
payment.Status = "Completed";
db.ChangeTracker.DetectChanges();
Console.WriteLine(db.Entry(payment).State); // Modified

پس از SaveChanges موفق در رفتار پیش‌فرض، وضعیت یک موجودیت Added به Unchanged تبدیل می‌شود.

درس 6 · آموزش و تمرین

Optimistic Concurrency با RowVersion

برای جلوگیری از Lost Update، نسخه رکورد را هنگام به‌روزرسانی بررسی می‌کنیم.

سناریوی رقابت دو برداشت

اگر دو درخواست موجودی ۱۰۰ هزار تومان را بخوانند، درخواست A مبلغ ۸۰ هزار و B مبلغ ۵۰ هزار برداشت کند، ذخیره بدون کنترل نسخه ممکن است اثر یکی از درخواست‌ها را بازنویسی کند.

مدل حسابC#
public class Account
{
    public int Id { get; set; }
    public decimal Balance { get; set; }
    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
SQL مفهومی نسخه‌دارSQL
UPDATE Accounts
SET Balance = @Balance
WHERE Id = @Id AND RowVersion = @OriginalRowVersion;

اگر نسخه رکورد تغییر کرده باشد، صفر ردیف تحت تأثیر قرار می‌گیرد و EF Core در به‌روزرسانی معمولی ردیابی‌شده خطای DbUpdateConcurrencyException می‌دهد.

نکته مهمدر SQL Server ستون rowversion مقدار عددی تجاری نیست؛ مقدار باینری تولیدشده به‌وسیله دیتابیس است.

سؤال مرور درس 6

اگر A با نسخه ۱ ذخیره کند و نسخه به ۲ تغییر کند، B با نسخه ۱ چه خطایی دریافت می‌کند؟

نمایش پاسخ تشریحی
DbUpdateConcurrencyException، زیرا شرط نسخه قبلی دیگر برقرار نیست.

درس 7 · آموزش و تمرین

مدیریت خطای Concurrency و Retry

تکرار عملیات فقط وقتی درست است که اطلاعات جدید دوباره خوانده و قوانین مالی دوباره ارزیابی شوند.

الگوی آموزشی تلاش مجددC#
public async Task<bool> WithdrawAsync(int accountId, decimal amount)
{
    for (var attempt = 0; attempt < 3; attempt++)
    {
        await using var db = new AppDbContext();
        var account = await db.Accounts.FirstAsync(a => a.Id == accountId);
        if (account.Balance < amount) return false;
        account.Balance -= amount;
        try
        {
            await db.SaveChangesAsync();
            return true;
        }
        catch (DbUpdateConcurrencyException)
        {
            // Re-read with a fresh context on next attempt.
        }
    }
    throw new InvalidOperationException("Concurrency retry exhausted");
}

اگر درخواست A از ۱۰۰ هزار تومان، ۶۰ هزار برداشت کرده باشد، موجودی جدید ۴۰ هزار است. درخواست B با مبلغ ۵۰ هزار پس از بازخوانی باید رد شود.

احتیاط در محیط عملیاتیاین نمونه تنها کنترل رقابت روی موجودی را نشان می‌دهد. عملیات مالی واقعی باید همراه با Ledger، تراکنش اتمیک و کلید Idempotency طراحی شود؛ Retry نباید برداشت تکراری ایجاد کند.

سؤال مرور درس 7

اگر پس از برداشت ۶۰ هزار، موجودی ۴۰ هزار باشد، برداشت مجدد ۵۰ هزار چه نتیجه‌ای دارد؟

نمایش پاسخ تشریحی
رد می‌شود؛ چون موجودی جدید کافی نیست.

Optimistic و Pessimistic Locking

دو شیوه کنترل هم‌زمانی با هزینه‌ها و رفتارهای متفاوت.

Optimistic

هنگام خواندن، قفل طولانی‌مدت محافظت‌کننده از تغییر دیگران نگه نمی‌داریم؛ تعارض در زمان ذخیره با RowVersion تشخیص داده می‌شود.

Pessimistic

نمونه SQL با قفل خواندنSQL
BEGIN TRANSACTION;
SELECT Balance
FROM Accounts WITH (UPDLOCK, HOLDLOCK)
WHERE Id = @Id;
-- Validate and update in the same transaction
COMMIT TRANSACTION;

در روش Pessimistic، قفل‌ها می‌توانند درخواست‌های دیگر را منتظر نگه دارند. مدت تراکنش، ایندکس‌ها و ترتیب دسترسی اهمیت دارند.

ویژگیOptimisticPessimistic
کنترلتشخیص تعارض هنگام ذخیرهقفل‌گذاری
هزینه رایجConflict و RetryBlocking و Deadlock
کاربردتداخل کمکنترل مناسب در تداخل بالا

اگر هزاران درخواست به یک حساب مشترک برسند، تعداد Conflictها و Retryهای Optimistic ممکن است بالا برود.

سؤال مرور درس 8

وقتی هزاران درخواست هم‌زمان یک رکورد RowVersionدار را تغییر دهند، چه رخ می‌دهد؟

نمایش پاسخ تشریحی
معمولاً تعارض‌های هم‌زمانی و تعداد Retryها افزایش پیدا می‌کند.

درس 9 · آموزش و تمرین

Deadlock در SQL Server

دو تراکنش با قفل‌گیری معکوس ممکن است وارد چرخه انتظار شوند.

تراکنش اول ابتدا A و سپس B را قفل می‌کند. تراکنش دوم ابتدا B و سپس A را قفل می‌کند. اگر هرکدام قفل اول را نگه دارد و منتظر قفل دوم بماند، Deadlock رخ می‌دهد.

دسترسی به منابع با ترتیب ثابتC#
// Conceptual rule:
// Always lock Account with smaller Id first,
// then Account with larger Id.

SQL Server معمولاً یکی از تراکنش‌ها را Deadlock Victim انتخاب کرده، آن را Rollback می‌کند و خطای 1205 را گزارش می‌دهد.

نکته مهمترتیب یکسان دسترسی به حساب‌ها، کوتاه نگه داشتن Transaction و Retry محدود همراه Idempotency احتمال مشکل را کم می‌کند؛ تضمین حذف همه Deadlockها نیست.

سؤال مرور درس 9

برای کاهش Deadlock میان دو تراکنش که دو حساب را به ترتیب معکوس قفل می‌کنند چه باید کرد؟

نمایش پاسخ تشریحی
منابع را در همه تراکنش‌ها با ترتیب یکسان قفل کنیم.

var payment = await db.Payments
    .AsNoTracking()

var payment = await connection.QueryFirstOrDefaultAsync<Payment>(

درس 11 · آموزش و تمرین

تراکنش مشترک EF Core و Dapper

می‌توان یک DbConnection و DbTransaction مشترک داشت تا دو عملیات روی یک دیتابیس اتمیک شوند.

نمونه ترکیبی ثبت پرداخت و کاهش موجودیC#
using Dapper;
using Microsoft.EntityFrameworkCore.Storage;

await db.Database.OpenConnectionAsync();
var connection = db.Database.GetDbConnection();
await using var tx = await db.Database.BeginTransactionAsync();
try
{
    db.Payments.Add(new Payment
    {
        AccountId = 1, Amount = 50000, Status = "Completed"
    });
    await db.SaveChangesAsync();

    var rows = await connection.ExecuteAsync(
        """
        UPDATE Accounts SET Balance = Balance - @Amount
        WHERE Id = @AccountId AND Balance >= @Amount
        """,
        new { AccountId = 1, Amount = 50000 },
        transaction: tx.GetDbTransaction());
    if (rows != 1)
        throw new InvalidOperationException("Insufficient balance");
    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();
    throw;
}

اجرای SaveChangesAsync داخل Transaction به معنی Commit نهایی نیست. اگر Dapper خطا دهد و Rollback موفق اجرا شود، ثبت پرداخت هم برگردانده می‌شود.

احتیاط در محیط عملیاتیاین کد برای نشان دادن تراکنش مشترک است. برای پرداخت واقعی، رکورد تکراری، Ledger و مدیریت وضعیت نهایی باید بررسی شوند. این تراکنش محلی بین چند دیتابیس یا سرویس مستقل توزیع نمی‌شود.

سؤال مرور درس 11

اگر EF Core INSERT را انجام دهد ولی Dapper خطا دهد و Rollback اجرا شود، وضعیت INSERT چیست؟

نمایش پاسخ تشریحی
به دلیل یک Transaction مشترک، INSERT نیز Rollback می‌شود.

Migration امن در Production

تغییر ساختار جداول بزرگ ممکن است قفل، فشار روی Transaction Log و Timeout ایجاد کند.

ایجاد MigrationBash
dotnet ef migrations add AddPaymentReferenceCode
dotnet ef database update

الگوی Expand and Contract

مرحله ExpandSQL
ALTER TABLE Payments
ADD ReferenceCode NVARCHAR(50) NULL;

ابتدا ستون Nullable اضافه می‌شود تا نسخه قدیمی برنامه همچنان قابل اجرا بماند. سپس نسخه جدید منتشر می‌شود و داده‌های قدیمی به‌صورت Batch تکمیل می‌شوند.

مرحله ContractSQL
ALTER TABLE Payments
ALTER COLUMN ReferenceCode NVARCHAR(50) NOT NULL;

محدودیت NOT NULL فقط پس از تکمیل داده‌ها، تأیید سازگاری و بررسی اثر قفل‌گذاری اعمال می‌شود.

اسکریپت قابل بررسی قبل از استقرارBash
dotnet ef migrations script --idempotent -o migration.sql
نکته مهمIdempotent بودن اسکریپت، فقط اعمال‌شدن Migrationهای اجرا‌نشده را بر اساس تاریخچه مدیریت می‌کند؛ به معنی بدون‌ریسک یا بدون‌قطعی بودن تغییر نیست.

سؤال مرور درس 12

برای افزودن ستون اجباری به جدول ۵۰ میلیون رکوردی، چه روشی مناسب‌تر است؟

نمایش پاسخ تشریحی
افزودن Nullable، تکمیل مرحله‌ای داده و سپس اعمال NOT NULL با بررسی ریسک قفل‌ها.

درس 13 · آموزش و تمرین

Rollback و Zero-Downtime Deployment

در زمان استقرار تدریجی، نسخه قدیمی و جدید برنامه ممکن است هم‌زمان به دیتابیس متصل باشند.

مشکل تغییر نام مستقیم ستون

تغییر نام پرریسکSQL
EXEC sp_rename
    'Payments.Amount',
    'PaymentAmount',
    'COLUMN';

اگر نسخه جدید منتشر شود و سپس بخواهیم نسخه قبلی را برگردانیم، برنامه قدیمی هنوز ستون Amount را انتظار دارد و ممکن است خطا بدهد.

روش سازگار با نسخه قبل

افزودن به‌جای حذف فوریSQL
ALTER TABLE Payments
ADD PaymentAmount DECIMAL(18,2) NULL;

نسخه جدید باید برای دوره انتقال با هر دو ساختار سازگار باشد؛ در صورت نیاز Dual Write و Backfill اجرا شود. حذف ستون قدیمی فقط پس از خروج همه نسخه‌های وابسته انجام شود.

مفهوممعنا
Application Rollbackبازگرداندن نسخه برنامه
Database Rollbackبرگرداندن تغییرات دیتابیس؛ همیشه امن نیست
Backward Compatibilityسازگاری ساختار دیتابیس با نسخه‌های فعال
Zero-Downtimeاستقرار همراه حفظ دسترس‌پذیری با طراحی صحیح
نکته مهمReadiness Probe، مدیریت درخواست‌های در جریان و انتشار تدریجی نیز از اجزای مهم استقرار بدون قطعی هستند.

سؤال مرور درس 13

بعد از حذف ستون Amount و بازگشت به نسخه قدیمی چه مشکلی ممکن است ایجاد شود؟

نمایش پاسخ تشریحی
نسخه قدیمی خطا می‌دهد چون ستون Amount دیگر وجود ندارد.

درس 14 · آموزش و تمرین

تکمیل دوره: Migration در CI/CD و جمع‌بندی

این درس تکمیلی، موضوع وعده‌داده‌شده بعد از درس ۱۳ را پوشش می‌دهد.

الگوی پیشنهادی استقرار

در CI، Migration تولید و اسکریپت SQL ساخته می‌شود. در CD، اسکریپت مرور، در محیط مشابه Production آزمایش، و سپس در یک مرحله کنترل‌شده اجرا می‌شود. پس از آماده بودن دیتابیس، نسخه سازگار برنامه به‌تدریج منتشر می‌شود.

تولید اسکریپتBash
dotnet ef migrations script --idempotent --output migration.sql

چک‌لیست عملیاتی

قبل از اجرا، زمان اجرای تغییر، قفل‌های Schema، استفاده از CPU و I/O، Transaction Log، ظرفیت دیسک، Backup قابل‌بازیابی و روش توقف یا اصلاح را بررسی کن.

در استقرار با چند Replica، معمولاً Migration را به‌عنوان یک مرحله جداگانه و کنترل‌شده اجرا می‌کنیم، نه هم‌زمان هنگام Startup همه Replicaها.

جمع‌بندی پنج موضوع تصویر

موضوعنکته کلیدی
N+1کنترل تعداد Queryها با Include، SplitQuery یا Projection
Change Trackerتشخیص تغییرات و استفاده آگاهانه از AsNoTracking
ConcurrencyRowVersion، بررسی تعارض و Retry امن
EF Core و Dapperانتخاب بر اساس Query، نیاز به ORM و Performance
Production MigrationExpand/Contract، سازگاری نسخه‌ها و بازبینی SQL
احتیاط در محیط عملیاتیبرای تغییرات مخرب یا سنگین، صرفاً به Down Migration تکیه نکن؛ به برنامه بازیابی داده‌ها و سازگاری نسخه‌های برنامه نیاز داری.

سؤال مرور درس 14

آیا بهتر است همه Replicaهای سرویس در Startup خودشان Migration را اجرا کنند؟

نمایش پاسخ تشریحی
خیر؛ معمولاً اجرای مرحله‌ای و کنترل‌شده در فرایند Deploy امن‌تر و قابل ممیزی‌تر است.

پایان دوره

راهنمای تصمیم‌گیری در پروژه واقعی

برای Queryهای خواندنی ابتدا Projection و AsNoTracking را ارزیابی کن؛ برای تغییر داده‌های رقابتی از کنترل هم‌زمانی و قواعد تجاری مناسب استفاده کن؛ برای عملیات چندگانه در یک دیتابیس از Transaction واحد کمک بگیر؛ و برای تغییر ساختار دیتابیس، سازگاری نسخه‌ها را قبل از انتشار بررسی کن.

برای تمرین مصاحبه، بتوانی توضیح بدهی چرا N+1 رخ می‌دهد، چرا SaveChangesAsync بدون Change Tracker یک شیء Detached را تغییر نمی‌دهد، چرا Retry بدون بازخوانی خطرناک است و چرا Rollback برنامه الزاماً Rollback دیتابیس نیست.

منابع و نکته‌های پایانی

این جزوه از سرفصل‌ها و مثال‌های همین گفت‌وگوی آموزشی گردآوری شده و در قالب فایل پیوست طراحی شده است. درس ۱۴ به‌عنوان تکمیل وعده آموزشی انتهای درس ۱۳ افزوده شده است.

برای مطالعه بیشتر: بارگذاری داده‌های مرتبط، Change Tracking، Concurrency و اعمال Migration.
