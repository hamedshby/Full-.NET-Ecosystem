درس 1 · آموزش و تمرین

Middleware چیست و چه کاری انجام می‌دهد؟

در یک سرویس پرداخت، درخواست پیش از رسیدن به Endpoint ممکن است ثبت لاگ، احراز هویت، مدیریت خطا و سایر مراحل را طی کند.

تعریف Middleware

هر Middleware یک جزء از مسیر پردازش درخواست HTTP است؛ می‌تواند قبل و بعد از جزء بعدی کاری انجام دهد، پاسخ را مستقیماً بسازد یا پردازش را به مرحلهٔ بعد بسپارد.

ساده‌ترین MiddlewareC#
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    Console.WriteLine("Request received");
    await next(context);
});

app.MapGet("/payments", () => "Payments");
app.Run();
نکته مهمدر این صفحه، app.Run() بدون پارامتر برای اجرای برنامه است؛ app.Run(RequestDelegate) با ورودی، Middleware پایانی تعریف می‌کند.

درس 2 · آموزش و تمرین

مفهوم Pipeline و مسیر رفت‌وبرگشت

ترتیب تعریف Middlewareها مشخص می‌کند کدهای قبل و بعد از next در چه زمانی اجرا شوند.

رفت درخواست و برگشت پاسخ

درخواست به‌ترتیب به مراحل بعدی می‌رود؛ هنگام پایان یافتن مراحل داخلی، کنترل به اجزای قبلی بازمی‌گردد. این رفتار شبیه لایه‌های تو در تو است.

A Before→B Before→Endpoint→B After→A After
سؤال تمرینی از گفت‌وگوC#
app.Use(async (context, next) =>
{
    Console.WriteLine("1");
    await next(context);
    Console.WriteLine("2");
});

app.Use(async (context, next) =>
{
    Console.WriteLine("3");
    await next(context);
    Console.WriteLine("4");
});

app.Run(context =>
{
    Console.WriteLine("5");
    return Task.CompletedTask;
});

خروجی این مثال: 1 → 3 → 5 → 4 → 2. پس از await next(context)، اجرای متد به همان نقطه بازمی‌گردد؛ البته اگر Exception کنترل را از مسیر عادی خارج نکند.

اهمیت ترتیب Authentication و Authorization

برای تصمیم‌گیری دربارهٔ مجوز، معمولاً لازم است هویت کاربر قبلاً تعیین شده باشد.

ترتیب متداولC#
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

چرا جابه‌جایی خطرناک است؟

Middleware احراز هویت معمولاً توکن را ارزیابی می‌کند و HttpContext.User را تنظیم می‌کند. سپس Middleware مجوزدهی بررسی می‌کند آیا هویت شناسایی‌شده اجازهٔ دسترسی به Endpoint را دارد یا خیر.

ترتیب مسئله‌دارC#
// Incorrect in the typical setup:
app.UseAuthorization();
app.UseAuthentication();
نکته مهمرفتار دقیق به تنظیم سیاست‌ها و Schemeها بستگی دارد، اما ترتیب پیش‌فرض توصیه‌شده معمولاً UseAuthentication قبل از UseAuthorization است.

کد وضعیت 401 معمولاً وقتی برمی‌گردد که کاربر احراز هویت نشده باشد؛ 403 وقتی که هویت تأیید شده ولی مجوز کافی ندارد.

سؤال مرور درس 3

نمایش پاسخ تشریحی
چون برای بررسی مجوز، به هویت کاربر که توسط Authentication تعیین می‌شود نیاز دارد.

درس 4 · آموزش و تمرین

Short-Circuit و متوقف کردن Pipeline

گاهی یک درخواست قبل از رسیدن به Controller باید رد شود؛ مثلاً وقتی هدر ضروری را ندارد.

بررسی وجود هدرC#
app.Use(async (context, next) =>
{
    Console.WriteLine("A");
    if (!context.Request.Headers.ContainsKey("X-Api-Key"))
    {
        context.Response.StatusCode = 401;
        await context.Response.WriteAsync("Unauthorized");
        return;
    }

    await next(context);
    Console.WriteLine("B");
});

app.Run(context =>
{
    Console.WriteLine("C");
    return Task.CompletedTask;
});

اگر هدر وجود نداشته باشد، خروجی تنها A است. اگر هدر وجود داشته باشد، خروجی A → C → B است.

نکته مهماین مثال فقط وجود هدر را کنترل می‌کند و صحت کلید را نمی‌سنجد؛ برای سامانهٔ واقعی باید اعتبارسنجی درست، پاسخ مناسب و حفاظت از اطلاعات حساس انجام شود.

ویژگی Short-Circuit

حذف await next(context) از یک Middleware باعث می‌شود مراحل بعدی اجرا نشوند. البته کدهای Middlewareهایی که پیش‌تر وارد آن‌ها شده‌ایم، در مسیر بازگشت می‌توانند همچنان اجرا شوند.

سؤال مرور درس 4

اگر هدر وجود داشته باشد، ترتیب چاپ چیست؟

نمایش پاسخ تشریحی
A → C → B.

تفاوت Use و Run و Map

این سه ابزار برای ساخت مسیر اصلی و شاخه‌های جداگانهٔ Pipeline به کار می‌روند.

Use: ادامه یا توقف

UseC#
app.Use(async (context, next) =>
{
    Console.WriteLine("Before");
    await next(context);
    Console.WriteLine("After");
});

Run: بخش پایانی

Run با RequestDelegateC#
app.Run(async context =>
{
    await context.Response.WriteAsync("Hello");
});

Map: شاخه‌بندی براساس مسیر

Map برای شاخهٔ adminC#
app.Map("/admin", adminApp =>
{
    adminApp.Run(async context =>
        await context.Response.WriteAsync("Admin Area"));
});

app.Run(async context =>
    await context.Response.WriteAsync("Main Area"));
سؤال دوره: Run و قطع مسیرC#
app.Use(async (ctx, next) =>
{
    Console.WriteLine("A");
    await next(ctx);
    Console.WriteLine("B");
});

app.Run(ctx =>
{
    Console.WriteLine("C");
    return Task.CompletedTask;
});

app.Use(async (ctx, next) =>
{
    Console.WriteLine("D");
    await next(ctx);
});
// Output: A, C, B  (D never executes)
نکته مهممتد MapGet برای ثبت Route یک Endpoint است و با app.Map("/admin", ...) که شاخهٔ Middleware می‌سازد متفاوت است.

نمایش پاسخ تشریحی

نوشتن Custom Middleware

برای کدهای قابل استفادهٔ مجدد، منطق را در یک کلاس مستقل قرار می‌دهیم.

کلاس Middleware برای اندازه‌گیری زمانC#
using System.Diagnostics;

public sealed class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(
        RequestDelegate next,
        ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var watch = Stopwatch.StartNew();
        await _next(context);
        watch.Stop();

        _logger.LogInformation(
            "Request {Path} took {Ms} ms",
            context.Request.Path, watch.ElapsedMilliseconds);
    }
}
ثبت در Program.csC#
app.UseMiddleware<RequestTimingMiddleware>();
app.MapGet("/payments", () => "Payment List");

کلاس، RequestDelegate مرحلهٔ بعد را در سازنده دریافت می‌کند و از متد InvokeAsync برای پردازش هر درخواست استفاده می‌کند.

نکته مهمبرای تضمین ثبت زمان هنگام وقوع Exception، نسخهٔ try/finally را در درس ۱۲ می‌بینیم.

سؤال مرور درس 6

نمایش پاسخ تشریحی
خیر؛ Middleware مسیر را قطع می‌کند و Endpoint بعدی اجرا نمی‌شود.

درس 7 · آموزش و تمرین

Exception Handling Middleware

خطاهای Endpointها و Middlewareهای بعدی می‌توانند به Middleware محافظ بیرونی برگردند.

نمونهٔ آموزشی با محافظ پاسخ شروع‌شدهC#
public sealed class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _logger;

    public ExceptionMiddleware(RequestDelegate next,
        ILogger<ExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled request error");
            if (context.Response.HasStarted) throw;

            context.Response.Clear();
            context.Response.StatusCode = 500;
            await context.Response.WriteAsJsonAsync(new
            {
                title = "Internal Server Error",
                status = 500
            });
        }
    }
}
قرارگیری در ابتداC#
app.UseMiddleware<ExceptionMiddleware>();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

اگر Authentication قبل از Middleware مدیریت خطا قرار گرفته باشد، Exception ناشی از Authentication در محدودهٔ try/catch آن قرار نمی‌گیرد.

نکته مهمدر پروژهٔ واقعی می‌توان از UseExceptionHandler یا IExceptionHandler استفاده کرد. Middleware سفارشی بالا برای توضیح مفهوم است؛ وضعیت پاسخ و logging باید با سیاست سرویس سازگار باشد.

سؤال مرور درس 7

اگر Authentication قبل از ExceptionMiddleware خطا بدهد، آیا دومی آن را می‌گیرد؟

نمایش پاسخ تشریحی
خیر؛ هنوز وارد محدودهٔ try/catch آن نشده‌ایم.

ترتیب عملی Middlewareها در Web API

در سامانهٔ پرداخت، جای مراحل امنیتی، مسیریابی، مدیریت خطا و Rate Limiting را باید هدفمند انتخاب کنیم.

نمونهٔ شماتیک ترتیب (تنظیمات Service لازم‌اند)C#
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
// Configure Authentication and Authorization schemes/policies.
// Configure Rate Limiting policies.

var app = builder.Build();

app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseRateLimiter();
app.UseAuthorization();
app.MapControllers();
app.Run();
مرحلهوظیفه
Exception Handlerمدیریت خطاهای مراحل بعدی
HTTPS Redirectionهدایت به HTTPS
Routingشناسایی Endpoint
Authenticationشناسایی کاربر
Rate Limiterاعمال سیاست محدودیت درخواست
Authorizationبررسی دسترسی
MapControllersثبت Endpointهای کنترلر

در سیاست‌های محدودسازی درخواست وابسته به Endpoint، معمولاً UseRateLimiter را بعد از UseRouting قرار می‌دهیم. جای دقیق آن نسبت به احراز هویت، به نیاز سیاست بستگی دارد.

محافظت EndpointC#
[Authorize(Roles = "Admin")]
[HttpPost("payments")]
public IActionResult CreatePayment() => Ok();

اگر توکن نامعتبر باشد و سیاست نیاز به کاربر معتبر داشته باشد، معمولاً 401 برمی‌گردد. اگر توکن معتبر باشد اما نقش Admin وجود نداشته باشد، معمولاً 403 دریافت می‌کنیم.

نکته مهماین قطعه یک اسکلت آموزشی است و بدون ثبت Schemeها، سیاست‌ها و Endpoint مدیریت خطا، یک تنظیم کامل قابل اجرا نیست.

تمرین تکمیلی: 401 و 403

احراز هویت ناموفق

Pipeline امنیتیC#
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

در پیکربندی متداول، وقتی توکن نامعتبر است، Authentication هویت احراز‌شده‌ای تولید نمی‌کند. سپس Authorization در Endpoint دارای [Authorize] معمولاً با 401 جلوی اجرای اکشن را می‌گیرد.

دسترسی ناکافی

کنترلر دارای محدودیت نقشC#
[Authorize(Roles = "Admin")]
[HttpPost("payments")]
public IActionResult CreatePayment() => Ok();

اگر توکن معتبر باشد ولی کاربر نقش Admin نداشته باشد، نتیجهٔ معمول 403 Forbidden است.

وضعیتنتیجهٔ معمول
هویت نامعتبر یا غایب401 Unauthorized
هویت معتبر با مجوز ناکافی403 Forbidden
نکته مهمپیاده‌سازی Schemeها، Handlerهای چالش و سیاست‌ها می‌تواند جزئیات رفتار را تغییر دهد.

تفاوت Middleware، Action Filter و Endpoint Filter

هر سه امکان اجرای منطق در بخشی از چرخهٔ درخواست را می‌دهند، اما محل اجرا و دسترسی آن‌ها متفاوت است.

MiddlewareC#
app.Use(async (context, next) =>
{
    Console.WriteLine("Middleware Before");
    await next(context);
    Console.WriteLine("Middleware After");
});
Action Filter (نیازمند Microsoft.AspNetCore.Mvc.Filters)C#
public class LoggingFilter : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(
        ActionExecutingContext context,
        ActionExecutionDelegate next)
    {
        Console.WriteLine("Action Before");
        await next();
        Console.WriteLine("Action After");
    }
}
Endpoint FilterC#
app.MapPost("/payments", () => Results.Ok("Created"))
   .AddEndpointFilter(async (context, next) =>
   {
       Console.WriteLine("Endpoint Before");
       var result = await next(context);
       Console.WriteLine("Endpoint After");
       return result;
   });
ابزارمحل اجراکاربرد
Middlewareدر HTTP Pipelineلاگ و پردازش مشترک درخواست‌ها
Action Filterدر چرخهٔ اجرای Action در MVCمنطق و پارامترهای اکشن کنترلر
Endpoint Filterدر اجرای Endpoint پشتیبانی‌شدهاعتبارسنجی و منطق مربوط به Endpoint
نکته مهماگر هدف اندازه‌گیری زمان پردازش همهٔ درخواست‌ها، اعم از Controller و Minimal API باشد، Middleware انتخاب طبیعی‌تری است.

Dependency Injection و Scoped Service در Middleware

Middleware معمولی مبتنی بر کلاس در زمان ساخت Pipeline ساخته می‌شود، اما Scoped باید از Scope درخواست دریافت شود.

روش نادرست برای Scoped ServiceC#
builder.Services.AddScoped<IPaymentService, PaymentService>();

public sealed class PaymentMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IPaymentService _paymentService;

    // Wrong for conventional middleware:
    public PaymentMiddleware(RequestDelegate next,
        IPaymentService paymentService)
    {
        _next = next;
        _paymentService = paymentService;
    }
}

تزریق Scoped در سازندهٔ Middleware معمولی ممکن است با اعتبارسنجی DI خطا دهد یا در تنظیمات نامناسب طول‌عمر نادرستی ایجاد کند.

روش درست: تزریق در InvokeAsyncC#
public sealed class PaymentMiddleware
{
    private readonly RequestDelegate _next;

    public PaymentMiddleware(RequestDelegate next)
        => _next = next;

    public async Task InvokeAsync(
        HttpContext context, IPaymentService paymentService)
    {
        await paymentService.ProcessAsync();
        await _next(context);
    }
}

راه جایگزین: IMiddleware

اگر Middleware را با رابط IMiddleware بسازیم و به‌صورت Scoped در DI ثبت کنیم، امکان تزریق سرویس Scoped در سازنده وجود دارد. این دو شیوهٔ ساخت، طول‌عمر یکسانی ندارند.

نکته مهمپیش از استفاده از سرویس پردازش پرداخت در هر درخواست، اثر آن بر امنیت، کارایی و idempotency را نیز بررسی کن؛ کد این درس صرفاً برای نمایش DI است.

سؤال مرور درس 10

چرا Scoped را نباید در سازندهٔ Middleware معمولی تزریق کرد؟

نمایش پاسخ تشریحی
چون Middleware معمولی برای Pipeline ساخته می‌شود و با Scope یک درخواست یکسان نیست؛ وابستگی Scoped باید در InvokeAsync دریافت شود.

مصاحبه Senior: خطا، ترتیب و try/finally

این درس سناریوهای تمرینی گفت‌وگو را جمع‌بندی می‌کند و نسخهٔ مقاوم Middleware اندازه‌گیری زمان را نشان می‌دهد.

سناریوی ۱: خطای Authentication

قرارگیری ExceptionMiddleware قبل از بخش‌های حساسC#
app.UseMiddleware<ExceptionMiddleware>();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

این ترتیب خطاهای منتشرشده از Authentication و مراحل بعدی را می‌تواند دریافت کند؛ اما خطاهای Startup، Background Service یا خطاهایی که قبل از ورود به این Middleware رخ دهند را پوشش نمی‌دهد.

سناریوی ۲: خروجی try/catch

ترتیب خروجی مورد آزمونC#
app.Use(async (context, next) =>
{
    Console.WriteLine("A");
    try { await next(context); }
    catch (Exception) { Console.WriteLine("B"); }
    Console.WriteLine("C");
});

app.Use(async (context, next) =>
{
    Console.WriteLine("D");
    throw new Exception("Database Error");
});

app.Run(ctx =>
{
    Console.WriteLine("E");
    return Task.CompletedTask;
});

// Output: A, D, B, C

چون Middleware دوم پیش از رسیدن به E خطا می‌دهد، خروجی برابر A → D → B → C خواهد بود.

ثبت زمان درخواست با try/finally و جمع‌بندی

در آخرین درس بررسی می‌کنیم چگونه ثبت لاگ حتی هنگام Exception هم انجام شود.

سناریوی ۳: ثبت زمان هنگام Exception

نسخهٔ مقاوم برای ثبت زمانC#
using System.Diagnostics;

public sealed class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(
        RequestDelegate next,
        ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var stopwatch = Stopwatch.StartNew();
        try
        {
            await _next(context);
        }
        finally
        {
            stopwatch.Stop();
            _logger.LogInformation(
                "Request {Method} {Path} took {Ms} ms",
                context.Request.Method,
                context.Request.Path,
                stopwatch.ElapsedMilliseconds);
        }
    }
}
ترتیب نمونهC#
app.UseMiddleware<RequestTimingMiddleware>();
app.UseExceptionHandler("/error");
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

بلوک finally حتی هنگام انتشار Exception اجرا می‌شود، ولی خودِ خطا را مدیریت نمی‌کند. برای مدیریت خطا باید در جای مناسب catch یا Exception Handler جدا داشته باشیم.

نکته مهمبرای استفادهٔ عملی در Production وضعیت شروع پاسخ، ساختار Problem Details، داده‌های حساس لاگ، cancellation و مسیرهای استثنایی را نیز بررسی کن.

سؤال مرور درس 12

چرا finally برای ثبت زمان مطمئن‌تر از دستور بعد از await next است؟

نمایش پاسخ تشریحی
چون حتی اگر Exception از await _next(context) خارج شود، کد داخل finally هنگام خروج از try اجرا می‌شود.
