۱. انگلیسی و آمادگی مصاحبه ۴۰ دقیقه

معرفی حرفه‌ای در مصاحبه

آموزش: معرفی را با نقش و تخصص شروع کن. بعد یک مثال از محصول یا تیمی که روی آن کار کرده‌ای بیاور. برای فعالیتی که از گذشته آغاز شده و هنوز ادامه دارد، می‌توانی از Present Perfect Continuous استفاده کنی: subject + have/has been + verb-ing. برای مسئولیت یک پروژهٔ تمام‌شده، Past Simple مناسب است.

I have been working as a backend developer for several years. On my last project, I led a team of three developers.

چند سال است که به‌عنوان توسعه‌دهندهٔ بک‌اند کار می‌کنم. در پروژهٔ قبلی، تیمی سه‌نفره از توسعه‌دهندگان را هدایت کردم.

بگو as a backend developer یا in backend development. عبارت‌های software architecture، fintech و three developers به‌ترتیب برای معماری نرم‌افزار، فناوری مالی و سه توسعه‌دهنده به کار می‌روند.

سؤال

Could you introduce yourself and describe your experience with .NET and team leadership?

می‌توانید خودتان را معرفی کنید و از تجربه‌تان با دات‌نت و هدایت تیم بگویید؟

نمایش پاسخ نمونه

I'm a senior backend developer specializing in .NET. I've worked with ASP.NET Core Web API, Entity Framework Core, and SQL Server. In fintech, I worked on a microservices architecture, led a team of three developers, and reviewed their code.

من توسعه‌دهندهٔ ارشد بک‌اند با تخصص دات‌نت هستم. با ASP.NET Core Web API، Entity Framework Core و SQL Server کار کرده‌ام. در حوزهٔ فناوری مالی روی معماری Microservices کار کردم، تیمی سه‌نفره را هدایت کردم و کد اعضای تیم را بازبینی کردم.

شرح یک گلوگاه در SQL Server

آموزش: روایت را با چهار گام بساز: مسئله، روش تشخیص، اقدام و نتیجه. برای رخداد مشخص گذشته از فعل‌هایی مثل measured، analyzed و refactored استفاده کن. Execution Plan نشان می‌دهد پایگاه‌داده برای اجرای کوئری چه عملگرهایی را انتخاب کرده است.

Bottleneck
گلوگاه: بخشی که سرعت یا ظرفیت کل را محدود می‌کند. The database query was the bottleneck.
Scalability
مقیاس‌پذیری: توان پاسخ‌گویی به بار بیشتر با افزودن منابع. We measured scalability under higher load.
Resilience
تاب‌آوری: توان ادامهٔ کار یا بازیابی پس از خطا. The service recovered after a temporary failure.

سؤال

Tell me about a performance bottleneck you found in SQL Server or a backend API. How did you diagnose it, and what changed?

دربارهٔ یک گلوگاه کارایی در SQL Server یا یک Backend API بگویید. چطور آن را پیدا کردید و چه تغییری ایجاد شد؟

نمایش پاسخ نمونه

One query was taking about 20 seconds. I reviewed the actual execution plan and found joins involving two large tables and two reference tables. I split the work into two queries and cached the reference data because it changed infrequently. I measured the revised version at about 200 milliseconds in that comparison.

اجرای یک کوئری حدود ۲۰ ثانیه طول می‌کشید. Actual Execution Plan را بررسی کردم و دیدم کوئری دو جدول بزرگ و دو جدول مرجع را به هم پیوند می‌دهد. کار را به دو کوئری تقسیم کردم و دادهٔ مرجع را که کم‌تغییر بود در Cache گذاشتم. در همان مقایسه، نسخهٔ اصلاح‌شده را حدود ۲۰۰ میلی‌ثانیه اندازه گرفتم.

اعداد نمونه از روایت تمرین‌اند. در مصاحبه فقط اعدادی را بگو که اندازه گرفته‌ای؛ از بهتر شدن زمان یک کوئری نمی‌شود به‌تنهایی بهبود Resilience را نتیجه گرفت. حالا پاسخ را یک‌بار بدون خواندن متن به انگلیسی بگو.

۲. حافظه در .NET و پردازش رشته ۳۵ دقیقه

از تخصیص حافظه تا ReadOnlySpan<char>

آموزش: فرض کن هر سطر یک فایل پرداخت با شناسه شروع می‌شود: TX-42,70,IRR. اگر برای خواندن شناسه روی هر سطر Split صدا بزنی، داده را به مجموعه‌ای از بخش‌ها تبدیل می‌کنی در حالی که فقط قطعهٔ اول را لازم داری. ReadOnlySpan<char> نمایی فقط‌خواندنی از همان کاراکترها می‌دهد. Slice یک نمای کوچک‌تر برمی‌گرداند و برای خود برش رشتهٔ تازه نمی‌سازد.

Garbage Collector یا GC حافظهٔ اشیای مدیریت‌شده‌ای را که دیگر دسترس‌پذیر نیستند بازیابی می‌کند. اشیای تازه معمولاً از نسل صفر شروع می‌کنند؛ اشیای مانده ممکن است به نسل‌های بالاتر برسند. Large Object Heap یا LOH ناحیه‌ای برای اشیای بزرگ است. در پردازش حجیم، اول نرخ تخصیص را اندازه بگیر؛ استفاده از Span به‌تنهایی روی کل برنامه تضمین «بدون تخصیص» نمی‌دهد.

سؤال

چطور شناسهٔ قبل از نخستین کاما را بدون ساخت رشتهٔ تازه برداری؟ اگر IndexOf(',') مقدار -1 یا 0 بدهد چه می‌شود؟

نمایش پاسخ و کد C# 
static bool TryReadTransactionId(
    ReadOnlySpan<char> line, out ReadOnlySpan<char> transactionId)
{
    int commaIndex = line.IndexOf(',');
    if (commaIndex <= 0)
    {
        transactionId = default;
        return false;
    }

    transactionId = line.Slice(0, commaIndex);
    return true;
}

به تابع line.AsSpan() بده. برای نمونهٔ بالا، نتیجهٔ true و یک نمای حاوی TX-42 می‌گیری. -1 یعنی جداکننده پیدا نشده و 0 یعنی شناسه خالی است؛ در هر دو حالت سطر را رد می‌کنیم. تابع فقط شناسه را استخراج می‌کند؛ بررسی مبلغ و سایر ستون‌ها به بخش اعتبارسنجی مربوط است. اگر شناسه را به string تبدیل کنی، آن تبدیل می‌تواند تخصیص ایجاد کند. اگر داده باید از مرز await عبور کند، ReadOnlyMemory<char> را با توجه به طول‌عمر بافر بررسی کن.

۳. طراحی انتقال وجه ۲۵ دقیقه

برداشت همزمان، Lost Update و rowversion

آموزش: اگر حساب ۱۰۰ واحد موجودی داشته باشد، دو نسخه از سرویس ممکن است همزمان همان ۱۰۰ واحد را بخوانند. اگر هر دو پس از محاسبهٔ محلی موجودی ۳۰ را بنویسند، دو خرید می‌توانند موفق گزارش شوند در حالی که فقط یک برداشت در مانده دیده می‌شود. این یک Lost Update است: یک به‌روزرسانی، اثر به‌روزرسانی دیگر را می‌پوشاند.

سؤال

با دو درخواست برداشت ۷۰ واحدی و موجودی اولیهٔ ۱۰۰، چطور مطمئن می‌شوی هر دو موفق نمی‌شوند؟ rowversion چه کاری انجام می‌دهد؟

نمایش پاسخ و نمونهٔ SQL 
UPDATE dbo.Accounts
SET Balance = Balance - @Amount
WHERE Id = @SourceId AND Balance >= @Amount;

بعد از اعتبارسنجی مبلغ مثبت، شرط موجودی را در خود UPDATE اعمال کن. اگر برداشت اول موجودی را به ۳۰ برساند، برداشت دوم با شرط Balance >= 70 ردیفی را تغییر نمی‌دهد. تعداد ردیف‌های تغییرکرده را بلافاصله بررسی کن. در Optimistic Concurrency، مقدار قبلی rowversion هم در شرط به‌روزرسانی قرار می‌گیرد تا تغییر همزمان تشخیص داده شود. rowversion توکن نسخه است و خودش قفل نمی‌گیرد.

ترتیب قفل‌گیری و Rollback

آموزش: انتقال دو تغییر دارد: برداشت از مبدأ و واریز به مقصد. هر دو باید در یک Transaction انجام شوند. اگر دو انتقال معکوس ابتدا حساب مبدأ خودشان را قفل کنند، هرکدام ممکن است منتظر قفل دیگری بماند. این چرخهٔ انتظار Deadlock است. گرفتن قفل با ترتیب ثابت احتمال این چرخه را کم می‌کند.

سؤال

در انتقال از حساب ۲۰ به حساب ۱۰، کدام را اول قفل می‌کنی؟ اگر برداشت انجام شد اما واریز شکست خورد چه می‌شود؟

نمایش پاسخ نمونه

ابتدا ۱۰ و سپس ۲۰ را قفل می‌کنم؛ جهت انتقال ترتیب را عوض نمی‌کند. اگر راهکارم Pessimistic Locking باشد، در همان تراکنش قفل‌ها را به ترتیب مشخص می‌گیرم، مثلاً با خواندن هر حساب به‌صورت جداگانه با UPDLOCK. صرف وجود ORDER BY در یک کوئری، ترتیب گرفتن قفل‌ها را تضمین نمی‌کند. بعد برداشت شرطی و واریز را انجام می‌دهم و فقط بعد از موفقیت هر دو COMMIT می‌کنم. اگر واریز شکست بخورد، ROLLBACK برداشت را هم برمی‌گرداند. ترتیب ثابت جای رسیدگی به خطای Deadlock و تلاش مجدد محدود را نمی‌گیرد.

Idempotency پس از Timeout

آموزش: ممکن است سرور انتقال را ثبت کند، اما پاسخ به کاربر نرسد. Idempotency در این سناریو یعنی فرستادن دوبارهٔ همان درخواست نباید برداشت جدیدی ایجاد کند. کلاینت همان Idempotency-Key را دوباره می‌فرستد و پایگاه‌داده با قید یکتا برای محدودهٔ همان کاربر یا مشتری مانع ثبت دوباره می‌شود.

سؤال

اگر درخواست اول ثبت شد ولی پاسخ از بین رفت، درخواست بعدی چه می‌گیرد؟ اگر پردازش هنوز تمام نشده یا همان کلید با مبلغ متفاوت ارسال شود چه می‌کنی؟ آیا Redis Lock کافی است؟

نمایش پاسخ نمونه

ثبت نتیجه یا شناسهٔ پرداخت را همراه اثر انتقال در همان تراکنش انجام می‌دهم تا وقفهٔ بعد از COMMIT نتیجه را گم نکند. درخواست همسان نتیجهٔ ثبت‌شده را می‌گیرد. اگر پردازش مستقل و در جریان است، مطابق قرارداد وضعیت در حال پردازش را گزارش می‌دهم و اجرای دوم را شروع نمی‌کنم. اگر ورودی با درخواست قبلی فرق دارد، استفادهٔ مجدد از همان کلید را رد می‌کنم. Redis Lock می‌تواند هماهنگی را بهتر کند؛ چون احتمال انقضا یا قطعی دارد، درستی مالی را با تراکنش و قید یکتای پایگاه‌داده حفظ می‌کنم. اگر رویدادی هم باید منتشر شود، می‌توان قصد انتشار را با Outbox در همان تراکنش ذخیره کرد.

۴. آزمون، Docker و استقرار ۲۰ دقیقه

آزمون یکپارچهٔ انتقال

آموزش: یک آزمون واحد می‌تواند قاعدهٔ «مبلغ باید مثبت باشد» را جداگانه بسنجد. آزمون یکپارچه درخواست را از API عبور می‌دهد تا اثر واقعی آن را در SQL Server آزمایشی ببیند. دادهٔ آزمون باید از آزمون‌های موازی جدا باشد.

سؤال

موجودی مبدأ ۱۰۰ و مقصد ۲۰ است. پس از انتقال ۷۰ و ارسال دوبارهٔ همان کلید، چه چیزهایی را بررسی می‌کنی؟

نمایش پاسخ نمونه

پاسخ اول موفق است و درخواست تکراری همان شناسهٔ انتقال را می‌گیرد. موجودی‌ها ۳۰ و ۹۰ می‌مانند و فقط یک رکورد انتقال ثبت شده است. برای سنجش Rollback، جداگانه شکست واریز را شبیه‌سازی می‌کنم و مطمئن می‌شوم هیچ‌کدام از مانده‌ها عوض نشده‌اند.

Multi-stage Build، نسخهٔ Image و اجرای Container

آموزش: Image بسته‌ای است که فایل‌ها و تنظیم اجرای برنامه را در خود دارد. Container نمونه‌ای از همان بسته است که می‌تواند اجرا یا متوقف شود. در Multi-stage Build نسخهٔ sdk برنامه را می‌سازد و نسخهٔ aspnet برنامهٔ وب منتشرشده را اجرا می‌کند. دستور COPY --from=build خروجی انتشار را از مرحلهٔ ساخت به مرحلهٔ نهایی منتقل می‌کند. در این مثال Payment.Api.csproj در ریشهٔ پوشهٔ ساخت است و پروژه .NET 10 را هدف می‌گیرد.

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish Payment.Api.csproj -c Release -o /out

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
WORKDIR /app
COPY --from=build /out .
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "Payment.Api.dll"]

سؤال

چرا مرحلهٔ نهایی از aspnet استفاده می‌کند؟ با ساخت دوبارهٔ یک Image با همان tag چه اتفاقی برای نسخهٔ قبلی می‌افتد؟ چه کسی docker run -p 8080:80 my-app را اجرا می‌کند؟

نمایش پاسخ نمونه

برای اجرای برنامهٔ وابسته به ASP.NET Core، ایمیج aspnet وابستگی‌های اجرای وب را دارد؛ نیازی به ابزارهای ساخت sdk نیست. حذف محتویات اضافی اندازه را کاهش می‌دهد و اجزای کمتری برای نگهداری باقی می‌گذارد.

اگر محتوای Image عوض شود، tag به Image جدید اشاره می‌کند. Image قبلی ممکن است بدون tag بماند و Containerهای قبلی خودبه‌خود تغییر نمی‌کنند. برای بازگشت، نسخه‌ها را با tag مشخص یا شناسهٔ محتوا (Digest) نگه دار. docker image ls نسخه‌های محلی را نشان می‌دهد؛ docker image prune به‌طور پیش‌فرض Imageهای بدون tag و بدون Container مرجع را پاک می‌کند. نگهداری نسخه در Registry سیاست جداگانه‌ای دارد.

Docker CLI درخواست را به Docker Engine می‌فرستد. Engine با کمک Container Runtime، Container را می‌سازد و برنامهٔ تعریف‌شده در ENTRYPOINT آن اجرا می‌شود. در کانتینر لینوکسی، Namespaces محیط فرایند را جدا می‌کنند و cgroups برای کنترل مصرف منابع به کار می‌روند. با Backend مبتنی بر WSL 2 در Docker Desktop، این محیط لینوکسی روی ویندوز از طریق WSL 2 فراهم می‌شود.

در -p 8080:80، پورت ۸۰۸۰ میزبان به پورت ۸۰ داخل Container می‌رسد. چون مثال بالا صریحاً روی ۸۰۸۰ گوش می‌دهد، برای همین Dockerfile از -p 8080:8080 استفاده کن. EXPOSE به‌تنهایی پورت را روی میزبان منتشر نمی‌کند.

از git push تا Rolling Update

آموزش: در یک مسیر نمونه، بعد از git push، GitLab Runner وظایف فایل .gitlab-ci.yml را اجرا می‌کند: ساخت، آزمون، ساخت Image و انتشار آن در Container Registry. مرحلهٔ استقرار با kubectl یا Helm نسخهٔ مطلوب را به Kubernetes API Server اعلام می‌کند. Deployment و ReplicaSet ایجاد Podها را پیش می‌برند، Scheduler گرهٔ مناسب را انتخاب می‌کند و kubelet با Runtime برای اجرای Container روی گره کار می‌کند. Service دسترسی پایدار به Podها می‌دهد و Ingress با کنترلر مناسب می‌تواند ترافیک HTTP را به Service هدایت کند.

سؤال

هنگام انتشار نسخهٔ جدید، چرا ترافیک نباید بلافاصله به Pod تازه برسد؟ readinessProbe با livenessProbe و startupProbe چه فرقی دارد؟

نمایش پاسخ نمونه

ممکن است فرایند اجرا شده باشد اما API هنوز آمادهٔ پاسخ نباشد. اگر readinessProbe موفق نباشد، Pod برای دریافت ترافیک عادی Service آماده محسوب نمی‌شود. شکست livenessProbe پس از آستانهٔ تعریف‌شده باعث Restart کانتینر می‌شود؛ startupProbe برای راه‌اندازی کند است و تا موفقیتش، بررسی‌های Readiness و Liveness شروع نمی‌شوند.

در Rolling Update، maxSurge ظرفیت موقت اضافه و maxUnavailable تعداد مجاز Podهای خارج از دسترس را کنترل می‌کنند. این تنظیمات مدت و اثر جایگزینی را تغییر می‌دهند. جلوگیری از قطعی به Readiness درست، ظرفیت کافی، خروج امن نسخهٔ قبلی و سازگاری تغییرات داده هم وابسته است.
