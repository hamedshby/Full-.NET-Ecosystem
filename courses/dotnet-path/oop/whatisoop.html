فرض کنید قرار است یک سامانهٔ بانکی بسازیم. هر حساب، یک شماره، یک موجودی و رفتارهایی مانند واریز و برداشت دارد. در Object-Oriented Programming این داده‌ها و رفتارهای مرتبط را در یک واحد معنادار به نام object کنار هم قرار می‌دهیم.

💡
OOP فقط نوشتن class نیست؛ روشی برای تقسیم مسئولیت‌ها و مدل‌کردن مفاهیم مسئله در نرم‌افزار است.

تعریف Object-Oriented Programming

Object-Oriented Programming (OOP) یک programming paradigm است که برنامه را به مجموعه‌ای از objectهای همکار تقسیم می‌کند. هر object معمولاً State خود را نگه می‌دارد و Behavior مرتبط با آن State را ارائه می‌دهد.

برای نمونه، یک حساب بانکی موجودی دارد و عملیات واریز را انجام می‌دهد. به‌جای آنکه موجودی در یک بخش و منطق واریز در بخشی نامرتبط قرار بگیرد، هر دو در یک class کنار هم قرار می‌گیرند:

C#
public class BankAccount
{
    public string AccountNumber { get; }
    public decimal Balance { get; private set; }

    public BankAccount(string accountNumber)
    {
        AccountNumber = accountNumber;
    }

    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        Balance += amount;
    }
}

var account = new BankAccount("IR-1001");
account.Deposit(500_000);

Console.WriteLine($"موجودی حساب: {account.Balance} تومان");

نتیجهٔ اجرای کد، عبارت «موجودی حساب: 500000 تومان» است. خود حساب از موجودی‌اش محافظت می‌کند و اجازه نمی‌دهد کد بیرونی مقدار آن را مستقیماً به یک عدد نامعتبر تغییر دهد.

چرا OOP به وجود آمد؟

با بزرگ‌ترشدن نرم‌افزارها، نگهداری تعداد زیادی function و متغیر مشترک دشوار شد. تغییر یک بخش می‌توانست رفتار بخش‌های دیگر را ناخواسته خراب کند و پیدا کردن مسئول هر عملیات آسان نبود.

OOP کمک کرد داده و عملیات مرتبط کنار هم قرار بگیرند، جزئیات داخلی پنهان شوند و سیستم به بخش‌های کوچک‌تر با مسئولیت روشن تقسیم شود. در نتیجه، توسعه‌دهنده می‌تواند روی یک بخش تمرکز کند بدون آنکه تمام برنامه را هم‌زمان در ذهن نگه دارد.

تفاوت Procedural Programming و OOP

موضوع Procedural Programming OOP
واحد اصلی طراحی function و procedure object و مسئولیت آن
داده و رفتار اغلب جدا از یکدیگرند در یک مرز معنادار کنار هم قرار می‌گیرند
کنترل State ممکن است چند function دادهٔ مشترک را تغییر دهند object تغییر State خود را کنترل می‌کند
گسترش سیستم معمولاً با افزودن شرط و function جدید با افزودن typeها و همکاری objectها

هیچ‌کدام همیشه بر دیگری برتری مطلق ندارد. برای یک محاسبهٔ کوتاه و بدون State، یک function ساده روشن‌تر است. OOP زمانی ارزش بیشتری دارد که مسئله شامل موجودیت‌ها، State، قوانین و همکاری چند بخش باشد.

مزایا و معایب OOP

مزایا

  • مدل‌سازی بهتر: مفاهیمی مثل Customer، Order و Payment مستقیماً در کد نمایان می‌شوند.
  • Encapsulation: object از State معتبر خود محافظت می‌کند.
  • نگهداری‌پذیری: مسئولیت‌ها و محل تغییرات روشن‌تر می‌شوند.
  • استفادهٔ مجدد: رفتار مشترک می‌تواند از طریق Composition، Interface یا در موارد مناسب Inheritance استفاده شود.
  • تست‌پذیری: objectهای کوچک با dependencyهای روشن راحت‌تر Unit Test می‌شوند.

معایب

  • برای مسئله‌های ساده می‌تواند class و abstraction اضافی ایجاد کند.
  • استفادهٔ نادرست از Inheritance باعث Tight Coupling و ساختارهای شکننده می‌شود.
  • ساختن Interface و Design Pattern بدون نیاز واقعی، پیچیدگی و هزینهٔ نگهداری را افزایش می‌دهد.
  • objectهای mutable و ارتباط‌های زیاد میان آن‌ها می‌توانند دنبال‌کردن تغییر State را دشوار کنند.
⚠️
هدف طراحی شی‌گرا تولید بیشترین تعداد class نیست. هر abstraction باید مسئله‌ای واقعی را ساده‌تر کند؛ وگرنه به Overengineering تبدیل می‌شود.

OOP در C# و .NET

C# یک زبان چندپارادایمی با پشتیبانی کامل از طراحی شی‌گرا است. ابزارهایی مانند class، interface، abstract، virtual، override، access modifierها و Genericها برای بیان مرزها و همکاری objectها استفاده می‌شوند.

.NET نیز type system و runtime لازم را فراهم می‌کند. typeهای اصلی کتابخانهٔ استاندارد، exceptionها، collectionها، middlewareهای ASP.NET Core و serviceهای ثبت‌شده در Dependency Injection Container همگی از objectها و قراردادهای میان آن‌ها استفاده می‌کنند.

بااین‌حال، برنامهٔ C# مجبور نیست همه‌چیز را شی‌گرا بنویسد. می‌توان در کنار OOP از functional style، pattern matching، functionهای کوچک و داده‌های immutable نیز استفاده کرد.

کاربرد OOP در پروژه‌های واقعی

در یک فروشگاه اینترنتی می‌توان مفاهیم اصلی دامنه را با objectهای مشخص نمایش داد:

  • Order افزودن محصول و محاسبهٔ مبلغ نهایی را کنترل می‌کند.
  • Customer اطلاعات و قوانین مرتبط با مشتری را نگه می‌دارد.
  • IPaymentGateway قرارداد پرداخت را تعریف می‌کند و پیاده‌سازی‌های مختلف بانکی پشت آن قرار می‌گیرند.
  • InventoryService موجودی کالا را بررسی و رزرو می‌کند.

در چنین سیستمی، Encapsulation از قانون‌های هر object محافظت می‌کند، Abstraction جزئیات بانک یا پایگاه داده را پنهان می‌کند و Polymorphism اجازه می‌دهد روش‌های پرداخت تازه بدون ساختن یک switch بزرگ اضافه شوند.
