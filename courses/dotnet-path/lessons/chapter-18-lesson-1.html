18.1 — Composition over Inheritance

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۱۵
⏱️ زمان مطالعه: ۱۲ دقیقه
👤 تیم فنی

Composition over Inheritance یک اصل طراحی است که می‌گوید برای استفادهٔ مجدد و ترکیب رفتارها، در بسیاری از سناریوها بهتر است ابتدا Composition را بررسی کنیم و فقط زمانی از Inheritance استفاده کنیم که یک رابطهٔ واقعی و پایدار is-a وجود داشته باشد.

💡
این اصل نمی‌گوید Inheritance بد است؛ می‌گوید برای اشتراک رفتار، Composition معمولاً انعطاف‌پذیری بیشتری ایجاد می‌کند.

مشکل Inheritance برای اشتراک رفتار

C#
public abstract class PaymentProcessor
{
    public void WriteLog() { }
    public abstract Task PayAsync();
}

public class CardPaymentProcessor
    : PaymentProcessor
{
    public override Task PayAsync()
    {
        return Task.CompletedTask;
    }
}

در این طراحی، Logging بخشی از Hierarchy شده است. اگر بعداً Logging تغییر کند یا بعضی Processorها رفتار دیگری بخواهند، Base Class می‌تواند به محل تجمع Responsibilityها تبدیل شود.

راه‌حل با Composition

C#
public interface IPaymentLogger
{
    void Log(string message);
}

public class CardPaymentProcessor
{
    private readonly IPaymentLogger _logger;

    public CardPaymentProcessor(
        IPaymentLogger logger)
    {
        _logger = logger;
    }

    public Task PayAsync()
    {
        _logger.Log("Processing payment");
        return Task.CompletedTask;
    }
}

اکنون Payment Processor رفتار Logging را دریافت می‌کند، نه اینکه برای به‌دست‌آوردن آن مجبور باشد از یک Base Class ارث‌بری کند.

Inheritance vs Composition

Inheritance Composition
رابطهٔ is-a رابطهٔ has-a / uses-a
وابستگی به Hierarchy ترکیب Objectهای مستقل
رفتار معمولاً در Compile Time تثبیت می‌شود Dependency می‌تواند قابل جایگزینی باشد
برای Subtyping واقعی مناسب است برای ترکیب Capabilityها مناسب است

مثال Payment System

C#
public class PaymentService
{
    private readonly IPaymentGateway _gateway;
    private readonly IFraudChecker _fraudChecker;
    private readonly IEventPublisher _publisher;

    public PaymentService(
        IPaymentGateway gateway,
        IFraudChecker fraudChecker,
        IEventPublisher publisher)
    {
        _gateway = gateway;
        _fraudChecker = fraudChecker;
        _publisher = publisher;
    }
}

PaymentService قابلیت‌های مورد نیازش را از چند Object مستقل Compose می‌کند.

چه زمانی Inheritance مناسب است؟

  • رابطهٔ is-a واقعی و پایدار است.
  • Substitution معنی‌دار است.
  • Base Type یک Contract مفهومی واقعی ارائه می‌دهد.
  • Subclass واقعاً نوع خاصی از Base Type است، نه صرفاً مصرف‌کنندهٔ چند Method مشترک.
⚠️
اگر فقط برای Reuse چند خط کد از Inheritance استفاده می‌کنید، Composition را هم بررسی کنید. Hierarchy عمیق معمولاً Change Impact را افزایش می‌دهد.

نکته مصاحبه‌ای

🎤
Favor composition over inheritance means composing objects from smaller behaviors instead of building deep inheritance hierarchies when inheritance is not a true is-a relationship.

جمع‌بندی

Composition کمک می‌کند رفتارها را از Objectهای مستقل بسازیم و Dependencyها را قابل جایگزینی نگه داریم. Inheritance همچنان ابزار مفیدی است، اما باید برای Subtyping واقعی استفاده شود.
