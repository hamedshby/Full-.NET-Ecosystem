فصل 12 — Static در طراحی شی‌گرا

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

کلمهٔ کلیدی static یکی از ابزارهای مهم C# است. با Static می‌توان عضو یا حتی یک class را به خود type وابسته کرد، نه به یک object مشخص. این قابلیت برای utilityهای بدون State و بعضی داده‌های مشترک مفید است، اما استفادهٔ بیش از حد از آن می‌تواند Coupling، Shared State و مشکلات تست‌پذیری ایجاد کند.

💡
عضو Instance به یک object مشخص تعلق دارد؛ عضو Static به خود type تعلق دارد. بنابراین برای استفاده از عضو Static معمولاً نیازی به ساخت object با new نیست.

12.1 Static Class

Static Class کلاسی است که نمی‌توان از آن instance ساخت و تمام اعضای آن باید static باشند. این نوع class برای عملیات stateless و utilityهای عمومی مناسب است.

C#
public static class MoneyCalculator
{
    public static decimal CalculateFee(
        decimal amount,
        decimal feePercent)
    {
        return amount * feePercent;
    }
}
C#
decimal fee =
    MoneyCalculator.CalculateFee(
        1_000_000,
        0.01m);

Console.WriteLine(fee);
// 10000

ویژگی‌های Static Class

  • نمی‌توان از آن object ساخت.
  • Instance Constructor ندارد.
  • تمام اعضای آن static هستند.
  • برای utilityهای stateless مناسب است.
⚠️
هر class بدون State لزوماً نباید Static باشد. اگر نیاز به Dependency Injection، چند implementation یا Test Double دارید، Static کردن class می‌تواند انعطاف طراحی را کاهش دهد.

12.2 Static Method

Static Method به خود type تعلق دارد و برای فراخوانی آن نیازی به instance نداریم.

C#
public class PaymentValidator
{
    public static bool IsValidAmount(
        decimal amount)
    {
        return amount > 0;
    }
}
C#
bool isValid =
    PaymentValidator.IsValidAmount(
        500_000);

Static Method بدون داشتن reference به یک object نمی‌تواند مستقیماً به Instance State دسترسی داشته باشد.

چه زمانی Static Method مناسب است؟

  • عملیات stateless است.
  • به dependency خارجی نیاز ندارد.
  • به State یک object مشخص وابسته نیست.
  • رفتار pure یا utility است.

12.3 Static Property

Static Property به type تعلق دارد و مقدار آن بین تمام instanceها مشترک است.

C#
public class BankAccount
{
    public static string BankName
    {
        get;
        set;
    } = "DotNet Bank";
}
C#
Console.WriteLine(
    BankAccount.BankName);

BankAccount.BankName =
    "OOP Bank";

تغییر این Property برای کل type قابل مشاهده است، نه فقط برای یک object.

12.4 Static Field

Static Field یک محل ذخیره‌سازی مشترک برای کل type ایجاد می‌کند.

C#
public class BankAccount
{
    private static int _accountCount;

    public BankAccount()
    {
        _accountCount++;
    }

    public static int AccountCount
        => _accountCount;
}
C#
var account1 =
    new BankAccount();

var account2 =
    new BankAccount();

Console.WriteLine(
    BankAccount.AccountCount);
// 2

Shared Mutable State

C#
public static class GlobalPaymentState
{
    public static decimal TotalAmount;
}
🚨
Shared Mutable Static State می‌تواند باعث Race Condition، coupling پنهان و وابستگی بین Testها شود، مخصوصاً در برنامه‌های concurrent مانند ASP.NET Core.

12.5 Static Constructor

Static Constructor برای initialization یک‌بارهٔ State مربوط به type استفاده می‌شود و Runtime آن را مدیریت می‌کند.

C#
public class PaymentSettings
{
    public static readonly Guid InstanceId;

    public static string EnvironmentName
    {
        get;
    }

    static PaymentSettings()
    {
        InstanceId =
            Guid.NewGuid();

        EnvironmentName =
            Environment.GetEnvironmentVariable(
                "ASPNETCORE_ENVIRONMENT")
            ?? "Production";
    }
}
  • Parameter ندارد.
  • Access Modifier ندارد.
  • مستقیماً فراخوانی نمی‌شود.
  • حداکثر یک‌بار برای type اجرا می‌شود.

12.6 مشکلات استفاده بیش از حد از Static

Global State

C#
public static class CurrentPayment
{
    public static string?
        TransactionId { get; set; }

    public static decimal
        Amount { get; set; }
}

چند request یا thread می‌توانند روی State مشترک کار کنند و اطلاعات یکدیگر را overwrite کنند.

Hidden Dependency

C#
public static class EmailSender
{
    public static void Send(
        string message)
    {
        // Send email
    }
}

public class PaymentService
{
    public void Pay()
    {
        EmailSender.Send(
            "Payment completed");
    }
}

از Constructor مربوط به PaymentService مشخص نیست که این class به Email Sending وابسته است.

Coupling بالا

کد مستقیماً به implementation مشخص وابسته می‌شود و جایگزین‌کردن آن سخت‌تر خواهد شد.

Concurrency

C#
public static class Counter
{
    public static int Value;

    public static void Increment()
    {
        Value++;
    }
}

در محیط concurrent، Value++ یک عملیات atomic نیست و می‌تواند باعث Lost Update شود.

💡
مشکل اصلی Static بودن نیست؛ مشکل زمانی ایجاد می‌شود که Business State قابل‌تغییر یا dependency خارجی را به‌صورت global و پنهان مدیریت کنیم.

12.7 Static و Testability

Static Utilityهای ساده معمولاً تست‌پذیری خوبی دارند:

C#
public static class FeeCalculator
{
    public static decimal Calculate(
        decimal amount)
    {
        return amount * 0.01m;
    }
}

این Method deterministic است و dependency خارجی ندارد.

مشکل dependencyهای Static

C#
public static class SystemClock
{
    public static DateTime UtcNow
        => DateTime.UtcNow;
}

public class TransactionService
{
    public Transaction Create()
    {
        return new Transaction
        {
            CreatedAt =
                SystemClock.UtcNow
        };
    }
}

Unit Test نمی‌تواند زمان را به‌راحتی کنترل کند.

نسخه قابل تست

C#
public interface IClock
{
    DateTime UtcNow { get; }
}

public class SystemClock
    : IClock
{
    public DateTime UtcNow
        => DateTime.UtcNow;
}

public class TransactionService
{
    private readonly IClock _clock;

    public TransactionService(
        IClock clock)
    {
        _clock = clock;
    }

    public Transaction Create()
    {
        return new Transaction
        {
            CreatedAt =
                _clock.UtcNow
        };
    }
}

Fake برای Unit Test

C#
public class FakeClock
    : IClock
{
    public DateTime UtcNow
    {
        get;
        set;
    }
}
⚠️
Static Mutable State یکی از دلایل رایج Testهای flaky است؛ مخصوصاً وقتی ترتیب اجرای Testها یا Parallel Execution روی نتیجه اثر بگذارد.

12.8 Static vs Dependency Injection

Static و Dependency Injection جایگزین مطلق یکدیگر نیستند. هرکدام برای سناریوی متفاوتی مناسب‌اند.

طراحی Static

C#
public static class NotificationService
{
    public static Task SendAsync(
        string message)
    {
        return Task.CompletedTask;
    }
}

طراحی با Dependency Injection

C#
public interface INotificationSender
{
    Task SendAsync(
        string message);
}

public class SmsNotificationSender
    : INotificationSender
{
    public Task SendAsync(
        string message)
    {
        return Task.CompletedTask;
    }
}

public class PaymentService
{
    private readonly INotificationSender
        _notificationSender;

    public PaymentService(
        INotificationSender notificationSender)
    {
        _notificationSender =
            notificationSender;
    }

    public async Task PayAsync()
    {
        // Payment logic

        await _notificationSender.SendAsync(
            "Payment completed");
    }
}

ثبت در ASP.NET Core DI

C#
builder.Services.AddScoped
    <INotificationSender,
     SmsNotificationSender>();

builder.Services.AddScoped
    <PaymentService>();

مقایسه Static و DI

موضوع Static Dependency Injection
ساخت object نیاز ندارد. Container یا Caller مدیریت می‌کند.
Dependency visibility ممکن است پنهان باشد. معمولاً در Constructor واضح است.
چند Implementation سخت‌تر طبیعی و ساده
Unit Testing برای dependency خارجی سخت‌تر Fake/Mock قابل inject است.
Lifetime Type/Process-level Transient / Scoped / Singleton
Utility بدون State بسیار مناسب اغلب unnecessary
Business Service وابسته به IO معمولاً ضعیف‌تر معمولاً مناسب‌تر

چه چیزهایی معمولاً Static مناسبی هستند؟

  • Pure Functionها
  • Extension Methodها
  • Helperهای بدون dependency و State
  • Constants و metadataهای واقعاً سراسری
C#
public static class CardNumberExtensions
{
    public static string Mask(
        this string cardNumber)
    {
        return
            $"******{cardNumber[^4..]}";
    }
}

چه چیزهایی معمولاً بهتر است Static نباشند؟

  • Repositoryها
  • Database Access
  • HTTP Client Wrapperها
  • Message Publisherها
  • Email/SMS Senderها
  • Clock و Random Generator وقتی کنترل آن‌ها در Test مهم است
  • Business Serviceهای وابسته به IO
  • State مربوط به Request یا User

مثال واقعی: Payment Service

نسخه با Static Dependency

C#
public class PaymentService
{
    public async Task PayAsync(
        decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        await BankApi.SendAsync(
            amount);

        await SmsSender.SendAsync(
            "Payment completed");

        GlobalMetrics.PaymentCount++;
    }
}

این class ظاهراً Constructor ندارد، اما در واقع چند dependency پنهان دارد.

نسخه مبتنی بر Abstraction و DI

C#
public interface IPaymentGateway
{
    Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken);
}

public interface INotificationSender
{
    Task SendAsync(
        string message,
        CancellationToken cancellationToken);
}

public interface IPaymentMetrics
{
    void PaymentCompleted();
}

public class PaymentService
{
    private readonly IPaymentGateway
        _paymentGateway;

    private readonly INotificationSender
        _notificationSender;

    private readonly IPaymentMetrics
        _metrics;

    public PaymentService(
        IPaymentGateway paymentGateway,
        INotificationSender notificationSender,
        IPaymentMetrics metrics)
    {
        _paymentGateway = paymentGateway;
        _notificationSender = notificationSender;
        _metrics = metrics;
    }

    public async Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        await _paymentGateway.PayAsync(
            amount,
            cancellationToken);

        await _notificationSender.SendAsync(
            "Payment completed",
            cancellationToken);

        _metrics.PaymentCompleted();
    }
}

در نسخهٔ دوم dependencyها explicit هستند، implementationها قابل جایگزینی‌اند و Unit Test می‌تواند Fakeهای مناسب را inject کند.

🎯
قاعدهٔ عملی: اگر رفتار stateless، deterministic و بدون dependency خارجی است، Static می‌تواند انتخاب خوبی باشد. اگر رفتار به Database، HTTP، Clock، File، Message Broker یا State وابسته است، object با dependencyهای صریح و DI معمولاً طراحی انعطاف‌پذیرتری می‌دهد.

جمع‌بندی فصل

مفهوم نکتهٔ اصلی
Static Class Type بدون instance برای رفتارهای stateless
Static Method رفتاری متعلق به type
Static Property Property مشترک در سطح type
Static Field State مشترک؛ در صورت mutable بودن نیازمند احتیاط
Static Constructor Initialization یک‌بارهٔ type
Testability Static dependencyهای خارجی معمولاً تست را سخت‌تر می‌کنند.
Dependency Injection Dependencyها را explicit، قابل جایگزینی و قابل تست می‌کند.
✅
خلاصه: Static دشمن OOP نیست. برای utilityهای بدون State ابزار بسیار خوبی است. مشکل زمانی آغاز می‌شود که Static به محل نگهداری Business State یا دسترسی مستقیم به dependencyهای خارجی تبدیل شود. در چنین سناریوهایی Dependency Injection معمولاً Coupling کمتر، Testability بهتر و کنترل Lifetime دقیق‌تری فراهم می‌کند.
