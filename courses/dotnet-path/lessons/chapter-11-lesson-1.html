فصل 11 — Object، Memory و Reference Types

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

برای درک عمیق‌تر رفتار objectها در C# باید بدانیم هنگام ساخت یک object چه اتفاقی برای داده‌ها و referenceها می‌افتد، تفاوت Value Type و Reference Type چیست، assignment چگونه کار می‌کند و .NET چگونه حافظهٔ objectهای مدیریت‌شده را با Garbage Collector مدیریت می‌کند.

💡
در این فصل هدف حفظ‌کردن جملهٔ سادهٔ «Value Type روی Stack و Reference Type روی Heap است» نیست؛ این جمله بیش از حد ساده‌سازی شده است. محل ذخیره‌سازی به context بستگی دارد. چیزی که باید دقیق یاد بگیریم، تفاوت Value Semantics و Reference Semantics است.

11.1 Stack و Heap

در اجرای برنامه، .NET از بخش‌های مختلف حافظه استفاده می‌کند. دو مفهوم مهمی که هنگام آموزش C# زیاد با آن‌ها روبه‌رو می‌شویم Stack و Managed Heap هستند.

Stack

Stack با اجرای Methodها و Call Frameهای آن‌ها ارتباط دارد. اطلاعاتی مانند بعضی local variableها، پارامترها و داده‌های موردنیاز برای اجرای Method می‌توانند در stack frame قرار بگیرند.

C#
static void Calculate()
{
    int count = 10;
    decimal amount = 500_000m;

    Console.WriteLine(
        count * amount);
}

با پایان اجرای Method، stack frame مربوط به آن دیگر موردنیاز نیست.

Managed Heap

objectهای reference type معمولاً روی Managed Heap ساخته می‌شوند و Garbage Collector مسئول مدیریت حافظهٔ آن‌هاست.

C#
public class Customer
{
    public string Name { get; set; }
}

var customer =
    new Customer
    {
        Name = "Hamed"
    };

عبارت new Customer() یک object ایجاد می‌کند و متغیر customer یک reference برای دسترسی به آن object نگه می‌دارد.

⚠️
نگویید «هر Value Type همیشه روی Stack است». مثلاً یک Value Type می‌تواند Field یک object باشد و دادهٔ آن به‌عنوان بخشی از همان object روی Heap قرار بگیرد. همچنین runtime و JIT در جزئیات پیاده‌سازی آزادی عمل دارند.

11.2 Value Type vs Reference Type

تفاوت اصلی این دو گروه در semantics مربوط به مقدار و assignment است.

Value Type

متغیر Value Type مقدار خودش را نگه می‌دارد. هنگام assignment معمولاً مقدار کپی می‌شود.

C#
int number1 = 10;

int number2 = number1;

number2 = 50;

Console.WriteLine(number1);
// 10

Console.WriteLine(number2);
// 50

تغییر number2 روی number1 اثری ندارد.

نمونه‌های مهم Value Type:

  • int
  • long
  • decimal
  • bool
  • DateTime
  • struct
  • enum

Reference Type

متغیر Reference Type به یک object اشاره می‌کند. هنگام assignment، reference کپی می‌شود؛ نه اینکه الزاماً یک object جدید ساخته شود.

C#
var customer1 =
    new Customer
    {
        Name = "Hamed"
    };

var customer2 = customer1;

customer2.Name = "Ali";

Console.WriteLine(
    customer1.Name);
// Ali

هر دو reference به یک object اشاره می‌کنند؛ بنابراین تغییر object از طریق یکی، از طریق دیگری نیز قابل مشاهده است.

Value Type Reference Type
assignment معمولاً Value را کپی می‌کند. assignment مقدار reference را کپی می‌کند.
دو متغیر معمولاً دادهٔ مستقل دارند. چند متغیر می‌توانند به یک object اشاره کنند.
نمونه: int و struct نمونه: class، array و delegate

11.3 Object Reference

Reference را می‌توان مانند راه دسترسی به یک object در نظر گرفت. خود متغیر reference با object یکی نیست.

C#
Customer customer =
    new Customer
    {
        Name = "Hamed"
    };

در این کد دو مفهوم داریم:

  • new Customer(...) → ساخت object
  • customer → reference برای دسترسی به object

یک object می‌تواند هم‌زمان از طریق چند reference قابل دسترسی باشد.

C#
Customer customer1 =
    new Customer
    {
        Name = "Hamed"
    };

Customer customer2 = customer1;
Customer customer3 = customer1;

در اینجا سه object نداریم؛ یک object داریم و سه متغیر به همان instance اشاره می‌کنند.

Reference می‌تواند null باشد

C#
Customer? customer = null;

در این حالت reference به هیچ instanceای اشاره نمی‌کند. تلاش برای دسترسی نامعتبر به عضو object می‌تواند باعث NullReferenceException شود.

11.4 Reference Assignment

یکی از رایج‌ترین اشتباهات افراد تازه‌کار این است که تصور می‌کنند assignment یک Reference Type، object را clone می‌کند.

C#
var account1 =
    new BankAccount
    {
        Balance = 1_000_000
    };

var account2 = account1;

account2.Balance = 500_000;

Console.WriteLine(
    account1.Balance);
// 500000

account1 و account2 دو reference هستند، اما هر دو به یک object اشاره می‌کنند.

ساخت object جدید

C#
var account1 =
    new BankAccount
    {
        Balance = 1_000_000
    };

var account2 =
    new BankAccount
    {
        Balance = account1.Balance
    };

account2.Balance = 500_000;

Console.WriteLine(
    account1.Balance);
// 1000000

اینجا دو object مستقل ساخته شده‌اند؛ بنابراین تغییر یکی مستقیماً دیگری را تغییر نمی‌دهد.

11.5 Passing Objects to Methods

در C# پارامترها به‌صورت پیش‌فرض By Value ارسال می‌شوند. برای Reference Type این یعنی مقدار reference کپی می‌شود.

C#
static void Rename(
    Customer customer)
{
    customer.Name = "Ali";
}

var customer =
    new Customer
    {
        Name = "Hamed"
    };

Rename(customer);

Console.WriteLine(
    customer.Name);
// Ali

Method یک کپی از reference دریافت کرده، اما آن reference کپی‌شده همچنان به همان object اشاره می‌کند. پس Method می‌تواند State object را تغییر دهد.

Reassign کردن Parameter

C#
static void Replace(
    Customer customer)
{
    customer =
        new Customer
        {
            Name = "Replaced"
        };
}

var customer =
    new Customer
    {
        Name = "Hamed"
    };

Replace(customer);

Console.WriteLine(
    customer.Name);
// Hamed

چرا مقدار اصلی تغییر نکرد؟ چون Method فقط کپی reference را reassign کرده است. متغیر customer بیرون Method همچنان به object قبلی اشاره می‌کند.

💡
عبارت «objectها By Reference پاس داده می‌شوند» دقیق نیست. Reference Typeها نیز به‌صورت پیش‌فرض By Value پاس داده می‌شوند؛ چیزی که کپی می‌شود مقدار reference است.

ارسال reference با ref

اگر خود متغیر reference را با ref ارسال کنیم، Method می‌تواند reference caller را نیز تغییر دهد.

C#
static void Replace(
    ref Customer customer)
{
    customer =
        new Customer
        {
            Name = "Replaced"
        };
}

var customer =
    new Customer
    {
        Name = "Hamed"
    };

Replace(ref customer);

Console.WriteLine(
    customer.Name);
// Replaced

11.6 Garbage Collector

در .NET حافظهٔ Managed Objectها عمدتاً توسط Garbage Collector یا GC مدیریت می‌شود. برنامه‌نویس معمولاً لازم نیست حافظهٔ objectهای managed را به‌صورت دستی آزاد کند.

C#
static void CreateCustomer()
{
    var customer =
        new Customer
        {
            Name = "Hamed"
        };

    Console.WriteLine(
        customer.Name);
}

پس از پایان Method، اگر دیگر هیچ مسیر قابل‌دسترسی به object وجود نداشته باشد، object می‌تواند برای Garbage Collection واجد شرایط شود.

GC چه کاری انجام می‌دهد؟

  • objectهای managed را بررسی می‌کند.
  • objectهای قابل‌دسترسی را زنده نگه می‌دارد.
  • حافظهٔ objectهای غیرقابل‌دسترسی را در زمان مناسب reclaim می‌کند.
  • برای بهینه‌سازی، objectها را در Generationهای مختلف مدیریت می‌کند.

Generationها

Generation مفهوم کلی
Gen 0 معمولاً objectهای جدید و کوتاه‌عمر
Gen 1 مرحلهٔ میانی برای objectهایی که از collection قبلی زنده مانده‌اند
Gen 2 معمولاً objectهای طولانی‌عمرتر
⚠️
واجد شرایط شدن برای Garbage Collection به این معنی نیست که object همان لحظه حذف می‌شود. زمان اجرای GC را Runtime مدیریت می‌کند و نباید به زمان دقیق آن وابسته باشیم.

11.7 Object Lifetime

Lifetime یک object از زمان ایجاد آن شروع می‌شود و تا زمانی ادامه دارد که Runtime بتواند آن object را از طریق referenceهای زنده و rootهای GC قابل‌دسترسی تشخیص دهد.

C#
Customer CreateCustomer()
{
    var customer =
        new Customer
        {
            Name = "Hamed"
        };

    return customer;
}

var customer =
    CreateCustomer();

با پایان CreateCustomer()، object از بین نمی‌رود؛ چون reference آن return شده و هنوز از بیرون قابل دسترسی است.

Eligible for Collection

C#
var customer =
    new Customer
    {
        Name = "Hamed"
    };

customer = null;

اگر reference دیگری به object وجود نداشته باشد، object می‌تواند برای collection واجد شرایط شود. اما زمان واقعی reclaim شدن حافظه توسط GC تعیین می‌شود.

11.8 IDisposable

Garbage Collector برای مدیریت حافظهٔ managed عالی است، اما بعضی objectها منابعی دارند که باید deterministically و در زمان مشخص آزاد شوند؛ مانند streamها، handleهای سیستم‌عامل و برخی resourceهای unmanaged.

برای چنین سناریوهایی از قرارداد IDisposable استفاده می‌شود.

C#
public class PaymentFileWriter
    : IDisposable
{
    private readonly StreamWriter _writer;

    public PaymentFileWriter(
        string path)
    {
        _writer =
            new StreamWriter(path);
    }

    public void Write(
        string transactionId)
    {
        _writer.WriteLine(
            transactionId);
    }

    public void Dispose()
    {
        _writer.Dispose();
    }
}

Dispose() به مصرف‌کننده اجازه می‌دهد اعلام کند کار با resource تمام شده و resource باید آزاد شود.

💡
IDisposable جای Garbage Collector را نمی‌گیرد. GC حافظهٔ managed را مدیریت می‌کند؛ Dispose برای آزادسازی به‌موقع resourceهایی است که lifetime آن‌ها نباید به زمان نامشخص اجرای GC وابسته باشد.

11.9 using

بهترین روش معمول برای استفاده از objectهای IDisposable، استفاده از using است. این syntax تضمین می‌کند Dispose در پایان scope مربوطه فراخوانی شود، حتی اگر exception رخ دهد.

C#
using (
    var writer =
        new PaymentFileWriter(
            "transactions.txt"))
{
    writer.Write("TX-1001");
    writer.Write("TX-1002");
}

بعد از خروج از block، Dispose() فراخوانی می‌شود.

Using Declaration

در C# مدرن می‌توان syntax کوتاه‌تری استفاده کرد:

C#
using var writer =
    new PaymentFileWriter(
        "transactions.txt");

writer.Write("TX-1001");
writer.Write("TX-1002");

در این حالت resource در پایان scope جاری Dispose می‌شود.

تقریب ذهنی using

برای درک مفهوم، می‌توان using را شبیه مدیریت resource با try/finally در نظر گرفت:

C#
var writer =
    new PaymentFileWriter(
        "transactions.txt");

try
{
    writer.Write("TX-1001");
}
finally
{
    writer.Dispose();
}

11.10 Finalizer

Finalizer مکانیزمی برای cleanup نهایی typeهایی است که مستقیماً مالک unmanaged resource هستند و نیاز به fallback cleanup دارند. Syntax آن شبیه Destructor در C++ به نظر می‌رسد، اما رفتار آن متفاوت است.

C#
public class NativeResource
{
    ~NativeResource()
    {
        // Cleanup unmanaged resource
    }
}

برنامه‌نویس Finalizer را مستقیماً فراخوانی نمی‌کند و زمان اجرای دقیق آن قابل پیش‌بینی نیست. Finalization همچنین هزینهٔ بیشتری برای GC ایجاد می‌کند.

⚠️
برای هر class یک Finalizer نسازید. بیشتر classهای معمولی به Finalizer نیاز ندارند. اگر class فقط objectهای managed مانند StreamWriter را در اختیار دارد، معمولاً Dispose کردن همان resource کافی است. Finalizer عمدتاً برای typeهایی مطرح است که مستقیماً unmanaged resource را مالک‌اند.

Dispose در برابر Finalizer

Dispose Finalizer
Cleanup deterministic زمان اجرا غیرقطعی است.
توسط مصرف‌کننده یا using فراخوانی می‌شود. Runtime/GC آن را مدیریت می‌کند.
روش اصلی آزادسازی به‌موقع resource Fallback برای سناریوهای خاص unmanaged resource
هزینهٔ کمتری نسبت به finalization دارد. Finalizable object هزینهٔ بیشتری برای GC دارد.

Disposable Pattern با Finalizer

اگر type مستقیماً unmanaged resource را مدیریت کند، الگوی Dispose می‌تواند شامل Finalizer و GC.SuppressFinalize باشد. در کد production معمولاً استفاده از wrapperهای امنی مانند SafeHandle بر مدیریت مستقیم handle ترجیح دارد.

C#
public class NativeResource
    : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(true);

        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(
        bool disposing)
    {
        if (_disposed)
            return;

        if (disposing)
        {
            // Dispose managed resources
        }

        // Release unmanaged resources

        _disposed = true;
    }

    ~NativeResource()
    {
        Dispose(false);
    }
}

اگر Dispose() به‌درستی اجرا شود، GC.SuppressFinalize(this) به Runtime می‌گوید دیگر نیازی به اجرای Finalizer این instance نیست.

مثال واقعی: کار با فایل Transactionها

C#
public sealed class TransactionLogger
    : IDisposable
{
    private readonly StreamWriter _writer;
    private bool _disposed;

    public TransactionLogger(
        string filePath)
    {
        _writer =
            new StreamWriter(
                filePath,
                append: true);
    }

    public void Log(
        string transactionId,
        decimal amount)
    {
        ObjectDisposedException
            .ThrowIf(_disposed, this);

        _writer.WriteLine(
            $"{transactionId} | {amount}");
    }

    public void Dispose()
    {
        if (_disposed)
            return;

        _writer.Dispose();

        _disposed = true;
    }
}
C#
using var logger =
    new TransactionLogger(
        "transactions.txt");

logger.Log(
    "TX-1001",
    500_000);

logger.Log(
    "TX-1002",
    750_000);

TransactionLogger مالک یک StreamWriter است. با پایان scope، using متد Dispose() را اجرا می‌کند و StreamWriter نیز به‌موقع Dispose می‌شود. برای این class Finalizer لازم نیست، چون خودش مستقیماً unmanaged handle را مدیریت نمی‌کند.

اشتباهات رایج

  • فرض کردن اینکه assignment یک Reference Type باعث clone شدن object می‌شود.
  • گفتن اینکه objectها به‌صورت پیش‌فرض By Reference به Method ارسال می‌شوند.
  • فرض کردن اینکه تمام Value Typeها همیشه روی Stack هستند.
  • وابسته شدن به زمان دقیق اجرای Garbage Collector.
  • استفاده نکردن از using برای resourceهای Disposable مناسب.
  • نوشتن Finalizer برای classهایی که نیازی به آن ندارند.
  • تصور اینکه GC به‌تنهایی تمام resourceهای خارجی را به‌موقع آزاد می‌کند.

جمع‌بندی فصل

مفهوم نکتهٔ اصلی
Stack با Method Callها و stack frameها ارتباط دارد.
Managed Heap محل معمول allocation objectهای reference type مدیریت‌شده است.
Value Type assignment معمولاً مقدار را کپی می‌کند.
Reference Type assignment مقدار reference را کپی می‌کند.
Passing Object به‌صورت پیش‌فرض reference نیز By Value پاس داده می‌شود.

using Dispose را در پایان scope تضمین می‌کند.
Finalizer Fallback خاص برای cleanup منابع unmanaged است.
✅
خلاصه: در Reference Typeها باید تفاوت میان object و reference را درک کنید. Assignment و ارسال object به Method معمولاً reference را کپی می‌کنند. Garbage Collector حافظهٔ managed را مدیریت می‌کند، اما resourceهایی که نیاز به cleanup به‌موقع دارند باید با IDisposable و using مدیریت شوند. Finalizer ابزار عمومی cleanup نیست و فقط در سناریوهای خاص مالکیت مستقیم unmanaged resource کاربرد دارد.
