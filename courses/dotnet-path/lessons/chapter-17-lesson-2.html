🔗 Coupling در طراحی نرم‌افزار

17.2 — Tight Coupling

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Tight Coupling زمانی است که Componentها شدیداً به Concrete Implementation و جزئیات یکدیگر وابسته باشند.

💡
در Tight Coupling، تغییر یا جایگزینی یک Dependency معمولاً Consumer را هم مجبور به تغییر می‌کند.

مثال اشتباه

C#
public class PaymentService
{
    private readonly SqlPaymentRepository _repository;

    public PaymentService()
    {
        _repository = new SqlPaymentRepository();
    }

    public Task PayAsync(Payment payment)
    {
        return _repository.SaveAsync(payment);
    }
}

PaymentService هم Concrete Type را می‌شناسد و هم خودش آن را می‌سازد.

Text
PaymentService
      │
      ▼
SqlPaymentRepository
      │
      ▼
SQL Server

مشکلات

  • جایگزینی Repository سخت‌تر است.
  • Unit Test ممکن است به Database واقعی وابسته شود.
  • Business Logic جزئیات Persistence را می‌شناسد.
  • تغییر Infrastructure به Consumer سرایت می‌کند.

مثال واقعی‌تر

C#
public async Task ProcessAsync(Payment payment)
{
    var repository = new SqlPaymentRepository();
    var publisher = new RabbitMqPublisher();
    var notifier = new SmtpEmailSender();

    await repository.SaveAsync(payment);
    await publisher.PublishAsync(payment);
    await notifier.SendAsync(payment);
}

Business Flow مستقیماً به SQL Server، RabbitMQ و SMTP گره خورده است.

مشکل در Unit Test

⚠️
اگر برای تست یک Business Rule ساده مجبور به راه‌اندازی Database، Network یا External Service واقعی باشید، Coupling طراحی را بررسی کنید.

آیا new همیشه بد است؟

خیر. ساخت Entity، DTO یا Value Object با new طبیعی است. مسئله زمانی مهم می‌شود که Business Service خودش External/Infrastructure Dependency قابل جایگزینی را بسازد.

Tight Coupling در Microservices

Text
Payment
   ├──► Customer
   ├──► Order
   ├──► Notification
   └──► Reporting

اگر مسیر اصلی Payment به Availability هم‌زمان همه این سرویس‌ها وابسته باشد، Operational/Temporal Coupling افزایش می‌یابد.

Shared Database

وقتی چند Service مستقیماً Tableهای یکدیگر را تغییر می‌دهند، تغییر Schema می‌تواند چند سرویس را هم‌زمان بشکند.

کاهش Tight Coupling با DIP

Text
Before:
PaymentService → SqlPaymentRepository

After:
PaymentService → IPaymentRepository ← SqlPaymentRepository

نشانه‌ها

  • Concrete Dependencyهای زیاد در Business Logic
  • ساخت Repository/Gateway/Publisher داخل Service
  • شناخت Connection String یا Queue Detail در Business Code
  • تغییر Provider باعث تغییر چند Consumer می‌شود
  • Mock کردن Dependency دشوار است
🎯
Concrete Dependency همیشه بد نیست. معیار اصلی این است: آیا تغییر Detail باعث تغییر غیرضروری Consumer می‌شود؟

نکته مصاحبه‌ای

🎤
Tight coupling means components depend heavily on concrete details of each other. This increases change impact and usually makes testing and replacement harder.

جمع‌بندی

Tight Coupling یعنی knowledge زیاد از Implementation و وابستگی شدید بین اجزا؛ نتیجه آن معمولاً Flexibility و Testability کمتر است.
