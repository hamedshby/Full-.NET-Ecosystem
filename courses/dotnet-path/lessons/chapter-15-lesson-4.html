15.4 — Liskov Substitution Principle — LSP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Liskov Substitution Principle یا LSP سومین اصل SOLID است. این اصل می‌گوید اگر Typeای از Base Type یا Interface دیگری مشتق شده است، باید بتوان آن را بدون شکستن رفتار مورد انتظار سیستم جایگزین Base Type کرد.

💡
تعریف ساده: Subtypes must be substitutable for their base types. یعنی هر Subtype باید Contract رفتاری Base Type را حفظ کند.

LSP دقیقاً یعنی چه؟

فرض کنید یک Method با Base Type کار می‌کند:

C#
public void Execute(
    PaymentMethod paymentMethod)
{
    paymentMethod.Pay(
        500_000);
}

اگر CardPayment و WalletPayment از PaymentMethod مشتق شده‌اند، هر دو باید بدون ایجاد رفتار غیرمنتظره قابل استفاده باشند.

مثال اشتباه معروف: Rectangle و Square

C#
public class Rectangle
{
    public virtual int Width { get; set; }

    public virtual int Height { get; set; }

    public int Area()
    {
        return Width * Height;
    }
}
C#
public class Square
    : Rectangle
{
    public override int Width
    {
        set
        {
            base.Width = value;
            base.Height = value;
        }
    }

    public override int Height
    {
        set
        {
            base.Width = value;
            base.Height = value;
        }
    }
}

حالا این Method را ببینید:

C#
public static void Resize(
    Rectangle rectangle)
{
    rectangle.Width = 5;
    rectangle.Height = 10;

    Console.WriteLine(
        rectangle.Area());
}

برای Rectangle انتظار Area برابر 50 است، اما اگر Square جایگزین شود نتیجه 100 می‌شود. پس Subtype رفتار مورد انتظار Base Type را تغییر داده است.

⚠️
ممکن است inheritance از نظر Syntax کاملاً معتبر باشد، اما از نظر رفتار و Contract، LSP را نقض کند.

Refactoring مثال Rectangle و Square

یک abstraction واقعی‌تر تعریف می‌کنیم:

C#
public interface IShape
{
    int Area();
}

public class Rectangle
    : IShape
{
    public int Width { get; init; }

    public int Height { get; init; }

    public int Area()
    {
        return Width * Height;
    }
}

public class Square
    : IShape
{
    public int Side { get; init; }

    public int Area()
    {
        return Side * Side;
    }
}

حالا Contract مشترک فقط چیزی است که واقعاً بین هر دو Type مشترک است: محاسبه Area.

مثال اشتباه در Payment System

C#
public abstract class PaymentMethod
{
    public abstract Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken);

    public abstract Task RefundAsync(
        decimal amount,
        CancellationToken cancellationToken);
}

CardPayment هر دو قابلیت را دارد:

C#
public class CardPayment
    : PaymentMethod
{
    public override Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }

    public override Task RefundAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }
}

اما GiftCardPayment Refund را پشتیبانی نمی‌کند:

C#
public class GiftCardPayment
    : PaymentMethod
{
    public override Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }

    public override Task RefundAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        throw new NotSupportedException(
            "Gift card cannot be refunded.");
    }
}

این Class از نظر Compiler یک PaymentMethod است، ولی از نظر رفتار نمی‌تواند جایگزین آن شود.

چرا این طراحی نقض LSP است؟

C#
public async Task RefundAsync(
    PaymentMethod paymentMethod,
    decimal amount,
    CancellationToken cancellationToken)
{
    await paymentMethod.RefundAsync(
        amount,
        cancellationToken);
}

Caller با دیدن PaymentMethod انتظار دارد Refund قابل انجام باشد. اما GiftCardPayment در Runtime Exception می‌دهد.

Refactoring با Interfaceهای دقیق‌تر

C#
public interface IPayable
{
    Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken);
}

public interface IRefundable
{
    Task RefundAsync(
        decimal amount,
        CancellationToken cancellationToken);
}

CardPayment هر دو قابلیت را دارد:

C#
public class CardPayment
    : IPayable,
      IRefundable
{
    public Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }

    public Task RefundAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }
}

GiftCardPayment فقط Contract واقعی خودش را اعلام می‌کند:

C#
public class GiftCardPayment
    : IPayable
{
    public Task PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return Task.CompletedTask;
    }
}
🎯
اگر implementation طبیعی یک Method فقط NotSupportedException است، احتمالاً abstraction بیش از حد بزرگ یا hierarchy اشتباه طراحی شده است.

LSP و Contract

Contract فقط Method Signature نیست. رفتار مورد انتظار نیز بخشی از Contract است. Subtype باید انتظارهای Base Type را حفظ کند.

  • ورودی معتبر Base Type را بی‌دلیل رد نکند.
  • Guarantee خروجی را ضعیف‌تر نکند.
  • Invariantهای اصلی را نشکند.
  • برای رفتار عادی Exception غیرمنتظره ایجاد نکند.

Precondition

Subtype نباید Precondition را سخت‌تر کند.

C#
public abstract class Payment
{
    public abstract void Pay(
        decimal amount);
}

public class SpecialPayment
    : Payment
{
    public override void Pay(
        decimal amount)
    {
        if (amount < 1_000_000)
        {
            throw new InvalidOperationException();
        }

        // ...
    }
}

اگر Base Type هر Amount مثبت را قبول می‌کند، Derived Type نباید ناگهان فقط Amountهای بالاتر از یک میلیون را بپذیرد.

Postcondition

Subtype نباید Guarantee خروجی Base Type را ضعیف‌تر کند. مثلاً اگر Contract می‌گوید در Success همیشه TransactionId تولید می‌شود، تمام implementationها باید آن را رعایت کنند.

Inheritance فقط برای Code Reuse نیست

⚠️
Inheritance یک تعهد رفتاری است. اگر فقط برای reuse کردن چند Method از Base Class ارث‌بری می‌کنیم، ولی Subtype Contract آن را حفظ نمی‌کند، Composition معمولاً انتخاب بهتری است.

LSP و Interfaceها

LSP فقط برای Class inheritance نیست. Implementationهای یک Interface هم باید Contract مشترک را حفظ کنند.

C#
public interface ITransactionRepository
{
    Task<Transaction?> GetAsync(
        Guid id,
        CancellationToken cancellationToken);
}

اگر یک Repository برای Not Found مقدار null برگرداند ولی implementation دیگری برای همان وضعیت Exception بدهد، رفتار abstraction برای Caller قابل اعتماد نیست؛ مگر اینکه Contract این تفاوت را صریح تعریف کرده باشد.

Code Smell: Type Checking

C#
public void Process(
    PaymentMethod payment)
{
    if (payment is GiftCardPayment)
    {
        // Special workaround
    }
    else
    {
        // Normal behavior
    }
}

اگر Caller مرتباً مجبور شود Type واقعی را بررسی کند، ممکن است polymorphic abstraction اشتباه طراحی شده باشد.

مثال واقعی Refactored در Payment System

C#
public interface IPaymentProcessor
{
    Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}

public interface IRefundProcessor
{
    Task<RefundResult> RefundAsync(
        RefundRequest request,
        CancellationToken cancellationToken);
}
C#
public class CardProcessor
    : IPaymentProcessor,
      IRefundProcessor
{
    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        return Task.FromResult(
            new PaymentResult());
    }

    public Task<RefundResult> RefundAsync(
        RefundRequest request,
        CancellationToken cancellationToken)
    {
        return Task.FromResult(
            new RefundResult());
    }
}

public class GiftCardProcessor
    : IPaymentProcessor
{
    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        return Task.FromResult(
            new PaymentResult());
    }
}

Caller مسیر Refund فقط IRefundProcessor می‌گیرد. پس هیچ Processor ناسازگار وارد این مسیر نمی‌شود و Contract قابل اعتماد می‌ماند.

نشانه‌های نقض LSP

  • Derived Type برای Methodهای Base Type NotSupportedException می‌دهد.
  • Subtype ورودی‌های معتبر Base Type را رد می‌کند.
  • Subtype Guarantee ضعیف‌تری ایجاد می‌کند.
  • Caller مجبور است با is یا Type Check رفتار خاص بنویسد.
  • Derived Type معنای اصلی عملیات Base Type را تغییر می‌دهد.

قبل و بعد از LSP

طراحی ضعیف طراحی بهتر
Subtype بعضی Methodها را پشتیبانی نمی‌کند. Contractهای دقیق و capability-based
NotSupportedException Interface مناسب برای قابلیت واقعی
Type Checking در Caller Polymorphism قابل اعتماد
Inheritance فقط برای Reuse Inheritance برای رابطه رفتاری واقعی
Contract مبهم Contract مشخص و قابل پیش‌بینی

نکته مصاحبه‌ای

🎤
پاسخ خوب: LSP means a subtype should be usable wherever its base type is expected without breaking the expected behavior. مثال: اگر Base Payment قابلیت Refund دارد ولی یک Derived Type در Refund NotSupportedException بدهد، hierarchy احتمالاً LSP را نقض کرده است.

جمع‌بندی LSP

Liskov Substitution Principle می‌گوید Subtype باید Contract رفتاری Base Type را حفظ کند. Inheritance صرفاً یک رابطه Syntaxی نیست؛ یک تعهد رفتاری است.

✅
مدل ذهنی: اگر B از A است، باید بتوان B را هر جایی که A انتظار می‌رود قرار داد، بدون اینکه رفتار قابل انتظار سیستم شکسته شود.
