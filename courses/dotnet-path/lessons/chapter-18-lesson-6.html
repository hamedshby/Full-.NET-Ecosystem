18.6 — Encapsulate What Changes

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۱۵
⏱️ زمان مطالعه: ۱۲ دقیقه
👤 تیم فنی

Encapsulate What Changes یعنی بخش‌هایی را که احتمال تغییر دارند شناسایی کنیم و آن‌ها را پشت یک Boundary پایدار قرار دهیم تا تغییرشان به کل سیستم سرایت نکند.

مثال: Fee Rule متغیر

C#
public decimal CalculateFee(
    Payment payment)
{
    if (payment.Type == PaymentType.Card)
        return payment.Amount * 0.01m;

    if (payment.Type == PaymentType.Wallet)
        return payment.Amount * 0.005m;

    return 0;
}

با اضافه شدن روش‌های پرداخت، این Method دائماً تغییر می‌کند.

Encapsulate Variation

C#
public interface IFeePolicy
{
    decimal Calculate(decimal amount);
}

public class CardFeePolicy : IFeePolicy
{
    public decimal Calculate(decimal amount)
        => amount * 0.01m;
}

public class WalletFeePolicy : IFeePolicy
{
    public decimal Calculate(decimal amount)
        => amount * 0.005m;
}

Variation مربوط به Fee داخل Policyهای مستقل قرار گرفته است.

چه چیزهایی معمولاً تغییر می‌کنند؟

  • Business Ruleها
  • External Providerها
  • Persistence
  • Pricing و Fee Policy
  • Serialization/Protocol
  • Notification Channelها

ارتباط با OCP و Strategy

این اصل پایهٔ بسیاری از Patternهاست. Strategy Pattern نمونه‌ای از Encapsulate کردن Algorithmهای متغیر است و OCP کمک می‌کند Variation جدید با تغییر کمتر در Consumer اضافه شود.

⚠️
هر چیزی که «ممکن است روزی تغییر کند» را Abstract نکنید. Variation باید واقعی، محتمل یا از نظر معماری پرهزینه باشد؛ وگرنه YAGNI را نقض می‌کنید.

نکته مصاحبه‌ای

🎤
Encapsulate what changes means isolating volatile behavior behind stable boundaries so changes remain local instead of propagating through the system.

جمع‌بندی

نقاط تغییر سیستم را پیدا کنید و Variation واقعی را پشت Contract یا Component مناسب قرار دهید؛ نه اینکه کل سیستم را از قبل Abstract کنید.
