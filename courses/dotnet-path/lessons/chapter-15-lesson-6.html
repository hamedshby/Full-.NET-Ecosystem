15.6 — Dependency Inversion Principle — DIP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Dependency Inversion Principle یا DIP پنجمین اصل از مجموعه SOLID است. این اصل دربارهٔ جهت Dependencyها در طراحی نرم‌افزار است و می‌گوید Business Logic سطح بالا نباید مستقیماً به جزئیات Infrastructure وابسته باشد.

💡
تعریف معروف DIP دو بخش دارد:
1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
2. Abstractions should not depend on details. Details should depend on abstractions.

High-Level Module چیست؟

High-Level Module معمولاً بخشی از سیستم است که Business Rule یا Use Case اصلی را اجرا می‌کند.

برای مثال در Payment System:

  • Process Payment
  • Refund Transaction
  • Settlement
  • Transfer Money
  • Create Order

این بخش‌ها مشخص می‌کنند سیستم چه کاری باید انجام دهد.

Low-Level Module چیست؟

Low-Level Module معمولاً جزئیات فنی اجرای عملیات است.

  • SQL Server
  • Entity Framework Core
  • Redis
  • RabbitMQ
  • SMTP
  • File System
  • External Bank API

این بخش‌ها بیشتر مشخص می‌کنند سیستم چگونه یک کار را انجام دهد.

مثال اشتباه

فرض کنید PaymentService مستقیماً Repository مربوط به SQL Server را می‌سازد:

C#
public class PaymentService
{
    private readonly SqlPaymentRepository
        _repository;

    public PaymentService()
    {
        _repository =
            new SqlPaymentRepository();
    }

    public async Task ProcessAsync(
        Payment payment)
    {
        // Business Logic

        await _repository.SaveAsync(
            payment);
    }
}

در این طراحی PaymentService که یک High-Level Module است، مستقیماً به SqlPaymentRepository که یک Detail سطح پایین است وابسته شده است.

Text
PaymentService
      │
      ▼
SqlPaymentRepository
      │
      ▼
SQL Server

مشکل این Dependency چیست؟

اگر فردا Persistence تغییر کند و بخواهیم به‌جای SQL Server از API، MongoDB یا یک Implementation دیگر استفاده کنیم، باید PaymentService را تغییر دهیم.

Business Logic به یک Detail فنی گره خورده است.

  • Coupling بالا می‌رود.
  • Unit Test سخت‌تر می‌شود.
  • جایگزینی Infrastructure دشوار می‌شود.
  • Business Logic دربارهٔ جزئیات فنی knowledge پیدا می‌کند.
  • تغییر Low-Level Module روی High-Level Module اثر مستقیم دارد.
⚠️
مشکل فقط استفاده از SQL Server نیست. مشکل این است که Business Logic مستقیماً به Implementation مشخص SQL وابسته شده است.

Refactoring با Abstraction

بین High-Level و Low-Level Module یک Abstraction قرار می‌دهیم:

C#
public interface IPaymentRepository
{
    Task SaveAsync(
        Payment payment);
}

PaymentService حالا به Interface وابسته می‌شود:

C#
public class PaymentService
{
    private readonly IPaymentRepository
        _repository;

    public PaymentService(
        IPaymentRepository repository)
    {
        _repository =
            repository;
    }

    public async Task ProcessAsync(
        Payment payment)
    {
        // Business Logic

        await _repository.SaveAsync(
            payment);
    }
}

Implementation مربوط به SQL نیز به همان Abstraction وابسته است:

C#
public class SqlPaymentRepository
    : IPaymentRepository
{
    public Task SaveAsync(
        Payment payment)
    {
        // SQL Server implementation

        return Task.CompletedTask;
    }
}

جهت Dependency بعد از DIP

Text
        IPaymentRepository
         ▲             ▲
         │             │
PaymentService   SqlPaymentRepository
 High-Level          Low-Level

هر دو طرف به Abstraction وابسته‌اند. PaymentService دیگر SqlPaymentRepository را نمی‌شناسد.

🎯
نکتهٔ اصلی DIP این نیست که «همه‌جا Interface بسازیم». هدف این است که Policy و Business Logic به Detail وابسته نباشند؛ Detail باید با Contract مورد نیاز Policy سازگار شود.

Dependency Inversion با Dependency Injection فرق دارد

این دو مفهوم بسیار به هم مرتبط‌اند، اما یکی نیستند.

Dependency Inversion Principle Dependency Injection
یک Design Principle است. یک Technique برای تأمین Dependency است.
دربارهٔ جهت Dependency صحبت می‌کند. دربارهٔ نحوهٔ دریافت Dependency صحبت می‌کند.
High-Level باید به Abstraction وابسته باشد. Dependency از بیرون به Object داده می‌شود.
عضوی از SOLID است. یکی از روش‌های پیاده‌سازی loosely coupled design است.

Dependency Injection بدون DIP

حتی می‌توان Dependency Injection داشت ولی DIP را خوب رعایت نکرد:

C#
public class PaymentService
{
    private readonly SqlPaymentRepository
        _repository;

    public PaymentService(
        SqlPaymentRepository repository)
    {
        _repository =
            repository;
    }
}

Dependency از Constructor تزریق شده است، اما High-Level Module هنوز به Concrete Implementation وابسته است.

⚠️
Constructor Injection به‌تنهایی به معنی رعایت DIP نیست. مهم این است که Dependencyهای معماری در نقاط مناسب به Abstraction وابسته شوند.

Constructor Injection

رایج‌ترین روش Dependency Injection در ASP.NET Core، Constructor Injection است:

C#
public class PaymentService
{
    private readonly IPaymentRepository
        _repository;

    public PaymentService(
        IPaymentRepository repository)
    {
        _repository =
            repository;
    }
}

PaymentService Dependency را نمی‌سازد. Dependency از بیرون به آن داده می‌شود.

ثبت Dependency در ASP.NET Core

C#
builder.Services.AddScoped
    <IPaymentRepository,
     SqlPaymentRepository>();

builder.Services.AddScoped
    <PaymentService>();

DI Container هنگام ساخت PaymentService، Implementation مربوط به IPaymentRepository را Resolve می‌کند.

تغییر Implementation

فرض کنید برای Integration Test یا یک محیط دیگر Implementation جدیدی داریم:

C#
public class InMemoryPaymentRepository
    : IPaymentRepository
{
    private readonly List<Payment>
        _payments = new();

    public Task SaveAsync(
        Payment payment)
    {
        _payments.Add(
            payment);

        return Task.CompletedTask;
    }
}

بدون تغییر PaymentService می‌توان Mapping را عوض کرد:

C#
builder.Services.AddScoped
    <IPaymentRepository,
     InMemoryPaymentRepository>();

مثال واقعی: Notification

نسخهٔ Coupled:

C#
public class PaymentService
{
    private readonly SmtpClient
        _smtpClient;

    public PaymentService()
    {
        _smtpClient =
            new SmtpClient();
    }

    public void CompletePayment(
        Payment payment)
    {
        // Business Logic

        _smtpClient.Send(
            "system@company.com",
            payment.CustomerEmail,
            "Payment",
            "Payment completed.");
    }
}

PaymentService مستقیماً SMTP را می‌شناسد. نسخه بهتر:

C#
public interface IPaymentNotifier
{
    Task NotifySuccessAsync(
        Payment payment,
        CancellationToken cancellationToken);
}
C#
public class EmailPaymentNotifier
    : IPaymentNotifier
{
    public Task NotifySuccessAsync(
        Payment payment,
        CancellationToken cancellationToken)
    {
        // SMTP / Email Provider

        return Task.CompletedTask;
    }
}
C#
public class PaymentService
{
    private readonly IPaymentNotifier
        _notifier;

    public PaymentService(
        IPaymentNotifier notifier)
    {
        _notifier =
            notifier;
    }

    public async Task CompleteAsync(
        Payment payment,
        CancellationToken cancellationToken)
    {
        // Business Logic

        await _notifier.NotifySuccessAsync(
            payment,
            cancellationToken);
    }
}

مثال واقعی: Message Broker

یکی از کاربردهای مهم DIP در Microserviceها جدا کردن Application Logic از Message Broker است.

طراحی Coupled

C#
public class PurchaseService
{
    private readonly RabbitMqPublisher
        _publisher;

    public PurchaseService(
        RabbitMqPublisher publisher)
    {
        _publisher =
            publisher;
    }

    public async Task PurchaseAsync()
    {
        // Business Logic

        await _publisher.PublishAsync(
            "payment.created");
    }
}

Application Service اکنون RabbitMQ را مستقیماً می‌شناسد.

نسخه Refactored

C#
public interface IEventPublisher
{
    Task PublishAsync<TEvent>(
        TEvent @event,
        CancellationToken cancellationToken);
}
C#
public class RabbitMqEventPublisher
    : IEventPublisher
{
    public Task PublishAsync<TEvent>(
        TEvent @event,
        CancellationToken cancellationToken)
    {
        // RabbitMQ implementation

        return Task.CompletedTask;
    }
}

Application Service فقط مفهوم Event Publishing را می‌شناسد:

C#
public class PurchaseService
{
    private readonly IEventPublisher
        _publisher;

    public PurchaseService(
        IEventPublisher publisher)
    {
        _publisher =
            publisher;
    }

    public async Task PurchaseAsync(
        CancellationToken cancellationToken)
    {
        // Business Logic

        await _publisher.PublishAsync(
            new PaymentCreated(),
            cancellationToken);
    }
}

اگر RabbitMQ با Kafka یا Azure Service Bus جایگزین شود، Application Service نباید به خاطر تغییر Message Broker بازنویسی شود. Infrastructure جدید Contract مربوط به IEventPublisher را پیاده‌سازی می‌کند.

مثال واقعی Payment Gateway

Business Logic نباید مستقیماً Client مربوط به یک بانک خاص را بشناسد:

C#
public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
C#
public class BankAPaymentGateway
    : IPaymentGateway
{
    private readonly HttpClient
        _httpClient;

    public BankAPaymentGateway(
        HttpClient httpClient)
    {
        _httpClient =
            httpClient;
    }

    public async Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        // Call Bank A API

        return new PaymentResult();
    }
}

Payment Use Case فقط Contract را می‌شناسد:

C#
public class ProcessPaymentUseCase
{
    private readonly IPaymentGateway
        _paymentGateway;

    public ProcessPaymentUseCase(
        IPaymentGateway paymentGateway)
    {
        _paymentGateway =
            paymentGateway;
    }

    public Task<PaymentResult> ExecuteAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        return _paymentGateway.PayAsync(
            request,
            cancellationToken);
    }
}

DIP و Testability

یکی از نتایج مهم DIP این است که High-Level Logic را می‌توان بدون Infrastructure واقعی تست کرد.

C#
public class FakePaymentRepository
    : IPaymentRepository
{
    public bool WasSaved
    {
        get;
        private set;
    }

    public Task SaveAsync(
        Payment payment)
    {
        WasSaved = true;

        return Task.CompletedTask;
    }
}

برای Unit Test نیازی به SQL Server واقعی نداریم.

DIP و Clean Architecture

Dependency Inversion یکی از پایه‌های مهم معماری‌هایی مانند Clean Architecture است. در چنین طراحی‌هایی Business Layer نباید به Infrastructure Layer وابسته باشد.

Text
Infrastructure
      │
      │ implements
      ▼
Application Abstraction
      ▲
      │ depends on
      │
Application / Domain

در سطح Source Code، Infrastructure معمولاً Reference لازم را به لایه‌ای می‌دهد که Contract در آن تعریف شده است، نه برعکس.

💡
در معماری خوب، Business Rules در مرکز قرار می‌گیرند. Database، Message Broker، Email Provider و External APIها جزئیاتی هستند که باید بتوان آن‌ها را در اطراف Business Logic تغییر داد.

Abstraction را کجا تعریف کنیم؟

یک نکتهٔ معماری مهم این است که Contract بهتر است از نیاز Consumer و High-Level Policy شکل بگیرد، نه صرفاً به‌عنوان یک Wrapper از API یک ابزار Infrastructure.

مثلاً Application به این قابلیت نیاز دارد:

C#
public interface ITransactionRepository
{
    Task<Transaction?> GetAsync(
        Guid transactionId,
        CancellationToken cancellationToken);

    Task SaveAsync(
        Transaction transaction,
        CancellationToken cancellationToken);
}

Infrastructure باید خودش را با این نیاز سازگار کند.

آیا برای هر Class باید Interface بسازیم؟

خیر. DIP به معنی Interface برای همه چیز نیست.

⚠️
اگر Class یک Detail قابل تعویض، مرز معماری، External Dependency یا نقطهٔ Variation نیست، ساخت Interface فقط برای اینکه «SOLID رعایت شود» می‌تواند Over-Engineering باشد.

چه Dependencyهایی معمولاً ارزش Abstraction دارند؟

  • Database / Repository
  • External API
  • Message Broker
  • Email / SMS Provider
  • File Storage
  • Clock / Time Provider در بعضی Domainها
  • Payment Gateway
  • Cache Provider

DIP و OCP

DIP معمولاً به رعایت OCP کمک می‌کند. وقتی High-Level Module به Abstraction وابسته است، می‌توان Implementation جدید اضافه کرد بدون اینکه Business Logic تغییر کند.

Text
IPaymentGateway
      ▲
      │
 ┌────┴──────────┐
 │               │
BankAGateway   BankBGateway

اضافه شدن Bank C می‌تواند فقط با یک Implementation جدید انجام شود.

DIP و Dependency Injection Container

DI Container ابزار مفیدی برای Wire کردن Dependencyها است، اما خود Container اصل DIP نیست.

C#
builder.Services.AddScoped
    <IPaymentGateway,
     BankAPaymentGateway>();

builder.Services.AddScoped
    <IEventPublisher,
     RabbitMqEventPublisher>();

builder.Services.AddScoped
    <IPaymentRepository,
     SqlPaymentRepository>();

این قسمت معمولاً در Composition Root قرار می‌گیرد؛ جایی که Concrete Implementationها به Abstractionها متصل می‌شوند.

Composition Root چیست؟

Composition Root محلی است که Object Graph برنامه ساخته و Dependencyها به هم متصل می‌شوند. در ASP.NET Core معمولاً بخش بزرگی از این کار در Program.cs انجام می‌شود.

C#
var builder =
    WebApplication.CreateBuilder(
        args);

builder.Services.AddScoped
    <IPaymentRepository,
     SqlPaymentRepository>();

builder.Services.AddScoped
    <IPaymentGateway,
     BankAPaymentGateway>();

builder.Services.AddScoped
    <PaymentService>();

نشانه‌های نقض DIP

  • Business Service داخل خودش Dependency را با new می‌سازد.
  • Application Layer مستقیماً به EF Core، RabbitMQ یا SMTP وابسته است.
  • تغییر Infrastructure نیازمند تغییر Business Logic است.
  • Unit Test بدون Database یا External Service قابل اجرا نیست.
  • High-Level Module به Concrete Class وابسته است در حالی که Variation واقعی وجود دارد.
  • Business Code جزئیات Connection، Queue یا HTTP Provider را می‌داند.

Code Smell: ساخت Dependency داخل Service

C#
public class OrderService
{
    public void CreateOrder()
    {
        var repository =
            new SqlOrderRepository();

        var email =
            new SmtpEmailSender();

        var publisher =
            new RabbitMqPublisher();

        // ...
    }
}

این Service هم به Concrete Typeها وابسته است و هم مسئول ساخت Dependencyها شده است. تست و تغییر آن دشوارتر خواهد بود.

قبل و بعد از DIP

قبل بعد
High-Level → Concrete Low-Level High-Level → Abstraction ← Low-Level
Business Logic وابسته به SQL/RabbitMQ Business Logic وابسته به Contract
تغییر Infrastructure سخت Implementation قابل جایگزینی
Unit Test وابسته به Infrastructure Fake/Mock ساده‌تر
Coupling بالا Coupling کنترل‌شده‌تر

نکته مصاحبه‌ای

🎤
پاسخ خوب: Dependency Inversion says high-level modules should not depend on low-level modules; both should depend on abstractions. سپس توضیح دهید که مثلاً PaymentService نباید مستقیماً به SqlPaymentRepository یا RabbitMqPublisher وابسته باشد، بلکه باید به Contractهایی مثل IPaymentRepository و IEventPublisher وابسته شود.

اشتباهات رایج

  • یکی دانستن DIP و Dependency Injection.
  • تصور اینکه Constructor Injection به‌تنهایی یعنی رعایت DIP.
  • ساخت Interface برای تمام Classها بدون وجود Boundary یا Variation واقعی.
  • تعریف Abstraction بر اساس جزئیات Infrastructure به‌جای نیاز Business.
  • استفاده از Service Locator به‌جای Dependencyهای واضح.
  • تزریق تعداد بسیار زیادی Dependency بدون بررسی SRP.
🎯
مدل ذهنی: Business Logic نباید بداند داده در SQL ذخیره می‌شود، Event با RabbitMQ ارسال می‌شود یا Email با چه Providerی فرستاده می‌شود. Business Logic باید فقط Contract مورد نیاز خودش را بشناسد.

جمع‌بندی DIP

Dependency Inversion Principle جهت Dependencyهای معماری را از Detailهای فنی به سمت Abstractionها تغییر می‌دهد. High-Level Business Logic نباید مستقیماً به Low-Level Infrastructure وابسته باشد. هر دو باید از Contractهای مناسب استفاده کنند.

Dependency Injection و DI Container ابزارهایی هستند که پیاده‌سازی چنین طراحی‌ای را ساده‌تر می‌کنند، اما DIP یک اصل معماری است و نباید با DI اشتباه گرفته شود.

✅
نکته کلیدی: Depend on abstractions, not concrete details — especially across architectural boundaries. Database، Message Broker و External Provider باید Detailهای قابل جایگزینی باشند؛ Business Rules باید تا حد ممکن مستقل از آن‌ها باقی بمانند.
