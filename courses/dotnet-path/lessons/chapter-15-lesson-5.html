15.5 — Interface Segregation Principle — ISP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Interface Segregation Principle یا ISP چهارمین اصل از مجموعه SOLID است. این اصل می‌گوید Clientها نباید مجبور شوند به Methodهایی وابسته باشند که به آن‌ها نیاز ندارند.

💡
تعریف معروف ISP: Clients should not be forced to depend on methods they do not use. یعنی به‌جای یک Interface بزرگ و عمومی، بهتر است Interfaceهای کوچک‌تر و متمرکز بر قابلیت واقعی طراحی شوند.

ISP دقیقاً چه مشکلی را حل می‌کند؟

اگر یک Interface چند قابلیت نامرتبط را کنار هم قرار دهد، هر Implementation مجبور می‌شود تمام Methodهای آن را پیاده‌سازی کند؛ حتی وقتی بعضی Methodها هیچ معنایی برای آن Class ندارند.

  • Method خالی نوشته می‌شود.
  • NotSupportedException پرتاب می‌شود.
  • Implementation مصنوعی ایجاد می‌شود.
  • Client به قابلیت‌هایی وابسته می‌شود که استفاده نمی‌کند.

مثال اشتباه: Fat Interface

C#
public interface IPaymentDevice
{
    void Pay(
        decimal amount);

    void Refund(
        decimal amount);

    void PrintReceipt();

    void ReadNfcCard();

    void ScanQrCode();
}

حالا یک Online Payment Gateway داریم که فقط Pay و Refund انجام می‌دهد:

C#
public class OnlinePaymentGateway
    : IPaymentDevice
{
    public void Pay(
        decimal amount)
    {
        // Online payment
    }

    public void Refund(
        decimal amount)
    {
        // Online refund
    }

    public void PrintReceipt()
    {
        throw new NotSupportedException();
    }

    public void ReadNfcCard()
    {
        throw new NotSupportedException();
    }

    public void ScanQrCode()
    {
        throw new NotSupportedException();
    }
}
⚠️
اگر یک Interface باعث شود Implementationها Methodهای خالی یا NotSupportedException داشته باشند، احتمالاً Interface بیش از حد بزرگ است.

ISP یعنی Interfaceها را بر اساس نیاز Client و قابلیت واقعی طراحی کنیم، نه اینکه تمام Methodهای مرتبط با یک موضوع را داخل یک Interface بزرگ قرار دهیم.

مثال اشتباه در Repository

C#
public interface IRepository<T>
{
    Task<T?> GetAsync(
        Guid id);

    Task AddAsync(
        T entity);

    Task UpdateAsync(
        T entity);

    Task DeleteAsync(
        T entity);

    Task ExportAsync();

    Task ArchiveAsync();
}

ممکن است بعضی Repositoryها فقط Read-only باشند، اما مجبور می‌شوند Add، Update، Delete و Archive را هم implement کنند.

Refactoring Repository بر اساس Capability

C#
public interface IReadRepository<T>
{
    Task<T?> GetAsync(
        Guid id);
}

public interface IWriteRepository<T>
{
    Task AddAsync(
        T entity);

    Task UpdateAsync(
        T entity);
}

public interface IDeleteRepository<T>
{
    Task DeleteAsync(
        T entity);
}

حالا یک Read-only Service فقط به Contract مورد نیاز خودش وابسته می‌شود:

C#
public class PaymentQueryService
{
    private readonly IReadRepository<Payment>
        _repository;

    public PaymentQueryService(
        IReadRepository<Payment> repository)
    {
        _repository =
            repository;
    }
}

مثال واقعی در Payment System

C#
public interface IPaymentProvider
{
    Task<PurchaseResult> PurchaseAsync(
        PurchaseRequest request,
        CancellationToken cancellationToken);

    Task<RefundResult> RefundAsync(
        RefundRequest request,
        CancellationToken cancellationToken);

    Task<BalanceResult> GetBalanceAsync(
        CancellationToken cancellationToken);

    Task<SettlementResult> SettleAsync(
        CancellationToken cancellationToken);
}

Provider A شاید تمام قابلیت‌ها را پشتیبانی کند، اما Provider B فقط Purchase و Refund داشته باشد. در این حالت Interface بالا برای Provider B بیش از حد بزرگ است.

Refactoring Payment Provider

{

{

C#
public class ProviderA
    : IPurchaseProvider,
      IRefundProvider,
      IBalanceProvider,
      ISettlementProvider
{
    // All supported operations
}

public class ProviderB
    : IPurchaseProvider,
      IRefundProvider
{
    // Only supported operations
}

هر Provider فقط Capability واقعی خودش را اعلام می‌کند. دیگر Method جعلی یا NotSupportedException لازم نیست. این یک کاربرد واقعی ISP در Payment System است.

ISP و Dependency Injection

C#
public class RefundService
{
    private readonly IRefundProvider
        _refundProvider;

    public RefundService(
        IRefundProvider refundProvider)
    {
        _refundProvider =
            refundProvider;
    }
}

RefundService فقط چیزی را دریافت می‌کند که واقعاً نیاز دارد. این موضوع Coupling را کمتر و Intent را واضح‌تر می‌کند.

ISP و Unit Test

Interfaceهای کوچک‌تر Mock و Fake کردن Dependencyها را ساده‌تر می‌کنند. Client مجبور نیست برای Test یک Method ساده، Contract بزرگی را Mock کند.

C#
public interface INotificationSender
{
    Task SendAsync(
        string message);
}

آیا Interface هرچه کوچک‌تر باشد بهتر است؟

خیر. هدف ISP ساخت یک Interface برای هر Method نیست. Methodهایی که از دید Client یک مفهوم منسجم دارند می‌توانند داخل یک Interface باقی بمانند.

⚠️
ISP یعنی Client-specific interfaces، نه اینکه هر Method را بی‌دلیل داخل Interface جدا قرار دهیم. Cohesion همچنان مهم است.

ISP و LSP چه ارتباطی دارند؟

یک Fat Interface ممکن است Class را مجبور کند Methodهایی را implement کند که پشتیبانی نمی‌کند. در نتیجه NotSupportedException ایجاد می‌شود و این موضوع می‌تواند LSP را هم نقض کند.

نشانه‌های نقض ISP

  • Interface تعداد زیادی Method نامرتبط دارد.
  • Implementation بعضی Methodها را خالی می‌گذارد.
  • NotSupportedException زیاد دیده می‌شود.
  • Client فقط بخش کوچکی از Interface را استفاده می‌کند.
  • Mock کردن Interface برای Unit Test سخت و پرحجم است.
  • یک تغییر کوچک روی Interface، Clientهای نامرتبط را تحت تأثیر قرار می‌دهد.

نکته مصاحبه‌ای

🎤
پاسخ مناسب: ISP says that clients should not be forced to depend on methods they do not use. مثلاً اگر یک Payment Provider فقط Purchase را پشتیبانی می‌کند، نباید مجبور شود Interfaceای با Refund، Settlement و Balance را کامل implement کند.

اشتباهات رایج

  • ساخت یک Interface برای تمام قابلیت‌های یک Domain.
  • ساخت یک Interface جدا برای هر Method بدون نیاز واقعی.
  • نادیده گرفتن Client هنگام طراحی Interface.
  • استفاده از NotSupportedException برای Methodهای اجباری.
  • وابسته کردن Read-only Service به Interface کامل CRUD.
  • تصور اینکه ISP فقط درباره تعداد Methodهاست.
🎯
مدل ذهنی: هر Client فقط باید Contractی را ببیند که واقعاً به آن نیاز دارد.

جمع‌بندی ISP

Interface Segregation Principle می‌گوید Interfaceها باید متناسب با نیاز Clientها و قابلیت واقعی Implementationها طراحی شوند. Fat Interface باعث Coupling بیشتر، Implementationهای مصنوعی و Testability پایین‌تر می‌شود.

✅
نکته کلیدی: Prefer small, cohesive, client-focused interfaces over large general-purpose interfaces.
