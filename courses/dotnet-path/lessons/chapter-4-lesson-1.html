مفهوم Encapsulation در OOP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

یکی از مهم‌ترین اصول Object-Oriented Programming مفهوم Encapsulation است. Encapsulation یعنی یک object مسئول نگهداری و محافظت از State خودش باشد و اجازه ندهد هر بخش از برنامه بدون کنترل، اطلاعات داخلی آن را تغییر دهد.

💡
Encapsulation فقط private کردن Fieldها نیست؛ هدف اصلی این است که object مشخص کند State آن چگونه و تحت چه قوانینی می‌تواند تغییر کند.

مشکل بدون Encapsulation

فرض کنید یک حساب بانکی داریم و موجودی آن را به‌صورت public تعریف کرده‌ایم:

C#
public class BankAccount
{
    public decimal Balance;
}

اکنون هر قسمت برنامه می‌تواند مقدار موجودی را مستقیماً تغییر دهد:

C#
var account = new BankAccount();

account.Balance = 1_000_000;

// هر کدی می‌تواند این کار را انجام دهد
account.Balance = -50_000_000;

مشکل اینجاست که BankAccount هیچ کنترلی روی State خودش ندارد. حتی اگر قانون سیستم بگوید موجودی نباید منفی شود، کد بیرونی می‌تواند این قانون را دور بزند.

⚠️
وقتی State داخلی یک object بدون محدودیت قابل تغییر باشد، حفظ Business Ruleها سخت می‌شود و object می‌تواند به‌راحتی وارد یک State نامعتبر شود.

حل مشکل با Encapsulation

به‌جای اینکه اجازه دهیم موجودی مستقیماً تغییر کند، تغییر Balance را در اختیار خود BankAccount قرار می‌دهیم:

C#
public class BankAccount
{
    public decimal Balance { get; private set; }

    public void Deposit(decimal amount)
    {
        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(amount));
        }

        Balance += amount;
    }
}

حالا کد بیرونی نمی‌تواند موجودی را مستقیماً تغییر دهد:

C#
var account = new BankAccount();

account.Deposit(500_000);

Console.WriteLine(account.Balance);

// Compile Error
// account.Balance = -10_000_000;

کد بیرونی فقط درخواست «واریز» می‌دهد. این خود BankAccount است که بررسی می‌کند مبلغ معتبر است یا نه و سپس State خودش را تغییر می‌دهد.

State و Behavior کنار یکدیگر

یکی از ایده‌های مهم Encapsulation این است که داده و رفتار مرتبط با آن در یک مرز معنادار کنار هم قرار بگیرند.

C#
public class BankAccount
{
    // State
    public decimal Balance { get; private set; }

    // Behavior
    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        Balance += amount;
    }

    // Behavior
    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        if (amount > Balance)
            throw new InvalidOperationException(
                "Insufficient balance.");

        Balance -= amount;
    }
}

موجودی حساب State است و Deposit و Withdraw رفتارهایی هستند که اجازه دارند آن State را طبق قوانین سیستم تغییر دهند.

✅
object فقط یک ظرف برای نگهداری داده نیست. در یک طراحی شی‌گرای مناسب، object از داده‌های خودش محافظت می‌کند و رفتارهای مجاز برای تغییر آن‌ها را ارائه می‌دهد.

Encapsulation با Access Modifierها

C# ابزارهایی مانند Access Modifierها را برای کنترل سطح دسترسی اعضای class در اختیار ما قرار می‌دهد.

Access Modifier مفهوم کلی
public عضو از بیرون قابل دسترسی است.
private عضو فقط داخل همان type قابل دسترسی است.
protected برای type و typeهای مشتق‌شده قابل دسترسی است.
internal دسترسی در همان assembly را فراهم می‌کند.

برای مثال می‌توان Balance را پشت یک Field خصوصی نگه داشت:

C#
public class BankAccount
{
    private decimal _balance;

    public decimal GetBalance()
    {
        return _balance;
    }
}

کد بیرونی به _balance دسترسی مستقیم ندارد و فقط از APIای که class ارائه کرده استفاده می‌کند.

Encapsulation با Property

در C# یکی از رایج‌ترین روش‌های کنترل دسترسی به State استفاده از Property است:

C#
public class BankAccount
{
    public decimal Balance { get; private set; }
}

در این حالت همه می‌توانند مقدار Balance را بخوانند، اما فقط خود class می‌تواند آن را تغییر دهد.

Validation در Property

C#
public class Customer
{
    private string _name;

    public string Name
    {
        get => _name;

        set
        {
            if (string.IsNullOrWhiteSpace(value))
            {
                throw new ArgumentException(
                    "Name is required.");
            }

            _name = value;
        }
    }
}

در این مثال class اجازه نمی‌دهد Name با مقدار خالی تنظیم شود.

Encapsulation با Method

برای تغییرات مهم Domain معمولاً Method می‌تواند Intent را بهتر از یک Setter عمومی نمایش دهد.

این طراحی را ببینید:

C#
public class Order
{
    public OrderStatus Status { get; set; }
}

هر بخش برنامه می‌تواند Status را به هر مقداری تغییر دهد. در مقابل می‌توان رفتار مشخصی تعریف کرد:

C#
public class Order
{
    public OrderStatus Status { get; private set; }

    public void Cancel()
    {
        if (Status == OrderStatus.Delivered)
        {
            throw new InvalidOperationException(
                "Delivered order cannot be canceled.");
        }

        Status = OrderStatus.Canceled;
    }
}

حالا کد بیرونی نمی‌گوید «Status را برابر Canceled کن»، بلکه به object می‌گوید «خودت را Cancel کن». خود Order تصمیم می‌گیرد این عملیات مجاز است یا نه.

جلوگیری از Invalid State

یکی از اهداف مهم Encapsulation این است که object تا جای ممکن همیشه در یک State معتبر باقی بماند. برای مثال یک حساب بانکی باید شماره حساب معتبر داشته باشد:

C#
public class BankAccount
{
    public string AccountNumber { get; }

    public BankAccount(
        string accountNumber)
    {
        if (string.IsNullOrWhiteSpace(
            accountNumber))
        {
            throw new ArgumentException(
                "Account number is required.",
                nameof(accountNumber));
        }

        AccountNumber = accountNumber;
    }
}

به‌جای ساختن object ناقص و امیدوار بودن به اینکه بعداً کسی شماره حساب را تنظیم کند، Constructor اجازه نمی‌دهد object نامعتبر از ابتدا ساخته شود.

Encapsulation یعنی Data Hiding؟

Data Hiding بخشی از Encapsulation است، اما این دو دقیقاً یک مفهوم نیستند. مخفی‌کردن یک Field با private فقط دسترسی مستقیم را محدود می‌کند. Encapsulation مفهوم گسترده‌تری دارد: object باید یک API مناسب ارائه دهد و قوانین تغییر State را نیز کنترل کند.

C#
public class BankAccount
{
    private decimal _balance;

    public decimal Balance
    {
        get => _balance;
        set => _balance = value;
    }
}

با اینکه _balance private است، Setter عمومی همچنان اجازه می‌دهد هر مقداری مستقیماً وارد State شود. پس صرف private بودن Field لزوماً Encapsulation قوی ایجاد نمی‌کند.

⚠️
تبدیل همهٔ Public Fieldها به { get; set; } به‌تنهایی طراحی را Encapsulated نمی‌کند. سؤال اصلی این است: «چه کسی اجازه دارد State را تغییر دهد و قوانین این تغییر کجا enforce می‌شوند؟»

Tell, Don't Ask

Encapsulation با اصل Tell, Don't Ask ارتباط نزدیکی دارد. به‌جای گرفتن State یک object، تصمیم‌گیری بیرون از آن و سپس تغییر دادن State، بهتر است در صورت مناسب بودن مسئولیت، از خود object بخواهیم رفتار را انجام دهد.

طراحی ضعیف‌تر

C#
if (account.Balance >= amount)
{
    account.Balance -= amount;
}

طراحی Encapsulated

C#
account.Withdraw(amount);

در نسخهٔ دوم، قانون برداشت در خود BankAccount قرار دارد و مصرف‌کننده لازم نیست جزئیات پیاده‌سازی آن را بداند.

مزایای Encapsulation

  • محافظت از State: تغییرات فقط از مسیرهای مجاز انجام می‌شوند.
  • حفظ Business Rule: قوانین در محل مرتبط با داده enforce می‌شوند.
  • کاهش Coupling: کد بیرونی کمتر به جزئیات داخلی object وابسته می‌شود.
  • Refactoring آسان‌تر: پیاده‌سازی داخلی می‌تواند بدون شکستن مصرف‌کننده‌ها تغییر کند.
  • خوانایی بهتر: Methodهایی مانند Withdraw() Intent سیستم را واضح بیان می‌کنند.
  • کاهش State نامعتبر: object کنترل بیشتری روی چرخهٔ زندگی خودش دارد.

مثال کامل: BankAccount بدون Encapsulation

C#
public class BankAccount
{
    public string AccountNumber { get; set; }
    public decimal Balance { get; set; }
    public bool IsBlocked { get; set; }
}

این class تقریباً هیچ کنترلی روی خودش ندارد:

C#
var account = new BankAccount();

account.AccountNumber = "";
account.Balance = -5_000_000;
account.IsBlocked = false;

نسخه Encapsulated

C#
public class BankAccount
{
    public string AccountNumber { get; }

    public decimal Balance { get; private set; }

    public bool IsBlocked { get; private set; }

    public BankAccount(
        string accountNumber)
    {
        if (string.IsNullOrWhiteSpace(
            accountNumber))
        {
            throw new ArgumentException(
                "Account number is required.",
                nameof(accountNumber));
        }

        AccountNumber = accountNumber;
    }

    public void Deposit(decimal amount)
    {
        EnsureAccountIsActive();

        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(amount));
        }

        Balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        EnsureAccountIsActive();

        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(amount));
        }

        if (amount > Balance)
        {
            throw new InvalidOperationException(
                "Insufficient balance.");
        }

        Balance -= amount;
    }

    public void Block()
    {
        IsBlocked = true;
    }

    private void EnsureAccountIsActive()
    {
        if (IsBlocked)
        {
            throw new InvalidOperationException(
                "Account is blocked.");
        }
    }
}
C#
var account =
    new BankAccount("IR-1001");

account.Deposit(1_000_000);

account.Withdraw(200_000);

account.Block();

Console.WriteLine(account.Balance);
// 800000

در نسخهٔ نهایی، شماره حساب فقط هنگام ایجاد تعیین می‌شود، Balance مستقیماً قابل تغییر نیست، برداشت و واریز قوانین خود را دارند و وضعیت Block شدن حساب نیز توسط رفتار خود object کنترل می‌شود.

✅
خلاصه: Encapsulation یعنی object مالک State و قوانین مرتبط با آن باشد. جزئیات غیرضروری را پنهان می‌کنیم و به‌جای ارائهٔ دسترسی آزاد به داده‌ها، رفتارهای مشخص و کنترل‌شده‌ای مانند Deposit()، Withdraw() و Block() ارائه می‌دهیم.
