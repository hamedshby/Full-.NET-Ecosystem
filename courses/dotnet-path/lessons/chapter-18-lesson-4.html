18.4 — Tell, Don't Ask

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۱۵
⏱️ زمان مطالعه: ۱۲ دقیقه
👤 تیم فنی

Tell, Don't Ask می‌گوید به‌جای اینکه State یک Object را بیرون بکشیم، دربارهٔ آن تصمیم بگیریم و دوباره State را تغییر دهیم، بهتر است از خود Object بخواهیم Behavior مربوط به آن State را اجرا کند.

Ask Style

C#
if (account.Balance >= amount)
{
    account.Balance -= amount;
}

کد بیرونی State داخلی Account را می‌خواند، Business Rule را اجرا می‌کند و State را تغییر می‌دهد.

Tell Style

C#
public class Account
{
    public decimal Balance { get; private set; }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        if (Balance < amount)
            throw new InvalidOperationException(
                "Insufficient balance.");

        Balance -= amount;
    }
}

// Tell the object what to do
account.Withdraw(amount);

Rule مربوط به برداشت در همان Objectی قرار دارد که State را مالک است.

چرا مفید است؟

  • Encapsulation قوی‌تر
  • Business Rule نزدیک State
  • کاهش Anemic Domain Model
  • کاهش Duplication قوانین در Consumerها

مثال Payment

C#
// Ask
if (payment.Status == PaymentStatus.Pending)
{
    payment.Status = PaymentStatus.Succeeded;
}

// Tell
payment.MarkAsSucceeded();

آیا Getter بد است؟

⚠️
خیر. Tell, Don't Ask یک قانون مطلق برای حذف Query نیست. خواندن State برای نمایش، Reporting یا تصمیم‌هایی که متعلق به Object دیگری هستند طبیعی است.

تفاوت Command و Query

گاهی Consumer واقعاً باید سؤال بپرسد. مسئله زمانی است که مرتب State داخلی را Ask می‌کنیم تا Behavior متعلق به همان Object را بیرون از آن پیاده کنیم.

نکته مصاحبه‌ای

🎤
Tell, Don't Ask encourages sending behavior to the object that owns the state instead of extracting its state and implementing its business rules elsewhere.

جمع‌بندی

Object فقط Data Container نیست. اگر Rule مستقیماً به State آن مربوط است، معمولاً Behavior باید نزدیک همان State قرار گیرد.
