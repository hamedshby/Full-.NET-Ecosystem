15.2 — Single Responsibility Principle — SRP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Single Responsibility Principle یا SRP اولین اصل از مجموعه SOLID است. این اصل می‌گوید یک Class باید فقط یک Reason to Change اصلی داشته باشد. یعنی مسئولیت‌های مستقل و نامرتبط نباید داخل یک Class جمع شوند.

💡
تعریف معروف SRP: A class should have only one reason to change. نکته مهم این است که «یک مسئولیت» الزاماً یعنی «یک Method» نیست.

تعریف SRP

برای درک SRP بهتر است به جای پرسیدن «این Class چند کار انجام می‌دهد؟» بپرسیم: این Class به چند دلیل مستقل ممکن است تغییر کند؟

اگر یک Class هم Business Rule داشته باشد، هم Database Code، هم Email ارسال کند و هم Logging انجام دهد، چند منبع تغییر مختلف روی آن اثر می‌گذارند و SRP نقض شده است.

مثال اشتباه

C#
public class PaymentService
{
    public void ProcessPayment(
        PaymentRequest request)
    {
        // Business validation
        if (request.Amount <= 0)
        {
            throw new InvalidOperationException();
        }

        // Fee calculation
        decimal fee =
            request.Amount * 0.01m;

        // Save to database
        using var connection =
            new SqlConnection(
                "connection-string");

        connection.Open();

        // Send email
        using var smtp =
            new SmtpClient();

        smtp.Send(
            "payment@company.com",
            request.CustomerEmail,
            "Payment completed",
            "Your payment was successful.");

        // Logging
        File.AppendAllText(
            "payment-log.txt",
            request.Amount.ToString());
    }
}

این Class چند Responsibility مختلف دارد:

  • Validation
  • Fee Calculation
  • Persistence
  • Notification
  • Logging
بخش Reason to Change
Validation تغییر Business Rules
Fee تغییر قوانین کارمزد
Database تغییر Persistence
Email تغییر Notification Provider
Logging تغییر Logging Infrastructure
⚠️
اینکه همه این کدها به «Payment» مربوط هستند، به این معنی نیست که یک Responsibility دارند. منبع تغییر آن‌ها متفاوت است.

Refactoring

اول Persistence را جدا می‌کنیم:

PaymentService بعد از Refactoring

C#
public class PaymentService
{
    private readonly IPaymentRepository
        _repository;

    private readonly IFeeCalculator
        _feeCalculator;

    private readonly IPaymentNotifier
        _notifier;

    public PaymentService(
        IPaymentRepository repository,
        IFeeCalculator feeCalculator,
        IPaymentNotifier notifier)
    {
        _repository = repository;
        _feeCalculator = feeCalculator;
        _notifier = notifier;
    }

    public async Task ProcessAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        if (request.Amount <= 0)
        {
            throw new InvalidOperationException(
                "Amount must be greater than zero.");
        }

        decimal fee =
            _feeCalculator.Calculate(
                request.Amount);

        var payment =
            new Payment(
                request.Amount,
                fee,
                request.CustomerEmail);

        await _repository.SaveAsync(
            payment,
            cancellationToken);

        await _notifier.NotifySuccessAsync(
            payment,
            cancellationToken);
    }
}

اکنون PaymentService مسئول Orchestration مربوط به Use Case پرداخت است. Persistence، Fee Calculation و Notification هر کدام در Component مخصوص خود قرار دارند.

SRP یعنی یک Method؟

خیر. یک Class می‌تواند چند Method داشته باشد، به شرط اینکه همه حول یک Responsibility منسجم باشند.

C#
public class PaymentFeeCalculator
{
    public decimal CalculatePurchaseFee(
        decimal amount)
    {
        return amount * 0.01m;
    }

    public decimal CalculateRefundFee(
        decimal amount)
    {
        return amount * 0.005m;
    }

    public decimal CalculateSettlementFee(
        decimal amount)
    {
        return amount * 0.002m;
    }
}

این Class سه Method دارد، اما هر سه درباره یک Responsibility هستند: محاسبه Fee.

مثال واقعی در Payment System

فرض کنید Purchase Service باید Transaction را Validate کند، ذخیره کند و Event منتشر کند. نسخه ضعیف ممکن است همه چیز را داخل یک Class قرار دهد:

C#
public class PurchaseService
{
    public async Task PurchaseAsync(
        PurchaseRequest request)
    {
        // Validation

        // Create transaction

        // SQL insert

        // Publish RabbitMQ event

        // Logging
    }
}

با رشد سیستم، این Class به دلایل مختلف تغییر می‌کند. راه بهتر این است که Responsibilityها جدا شوند:

C#
public interface IPurchaseValidator
{
    void Validate(
        PurchaseRequest request);
}

public interface ITransactionRepository
{
    Task SaveAsync(
        Transaction transaction,
        CancellationToken cancellationToken);
}

public interface IEventPublisher
{
    Task PublishAsync<T>(
        T message,
        CancellationToken cancellationToken);
}
C#
public class PurchaseService
{
    private readonly IPurchaseValidator
        _validator;

    private readonly ITransactionRepository
        _repository;

    private readonly IEventPublisher
        _publisher;

    public PurchaseService(
        IPurchaseValidator validator,
        ITransactionRepository repository,
        IEventPublisher publisher)
    {
        _validator = validator;
        _repository = repository;
        _publisher = publisher;
    }

    public async Task PurchaseAsync(
        PurchaseRequest request,
        CancellationToken cancellationToken)
    {
        _validator.Validate(request);

        var transaction =
            Transaction.CreatePurchase(
                request.CardNumber,
                request.Amount);

        await _repository.SaveAsync(
            transaction,
            cancellationToken);

        await _publisher.PublishAsync(
            new PaymentCreated(
                transaction.Id,
                transaction.Amount),
            cancellationToken);
    }
}

اگر RabbitMQ با Kafka جایگزین شود، PurchaseService نباید به خاطر این تغییر Infrastructure مجبور به تغییر Business Logic شود. این یکی از نشانه‌های طراحی بهتر بر اساس SRP است.

مزایای SRP

  • Maintainability بهتر
  • Testability بیشتر
  • Coupling کمتر بین مسئولیت‌های نامرتبط
  • Refactoring ساده‌تر
  • کاهش Side Effect هنگام تغییر
  • خوانایی بهتر کد

نشانه‌های نقض SRP

  • Class بسیار بزرگ و شبیه God Class است.
  • Business Logic و Infrastructure Code مخلوط شده‌اند.
  • Constructor تعداد زیادی Dependency نامرتبط دارد.
  • برای تست یک Rule ساده باید Database یا Message Broker را Mock کنیم.
  • یک Class توسط چند نوع تغییر مستقل دائماً ویرایش می‌شود.
⚠️
SRP به معنی ساخت صدها Class کوچک نیست. اگر Responsibilityها واقعاً از یک منبع تغییر می‌آیند، جدا کردن آن‌ها فقط به خاطر کم کردن تعداد خطوط می‌تواند Over-Engineering باشد.

نکته مصاحبه‌ای

🎤
در مصاحبه بهتر است نگویید: «SRP یعنی هر Class فقط یک کار انجام دهد.» پاسخ دقیق‌تر: A class should have only one reason to change. سپس یک مثال از جدا کردن Business Logic از Persistence یا Notification بزنید.

جمع‌بندی 15.2

Single Responsibility Principle می‌گوید هر Class باید Responsibility منسجمی داشته باشد و تا حد امکان تنها یک Reason to Change اصلی داشته باشد. ترکیب Business Logic، Database، Messaging، Notification و Logging در یک Class باعث Coupling بالا و نگهداری سخت‌تر می‌شود.

✅
نکته کلیدی: SRP یعنی Separation by Reason to Change، نه Separation by Number of Methods.
