فصل 7 — Abstraction

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Abstraction یا انتزاع یکی از اصول اصلی Object-Oriented Programming است. Abstraction یعنی مصرف‌کننده بداند یک object چه کاری انجام می‌دهد، بدون اینکه مجبور باشد جزئیات داخلی و نحوهٔ انجام آن کار را بداند.

💡
در Abstraction تمرکز روی What است، نه How. مثلاً کد Business فقط می‌گوید «پرداخت را انجام بده»؛ لازم نیست بداند ارتباط با بانک، ساخت Request، امضای پیام و پردازش Response دقیقاً چگونه انجام می‌شود.

7.1 Abstraction چیست؟

فرض کنید برای پرداخت با درگاه بانکی چنین کدی داریم:

C#
var gateway =
    new BankPaymentGateway();

PaymentResult result =
    gateway.Pay(
        amount: 500_000);

مصرف‌کننده فقط متد Pay را می‌بیند. جزئیاتی مانند ساخت HTTP Request، Authentication، Serialization، Retry و ارتباط با سرویس خارجی می‌توانند پشت این API پنهان شوند.

این همان Abstraction است: ارائهٔ یک مدل ساده و معنادار از یک عملیات پیچیده.

Abstraction و Encapsulation چه تفاوتی دارند؟

Abstraction Encapsulation
تمرکز روی چه چیزی ارائه می‌شود. تمرکز روی محافظت از State و جزئیات داخلی است.
Complexity را از مصرف‌کننده پنهان می‌کند. دسترسی مستقیم و تغییر نامعتبر را محدود می‌کند.
مثلاً IPaymentGateway.Pay() مثلاً Balance { get; private set; }
⚠️
Abstraction فقط به معنی استفاده از abstract یا interface نیست. این دو ابزار زبان برای ساخت abstraction هستند، اما خود مفهوم Abstraction گسترده‌تر از syntax زبان است.

7.2 Abstract Class

Abstract Class کلاسی است که برای ارائهٔ یک Base Type عمومی طراحی شده و نمی‌توان مستقیماً از آن instance ساخت. این class می‌تواند هم رفتار ناقص و قابل‌تخصصی‌سازی و هم رفتار کامل و مشترک داشته باشد.

abstract class

C#
public abstract class Payment
{
    public decimal Amount { get; }

    protected Payment(decimal amount)
    {
        Amount = amount;
    }
}

نمی‌توان مستقیماً چنین کاری انجام داد:

C#
// Compile Error
// var payment =
//     new Payment(500_000);

باید یک class واقعی‌تر از آن ارث ببرد:

C#
public class CardPayment
    : Payment
{
    public CardPayment(
        decimal amount)
        : base(amount)
    {
    }
}

Abstract Method

Abstract Method فقط قرارداد Method را مشخص می‌کند و implementation ندارد. Derived Class موظف است آن را override کند.

C#
public abstract class Payment
{
    public decimal Amount { get; }

    protected Payment(decimal amount)
    {
        Amount = amount;
    }

    public abstract PaymentResult Process();
}
C#
public class CardPayment
    : Payment
{
    public CardPayment(
        decimal amount)
        : base(amount)
    {
    }

    public override PaymentResult Process()
    {
        Console.WriteLine(
            "Processing card payment");

        return new PaymentResult(true);
    }
}

Concrete Method

Abstract Class می‌تواند Method معمولی با implementation کامل نیز داشته باشد. این رفتار می‌تواند بین تمام Derived Classها مشترک باشد.

C#
public abstract class Payment
{
    public decimal Amount { get; }

    protected Payment(decimal amount)
    {
        Amount = amount;
    }

    public abstract PaymentResult Process();

    public void ValidateAmount()
    {
        if (Amount <= 0)
        {
            throw new InvalidOperationException(
                "Amount must be greater than zero.");
        }
    }
}

Process() رفتار abstract است، اما ValidateAmount() یک Concrete Method با implementation مشترک است.

Abstract Property

Property نیز می‌تواند abstract باشد. Base Class فقط اعلام می‌کند Derived Class باید آن را ارائه کند.

C#
public abstract class Payment
{
    public abstract string ProviderName
    {
        get;
    }

    public abstract PaymentResult Process();
}
C#
public class CardPayment
    : Payment
{
    public override string ProviderName
        => "Bank Gateway";

    public override PaymentResult Process()
    {
        return new PaymentResult(true);
    }
}

Abstract Class می‌تواند State داشته باشد

C#
public abstract class Payment
{
    protected Payment(
        Guid transactionId,
        decimal amount)
    {
        TransactionId = transactionId;
        Amount = amount;
    }

    public Guid TransactionId { get; }

    public decimal Amount { get; }

    public abstract PaymentResult Process();
}

این ویژگی زمانی مفید است که typeهای مختلف واقعاً یک Base Concept مشترک با State و رفتار مشترک داشته باشند.

7.3 Interface

Interface یک قرارداد را تعریف می‌کند. مصرف‌کننده می‌تواند به جای وابستگی به یک Concrete Class، به این قرارداد وابسته شود.

تعریف Interface

C#
public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(
        decimal amount,
        CancellationToken cancellationToken);
}

این interface نمی‌گوید پرداخت چگونه انجام شود؛ فقط می‌گوید هر Payment Gateway باید چنین عملیاتی ارائه دهد.

پیاده‌سازی Interface

C#
public class MellatPaymentGateway
    : IPaymentGateway
{
    public async Task<PaymentResult> PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        // Call Mellat Bank API

        await Task.Delay(
            100,
            cancellationToken);

        return new PaymentResult(true);
    }
}

کد Business می‌تواند فقط IPaymentGateway را بشناسد:

C#
public class PaymentService
{
    private readonly IPaymentGateway
        _paymentGateway;

    public PaymentService(
        IPaymentGateway paymentGateway)
    {
        _paymentGateway =
            paymentGateway;
    }

    public Task<PaymentResult> PayAsync(
        decimal amount,
        CancellationToken cancellationToken)
    {
        return _paymentGateway.PayAsync(
            amount,
            cancellationToken);
    }
}

PaymentService نمی‌داند پشت interface درگاه ملت، سامان یا یک Fake Gateway برای تست قرار دارد. این وابستگی به abstraction، Coupling را کاهش می‌دهد.

چند Interface برای یک Class

C# اجازهٔ Multiple Class Inheritance نمی‌دهد، اما یک class می‌تواند چند interface را implement کند.

C#
public interface IPaymentGateway
{
    Task PayAsync();
}

public interface IHealthCheck
{
    bool IsHealthy();
}

public interface ITransactionLogger
{
    void Log(string transactionId);
}
C#
public class BankGateway
    : IPaymentGateway,
      IHealthCheck,
      ITransactionLogger
{
    public Task PayAsync()
    {
        return Task.CompletedTask;
    }

    public bool IsHealthy()
    {
        return true;
    }

    public void Log(
        string transactionId)
    {
        Console.WriteLine(
            transactionId);
    }
}

Explicit Interface Implementation

گاهی دو interface عضو هم‌نام دارند، یا نمی‌خواهیم یک عضو interface مستقیماً از طریق Concrete Type دیده شود. در این حالت Explicit Interface Implementation مفید است.

C#
public interface ICustomerNotifier
{
    void Send();
}

public interface IAdminNotifier
{
    void Send();
}

public class NotificationService
    : ICustomerNotifier,
      IAdminNotifier
{
    void ICustomerNotifier.Send()
    {
        Console.WriteLine(
            "Send customer notification");
    }

    void IAdminNotifier.Send()
    {
        Console.WriteLine(
            "Send admin notification");
    }
}

برای فراخوانی باید object را از طریق interface مناسب ببینیم:

C#
var service =
    new NotificationService();

ICustomerNotifier customerNotifier =
    service;

customerNotifier.Send();

IAdminNotifier adminNotifier =
    service;

adminNotifier.Send();
💡
Explicit Interface Implementation زمانی مفید است که یک class چند نقش متفاوت دارد و می‌خواهیم رفتار هر نقش فقط از طریق interface مربوط به همان نقش قابل دسترسی باشد.

7.4 Abstract Class vs Interface

Abstract Class Interface
برای یک Base Type واقعی و مشترک مناسب است. برای تعریف Capability یا Contract مناسب است.
می‌تواند Instance State داشته باشد. برای نگهداری Instance State طراحی نشده است.
می‌تواند Constructor داشته باشد. Constructor برای ساخت instance ندارد.
می‌تواند Field داشته باشد. Instance Field ندارد.
می‌تواند abstract و concrete member داشته باشد. Contract را تعریف می‌کند و در C# مدرن می‌تواند بعضی memberها implementation پیش‌فرض داشته باشد.
یک class فقط از یک class مستقیم ارث می‌برد. یک class می‌تواند چند interface را implement کند.
رابطهٔ Is-A قوی‌تر است. بیشتر بیانگر «این type این قابلیت/قرارداد را دارد» است.

مثال Abstract Class

C#
public abstract class Payment
{
    protected Payment(
        decimal amount)
    {
        Amount = amount;
    }

    public decimal Amount { get; }

    public abstract void Process();

    protected void Validate()
    {
        if (Amount <= 0)
            throw new InvalidOperationException();
    }
}

مثال Interface

C#
public interface IPaymentProcessor
{
    Task<PaymentResult> ProcessAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}

در مثال اول typeها یک Base Concept و State مشترک دارند. در مثال دوم فقط می‌خواهیم Contract پردازش پرداخت را تعریف کنیم.

آیا Interface همیشه فقط Method Signature دارد؟

در C# مدرن Interfaceها قابلیت‌هایی مانند Default Interface Members و اعضای static نیز دارند. بنابراین تعریف قدیمی «Interface هیچ implementationای ندارد» دیگر به‌صورت مطلق صحیح نیست. با این حال، نقش اصلی Interface همچنان تعریف یک قرارداد و abstraction بین اجزای سیستم است.

C#
public interface ILogger
{
    void Log(string message);

    void LogInfo(string message)
    {
        Log($"INFO: {message}");
    }
}
⚠️
وجود Default Implementation به این معنی نیست که Interface را به یک Base Class بزرگ تبدیل کنیم. Interface بهتر است همچنان یک قرارداد منسجم و کوچک باقی بماند.

7.5 چه زمانی Interface استفاده کنیم؟

Interface زمانی بسیار مفید است که بخواهیم کد مصرف‌کننده از implementation واقعی مستقل باشد.

1. چند Implementation داریم

C#
public interface IPaymentGateway
{
    Task PayAsync();
}

public class MellatGateway
    : IPaymentGateway
{
    public Task PayAsync()
        => Task.CompletedTask;
}

public class SamanGateway
    : IPaymentGateway
{
    public Task PayAsync()
        => Task.CompletedTask;
}

2. Dependency Injection

C#
services.AddScoped
    <IPaymentGateway,
     MellatGateway>();

Business Service به interface وابسته می‌شود و DI Container implementation واقعی را inject می‌کند.

3. تست‌پذیری

C#
public class FakePaymentGateway
    : IPaymentGateway
{
    public Task PayAsync()
    {
        return Task.CompletedTask;
    }
}

در Unit Test می‌توان implementation واقعی شبکه را با Fake یا Mock جایگزین کرد.

4. جداکردن لایه‌ها

در معماری‌هایی مانند Clean Architecture، Application Layer می‌تواند Contract را تعریف کند و Infrastructure Layer implementation مربوط به Database، Message Broker یا External API را ارائه دهد.

    │
    │ depends on
    ▼

MellatPaymentGateway

5. وقتی یک Capability مستقل داریم

C#
public interface ICacheable
{
    string CacheKey { get; }
}

public interface IAuditable
{
    DateTimeOffset CreatedAt { get; }
}

یک type می‌تواند چند capability مستقل را هم‌زمان داشته باشد، بدون اینکه مجبور به ساخت hierarchy پیچیدهٔ Inheritance شویم.

Interface را فقط برای Mock نسازید

Testability مزیت مهم Interface است، اما تنها دلیل ساخت interface نباید «شاید روزی Mock لازم شود» باشد. Interface باید یک abstraction معنادار در طراحی ایجاد کند.

🎯
Interface خوب معمولاً یک نقش یا capability واضح دارد؛ مانند IPaymentGateway، IMessagePublisher یا IClock. نام و اعضای آن باید نشان دهند مصرف‌کننده دقیقاً به چه قراردادی وابسته است.

7.6 Interface Segregation در طراحی واقعی

Interface Segregation Principle یا ISP یکی از اصول SOLID است و می‌گوید: Client نباید مجبور باشد به Methodهایی وابسته شود که به آن‌ها نیاز ندارد. به زبان ساده، چند interface کوچک و متمرکز معمولاً بهتر از یک interface بزرگ و همه‌کاره هستند.

طراحی ضعیف: Fat Interface

C#
public interface IPaymentService
{
    Task<PaymentResult> PayAsync(
        decimal amount);

    Task RefundAsync(
        string transactionId);

    Task SendSmsAsync(
        string mobile);

    Task SaveReportAsync();

    Task ExportExcelAsync();

    Task ClearCacheAsync();
}

این interface چند مسئولیت کاملاً متفاوت دارد. یک class که فقط Payment Processing انجام می‌دهد مجبور است به عملیات SMS، Excel و Cache نیز وابسته شود.

تفکیک Interfaceها

C#
public interface IPaymentProcessor
{
    Task<PaymentResult> PayAsync(
        decimal amount);
}

public interface IRefundProcessor
{
    Task RefundAsync(
        string transactionId);
}

public interface INotificationSender
{
    Task SendAsync(
        string mobile,
        string message);
}

public interface IReportExporter
{
    Task ExportAsync();
}

حالا هر Client فقط contract موردنیاز خودش را دریافت می‌کند.

مثال واقعی در Payment System

فرض کنید یک API فقط وظیفهٔ انجام تراکنش خرید را دارد:

C#
public class PurchaseService
{
    private readonly IPaymentProcessor
        _paymentProcessor;

    public PurchaseService(
        IPaymentProcessor paymentProcessor)
    {
        _paymentProcessor =
            paymentProcessor;
    }

    public Task<PaymentResult> PurchaseAsync(
        decimal amount)
    {
        return _paymentProcessor.PayAsync(
            amount);
    }
}

PurchaseService فقط چیزی را می‌بیند که واقعاً لازم دارد. عملیات Refund، Report و Notification جزء dependencyهای آن نیستند.

یک Class می‌تواند چند Interface کوچک را پیاده‌سازی کند

C#
public class BankPaymentService
    : IPaymentProcessor,
      IRefundProcessor
{
    public Task<PaymentResult> PayAsync(
        decimal amount)
    {
        // Process payment

        return Task.FromResult(
            new PaymentResult(true));
    }

    public Task RefundAsync(
        string transactionId)
    {
        // Process refund

        return Task.CompletedTask;
    }
}

با اینکه یک concrete class هر دو قابلیت را دارد، Clientها مجبور نیستند به هر دو capability وابسته شوند.

ISP و Dependency Injection

Interfaceهای کوچک باعث می‌شوند Constructor هر Service دقیق‌تر نشان دهد آن Service واقعاً به چه قابلیت‌هایی نیاز دارد.

C#
public class RefundService
{
    private readonly IRefundProcessor
        _refundProcessor;

    public RefundService(
        IRefundProcessor refundProcessor)
    {
        _refundProcessor =
            refundProcessor;
    }
}

این طراحی بهتر از inject کردن یک interface عظیم است که ده‌ها Method غیرمرتبط دارد.

نشانه‌های Interface بیش از حد بزرگ

  • بعضی implementationها مجبورند Methodهایی را با NotSupportedException پیاده‌سازی کنند.
  • Client فقط از یک یا دو Method از یک interface بزرگ استفاده می‌کند.
  • تغییر یک قابلیت باعث rebuild یا تغییر Clientهای نامرتبط می‌شود.
  • نام interface بسیار عمومی است؛ مانند IManager یا IService.
  • Interface چند مسئولیت متفاوت مانند Payment، Logging، Cache و Reporting را هم‌زمان دارد.
⚠️
Interface Segregation به معنی ساختن یک interface برای تک‌تک Methodها نیست. هدف، ساخت contractهای cohesive و متناسب با نیاز Clientهاست؛ نه خردکردن افراطی طراحی.

مثال کامل Abstraction در Payment Processing

C#
public record PaymentRequest(
    string CardNumber,
    decimal Amount);

public record PaymentResult(
    bool IsSuccess,
    string? TransactionId = null);

public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}

public class BankPaymentGateway
    : IPaymentGateway
{
    public async Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        // Authentication
        // Create bank request
        // Send HTTP request
        // Parse response

        await Task.Delay(
            100,
            cancellationToken);

        return new PaymentResult(
            true,
            Guid.NewGuid().ToString());
    }
}

public class PaymentService
{
    private readonly IPaymentGateway
        _gateway;

    public PaymentService(
        IPaymentGateway gateway)
    {
        _gateway = gateway;
    }

    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        if (request.Amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(request.Amount));
        }

        return _gateway.PayAsync(
            request,
            cancellationToken);
    }
}

در این طراحی PaymentService به جزئیات بانک وابسته نیست. فقط contract مربوط به IPaymentGateway را می‌شناسد.

C#
services.AddScoped
    <IPaymentGateway,
     BankPaymentGateway>();

services.AddScoped
    <PaymentService>();

اگر فردا بانک یا Provider تغییر کند، می‌توان implementation جدیدی از IPaymentGateway ساخت. Business Service همچنان با همان abstraction کار می‌کند و نیازی ندارد جزئیات Provider جدید را بشناسد.

جمع‌بندی Abstract Class و Interface

نیاز طراحی انتخاب محتمل
Base Concept واقعی با State مشترک Abstract Class
رفتار مشترک و قابل reuse میان Derived Typeها Abstract Class
تعریف Contract بین لایه‌ها Interface
چند implementation قابل جایگزینی Interface
یک class با چند capability مستقل چند Interface
Dependency Injection و جداکردن Infrastructure Interface معمولاً مناسب است.
✅
خلاصه: Abstraction جزئیات غیرضروری را از مصرف‌کننده پنهان می‌کند و یک قرارداد ساده و معنادار ارائه می‌دهد. Abstract Class زمانی مفید است که typeها واقعاً Base State و رفتار مشترک دارند. Interface برای تعریف contract، جایگزین‌کردن implementationها و کاهش Coupling بسیار مناسب است. با Interface Segregation نیز contractها را کوچک، cohesive و متناسب با نیاز Client طراحی می‌کنیم.
