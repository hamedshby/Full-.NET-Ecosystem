OOP و Layered Architecture

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۲
⏱️ زمان مطالعه: ۲۰ دقیقه
👤 تیم فنی

فرض کنید در یک فروشگاه اینترنتی، کاربر روی دکمهٔ «ثبت سفارش» کلیک می‌کند. برنامه باید ورودی را اعتبارسنجی کند، مجموع مبلغ را به دست آورد، سفارش را ثبت کند و یک پاسخ مناسب برگرداند. اگر همهٔ این کارها داخل یک Controller نوشته شوند، قابلیت کار می‌کند؛ اما با اضافه‌شدن تخفیف، انبار، پرداخت و ارسال، همان Controller به بخشی بزرگ و شکننده تبدیل می‌شود.

💡
Layered Architecture سیستم را بر اساس نوع مسئولیت به چند Layer تقسیم می‌کند. OOP نیز داخل هر Layer کمک می‌کند مسئولیت‌ها را میان Objectهای همکار توزیع کنیم و جزئیات را پشت Interfaceها پنهان نگه داریم.

ابتدا مشکل را ببینیم: همه‌چیز در یک Class

C#
[HttpPost]
public IActionResult PlaceOrder(PlaceOrderRequest request)
{
    if (request.Items.Count == 0)
        return BadRequest("Order must contain an item.");

    decimal total = request.Items.Sum(item => item.Price * item.Quantity);

    using var connection = new SqlConnection(_connectionString);
    connection.Execute(
        "INSERT INTO Orders (Id, CustomerId, Total) VALUES (@Id, @CustomerId, @Total)",
        new { Id = Guid.NewGuid(), request.CustomerId, Total = total });

    return Ok();
}

رفتار این کد ساده است: درخواست HTTP را می‌گیرد، Business Rule را اجرا می‌کند و مستقیم در Database می‌نویسد. مشکل این است که سه دلیل متفاوت برای تغییر در یک Method جمع شده‌اند:

  • تغییر قرارداد HTTP یا شکل پاسخ؛
  • تغییر Ruleهای ثبت سفارش و محاسبهٔ مبلغ؛
  • تغییر روش ذخیره‌سازی یا Database.

این ترکیب، آزمودن Ruleها را نیز دشوار می‌کند؛ چون برای بررسی محاسبهٔ مبلغ باید HTTP و Database را هم وارد Test کنیم. هدف Layering جداکردن همین دلایل تغییر است.

Layer چیست؟

Layer یک مرز منطقی است که مجموعه‌ای از Classها با مسئولیت مشابه را کنار هم قرار می‌دهد. برای نمونه، Classهایی که ورودی HTTP را مدیریت می‌کنند در Presentation Layer و Classهایی که با Database ارتباط دارند در Data Access یا Infrastructure Layer قرار می‌گیرند.

Layer با Tier یکسان نیست. Layer مرز منطقی در Code است؛ Tier مرز فیزیکی اجرای برنامه است. یک برنامه می‌تواند چهار Layer داشته باشد، اما همهٔ آن‌ها در یک Process و روی یک Server اجرا شوند. بنابراین ساختن چند Class Library به‌تنهایی برنامه را چند Tier نمی‌کند.

Layerهای رایج در یک برنامهٔ .NET

Layer مسئولیت اصلی نمونه اجزا چه چیزی نباید بداند؟
Presentation دریافت ورودی و ساخت خروجی برای کاربر یا Client Controller، Endpoint، View Model جزئیات SQL و Ruleهای اصلی Business
Application یا Business هماهنگ‌کردن Use Case و اجرای جریان برنامه PlaceOrderService، Command، DTO جزئیات HTTP و پیاده‌سازی Database
Domain نگهداری State و Ruleهای اصلی Business Order، OrderItem، Value Object Framework، UI و Database
Data Access یا Infrastructure ارتباط با منابع بیرونی و جزئیات فنی EF Core، Repository، Email Gateway نحوهٔ نمایش پاسخ به کاربر
⚠️
نام و تعداد Layerها قانون ثابت نیست. در یک برنامهٔ ساده ممکن است Business و Domain یک Layer باشند. مهم‌تر از نام Projectها، روشن‌بودن مسئولیت و کنترل Dependencyها است.

OOP در این معماری چه نقشی دارد؟

Layered Architecture دربارهٔ سازمان‌دهی اجزای بزرگ سیستم است؛ OOP دربارهٔ طراحی Objectها و همکاری میان آن‌ها. این دو در سطح‌های متفاوت عمل می‌کنند و مکمل یکدیگرند:

  • Encapsulation: هر Object از State معتبر خود محافظت می‌کند؛ مثلاً Order اجازه نمی‌دهد Item با تعداد صفر اضافه شود.
  • Abstraction: یک Interface مانند IOrderRepository نیاز Application Layer را بیان می‌کند، بدون آنکه SQL یا EF Core را آشکار کند.
  • Polymorphism: Application Service می‌تواند با پیاده‌سازی واقعی Repository یا یک Fake در Test کار کند.
  • Composition: در Composition Root، Objectهای لازم ساخته و به یکدیگر متصل می‌شوند.

وجود class و interface به‌تنهایی نشانهٔ طراحی خوب نیست. اگر Controller تمام Ruleها را اجرا کند و فقط برای ذخیره‌سازی یک Repository صدا بزند، سیستم هنوز رفتار Business را درست مدل نکرده است.

مثال مرحله‌به‌مرحله: ثبت سفارش

گام اول: Domain از اعتبار State محافظت می‌کند

C# — Domain
public sealed class Order
{
    private readonly List<OrderItem> _items = [];

    public Guid Id { get; } = Guid.NewGuid();
    public Guid CustomerId { get; }
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();
    public decimal Total => _items.Sum(item => item.Subtotal);

    public Order(Guid customerId)
    {
        if (customerId == Guid.Empty)
            throw new ArgumentException("Customer is required.", nameof(customerId));

        CustomerId = customerId;
    }

    public void AddItem(Guid productId, decimal unitPrice, int quantity)
    {
        if (productId == Guid.Empty)
            throw new ArgumentException("Product is required.", nameof(productId));
        if (unitPrice <= 0)
            throw new ArgumentOutOfRangeException(nameof(unitPrice));
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _items.Add(new OrderItem(productId, unitPrice, quantity));
    }
}

public sealed record OrderItem(Guid ProductId, decimal UnitPrice, int Quantity)
{
    public decimal Subtotal => UnitPrice * Quantity;
}

Order یک Data Container منفعل نیست. Collection داخلی قابل‌تغییر را بیرون نمی‌دهد و افزودن Item فقط از مسیر AddItem انجام می‌شود. در نتیجه Ruleهای قیمت و تعداد در هر ورودی برنامه یکسان اجرا می‌شوند. برای دو Item با قیمت ۱۰۰ و تعداد ۲، مقدار Total برابر ۲۰۰ خواهد بود.

گام دوم: Application Layer جریان Use Case را هماهنگ می‌کند

Use Case یک هدف مشخص کاربر از سیستم است؛ مانند «ثبت سفارش». Application Service ورودی این Use Case را می‌گیرد، Objectهای Domain را به کار می‌اندازد و ذخیره‌سازی را درخواست می‌کند.

C# — Application
public sealed record PlaceOrderItem(
    Guid ProductId,
    decimal UnitPrice,
    int Quantity);

public sealed record PlaceOrderCommand(
    Guid CustomerId,
    IReadOnlyCollection<PlaceOrderItem> Items);

public interface IOrderRepository
{
    Task AddAsync(Order order, CancellationToken cancellationToken);
}

public sealed class PlaceOrderService(IOrderRepository orders)
{
    public async Task<Guid> HandleAsync(
        PlaceOrderCommand command,
        CancellationToken cancellationToken)
    {
        if (command.Items.Count == 0)
            throw new InvalidOperationException("Order must contain an item.");

        var order = new Order(command.CustomerId);

        foreach (var item in command.Items)
            order.AddItem(item.ProductId, item.UnitPrice, item.Quantity);

        await orders.AddAsync(order, cancellationToken);
        return order.Id;
    }
}

این Service نمی‌داند درخواست از HTTP آمده یا یک Background Job؛ همچنین نمی‌داند داده با EF Core ذخیره می‌شود یا روش دیگری. Interface فقط قابلیتی را بیان می‌کند که Use Case نیاز دارد: افزودن یک سفارش.

گام سوم: Infrastructure جزئیات ذخیره‌سازی را پیاده‌سازی می‌کند

C# — Infrastructure
public sealed class EfOrderRepository(AppDbContext dbContext)
    : IOrderRepository
{
    public async Task AddAsync(
        Order order,
        CancellationToken cancellationToken)
    {
        await dbContext.Orders.AddAsync(order, cancellationToken);
        await dbContext.SaveChangesAsync(cancellationToken);
    }
}

EF Core یک جزئیات فنی است و در این طراحی داخل Infrastructure باقی می‌ماند. تغییر این Class نباید Rule محاسبهٔ مبلغ یا قرارداد HTTP را تغییر دهد.

گام چهارم: Presentation ورودی و خروجی HTTP را مدیریت می‌کند

C# — Presentation
[ApiController]
[Route("api/orders")]
public sealed class OrdersController(PlaceOrderService service) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> PlaceOrder(
        PlaceOrderRequest request,
        CancellationToken cancellationToken)
    {
        var command = new PlaceOrderCommand(
            request.CustomerId,
            request.Items
                .Select(item => new PlaceOrderItem(
                    item.ProductId,
                    item.UnitPrice,
                    item.Quantity))
                .ToArray());

        var orderId = await service.HandleAsync(command, cancellationToken);

        return CreatedAtAction(
            nameof(GetById),
            new { id = orderId },
            new { id = orderId });
    }

    [HttpGet("{id:guid}")]
    public IActionResult GetById(Guid id) => Ok();
}

Controller اکنون نقش مترجم مرز HTTP را دارد: Request را به Command تبدیل می‌کند و نتیجه را با Status Code مناسب برمی‌گرداند. Business Rule و Code مربوط به Database در آن وجود ندارد.

جریان اجرا و جهت Dependency را اشتباه نگیریم

هنگام اجرا، درخواست معمولاً این مسیر را طی می‌کند:

➡️
HTTP Request → Controller → Application Service → Domain Object → Repository Implementation → Database

اما جهت اجرای Methodها الزاماً با Dependency زمان Compile یکسان نیست. PlaceOrderService به IOrderRepository وابسته است، نه به EfOrderRepository. پیاده‌سازی Infrastructure این Interface را اجرا می‌کند و در نقطهٔ شروع برنامه به Service تزریق می‌شود:

C# — Composition Root
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<PlaceOrderService>();

Composition Root محل ساخت و اتصال Dependencyهای اصلی برنامه است؛ در ASP.NET Core معمولاً این اتصال در Program.cs انجام می‌شود. Container فقط Object Graph را می‌سازد و نباید Business Rule را در خود جای دهد.

یک ساختار پیشنهادی برای Solution

Text

│   ├── Orders/Order.cs
│   └── Orders/OrderItem.cs

Folderها و Projectها ابزار نمایش مرزها هستند، نه خود معماری. اگر Store.Domain به WebApi یا EF Core Reference بدهد، نام Domain روی Project نمی‌تواند آن Dependency اشتباه را جبران کند.

Dependencyهای مجاز را چگونه کنترل کنیم؟

در شکل کلاسیک Layered Architecture، هر Layer معمولاً فقط Layer پایین‌تر را صدا می‌زند. در طراحی‌های جدیدتر می‌توان با Dependency Inversion، Interface را در Layer نیازمند قرار داد تا جزئیات به Policy وابسته شوند. برای مثال بالا یک قاعدهٔ عملی چنین است:

  • Domain به Projectهای دیگر وابسته نیست.
  • Application به Domain وابسته است.
  • Infrastructure برای پیاده‌سازی Interfaceها به Application و Domain وابسته است.
  • WebApi ورودی برنامه و Composition Root است و اجزا را به هم متصل می‌کند.

این قاعده زمینه را برای درس بعدی، یعنی Clean Architecture، فراهم می‌کند؛ اما هر Layered Architecture لزوماً Clean Architecture نیست. در مدل سنتی ممکن است Business Layer مستقیماً به Data Access Layer وابسته باشد.

تست‌پذیری حاصل از جداسازی

چون Application Service به Abstraction وابسته است، می‌توان Use Case را بدون Database واقعی آزمود:

C# — xUnit
[Fact]
public async Task HandleAsync_Saves_order_and_returns_its_id()
{
    var repository = new FakeOrderRepository();
    var service = new PlaceOrderService(repository);
    var command = new PlaceOrderCommand(
        Guid.NewGuid(),
        [new PlaceOrderItem(Guid.NewGuid(), 100_000m, 2)]);

    var orderId = await service.HandleAsync(command, CancellationToken.None);

    Assert.NotNull(repository.SavedOrder);
    Assert.Equal(orderId, repository.SavedOrder.Id);
    Assert.Equal(200_000m, repository.SavedOrder.Total);
}

private sealed class FakeOrderRepository : IOrderRepository
{
    public Order? SavedOrder { get; private set; }

    public Task AddAsync(Order order, CancellationToken cancellationToken)
    {
        SavedOrder = order;
        return Task.CompletedTask;
    }
}

این Test سه رفتار قابل‌مشاهده را بررسی می‌کند: سفارش به Repository تحویل داده شده، شناسهٔ برگشتی همان شناسهٔ سفارش است و مجموع مبلغ درست محاسبه شده است. چون SQL و HTTP وارد Test نشده‌اند، Test سریع و متمرکز باقی می‌ماند. خود EfOrderRepository را باید جداگانه با Integration Test بررسی کرد.

اشتباهات رایج

۱. عبور مستقیم Presentation از روی Business Layer

اگر Controller مستقیماً DbContext را صدا بزند، هر Endpoint می‌تواند Ruleها را به شکل متفاوتی اجرا کند. Controller باید Use Case را فراخوانی کند، نه اینکه خودش Use Case باشد.

۲. ساختن Classهای عبوری بدون مسئولیت

گاهی Controller، Service و Repository فقط همان DTO را بدون تصمیم یا تبدیل به Layer بعدی می‌فرستند. این حالت Layerهای بیشتری می‌سازد، اما جداسازی مفیدی ایجاد نمی‌کند. هر مرز باید دلیل تغییر مشخصی داشته باشد.

۳. نشت Entity مربوط به Persistence به همهٔ Layerها

برگرداندن مستقیم Entityهای EF Core از API باعث می‌شود تغییر Mapping یا رابطه‌های Database روی قرارداد API اثر بگذارد. DTO مرزی را زمانی استفاده کنید که قرارداد بیرونی با مدل داخلی تفاوت دارد؛ نه صرفاً برای کپی مکانیکی همهٔ Propertyها.

۴. Interface برای هر Class

Interface زمانی ارزش دارد که یک مرز، چند رفتار جایگزین یا نیاز واقعی به جداسازی وجود داشته باشد. ساختن IOrderService فقط چون Classی به نام OrderService داریم، بدون این نیازها Abstraction مفیدی ایجاد نمی‌کند.

۵. قرار دادن Business Rule در Repository

Repository مسئول Persistence است. Ruleهایی مانند «سفارش خالی مجاز نیست» یا «تعداد باید مثبت باشد» به Domain یا Use Case تعلق دارند و نباید فقط هنگام ذخیره‌سازی اجرا شوند.

۶. وابستگی چرخه‌ای میان Projectها

اگر Application به Infrastructure و Infrastructure نیز به Application وابسته شود، مرزها مبهم می‌شوند و Build نیز ممکن است با Circular Reference روبه‌رو شود. Interfaceها را در سمت نیاز قرار دهید و اتصال را در Composition Root انجام دهید.

چه زمانی Layered Architecture انتخاب مناسبی است؟

این سبک برای Business Applicationهای معمول، APIهای سازمانی و سیستم‌هایی که UI، Rule و Persistence قابل‌تفکیک دارند، نقطهٔ شروع قابل‌فهمی است. اعضای تیم به‌سادگی می‌توانند محل هر نوع Code را پیدا کنند و بخش‌های اصلی را مستقل‌تر Test کنند.

برای یک ابزار بسیار کوچک یا CRUD ساده، چهار Project و تعداد زیادی Mapping ممکن است هزینه‌ای بیشتر از منفعت ایجاد کند. در سوی دیگر، اگر سیستم Domain پیچیده، چند روش ورودی یا Integrationهای متعدد دارد، مرزهای دقیق‌تر مانند Clean Architecture یا سازمان‌دهی Feature-based می‌توانند مناسب‌تر باشند. معماری باید متناسب با مسئله رشد کند.

چک‌لیست طراحی یک Feature

  1. Use Case را با یک فعل روشن نام‌گذاری کنید؛ مانند PlaceOrder.
  2. Business Ruleها و State معتبر را در Domain Objectهای مناسب قرار دهید.
  3. هماهنگی مراحل Use Case را به Application Service بسپارید.
  4. جزئیات HTTP را در Presentation و جزئیات فنی را در Infrastructure نگه دارید.
  5. برای Dependency بیرونی، نیاز Layer مصرف‌کننده را با یک Interface کوچک بیان کنید.
  6. Dependencyها را در Composition Root متصل کنید.
  7. Ruleهای Domain را با Unit Test و Adapterهای فنی را با Integration Test بررسی کنید.

تمرین

به مثال ثبت سفارش، قابلیت بررسی موجودی را اضافه کنید. یک IInventoryGateway با عملیاتی کوچک مانند IsAvailableAsync تعریف کنید، آن را به Application Service تزریق کنید و در صورت نبود موجودی، از ثبت سفارش جلوگیری کنید. سپس با یک Fake دو حالت «موجود» و «ناموجود» را Test کنید.

🎯
پیش از نوشتن Code تصمیم بگیرید Interface باید در کدام Layer قرار گیرد. معیار پاسخ این است: کدام Layer برای اجرای Use Case به این قابلیت نیاز دارد؟

جمع‌بندی

Layered Architecture سیستم را با مرزهای مسئولیتی سازمان می‌دهد و OOP رفتار هر بخش و قرارداد همکاری میان بخش‌ها را شکل می‌دهد. Presentation با ورودی و خروجی سروکار دارد، Application جریان Use Case را هماهنگ می‌کند، Domain از Ruleها و State معتبر محافظت می‌کند و Infrastructure جزئیات فنی را در خود نگه می‌دارد. نتیجهٔ مطلوب فقط Projectهای بیشتر نیست؛ نتیجه باید تغییرات محلی‌تر، Dependencyهای روشن‌تر و Testهای ساده‌تر باشد.
