🏭 Creational Design Patterns

Builder

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۱۵
⏱️ زمان مطالعه: ۱۲ دقیقه
👤 تیم فنی

Builder یکی از Creational Design Patternهای کلاسیک GoF است. این Pattern زمانی استفاده می‌شود که ساخت یک Object پیچیده شامل چند مرحله، تعداد زیادی Parameter، مقادیر Optional یا Validation باشد.

💡
Builder فرآیند ساخت Object را مرحله‌به‌مرحله می‌کند و باعث می‌شود Creation Code خواناتر و قابل کنترل‌تر باشد.

مسئله در Payment System

فرض کنید برای ارسال درخواست پرداخت باید اطلاعات زیادی آماده کنیم:

  • Amount
  • MerchantId
  • OrderId
  • CallbackUrl
  • MobileNumber
  • Description
  • Metadata
  • RetryCount

Constructor طولانی

var request =

ساخت Builder

C#
public class PaymentRequestBuilder
{
    private decimal _amount;
    private string _merchantId = string.Empty;
    private string _orderId = string.Empty;
    private string? _callbackUrl;
    private string? _mobileNumber;
    private string? _description;
    private readonly Dictionary<string, string>
        _metadata = new();
    private int _retryCount;

    public PaymentRequestBuilder
        WithAmount(decimal amount)
    {
        _amount = amount;
        return this;
    }

    public PaymentRequestBuilder
        ForMerchant(string merchantId)
    {
        _merchantId = merchantId;
        return this;
    }

    public PaymentRequestBuilder
        WithOrderId(string orderId)
    {
        _orderId = orderId;
        return this;
    }

    public PaymentRequestBuilder
        WithCallbackUrl(string callbackUrl)
    {
        _callbackUrl = callbackUrl;
        return this;
    }

    public PaymentRequestBuilder
        WithMobileNumber(string mobileNumber)
    {
        _mobileNumber = mobileNumber;
        return this;
    }

    public PaymentRequestBuilder
        WithDescription(string description)
    {
        _description = description;
        return this;
    }

    public PaymentRequestBuilder
        AddMetadata(string key, string value)
    {
        _metadata[key] = value;
        return this;
    }

    public PaymentRequestBuilder
        WithRetryCount(int retryCount)
    {
        _retryCount = retryCount;
        return this;
    }

    public PaymentRequest Build()
    {
        return new PaymentRequest
        {
            Amount = _amount,
            MerchantId = _merchantId,
            OrderId = _orderId,
            CallbackUrl = _callbackUrl,
            MobileNumber = _mobileNumber,
            Description = _description,
            Metadata =
                new Dictionary<string, string>(
                    _metadata),
            RetryCount = _retryCount
        };
    }
}

Validation در Build

C#
public PaymentRequest Build()
{
    if (_amount <= 0)
        throw new InvalidOperationException(
            "Amount must be greater than zero.");

    if (string.IsNullOrWhiteSpace(
        _merchantId))
        throw new InvalidOperationException(
            "MerchantId is required.");

    if (string.IsNullOrWhiteSpace(
        _orderId))
        throw new InvalidOperationException(
            "OrderId is required.");

    return new PaymentRequest
    {
        Amount = _amount,
        MerchantId = _merchantId,
        OrderId = _orderId,
        CallbackUrl = _callbackUrl,
        MobileNumber = _mobileNumber,
        Description = _description,
        Metadata =
            new Dictionary<string, string>(
                _metadata),
        RetryCount = _retryCount
    };
}

Builder کلاسیک و Concrete Builderها

در نسخه کلاسیک GoF، می‌توان یک فرآیند ساخت مشترک داشت اما Representation نهایی برای Providerهای مختلف متفاوت باشد.

C#
public interface IPaymentRequestBuilder
{
    void Reset();

    void SetAmount(decimal amount);

    void SetMerchant(string merchantId);

    void SetOrder(string orderId);

    ProviderPaymentRequest Build();
}

Director چیست؟

در Builder کلاسیک، Director ترتیب مراحل ساخت را مدیریت می‌کند.

C#
public class PaymentRequestDirector
{
    public ProviderPaymentRequest
        BuildStandardPayment(
            IPaymentRequestBuilder builder,
            decimal amount,
            string merchantId,
            string orderId)
    {
        builder.Reset();
        builder.SetAmount(amount);
        builder.SetMerchant(merchantId);
        builder.SetOrder(orderId);

        return builder.Build();
    }
}

⚠️
در پروژه‌های مدرن .NET معمولاً Fluent Builder بدون Director رایج‌تر است. Director زمانی مفید است که چند Recipe استاندارد و تکرارشونده برای Construction داشته باشیم.

Builder در Unit Test

یکی از کاربردهای بسیار خوب Builder ساخت Test Data است.

public class PaymentBuilder
{
    private decimal _amount = 100_000;
    private PaymentStatus _status =
        PaymentStatus.Pending;

    public PaymentBuilder
        WithAmount(decimal amount)
    {
        _amount = amount;
        return this;
    }

    public PaymentBuilder
        WithStatus(PaymentStatus status)
    {
        _status = status;
        return this;
    }

    public Payment Build()
    {
        return Payment.CreateForTest(
            _amount,
            _status);
    }
}

Builder vs Factory

Builder Factory
ساخت مرحله‌به‌مرحله معمولاً ساخت در یک Call
تمرکز بر How to build تمرکز بر What to create
مناسب Object پیچیده مناسب انتخاب Product/Implementation
Optional stepهای متعدد Creation متمرکز

Builder vs Factory Method

Text
Factory Method:
    Which concrete object
    should be created?

Builder:
    How should this complex
    object be built step by step?

Builder vs Abstract Factory

Abstract Factory یک Family از Productهای مرتبط می‌سازد؛ Builder روی فرآیند ساخت یک Product پیچیده تمرکز دارد.

مزایای Builder

  • خوانایی بهتر Creation Code
  • حذف Constructorهای بسیار طولانی
  • مدیریت Parameterهای Optional
  • Validation قبل از Build
  • ساخت Objectهای Immutable
  • مناسب برای Test Data

معایب Builder

  • افزایش Boilerplate
  • برای Object ساده Overengineering است
  • ممکن است Validation بین Builder و Domain پخش شود
⚠️
Business Invariantهای اصلی فقط نباید داخل Builder باشند. اگر Amount پرداخت همیشه باید مثبت باشد، خود Domain Object نیز باید از این Rule محافظت کند.

چه زمانی استفاده کنیم؟

  • Constructor Parameterهای زیاد
  • Optional Parameterهای متعدد
  • Construction چندمرحله‌ای
  • Representationهای مختلف
  • Product نهایی Immutable
  • Test Data پیچیده

چه زمانی استفاده نکنیم؟

  • Object ساده است.
  • Constructor کوتاه و واضح است.
  • Object Initializer کافی است.
  • Creation Complexity واقعی نداریم.

مثال نهایی Payment

C#
var paymentRequest =
    new PaymentRequestBuilder()
        .WithAmount(2_500_000)
        .ForMerchant("M-500")
        .WithOrderId("ORDER-2026-100")
        .WithMobileNumber("09121234567")
        .WithCallbackUrl(
            "https://merchant.example/callback")
        .AddMetadata("channel", "mobile")
        .AddMetadata("customerType", "VIP")
        .WithRetryCount(2)
        .Build();

var result =
    await paymentGateway.PayAsync(
        paymentRequest,
        cancellationToken);

نکته مصاحبه‌ای

🎤
Builder separates the construction of a complex object from its final representation. In a payment system, it is useful for building complex payment requests step by step, especially when there are many optional parameters, validations, or provider-specific representations.

جمع‌بندی 20.3

Builder زمانی مناسب است که Creation یک Object پیچیده، چندمرحله‌ای یا دارای Optionهای متعدد باشد. در Payment System می‌توان از آن برای ساخت PaymentRequest، Provider-specific Request و Test Data استفاده کرد.

✅
نکته کلیدی: Factory بیشتر می‌پرسد «چه Objectی بسازم؟»؛ Builder بیشتر می‌پرسد «این Object پیچیده را چگونه مرحله‌به‌مرحله بسازم؟».
