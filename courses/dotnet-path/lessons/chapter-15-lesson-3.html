Open/Closed Principle — OCP

📅 به‌روزرسانی: ۱۴۰۵/۰۵/۲۳
⏱️ زمان مطالعه: ۱۸ دقیقه
👤 تیم فنی

Open/Closed Principle یا OCP دومین اصل از مجموعه SOLID است. این اصل می‌گوید اجزای نرم‌افزار باید برای Extension باز باشند، اما برای Modification بسته باشند.

💡
تعریف معروف OCP: Software entities should be open for extension, but closed for modification. یعنی بتوانیم رفتار جدید اضافه کنیم، بدون اینکه دائماً کد پایدار و موجود را تغییر دهیم.

OCP دقیقاً یعنی چه؟

هدف OCP این نیست که هیچ Classی هرگز تغییر نکند. بلکه می‌گوید وقتی یک بخش از سیستم پایدار شده است، اضافه شدن Feature یا رفتار جدید بهتر است از طریق Extension انجام شود، نه با دستکاری مداوم کد قبلی.

یکی از رایج‌ترین روش‌های رسیدن به OCP استفاده از:

  • Abstraction
  • Interface
  • Inheritance
  • Polymorphism
  • Strategy Pattern
  • Dependency Injection

مثال اشتباه

فرض کنید در یک Payment System چند روش پرداخت داریم: Card، Wallet و Crypto. یک پیاده‌سازی ضعیف ممکن است چنین باشد:

C#
public class PaymentProcessor
{
    public void Process(
        string paymentType,
        decimal amount)
    {
        if (paymentType == "Card")
        {
            Console.WriteLine(
                $"Card payment: {amount}");
        }
        else if (paymentType == "Wallet")
        {
            Console.WriteLine(
                $"Wallet payment: {amount}");
        }
        else if (paymentType == "Crypto")
        {
            Console.WriteLine(
                $"Crypto payment: {amount}");
        }
    }
}

در این طراحی هر بار روش پرداخت جدیدی اضافه شود، باید Class موجود را تغییر دهیم.

C#
else if (paymentType == "BankTransfer")
{
    // New logic
}

این یعنی Class برای Extension باز نیست؛ چون برای اضافه کردن رفتار جدید مجبوریم Implementation موجود را Modify کنیم.

مشکل این طراحی چیست؟

  • با اضافه شدن هر Payment Type، شرط‌های بیشتری ایجاد می‌شود.
  • احتمال Regression بالا می‌رود.
  • Class بزرگ‌تر و پیچیده‌تر می‌شود.
  • Unit Testها سخت‌تر می‌شوند.
  • تغییر یک Payment Method ممکن است روی بقیه اثر بگذارد.
⚠️
وجود if/else یا switch همیشه به معنی نقض OCP نیست، اما اگر برای هر Feature جدید مجبور باشید دائماً شرط جدیدی به یک Class مرکزی اضافه کنید، احتمالاً طراحی نیاز به بازنگری دارد.

Refactoring با Abstraction

ابتدا یک قرارداد مشترک برای روش‌های پرداخت تعریف می‌کنیم:

C#
public interface IPaymentMethod
{
    void Process(
        decimal amount);
}

هر Payment Method پیاده‌سازی خودش را دارد:

C#
public class CardPayment
    : IPaymentMethod
{
    public void Process(
        decimal amount)
    {
        Console.WriteLine(
            $"Card payment: {amount}");
    }
}

public class WalletPayment
    : IPaymentMethod
{
    public void Process(
        decimal amount)
    {
        Console.WriteLine(
            $"Wallet payment: {amount}");
    }
}

PaymentProcessor بعد از Refactoring

C#
public class PaymentProcessor
{
    private readonly IPaymentMethod
        _paymentMethod;

    public PaymentProcessor(
        IPaymentMethod paymentMethod)
    {
        _paymentMethod =
            paymentMethod;
    }

    public void Process(
        decimal amount)
    {
        _paymentMethod.Process(
            amount);
    }
}

اکنون PaymentProcessor به یک Abstraction وابسته است و درباره Implementationها چیزی نمی‌داند.

اضافه کردن Feature جدید بدون تغییر کد قبلی

اگر فردا Bank Transfer اضافه شود، فقط یک Class جدید ایجاد می‌کنیم:

C#
public class BankTransferPayment
    : IPaymentMethod
{
    public void Process(
        decimal amount)
    {
        Console.WriteLine(
            $"Bank transfer: {amount}");
    }
}

نیازی نیست PaymentProcessor یا Classهای قبلی را تغییر دهیم.

🎯
اینجا سیستم برای Extension باز است، چون می‌توانیم Payment Method جدید اضافه کنیم، و برای Modification بسته است، چون کد پایدار قبلی را دست نمی‌زنیم.

OCP و Polymorphism

Polymorphism یکی از مهم‌ترین ابزارهای اجرای OCP در OOP است.

C#
IPaymentMethod paymentMethod =
    new CardPayment();

paymentMethod.Process(
    500_000);

paymentMethod =
    new WalletPayment();

paymentMethod.Process(
    250_000);

Caller فقط Interface را می‌شناسد؛ رفتار واقعی بر اساس Implementation انتخاب می‌شود.

مثال واقعی: Fee Calculation

فرض کنید Fee برای Transaction Typeهای مختلف متفاوت است. نسخه ضعیف:

C#
public class FeeCalculator
{
    public decimal Calculate(
        string transactionType,
        decimal amount)
    {
        if (transactionType == "Purchase")
        {
            return amount * 0.01m;
        }

        if (transactionType == "Refund")
        {
            return amount * 0.005m;
        }

        if (transactionType == "Settlement")
        {
            return amount * 0.002m;
        }

        return 0;
    }
}

هر بار Transaction Type جدید اضافه شود، باید همین Class تغییر کند.

Refactoring با Strategy

C#
public interface IFeeStrategy
{
    decimal Calculate(
        decimal amount);
}
C#
public class PurchaseFeeStrategy
    : IFeeStrategy
{
    public decimal Calculate(
        decimal amount)
    {
        return amount * 0.01m;
    }
}

public class RefundFeeStrategy
    : IFeeStrategy
{
    public decimal Calculate(
        decimal amount)
    {
        return amount * 0.005m;
    }
}

Calculator اصلی فقط Strategy را اجرا می‌کند:

C#
public class FeeCalculator
{
    private readonly IFeeStrategy
        _strategy;

    public FeeCalculator(
        IFeeStrategy strategy)
    {
        _strategy =
            strategy;
    }

    public decimal Calculate(
        decimal amount)
    {
        return _strategy.Calculate(
            amount);
    }
}

مثال واقعی‌تر: Discount System

فرض کنید قوانین Discount مرتباً تغییر می‌کنند. یک طراحی شرطی ممکن است سریعاً پیچیده شود:

C#
public decimal CalculateDiscount(
    Customer customer,
    decimal amount)
{
    if (customer.Type == CustomerType.Normal)
    {
        return amount * 0.02m;
    }

    if (customer.Type == CustomerType.Vip)
    {
        return amount * 0.10m;
    }

    if (customer.Type == CustomerType.Partner)
    {
        return amount * 0.15m;
    }

    return 0;
}

راه extensible:

C#
public interface IDiscountPolicy
{
    decimal Calculate(
        decimal amount);
}

public class NormalCustomerDiscount
    : IDiscountPolicy
{
    public decimal Calculate(
        decimal amount)
        => amount * 0.02m;
}

public class VipCustomerDiscount
    : IDiscountPolicy
{
    public decimal Calculate(
        decimal amount)
        => amount * 0.10m;
}

OCP و Dependency Injection

Dependency Injection کمک می‌کند Implementationها بدون تغییر Consumer جایگزین شوند.

C#
builder.Services.AddScoped
    <IPaymentMethod,
     CardPayment>();

اگر Implementation عوض شود:

C#
builder.Services.AddScoped
    <IPaymentMethod,
     WalletPayment>();

Consumer نیازی به تغییر ندارد.

OCP به معنی Interface برای همه چیز نیست

یکی از سوءبرداشت‌های رایج این است که برای رعایت OCP باید برای تمام Classها Interface بسازیم. این کار می‌تواند سیستم را بیش از حد Abstract کند.

⚠️
Abstraction را زمانی ایجاد کنید که واقعاً یک محور تغییر یا Extension وجود دارد. اگر یک Class ساده و پایدار است و هیچ رفتار جایگزینی ندارد، ساخت Interface فقط برای «رعایت SOLID» می‌تواند Over-Engineering باشد.

OCP و Switch Expression

وجود Switch همیشه بد نیست. برای داده‌های ثابت و محدود، گاهی Switch ساده‌تر و خواناتر است.

C#
string GetStatusText(
    PaymentStatus status)
{
    return status switch
    {
        PaymentStatus.Pending =>
            "Pending",

        PaymentStatus.Successful =>
            "Successful",

        PaymentStatus.Failed =>
            "Failed",

        _ =>
            "Unknown"
    };
}

اگر مجموعه Statusها عملاً ثابت و محدود باشد، این طراحی لزوماً مشکل OCP ندارد. اما اگر هر Feature جدید دائماً branch جدیدی به Business Logic اضافه می‌کند، Abstraction احتمالاً مناسب‌تر است.

نشانه‌های نقض OCP

  • اضافه شدن هر Feature نیازمند تغییر یک Class مرکزی است.
  • Switch یا if/else دائماً بزرگ‌تر می‌شود.
  • Class درباره همه Implementationهای ممکن knowledge دارد.
  • افزودن رفتار جدید باعث Regression در رفتارهای قبلی می‌شود.
  • برای اضافه کردن یک Provider جدید باید Business Service را تغییر دهید.

OCP در Payment Gateway

فرض کنید سیستم باید با چند Payment Gateway مختلف کار کند:

C#
public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken);
}
C#
public class BankAGateway
    : IPaymentGateway
{
    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        // Bank A API call

        return Task.FromResult(
            new PaymentResult());
    }
}

public class BankBGateway
    : IPaymentGateway
{
    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        // Bank B API call

        return Task.FromResult(
            new PaymentResult());
    }
}

Application Service فقط Abstraction را می‌شناسد:

C#
public class PaymentService
{
    private readonly IPaymentGateway
        _gateway;

    public PaymentService(
        IPaymentGateway gateway)
    {
        _gateway =
            gateway;
    }

    public Task<PaymentResult> PayAsync(
        PaymentRequest request,
        CancellationToken cancellationToken)
    {
        return _gateway.PayAsync(
            request,
            cancellationToken);
    }
}

اگر فردا Bank C اضافه شود، یک Implementation جدید از IPaymentGateway ساخته می‌شود. PaymentService نیازی به تغییر ندارد. این یک مثال واقعی از OCP در سیستم‌های Payment است.

مزایای OCP

  • کاهش Regression Risk
  • Extension ساده‌تر
  • Coupling کمتر
  • استفاده بهتر از Polymorphism
  • Testability بهتر
  • جایگزینی ساده‌تر Implementationها
  • کاهش تغییرات روی کد پایدار

قبل و بعد از OCP

قبل بعد
if/else مرکزی Implementationهای مستقل
تغییر Class قبلی برای Feature جدید اضافه کردن Class جدید
Coupling بالا وابستگی به Abstraction
Risk بالاتر Regression تغییرات ایزوله‌تر

نکته مصاحبه‌ای

🎤
در مصاحبه می‌توانید بگویید: OCP means software entities should be open for extension but closed for modification. بعد مثال بزنید که به‌جای اضافه کردن if/else برای Payment Type جدید، یک Interface تعریف می‌کنیم و Implementation جدید اضافه می‌کنیم.

اشتباهات رایج

  • تصور اینکه OCP یعنی هیچ کدی نباید تغییر کند.
  • ساخت Interface برای تمام Classها بدون نیاز واقعی.
  • استفاده از inheritance فقط برای رعایت OCP.
  • ایجاد Abstractionهای پیچیده برای سناریوهای ساده.
  • تبدیل هر switch کوچک به چندین Class بدون دلیل.
  • نادیده گرفتن Polymorphism و Dependency Injection در نقاط Extension واقعی.
🎯
مدل ذهنی خوب: اگر هر بار Feature جدید می‌آید مجبورید یک Class پایدار را باز کنید و branch جدید اضافه کنید، به این فکر کنید که آیا آن نقطه باید یک Extension Point داشته باشد یا نه.

جمع‌بندی OCP

Open/Closed Principle می‌گوید طراحی خوب باید اجازه دهد رفتار جدید با کمترین تغییر در کد موجود اضافه شود. در OOP، Interface، Abstraction و Polymorphism ابزارهای اصلی برای ساخت Extension Point هستند.

✅
نکته کلیدی: Extend behavior by adding new code, not by repeatedly rewriting stable code. اما OCP را فقط در نقاطی اعمال کنید که واقعاً احتمال Extension و Variation وجود دارد.
