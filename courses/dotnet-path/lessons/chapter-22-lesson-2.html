OOP و Clean Architecture

📅 به‌روزرسانی: ۱۴۰۵/۰۶/۲۲
⏱️ زمان مطالعه: ۲۲ دقیقه
👤 تیم فنی

فرض کنید یک Payment API ساخته‌ایم. در نسخهٔ اول، Controller مستقیماً از AppDbContext و SDK یک Payment Provider استفاده می‌کند. برنامه امروز کار می‌کند؛ اما برای آزمودن Ruleهای پرداخت به Database و Provider واقعی نیاز داریم و تعویض هرکدام، Code مربوط به Use Case را نیز تغییر می‌دهد.

C# — طراحی وابسته به جزئیات
[HttpPost]
public async Task<IActionResult> Pay(PayRequest request)
{
    var payment = new PaymentRow
    {
        Id = Guid.NewGuid(),
        Amount = request.Amount,
        Status = "Pending"
    };

    _dbContext.Payments.Add(payment);
    var gatewayResult = await _providerSdk.ChargeAsync(request.Amount);
    payment.Status = gatewayResult.IsSuccessful ? "Succeeded" : "Failed";
    await _dbContext.SaveChangesAsync();

    return Ok(new { payment.Id, payment.Status });
}

در این Method، قرارداد HTTP، Business Rule، EF Core و SDK خارجی به هم چسبیده‌اند. تغییر Provider، روش Persistence یا حتی شیوهٔ نمایش Status می‌تواند یک فایل را از چند جهت تغییر دهد. Clean Architecture برای کنترل همین Dependencyها یک قاعدهٔ محوری ارائه می‌کند.

Clean Architecture چیست؟

Clean Architecture یک سبک معماری است که Business Ruleها و Use Caseهای برنامه را در مرکز قرار می‌دهد و جزئیات قابل‌تعویض مانند Web Framework، Database، Message Broker و سرویس‌های خارجی را در مرزهای بیرونی نگه می‌دارد.

Use Case یک هدف مشخص کاربر یا Actor از سیستم است؛ مانند «شروع پرداخت»، «لغو سفارش» یا «تأیید برداشت». هدف این معماری آن نیست که Business از همه‌چیز جدا و بدون ارتباط بماند؛ هدف این است که ارتباط از طریق قراردادهای کنترل‌شده انجام شود.

🧭
مدل ذهنی: Business Ruleها Policyهای اصلی سیستم‌اند؛ EF Core، ASP.NET Core و Payment Provider جزئیات اجرای آن Policyها هستند. Detail باید خود را با نیاز Policy تطبیق دهد، نه اینکه Policy را به شکل API خود وابسته کند.

لایه‌های مفهومی Clean Architecture

نمودارهای Clean Architecture معمولاً چند حلقهٔ هم‌مرکز دارند. تعداد Projectها می‌تواند متفاوت باشد، اما مسئولیت‌های مفهومی زیر باید قابل‌تشخیص باشند:

حلقه مسئولیت نمونه در .NET
Entities Business Ruleهای مستقل و State معتبر Domain Payment، Order، Value Object
Use Cases جریان‌های کاربردی و هماهنگی عملیات سیستم StartPaymentHandler، Command، Output Model
Interface Adapters تبدیل داده میان شکل داخلی و شکل موردنیاز ابزارهای بیرونی Controller، Presenter، Repository Adapter، Mapper
Frameworks & Drivers جزئیات فنی و ابزارهای قابل‌تعویض ASP.NET Core، EF Core، SQL Server، Provider SDK

در Solutionهای .NET، معمولاً Entities در Projectی به نام Domain، Use Caseها در Application و Adapterهای فنی در Infrastructure و WebApi قرار می‌گیرند. این نام‌ها قرارداد رایج‌اند، نه الزام معماری.

Dependency Rule: مهم‌ترین قانون

Dependency Rule می‌گوید Dependency مربوط به Source Code باید به سمت داخل، یعنی به سمت Policyهای سطح بالاتر، حرکت کند. Code یک حلقهٔ داخلی نباید دربارهٔ Typeها و جزئیات حلقهٔ بیرونی اطلاعات داشته باشد.

  • Domain نباید به EF Core، ASP.NET Core یا Infrastructure Reference داشته باشد.
  • Application می‌تواند Domain را بشناسد، اما نباید به Provider SDK وابسته شود.
  • Infrastructure می‌تواند Interface تعریف‌شده برای Use Case را پیاده‌سازی کند.
  • WebApi می‌تواند ورودی HTTP را به مدل ورودی Application تبدیل کند.
⚠️
«به سمت داخل» به معنی فراخوانی نشدن Code بیرونی نیست. Application در زمان اجرا Gateway را فراخوانی می‌کند، اما در زمان Compile فقط Interface خود را می‌شناسد؛ Object واقعی در Composition Root به آن تزریق می‌شود.

OOP چگونه Dependency Rule را ممکن می‌کند؟

Clean Architecture به OOP محدود نیست، اما چند ابزار OOP اجرای مرزها را در C# ساده می‌کنند:

  • Encapsulation: Entity تغییر State خود را از طریق Methodهای معتبر کنترل می‌کند.
  • Abstraction: Interface نیاز Use Case به دنیای بیرون را بیان می‌کند.
  • Polymorphism: Adapter واقعی و Fake آزمایشی هر دو می‌توانند همان Interface را اجرا کنند.
  • Dependency Inversion: Policy سطح بالا به Detail سطح پایین وابسته نیست؛ هر دو به قراردادی وابسته‌اند که بر اساس نیاز Policy طراحی شده است.
  • Composition: در مرز بیرونی، Objectهای مستقل به یک Object Graph اجرایی متصل می‌شوند.

مثال کامل: Use Case شروع پرداخت

گام اول: Entity از Ruleهای پرداخت محافظت می‌کند

C# — Domain
public enum PaymentStatus
{
    Pending,
    Succeeded,
    Failed
}

public sealed class Payment
{
    public Guid Id { get; }
    public decimal Amount { get; }
    public PaymentStatus Status { get; private set; }
    public string? FailureReason { get; private set; }

    public Payment(Guid id, decimal amount)
    {
        if (id == Guid.Empty)
            throw new ArgumentException("Payment id is required.", nameof(id));
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        Id = id;
        Amount = amount;
        Status = PaymentStatus.Pending;
    }

    public void MarkAsSucceeded()
    {
        EnsurePending();
        Status = PaymentStatus.Succeeded;
    }

    public void MarkAsFailed(string reason)
    {
        EnsurePending();

        if (string.IsNullOrWhiteSpace(reason))
            throw new ArgumentException("Failure reason is required.", nameof(reason));

        Status = PaymentStatus.Failed;
        FailureReason = reason;
    }

    private void EnsurePending()
    {
        if (Status != PaymentStatus.Pending)
            throw new InvalidOperationException("Only a pending payment can change.");
    }
}

Entity هیچ شناختی از HTTP، EF Core یا Provider ندارد. رفتار قابل‌مشاهدهٔ آن روشن است: Payment با مبلغ مثبت در حالت Pending ساخته می‌شود و فقط یک‌بار می‌تواند به Succeeded یا Failed تغییر کند. Setter عمومی نیز نمی‌تواند این Rule را دور بزند.

گام دوم: Application قراردادهای موردنیاز خود را تعریف می‌کند

قرارداد خروجی به سیستم خارجی را معمولاً Output Port می‌نامند. این قرارداد باید با زبان Use Case طراحی شود، نه با Typeهای SDK بیرونی.

C# — Application Ports
public sealed record ChargeResult(bool IsSuccessful, string? Error)
{
    public static ChargeResult Success() => new(true, null);
    public static ChargeResult Failure(string error) => new(false, error);
}

public interface IPaymentGateway
{
    Task<ChargeResult> ChargeAsync(
        Guid paymentId,
        decimal amount,
        CancellationToken cancellationToken);
}

public interface IPaymentRepository
{
    Task AddAsync(Payment payment, CancellationToken cancellationToken);
}

public sealed record StartPaymentCommand(decimal Amount);
public sealed record StartPaymentResult(Guid PaymentId, PaymentStatus Status);

ChargeResult مدل داخلی Application است. اگر SDK یک Type مانند ProviderChargeResponse برگرداند، آن Type نباید از Infrastructure عبور کند؛ Adapter آن را به ChargeResult تبدیل می‌کند.

گام سوم: Use Case فقط Policy و Portها را می‌شناسد

C# — Application Use Case
public sealed class StartPaymentHandler(
    IPaymentGateway gateway,
    IPaymentRepository payments)
{
    public async Task<StartPaymentResult> HandleAsync(
        StartPaymentCommand command,
        CancellationToken cancellationToken)
    {
        var payment = new Payment(Guid.NewGuid(), command.Amount);

        var charge = await gateway.ChargeAsync(
            payment.Id,
            payment.Amount,
            cancellationToken);

        if (charge.IsSuccessful)
            payment.MarkAsSucceeded();
        else
            payment.MarkAsFailed(charge.Error ?? "Payment provider rejected the charge.");

        await payments.AddAsync(payment, cancellationToken);

        return new StartPaymentResult(payment.Id, payment.Status);
    }
}

Handler ترتیب اجرای Use Case را مشخص می‌کند: ساخت Payment، درخواست Charge، اعمال نتیجه بر Entity، ذخیره و تولید Output. هیچ Type مربوط به ASP.NET Core، EF Core یا Provider در این Class دیده نمی‌شود.

گام چهارم: Infrastructure قراردادها را با جزئیات واقعی تطبیق می‌دهد

C# — Infrastructure Adapter
public sealed class ProviderPaymentGateway(ProviderClient client)
    : IPaymentGateway
{
    public async Task<ChargeResult> ChargeAsync(
        Guid paymentId,
        decimal amount,
        CancellationToken cancellationToken)
    {
        var response = await client.CreateChargeAsync(
            reference: paymentId.ToString(),
            amount: amount,
            cancellationToken: cancellationToken);

        return response.Approved
            ? ChargeResult.Success()
            : ChargeResult.Failure(response.ErrorMessage);
    }
}

public sealed class EfPaymentRepository(AppDbContext dbContext)
    : IPaymentRepository
{
    public async Task AddAsync(
        Payment payment,
        CancellationToken cancellationToken)
    {
        dbContext.Payments.Add(payment);
        await dbContext.SaveChangesAsync(cancellationToken);
    }
}

این دو Class نقش Adapter دارند. یکی زبان Provider را به زبان Application ترجمه می‌کند و دیگری Object Domain را با سازوکار Persistence ذخیره می‌کند. تغییر SDK فقط Adapter مربوط به همان SDK را تحت‌تأثیر قرار می‌دهد.

گام پنجم: Presentation قرارداد HTTP را تطبیق می‌دهد

C# — ASP.NET Core
public sealed record StartPaymentRequest(decimal Amount);
public sealed record StartPaymentResponse(Guid Id, string Status);

[ApiController]
[Route("api/payments")]
public sealed class PaymentsController(StartPaymentHandler handler)
    : ControllerBase
{
    [HttpPost]
    public async Task<ActionResult<StartPaymentResponse>> Start(
        StartPaymentRequest request,
        CancellationToken cancellationToken)
    {
        var result = await handler.HandleAsync(
            new StartPaymentCommand(request.Amount),
            cancellationToken);

        var response = new StartPaymentResponse(
            result.PaymentId,
            result.Status.ToString());

        return Ok(response);
    }
}

Controller یک Input Adapter است: JSON و HTTP را به Input Model مربوط به Use Case تبدیل می‌کند و Output داخلی را به قرارداد API برمی‌گرداند. اگر ورودی برنامه بعداً از Message Broker بیاید، Consumer تازه می‌تواند همان Handler را بدون انتقال HTTP به Application صدا بزند.

گام ششم: Composition Root پیاده‌سازی‌ها را انتخاب می‌کند

C# — Program.cs
builder.Services.AddScoped<StartPaymentHandler>();
builder.Services.AddScoped<IPaymentGateway, ProviderPaymentGateway>();
builder.Services.AddScoped<IPaymentRepository, EfPaymentRepository>();

Composition Root بیرونی‌ترین نقطه‌ای است که Concrete Typeها را می‌شناسد و Object Graph را می‌سازد. Dependency Injection Container ابزار اتصال است؛ خود Container معماری را Clean نمی‌کند. پاکی مرزها از جهت Referenceها و مسئولیت Classها می‌آید.

جهت Source Code و جریان Runtime

نوع رابطه مسیر مثال پرداخت
جریان Runtime Controller → Handler → IPaymentGateway → ProviderPaymentGateway → Provider
Dependency در Source Code WebApi → Application ← Infrastructure

علامت برگشتی در ردیف دوم نکتهٔ اصلی است: Infrastructure برای پیاده‌سازی IPaymentGateway به قرارداد Application وابسته می‌شود. Handler هیچ Reference مستقیمی به Infrastructure ندارد، هرچند در Runtime Method همان Adapter اجرا می‌شود.

ساختار پیشنهادی Solution و Project Referenceها

Text
Payments.sln
├── Payments.Domain
│   └── Payments/Payment.cs
├── Payments.Application             → Payments.Domain
│   └── Payments/StartPayment/

Reference از WebApi به Infrastructure معمولاً برای Registration و Composition لازم می‌شود. می‌توان ثبت سرویس‌ها را در یک Extension Method داخل Infrastructure پنهان کرد، اما Dependency واقعی همچنان وجود دارد و در بیرونی‌ترین حلقه مجاز است.

مرزها و Data Modelها

یک Object را بدون فکر از Database تا HTTP عبور ندهید. هر مرز ممکن است مدل متناسب با مسئولیت خود را داشته باشد:

  • StartPaymentRequest قرارداد عمومی HTTP است.
  • StartPaymentCommand ورودی پایدار Use Case است.
  • Payment رفتار و State معتبر Domain را نگه می‌دارد.
  • ProviderChargeResponse فقط به SDK خارجی تعلق دارد.

این جداسازی به معنی ساخت DTO برای تک‌تک Classها نیست. وقتی دو مدل معنا، چرخهٔ تغییر و مخاطب یکسان دارند، Mapping اضافی فقط هزینه می‌سازد. مرز را جایی ایجاد کنید که از نشت یک Detail یا قرارداد مستقل جلوگیری کند.

تست Use Case بدون Framework و Database

C# — xUnit
[Fact]
public async Task HandleAsync_Marks_payment_as_succeeded_when_charge_is_approved()
{
    var gateway = new ApprovedGateway();
    var repository = new InMemoryPaymentRepository();
    var handler = new StartPaymentHandler(gateway, repository);

    var result = await handler.HandleAsync(
        new StartPaymentCommand(250_000m),
        CancellationToken.None);

    Assert.Equal(PaymentStatus.Succeeded, result.Status);
    Assert.Equal(result.PaymentId, repository.SavedPayment?.Id);
}

private sealed class ApprovedGateway : IPaymentGateway
{
    public Task<ChargeResult> ChargeAsync(
        Guid paymentId,
        decimal amount,
        CancellationToken cancellationToken)
        => Task.FromResult(ChargeResult.Success());
}

private sealed class InMemoryPaymentRepository : IPaymentRepository
{
    public Payment? SavedPayment { get; private set; }

    public Task AddAsync(Payment payment, CancellationToken cancellationToken)
    {
        SavedPayment = payment;
        return Task.CompletedTask;
    }
}

این Test بدون Web Server، Database و Provider اجرا می‌شود و Policy موردنظر را بررسی می‌کند: وقتی Charge موفق است، Payment با Status موفق ذخیره می‌شود. برای اطمینان از Mappingهای EF Core و ارتباط واقعی Provider، Testهای Integration جداگانه لازم‌اند.

Clean Architecture با Layered Architecture چه تفاوتی دارد؟

هر دو سبک مسئولیت‌ها را جدا می‌کنند. تفاوت برجسته در کنترل Dependency است. در Layered Architecture سنتی، Business Layer ممکن است مستقیماً Data Access Layer را Reference کند. در Clean Architecture، قرارداد موردنیاز Business در سمت داخلی قرار می‌گیرد و Adapter بیرونی آن را پیاده‌سازی می‌کند.

🔍
Clean Architecture را با تعداد Projectها تشخیص ندهید. پرسش بهتر این است: «آیا می‌توان Business Rule و Use Case را بدون وابستگی مستقیم به Framework، Database و سرویس خارجی فهمید و Test کرد؟»

اشتباهات رایج

۱. تبدیل Architecture به Folder Structure

ساختن Projectهای Domain و Application کافی نیست. اگر Domain به EF Core و Handler به SDK خارجی Reference داشته باشند، Dependency Rule نقض شده است.

۲. ایجاد Interface برای تمام Classها

Interface باید یک مرز واقعی را بیان کند. Entity و Use Case معمولاً فقط برای هماهنگ‌شدن با یک Template به Interface هم‌نام نیاز ندارند. Abstraction بی‌دلیل، تعداد فایل‌ها و مسیر دنبال‌کردن Code را افزایش می‌دهد.

۳. مدل Domain بدون Behavior

اگر Entityها فقط Getter و Setter داشته باشند و تمام Ruleها در Handlerها نوشته شوند، Encapsulation ضعیف می‌شود. Rule وابسته به State یک Entity، مانند انتقال Status پرداخت، معمولاً باید توسط همان Entity محافظت شود.

۴. نشت Typeهای بیرونی به Application

استفاده از DbSet، HttpContext یا Response اختصاصی Provider در Use Case، حلقهٔ داخلی را به Detail بیرونی وابسته می‌کند. Adapter باید این Typeها را در مرز ترجمه کند.

۵. Business Rule در Controller یا Repository

Controller و Repository Adapter هستند. تصمیم‌هایی مانند امکان تغییر Status یا حداقل مبلغ پرداخت باید در Domain یا Application قرار گیرند تا از هر ورودی و با هر Persistence یکسان اجرا شوند.

۶. وابستگی به DI Container در Domain

فراخوانی IServiceProvider.GetService در Entity یا Use Case، Dependencyهای واقعی را پنهان می‌کند. Dependency لازم را صریحاً از Constructor دریافت کنید و Container را در Composition Root نگه دارید.

۷. پیچیدگی زودهنگام

برای یک CRUD کوچک، تعداد زیاد Project، Command، Handler، Mapper و Interface ممکن است ارزش اقتصادی نداشته باشد. استقلال باید در برابر هزینهٔ Navigation، Mapping و نگهداری سنجیده شود.

چه زمانی Clean Architecture مناسب است؟

  • Business Ruleها پیچیده‌اند و عمرشان از Framework یا Database بیشتر است.
  • چند ورودی مانند HTTP، Worker و Message Consumer از Use Caseهای مشترک استفاده می‌کنند.
  • Integrationهای بیرونی قابل‌تعویض یا پرریسک‌اند.
  • تست سریع و مستقل Use Caseها برای تیم ارزش بالایی دارد.
  • چند تیم یا ماژول به مرزهای روشن و قابل‌کنترل نیاز دارند.

برای Prototype کوتاه‌عمر یا برنامه‌ای با Ruleهای بسیار کم، یک Modular Monolith ساده یا Layered Architecture سبک می‌تواند انتخاب بهتری باشد. Clean Architecture مقصد اجباری هر پروژه نیست؛ پاسخی به نیاز استقلال و کنترل Dependency است.

چک‌لیست بررسی یک Use Case

  1. آیا نام Use Case هدف Actor را روشن بیان می‌کند؟
  2. آیا Domain بدون اجرای Web Server و Database قابل‌فهم و قابل‌آزمون است؟
  3. آیا Application فقط Interfaceهای متناسب با نیاز خود را می‌شناسد؟
  4. آیا Typeهای EF Core، ASP.NET Core و SDK خارجی پشت Adapter مانده‌اند؟
  5. آیا Controller فقط تبدیل ورودی، فراخوانی Use Case و تبدیل خروجی را انجام می‌دهد؟
  6. آیا Concrete Typeها فقط در Composition Root به هم متصل می‌شوند؟
  7. آیا هر Mapping از یک مرز واقعی محافظت می‌کند یا صرفاً Code اضافی است؟

تمرین

به مثال پرداخت یک Provider دوم اضافه کنید. Class جدید باید IPaymentGateway را پیاده‌سازی و پاسخ SDK خود را به ChargeResult تبدیل کند. سپس فقط Registration موجود در Composition Root را تغییر دهید. اگر برای تعویض Provider مجبور به تغییر StartPaymentHandler شدید، مرز Abstraction را دوباره بررسی کنید.

جمع‌بندی

Clean Architecture، Business Ruleها و Use Caseها را مرکز طراحی قرار می‌دهد. Dependency Rule از وابسته‌شدن این Policyها به Web Framework، Database و سرویس‌های خارجی جلوگیری می‌کند. OOP با Encapsulation، Abstraction، Polymorphism، Dependency Inversion و Composition ابزار اجرای این مرزها را فراهم می‌کند. خروجی مطلوب، شکل ظاهری خاص یا تعداد بیشتری Project نیست؛ هدف سیستمی است که Core آن مستقل‌تر، تغییرات Detail در آن محلی‌تر و رفتارهای مهم آن ساده‌تر قابل‌آزمون باشند.
