مفهوم Background Job و کاربردهای آن

یک کار پس‌زمینه می‌تواند مستقل از چرخه پاسخ‌دهی درخواست HTTP اجرا شود. در سیستم پرداخت، ارسال اعلان، تولید گزارش و پاک‌سازی داده‌ها نمونه‌های رایج هستند.

سناریوی پرداخت

کاربر پرداختی را ثبت می‌کند؛ ثبت نتیجه مالی باید در مسیر اصلی و با تضمین‌های لازم انجام شود، ولی ارسال پیامک یا تولید گزارش می‌تواند بعداً پردازش شود.

Payment API→Persist payment→Queue notification→Worker→SMS

اگر ثبت پرداخت ۱۰۰ میلی‌ثانیه و ارسال پیامک دو ثانیه طول بکشد، منتظر ماندن برای پیامک زمان پاسخ را افزایش می‌دهد. انتقال پیامک به مسیر پس‌زمینه فقط وقتی درست است که نحوه ثبت و بازیابی کار را هم طراحی کنیم.

هشدار Productionاجرای پس‌زمینه به معنی اجرای تضمینی نیست؛ کارهای فقط در حافظه ممکن است با Crash از دست بروند.

سؤال مرور درس 1

برای ارسال پیامک پس از پرداخت، بهتر است کدام کار در پس‌زمینه انجام شود؟

نمایش پاسخ تشریحی
ارسال پیامک؛ پس از ثبت موفق پرداخت، درخواست اعلان را به شکل امن در صف ثبت می‌کنیم و پاسخ را برمی‌گردانیم.

تفاوت async/await و Task.Run با Background Job

غیرهم‌زمان بودن عملیات، جدا بودن آن از درخواست HTTP و پایدار بودن کار سه موضوع متفاوت هستند.

await همچنان منتظر نتیجه است

نمونه کد C#C#
[HttpPost("pay")]
public async Task<IActionResult> Pay()
{
    await SavePaymentAsync();
    await SendSmsAsync();
    return Ok();
}

در این حالت Thread لزوماً مسدود نمی‌شود، ولی پاسخ HTTP تا پایان SendSmsAsync ارسال نمی‌شود.

Task.Run راهکار مطمئن صف نیست

نمونه کد C#C#
await SavePaymentAsync();
_ = Task.Run(async () => await SendSmsAsync());
return Ok();

در این نمونه ممکن است برنامه قبل از اتمام ارسال پیامک بسته شود؛ خطاهای کار پس‌زمینه نیز مدیریت نشده‌اند. به علاوه، استفاده از سرویس Scoped متعلق به Request داخل آن خطر ObjectDisposedException دارد.

BackgroundService

کلاس BackgroundService برای اجرای عملیات طولانی یا مداوم زیر نظر Host استفاده می‌شود؛ برای اطمینان از تحویل کار باید آن را به صف پایدار و سیاست بازیابی متصل کنیم.

روشآیا پاسخ منتظر می‌ماند؟آیا کار تضمین‌شده است؟
await مستقیمبلهبه موفقیت درخواست وابسته است
Task.Run بدون awaitخیرخیر
BackgroundService با صف حافظه‌ایخیرخیر، بعد از Crash
Worker + ذخیره پایدارخیربا طراحی درست قابل بازیابی است

سؤال مرور درس 2

اگر پس از return Ok برنامه کرش کند، برای Task.Run بدون await چه رخ می‌دهد؟

آشنایی با IHostedService و چرخه عمر Host

IHostedService قرارداد StartAsync و StopAsync را تعریف می‌کند؛ Host هنگام راه‌اندازی و توقف کنترل‌شده این متدها را فراخوانی می‌کند.

قرارداد رابطC#
public interface IHostedService
{
    Task StartAsync(CancellationToken cancellationToken);
    Task StopAsync(CancellationToken cancellationToken);
}
نمونه کد C#C#
public sealed class PaymentHostedService : IHostedService
{
    public Task StartAsync(CancellationToken token)
    {
        Console.WriteLine("Payment service started");
        return Task.CompletedTask;
    }

    public Task StopAsync(CancellationToken token)
    {
        Console.WriteLine("Payment service stopped");
        return Task.CompletedTask;
    }
}
ثبت در Program.csC#
builder.Services.AddHostedService<PaymentHostedService>();
هشدار ProductionStartAsync باید معمولاً سریع تمام شود. await کردن یک عملیات ۳۰ ثانیه‌ای در StartAsync می‌تواند مراحل راه‌اندازی را عقب بیندازد. StopAsync در Crash ناگهانی تضمین نمی‌شود.

سؤال مرور درس 3

اگر در StartAsync از await Task.Delay(30000) استفاده کنیم چه می‌شود؟

نمایش پاسخ تشریحی
تکمیل StartAsync حدود ۳۰ ثانیه به تأخیر می‌افتد و می‌تواند آماده‌شدن Host را عقب بیندازد.

درس 4 · آموزش و تمرین

پیاده‌سازی BackgroundService و ExecuteAsync

BackgroundService اجرای طولانی‌مدت را با متد ExecuteAsync آسان می‌کند و چرخه عمر آن زیر نظر Host است.

نمونه کد C#C#
public sealed class PaymentBackgroundService : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            Console.WriteLine("Checking payments...");
            await Task.Delay(5000, stoppingToken);
        }
    }
}
ثبت سرویسC#
builder.Services.AddHostedService<PaymentBackgroundService>();

حلقه هر بار پیام را چاپ می‌کند و سپس ۵ ثانیه صبر می‌کند. این نمونه صرفاً چرخه اجرا را نمایش می‌دهد و هنوز پردازش واقعی تراکنش ندارد.

توکن توقف

هنگام درخواست توقف، stoppingToken لغو می‌شود؛ Task.Delay با این توکن می‌تواند بلافاصله با OperationCanceledException یا زیرنوع TaskCanceledException خارج شود.

نکته مهمبرای پردازش واقعی، خطاها، مدیریت Scope، ثبت وضعیت کار و جلوگیری از اجرای تکراری ضروری هستند.

سؤال مرور درس 4

اگر هنگام Task.Delay درخواست توقف برسد، آیا الزاماً ۵ ثانیه صبر می‌کنیم؟

نمایش پاسخ تشریحی
خیر؛ اگر توکن به Task.Delay داده شده باشد، انتظار لغو می‌شود.

اجرای دوره‌ای با PeriodicTimer

PeriodicTimer زمان‌بندی مبتنی بر Tick را فراهم می‌کند و با Task.Delay بعد از پایان پردازش رفتار متفاوتی دارد.

Task.Delay: فاصله پس از پایان کار

نمونه کد C#C#
while (!stoppingToken.IsCancellationRequested)
{
    await CheckPendingPaymentsAsync(stoppingToken); // فرض: 3s
    await Task.Delay(10000, stoppingToken);
}

در فرض پردازش سه‌ثانیه‌ای، شروع دو اجرا حدود ۱۳ ثانیه فاصله خواهد داشت.

PeriodicTimer: Tickهای دوره‌ای

نمونه کد C#C#
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(10));
while (await timer.WaitForNextTickAsync(stoppingToken))
{
    await CheckPendingPaymentsAsync(stoppingToken);
}

اولین اجرا بعد از نخستین Tick رخ می‌دهد. اگر پردازش ۲۵ ثانیه طول بکشد، اجرای همان حلقه هم‌پوشانی ندارد و Tickهای ازدست‌رفته تجمیع می‌شوند؛ اجرای بعدی ممکن است بی‌درنگ شروع شود.

ویژگیTask.Delay پس از پردازشPeriodicTimer
محاسبه فاصلهپس از اتمام پردازشبراساس Tick
اجرای هم‌زمان در همین حلقهخیرخیر
تحمل Crashبه‌تنهایی نداردبه‌تنهایی ندارد

سؤال مرور درس 5

وقتی اجرای Job ۲۵ ثانیه و دوره تایمر ۱۰ ثانیه است، آیا چند اجرا هم‌زمان آغاز می‌شود؟

نمایش پاسخ تشریحی
خیر. در همین حلقه، پردازش جاری تمام می‌شود، سپس نوبت بعدی دریافت می‌شود.

درس 6 · آموزش و تمرین

CancellationToken و توقف کنترل‌شده

زمان Deploy یا توقف برنامه، Worker باید سیگنال توقف را دریافت و برای کار در حال اجرا سیاست مشخصی داشته باشد.

نمونه مفهومی؛ متدهای وابسته باید پیاده‌سازی شوندC#
while (!stoppingToken.IsCancellationRequested)
{
    var payment = await GetNextPaymentAsync(stoppingToken);
    if (payment is null)
    {
        await Task.Delay(1000, stoppingToken);
        continue;
    }
    await ProcessPaymentAsync(payment);
}

عدم ارسال stoppingToken به ProcessPaymentAsync در این نمونه نشان می‌دهد می‌توان به کار جاری فرصت تکمیل داد؛ اما کرش یا پایان مهلت توقف ممکن است آن را قطع کند.

مهلت خاموش‌شدن

نمونه کد C#C#
builder.Services.Configure<HostOptions>(options =>
{
    options.ShutdownTimeout = TimeSpan.FromSeconds(60);
});

افزایش ShutdownTimeout تنها مهلت توقف کنترل‌شده را بیشتر می‌کند و جایگزین بازیابی وضعیت نیست. در Kubernetes زمان پایان Pod نیز باید با آن هماهنگ شود.

هشدار Productionاگر بانک انتقال را انجام دهد ولی نتیجه قبل از ثبت در دیتابیس گم شود، درخواست انتقال را کورکورانه تکرار نکن. وضعیت را با شناسه یکتا استعلام کن و Reconciliation داشته باش.

سؤال مرور درس 6

بانک پرداخت را انجام داده ولی قبل از ثبت نتیجه، Worker کرش کرده است. اولین اقدام چیست؟

نمایش پاسخ تشریحی
استعلام وضعیت واقعی بانک با شناسه یکتا و جلوگیری از ارسال دوباره بدون بررسی.

درس 7 · آموزش و تمرین

DbContext و Scoped Service در BackgroundService

HostedService به‌طور پیش‌فرض Singleton است اما AddDbContext معمولاً DbContext را Scoped ثبت می‌کند؛ تزریق مستقیم آن در Constructor Worker طراحی درستی نیست.

مثال نامناسبC#
// Incorrect lifetime dependency:
public sealed class PaymentWorker(PaymentDbContext db)
    : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken token)
        => Task.CompletedTask;
}

ساخت Scope برای هر دور پردازش

به Microsoft.EntityFrameworkCore نیاز داردC#
public sealed class PaymentWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using (var scope = scopeFactory.CreateAsyncScope())
            {
                var db = scope.ServiceProvider
                    .GetRequiredService<PaymentDbContext>();
                var count = await db.Payments.CountAsync(
                    x => x.Status == "Pending", stoppingToken);
                Console.WriteLine($"Pending: {count}");
            }
            await Task.Delay(5000, stoppingToken);
        }
    }
}

در هر چرخه Scope جدید ساخته می‌شود؛ پس از کار با دیتابیس و پیش از تأخیر، Scope Dispose می‌شود.

نکته مهمبرای حجم بالا، همه رکوردهای Pending را یک‌باره با ToListAsync بارگیری نکن. Batch، Claim کردن اتمیک کارها و کنترل رقابت را طراحی کن.

سؤال مرور درس 7

چرا تزریق مستقیم DbContext در سازنده BackgroundService مشکل دارد؟

نمایش پاسخ تشریحی
زیرا Worker به صورت Singleton و DbContext به صورت Scoped ثبت می‌شود و طول عمر آن‌ها با هم ناسازگار است.

مدیریت Exception و Retry

در .NET 6 به بعد، Exception مدیریت‌نشده خارج‌شده از ExecuteAsync به‌صورت پیش‌فرض باعث درخواست توقف Host می‌شود.

منطق نمونه؛ logger و ProcessPendingPaymentsAsync وابستگی‌های کلاس‌اندC#
protected override async Task ExecuteAsync(
    CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        try
        {
            await ProcessPendingPaymentsAsync(stoppingToken);
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            break;
        }
        catch (Exception ex)
        {
            logger.LogError(ex, "Payment processing failed");
        }

        try { await Task.Delay(5000, stoppingToken); }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested) { break; }
    }
}

Retry متناسب با نوع شکست

شکستاقدام
قطعی گذرای دیتابیسRetry محدود با Backoff و Logging
داده نامعتبرثبت خطای دائمی؛ Retry بی‌هدف نکن
Timeout درخواست مالی به بانکاستعلام وضعیت و Idempotency پیش از اقدام مجدد
رفتار پیش‌فرض برای خطای مدیریت‌نشدهC#
builder.Services.Configure<HostOptions>(options =>
{
    options.BackgroundServiceExceptionBehavior =
        BackgroundServiceExceptionBehavior.StopHost;
});
هشدار Productionتنظیم Ignore به‌معنای راه‌اندازی مجدد Worker نیست. استثناهای غیرمنتظره را کورکورانه نادیده نگیر.

سؤال مرور درس 8

اگر SqlException مدیریت‌نشده از ExecuteAsync خارج شود، رفتار پیش‌فرض Host در .NET 8 چیست؟

نمایش پاسخ تشریحی
در حالت پیش‌فرض StopHost رخ می‌دهد؛ Host درخواست توقف دریافت می‌کند.

درس 9 · آموزش و تمرین

Queued Background Job با Channel

Channel یک صف درون‌حافظه‌ای غیرهم‌زمان برای ارتباط Producer و Consumer است. در این درس یک Worker صف‌محور می‌سازیم.

Payment API→Bounded Channel→SmsWorker→SMS Provider
ثبت در Program.cs؛ قبل از builder.BuildC#
using System.Threading.Channels;
var channel = Channel.CreateBounded<string>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true
});
builder.Services.AddSingleton(channel);
builder.Services.AddHostedService<SmsWorker>();
نمونه کد C#C#
public sealed class SmsWorker(Channel<string> queue)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken token)
    {
        await foreach (var message in queue.Reader.ReadAllAsync(token))
        {
            Console.WriteLine($"Sending SMS: {message}");
            await Task.Delay(2000, token); // شبیه‌سازی ارسال
        }
    }
}
ثبت Endpoint پس از builder.BuildC#
app.MapPost("/send-sms", async (
    Channel<string> queue, CancellationToken token) =>
{
    await queue.Writer.WriteAsync("Payment successful", token);
    return Results.Accepted();
});

Backpressure

وقتی BoundedChannel با FullMode.Wait پر باشد، WriteAsync تا آزادشدن ظرفیت به‌طور غیرمسدودکننده منتظر می‌ماند. لازم است Timeout و پاسخ مناسب API هم طراحی شود.

هشدار ProductionChannel حافظه‌ای پایدار نیست؛ Crash صف را از بین می‌برد. دریافت پیام نیز Ack پایدار ندارد. برای عملیات مهم به دیتابیس، Outbox یا Broker پایدار نیاز داریم.

سؤال مرور درس 9

اگر ظرفیت BoundedChannel برابر ۳ و پر شده باشد، WriteAsync چهارم چه می‌کند؟

نمایش پاسخ تشریحی
با FullMode پیش‌فرض Wait تا آزاد شدن ظرفیت منتظر می‌ماند؛ مگر عملیات لغو شود یا Channel بسته شود.

درس 10 · آموزش و تمرین

Hangfire و Quartz.NET

وقتی به Jobهای زمان‌بندی‌شده، پیگیری وضعیت یا اجرای پایدار پس از Restart نیاز داریم، کتابخانه‌های تخصصی کمک می‌کنند.

Hangfire

Hangfire اجرای Fire-and-forget، Delayed و Recurring Job را با Storage پشتیبانی می‌کند و داشبورد عملیاتی دارد. در تنظیم درست، وضعیت کار در فضای ذخیره‌سازی پایدار قرار می‌گیرد.

نمای مفهومی؛ وابستگی‌ها و نوع job باید تعریف شوندC#
// Packages: Hangfire.AspNetCore + Hangfire.SqlServer
builder.Services.AddHangfire(config =>
    config.UseSqlServerStorage(connectionString));
builder.Services.AddHangfireServer();

// After app starts / from application code:
BackgroundJob.Enqueue<INotificationJobs>(
    job => job.SendPaymentSmsAsync(paymentId));

اگر کاری باید در زمان آینده انجام شود، می‌توان از Schedule و برای کارهای تکرارشونده از RecurringJob استفاده کرد. نام متدها باید به شکل قابل سریال‌سازی و مطابق API نسخه نصب‌شده باشند.

Quartz.NET

Quartz.NET بیشتر برای زمان‌بندی پیچیده، Cron، Trigger و Calendar مناسب است. با Persistent Job Store می‌توان برنامه‌ریزی را در دیتابیس نگهداری کرد.

Quartz.NET — پیاده‌سازی IJobC#
public sealed class SettlementJob : IJob
{
    public Task Execute(IJobExecutionContext context)
    {
        Console.WriteLine("Running settlement check");
        return Task.CompletedTask;
    }
}
ویژگیHangfireQuartz.NET
سناریوی رایجصف Job و مدیریت عملیاتیScheduler و Trigger پیچیده
Storage پایداربا تنظیم Storageبا Persistent Store
Cronپشتیبانی می‌شودپشتیبانی پیشرفته
داشبورد آمادهدارددر هسته مشابه Hangfire ندارد
نکته مهمپایدار بودن Storage به معنی Exactly-once execution نیست؛ Job همچنان باید Idempotent طراحی شود.

سؤال مرور درس 10

برای زمان‌بندی پیچیده Cron و Trigger کدام ابزار معمولاً انتخاب مناسب‌تری است؟

برای جلوگیری از گم‌شدن Job در صورت Crash باید Lease/Timeout و بازپس‌گیری کارهای رهاشده را طراحی کنیم. قفل توزیع‌شده می‌تواند اجرای هم‌زمان یک Scheduler را کاهش دهد، اما تضمین عدم تکرار عملیات مالی نیست.

Idempotency

برای درخواست مالی از شناسه یکتای عملیات، قید Unique و بررسی وضعیت نهایی استفاده کن. در صورت قطع ارتباط، تکرار باید با همان شناسه و براساس قرارداد بانک/درگاه انجام شود.

هشدار Productionاگر از Redis Lock استفاده می‌کنی، به انقضای Lease، توقف طولانی و احتمال مالکیت هم‌زمان توجه کن. برای نوشتن روی منابع حساس، Fencing Token یا کنترل تراکنشی مناسب ممکن است لازم شود.

درس 12 · آموزش و تمرین

طراحی Production و جمع‌بندی مصاحبه Senior

هدف: پس از ثبت پرداخت، اعلان و گزارش را قابل بازیابی اجرا کنیم، بدون اینکه شکست Worker باعث گم شدن تراکنش یا دوباره‌کاری مالی شود.

معماری پیشنهادی

Payment API + DB Transaction→Outbox table→Publisher Worker→RabbitMQ durable→Consumer + Inbox→SMS / Report

در یک تراکنش دیتابیس، وضعیت پرداخت و رویداد Outbox را ثبت می‌کنیم. Worker پیام Outbox را منتشر می‌کند؛ پس از دریافت تأیید مناسب Broker، وضعیت انتشار را تغییر می‌دهد. در سمت مصرف‌کننده، Inbox با کلید یکتا و تغییرات دیتابیس در یک تراکنش انجام می‌شوند.

اگر RabbitMQ قطع باشد

Outbox در دیتابیس می‌ماند و Publisher بعداً دوباره تلاش می‌کند. تکرار ارسال قابل‌قبول است، چون Consumer باید Idempotent باشد.

اگر دیتابیس کند شود

Batch را کوچک می‌کنیم، صف‌ها را محدود و Backpressure را فعال می‌کنیم، Query و Index را بهینه می‌کنیم و مصرف را با ظرفیت DB هماهنگ می‌کنیم. افزایش تعداد Worker بدون رفع گلوگاه دیتابیس ممکن است وضعیت را بدتر کند.

اگر Worker کرش کند

وضعیت پایدار Job، Lease/Visibility Timeout و Retry کنترل‌شده امکان ادامه کار را فراهم می‌کنند؛ عملیات دارای نتیجه نامشخص باید استعلام و تطبیق داده شود.

Logging و Monitoring

تعداد Pending، تأخیر قدیمی‌ترین Job، نرخ خطا، تعداد Retry، DLQ، مدت پردازش، TraceId و CorrelationId را اندازه بگیر. هشدار برای رشد صف و توقف Worker تعریف کن.
