درس 01 · REST

REST و مفهوم Resource

در سبک معماری REST، مسیرها نماینده منابع هستند و متد HTTP نوع عملیات روی منبع را بیان می‌کند. منابع سیستم پرداخت می‌توانند payments، accounts و users باشند.

نمونه مسیرهای مبتنی بر ResourceHTTP
GET /api/payments
GET /api/payments/1001
POST /api/payments
PUT /api/payments/1001
DELETE /api/payments/1001

نام‌گذاری مناسب

به‌جای GET /api/GetPayment/1001 بهتر است بنویسیم GET /api/payments/1001. اسم منبع در مسیر می‌آید و عملیات از متد فهمیده می‌شود.

ملاحظات مالیحذف واقعی تراکنش مالی عموماً قابل قبول نیست؛ عملیات‌هایی مانند ابطال یا برگشت وجه معمولاً مدل و قرارداد مستقلی دارند.

سؤال مرور درس

برای دریافت پرداخت شماره ۵۰۰۱ چه متد و مسیری مناسب است؟

نمایش پاسخ تشریحی
GET /api/payments/5001؛ چون پرداخت یک Resource است و GET برای بازیابی آن به کار می‌رود.

درس 02 · REST

Stateless و اصول ارتباط Client و Server

در معماری Stateless هر درخواست باید اطلاعات موردنیاز پردازش خودش را داشته باشد. سرور نباید به Session مکالمه‌ای درخواست قبلی همان Client وابسته باشد.

دو درخواست مستقلHTTP
GET /api/accounts/1001
Authorization: Bearer <access-token>

GET /api/payments/5001
Authorization: Bearer <access-token>

این اصل به معنی ممنوعیت دیتابیس یا Cache نیست. داده حساب، پرداخت یا کاربر می‌تواند در SQL Server یا Redis ذخیره شود؛ اما درخواست بعدی نباید فقط به خاطر اینکه درخواست قبلی روی یک Instance خاص اجرا شده، به همان Instance وابسته باشد.

مزیت عملی

با Stateless بودن، Load Balancer می‌تواند درخواست‌ها را بین Instanceهای مختلف توزیع کند و Horizontal Scaling ساده‌تر می‌شود.

سؤال مرور درس

اگر درخواست اول به PaymentService-A و دومی به PaymentService-B برود چه می‌شود؟

نمایش پاسخ تشریحی
درخواست دوم بدون نیاز به Session اول قابل پردازش است، مشروط به اینکه همه داده‌ها و وابستگی‌های موردنیاز در دسترس باشند.

درس 04 · REST

تفاوت GET و POST

GET

متد GET برای دریافت اطلاعات است؛ طبق قرارداد نباید برای تغییر عمدی وضعیت تجاری سیستم استفاده شود. این متد Safe و Idempotent است و پاسخ آن با رعایت قواعد Cache می‌تواند کش شود.

نمونه کدHTTP
GET /api/payments/1001

HTTP/1.1 200 OK
Content-Type: application/json

{"id":1001,"amount":500000,"status":"Success"}

POST

متد POST برای ارسال درخواست پردازش یا ایجاد منبع استفاده می‌شود و ذاتاً Idempotent نیست.

نمونه کدHTTP
POST /api/payments
Content-Type: application/json

{"accountId":1001,"amount":500000}
سناریوی تکراریاگر پاسخ ثبت پرداخت در شبکه گم شود و کلاینت همان POST را تکرار کند، بدون حفاظت Idempotency ممکن است پرداخت دیگری ایجاد شود.

سؤال مرور درس

اگر POST پرداخت ثبت شود اما پاسخ نرسد، ارسال دوباره چه خطری دارد؟

نمایش پاسخ تشریحی
ممکن است یک پرداخت جدید دیگر ثبت شود؛ پروتکل HTTP به‌خودی‌خود تکرار POST را حذف نمی‌کند.

درس 05 · REST

تفاوت PUT و PATCH

PUT وضعیت منبع هدف را جایگزین می‌کند؛ PATCH تغییری جزئی را طبق فرمت Patch به منبع اعمال می‌کند.

نمونه کدHTTP
PUT /api/users/1001
Content-Type: application/json

{"name":"Hamed","city":"Shiraz","age":40}
نمونه کدHTTP
PATCH /api/users/1001
Content-Type: application/merge-patch+json

{"city":"Shiraz"}

حذف یک فیلد در درخواست PUT بسته به قرارداد می‌تواند باعث حذف، مقدار پیش‌فرض یا خطای اعتبارسنجی شود. در PATCH مثال بالا فقط city عوض می‌شود.

تفاوت از دید Idempotency

تنظیم قیمت روی یک مقدار ثابت، حتی در PATCH، می‌تواند Idempotent باشد؛ اما عملیات افزایشی مانند «هر بار ۱۰۰ واحد کم کن» با تکرار، وضعیت را باز هم تغییر می‌دهد.

مثال PATCH با رفتار IdempotentHTTP
PATCH /api/products/1001
Content-Type: application/merge-patch+json

{"price":500000}

سؤال مرور درس

اگر PATCH قیمت را هر بار برابر ۵۰۰۰۰۰ تنظیم کند، اجرای ۵ باره Idempotent است؟

نمایش پاسخ تشریحی
بله؛ چون اثر موردنظر در پایان همان تعیین قیمت به مقدار ۵۰۰۰۰۰ است.

درس 06 · REST

DELETE و درخواست تکراری

DELETE ذاتاً Idempotent است. حذف یک منبع در بار نخست و تلاش مجدد برای حذف همان منبع نباید اثر حذفِ اضافی روی آن منبع ایجاد کند.

نمونه کدHTTP
DELETE /api/products/1001

HTTP/1.1 204 No Content

DELETE /api/products/1001

HTTP/1.1 404 Not Found

متفاوت بودن پاسخ‌های ۲۰۴ و ۴۰۴ باعث نقض Idempotency نمی‌شود؛ این ویژگی درباره اثر موردنظر روی سرور است، نه الزام بر یکسان بودن Status Code.

مثال ASP.NET CoreC#
[HttpDelete("{id}")]
public async Task<IActionResult> Delete(int id)
{
    var product = await db.Products.FindAsync(id);
    if (product is null) return NotFound();
    db.Products.Remove(product);
    await db.SaveChangesAsync();
    return NoContent();
}

سؤال مرور درس

چرا پاسخ DELETE اول 204 و دوم 404 همچنان Idempotent است؟

نمایش پاسخ تشریحی
چون وضعیت نهایی منبع در هر دو حالت «حذف‌شده» باقی می‌ماند.

درس 07 · REST

Idempotency در پرداخت و Idempotency-Key

اگر اجرای چندباره یک درخواست اثر تجاری بیشتری از اجرای یک‌باره نداشته باشد، عملیات Idempotent است. این مفهوم در جلوگیری از برداشت یا انتقال وجه تکراری حیاتی است.

نمونه کدHTTP
POST /api/transfers
Idempotency-Key: abc-123
Content-Type: application/json

{"fromAccount":1001,"toAccount":2002,"amount":500000}

منطق پیشنهادی

کلاینت برای یک عملیات منطقی، یک شناسه پایدار تولید می‌کند. سرور شناسه را همراه با اثر عملیات و نتیجه آن ثبت می‌کند. هنگام تکرار درخواست با همان کلید و همان داده، به‌جای انتقال دوباره پول، نتیجه قبلی برگردانده می‌شود.

درخواستکلیدرفتار
اولabc-123پردازش انتقال و ذخیره نتیجه
دومabc-123بازگرداندن نتیجه قبلی
سومabc-123بازگرداندن نتیجه قبلی
خطر هم‌زمانیCheck-then-Insert ساده امن نیست؛ ممکن است دو Instance هم‌زمان نبود کلید را ببینند. باید محدودیت یکتایی و ثبت هماهنگ/اتمیک عملیات مالی داشته باشیم.

سؤال مرور درس

دو درخواست هم‌زمان با کلید یکسان روی دو Instance چگونه کنترل می‌شوند؟

نمایش پاسخ تشریحی
با Unique Constraint در دیتابیس به همراه تراکنش اتمیک ثبت درخواست و تغییرات مالی، نه صرفاً با یک بررسی اولیه.

درس 08 · REST

فهرست متدهای Idempotent

متدIdempotentSafe
GETبلهبله
HEADبلهبله
OPTIONSبلهبله
TRACEبلهبله
PUTبلهخیر
DELETEبلهخیر
POSTذاتاً خیرخیر
PATCHذاتاً خیرخیر

به‌صورت استاندارد، GET، HEAD، OPTIONS، TRACE، PUT و DELETE دارای معنای Idempotent هستند. POST و PATCH می‌توانند در یک پیاده‌سازی خاص Idempotent باشند، ولی HTTP چنین تضمینی برای آن‌ها نمی‌دهد.

نمونه کدHTTP
PUT /api/products/1001
Content-Type: application/json

{"name":"Laptop","price":50000000}

تکرار درخواست PUT بالا قیمت را روی همان مقدار تنظیم می‌کند. ممکن است لاگ‌ها یا پاسخ‌ها یکسان نباشند، اما اثر موردنظر یکسان می‌ماند.

نمایش پاسخ تشریحی
قیمت نهایی همان ۱۰۰۰۰۰ خواهد بود؛ عملیات Idempotent است.

درس 09 · REST

تفاوت Safe و Idempotent

Safe یعنی کلاینت قصد تغییر وضعیت تجاری سرور را از اجرای متد ندارد؛ Idempotent یعنی درخواست تکراری اثر موردنظر بیشتری از اجرای یک‌باره ندارد.

متدSafeIdempotent
GETبلهبله
PUTخیربله
DELETEخیربله
POSTخیرذاتاً خیر
PATCHخیرذاتاً خیر

برای مثال DELETE وضعیت منبع را تغییر می‌دهد پس Safe نیست، اما اجرای تکراری آن نباید اثر حذف بیشتری ایجاد کند پس Idempotent است. ثبت Log و Metrics به‌تنهایی ناقض Safe بودن GET نیست.

قانون مصاحبههر متد Safe در تعریف HTTP، Idempotent نیز هست؛ اما هر متد Idempotent لزوماً Safe نیست.

سؤال مرور درس

DELETE از نظر Safe و Idempotent چه وضعیتی دارد؟

نمایش پاسخ تشریحی
Safe نیست ولی Idempotent است.

درس 11 · REST

پیاده‌سازی Idempotency-Key در ASP.NET Core

برای جلوگیری از اجرای دوباره عملیات مالی، می‌توان یک جدول ذخیره شناسه، Hash درخواست، وضعیت و نتیجه ساخت و روی ترکیب کلاینت و کلید محدودیت یکتایی گذاشت.

طرح جدول SQL ServerSQL
CREATE TABLE IdempotencyRequests
(
    Id BIGINT IDENTITY PRIMARY KEY,
    ClientId BIGINT NOT NULL,
    IdempotencyKey NVARCHAR(100) NOT NULL,
    RequestHash VARCHAR(64) NOT NULL,
    Status VARCHAR(20) NOT NULL,
    ResponseBody NVARCHAR(MAX) NULL,
    CONSTRAINT UQ_Idempotency UNIQUE (ClientId, IdempotencyKey)
);

تراکنش دیتابیسی

در سناریوی ساده‌ای که همه تغییرات در یک SQL Server انجام می‌شوند، ثبت کلید، بررسی و تغییر موجودی، ثبت سند انتقال و ذخیره نتیجه باید در یک تراکنش هماهنگ انجام شوند؛ در شکست، Rollback و در موفقیت Commit می‌کنیم.

وضعیت کلیدرفتار
Completedبرگرداندن نتیجه ذخیره‌شده
Processingاعلام درحال‌پردازش بودن یا نتیجه موقت قراردادی
Failedتصمیم براساس نوع شکست و سیاست Retry
همان کلید، اطلاعات متفاوترد به دلیل تعارض
محدوده تضمیناگر سرویس خارجی یا چند دیتابیس مستقل درگیر شوند، یک تراکنش محلی کافی نیست. ممکن است به Inbox/Outbox، وضعیت پایدار و Reconciliation نیاز باشد.

سؤال مرور درس

پس از Completed شدن یک کلید، تکرار همان درخواست چه می‌کند؟

نمایش پاسخ تشریحی
باید بدون اجرای دوباره اثر مالی، نتیجه قبلی را برگرداند.

درس 12 · REST

Retry، Timeout و سناریوهای مصاحبه Senior

Timeout کلاینت به معنی شکست قطعی عملیات سمت سرور نیست. ممکن است درخواست نرسیده، اجرا و پاسخ گم شده، یا هنوز در حال پردازش باشد.

سناریورفتار درست
درخواست به سرور نرسیدهتلاش مجدد با همان شناسه منطقی
عملیات قبلاً Commit شدهبرگرداندن نتیجه بدون برداشت دوباره
پردازش همچنان در جریانعدم شروع عملیات مالی دوم
نمونه ثبت Handler تاب‌آوریC#
builder.Services
    .AddHttpClient("PaymentClient")
    .AddStandardResilienceHandler();

این نمونه به پکیج Microsoft.Extensions.Http.Resilience وابسته است. سیاست‌های پیش‌فرض Retry را نباید بدون بررسی روی POST مالی استفاده کرد؛ Backoff، وضعیت مبهم و Idempotency باید تنظیم شوند.

پرسش مصاحبه

اگر درخواست انتقال وجه روی Instance نخست موفق شود ولی پاسخ گم شود و Retry به Instance دوم برسد، راه‌حل چیست؟ استفاده از Idempotency-Key، محدودیت یکتایی پایدار و ثبت تراکنشی هماهنگ با تغییرات مالی.

سؤال مرور درس

چرا lock داخل حافظه دو Instance کافی نیست؟

نمایش پاسخ تشریحی
چون هر Instance حافظه مستقلی دارد و lock یکی مانع اجرای هم‌زمان Instance دیگر نمی‌شود.

درس 13 · API Versioning

API Versioning و اشتراک Business Logic

نسخه‌بندی API اجازه می‌دهد قرارداد جدیدی منتشر کنیم بی‌آنکه کلاینت‌های نسخه قدیمی از کار بیفتند.

نمونه کدHTTP
GET /api/v1/payments/1001
GET /api/v2/payments/1001

مثال تغییر Response

تغییر قرارداد خروجیJSON
// V1
{"id":1001,"amount":500000,"status":1}

// V2
{"id":1001,"amount":500000,"status":"Success","currency":"IRR"}

وقتی فقط Response DTO تغییر می‌کند، هر دو نسخه می‌توانند یک IPaymentService مشترک را استفاده کنند. لازم نیست منطق تجاری یا دیتابیس به‌صورت اجباری برای هر نسخه تکرار شود.

راه‌اندازی پکیج

نصب برای Controller-based APIbash
dotnet add package Asp.Versioning.Mvc
تنظیمات پایه Program.csC#
using Asp.Versioning;

درس 14 · API Versioning

Breaking و Non-Breaking Changes

Breaking Change تغییری است که می‌تواند سازگاری با مصرف‌کنندگان قرارداد قبلی را بشکند. Non-Breaking Change عموماً کلاینت‌های قبلی را بدون تغییر قابل استفاده نگه می‌دارد.

تغییر قراردادارزیابی متداول
اضافه‌کردن فیلد اختیاری به پاسخاغلب Non-Breaking
حذف یا تغییر نام فیلد پاسخBreaking
تغییر نوع فیلد از int به stringBreaking
اجباری‌کردن پارامتر قبلاً اختیاریBreaking
اضافه‌کردن پارامتر اختیاریاغلب Non-Breaking
تغییر معنای تجاری فیلدBreaking
DTOهای نسخه اول و دومC#
public record PaymentResponseV1(long Id, decimal Amount, int Status);

public record PaymentResponseV2(long Id, decimal Amount,
    string Status, string Currency);
دقتاضافه‌کردن فیلد جدید در قراردادهای بسیار سخت‌گیرانه هم ممکن است Breaking باشد؛ تصمیم نهایی وابسته به رفتار مصرف‌کنندگان است.

درس 15 · API Versioning

URL Versioning: روش اول نسخه‌بندی API

در روش URL Versioning نسخه در مسیر درخواست قرار می‌گیرد. این روش واضح، آسان برای تست و مناسب بسیاری از APIهای عمومی است.

نمونه کدHTTP
GET /api/v1/payments/1001
GET /api/v2/payments/1001

تنظیم نسخه از URL

Program.csC#
using Asp.Versioning;

builder.Services.AddControllers();
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = false;
    options.ReportApiVersions = true;
    options.ApiVersionReader = new UrlSegmentApiVersionReader();
}).AddMvc();

var app = builder.Build();
app.MapControllers();
app.Run();

کنترلر نسخه اول

PaymentsV1Controller.csC#
[ApiController]
[ApiVersion("1.0")]
[Route("api/v{version:apiVersion}/payments")]
public class PaymentsV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(long id) => Ok(new
    {
        Id = id, Amount = 500000, Status = 1
    });
}

کنترلر نسخه دوم

PaymentsV2Controller.csC#
[ApiController]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/payments")]
public class PaymentsV2Controller : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(long id) => Ok(new
    {

    });

نکته درباره Routingدر این مثال نام Controller در Route دخالت ندارد، چون Route به‌صورت صریح با payments تعریف شده است. هر اکشن بر اساس ApiVersion مربوط به Controller انتخاب می‌شود.

مزایا و محدودیت

مزیت‌ها: نسخه در URL واضح است و تست و مستندسازی آسان‌تر می‌شود. محدودیت: برای استفاده از نسخه جدید باید آدرس عوض شود و URLهای نسخه‌دار جداگانه مدیریت شوند.

سؤال مرور درس

وقتی نسخه در /api/v2/payments قرار می‌گیرد از چه ApiVersionReader استفاده می‌کنیم؟

نمایش پاسخ تشریحی
UrlSegmentApiVersionReader. این جزوه در همین بخش از API Versioning متوقف می‌شود.
