PART 1 — LLM Fundamentals

AI & LLM Fundamentals

Token چیست؟

Token واحدی است که Model هنگام پردازش Language با آن کار می‌کند. Token الزاماً یک واژه یا یک کاراکتر نیست؛ ممکن است یک واژهٔ کامل، بخشی از واژه، عدد، نشانه یا حتی بخشی از نمایش یک نویسه باشد.

یک جمله، چند روش برای شکستن

جملهٔ زیر را در نظر بگیرید:

«پرداخت ناموفق بود!»

یک انسان احتمالاً سه واژه و یک علامت می‌بیند. اما Model مستقیماً با «واژه» کار نمی‌کند. یک جزء به نام Tokenizer می‌تواند Text را به قطعه‌هایی شبیه نمونهٔ زیر تبدیل کند:

بود

این فقط یک نمایش آموزشی است. Tokenizer یک Model واقعی ممکن است همین Text را به قطعه‌های کمتر یا بیشتری تقسیم کند. بنابراین بدون اجرای Tokenizer دقیق همان Model نمی‌توان شمارش قطعی ارائه داد.

تعریف Token و Tokenizer

Token یکی از واحدهای موجود در Vocabulary یک Model است. Vocabulary فهرست قطعه‌هایی است که Tokenizer می‌تواند آن‌ها را به شناسه‌های عددی نگاشت کند.

Tokenizer ابزاری است که دو عملیات اصلی انجام می‌دهد:

  • Encode: Text را به دنباله‌ای از Token IDها تبدیل می‌کند.
  • Decode: Token IDها را دوباره به Text قابل‌خواندن تبدیل می‌کند.

Token ID یک عدد است که به یک Token در Vocabulary اشاره می‌کند. Model به‌جای نگهداری رشتهٔ «پرداخت»، شناسهٔ عددی آن را دریافت می‌کند و سپس آن شناسه را به نمایش عددی مناسب برای محاسبات داخلی تبدیل می‌کند.

Token با واژه یا کاراکتر یکسان نیست

واحدمعنانمونه
واژهواحدی که انسان در Language تشخیص می‌دهد.پرداخت‌ها ممکن است یک واژه دیده شود.
Characterیک نویسه در Text است.«پ» یک Character است.
Byteواحد ذخیره‌سازی داده است.یک Character در UTF-8 ممکن است چند Byte داشته باشد.
Tokenقطعه‌ای وابسته به Vocabulary و Tokenizer است.ممکن است واژه، بخشی از آن یا یک نشانه باشد.

در نتیجه، فرمول عمومی و دقیقی مانند «هر واژه برابر یک Token است» وجود ندارد. حتی دو Text با تعداد کاراکتر یکسان می‌توانند Token Count متفاوتی داشته باشند.

قانون عملی: برای Estimate اولیه می‌توان از اندازهٔ Text کمک گرفت، اما برای محدودیت واقعی Context یا محاسبهٔ دقیق، Tokenizer همان Model را اجرا کنید.

چرا از Subword استفاده می‌شود؟

اگر Vocabulary فقط شامل واژه‌های کامل باشد، باید فهرست بسیار بزرگی از شکل‌های مختلف واژه‌ها نگهداری شود و واژه‌های جدید نیز مشکل‌ساز می‌شوند. بسیاری از Tokenizerها از قطعه‌های کوچک‌تر از واژه، یعنی Subword، استفاده می‌کنند.

برای نمونه، یک Tokenizer ممکن است واژهٔ انگلیسی unhelpful را به قطعه‌هایی مانند un، help و ful تبدیل کند. این تقسیم صرفاً نمونه است و برای همهٔ Modelها یکسان نیست.

Subwordها چند مزیت دارند:

  • ریشه‌ها و پسوندهای مشترک می‌توانند دوباره استفاده شوند.
  • واژهٔ تازه را می‌توان از قطعه‌های شناخته‌شده ساخت.
  • Vocabulary لازم نیست تمام واژه‌های ممکن را جداگانه نگه دارد.

نقطهٔ مقابل این است که یک واژهٔ ساده برای انسان ممکن است به چند Token تبدیل شود و Token Count افزایش پیدا کند.

Tokenization به Model وابسته است

هر Model با Tokenizer و Vocabulary مشخصی آموزش دیده است. تغییر Tokenizer بعد از Training ساده نیست، زیرا Token IDها و Parameterهای Model با همان Vocabulary یاد گرفته شده‌اند.

بنابراین ممکن است دو Model برای Text یکسان:

  • تعداد Token متفاوتی تولید کنند؛
  • مرز Tokenها را در جای متفاوت قرار دهند؛
  • برای قطعه‌های مشابه Token IDهای متفاوت داشته باشند.

Token ID عددی هیچ معنای عمومی میان Modelها ندارد. برای مثال، ID فرضی 1842 ممکن است در یک Vocabulary به یک قطعه اشاره کند و در Vocabulary دیگر معنای کاملاً متفاوتی داشته باشد.

نکات مهم Tokenization در Text فارسی

ظاهر یکسان یا نزدیک دو Text فارسی تضمین نمی‌کند نمایش Unicode و Tokenization آن‌ها یکسان باشد. چند عامل مهم‌اند:

  • فاصله و نیم‌فاصله: «می شود»، «می‌شود» و «میشود» رشته‌های یکسانی نیستند.
  • نویسه‌های عربی و فارسی: شکل‌های مختلف «ی» و «ک» ممکن است Code Point متفاوت داشته باشند.
  • اعراب و علامت‌ها: افزودن یا حذف نشانه‌های ترکیبی می‌تواند ورودی Tokenizer را تغییر دهد.
  • ترکیب Languageها: Text فارسی همراه با نام API، Code و عدد ممکن است الگوی Tokenization متفاوتی ایجاد کند.

Unicode Normalization یعنی تبدیل نمایش‌های معادل یا نزدیک Unicode به یک شکل استاندارد. Normalization می‌تواند برای پاک‌سازی داده مفید باشد، اما نباید بدون شناخت نیاز Business انجام شود؛ زیرا برخی تفاوت‌ها ممکن است در دامنهٔ شما معنی‌دار باشند.

نکته: مقدار Token Count زبان‌های مختلف را با یک نسبت ثابت مقایسه نکنید. شمارش واقعی به Model، Tokenizer و خود Text وابسته است.

Special Token چیست؟

برخی Tokenها برای نمایش محتوای عادی نیستند و نقش کنترلی دارند. به چنین واحدهایی Special Token گفته می‌شود.

بسته به Model و قالب مکالمه، Special Tokenها می‌توانند مرز Messageها، پایان دنباله یا بخش‌های ساختاری ورودی را مشخص کنند. این Tokenها همیشه در Text قابل‌مشاهده نیستند، اما ممکن است بخشی از ورودی واقعی Model باشند.

به همین دلیل، جمع Tokenهای Text خام همیشه دقیقاً با Usage گزارش‌شده توسط Provider برابر نیست. قالب‌سازی Messageها و داده‌های کنترلی نیز می‌توانند در شمارش اثر داشته باشند.

یک Tokenizer آموزشی با C#

مثال زیر Text را به واژه‌ها و نشانه‌ها تقسیم و سپس هر قطعه را به یک ID فرضی نگاشت می‌کند. این کد الگوریتم Tokenizer واقعی یک LLM نیست؛ هدف آن فقط نمایش جریان Encode است.

using System.Text.RegularExpressions;

var text = "پرداخت ناموفق بود!";

var pieces = Regex.Matches(
        text,
        @"[\p{L}\p{N}]+|[^\s\p{L}\p{N}]")
    .Select(match => match.Value)
    .ToArray();

var vocabulary = new Dictionary<string, int>
{
    ["پرداخت"] = 104,
    ["ناموفق"] = 287,
    ["بود"] = 63,
    ["!"] = 9
};

var tokenIds = pieces
    .Select(piece => vocabulary[piece])
    .ToArray();

Console.WriteLine(string.Join(" | ", pieces));
Console.WriteLine(string.Join(", ", tokenIds));

خروجی

پرداخت | ناموفق | بود | !
104, 287, 63, 9

Regex.Matches در این مثال Letter و Numberهای پشت‌سرهم را یک قطعه و هر نشانهٔ دیگر را قطعه‌ای جدا در نظر می‌گیرد. سپس Dictionary نقش یک Vocabulary کوچک و فرضی را دارد.

Tokenizer واقعی معمولاً قواعد و Vocabulary بزرگ‌تری دارد، واژه را ممکن است به Subword تقسیم کند و برای ورودی ناشناخته رفتار مشخصی دارد. بنابراین از این کد برای محاسبهٔ Token Count یک Model واقعی استفاده نکنید.

Token چگونه پاسخ LLM را می‌سازد؟

در درس قبل دیدیم که LLM پاسخ را گام‌به‌گام می‌سازد. در هر گام، Model برای Tokenهای ممکن Score تولید می‌کند. سپس براساس روش انتخاب، Token بعدی مشخص می‌شود.

  1. Prompt به Input Tokenها تبدیل می‌شود.
  2. Model توزیع Score مربوط به Token بعدی را محاسبه می‌کند.
  3. یک Token انتخاب و به خروجی افزوده می‌شود.
  4. Input قبلی به‌علاوهٔ Token تازه، Context گام بعد را می‌سازد.
  5. فرایند تا تولید Stop Token یا رسیدن به محدودیت خروجی ادامه پیدا می‌کند.

وقتی Application پاسخ را به‌صورت Streaming نمایش می‌دهد، ممکن است داده در قطعه‌هایی دریافت شود که دقیقاً با واژه‌های قابل‌مشاهده برابر نیستند. UI باید Text دریافتی را پیوسته کنار هم قرار دهد.

رابطهٔ Token با Context Window

Context Window ظرفیت Tokenهایی است که Model در یک اجرا می‌تواند در محدودهٔ پردازش خود داشته باشد. این ظرفیت معمولاً فقط مربوط به سؤال کاربر نیست.

در یک AI Agent، اجزای زیر می‌توانند Token مصرف کنند:

  • System و Developer Instructions
  • Messageهای قبلی Conversation
  • درخواست فعلی کاربر
  • Tool Description و Schemaها
  • Tool Resultها
  • Documentهای بازیابی‌شده برای RAG
  • Tokenهای پاسخ Model

اگر مجموع ورودی و فضای لازم برای خروجی از ظرفیت مجاز عبور کند، Application باید بخشی از Context را حذف، خلاصه یا فشرده کند. جزئیات این موضوع در درس بعدی، Context Window، بررسی می‌شود.

Token Budget برنامه‌ای برای تقسیم ظرفیت Token میان اجزای درخواست است. هدف این است که اطلاعات مهم جا بگیرند و برای پاسخ نیز فضای کافی باقی بماند.

اثر Token بر Cost و Performance

Providerها معمولاً Usage ورودی و خروجی را برحسب Token گزارش می‌کنند. قرارداد قیمت‌گذاری و نام فیلدها ممکن است میان Providerها متفاوت باشد، اما Token Count یکی از ورودی‌های اصلی محاسبهٔ Cost است.

  • Input Token: Tokenهایی که برای پردازش به Model ارسال می‌شوند.
  • Output Token: Tokenهایی که Model در پاسخ تولید می‌کند.
  • Cached Token: در برخی سرویس‌ها بخشی از Input تکراری می‌تواند با سازوکار Cache جداگانه محاسبه شود.

Token بیشتر معمولاً محاسبات، زمان یا Cost بیشتری ایجاد می‌کند، اما رابطهٔ دقیق به Model، Provider، Cache، Batch و زیرساخت وابسته است. برای تصمیم Production باید Usage واقعی اندازه‌گیری شود.

مدیریت Token در AI Agent

Agent معمولاً نسبت به یک Chat ساده Context بیشتری دارد، چون Toolها، Memory و نتیجهٔ چند گام را همراه خود حمل می‌کند. بدون مدیریت Token، Agent ممکن است کند، پرهزینه یا دچار حذف اطلاعات مهم شود.

چند راهکار عملی:

  • فقط Toolهای مرتبط با Goal فعلی را در اختیار Model قرار دهید.
  • Tool Resultهای بزرگ را Filter یا خلاصه کنید و دادهٔ غیرضروری را نفرستید.
  • Conversation History قدیمی را با سیاست مشخص Compact کنید.
  • در RAG به‌جای سند کامل، Chunkهای مرتبط را بازیابی کنید.
  • برای Output سقف و Format روشن تعریف کنید.
  • Input، Output و Cost را در Observability ثبت کنید.

کم‌کردن Token نباید کورکورانه باشد. حذف جزئیات ضروری ممکن است کیفیت تصمیم را کاهش دهد. هدف، بیشترین Context نیست؛ هدف، مرتبط‌ترین Context کافی است.

اشتباهات رایج

  • هر Token را یک واژه دانستن: Token ممکن است کوچک‌تر یا بزرگ‌تر از یک واژه باشد.
  • استفاده از Tokenizer اشتباه: شمارش یک Model لزوماً برای Model دیگر معتبر نیست.
  • شمردن فقط پیام کاربر: Instructions، History، Toolها و Output نیز در Budget نقش دارند.
  • حذف Text براساس Character Count: Character Count معادل Token Count نیست و بریدن Text می‌تواند بخش مهمی را ناقص کند.
  • پرکردن کامل Context: باید فضای کافی برای Output و مراحل احتمالی Agent باقی بماند.
  • نادیده‌گرفتن Unicode فارسی: نیم‌فاصله و شکل نویسه‌ها می‌توانند Tokenization را تغییر دهند.

مشاهدهٔ پاسخ پیشنهادی

خیر. برای پاسخ دقیق باید Tokenizer همان Model اجرا شود. علامت تعجب، نیم‌فاصله، پسوند، ترکیب فارسی و انگلیسی، Vocabulary و الگوریتم Tokenizer می‌توانند مرز و تعداد Tokenها را تغییر دهند.

جمع‌بندی

  • Token واحد پردازش Language در Model است و الزاماً با واژه یا Character برابر نیست.
  • Tokenizer با Encode، Text را به Token ID تبدیل می‌کند و با Decode خروجی را به Text برمی‌گرداند.
  • Tokenization به Vocabulary و Tokenizer همان Model وابسته است.
  • Subword اجازه می‌دهد واژه‌های متنوع از قطعه‌های مشترک ساخته شوند.
  • نیم‌فاصله، Unicode، نشانه‌ها و ترکیب Languageها می‌توانند Token Count را تغییر دهند.
  • Instructions، History، Toolها، RAG و Output همگی بخشی از Token Budget یک Agent هستند.
  • برای شمارش قطعی باید ابزار رسمی یا Tokenizer سازگار با Model هدف استفاده شود.
