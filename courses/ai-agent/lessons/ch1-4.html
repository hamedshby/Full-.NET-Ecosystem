PART 1 — LLM Fundamentals

AI & LLM Fundamentals

Context Window

یک LLM در هر لحظه فقط مقدار محدودی از متن را می‌تواند «ببیند» و برای پاسخ‌دهی از آن استفاده کند. به این مقدار محدود، Context Window می‌گویند. فهمیدن درست این محدودیت، پایهٔ طراحی هر Agent است.

یک مثال ساده

تصور کنید با یک دستیار مجازی صحبت می‌کنید. ابتدا می‌گویید:

گفتگوی کوتاه

شما: «نام من سارا است.»

مدل: «سلام سارا! چه کمکی می‌توانم بکنم؟»

شما: «سلام را با اسمی که قبلاً گفتم کامل کن.»

برای اینکه مدل بتواند به جملهٔ دوم پاسخ درست بدهد، باید «سارا» را از پیام قبلی خودش به‌یاد بسپارد. اگر آن پیام دیگر در Context مدل نباشد، نمی‌دانم اسم شما چیست. این مثال ساده نشان می‌دهد که Context Window مرز حافظهٔ کوتاه‌مدت مدل است.

Token چیست و چه ارتباطی با Context Window دارد؟

یک LLM متن را حرف‌به‌حرف نمی‌خواند، بلکه آن را به قطعات کوچکی به نام Token تقسیم می‌کند. یک Token لزوماً یک کلمه یا یک حرف نیست؛ می‌تواند بخشی از یک کلمه باشد. برای نمونه، جملهٔ «Context window is limited» توسط Tokenizer معمولاً به چند Token تقسیم می‌شود که در کنار هم معنا می‌سازند.

مدل ذهنی: Token را مانند «حبه‌های لگو» تصور کنید که جمله‌ها از آن‌ها ساخته می‌شوند. Context Window تعداد حبه‌هایی است که روی میز جا می‌گیرد؛ اگر حبه‌های بیشتری بسازید، از لبهٔ میز می‌فتند.

واحد اندازه‌گیری Context Window بر پایهٔ Token است، نه کاراکتر یا کلمه. به همین دلیل دو جمله با طول یکسان کاراکتری، می‌توانند تعداد Token متفاوتی داشته باشند.

Context Window دقیقاً چیست؟

Context Window حداکثر تعداد Tokenهایی است که یک مدل در یک فراخوانی می‌تواند هم ورودی (Input) و هم خروجی (Output) خود را در آن جای دهد. هر چیزی که وارد می‌شود و هر چیزی که مدل تولید می‌کند، Token محسوب می‌شود و از این ظرفیت مصرف می‌کند.

  • ورودی: پیام‌های System، User و Assistant، اسناد، کد یا هر متنی که به مدل می‌فرستید.
  • خروجی: پاسخی که مدل تولید می‌کند. در طول تولید پاسخ، فضای مصرف‌شده افزایش می‌یابد.
  • مجموع این دو: هرگز نباید از ظرفیت Context Window مدل بیشتر شود.

به عبارت دیگر، Context Window حافظهٔ کوتاه‌مدت یک مدل در هر request است. مدل بین دو فراخوانی مستقل، به‌صورت پیش‌فرض هیچ چیز را به‌یاد نمی‌ماند؛ برای ادامهٔ یک گفتگو باید خودتان تاریخچه را هر بار دوباره بفرستید تا در Context مدل قرار بگیرد.

چه چیزهایی داخل Context Window قرار می‌گیرند؟

در یک Agent معمولاً چند دستهٔ محتوا وارد می‌شود و همهٔ آن‌ها Token مصرف می‌کنند:

محتوانمونهنکته
System Instructionsدستورالعمل و رفتار مدلدر هر فراخوانی دوباره فرافرستید و همیشه Tokenمصرف می‌کند.
User / Assistant Messagesتاریخچهٔ گفتگوهرچه گفتگو بلندتر، حافظهٔ بیشتری از Context می‌گیرد.
محتوای برگرداندهمتن یک فایل، نتیجهٔ یک Tool callبرای کار با فایل، باید محتوای آن را در ورودی بفرستید.
RAG یا مقاله‌ای اضافهمقالهٔ مرتبط با سؤالافزودن متن بیشتر، تمام مدل را سریع‌تر به سقف می‌رساند.

نکتهٔ کلیدی این است که «هر چیزی که مدل باید بداند، باید در ورودی بفرستید». هرچه محتوای بیشتری بفرستید، سریع‌تر به سقف Context Window می‌رسید.

وقتی Context Window پر می‌شود چه اتفاقی می‌افتد؟

یک LLM نمی‌تواند محتوایی فراتر از Context Window خود پردازش کند. بسته به سرویس، یکی از این رفتارها مشاهده می‌شود:

  • خطای تجاوز از سقف: فراخوانی به دلیل تجاوز از حداکثر Token رد می‌شود (خطای Context Length Exceeded).
  • بریدن (Truncation): بخشی از ابتدا یا انتهای متن حذف می‌شود تا در سقف جای بگیرد.
  • فراموشی: بدون خطای ظاهر، مدل بخش‌های قدیمی را دیگر نمی‌ببیند و در نتیجه جزئیات اولیهٔ گفتگو را از دست می‌دهد.

رفتار مشاهده‌پذیر

اگر در یک گفتگوی بلند از مدل بپرسید «اسم من چه بود که اول گفتگو گفتم؟» و تاریخچهٔ اولیه بریده یا از Context خارج شده باشد، مدل نمی‌تواند درست جواب بدهد؛ نه به این دلیل که «حافظه‌اش نیست»، بلکه به این دلیل که آن اطلاعات هرگز به او فرستاده نشده است.

این تفاوت مهم است: فراموشی یک LLM در طول یک فراخوانی، نتیجهٔ نبودن محتوا در Context Window است، نه ضعف حافظهٔ انسانی.

مقیاس‌گیری Context برای یک Agent

زمانی PDF بزرگ یا یک Repository کد را به یک Agent می‌دهید، اولین سؤال این است که «آیا همهٔ آن در Context Window جا می‌گیرد؟»

نمونهٔ تخمین اولیه

فرض کنید یک سند ۱۰٬۰۰۰ واژه‌ای به انگلیسی دارید. برای برخی مدل‌ها، یک تخمین اولیهٔ رایج این است که هر واژهٔ انگلیسی به‌طور متوسط تقریباً ۱٫۳ تا ۱٫۵ Token مصرف می‌کند. بر این اساس، این سند حدود ۱۳٬۰۰۰ تا ۱۵٬۰۰۰ Token تولید می‌کند.

این فقط یک تخمین برای شروع است و عدد قطعی نیست. شمارش واقعی به Model و Tokenizer آن وابسته است (در درس Token دیدیم که نمی‌توان بدون اجرای Tokenizer همان مدل، Token Count دقیق به دست آورد). پیش از فرستادن محتوای سنگین به مدل، آن را با ابزار شمارش سازگار با همان مدل بررسی کنید و به‌جای ارسال کل فایل، بخش مرتبط یا خلاصهٔ آن را بفرستید.

روش‌های مدیریت Context Window

برای ساختن Agentهای پایدار، کنار این محدودیت را مدیریت می‌کنید. این روش‌ها جایگزین یکدیگر نیستند؛ معمولاً با هم استفاده می‌شوند:

  • مختصرکردن: به‌جای تاریخچهٔ کامل، خلاصهٔ آن را به مدل بفرستید.
  • انتخاب: تنها محتوای مرتبط با سؤال فعلی را در Context قرار دهید، نه همه‌چیز.
  • پنجرهٔ مرور: بخش قدیمی تاریخچه را حذف و فقط چند پیام آخر را نگه‌دارید.
  • استفاده از جستجو: به‌جای فرستم یک مقالهٔ بلند، نتیجهٔ جستجوی مرتبط را به مدل بدهید.
  • تقسیم محتوا: یک سند بلند را به بخش‌های کوچک تقسیم و فقط بخش‌های لازم را فرستید.
نکتهٔ مهم: هدف، کاهش محتوایی است که مدل واقعاً برای پاسخ درست به آن نیاز دارد؛ حذف نامنطقی اطلاعات، کیفیت پاسخ را پایین می‌آورد.

اشتباهات رایج

  • تصور اینکه مدل گفتگو را بیاد می‌سپارد: LLM به‌صورت پیش‌فرض حافظه ندارد؛ باید تاریخچه را هر بار بفرستید.
  • فرستادن کل محتوا بدون شمارش: سندهای بلند زود به سقف Context می‌رسند و خطا یا بریدن ایجاد می‌کنند.
  • واحد اندازه‌گیری را اشتباه فهمیدن: Context با Token سنجیده می‌شود، نه با تعداد حروف یا واژه.
  • نادیده‌گرفتن خروجی: پاسخ تولیدشدهٔ مدل نیز از Context Window مصرف می‌کند، نه فقط ورودی.
  • فرض اینکه همهٔ مدل‌ها یک اندازه‌اند: اندازهٔ Context Window بین مدل‌ها با هم متفاوت است و باید از مستندات هر مدل بررسی شود.

جمع‌بندی

  • Context Window حداکثر Tokenهایی است که یک LLM در یک فراخوانی هم ورودی و هم خروجی می‌تواند جا دهد.
  • مدل به‌صورت پیش‌فرض حافظه ندارد؛ برای ادامهٔ گفتگو باید تاریخچه را دوباره بفرستید.
  • ورودی، خروجی، اسناد و تاریخچهٔ گفتگو همگی Token مصرف می‌کنند.
  • پر‌شدن Context به خطا، بریدن یا فراموشی محتوای قدیمی منجر می‌شود.
  • با مختصرکردن، انتخاب، پنجرهٔ مرور و تقسیم محتوا، Context یک Agent را در محدوده نگه‌دارید.
