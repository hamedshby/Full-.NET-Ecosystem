پاسخ کوتاه مناسب مصاحبه

Model Binding in ASP.NET Core is the process of reading data from an HTTP request, such as route values, query strings, form fields, headers, or the request body, and converting that data into action method parameters or .NET objects.

After binding, Model Validation checks whether the created model satisfies the validation rules defined by attributes such as [Required], [Range], or custom validators. Any binding or validation errors are stored in ModelState.

When using [ApiController], ASP.NET Core automatically returns HTTP 400 Bad Request if the model is invalid, so we usually don't need to manually check ModelState.IsValid.

Model Binding چیست؟

در ASP.NET Core، فرآیند Model Binding مسئول تبدیل اطلاعات خام موجود در HTTP Request به پارامترهای قابل استفاده در Controller یا Endpoint است.

برای مثال فرض کنید چنین Actionی داریم: 

[HttpGet("{id}")]
public IActionResult GetProduct(int id, string? category)
{
    ...
}

اگر Request زیر ارسال شود: 

GET /api/products/10?category=mobile

در این حالت، سیستم Model Binding مقدار 10 را از Route می‌خواند و به پارامتر id تبدیل می‌کند. همچنین مقدار mobile را از Query String می‌خواند و در پارامتر category قرار می‌دهد.

بنابراین، Controller لازم نیست خودش Request را Parse کند؛ این کار توسط Framework انجام می‌شود.

Model Binding داده را از کجا می‌خواند؟

در ASP.NET Core، داده‌های ورودی می‌توانند از بخش‌های مختلف Request خوانده شوند:

  • از Route Values، مانند /products/10
  • از Query String، مانند ?page=2&pageSize=20
  • از Request Body، معمولاً برای JSON
  • از Form Data، مانند فرم‌های HTML یا Multipart Form
  • از Headers

Attributeهای مهم Model Binding

برای مشخص‌کردن صریح منبع داده می‌توانیم از Attributeهای زیر استفاده کنیم:

Attribute منبع داده
[FromRoute] خواندن از Route
[FromQuery] خواندن از Query String
[FromBody] خواندن از Request Body
[FromForm] خواندن از Form Data
[FromHeader] خواندن از HTTP Header
[FromServices] دریافت Dependency از DI Container

مثال Model Binding با DTO

برای Requestهای پیچیده معمولاً به‌جای دریافت چند پارامتر جداگانه، از DTO استفاده می‌کنیم. 

public class CreateProductRequest
{
    public string Name { get; set; } = null!;
    public decimal Price { get; set; }
    public int Stock { get; set; }
}

[HttpPost]
public IActionResult Create([FromBody] CreateProductRequest request)
{
    ...
}

حالا اگر Client چنین JSONی ارسال کند: 

{
  "name": "Laptop",
  "price": 1500,
  "stock": 10
}

ابتدا JSON توسط Input Formatter خوانده و Deserialize می‌شود و سپس یک نمونه از CreateProductRequest ساخته می‌شود.

در ASP.NET Core، این کار معمولاً با System.Text.Json انجام می‌شود.

Model Validation چیست؟

بعد از اینکه Model Binding داده را به یک Object دات‌نت تبدیل کرد، مرحله Model Validation شروع می‌شود.

در این مرحله، Framework بررسی می‌کند که داده‌های ورودی قوانین Validation تعریف‌شده روی مدل را رعایت می‌کنند یا نه.

رایج‌ترین روش تعریف Validation استفاده از Data Annotations است.

مثال Validation با Data Annotation

public class CreateProductRequest
{
    [Required]
    [MaxLength(100)]
    public string Name { get; set; } = null!;

    [Range(1, 100000)]
    public decimal Price { get; set; }

    [Range(0, 10000)]
    public int Stock { get; set; }
}

در این مثال، نام محصول اجباری است، طول آن نمی‌تواند بیشتر از 100 کاراکتر باشد، قیمت باید در محدوده تعیین‌شده باشد و مقدار Stock هم نمی‌تواند خارج از محدوده تعریف‌شده قرار بگیرد.

ModelState چیست؟

تمام خطاهایی که در مراحل Model Binding و Model Validation رخ می‌دهند داخل ModelState ذخیره می‌شوند.

برای مثال اگر کاربر برای یک فیلد عددی مقدار غیرعددی ارسال کند، خطای Binding ایجاد می‌شود. اگر مقدار عددی معتبر باشد ولی قانون [Range] را نقض کند، خطای Validation ایجاد می‌شود. 

[HttpPost]
public IActionResult Create(CreateProductRequest request)
{
    if (!ModelState.IsValid)
    {
        return BadRequest(ModelState);
    }

    return Ok();
}

تفاوت Binding Error و Validation Error

این دو مفهوم به هم مرتبط هستند، ولی دقیقاً یکسان نیستند.

نوع خطا مثال
Binding Error ارسال رشته "abc" برای یک فیلد از نوع int
Validation Error ارسال مقدار -10 برای فیلدی که دارای [Range(0, 100)] است

در خطای Binding، Framework نتوانسته داده ورودی را به نوع موردنظر تبدیل کند. اما در خطای Validation، تبدیل انجام شده است ولی مقدار تولیدشده قوانین مدل را نقض کرده است.

نقش [ApiController]

زمانی که Controller با Attribute زیر مشخص شود: 

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
}

رفتارهای مفیدی به‌صورت خودکار فعال می‌شوند که یکی از مهم‌ترین آن‌ها Automatic Model Validation است.

اگر Model معتبر نباشد، Framework قبل از اجرای Action معمولاً پاسخ 400 Bad Request برمی‌گرداند.

بنابراین معمولاً دیگر لازم نیست داخل هر Action چنین کدی بنویسیم: 

if (!ModelState.IsValid)
{
    return BadRequest(ModelState);
}
نکتهٔ مصاحبه‌ای: در Web APIهای مدرن ASP.NET Core که از [ApiController] استفاده می‌کنند، بررسی دستی ModelState.IsValid معمولاً لازم نیست.

ترتیب کلی اجرای Request

یک مدل ذهنی ساده از فرآیند اجرای Request به این شکل است:

  1. Request وارد ASP.NET Core Pipeline می‌شود.
  2. Routing مشخص می‌کند کدام Endpoint یا Action باید اجرا شود.
  3. Model Binding داده‌ها را از Route، Query، Body یا سایر منابع می‌خواند.
  4. داده‌ها به Typeهای دات‌نت یا DTO تبدیل می‌شوند.
  5. Model Validation روی Object تولیدشده اجرا می‌شود.
  6. خطاهای Binding و Validation داخل ModelState ذخیره می‌شوند.
  7. در صورت استفاده از [ApiController]، اگر Model نامعتبر باشد، معمولاً پاسخ 400 به‌صورت خودکار برگردانده می‌شود.
  8. اگر Model معتبر باشد، Action اجرا می‌شود.

مثال کامل

public class CreateUserRequest
{
    [Required]
    [MaxLength(100)]
    public string Name { get; set; } = null!;

    [Required]
    [EmailAddress]
    public string Email { get; set; } = null!;

    [Range(18, 120)]
    public int Age { get; set; }
}

[ApiController]
[Route("api/users")]
public class UsersController : ControllerBase
{
    [HttpPost]
    public IActionResult Create([FromBody] CreateUserRequest request)
    {
        return Ok(request);
    }
}

اگر Client چنین Requestی بفرستد: 

{
  "name": "",
  "email": "invalid-email",
  "age": 10
}

ابتدا Body به CreateUserRequest تبدیل می‌شود. سپس Validation اجرا می‌شود و چند خطا ایجاد می‌شود:

  • مقدار Name معتبر نیست.
  • فرمت Email صحیح نیست.
  • مقدار Age خارج از Range مجاز است.

به دلیل وجود [ApiController]، معمولاً Action اجرا نمی‌شود و Framework مستقیماً پاسخ 400 Bad Request برمی‌گرداند.

آیا Validation فقط با Data Annotation انجام می‌شود؟

خیر. برای Validation روش‌های مختلفی وجود دارد.

  • استفاده از Data Annotation مانند [Required] و [Range]
  • استفاده از Custom Validation Attribute
  • پیاده‌سازی IValidatableObject
  • استفاده از Libraryهایی مثل FluentValidation
  • پیاده‌سازی Business Validation در Service یا Domain Layer
نکتهٔ مهم معماری: Model Validation معمولاً برای بررسی صحت ورودی HTTP مناسب است، اما Business Ruleهای اصلی نباید فقط به Validation Attributeهای Controller وابسته باشند. قوانین مهم Domain بهتر است در لایه Domain یا Application نیز enforce شوند.

Model Validation و Business Validation چه تفاوتی دارند؟

نوع مثال
Model Validation Email اجباری است، طول Name حداکثر 100 است، Age باید عدد مثبت باشد.
Business Validation کاربر اجازه برداشت بیش از موجودی حساب را ندارد.

بنابراین، Validation مربوط به شکل و ساختار Request معمولاً در API Layer انجام می‌شود، اما Ruleهای تجاری مهم باید در لایه مناسب Business یا Domain بررسی شوند.

نکات مهم مصاحبه‌ای

  • در ASP.NET Core، Model Binding قبل از اجرای Action انجام می‌شود.
  • بعد از Binding، Model Validation اجرا می‌شود.
  • خطاهای هر دو مرحله در ModelState قرار می‌گیرند.
  • هنگام استفاده از [ApiController]، Model نامعتبر معمولاً به‌صورت خودکار پاسخ 400 Bad Request ایجاد می‌کند.
  • برای Complex Typeها در Web API، Body معمولاً با JSON Deserialize می‌شود.
  • برای مشخص‌کردن صریح منبع داده می‌توان از Attributeهایی مانند [FromRoute]، [FromQuery] و [FromBody] استفاده کرد.
  • قوانین Business مهم نباید فقط به Data Annotation وابسته باشند.

جمع‌بندی نهایی برای مصاحبه

در ASP.NET Core، Model Binding داده‌های HTTP Request را از منابعی مثل Route، Query String، Body، Form و Header می‌خواند و آن‌ها را به پارامترهای Action یا Objectهای دات‌نت تبدیل می‌کند. بعد از آن، Model Validation قوانین تعریف‌شده روی Model را بررسی می‌کند. خطاهای هر دو مرحله داخل ModelState ذخیره می‌شوند.

در Controllerهایی که از [ApiController] استفاده می‌کنند، اگر Model نامعتبر باشد، ASP.NET Core معمولاً قبل از اجرای Action به‌صورت خودکار پاسخ 400 Bad Request برمی‌گرداند.
