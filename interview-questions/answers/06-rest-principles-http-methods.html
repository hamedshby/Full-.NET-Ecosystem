پاسخ کوتاه مناسب مصاحبه

REST (Representational State Transfer) is an architectural style for designing networked APIs around resources — things like users or orders — identified by URIs. A REST API is stateless: each request carries all the information the server needs, and the server keeps no client session between requests.

Clients interact with resources using a small, fixed set of HTTP methods (GET, POST, PUT, PATCH, DELETE), each with a well-defined meaning, and the server returns representations of resources (usually JSON) along with a meaningful HTTP status code.

REST یعنی چه؟

REST یک سبک معماری برای طراحی API است، نه یک پروتکل یا استاندارد رسمی. ایدهٔ اصلی این است که هر چیزی در سیستم — مثل یک کاربر، یک سفارش، یا یک محصول — به‌عنوان یک Resource در نظر گرفته می‌شود که یک آدرس یکتا (URI) دارد، مثلاً /api/orders/42.

به‌جای اینکه برای هر عملیات یک Endpoint اختصاصی مثل /getOrder یا /deleteOrder بسازیم، همان یک آدرس ثابت را داریم و نوع عملیات را با HTTP Method مشخص می‌کنیم.

مدل ذهنی ساده

REST را مثل یک کتابخانه تصور کنید. هر کتاب یک شمارهٔ قفسهٔ ثابت (URI) دارد. شما برای «خواندن» کتاب (GET)، «اضافه کردن» کتاب جدید (POST)، «جایگزین کردن کامل» یک کتاب (PUT)، یا «برداشتن» کتاب (DELETE) از همان آدرس قفسه استفاده می‌کنید؛ فقط نوع درخواستتان فرق می‌کند، نه آدرس.

اصول اصلی REST

  • Client-Server: جدا بودن مسئولیت Client (نمایش/تعامل) از Server (داده و منطق کسب‌وکار)، که باعث می‌شود این دو مستقل از هم تکامل پیدا کنند.
  • Statelessness: هر Request باید تمام اطلاعات لازم (مثل Token احراز هویت) را خودش حمل کند؛ Server هیچ Session‌ای بین Requestها نگه نمی‌دارد.
  • Cacheability: پاسخ‌ها باید صریحاً مشخص کنند Cache-پذیر هستند یا نه، تا Performance بهتر شود.
  • Uniform Interface: یک قرارداد یکنواخت شامل شناسایی Resource با URI، دستکاری آن از طریق Representation (مثل JSON)، پیام‌های خودتوضیح (Self-descriptive)، و در حالت ایده‌آل، HATEOAS.
  • Layered System: Client نمی‌داند مستقیماً با Server اصلی صحبت می‌کند یا با یک لایهٔ میانی مثل Load Balancer یا Gateway.
  • Code on Demand (اختیاری): امکان ارسال کد اجراشدنی (مثل JavaScript) از Server به Client، که کمتر در APIهای معمول استفاده می‌شود.
نکتهٔ مصاحبه‌ای: Statelessness رایج‌ترین اصلی است که دربارهٔ آن سؤال می‌شود؛ نکتهٔ کلیدی این است که این یعنی «بدون Session سمت Server»، نه اینکه سیستم اصلاً حالتی ندارد (داده‌ها همچنان در دیتابیس State دارند).

متدهای اصلی HTTP

متد هدف Idempotent؟ Safe؟
GET خواندن یک Resource یا لیستی از Resourceها، بدون تغییر در Server بله بله
POST ایجاد یک Resource جدید (یا اجرای عملیاتی که در قالب CRUD ساده نمی‌گنجد) خیر خیر
PUT جایگزینی کامل یک Resource موجود با مقدار جدید بله خیر
PATCH اعمال تغییر جزئی (Partial Update) روی یک Resource موجود معمولاً خیر خیر
DELETE حذف یک Resource مشخص بله خیر

Safe یعنی متد هیچ تغییری در وضعیت Server ایجاد نمی‌کند. Idempotent یعنی اجرای چندبارهٔ همان درخواست، نتیجهٔ نهایی یکسانی دارد — برای مثال، حذف یک Resource که از قبل حذف شده، باز هم همان وضعیت «وجود ندارد» را نتیجه می‌دهد، پس DELETE Idempotent است، هرچند Safe نیست.

مثال در ASP.NET Core Web API

[ApiController]
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll() => Ok(_orders);

    [HttpGet("{id}")]
    public IActionResult GetById(int id)
    {
        var order = _repository.Find(id);
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    public IActionResult Create(OrderDto dto)
    {
        var created = _repository.Add(dto);
        return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
    }

    [HttpPut("{id}")]
    public IActionResult Replace(int id, OrderDto dto)
    {
        _repository.Replace(id, dto);
        return NoContent();
    }

    [HttpPatch("{id}")]
    public IActionResult UpdatePartial(int id, JsonPatchDocument<OrderDto> patch)
    {
        _repository.ApplyPatch(id, patch);
        return NoContent();
    }

    [HttpDelete("{id}")]
    public IActionResult Delete(int id)
    {
        _repository.Remove(id);
        return NoContent();
    }
}

توجه کنید که آدرس Resource (api/orders یا api/orders/{id}) در همهٔ Actionها ثابت است؛ فقط نوع عملیات با Attributeهای [HttpGet]، [HttpPost] و... مشخص می‌شود.

کدهای وضعیت (Status Codes) مهم

  • 200 OK: درخواست موفق بوده و پاسخی برگردانده شده (مناسب GET، PUT، PATCH).
  • 201 Created: Resource جدیدی ساخته شده؛ معمولاً همراه با Header Location (مناسب POST).
  • 204 No Content: عملیات موفق بوده اما بدنه‌ای برای برگرداندن وجود ندارد (مناسب DELETE یا PUT).
  • 400 Bad Request: ورودی نامعتبر یا ناقص است.
  • 401 Unauthorized / 403 Forbidden: به‌ترتیب یعنی کاربر شناسایی نشده، یا شناسایی شده اما اجازهٔ دسترسی ندارد.
  • 404 Not Found: Resource درخواست‌شده وجود ندارد.
  • 409 Conflict: درخواست با وضعیت فعلی Resource تناقض دارد (مثلاً ایجاد رکورد تکراری).
  • 500 Internal Server Error: خطای پیش‌بینی‌نشده در سمت Server.

چند نکتهٔ کاربردی طراحی REST

  • URIها باید اسم Resource باشند نه فعل: /orders درست است، نه /getOrders.
  • از جمع (Plural) برای نام Resourceها استفاده کنید: /orders، نه /order.
  • روابط تودرتو را با Nesting نشان دهید: /customers/5/orders برای سفارش‌های مشتری شماره ۵.
  • از Query String برای فیلتر، مرتب‌سازی و صفحه‌بندی استفاده کنید: /orders?status=pending&page=2.
  • Versioning را از ابتدا در نظر بگیرید، مثلاً /api/v1/orders، تا تغییرات آینده Breaking Change ایجاد نکنند.

جمع‌بندی نهایی برای مصاحبه

REST یک سبک معماری است که API را حول محور Resourceها طراحی می‌کند و بر اصولی مثل Statelessness، Uniform Interface و Cacheability استوار است. متدهای HTTP (GET، POST، PUT، PATCH، DELETE) عملیات استاندارد روی Resourceها را مشخص می‌کنند، و هرکدام ویژگی‌های خاص خود از نظر Safe و Idempotent بودن دارند. طراحی خوب REST یعنی URIهای معنادار، استفادهٔ درست از متدها و کدهای وضعیت، و رعایت Statelessness — نکاتی که هم در مصاحبه و هم در پروژه‌های واقعی ASP.NET Core اهمیت زیادی دارند.
