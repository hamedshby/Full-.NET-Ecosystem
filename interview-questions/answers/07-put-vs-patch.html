پاسخ کوتاه مناسب مصاحبه

PUT and PATCH are both HTTP methods used to update an existing resource, but they differ in scope and semantics. PUT replaces the entire resource with the representation sent in the request body — any field not included is expected to be removed or reset to its default. PATCH applies a partial update, modifying only the fields specified, leaving the rest of the resource untouched.

Another key distinction: PUT is idempotent by definition — sending the same PUT request multiple times always results in the same resource state. PATCH is not guaranteed to be idempotent, especially when the patch describes an operation (like incrementing a value) rather than a final state.

PUT یعنی چه؟

PUT برای جایگزین‌کردن کامل یک Resource استفاده می‌شود. وقتی یک Request از نوع PUT ارسال می‌کنید، انتظار می‌رود کل Body، نمایانگر وضعیت نهایی و کامل آن Resource باشد. اگر فیلدی در Body نباشد، سرور معمولاً آن را حذف یا به مقدار پیش‌فرض بازمی‌گرداند — دقیقاً مثل این‌که کل Object قدیمی را با Object جدید جایگزین کنید.

به همین دلیل، PUT معمولاً برای عملیات Create-or-Replace هم به کار می‌رود: اگر Resource با آن Id وجود نداشته باشد، بسیاری از APIها آن را می‌سازند؛ اگر وجود داشته باشد، آن را کامل جایگزین می‌کنند.

PATCH یعنی چه؟

PATCH برای اعمال یک تغییر جزئی روی Resource استفاده می‌شود. فقط فیلدهایی که در Body آمده‌اند تغییر می‌کنند و بقیهٔ فیلدها دست‌نخورده باقی می‌مانند. این یعنی Client لازم نیست کل Object را دوباره بفرستد؛ فقط تفاوت‌ها (Delta) کافی است.

PATCH برای سناریوهایی مثل تغییر یک فیلد ساده (مثلاً فقط IsActive یا فقط Email) یا برای APIهایی با Payload حجیم، بسیار کارآمدتر و شبکه‌دوستانه‌تر از PUT است.

مدل ذهنی ساده

PUT را مثل این تصور کنید که کل فرم یک کاربر را پاک می‌کنید و از نو با اطلاعات جدید پر می‌کنید — هر فیلدی که خالی بماند، در واقع خالی ثبت می‌شود. اما PATCH مثل این است که فقط یک خط از فرم را اصلاح کنید و بقیهٔ فرم دست‌نخورده بماند.

مثال در ASP.NET Core Web API

// PUT: replaces the entire resource
[HttpPut("{id}")]
public IActionResult UpdateProduct(int id, ProductDto product)
{
    // product must contain ALL fields (Name, Price, Stock, ...)
    // any omitted field is treated as its default value
    _service.Replace(id, product);
    return NoContent();
}

// PATCH: updates only the provided fields
[HttpPatch("{id}")]
public IActionResult PatchProduct(int id, JsonPatchDocument<ProductDto> patchDoc)
{
    var product = _service.GetById(id);
    patchDoc.ApplyTo(product);
    _service.Update(id, product);
    return NoContent();
}

در ASP.NET Core، PATCH معمولاً با JsonPatchDocument (بر اساس استاندارد JSON Patch — RFC 6902) یا با یک DTO جزئی (Partial DTO) که فیلدهای Nullable دارد، پیاده‌سازی می‌شود.

مقایسهٔ کلی

ویژگی PUT PATCH
نوع بروزرسانی کامل (Full Replace) جزئی (Partial Update)
Body مورد انتظار کل Resource فقط فیلدهای تغییریافته یا لیست عملیات
Idempotency همیشه Idempotent است لزوماً Idempotent نیست
فرمت رایج Body DTO کامل JSON Patch (RFC 6902) یا DTO جزئی با Nullable
ریسک اصلی حذف ناخواسهٔ فیلدهای ارسال‌نشده پیچیدگی بیشتر در پیاده‌سازی و Validation

چرا Idempotency اهمیت دارد؟

  • PUT Idempotent است: چون کل Resource را با یک مقدار مشخص جایگزین می‌کند، ارسال چندبارهٔ همان Request همیشه همان نتیجهٔ نهایی را تولید می‌کند.
  • PATCH می‌تواند Idempotent نباشد: اگر PATCH یک عملیات نسبی توصیف کند (مثلاً «مقدار Stock را یک واحد کم کن»)، اجرای چندبارهٔ آن نتیجه‌های متفاوتی می‌دهد. اما اگر PATCH یک مقدار نهایی مشخص را ست کند (مثلاً «Email را برابر این مقدار قرار بده»)، می‌تواند Idempotent باشد.
  • این تفاوت در طراحی API، تأثیر مستقیم روی نحوهٔ Retry کردن Requestها توسط Client و Proxyها دارد.
نکتهٔ مصاحبه‌ای: یک اشتباه رایج، استفاده از PUT برای بروزرسانی جزئی است — یعنی فقط چند فیلد از DTO را ست کردن و بقیه را با مقدار پیش‌فرض ارسال کردن. این کار باعث Overwrite ناخواستهٔ داده‌های موجود می‌شود و یکی از باگ‌های رایج در APIهای واقعی است.

چه زمانی از کدام استفاده کنیم؟

  1. اگر Client کل Object جدید را در اختیار دارد و می‌خواهد وضعیت قبلی را کاملاً جایگزین کند → PUT.
  2. اگر Client فقط چند فیلد خاص را تغییر می‌دهد و نمی‌خواهد بقیهٔ Resource دست بخورد → PATCH.
  3. اگر Payload حجیم است و Bandwidth اهمیت دارد (مثلاً اپلیکیشن موبایل) → PATCH معمولاً بهینه‌تر است.
  4. اگر سادگی پیاده‌سازی و پیش‌بینی‌پذیری مهم‌تر از بهینه‌سازی Payload است → PUT راحت‌تر و کم‌خطاتر است.

جمع‌بندی نهایی برای مصاحبه

PUT برای جایگزینی کامل یک Resource استفاده می‌شود و همیشه Idempotent است؛ هر فیلدی که در Body نیاید، از بین می‌رود یا به مقدار پیش‌فرض برمی‌گردد. PATCH برای اعمال یک تغییر جزئی روی Resource به کار می‌رود، فقط فیلدهای مشخص‌شده را تغییر می‌دهد و لزوماً Idempotent نیست. انتخاب بین این دو به این بستگی دارد که Client قرار است چه مقدار از Resource را در اختیار داشته باشد و ارسال کند: کل Object (PUT) یا فقط تفاوت‌ها (PATCH).
