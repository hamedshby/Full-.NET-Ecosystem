پاسخ کوتاه مناسب مصاحبه

A middleware in ASP.NET Core is a small piece of code that sits in the request pipeline and gets a chance to handle an incoming HttpContext before and/or after the rest of the pipeline runs. Each middleware receives a reference to the next middleware in the chain and decides whether to call it (pass the request forward) or short-circuit the pipeline (handle the request itself and return without calling next()).

Middleware components run in exactly the order they are registered in Program.cs — on the way in, top to bottom; on the way out, bottom to top — which is why registration order is one of the most frequently misunderstood (and asked-about) topics in ASP.NET Core.

Middleware یعنی چه؟

Middleware یک Component نرم‌افزاری کوچک و مستقل است که در مسیر پردازش هر Request در ASP.NET Core قرار می‌گیرد. هر Middleware به شیء HttpContext دسترسی دارد، می‌تواند آن را بخواند یا تغییر دهد، و سپس تصمیم می‌گیرد که آیا کنترل را به Middleware بعدی بدهد یا خودش پاسخ نهایی را تولید کند.

از نظر فنی، هر Middleware چیزی نیست جز یک Delegate (یا کلاسی با متد InvokeAsync) با این امضای ساده: «یک Request بگیر، کاری انجام بده، و در صورت نیاز به بعدی پاس بده».

مدل ذهنی ساده

Middlewareها را مثل حلقه‌های تودرتوی یک پیاز تصور کنید. Request از بیرونی‌ترین لایه وارد می‌شود و لایه‌به‌لایه به سمت مرکز (Endpoint نهایی) پیش می‌رود. Response از همان لایه‌ها اما به‌ترتیب معکوس، از مرکز به بیرون بازمی‌گردد. هر لایه هم روی مسیر رفت و هم روی مسیر برگشت می‌تواند کاری انجام دهد.

نکتهٔ کلیدی این است که هر Middleware کاملاً کنترل دارد که آیا اجازه دهد Request به لایهٔ داخلی‌تر برسد یا نه — و همین ویژگی، پایهٔ مفهوم Short-circuiting است.

ثبت Middleware در Program.cs

var app = builder.Build();

app.UseExceptionHandler("/error"); // لایهٔ بیرونی‌ترین
app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers(); // نزدیک‌ترین به مرکز

app.Run();

هر فراخوانی app.Use... یک Middleware جدید را به انتهای زنجیره اضافه می‌کند. ترتیب فراخوانی این متدها در کد، دقیقاً همان ترتیبی است که در زمان اجرا رعایت می‌شود.

ترتیب اجرا دقیقاً چطور کار می‌کند؟

فرض کنید سه Middleware به نام‌های A، B و C به همین ترتیب ثبت شده‌اند. مسیر واقعی اجرا این‌گونه است:

  1. Request وارد A می‌شود → کد قبل از next() در A اجرا می‌شود.
  2. A با فراخوانی next()، کنترل را به B می‌دهد → کد قبل از next() در B اجرا می‌شود.
  3. B با فراخوانی next()، کنترل را به C می‌دهد.
  4. C آخرین Middleware است (یا Endpoint را اجرا می‌کند) و Response تولید می‌شود.
  5. کنترل به B بازمی‌گردد و کد بعد از next() در B اجرا می‌شود.
  6. در نهایت کنترل به A بازمی‌گردد و کد بعد از next() در A اجرا می‌شود.

پس ترتیب اجرا روی Request به شکل A → B → C است، اما روی Response دقیقاً برعکس: C → B → A.

نوشتن یک Middleware سفارشی

app.Use(async (context, next) =>
{
    if (!context.Request.Headers.ContainsKey("X-Api-Key"))
    {
        context.Response.StatusCode = 401;
        await context.Response.WriteAsync("Missing API key");
        return; // next() فراخوانی نمی‌شود؛ Pipeline اینجا متوقف می‌شود
    }

    await next(); // ادامهٔ مسیر به سمت Middleware بعدی

    // این خط بعد از برگشت از بقیهٔ Pipeline اجرا می‌شود
    context.Response.Headers.Append("X-Processed-By", "CustomMiddleware");
});

اگر شرط برقرار نباشد و next() فراخوانی نشود، هیچ‌کدام از Middlewareهای بعدی — و حتی Endpoint نهایی — هرگز اجرا نخواهند شد. به این حالت Short-circuiting گفته می‌شود و برای سناریوهایی مثل Authentication ناموفق، Rate Limiting، یا Health Check بسیار پرکاربرد است.

سه سبک نوشتن Middleware

سبک توضیح مناسب برای
Inline Delegate مستقیماً با app.Use(async (context, next) => ...) نوشته می‌شود منطق ساده و کوتاه
کلاس Convention-based کلاسی با Constructor (RequestDelegate next) و متد InvokeAsync(HttpContext) منطق پیچیده‌تر، تست‌پذیری بهتر
IMiddleware پیاده‌سازی اینترفیس رسمی؛ از طریق DI Container ثبت و مدیریت می‌شود Middlewareهایی با Dependencyهای تزریق‌شده و طول عمر مشخص

چند نکتهٔ مهم دربارهٔ ترتیب

  • ترتیب ثبت Middlewareها، ترتیب واقعی اجراست — نه ترتیب تعریف کلاس‌ها یا فایل‌ها، بلکه دقیقاً همان خطوطی که در Program.cs نوشته شده‌اند.
  • UseAuthentication باید همیشه قبل از UseAuthorization ثبت شود، وگرنه هویت کاربر هنوز مشخص نشده در حالی که سیستم می‌خواهد دربارهٔ دسترسی تصمیم بگیرد.
  • UseRouting باید قبل از هر Middleware‌ای بیاید که به Endpoint انتخاب‌شده نیاز دارد (مثل Authorization بر اساس Policy مربوط به یک Endpoint خاص).
  • جابه‌جا کردن این ترتیب معمولاً خطا نمی‌دهد؛ به‌جایش رفتار نادرست و اشکالاتی مثل ۴۰۱/۴۰۳ غیرمنتظره یا نادیده‌گرفته‌شدن یک Policy تولید می‌کند — به همین دلیل Debug کردن آن سخت‌تر از یک Exception معمولی است.
نکتهٔ مصاحبه‌ای: اگر مصاحبه‌کننده بپرسد «اگر next() را صدا نزنیم چه می‌شود؟»، پاسخ درست این است: بقیهٔ Pipeline اصلاً اجرا نمی‌شود و همان Middleware مسئول تولید Response نهایی است — این دقیقاً همان مفهوم Short-circuit است.

جمع‌بندی نهایی برای مصاحبه

Middleware قطعه‌ای از کد است که در Request Pipeline قرار می‌گیرد، به HttpContext دسترسی دارد و می‌تواند قبل و بعد از فراخوانی next() منطقی اجرا کند یا با ندادن کنترل به بعدی، Pipeline را Short-circuit کند. ترتیب اجرا دقیقاً برابر با ترتیب ثبت در Program.cs است: روی مسیر Request از بالا به پایین، و روی مسیر Response دقیقاً برعکس. رعایت‌نکردن این ترتیب — به‌خصوص بین Routing، Authentication و Authorization — یکی از رایج‌ترین منابع باگ‌های پنهان در پروژه‌های واقعی ASP.NET Core است.
