پاسخ کوتاه مناسب مصاحبه

In ASP.NET Core Web API, I usually handle exceptions globally instead of adding try-catch blocks to every controller action. I use a centralized exception handler, such as custom middleware or IExceptionHandler, to catch unhandled exceptions from the request pipeline.

The handler logs the exception, maps known exception types to appropriate HTTP status codes, and returns a consistent error response, preferably using ProblemDetails. For example, a validation exception may return 400, a not-found exception 404, a conflict exception 409, and unexpected exceptions 500.

In production, I avoid exposing stack traces or internal exception messages to the client. Detailed information should be logged internally, while the API returns a safe and predictable error contract.

Global Exception Handling چیست؟

در یک Web API، ممکن است Exception در بخش‌های مختلفی مثل Controller، Application Service، Repository یا حتی Infrastructure رخ دهد.

اگر در هر Action یک try-catch جداگانه بنویسیم، کد تکراری، شلوغ و سخت برای نگهداری می‌شود.

برای همین بهتر است Exceptionهای مدیریت‌نشده را در یک نقطه مرکزی از Pipeline بگیریم و Response استاندارد و یکسانی به Client برگردانیم.

چرا نباید در همه Controllerها try-catch بنویسیم؟

استفاده از try-catch در تمام Actionها معمولاً باعث تکرار منطق Handling می‌شود. 

[HttpGet("{id}")]
public async Task<IActionResult> Get(int id)
{
    try
    {
        var product = await _service.GetByIdAsync(id);
        return Ok(product);
    }
    catch (ProductNotFoundException ex)
    {
        return NotFound(ex.Message);
    }
    catch (Exception ex)
    {
        return StatusCode(500, "Internal Server Error");
    }
}

اگر ده‌ها Endpoint داشته باشیم، همین منطق بارها تکرار می‌شود.

در نتیجه بهتر است Controller فقط مسئول دریافت Request و برگرداندن Result باشد و Exception Handling در یک لایه مرکزی انجام شود.

روش‌های رایج Global Exception Handling

در ASP.NET Core چند روش رایج برای مدیریت Exception به‌صورت سراسری وجود دارد:

  • استفاده از Custom Exception Middleware
  • استفاده از UseExceptionHandler
  • استفاده از IExceptionHandler در نسخه‌های جدید ASP.NET Core
  • استفاده از Exception Filter در MVC

در پروژه‌های جدید، استفاده از IExceptionHandler یا Exception Handling Middleware معمولاً انتخاب تمیز و مناسبی است.

رویکرد پیشنهادی با IExceptionHandler

در نسخه‌های جدید ASP.NET Core می‌توان Exception Handling را با IExceptionHandler به‌صورت متمرکز پیاده‌سازی کرد. 

public sealed class GlobalExceptionHandler
    : IExceptionHandler
{
    private readonly ILogger<GlobalExceptionHandler> _logger;

    public GlobalExceptionHandler(
        ILogger<GlobalExceptionHandler> logger)
    {
        _logger = logger;
    }

    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        _logger.LogError(
            exception,
            "Unhandled exception occurred.");

        var statusCode = exception switch
        {
            ValidationException => StatusCodes.Status400BadRequest,
            NotFoundException => StatusCodes.Status404NotFound,
            ConflictException => StatusCodes.Status409Conflict,
            UnauthorizedAccessException => StatusCodes.Status401Unauthorized,
            _ => StatusCodes.Status500InternalServerError
        };

        var problemDetails = new ProblemDetails
        {
            Status = statusCode,
            Title = GetTitle(statusCode),
            Detail = statusCode == 500
                ? "An unexpected error occurred."
                : exception.Message,
            Instance = httpContext.Request.Path
        };

        httpContext.Response.StatusCode = statusCode;

        await httpContext.Response.WriteAsJsonAsync(
            problemDetails,
            cancellationToken);

        return true;
    }

    private static string GetTitle(int statusCode)
    {
        return statusCode switch
        {
            400 => "Bad Request",
            401 => "Unauthorized",
            404 => "Resource Not Found",
            409 => "Conflict",
            _ => "Internal Server Error"
        };
    }
}

ثبت Exception Handler

بعد از ساخت Handler باید آن را در DI Container ثبت کنیم. 

builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();

سپس Middleware مربوط به Exception Handling را به Pipeline اضافه می‌کنیم: 

app.UseExceptionHandler();

از این نقطه به بعد، Exceptionهای مدیریت‌نشده‌ای که در Pipeline بالا می‌آیند می‌توانند توسط Global Handler پردازش شوند.

مسیر Exception در Pipeline

اگر برای مثال یک Service چنین Exceptionی ایجاد کند: 

public async Task<Product> GetProductAsync(int id)
{
    var product = await _repository.GetByIdAsync(id);

    if (product is null)
        throw new NotFoundException(
            $"Product with id {id} was not found.");

    return product;
}

Controller لازم نیست Exception را بگیرد: 

[HttpGet("{id}")]
public async Task<ActionResult<Product>> Get(int id)
{
    var product = await _service.GetProductAsync(id);

    return Ok(product);
}

Exception از Service به سمت بالا حرکت می‌کند تا Global Exception Handler آن را دریافت کند.

سپس Handler آن را به یک HTTP Response مناسب تبدیل می‌کند.

Exception Mapping چیست؟

یکی از وظایف مهم Global Exception Handler تبدیل Exceptionهای مختلف به HTTP Status Code مناسب است.

Exception Status Code معنی
ValidationException 400 ورودی Request نامعتبر است
UnauthorizedAccessException 401 Authentication معتبر نیست
ForbiddenException 403 کاربر اجازه دسترسی ندارد
NotFoundException 404 Resource پیدا نشده است
ConflictException 409 درخواست با وضعیت فعلی Resource تداخل دارد
Exception 500 خطای غیرمنتظره سمت Server
نکتهٔ مصاحبه‌ای: نباید همه Exceptionها را به 500 تبدیل کنیم. Exceptionهای شناخته‌شده باید به Status Code معنادار تبدیل شوند.

چرا ProblemDetails مناسب است؟

برای اینکه Error Responseهای API ساختار ثابتی داشته باشند، بهتر است از ProblemDetails استفاده کنیم.

نمونهٔ Response می‌تواند به این شکل باشد: 

{
  "type": "https://httpstatuses.com/404",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "Product with id 100 was not found.",
  "instance": "/api/products/100"
}

در این حالت Client می‌تواند بدون وابستگی به متن‌های تصادفی Exception، یک Error Contract مشخص داشته باشد.

Response استاندارد خطا چه مزیتی دارد؟

داشتن یک ساختار استاندارد برای Error Response چند مزیت مهم دارد:

  • رفتار تمام Endpointها یکسان می‌شود.
  • Frontend یا Consumer راحت‌تر Errorها را پردازش می‌کند.
  • Logging و Monitoring ساده‌تر می‌شود.
  • تغییر ساختار Error در یک نقطه انجام می‌شود.
  • اطلاعات داخلی سیستم به شکل کنترل‌شده‌تری به Client نمایش داده می‌شود.

آیا باید Exception Message را به Client برگردانیم؟

بستگی به نوع Exception دارد.

برای Exceptionهای شناخته‌شده مثل Validation یا Not Found، می‌توان یک Message کنترل‌شده و مناسب برای Client برگرداند.

اما برای Exceptionهای غیرمنتظره بهتر است متن اصلی Exception، Stack Trace، Database Error یا جزئیات داخلی Server به Client نمایش داده نشود. 

Detail = statusCode == 500
    ? "An unexpected error occurred."
    : exception.Message;
نکتهٔ امنیتی: برگرداندن Stack Trace، Connection String، SQL Error یا اطلاعات داخلی سیستم می‌تواند Information Disclosure ایجاد کند.

Logging در Global Exception Handler

Global Exception Handler مکان مناسبی برای Log کردن Exceptionهای مدیریت‌نشده است. 

_logger.LogError(
    exception,
    "Unhandled exception occurred while processing {Method} {Path}",
    httpContext.Request.Method,
    httpContext.Request.Path);

در سیستم‌های Production بهتر است همراه Exception اطلاعاتی مثل موارد زیر هم ثبت شوند:

  • Request Path
  • HTTP Method
  • TraceId یا CorrelationId
  • UserId در صورت وجود
  • Service Name
  • Exception Type

TraceId چه کاربردی دارد؟

در سیستم‌های Distributed، مخصوصاً Microserviceها، بهتر است Error Response یک TraceId یا CorrelationId داشته باشد.

Client می‌تواند این شناسه را برای تیم پشتیبانی ارسال کند و توسعه‌دهنده با همان شناسه Log مربوط به Request را پیدا کند. 

problemDetails.Extensions["traceId"] =
    Activity.Current?.Id
    ?? httpContext.TraceIdentifier;

Response می‌تواند شبیه این باشد: 

{
  "title": "Internal Server Error",
  "status": 500,
  "detail": "An unexpected error occurred.",
  "traceId": "00-a12b34c56d..."
}

Business Exception چیست؟

بعضی Exceptionها نشان‌دهنده خرابی فنی نیستند؛ بلکه یک Rule تجاری رعایت نشده است.

برای مثال در سیستم پرداخت: 

if (account.Balance < amount)
{
    throw new InsufficientBalanceException(
        "Account balance is not sufficient.");
}

این Exception لزوماً نباید به 500 تبدیل شود، چون Server خراب نشده است؛ Request از نظر Business Rule قابل انجام نیست.

بسته به Contract سیستم، می‌توان آن را به Status Code مناسب مثل 400، 409 یا کد دیگری که برای API تعریف شده تبدیل کرد.

آیا برای هر خطا Exception ایجاد کنیم؟

خیر. Exception باید برای شرایط استثنایی یا شکست یک Operation استفاده شود، نه برای کنترل جریان عادی برنامه.

برای مثال اگر جستجوی اختیاری هیچ نتیجه‌ای نداشته باشد، ممکن است برگرداندن یک Result خالی منطقی‌تر از Throw کردن Exception باشد.

اما اگر Use Case انتظار دارد Resource حتماً وجود داشته باشد و نبودن آن باعث شکست Operation شود، یک NotFoundException می‌تواند منطقی باشد.

Exception Filter و Middleware چه تفاوتی دارند؟

ویژگی Middleware / IExceptionHandler Exception Filter
سطح اجرا HTTP Pipeline MVC Pipeline
دامنه پوشش وسیع‌تر Controller و Actionهای MVC
مناسب برای Global Handling بسیار مناسب مناسب در سناریوهای MVC-specific
وابستگی به MVC کمتر بیشتر

به همین دلیل برای Error Handling عمومی Web API معمولاً Middleware یا IExceptionHandler انتخاب عمومی‌تری است.

نمونه با Custom Middleware

روش کلاسیک دیگر، ساخت Custom Middleware است. 

public sealed class ExceptionHandlingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionHandlingMiddleware> _logger;

    public ExceptionHandlingMiddleware(
        RequestDelegate next,
        ILogger<ExceptionHandlingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception exception)
        {
            _logger.LogError(
                exception,
                "Unhandled exception occurred.");

            await HandleExceptionAsync(
                context,
                exception);
        }
    }

    private static async Task HandleExceptionAsync(
        HttpContext context,
        Exception exception)
    {
        var statusCode = exception switch
        {
            NotFoundException
                => StatusCodes.Status404NotFound,

            ValidationException
                => StatusCodes.Status400BadRequest,

            ConflictException
                => StatusCodes.Status409Conflict,

            _
                => StatusCodes.Status500InternalServerError
        };

        context.Response.StatusCode = statusCode;
        context.Response.ContentType = "application/problem+json";

        var problem = new ProblemDetails
        {
            Status = statusCode,
            Title = statusCode == 500
                ? "Internal Server Error"
                : exception.GetType().Name,

            Detail = statusCode == 500
                ? "An unexpected error occurred."
                : exception.Message
        };

        await context.Response.WriteAsJsonAsync(problem);
    }
}

سپس Middleware را در Pipeline ثبت می‌کنیم: 

app.UseMiddleware<ExceptionHandlingMiddleware>();

ترتیب Middleware اهمیت دارد؟

بله. Exception Handling Middleware باید به اندازه کافی در ابتدای Pipeline قرار بگیرد تا بتواند Exceptionهای Middlewareها و Endpointهای بعد از خودش را Catch کند. 

app.UseExceptionHandler();

app.UseHttpsRedirection();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

Middleware فقط می‌تواند Exceptionهایی را Catch کند که در Middlewareهای بعد از خودش رخ می‌دهند.

نکتهٔ مصاحبه‌ای: Middleware Pipeline در ASP.NET Core به شکل زنجیره‌ای است. Exception Handling Middleware باید قبل از بخش‌هایی قرار بگیرد که قصد داریم Exceptionهایشان را مدیریت کنیم.

Validation Errorها را چطور مدیریت کنیم؟

همه Validation Errorها الزاماً Exception نیستند.

برای مثال در Controllerهایی که از [ApiController] استفاده می‌کنند، خطاهای Model Validation معمولاً قبل از اجرای Action به‌صورت خودکار به 400 Bad Request تبدیل می‌شوند.

اما اگر در Application Layer از Validation Library یا Validation Service استفاده کنیم و ValidationException ایجاد شود، می‌توان آن را در Global Exception Handler مدیریت کرد.

Cancellation را نباید به‌عنوان Error معمولی در نظر گرفت

اگر Client اتصال را قطع کند یا Request Cancel شود، ممکن است OperationCanceledException یا TaskCanceledException ایجاد شود.

در بسیاری از سیستم‌ها این مورد نباید مانند یک Server Error واقعی با Severity بالا Log شود.

بنابراین بهتر است Cancellation را از Exceptionهای واقعی تفکیک کنیم. 

catch (OperationCanceledException)
    when (context.RequestAborted.IsCancellationRequested)
{
    // Client cancelled the request.
}

در Production چه اطلاعاتی نباید برگردانیم؟

در محیط Production نباید اطلاعات فنی حساس را داخل Error Response قرار دهیم.

  • Stack Trace
  • Database Connection String
  • SQL Query
  • File System Path
  • Server Information
  • Secret و Token
  • جزئیات داخلی Exceptionهای Infrastructure

این اطلاعات باید در Logging System ثبت شوند، نه اینکه برای Client ارسال شوند.

یک معماری تمیز برای Exception Handling

یک جریان مناسب در سیستم می‌تواند به این شکل باشد:

  1. Domain یا Application Layer یک Exception معنادار ایجاد می‌کند.
  2. Exception بدون Catch غیرضروری به سمت API Layer حرکت می‌کند.
  3. Global Exception Handler آن را دریافت می‌کند.
  4. Exception در Logging System ثبت می‌شود.
  5. نوع Exception به HTTP Status Code مناسب Mapping می‌شود.
  6. یک ProblemDetails استاندارد ساخته می‌شود.
  7. اطلاعات حساس حذف می‌شوند.
  8. TraceId به Response اضافه می‌شود.
  9. Response استاندارد به Client برگردانده می‌شود.

مدل ذهنی ساده

Global Exception Handler را می‌توان مثل آخرین دروازهٔ کنترل خطا در API تصور کرد.

هر بخشی از سیستم ممکن است یک مشکل ایجاد کند، اما به‌جای اینکه هر بخش تصمیم بگیرد چه Responseی به Client بدهد، Exception را به نقطه مرکزی می‌فرستد.

آن نقطه مرکزی تصمیم می‌گیرد خطا چگونه Log شود، چه Status Code داشته باشد و Client چه Responseای دریافت کند.

اشتباهات رایج در Exception Handling

  • استفاده از try-catch در تمام Controllerها
  • برگرداندن تمام Exceptionها با Status Code برابر 500
  • برگرداندن مستقیم exception.Message برای Exceptionهای ناشناخته
  • ارسال Stack Trace به Client
  • Log نکردن Exceptionهای غیرمنتظره
  • Log کردن یک Exception چند بار در لایه‌های مختلف
  • استفاده از Exception برای کنترل جریان عادی برنامه
  • نداشتن Error Contract یکسان بین Endpointها
  • نداشتن TraceId یا CorrelationId در سیستم‌های Distributed

نکات مهم مصاحبه‌ای

  • در Web API بهتر است Exception Handling در یک نقطه مرکزی انجام شود.
  • در ASP.NET Core می‌توان از IExceptionHandler، Middleware یا UseExceptionHandler استفاده کرد.
  • در Handler بهتر است Exceptionهای شناخته‌شده به HTTP Status Code مناسب Mapping شوند.
  • برای Error Response استاندارد، استفاده از ProblemDetails انتخاب مناسبی است.
  • در Production نباید Stack Trace یا جزئیات داخلی Exception برای Client ارسال شود.
  • Exceptionهای غیرمنتظره باید Log شوند و معمولاً پاسخ 500 دریافت می‌کنند.
  • در سیستم‌های Distributed بهتر است TraceId یا CorrelationId در Log و Response وجود داشته باشد.
  • در Controller بهتر است از try-catchهای تکراری جلوگیری شود.

جمع‌بندی نهایی برای مصاحبه

در ASP.NET Core Web API، برای مدیریت Exceptionها معمولاً از یک Global Exception Handler مثل IExceptionHandler یا یک Middleware مرکزی استفاده می‌کنم، تا مجبور نباشم در تمام Controllerها try-catch تکراری بنویسم.

Handler Exception را Log می‌کند، نوع آن را به HTTP Status Code مناسب تبدیل می‌کند و یک Response استاندارد مثل ProblemDetails به Client برمی‌گرداند. برای مثال Validation Error می‌تواند 400، Resource پیدا نشده 404، Conflict برابر 409 و Exception غیرمنتظره برابر 500 باشد.

در Production جزئیات داخلی مثل Stack Trace و Database Error برای Client ارسال نمی‌شوند. این اطلاعات فقط Log می‌شوند و بهتر است یک TraceId هم در Response وجود داشته باشد تا بتوان Request را در Logging یا Distributed Tracing پیدا کرد.
