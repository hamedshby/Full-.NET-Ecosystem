پاسخ کوتاه مناسب مصاحبه

The ASP.NET Core request pipeline is an ordered chain of middleware components that every incoming HTTP request passes through before a response is sent back. Each middleware can inspect or modify the request, decide whether to pass control to the next middleware (call next()), and then inspect or modify the response on the way back out.

The pipeline is built in Program.cs using WebApplicationBuilder/WebApplication, and the order in which middleware is registered is the order in which it runs — this ordering is one of the most common interview and real-world debugging topics in ASP.NET Core.

Pipeline یعنی چه؟

وقتی یک Request به یک ASP.NET Core Application می‌رسد، مستقیماً به Controller یا Endpoint نمی‌رود. ابتدا از یک زنجیرهٔ منظم از قطعات کوچک کد به نام Middleware عبور می‌کند. هر Middleware یک وظیفهٔ مشخص دارد — مثلاً Logging، Authentication، یا Exception Handling — و می‌تواند تصمیم بگیرد Request را به Middleware بعدی منتقل کند یا پاسخ را همان‌جا Short-circuit کند.

این مجموعهٔ به‌هم‌پیوسته را Request Pipeline می‌نامند، و در کد با IApplicationBuilder ساخته می‌شود.

مدل ذهنی ساده

Pipeline را مانند یک خط تولید در کارخانه تصور کنید. هر ایستگاه (Middleware) یک کار مشخص انجام می‌دهد و سپس محصول را به ایستگاهِ بعدی می‌فرستد. بعضی ایستگاه‌ها می‌توانند محصول را رد نکنند و همان‌جا آن را برگردانند — مثلاً اگر Authentication ناموفق باشد، دیگر لازم نیست محصول تا انتهای خط برود.

نکتهٔ مهم این است که Response هم از همان مسیر، اما به‌صورت برعکس، بازمی‌گردد؛ یعنی هر Middleware هم روی Request و هم روی Response تأثیر می‌گذارد.

ساخت Pipeline در Program.cs

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddAuthentication();
builder.Services.AddAuthorization();

var app = builder.Build();

app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseStaticFiles();

app.UseRouting();

app.UseCors();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();

هر خط app.Use... یک Middleware جدید را به Pipeline اضافه می‌کند، و ترتیب همین خطوط، ترتیب اجرای واقعی آن‌هاست.

سه روش اصلی تعریف Middleware

روش رفتار مثال کاربرد
Use Middleware را اجرا می‌کند و در انتها می‌تواند با فراخوانی next()، کنترل را به Middleware بعدی بدهد Logging، Exception Handling، Authentication
Run یک Middleware ترمینال است؛ هیچ next() ندارد و Pipeline را همان‌جا به پایان می‌رساند یک Endpoint ساده در انتهای Pipeline
Map / MapWhen بر اساس Path یا شرط، Pipeline را به یک شاخهٔ جداگانه هدایت می‌کند مسیرهای جداگانه برای API نسخهٔ قدیمی یا Health Check

نوشتن یک Middleware سفارشی

app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();

    await next(); // پاس دادن Request به Middleware بعدی

    sw.Stop();
    Console.WriteLine($"{context.Request.Path} took {sw.ElapsedMilliseconds}ms");
});

کدی که قبل از await next() است روی Request اجرا می‌شود؛ کدی که بعد از آن است، روی Response در مسیر بازگشت اجرا می‌شود. اگر next() فراخوانی نشود، Pipeline در همین‌جا Short-circuit می‌شود و باقی Middlewareها اصلاً اجرا نخواهند شد.

چرا ترتیب Middleware اهمیت حیاتی دارد؟

  • Exception Handling باید نزدیک ابتدای Pipeline باشد تا خطاهای Middlewareهای بعدی را هم بگیرد.
  • Routing باید قبل از Authentication و Authorization ثبت شود، چون تصمیم‌گیری دربارهٔ دسترسی نیاز به دانستن Endpoint هدف دارد.
  • Authentication باید قبل از Authorization بیاید — اول باید بدانیم کاربر کیست، بعد تصمیم بگیریم به چه چیزی اجازهٔ دسترسی دارد.
  • Static Files معمولاً زودتر ثبت می‌شود تا درخواست‌های فایل بدون عبور از Authentication یا Routing کامل پاسخ داده شوند.
نکتهٔ مصاحبه‌ای: جابه‌جا کردن UseAuthentication و UseAuthorization، یا قرار دادن آن‌ها قبل از UseRouting، یکی از رایج‌ترین اشتباهات در پروژه‌های واقعی است و معمولاً به‌صورت خطاهای مبهم ۴۰۱ یا ۴۰۳ ظاهر می‌شود.

مسیر رفت و برگشت یک Request

  1. Request وارد Kestrel (یا Server میزبان) می‌شود.
  2. Request وارد اولین Middleware ثبت‌شده می‌شود (مثلاً Exception Handler).
  3. هر Middleware به نوبت اجرا می‌شود و با next()، کنترل را به بعدی می‌دهد.
  4. در انتهای Pipeline، یک Endpoint (Controller Action یا Minimal API) اجرا و Response تولید می‌شود.
  5. Response از همان زنجیره، اما به‌ترتیب معکوس، عبور می‌کند و هر Middleware می‌تواند آن را هم بررسی یا تغییر دهد.
  6. Response نهایی به Client بازگردانده می‌شود.

مثال واقعی

فرض کنید یک Web API دارید که هم نیاز به Authentication دارد و هم باید Exception‌های پیش‌بینی‌نشده را با یک پیام یکسان به Client برگرداند. یک ترتیب منطقی می‌تواند این باشد:

  • UseExceptionHandler در ابتدا، تا هر خطایی در هر Middleware بعدی گرفته شود.
  • UseHttpsRedirection و UseStaticFiles بلافاصله بعد از آن.
  • UseRouting برای تعیین Endpoint هدف.
  • UseAuthentication و سپس UseAuthorization.
  • در نهایت MapControllers یا MapGet/MapPost برای Minimal APIها.

این نشان می‌دهد که Pipeline فقط یک لیست از Featureها نیست؛ بلکه یک تصمیم معماری دربارهٔ این است که هر Request دقیقاً چه مراحلی را باید طی کند و چرا با همین ترتیب.

جمع‌بندی نهایی برای مصاحبه

Request Pipeline در ASP.NET Core از زنجیره‌ای از Middleware تشکیل شده که هر Request باید از آن‌ها عبور کند. Middlewareها در Program.cs با متدهایی مثل Use، Run و Map ثبت می‌شوند، و ترتیب ثبت آن‌ها دقیقاً ترتیب اجراست. هر Middleware می‌تواند Request را قبل از رسیدن به Endpoint پردازش کند، تصمیم به Short-circuit کردن Pipeline بگیرد، و روی مسیر بازگشت Response را هم تغییر دهد. درک درست ترتیب Middlewareهایی مانند Exception Handling، Routing، Authentication و Authorization یکی از مهم‌ترین مهارت‌های عملی توسعه‌دهندهٔ ASP.NET Core است.
