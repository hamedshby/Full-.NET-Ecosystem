پاسخ کوتاه مناسب مصاحبه

Configuration in ASP.NET Core is a unified, provider-based system for supplying settings to an application from many sources — appsettings.json, environment-specific JSON files, environment variables, command-line arguments, user secrets, Azure Key Vault, and more. All of these sources are merged into a single IConfiguration object, using a well-defined override order: sources added later take precedence over sources added earlier.

Configuration is hierarchical (sections and sub-sections), can be read directly via IConfiguration, or — the recommended approach — bound strongly-typed to POCO classes and consumed through the Options pattern (IOptions<T>, IOptionsSnapshot<T>, IOptionsMonitor<T>).

Configuration یعنی چه؟

هر Application در دنیای واقعی به مقادیری نیاز دارد که نباید داخل کد Hardcode شوند — مثل Connection String، آدرس یک API خارجی، کلیدهای API، یا تنظیمات Logging. ASP.NET Core یک سیستم یکپارچه برای جمع‌آوری این مقادیر از منابع مختلف فراهم می‌کند که به آن Configuration System می‌گویند.

نکتهٔ کلیدی این است که Configuration فقط محدود به یک فایل JSON نیست؛ بلکه از چند منبع مختلف خوانده و در نهایت در یک شیء واحد به نام IConfiguration ترکیب می‌شود.

مدل ذهنی ساده

Configuration را مانند چند لایهٔ شفاف روی هم تصور کنید. لایهٔ اول appsettings.json است، لایهٔ بعدی appsettings.Development.json، بعد Environment Variables، و در آخر Command-line Arguments. اگر یک Key در چند لایه تکرار شده باشد، مقدار لایهٔ بالاتر (که دیرتر اضافه شده) برنده می‌شود. این یعنی می‌توانید یک مقدار پیش‌فرض در فایل تنظیم کنید و در Production یا هنگام Deploy، بدون تغییر کد، آن را از طریق Environment Variable Override کنید.

منابع پیش‌فرض Configuration و ترتیب آن‌ها

وقتی از WebApplication.CreateBuilder(args) استفاده می‌کنید، این منابع به‌صورت خودکار و به همین ترتیب اضافه می‌شوند (منابع پایین‌تر، اولویت بالاتر دارند):

ترتیب منبع توضیح
۱ appsettings.json تنظیمات پایه و مشترک برای همهٔ Environmentها
۲ appsettings.{Environment}.json Override بر اساس Environment جاری، مثل Development یا Production
۳ User Secrets فقط در Development؛ مقادیر حساس را خارج از کنترل نسخه نگه می‌دارد
۴ Environment Variables مناسب برای تنظیمات Container و Deployment
۵ Command-line Arguments بالاترین اولویت؛ معمولاً برای Override موقت هنگام اجرا

در Production معمولاً منابعی مثل Azure Key Vault، AWS Secrets Manager یا یک Configuration Server نیز به‌صورت Custom Provider اضافه می‌شوند.

خواندن مستقیم با IConfiguration

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

string? connectionString = builder.Configuration["ConnectionStrings:Default"];
string? logLevel = builder.Configuration["Logging:LogLevel:Default"];

app.Run();

در این حالت، Key‌های تو در تو (Nested) با علامت : از هم جدا می‌شوند. این روش ساده است اما در مقیاس بزرگ‌تر باعث پخش‌شدن Magic Stringها در کد می‌شود.

روش پیشنهادی: Options Pattern

به‌جای خواندن مستقیم مقادیر، بهترین شیوه این است که یک بخش از Configuration را به یک کلاس POCO Bind کنید: 

public class SmtpOptions
{
    public string Host { get; set; } = string.Empty;
    public int Port { get; set; }
    public bool EnableSsl { get; set; }
}

// Program.cs
builder.Services.Configure<SmtpOptions>(
    builder.Configuration.GetSection("Smtp"));

// در یک Service یا Controller
public class MailService(IOptions<SmtpOptions> options)
{
    private readonly SmtpOptions _smtp = options.Value;
}
Interface Lifetime رفتار در برابر تغییر Runtime
IOptions<T> Singleton مقدار یک‌بار در ابتدای اجرا خوانده می‌شود و تغییر نمی‌کند
IOptionsSnapshot<T> Scoped در هر Request مجدداً محاسبه می‌شود؛ برای مقادیر قابل تغییر مناسب است
IOptionsMonitor<T> Singleton تغییرات Runtime فایل را Live دنبال می‌کند و Event تغییر هم می‌دهد

افزودن یک Configuration Provider سفارشی

var builder = WebApplication.CreateBuilder(args);

builder.Configuration
    .AddJsonFile("appsettings.json", optional: false, reloadOnChange: true)
    .AddJsonFile($"appsettings.{builder.Environment.EnvironmentName}.json", optional: true)
    .AddEnvironmentVariables()
    .AddCommandLine(args);

هر متد Add... یک Provider جدید به زنجیرهٔ Configuration اضافه می‌کند؛ همان‌طور که در Middleware Pipeline ترتیب ثبت اهمیت دارد، اینجا هم ترتیب فراخوانی این متدها، اولویت منابع را مشخص می‌کند.

چند نکتهٔ مهم دیگر

  • reloadOnChange: بسیاری از Provider‌های JSON از این قابلیت پشتیبانی می‌کنند تا با تغییر فایل روی دیسک، مقدار در حافظه هم به‌روزرسانی شود — بدون نیاز به Restart.
  • Secrets Manager (User Secrets): مخصوص Development است و مقادیر حساس مثل رمز عبور را خارج از فایل‌های Commit‌شده در Git نگه می‌دارد.
  • Validation: با استفاده از ValidateDataAnnotations() یا Validate() روی OptionsBuilder، می‌توان از صحت مقادیر Configuration در زمان Startup اطمینان حاصل کرد.
  • Configuration به‌طور پیش‌فرض Case-Insensitive است و کلیدهای تو در تو با : (یا در Environment Variables با __) جدا می‌شوند.
نکتهٔ مصاحبه‌ای: یکی از سوالات رایج این است که «چرا Environment Variable برای یک Nested Key باید به‌جای : از __ استفاده کند؟» — دلیل آن این است که بسیاری از سیستم‌عامل‌ها (مخصوصاً Linux) اجازهٔ استفاده از : در نام Environment Variable را نمی‌دهند.

مثال واقعی

فرض کنید یک Web API دارید که در Development باید به یک Database محلی وصل شود و در Production باید Connection String را از یک Environment Variable امن بخواند، بدون هیچ تغییری در کد:

  • در appsettings.Development.json: ConnectionStrings:Default به یک SQL Server محلی اشاره دارد.
  • در Pipeline استقرار (CI/CD) یا Container، یک Environment Variable به نام ConnectionStrings__Default با مقدار واقعی Production تنظیم می‌شود.
  • چون Environment Variables بعد از فایل‌های JSON اضافه می‌شوند، در Production مقدار آن‌ها Override می‌شود — بدون نیاز به تغییر یا Rebuild کد.

این دقیقاً همان چیزی است که Configuration Layering در ASP.NET Core را قدرتمند می‌کند: یک تصمیم معماری برای جدا نگه داشتن تنظیمات از کد و از Environment به Environment.

جمع‌بندی نهایی برای مصاحبه

Configuration در ASP.NET Core یک سیستم Layered و Provider-based است که مقادیر را از چندین منبع (JSON، Environment Variables، Command-line، User Secrets و غیره) جمع‌آوری کرده و در یک IConfiguration واحد ترکیب می‌کند؛ منابعی که دیرتر اضافه می‌شوند، اولویت بالاتری دارند. بهترین شیوهٔ مصرف آن، Bind کردن به کلاس‌های POCO از طریق Options Pattern است (IOptions، IOptionsSnapshot، IOptionsMonitor) که هم Type-Safety می‌دهد و هم امکان واکنش به تغییرات Runtime را فراهم می‌کند. تسلط بر ترتیب منابع، تفاوت این سه Interface، و نحوهٔ افزودن Provider سفارشی، از مهارت‌های اصلی هر توسعه‌دهندهٔ ASP.NET Core محسوب می‌شود.
