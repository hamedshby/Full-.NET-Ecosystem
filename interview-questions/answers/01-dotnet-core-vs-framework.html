پاسخ کوتاه مناسب مصاحبه

.NET Framework is the original, Windows-only implementation of .NET. .NET Core was a redesigned, open-source, cross-platform implementation built for modern workloads such as cloud services, containers, and high-performance web APIs. After .NET Core 3.1, Microsoft dropped “Core” from the product name, so .NET 5 and later are simply called .NET.

Modern .NET supports side-by-side runtime versions, flexible deployment, the dotnet CLI, and generally better performance and scalability. .NET Framework is still supported, but it is mainly used for existing Windows applications or technologies such as ASP.NET Web Forms that are not available in modern .NET. For a new application, I would normally choose the latest supported .NET version; I would keep .NET Framework only when a legacy dependency or Windows-specific technology requires it.

ابتدا نام‌ها را درست کنیم

.NET Framework نسخهٔ اصلی و قدیمی Platform دات‌نت است که برای Windows ساخته شد. سال‌ها بعد Microsoft محصولی تازه با معماری مدرن‌تر به نام .NET Core ایجاد کرد.

نسخه‌های این مسیر ابتدا .NET Core 1.0 تا .NET Core 3.1 نام داشتند. از .NET 5 به بعد، واژهٔ Core از نام محصول حذف شد. بنابراین وقتی امروز می‌گوییم modern .NET یا فقط .NET، منظور ادامهٔ همان مسیر .NET Core است؛ نه نسخهٔ تازه‌ای از .NET Framework.

نکتهٔ مصاحبه‌ای: عبارت «.NET Core در برابر .NET Framework» هنوز رایج است، اما نام دقیق محصول امروزی .NET است.

مدل ذهنی ساده

.NET Framework را مانند خانه‌ای قدیمی و بزرگ تصور کنید که کاملاً برای Windows ساخته شده و بعضی سامانه‌های سازمانی سال‌هاست داخل آن زندگی می‌کنند. modern .NET خانه‌ای بازطراحی‌شده است که روی Windows، Linux و macOS اجرا می‌شود و برای Cloud، Container و سرویس‌های جدید آماده‌تر است.

خانهٔ جدید به این معنا نیست که خانهٔ قدیمی فوراً خراب یا بدون پشتیبانی شده است؛ فقط برای ساخت یک پروژهٔ جدید، معمولاً انتخاب پیش‌فرض بهتری است.

چه چیزهایی عملاً تغییر کرده‌اند؟

  1. Platform دیگر به Windows محدود نیست. یک Web API مدرن را می‌توان روی Linux Server یا Linux Container اجرا کرد.
  2. استقرار انعطاف‌پذیرتر شده است. هر Application می‌تواند Runtime مناسب خودش را داشته باشد و سرویس‌های مختلف مجبور نیستند همگی از یک نسخه استفاده کنند.
  3. معماری برای Cloud و Container مناسب‌تر است. Runtime ماژولارتر و Imageهای Container معمولاً کوچک‌تر و عملی‌تر هستند.
  4. Performance و Scalability به اولویت اصلی تبدیل شده‌اند. این موضوع برای Web API، Microservice و سیستم‌های پرترافیک اهمیت زیادی دارد.
  5. تجربهٔ توسعه یکپارچه‌تر شده است. با dotnet restore، dotnet build، dotnet test و dotnet run می‌توان چرخهٔ توسعه را از Command Line و در CI/CD اجرا کرد.
  6. نسخه‌گذاری سریع‌تر شده است. modern .NET به‌صورت منظم نسخهٔ جدید منتشر می‌کند و نسخه‌های LTS و STS چرخهٔ پشتیبانی مشخص دارند.

آیا Code قدیمی بدون تغییر اجرا می‌شود؟

همیشه نه. بسیاری از Class Libraryها و Codeهای معمول C# قابل‌استفادهٔ مجدد هستند، اما Migration یک Application کامل ممکن است نیاز به تغییر داشته باشد. باید موارد زیر بررسی شوند:

  • آیا NuGet Packageها نسخهٔ سازگار با modern .NET دارند؟
  • آیا Application از Technology قدیمی مانند ASP.NET Web Forms استفاده می‌کند؟
  • آیا API مورد استفاده فقط در Windows یا فقط در .NET Framework وجود دارد؟
  • آیا Configuration، Authentication، Hosting یا Deployment باید بازطراحی شود؟

برای مثال، یک پروژهٔ Web Forms را نمی‌توان فقط با تغییر Target Framework به .NET تبدیل کرد؛ چون Web Forms در ASP.NET Core وجود ندارد و UI باید بازنویسی یا جایگزین شود.

برای پروژهٔ جدید کدام را انتخاب کنیم؟

modern .NET را انتخاب کنید اگر:
  • پروژه جدید است.
  • Web API، Cloud Service، Microservice یا Container می‌سازید.
  • Cross-platform بودن، Performance و توسعهٔ آینده مهم است.
.NET Framework را نگه دارید اگر:
  • Application موجود پایدار است و Migration ارزش تجاری کافی ندارد.
  • به Web Forms یا Technology قدیمیِ پشتیبانی‌نشده وابسته‌اید.
  • Library یا Platform ضروری شما فقط .NET Framework را پشتیبانی می‌کند.

مثال واقعی

فرض کنید یک شرکت یک Application قدیمی Web Forms روی .NET Framework 4.8 دارد و می‌خواهد سرویس سفارش جدیدی بسازد. لازم نیست ابتدا کل سیستم قدیمی بازنویسی شود. تصمیم منطقی می‌تواند این باشد:

  • Application قدیمی فعلاً روی .NET Framework باقی بماند.
  • سرویس سفارش جدید با ASP.NET Core روی modern .NET ساخته شود.
  • دو بخش از طریق HTTP یا Messaging با هم ارتباط داشته باشند.
  • Migration بخش‌های قدیمی به‌تدریج و براساس ارزش و ریسک انجام شود.

این پاسخ نشان می‌دهد که در مصاحبه فقط تفاوت فنی را نمی‌دانید؛ بلکه هزینه، ریسک و نیاز کسب‌وکار را هم در تصمیم لحاظ می‌کنید.

جمع‌بندی نهایی برای مصاحبه

.NET Framework محصول اصلی و Windows-only است و بیشتر برای Applicationهای موجود و Technologyهای Legacy استفاده می‌شود. .NET Core بازطراحی Cross-platform و Open Source این Platform بود که از .NET 5 به بعد فقط .NET نامیده می‌شود. modern .NET برای پروژه‌های جدید انتخاب پیش‌فرض است، چون Deployment منعطف‌تر، Performance بهتر، پشتیبانی از Cloud و Container و توسعهٔ فعال دارد. بااین‌حال، نگه‌داشتن .NET Framework برای یک سیستم Legacy پایدار یا وابسته به Technologyهای قدیمی می‌تواند تصمیم کاملاً درستی باشد.
