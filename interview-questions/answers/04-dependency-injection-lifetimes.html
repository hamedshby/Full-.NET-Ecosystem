پاسخ کوتاه مناسب مصاحبه

Dependency Injection (DI) is a design pattern in which a class receives its dependencies from an external source rather than creating them itself. Instead of a class calling new on the services it needs, those services are "injected" — usually through the constructor — by a DI Container (the built-in IServiceCollection / IServiceProvider in ASP.NET Core).

When a service is registered, its lifetime determines how long a single instance of it lives and is reused: Singleton (one instance for the whole application), Scoped (one instance per HTTP request), and Transient (a new instance every time it's requested). Choosing the wrong lifetime is one of the most common sources of bugs in real-world ASP.NET Core applications.

Dependency Injection یعنی چه؟

در برنامه‌نویسی سنتی، یک کلاس معمولاً وابستگی‌های خودش را مستقیماً می‌سازد؛ مثلاً یک Controller با new OrderService() نمونه‌ای از سرویس موردنیازش را ایجاد می‌کند. این کار باعث می‌شود کلاس‌ها به پیاده‌سازی خاصی از یک سرویس Tightly Coupled شوند و Test نوشتن یا تغییر پیاده‌سازی در آینده سخت شود.

Dependency Injection این مشکل را با یک اصل ساده حل می‌کند: یک کلاس نباید مسئول ساختن وابستگی‌های خودش باشد؛ در عوض، آن وابستگی‌ها از بیرون (معمولاً از طریق Constructor) به آن داده می‌شوند. مسئولیت ساختن و مدیریت چرخهٔ حیات این وابستگی‌ها به یک DI Container سپرده می‌شود.

مدل ذهنی ساده

تصور کنید به‌جای اینکه یک آشپز خودش برود و مواد اولیه را از بازار بخرد (بسازد)، یک تأمین‌کننده (Container) مواد اولهٔ لازم را دقیقاً وقتی که لازم است برایش فراهم می‌کند. آشپز فقط می‌گوید «من به این مواد نیاز دارم» و نگران نحوهٔ تهیهٔ آن‌ها نیست. این دقیقاً همان کاری‌ست که Constructor Injection انجام می‌دهد: کلاس فقط وابستگی موردنیازش را در Constructor اعلام می‌کند، و Container مسئول تأمین آن است.

ثبت و تزریق در Program.cs

var builder = WebApplication.CreateBuilder(args);

// ثبت وابستگی‌ها همراه با Lifetime آن‌ها
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();

var app = builder.Build();
app.MapControllers();
app.Run();
public class OrderController : ControllerBase
{
    private readonly IOrderRepository _repository;
    private readonly IEmailSender _emailSender;

    // وابستگی‌ها از طریق Constructor تزریق می‌شوند
    public OrderController(IOrderRepository repository, IEmailSender emailSender)
    {
        _repository = repository;
        _emailSender = emailSender;
    }
}

در اینجا OrderController اصلاً نمی‌داند OrderRepository چگونه ساخته می‌شود یا چه وابستگی‌های دیگری دارد؛ فقط به Interface تکیه می‌کند و Container بقیهٔ کار را انجام می‌دهد.

سه نوع Lifetime

Lifetime چرخهٔ حیات نمونه مثال کاربرد مناسب
Singleton یک‌بار در کل عمر Application ساخته می‌شود و همان نمونه در همهٔ Requestها استفاده می‌شود Configuration، Caching، Logging Factory، سرویس‌های بدون State
Scoped یک نمونهٔ جدید به‌ازای هر HTTP Request ساخته می‌شود و در طول همان Request بازاستفاده می‌شود DbContext در Entity Framework، Repository ها، Unit of Work
Transient هر بار که درخواست شود، یک نمونهٔ کاملاً جدید ساخته می‌شود — حتی چند بار در یک Request سرویس‌های سبک و Stateless مثل Validator ها یا Mapper ها

چرا انتخاب Lifetime اهمیت حیاتی دارد؟

  • Captive Dependency: اگر یک سرویس Singleton به یک سرویس Scoped (مثل DbContext) وابسته باشد، آن DbContext در واقع برای همیشه زنده می‌ماند و بین Requestهای مختلف به اشتراک گذاشته می‌شود — این باعث بروز خطاهای عجیب و Data Corruption می‌شود.
  • DbContext همیشه Scoped است، چون Thread-Safe نیست و نباید بین چند Request هم‌زمان به اشتراک گذاشته شود؛ ثبت آن به‌صورت Singleton یک اشتباه رایج و خطرناک است.
  • Transient برای سرویس‌های سنگین مناسب نیست، چون هر بار Instance جدید ساخته می‌شود و اگر ساخت آن هزینه‌بر باشد (مثلاً باز کردن یک Connection)، عملکرد برنامه افت می‌کند.
  • Container به‌صورت خودکار جلوی برخی ترکیب‌های نادرست را می‌گیرد؛ برای مثال تزریق یک سرویس Scoped داخل یک سرویس Singleton، در حالت توسعه معمولاً با یک Exception واضح گزارش می‌شود.
نکتهٔ مصاحبه‌ای: یک سؤال بسیار رایج این است: «اگر یک سرویس Singleton به یک DbContext (که Scoped است) نیاز داشته باشد چه اتفاقی می‌افتد؟» جواب درست این است که این کار باعث Captive Dependency می‌شود و به‌جای تزریق مستقیم DbContext، باید از IServiceScopeFactory برای ساختن یک Scope جدید در زمان نیاز استفاده کرد.

مسیر یک درخواست از دید DI Container

  1. یک HTTP Request وارد Application می‌شود و ASP.NET Core یک Scope جدید برای آن باز می‌کند.
  2. وقتی Controller ساخته می‌شود، Container به Constructor آن نگاه می‌کند و می‌فهمد چه Interfaceهایی نیاز دارد.
  3. برای هر وابستگی، Container بر اساس Lifetime ثبت‌شده تصمیم می‌گیرد: نمونهٔ موجود Singleton را برگرداند، نمونهٔ Scoped مربوط به همین Request را بسازد یا بازاستفاده کند، یا یک نمونهٔ کاملاً جدید Transient بسازد.
  4. این فرآیند به‌صورت بازگشتی برای وابستگی‌های خودِ آن سرویس‌ها هم تکرار می‌شود (Constructor Injection زنجیره‌ای).
  5. پس از پایان Request، Scope بسته می‌شود و تمام نمونه‌های Scoped و Transient که Disposable بودند، به‌صورت خودکار Dispose می‌شوند.

مثال واقعی

فرض کنید یک Web API دارید که با پایگاه‌داده کار می‌کند و همچنین یک سرویس Cache در حافظه برای تنظیمات عمومی دارد. یک ثبت‌نام منطقی می‌تواند این باشد:

  • AddSingleton<IAppSettingsCache> چون تنظیمات در کل عمر Application ثابت و بدون وابستگی به Request است.
  • AddScoped<AppDbContext> و AddScoped<IOrderRepository> چون هر دو باید در طول یک Request با هم سازگار و یکسان باشند.
  • AddTransient<IOrderValidator> چون Validator سبک است، هیچ Stateای نگه نمی‌دارد و ساخت مکرر آن هزینه‌ای ندارد.

این نشان می‌دهد که انتخاب Lifetime فقط یک تنظیم فنی نیست؛ بلکه یک تصمیم معماری دربارهٔ این است که یک سرویس چه رابطه‌ای با Request و با سایر سرویس‌ها دارد.

جمع‌بندی نهایی برای مصاحبه

Dependency Injection الگویی است که در آن یک کلاس وابستگی‌های خود را از یک منبع بیرونی (DI Container) دریافت می‌کند، نه اینکه خودش آن‌ها را بسازد؛ این کار باعث کاهش Coupling و افزایش قابلیت Test و نگه‌داری کد می‌شود. در ASP.NET Core، هر سرویس با یکی از سه Lifetime ثبت می‌شود: Singleton برای یک نمونهٔ ثابت در کل عمر Application، Scoped برای یک نمونه به‌ازای هر Request (مانند DbContext)، و Transient برای ساخت یک نمونهٔ جدید در هر درخواست. درک درست تفاوت این سه و خطرات ترکیب نادرست آن‌ها (به‌ویژه Captive Dependency) یکی از مهم‌ترین مهارت‌های عملی توسعه‌دهندهٔ ASP.NET Core است.
