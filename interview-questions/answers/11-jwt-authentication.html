پاسخ کوتاه مناسب مصاحبه

JWT authentication usually starts when a user sends credentials such as username and password to a login endpoint. The server validates the credentials and, if they are correct, creates a signed JWT containing claims such as the user's ID, roles, and token expiration time.

The client stores the token and sends it with subsequent requests in the Authorization header using the Bearer scheme. On every protected request, the server validates the token's signature, expiration time, issuer, and audience. If the token is valid, ASP.NET Core creates a ClaimsPrincipal and the request is considered authenticated.

Authentication answers "Who is the user?", while authorization answers "What is this user allowed to do?". Authorization can then use claims, roles, or policies to decide whether the user can access the endpoint.

JWT Authentication چیست؟

در احراز هویت مبتنی بر JWT، بعد از اینکه کاربر با موفقیت وارد سیستم شد، سرور یک Token امضاشده برای او تولید می‌کند.

این Token معمولاً شامل اطلاعاتی دربارهٔ کاربر است؛ برای مثال شناسهٔ کاربر، Roleها، Permissionها یا اطلاعات دیگری که به آن‌ها Claim گفته می‌شود.

در درخواست‌های بعدی، Client دیگر لازم نیست Username و Password را دوباره ارسال کند. به‌جای آن، JWT را همراه Request می‌فرستد و Server اعتبار Token را بررسی می‌کند.

ساختار کلی JWT

هر JWT معمولاً از سه بخش تشکیل می‌شود: 

Header.Payload.Signature

این سه بخش با نقطه از یکدیگر جدا می‌شوند.

بخش وظیفه
Header مشخص‌کردن نوع Token و Algorithm امضا
Payload نگهداری Claimها و اطلاعات Token
Signature بررسی اینکه Token تغییر نکرده و توسط صادرکننده معتبر ساخته شده است

مرحله اول: Login Request

فرآیند معمولاً با ارسال Username و Password به Endpoint مربوط به Login شروع می‌شود. 

POST /api/auth/login

{
  "username": "hamed",
  "password": "mypassword"
}

سرور اطلاعات کاربر را بررسی می‌کند و Password دریافتی را با Password ذخیره‌شده مقایسه می‌کند.

نکتهٔ امنیتی: در Database نباید Password خام ذخیره شود. معمولاً Password به‌صورت Hash شده و با Salt مناسب نگهداری می‌شود.

مرحله دوم: بررسی Credentials

در Server معمولاً Service مربوط به Authentication کاربر را از Database پیدا می‌کند و اعتبار Username و Password را بررسی می‌کند. 

public async Task<User?> ValidateUserAsync(
    string username,
    string password)
{
    var user = await _userRepository.GetByUsernameAsync(username);

    if (user is null)
        return null;

    var isValid = _passwordHasher.Verify(
        password,
        user.PasswordHash);

    return isValid ? user : null;
}

اگر Credentials اشتباه باشند، معمولاً پاسخ 401 Unauthorized برگردانده می‌شود.

مرحله سوم: ساخت JWT

بعد از احراز هویت موفق، Server یک JWT ایجاد می‌کند.

داخل Payload معمولاً Claimهایی شبیه موارد زیر قرار می‌گیرند:

  • شناسهٔ کاربر با Claimهایی مانند sub یا NameIdentifier
  • نام کاربر
  • Roleهای کاربر
  • Permissionها
  • زمان صدور Token
  • زمان انقضای Token
  • Issuer و Audience
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
    new Claim(ClaimTypes.Name, user.Username),
    new Claim(ClaimTypes.Role, user.Role)
};

var key = new SymmetricSecurityKey(
    Encoding.UTF8.GetBytes(configuration["Jwt:Key"]!));

var credentials = new SigningCredentials(
    key,
    SecurityAlgorithms.HmacSha256);

var token = new JwtSecurityToken(
    issuer: configuration["Jwt:Issuer"],
    audience: configuration["Jwt:Audience"],
    claims: claims,
    expires: DateTime.UtcNow.AddMinutes(30),
    signingCredentials: credentials);

var accessToken =
    new JwtSecurityTokenHandler().WriteToken(token);

Signature چه کاری انجام می‌دهد؟

بخش Signature برای اطمینان از Integrity Token استفاده می‌شود.

یعنی Server هنگام دریافت Token می‌تواند بررسی کند که Payload یا Header از زمان صدور Token تغییر نکرده باشند.

برای مثال اگر یک مهاجم مقدار Role را از User به Admin تغییر دهد، Signature دیگر معتبر نخواهد بود و Server باید Token را Reject کند.

نکتهٔ مصاحبه‌ای: JWT معمولاً Signed است، نه Encrypted. بنابراین Payload را می‌توان Decode کرد و نباید اطلاعات حساس مثل Password یا اطلاعات محرمانه داخل آن قرار داد.

مرحله چهارم: ارسال Token به Client

بعد از ساخته‌شدن Token، Server آن را در Response به Client برمی‌گرداند. 

{
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "expiresIn": 1800
}

Client سپس Token را برای Requestهای بعدی نگهداری می‌کند.

مرحله پنجم: ارسال JWT در Requestهای بعدی

برای دسترسی به Endpointهای محافظت‌شده، Client معمولاً JWT را داخل Header زیر ارسال می‌کند: 

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

عبارت Bearer یعنی Client با داشتن این Token اجازه درخواست Authentication را دارد.

مرحله ششم: Authentication Middleware

در ASP.NET Core، Middleware مربوط به Authentication درخواست را بررسی می‌کند.

معمولاً Authentication با چنین تنظیماتی اضافه می‌شود: 

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters =
            new TokenValidationParameters
            {
                ValidateIssuer = true,
                ValidateAudience = true,
                ValidateLifetime = true,
                ValidateIssuerSigningKey = true,

                ValidIssuer =
                    builder.Configuration["Jwt:Issuer"],

                ValidAudience =
                    builder.Configuration["Jwt:Audience"],

                IssuerSigningKey =
                    new SymmetricSecurityKey(
                        Encoding.UTF8.GetBytes(
                            builder.Configuration["Jwt:Key"]!))
            };
    });

همچنین در Pipeline معمولاً Middlewareهای زیر وجود دارند: 

app.UseAuthentication();
app.UseAuthorization();

مرحله هفتم: Token Validation

وقتی JWT دریافت می‌شود، Server چند بررسی مهم روی آن انجام می‌دهد.

بررسی هدف
Signature اطمینان از اینکه Token تغییر نکرده است
Expiration بررسی اینکه Token منقضی نشده باشد
Issuer بررسی اینکه Token توسط Server معتبر صادر شده باشد
Audience بررسی اینکه Token برای این API صادر شده باشد
Signing Key اعتبارسنجی Signature با Key معتبر

اگر Token معتبر باشد چه اتفاقی می‌افتد؟

اگر JWT معتبر باشد، ASP.NET Core از Claimهای داخل Token یک ClaimsIdentity و سپس یک ClaimsPrincipal می‌سازد.

این Object داخل HttpContext.User قرار می‌گیرد. 

var userId =
    User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

var username = User.Identity?.Name;

var isAdmin = User.IsInRole("Admin");

بنابراین Controller یا Service می‌تواند اطلاعات کاربر فعلی را از Claimها بخواند.

Authentication و Authorization چه تفاوتی دارند؟

در یک سیستم JWT، Authentication و Authorization دو مسئولیت متفاوت دارند.

مفهوم سؤال اصلی
Authentication این کاربر چه کسی است؟
Authorization این کاربر اجازه انجام چه کاری را دارد؟

یعنی ابتدا JWT Authentication هویت کاربر را مشخص می‌کند و بعد Authorization بررسی می‌کند که آیا کاربر اجازه دسترسی به Resource موردنظر را دارد یا نه.

استفاده از [Authorize]

برای محافظت از Endpoint معمولاً از Attribute زیر استفاده می‌کنیم: 

[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile()
{
    return Ok();
}

در این حالت فقط Requestهایی که Authentication موفق داشته باشند اجازه اجرای Action را دارند.

Authorization بر اساس Role

می‌توانیم دسترسی را به Role خاص محدود کنیم: 

[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id)
{
    ...
}

در این مثال فقط کاربری که Claim مربوط به Role برابر Admin داشته باشد اجازه دسترسی دارد.

Authorization بر اساس Policy

برای سیستم‌های پیچیده‌تر بهتر است به‌جای وابستگی مستقیم به Roleها از Policy استفاده شود. 

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy(
        "CanDeleteUser",
        policy =>
        {
            policy.RequireClaim(
                "permission",
                "users.delete");
        });
});

سپس Policy روی Endpoint استفاده می‌شود: 

[Authorize(Policy = "CanDeleteUser")]
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id)
{
    ...
}

این روش برای Permission-based Authorization انعطاف بیشتری دارد.

401 و 403 چه تفاوتی دارند؟

این تفاوت یکی از سؤال‌های بسیار رایج مصاحبه است.

Status Code معنی
401 Unauthorized Authentication انجام نشده یا Token معتبر نیست
403 Forbidden کاربر Authentication شده ولی Permission لازم را ندارد
نکتهٔ مصاحبه‌ای: نام 401 Unauthorized ممکن است کمی گمراه‌کننده باشد؛ از نظر مفهومی این Status بیشتر مربوط به شکست Authentication است، در حالی که 403 Forbidden مربوط به شکست Authorization است.

JWT چرا Stateless محسوب می‌شود؟

یکی از مزایای مهم JWT این است که Server معمولاً برای اعتبارسنجی هر Request نیاز ندارد Session کاربر را در Memory یا Database نگهداری کند.

اطلاعات موردنیاز داخل خود Token قرار دارد و Server می‌تواند با بررسی Signature و Claimها اعتبار آن را تعیین کند.

به همین دلیل JWT برای سیستم‌های Distributed و Microservice مناسب است، چون چند Instance مختلف می‌توانند با Signing Key مشترک Token را Validate کنند.

اما Stateless بودن چه مشکلی ایجاد می‌کند؟

یکی از چالش‌های اصلی JWT این است که Token صادرشده تا زمان Expire شدن معمولاً معتبر باقی می‌ماند.

برای مثال اگر کاربر Logout کند یا دسترسی او در سیستم حذف شود، JWT موجود ممکن است تا زمان انقضا همچنان قابل استفاده باشد.

برای حل این مشکل می‌توان از روش‌هایی مانند موارد زیر استفاده کرد:

  • کوتاه نگه‌داشتن عمر Access Token
  • استفاده از Refresh Token
  • استفاده از Token Revocation List در سناریوهای خاص
  • استفاده از Token Version برای باطل‌کردن Tokenهای قبلی

Access Token و Refresh Token

در بسیاری از سیستم‌های واقعی، Access Token عمر کوتاهی دارد؛ برای مثال 15 یا 30 دقیقه.

در کنار آن یک Refresh Token با عمر طولانی‌تر صادر می‌شود.

وقتی Access Token منقضی شود، Client می‌تواند Refresh Token را برای دریافت Access Token جدید ارسال کند، بدون اینکه کاربر دوباره Username و Password وارد کند. 

POST /api/auth/refresh

{
  "refreshToken": "..."
}

چرا Access Token باید کوتاه‌عمر باشد؟

اگر Access Token دزدیده شود، مهاجم تا زمان انقضای Token می‌تواند از آن استفاده کند.

بنابراین هرچه Lifetime Token کوتاه‌تر باشد، بازهٔ زمانی سوءاستفاده از Token سرقت‌شده کمتر می‌شود.

Refresh Token معمولاً کنترل‌شده‌تر است و امکان Revocation آن در Server وجود دارد.

جریان کامل JWT Authentication

جریان End-to-End را می‌توان به این ترتیب خلاصه کرد:

  1. کاربر Username و Password را به Login Endpoint ارسال می‌کند.
  2. Server اطلاعات کاربر را از Database دریافت می‌کند.
  3. Password بررسی می‌شود.
  4. اگر Credentials معتبر باشند، Server یک JWT ایجاد می‌کند.
  5. Claimهایی مانند UserId، Role و Permission داخل Token قرار می‌گیرند.
  6. Token با Secret Key یا Private Key امضا می‌شود.
  7. Token به Client برگردانده می‌شود.
  8. Client Token را نگهداری می‌کند.
  9. در Requestهای بعدی Token داخل Header مربوط به Authorization ارسال می‌شود.
  10. Authentication Middleware Token را Extract می‌کند.
  11. Signature، Expiration، Issuer و Audience بررسی می‌شوند.
  12. اگر Token معتبر باشد، ClaimsPrincipal ساخته می‌شود.
  13. اطلاعات کاربر داخل HttpContext.User قرار می‌گیرد.
  14. Authorization بررسی می‌کند که کاربر اجازه دسترسی دارد یا نه.
  15. اگر دسترسی مجاز باشد، Endpoint اجرا می‌شود.

مدل ذهنی ساده

JWT را می‌توان شبیه یک کارت ورود دیجیتال تصور کرد.

ابتدا مسئول امنیت هویت شما را بررسی می‌کند و یک کارت امضاشده به شما می‌دهد. بعد از آن برای ورود به بخش‌های مختلف ساختمان، دیگر Password را نمی‌گویید؛ کارت را نشان می‌دهید.

سیستم ابتدا بررسی می‌کند کارت جعلی نباشد و منقضی نشده باشد. سپس اطلاعات روی کارت را می‌خواند تا مشخص کند شما چه کسی هستید و به چه بخش‌هایی اجازه ورود دارید.

اشتباهات رایج در JWT Authentication

  • قرار دادن Password یا اطلاعات محرمانه داخل Payload
  • استفاده از Secret Key ضعیف
  • نداشتن Expiration برای Token
  • استفاده از Access Token با Lifetime بسیار طولانی
  • غیرفعال‌کردن بررسی Issuer یا Audience بدون دلیل
  • نگهداری ناامن Token در Client
  • اعتماد کامل به Claimها بدون Validation صحیح Signature
  • نداشتن استراتژی مناسب برای Refresh Token و Revocation

نکات مهم مصاحبه‌ای

  • در JWT Authentication، Server ابتدا Credentials را بررسی کرده و سپس Token صادر می‌کند.
  • در Requestهای بعدی، Client معمولاً Token را با Bearer Scheme ارسال می‌کند.
  • در Server، فقط Decode کردن JWT کافی نیست و Signature باید Validate شود.
  • در ASP.NET Core، Authentication Middleware بعد از Validation یک ClaimsPrincipal می‌سازد.
  • در سیستم، Authentication هویت کاربر را مشخص می‌کند و Authorization مجوزهای او را بررسی می‌کند.
  • در حالت معمول، پاسخ 401 برای Authentication ناموفق و پاسخ 403 برای Authorization ناموفق استفاده می‌شود.
  • در طراحی امن، Access Token بهتر است عمر کوتاه داشته باشد و در صورت نیاز از Refresh Token استفاده شود.
  • در JWT، Payload رمزنگاری‌شده نیست و نباید اطلاعات حساس داخل آن قرار بگیرد.

جمع‌بندی نهایی برای مصاحبه

در JWT Authentication، کاربر ابتدا Credentials خود را برای Login ارسال می‌کند. Server بعد از بررسی آن‌ها یک JWT امضاشده شامل Claimهایی مانند UserId، Role و Expiration تولید می‌کند. Client این Token را دریافت کرده و در Requestهای بعدی آن را داخل Authorization Header با Bearer Scheme ارسال می‌کند.

در Server، Authentication Middleware ابتدا Signature، Expiration، Issuer و Audience را Validate می‌کند. اگر Token معتبر باشد، از Claimهای آن یک ClaimsPrincipal ساخته شده و در HttpContext.User قرار می‌گیرد. سپس Authorization بر اساس Role، Claim یا Policy تصمیم می‌گیرد که کاربر اجازه دسترسی به Endpoint را دارد یا نه.

بنابراین جریان اصلی به شکل Login → Validate Credentials → Generate JWT → Send Token → Validate Token → Build ClaimsPrincipal → Authorization است.
