پاسخ کوتاه مناسب مصاحبه

Authentication answers the question "Who are you?", while Authorization answers "What are you allowed to do?".

Authentication happens first. The system verifies the user's identity, for example by validating a username and password, cookie, API key, or JWT access token. If authentication succeeds, ASP.NET Core creates a ClaimsPrincipal representing the authenticated user.

Authorization happens after authentication. It uses information such as roles, claims, permissions, or policies to determine whether that user is allowed to access a specific endpoint or resource.

Authentication چیست؟

در Authentication هدف این است که سیستم مشخص کند کاربر واقعاً چه کسی است.

یعنی سؤال اصلی این است: 

Who are you?

برای مثال وقتی کاربر Username و Password وارد می‌کند، سیستم اطلاعات او را بررسی می‌کند. اگر اطلاعات صحیح باشد، هویت کاربر تأیید می‌شود.

در Web API، Authentication می‌تواند با روش‌های مختلف انجام شود؛ برای مثال:

  • Username و Password
  • JWT Bearer Token
  • Cookie Authentication
  • API Key
  • OAuth 2.0 و OpenID Connect
  • Client Certificate

Authorization چیست؟

بعد از اینکه هویت کاربر مشخص شد، Authorization بررسی می‌کند که این کاربر اجازه انجام چه کارهایی را دارد.

سؤال اصلی Authorization این است: 

What are you allowed to do?

برای مثال ممکن است دو کاربر هر دو Login کرده باشند، اما فقط یکی از آن‌ها Role مربوط به Admin داشته باشد.

در این حالت هر دو Authentication شده‌اند، ولی فقط کاربر Admin برای عملیات خاص Authorization می‌شود.

مثال ساده

فرض کنید یک سیستم بانکی داریم.

ابتدا کاربر وارد سیستم می‌شود: 

Username: hamed
Password: ********

سیستم Username و Password را بررسی می‌کند. این مرحله Authentication است.

سپس کاربر درخواست زیر را ارسال می‌کند: 

DELETE /api/users/100

سیستم بررسی می‌کند که آیا کاربر اجازه حذف User را دارد یا نه. این مرحله Authorization است.

مقایسهٔ کلی

ویژگی Authentication Authorization
سؤال اصلی کاربر چه کسی است؟ کاربر چه کاری اجازه دارد انجام دهد؟
زمان اجرا اول بعد از Authentication
هدف تأیید هویت بررسی مجوز دسترسی
نمونه Login یا Token Validation Role، Permission یا Policy Check
نتیجه Authenticated User Allow یا Deny

ترتیب Authentication و Authorization

Authentication همیشه باید قبل از Authorization انجام شود.

ترتیب کلی به شکل زیر است:

  1. Client یک Request ارسال می‌کند.
  2. سیستم Credential یا Token را دریافت می‌کند.
  3. Authentication اطلاعات هویتی را بررسی می‌کند.
  4. اگر معتبر باشد، User Identity ساخته می‌شود.
  5. Claimهای کاربر در دسترس قرار می‌گیرند.
  6. Authorization بررسی می‌کند آیا کاربر اجازه دسترسی دارد یا نه.
  7. اگر مجاز باشد، Endpoint اجرا می‌شود.
  8. اگر مجاز نباشد، Request رد می‌شود.

Authentication در ASP.NET Core

در ASP.NET Core ابتدا Authentication Scheme را مشخص می‌کنیم.

برای مثال در JWT Authentication: 

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters =
            new TokenValidationParameters
            {
                ValidateIssuer = true,
                ValidateAudience = true,
                ValidateLifetime = true,
                ValidateIssuerSigningKey = true,

                ValidIssuer =
                    builder.Configuration["Jwt:Issuer"],

                ValidAudience =
                    builder.Configuration["Jwt:Audience"],

                IssuerSigningKey =
                    new SymmetricSecurityKey(
                        Encoding.UTF8.GetBytes(
                            builder.Configuration["Jwt:Key"]!))
            };
    });

سپس Authentication Middleware به Pipeline اضافه می‌شود: 

app.UseAuthentication();

بعد از Authentication چه اتفاقی می‌افتد؟

اگر Authentication موفق باشد، ASP.NET Core اطلاعات User را داخل HttpContext.User قرار می‌دهد.

این Object معمولاً از نوع ClaimsPrincipal است. 

var user = HttpContext.User;

var username = User.Identity?.Name;

var userId =
    User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

از این لحظه سیستم هویت کاربر را می‌شناسد، اما هنوز باید مشخص شود که کاربر اجازه انجام Operation موردنظر را دارد یا نه.

ClaimsPrincipal چیست؟

در ASP.NET Core، بعد از Authentication معمولاً اطلاعات کاربر در قالب ClaimsPrincipal نمایش داده می‌شود.

این Object شامل Identity و Claimهای مربوط به User است.

برای مثال: 

UserId = 100
Username = hamed
Role = Admin
Permission = users.delete
Permission = users.read

Authorization می‌تواند از همین اطلاعات برای تصمیم‌گیری استفاده کند.

Authorization با [Authorize]

ساده‌ترین حالت Authorization در ASP.NET Core استفاده از [Authorize] است. 

[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile()
{
    return Ok();
}

در این حالت هر کاربری که Authentication شده باشد می‌تواند Endpoint را اجرا کند.

کاربر Anonymous اجازه دسترسی ندارد.

Role-based Authorization

می‌توانیم دسترسی را براساس Role محدود کنیم. 

[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id)
{
    ...
}

در این حالت تنها Authentication کافی نیست. کاربر باید علاوه بر Authentication، Role برابر Admin هم داشته باشد.

Claim-based Authorization

Authorization می‌تواند بر اساس Claim نیز انجام شود.

برای مثال ممکن است کاربر Claim زیر را داشته باشد: 

permission = payments.refund

سپس سیستم بررسی می‌کند که آیا این Claim برای Operation موردنظر وجود دارد یا نه.

Policy-based Authorization

در پروژه‌های بزرگ‌تر معمولاً استفاده از Policy انعطاف بیشتری نسبت به Role-based Authorization دارد. 

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy(
        "CanRefundPayment",
        policy =>
        {
            policy.RequireClaim(
                "permission",
                "payments.refund");
        });
});

سپس می‌توان Policy را روی Endpoint استفاده کرد: 

[Authorize(Policy = "CanRefundPayment")]
[HttpPost("{id}/refund")]
public IActionResult RefundPayment(long id)
{
    ...
}

این روش باعث می‌شود قوانین Authorization از Controller جدا شوند و قابلیت نگهداری سیستم بهتر شود.

Permission-based Authorization

در بسیاری از سیستم‌های Enterprise، استفاده مستقیم از Role کافی نیست.

برای مثال به‌جای اینکه بگوییم فقط Admin اجازه Refund دارد، می‌توانیم Permission دقیق‌تری تعریف کنیم: 

payments.read
payments.create
payments.refund
payments.cancel

سپس Roleهای مختلف می‌توانند مجموعه متفاوتی از Permissionها داشته باشند.

این رویکرد انعطاف بیشتری نسبت به Hard-code کردن Role داخل Controller دارد.

Authentication Failure چه Status Code دارد؟

اگر User Authentication نشده باشد یا Token معتبر نباشد، معمولاً پاسخ زیر برگردانده می‌شود: 

401 Unauthorized

برای مثال:

  • Token ارسال نشده است.
  • Token منقضی شده است.
  • Signature معتبر نیست.
  • Credential اشتباه است.

Authorization Failure چه Status Code دارد؟

اگر User Authentication شده باشد ولی اجازه دسترسی به Resource را نداشته باشد، معمولاً پاسخ زیر برگردانده می‌شود: 

403 Forbidden

یعنی سیستم می‌داند User چه کسی است، ولی User مجوز لازم برای Operation موردنظر را ندارد.

تفاوت 401 و 403

Status Code وضعیت معنی
401 Unauthorized Authentication Failure User به‌درستی احراز هویت نشده است
403 Forbidden Authorization Failure User احراز هویت شده ولی Permission لازم را ندارد
نکتهٔ مصاحبه‌ای: اگر JWT نامعتبر یا Expired باشد معمولاً 401 دریافت می‌کنیم؛ اما اگر JWT معتبر باشد و User Permission لازم را نداشته باشد معمولاً 403 دریافت می‌کنیم.

Middleware Order

در ASP.NET Core ترتیب Authentication و Authorization Middleware اهمیت دارد. 

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

ابتدا Authentication باید User را شناسایی کند و HttpContext.User را بسازد.

سپس Authorization از اطلاعات همان User برای بررسی Permission استفاده می‌کند.

نکتهٔ مهم: اگر ترتیب این دو Middleware اشتباه باشد، Authorization اطلاعات Authentication موردنیاز خود را در اختیار نخواهد داشت.

مثال End-to-End با JWT

فرض کنید User ابتدا Login می‌کند: 

POST /api/auth/login

{
  "username": "hamed",
  "password": "..."
}

اگر Credential معتبر باشد، Server یک JWT صادر می‌کند: 

{
  "accessToken": "eyJhbGciOiJIUzI1NiIs..."
}

Client در Request بعدی Token را ارسال می‌کند: 

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Authentication Middleware ابتدا Token را Validate می‌کند.

سپس ClaimsPrincipal ساخته می‌شود: 

UserId = 100
Role = PaymentOperator
Permission = payments.read
Permission = payments.refund

بعد Authorization بررسی می‌کند که آیا Endpoint موردنظر به Permission payments.refund نیاز دارد یا نه.

اگر User این Permission را داشته باشد، Request اجازه اجرا می‌گیرد.

آیا Authentication به معنی Authorization است؟

خیر. این یکی از اشتباهات رایج است.

Authentication فقط ثابت می‌کند User چه کسی است. این به این معنی نیست که User اجازه انجام همه عملیات سیستم را دارد.

برای مثال یک Customer و یک Admin هر دو می‌توانند Authentication شوند، ولی سطح دسترسی آن‌ها متفاوت است.

آیا Authorization بدون Authentication ممکن است؟

در بیشتر Endpointهای محافظت‌شده، ابتدا باید User Authentication شود تا بتوانیم Authorization را بر اساس Identity او انجام دهیم.

اما بعضی Ruleهای دسترسی می‌توانند برای Anonymous User نیز تعریف شوند. برای مثال یک Endpoint عمومی ممکن است با [AllowAnonymous] قابل دسترسی باشد. 

[AllowAnonymous]
[HttpPost("login")]
public IActionResult Login(LoginRequest request)
{
    ...
}

Resource-based Authorization چیست؟

گاهی Permission فقط به Role یا Claim وابسته نیست و باید خود Resource هم بررسی شود.

برای مثال ممکن است User فقط اجازه ویرایش Transactionهایی را داشته باشد که متعلق به Client خودش هستند. 

if (transaction.ClientId != currentUser.ClientId)
{
    return Forbid();
}

این نوع بررسی را می‌توان با Resource-based Authorization و IAuthorizationService نیز پیاده‌سازی کرد.

Authentication و Authorization در Microservices

در معماری Microservices معمولاً Authentication در Identity Provider یا Authentication Service انجام می‌شود و یک Access Token صادر می‌شود.

سپس Serviceهای مختلف Token را Validate کرده و بر اساس Claimها و Permissionها Authorization انجام می‌دهند.

برای مثال: 

Client
   |
   | Login
   v
Identity Service
   |
   | Access Token
   v
Client
   |
   | Bearer Token
   v
API Gateway
   |
   v
Payment Service
   |
   v
Authorization

در این معماری مهم است که تمام Serviceها Issuer و Signing Key معتبر را بشناسند یا از یک Identity Provider قابل اعتماد استفاده کنند.

مدل ذهنی ساده

یک ساختمان اداری را تصور کنید.

در ورودی ساختمان، کارت شناسایی شما بررسی می‌شود تا مشخص شود چه کسی هستید. این مرحله Authentication است.

بعد از ورود، برای واردشدن به اتاق سرور کارت شما دوباره بررسی می‌شود تا مشخص شود آیا اجازه ورود به آن اتاق را دارید یا نه. این مرحله Authorization است.

بنابراین ممکن است اجازه ورود به ساختمان را داشته باشید، ولی اجازه ورود به تمام اتاق‌ها را نداشته باشید.

اشتباهات رایج

  • یکی دانستن Authentication و Authorization
  • بررسی Permission قبل از مشخص‌شدن Identity کاربر
  • استفاده از 401 به‌جای 403 برای User احراز هویت‌شده
  • Hard-code کردن Roleها در تمام Controllerها
  • نداشتن Policy یا Permission مناسب برای سیستم‌های بزرگ
  • اعتماد به اطلاعات ارسال‌شده از Client برای Authorization
  • اشتباه قراردادن ترتیب UseAuthentication و UseAuthorization

نکات مهم مصاحبه‌ای

  • در Authentication مشخص می‌کنیم User چه کسی است.
  • در Authorization مشخص می‌کنیم User چه کاری اجازه دارد انجام دهد.
  • Authentication قبل از Authorization انجام می‌شود.
  • بعد از Authentication موفق، ASP.NET Core معمولاً یک ClaimsPrincipal داخل HttpContext.User قرار می‌دهد.
  • Authorization می‌تواند بر اساس Role، Claim، Permission، Policy یا Resource انجام شود.
  • برای Authentication ناموفق معمولاً پاسخ 401 استفاده می‌شود.
  • برای User احراز هویت‌شده‌ای که Permission لازم ندارد معمولاً پاسخ 403 استفاده می‌شود.
  • در Pipeline باید UseAuthentication قبل از UseAuthorization قرار بگیرد.

جمع‌بندی نهایی برای مصاحبه

در ASP.NET Core، Authentication مشخص می‌کند User چه کسی است، در حالی که Authorization مشخص می‌کند آن User چه کاری اجازه دارد انجام دهد.

ابتدا Authentication با بررسی Credential، Cookie یا Token انجام می‌شود. اگر موفق باشد، Framework یک ClaimsPrincipal ساخته و آن را در HttpContext.User قرار می‌دهد.

سپس Authorization با استفاده از Role، Claim، Permission، Policy یا خود Resource تصمیم می‌گیرد که User اجازه دسترسی به Endpoint موردنظر را دارد یا نه.

بنابراین جریان کلی به شکل Request → Authentication → Identity / ClaimsPrincipal → Authorization → Endpoint است.
