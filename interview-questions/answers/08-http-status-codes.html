پاسخ کوتاه مناسب مصاحبه

In a typical ASP.NET Core Web API, status codes fall into a small, predictable set. For success: 200 OK for a normal successful response, 201 Created after creating a resource, and 204 No Content when the operation succeeds but there is nothing to return (e.g. a delete or update). For client errors: 400 Bad Request for invalid input, 401 Unauthorized when the caller isn't authenticated, 403 Forbidden when they're authenticated but not allowed, 404 Not Found when the resource doesn't exist, and 409 Conflict for state conflicts such as duplicates or concurrency issues.

For server errors, 500 Internal Server Error covers unexpected failures. The key interview point is choosing the status code that matches the semantics of what happened, not just returning 200 or 500 for everything.

چرا انتخاب درست Status Code مهم است؟

Status Code، اولین چیزی است که Client (چه یک Frontend، چه یک Service دیگر) برای تصمیم‌گیری دربارهٔ نحوهٔ واکنش به یک Response نگاه می‌کند. اگر همیشه 200 OK برگردانده شود و جزئیات خطا فقط در Body باشد، Client مجبور می‌شود منطق پردازش خطا را به‌صورت دستی و شکننده پیاده‌سازی کند. انتخاب درست Status Code یعنی معنای HTTP را به‌درستی حمل کردن، نه فقط برگرداندن یک عدد.

۲xx — موفقیت

کد کاربرد مثال در ASP.NET Core
200 OK درخواست با موفقیت پردازش شده و Body پاسخ برگردانده می‌شود return Ok(dto);
201 Created یک Resource جدید ساخته شده؛ معمولاً همراه با Header Location return CreatedAtAction(nameof(GetById), new { id = dto.Id }, dto);
202 Accepted درخواست پذیرفته شده اما پردازش آن Async/در پس‌زمینه است صف‌بندی یک Background Job و بازگرداندن شناسهٔ پیگیری
204 No Content عملیات موفق بوده اما چیزی برای برگرداندن در Body نیست return NoContent(); برای Delete یا Update

۴xx — خطای سمت Client

کد کاربرد مثال در ASP.NET Core
400 Bad Request ورودی نامعتبر است — خطای Validation، فرمت اشتباه، پارامتر ناقص return BadRequest(ModelState);
401 Unauthorized هویت کاربر مشخص نیست یا Token نامعتبر/منقضی است return Unauthorized(); یا نتیجهٔ خودکار Middleware Authentication
403 Forbidden هویت کاربر مشخص است، اما اجازهٔ دسترسی به این Resource را ندارد return Forbid();
404 Not Found Resource با شناسهٔ داده‌شده اصلاً وجود ندارد return NotFound();
405 Method Not Allowed Route وجود دارد اما این HTTP Method برای آن پشتیبانی نمی‌شود معمولاً به‌صورت خودکار توسط Routing مدیریت می‌شود
409 Conflict درخواست با وضعیت فعلی داده در تناقض است — رکورد تکراری، Concurrency Conflict return Conflict("Email already exists.");
422 Unprocessable Entity ساختار درخواست درست است اما از نظر معنایی/Business Rule نامعتبر است return UnprocessableEntity(errors);
429 Too Many Requests از حد مجاز Rate Limiting عبور شده است Middleware مربوط به Rate Limiting در .NET

۵xx — خطای سمت Server

کد کاربرد
500 Internal Server Error خطای پیش‌بینی‌نشده در Server — معمولاً توسط UseExceptionHandler گرفته و برگردانده می‌شود
502 Bad Gateway Server به‌عنوان Proxy/Gateway، پاسخ نامعتبری از یک Upstream Service گرفته است
503 Service Unavailable سرویس موقتاً در دسترس نیست — مثلاً در حال Restart یا زیر بار زیاد
نکتهٔ مصاحبه‌ای: ۵xx یعنی «مشکل از سمت ماست»، در حالی که ۴xx یعنی «مشکل از سمت درخواست شماست». این تفاوت معنایی، اولین چیزی است که مصاحبه‌کننده‌ها معمولاً چک می‌کنند.

401 در برابر 403 — تفاوت پرتکرار در مصاحبه

401 Unauthorized یعنی سیستم نمی‌داند شما کی هستید — یا اصلاً Token نفرستاده‌اید، یا Token نامعتبر/منقضی است. 403 Forbidden یعنی سیستم دقیقاً می‌داند شما کی هستید، اما طبق قوانین Authorization، اجازهٔ انجام این عملیات را ندارید. اشتباه گرفتن این دو یکی از رایج‌ترین اشتباهات عملی است.

مثال واقعی در یک Controller

[HttpPost]
public async Task<IActionResult> CreateOrder(CreateOrderDto dto)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState);              // 400

    var customer = await _customerRepo.GetByIdAsync(dto.CustomerId);
    if (customer is null)
        return NotFound($"Customer {dto.CustomerId} not found."); // 404

    var duplicate = await _orderRepo.ExistsAsync(dto.OrderNumber);
    if (duplicate)
        return Conflict("Order number already exists.");          // 409

    var order = await _orderService.CreateAsync(dto);
    return CreatedAtAction(nameof(GetById), new { id = order.Id }, order); // 201
}

در این مثال، هر مسیر خروجی متناظر با معنای واقعی اتفاقی است که افتاده — نه یک عدد ثابت برای همهٔ حالت‌ها.

جمع‌بندی نهایی برای مصاحبه

در عمل، اکثر Web APIها به یک زیرمجموعهٔ کوچک از Status Codeها نیاز دارند: 200، 201 و 204 برای موفقیت؛ 400، 401، 403، 404 و 409 برای خطاهای رایج سمت Client؛ و 500 برای خطاهای پیش‌بینی‌نشدهٔ سمت Server. نکتهٔ کلیدی این است که Status Code باید معنای دقیق اتفاق افتاده را منتقل کند تا Clientها بتوانند بدون حدس زدن، رفتار درستی داشته باشند.
