# سند بازطراحی کیفیت محتوای فصل مبانی C#

تاریخ: ۱۴۰۵/۰۵/۲۱ (۱۲ اوت ۲۰۲۶)

## هدف

بازنویسی هر ۳۰ پاسخ فصل «مبانی C#» به‌عنوان یک محتوای آموزشی مستقل، دقیق و قابل‌فهم. پاسخ‌ها باید برای یادگیری واقعی و آمادگی مصاحبه مناسب باشند، نه مجموعه‌ای از تعریف‌های کوتاه، اصطلاحات تعریف‌نشده و متن‌های تکراری.

## ریشهٔ مشکل فعلی

- بعضی پاسخ‌ها قبل از ساختن مدل ذهنی ساده، مفاهیم پیشرفته را وارد می‌کنند.
- بخش «توضیح کامل» کوتاه است و چرایی رفتار را مرحله‌به‌مرحله توضیح نمی‌دهد.
- generator از یک جمله برای چند بخش استفاده می‌کند و محتوای تکراری می‌سازد.
- «نکات کلیدی» به‌صورت ماشینی از توضیح کوتاه استخراج می‌شود و ارزش آموزشی مستقلی ندارد.
- مثال‌ها خروجی، وضعیت حافظه یا اثر تغییرات را همیشه توضیح نمی‌دهند.
- سطح مقدماتی، متوسط و ارشد در عمق واقعی پاسخ‌ها تفاوت کافی ندارد.

## اصل آموزشی

هر پاسخ باید از «یک مثال ساده و قابل مشاهده» آغاز شود، سپس مدل ذهنی را بسازد و در پایان به جزئیات Compiler، CLR، Performance یا طراحی API برسد. اصطلاح فنی پیش از تعریف‌شدن نباید مبنای توضیح قرار گیرد.

برای مثال، پاسخ `Value Type` و `Reference Type` ابتدا رفتار assignment را با دو متغیر نشان می‌دهد؛ موضوع `Stack` و `Heap` فقط پس از فهم رفتار کپی و در بخشی جداگانه مطرح می‌شود.

## قانون اصطلاحات

تمام محتوا تابع `RTK.md` است:

- نام رسمی concepts، keywords، types، APIs و runtime components ترجمه نمی‌شود.
- توضیح پیرامون آن‌ها فارسی، طبیعی و آموزشی می‌ماند.
- casing رسمی رعایت می‌شود.
- اصطلاحات انگلیسی در HTML با `code` یا `bdi` از متن RTL جدا می‌شوند.

## ساختار جدید دادهٔ هر سؤال

هر entry در `tools/generate-course.js` باید فیلدهای مستقل زیر داشته باشد؛ هیچ بخش محتوایی از بخش دیگر به‌صورت خودکار استخراج نمی‌شود:

- `slug`, `topic`, `level`, `title`
- `shortAnswer`: پاسخ مستقیم ۲ تا ۵ جمله‌ای
- `mentalModel`: تعریف ساده و مدل ذهنی پایه
- `deepDive`: توضیح مرحله‌به‌مرحلهٔ رفتار و چرایی آن
- `examples`: یک یا چند مثال با عنوان، کد و توضیح خروجی/رفتار
- `comparison`: ردیف‌های مقایسه، فقط اگر برای موضوع مفید باشد
- `keyPoints`: نکات مستقل و اختصاصی همان سؤال
- `pitfalls`: اشتباهات واقعی و توضیح دلیل اشتباه‌بودن
- `realWorld`: سناریوی واقعی و دلیل انتخاب
- `interviewAnswer`: پاسخ پیشنهادی ۳۰ تا ۶۰ ثانیه‌ای
- `furtherDetails`: جزئیات Compiler/CLR/Performance متناسب با سطح

## استاندارد مثال کد

- کد باید حداقل context لازم برای فهم را داشته باشد.
- type یا method استفاده‌شده بدون تعریف رها نمی‌شود، مگر عضو شناخته‌شدهٔ BCL باشد.
- برای مثال‌های رفتاری، مقدار نهایی یا output زیر کد توضیح داده می‌شود.
- کامنت فقط نکتهٔ مهم را بیان می‌کند و جای توضیح متن را نمی‌گیرد.
- مثال‌های مقایسه‌ای باید یک سناریوی واحد را در دو حالت نشان دهند.
- کدهای غیرقابل اجرا که صرفاً pseudo-code هستند صریحاً با عنوان «نمونهٔ مفهومی» مشخص می‌شوند.
- مثال‌ها نباید میان سؤال‌ها با تغییر نام متغیر تکرار شوند.

## بازنویسی سؤال اول

پاسخ `Value Type` و `Reference Type` باید مشخصاً این موارد را پوشش دهد:

1. متغیر یک `Value Type` خود value را نگه می‌دارد.
2. assignment یک کپی مستقل ایجاد می‌کند.
3. متغیر یک `Reference Type` یک reference به object را نگه می‌دارد.
4. assignment خود object را کپی نمی‌کند؛ reference کپی می‌شود.
5. مثال `int` مقدار `a` و `b` را قبل و بعد از تغییر نشان می‌دهد.
6. مثال `Person` نشان می‌دهد دو متغیر به یک object اشاره می‌کنند.
7. یک نمودار متنی کوچک وضعیت متغیرها را نمایش می‌دهد.
8. تفاوت با ارسال آرگومان به method توضیح داده می‌شود؛ خود متغیر به‌صورت پیش‌فرض by value ارسال می‌شود.
9. `class`، `struct`، `enum` و built-in types دسته‌بندی می‌شوند.
10. `Stack` و `Heap` در یک بخش «این تفاوت چه چیزی نیست؟» توضیح داده می‌شوند.
11. ادعای نادرست «Value Type همیشه روی Stack است» صریحاً اصلاح می‌شود.
12. انتخاب type در طراحی دامنه با identity، اندازه و mutation مرتبط می‌شود.

## قانون دائمی کیفیت در RTK.md

یک بخش «کیفیت محتوای آموزشی» اضافه می‌شود که الزام می‌کند:

- پاسخ از ساده به عمیق حرکت کند.
- هر اصطلاح پیش از اتکا تعریف شود.
- هر ادعای اصلی مثال یا استدلال داشته باشد.
- کد و رفتار آن هر دو توضیح داده شوند.
- بخش‌های صفحه متن تکراری نداشته باشند.
- generator از استخراج ماشینی نکات از یک پاراگراف استفاده نکند.
- کیفیت با تعداد کلمات سنجیده نشود؛ کامل‌بودن مدل ذهنی و پاسخ به «چرا» معیار باشد.
- هنگام درخواست اصلاح یک پاسخ، همان الگوی کیفیت در کل محتوای هم‌خانواده بررسی شود.

## کنترل خودکار کیفیت

آزمون‌های جدید یا توسعه‌یافته باید موارد زیر را بررسی کنند:

- وجود فیلدهای مستقل محتوایی برای هر ۳۰ سؤال
- نبود پاراگراف یکسان در بخش‌های مختلف یک صفحه
- نبود متن boilerplate مشترک در تعداد زیادی از صفحات
- وجود حداقل یک code example و توضیح رفتار آن
- وجود مدل ذهنی، deep dive، pitfalls، real-world و interview answer
- حداقل دو pitfall واقعی برای هر سؤال
- یکتایی عنوان، short answer و interview answer
- رعایت واژه‌نامهٔ `RTK.md`
- سالم‌بودن تمام لینک‌ها پس از بازتولید

آزمون‌ها جای بازبینی انسانی کیفیت را نمی‌گیرند؛ فقط از بازگشت خطاهای ساختاری جلوگیری می‌کنند.

## بازبینی انسانی

برای هر سؤال checklist زیر اجرا می‌شود:

- آیا فردی که topic را نمی‌داند می‌تواند پاراگراف اول را بفهمد؟
- آیا هر اصطلاح جدید تعریف شده است؟
- آیا مثال واقعاً ادعای متن را نشان می‌دهد؟
- آیا رفتار نهایی کد توضیح داده شده است؟
- آیا بخش پیشرفته پس از مبانی آمده است؟
- آیا پاسخ کوتاه برای مصاحبه قابل استفاده است؟
- آیا متن با پاسخ‌های دیگر تکرار نشده است؟
- آیا ادعای مطلق، گمراه‌کننده یا وابسته به implementation وجود دارد؟
